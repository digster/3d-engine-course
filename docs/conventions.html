Conventions

The handful of arbitrary-but-binding choices this course makes about direction, order, and range. Convention mismatches are the single largest source of silent rendering bugs — a wrong choice does not crash, it just quietly draws the mirror image.

How to use this page

Everything here is decided, not discovered — except the parts marked fixed by SDL_GPU, which are facts we must obey. Where a choice was genuinely open, this page says why we chose as we did, because a convention you understand is one you can debug.

1Why conventions deserve their own page

Most graphics bugs announce themselves. You get a crash, a validation error, a black screen. Convention bugs do not. They produce a picture that is almost right — mirrored, upside-down, inside-out, or depth-sorted backwards — and every individual piece of code looks correct in isolation. The bug lives in the disagreement between two files, not inside either one.

The cure is to decide once, write it down, and never deviate. That is this page. If a lesson ever contradicts it, the lesson is wrong.

2World space: right-handed, Y-up, −Z forward

Point your right hand's index finger along +x and your middle finger along +y; your thumb now points along +z, out of the screen toward you. That is a right-handed system, and it is what this course uses everywhere in model, world, and view space. Figure 1 is the picture to keep in your head.

Worked example — proving the handedness by cross product

The cross product of the first two basis vectors must give the third. With x = (1, 0, 0) and y = (0, 1, 0):

  • (x × y).x = x.y·y.z − x.z·y.y = 0·0 − 0·1 = 0
  • (x × y).y = x.z·y.x − x.x·y.z = 0·0 − 1·0 = 0
  • (x × y).z = x.x·y.y − x.y·y.x = 1·1 − 0·0 = 1

So x × y = (0, 0, 1) = +z. Right-handed, confirmed. In a left-handed system the same arithmetic would have to yield −z, which is why you cannot mix the two without noticing — eventually.

Why right-handed, when SDL_GPU's clip space is left-handed?

This is a fair objection and worth answering directly. Two reasons decided it:

  • glTF 2.0 is right-handed, Y-up. Module 6 loads glTF scenes. Matching it means zero axis conversion on import — and axis-conversion code is a permanent tax you pay on every asset, forever.
  • Every reference this course sends you to is right-handed. Scratchapixel, Real-Time Rendering, LearnOpenGL. When you read a derivation there and type it here, it should just work.

The cost is one sign flip inside the projection matrix — a single line, written once, in §5. That is a bargain compared to converting every mesh you ever load.

3The space chain

A vertex makes six stops between the model file and the pixel. Every renderer in this course — the CPU rasterizer in Modules 2–3 and the SDL_GPU renderer from Module 4 — walks exactly this chain, in this order. Figure 2 names each hop and the matrix responsible.

Written as one expression, with our column-vector convention (§6), a vertex reaches clip space like this:

\[ \mathbf{v}_{clip} = P \cdot V \cdot M \cdot \mathbf{v}_{model} \] v_clip = P * V * M * v_model

Read it right to left — the model matrix touches the vertex first, the projection matrix last. That right-to-left reading is a direct consequence of using column vectors; if you ever see an engine write v * M * V * P, it uses row vectors, and its matrices are the transposes of ours.

Naming the hops, and the model matrix's internal order

In prose and diagrams we abbreviate the three matrices M, V, P. In code, name each one a_from_b — the space it produces, then the space it consumes: world_from_model, view_from_world, clip_from_view. Then a product's adjacent labels must match (view_from_world · world_from_model), so a wrong-ordered composition is a spelling mistake you can see before running anything. This convention is introduced and justified in Lesson 2.8 §3.1.

The model matrix itself is always M = T · R · S — scale first, rotate, translate last. The order is derived (Lesson 2.8 §3.2), not conventional: it is the only order that scales an object along its own axes and rotates it about its own centre. Its columns are the object's own axes in world space, scaled by its size, with the position in column 3.

The view matrix (the V above) is view_from_world = inverse(world_from_camera) — a camera is an object with a placement, and looking through it is undoing that placement (Lesson 2.9). Because a camera has no scale, its placement is rigid and the inverse is free: affine(transpose(R), −transpose(R)·eye), no general 4×4 inversion. Transposing the orthonormal rotation puts the camera's right, up, backward axes into the view matrix's rows — the fastest way to read a camera off its matrix. The camera looks down its own −z, so its backward (+z) axis is eye − target, consistent with the world-space −Z-forward convention above.

The projection matrix (the P above) is perspective(fovy, aspect, near, far) (Lesson 2.10). It carries view space to clip space, and its defining trick is that it writes −z — the depth — into w, so the later perspective divide (÷w) shrinks distant things. This is where w stops being 1, where clip space and NDC become distinct (before and after the divide), and — per §5 below — where the right-handed → left-handed handedness flip happens. It targets SDL_GPU's clip space exactly: x, y in [−1,1] and depth in [0,1] (§4), so the software rasterizer and the Module 4 GPU renderer share one projection.

The viewport transform is the final hop, NDC → framebuffer pixels (Lesson 2.11), and it is an engine::viewport mirroring SDL_GPUViewport (x, y, w, h, min_depth, max_depth). It is three independent affine maps — and it is where the +y flip lives. NDC's +y points up; the framebuffer counts rows downward from the top (§4's "+Y up in NDC, +Y down in viewport" note), so y — and only y — reverses. That reversal belongs in exactly one function, viewport::to_screen; a scene rendered upside down is almost always this sign, missing or applied twice.

4Clip space and NDC — fixed by SDL_GPU

Not our choice

Everything in this section is dictated by SDL_GPU and verified against the SDL wiki and headers — see §10. We do not get a vote. Getting this wrong produces an upside-down or depth-inverted image, silently.

After the perspective divide, a vertex lands in normalized device coordinates. SDL_GPU defines that space precisely, and Figure 3 draws it:

  • x runs from −1 (left) to +1 (right).
  • y runs from −1 (bottom) to +1 (top) — +Y is up.
  • z runs from 0 (near plane) to 1 (far plane).

+Y is up in NDC, but +Y is down in viewport and texture space

This looks like a contradiction and is not. They are different spaces with different jobs:

SpaceOrigin+Y directionWhat it addresses
NDCcentreupvertex shader output
Viewporttop-leftdownpixels
Texture (UV)top-leftdowntexels

NDC is the geometric output of your maths. Viewport and UV space are addressing schemes for rectangular grids in memory, and memory rows run top to bottom — hence +Y down. The viewport transform is what bridges them, and the Y flip lives there.

Worked example — NDC to screen, with real numbers

For an 800 × 600 viewport, the transform is:

  • x_screen = (x_ndc * 0.5 + 0.5) * 800
  • y_screen = (0.5 − y_ndc * 0.5) * 600  ← note the minus: this is the flip

Push three points through:

  • Centre (0, 0) → x = (0 + 0.5)·800 = 400, y = (0.5 − 0)·600 = 300 → (400, 300). The middle of the screen. ✓
  • NDC top-left (−1, +1) → x = (−0.5 + 0.5)·800 = 0, y = (0.5 − 0.5)·600 = 0 → (0, 0). The top-left pixel. ✓
  • NDC bottom-right (+1, −1) → x = (0.5 + 0.5)·800 = 800, y = (0.5 + 0.5)·600 = 600 → (800, 600). The bottom-right corner. ✓

NDC's top (y = +1) maps to screen row 0. That is the whole content of "+Y up becomes +Y down", and it costs exactly one sign.

You do not flip Y in your shaders

Vulkan's native NDC has +Y down, unlike D3D12 and Metal. SDL_GPU papers over this: per the SDL wiki, if the backend differs from this convention, SDL converts the coordinate system behind the scenes, so you do not need to perform any coordinate flipping logic in your shaders. Write your shaders once, against the convention above, and let SDL handle the backend. This is one of SDL_GPU's genuinely nice guarantees.

5Where the handedness flip happens

Our world is right-handed. SDL_GPU's clip space is left-handed. Something must reconcile them, and that something is the projection matrix — as Figure 2 marks. This is normal and correct; it is one of the projection matrix's jobs, and hiding it only makes the inevitable "my scene is mirrored" bug harder to diagnose.

With vertical field of view fovY, aspect ratio a = width/height, and near/far planes n and f, let t = 1/tan(fovY/2) and R = f/(n−f). Our projection matrix is:

\[ P = \begin{bmatrix} t/a & 0 & 0 & 0 \\ 0 & t & 0 & 0 \\ 0 & 0 & R & R\,n \\ 0 & 0 & -1 & 0 \end{bmatrix} \] row0 = [t/a, 0, 0, 0]; row1 = [0, t, 0, 0]; row2 = [0, 0, R, R*n]; row3 = [0, 0, -1, 0] where t = 1/tan(fovY/2), R = f/(n-f)

The flip is the −1 in the bottom row. It sets w_clip = −z_view. In right-handed view space the camera looks down −z, so anything in front of the camera has a negative z_view, and negating it yields a positive w — which is what the perspective divide requires. Depth then increases with distance, and increasing-depth-into-the-screen is exactly what left-handed means.

Expect this matrix to differ from the tutorials

Most online derivations (LearnOpenGL especially) target OpenGL's z ∈ [−1, 1] and produce a different third row. Ours targets z ∈ [0, 1] — the D3D-style matrix — because that is what SDL_GPU requires. The t/a and t terms are identical; only the depth row differs. We derive all of this from similar triangles in Module 2, so it will not be a matrix you take on faith.

Worked example — verifying the near and far planes map to 0 and 1

Take n = 0.1 and f = 100. Then R = f/(n−f) = 100/(0.1−100) = 100/(−99.9) ≈ −1.001001, and R·n ≈ −0.1001001.

A point on the near plane sits at z_view = −0.1:

  • z_clip = R·z_view + R·n = (−1.001001)(−0.1) + (−0.1001001) = 0.1001001 − 0.1001001 = 0
  • w_clip = −z_view = 0.1
  • z_ndc = z_clip / w_clip = 0 / 0.1 = 0 ✓ — the near plane maps to 0.

A point on the far plane sits at z_view = −100:

  • z_clip = (−1.001001)(−100) + (−0.1001001) = 100.1001 − 0.1001 = 100.0
  • w_clip = −z_view = 100
  • z_ndc = 100 / 100 = 1 ✓ — the far plane maps to 1.

Both endpoints land exactly where SDL_GPU expects. Notice w_clip came out positive in both cases despite z_view being negative — that is the −1 doing its job.

6Matrices: column vectors, column-major

Two independent choices hide behind the word "convention" here, and conflating them causes endless confusion. Keep them separate:

QuestionOur answerConsequence
Notation — how do we write a transform? Column vectors: v' = M · v Compose right-to-left: P·V·M
Storage — how do the 16 floats sit in memory? Column-major: m[0..3] is column 0 Uploads to HLSL unchanged

A matrix is where the basis vectors land — that is the mental model this course builds in Module 2, and it is what makes column-major storage natural. Each column of M is the image of one basis vector, so storing column-by-column stores "where x went, where y went, where z went, where the origin went," in that order. Figure 4 shows the bytes.

The transpose trap

"Column-major" (storage) and "column vectors" (notation) are independent. Because we chose both, the two effects cancel and our in-memory layout matches HLSL's default — no transpose on upload. Choose only one and you need a transpose somewhere. If a matrix ever produces a transformation that looks like the transpose of what you wanted, this is the first place to look.

6bThe depth buffer — clear value, compare, format

Settled in Lesson 3.1. These four follow from the NDC depth range in §4 and are not independent choices — but every one of them is a silent, total failure if you get it backwards, so they are written down.

DecisionOursWhy
Directionsmaller is nearer Forced by §4: device depth is 0 at the near plane and 1 at the far plane.
Clear value1.0 (far) “Nothing here yet” must lose to everything. Clearing to 0 makes every fragment fail its test and renders a completely empty screen.
Comparison<, strictly On an exact tie the pixel already there keeps it, so coplanar geometry has one stable winner — the first drawn. Matches SDL_GPU_COMPAREOP_LESS.
What is storeddevice depth, never view-space z Device depth is exactly affine in screen space, so barycentric interpolation of it is exact; view-space z is a hyperbola and interpolating it linearly is simply wrong. Derived in Lesson 3.1 §3.4.
Depth vs other attributes depth is interpolated directly; everything else is perspective-corrected The asymmetry is the point. The projection matrix's third row has already made depth screen-affine, so correcting it again is wrong; no other attribute has had that done to it. Lesson 3.2. The regression test: the depth buffer's contents must not change when perspective correction is toggled.
Formatdepth_format::f32 by default Mirrors SDL_GPU_TEXTUREFORMAT_D32_FLOAT; unorm24 and unorm16 mirror D24_UNORM and D16_UNORM.

Precision is predictable, so predict it. One depth code spans

\[ \Delta w = \Delta z \cdot w^2 \left(\frac{1}{near} - \frac{1}{far}\right) \] delta_w = delta_z * w^2 * (1/near - 1/far)

of real distance at distance w, with Δz = 1/(2bits−1). Two consequences worth memorising: precision degrades with the square of distance, and the bracket is dominated by 1/near — so the near plane is the expensive one and the far plane is nearly free. Moving near from 1 to 0.1 costs 10.09× precision everywhere; moving far from 100 to 1000 costs 0.9%.

The test is not part of the buffer

Storage and comparison are separate, here and on the hardware. engine::depth_buffer clears and stores; the rasterizer compares. That is the same split as SDL_GPUDepthStencilState, whose compare_op, enable_depth_test and enable_depth_write are three independent knobs set per pipeline — a shadow pass writes depth and no colour, a transparent pass tests depth and does not write it.

6cInterpolating vertex attributes

Settled in Lesson 3.2. Barycentric interpolation produces the unique affine function of the pixel position that agrees with three corner values — so it is correct for a quantity that is affine in screen space, and wrong for one that is not.

\[ a \;=\; \frac{\sum_i f_i\,(a_i/w_i)}{\sum_i f_i\,(1/w_i)} \] a = ( f0*a0/w0 + f1*a1/w1 + f2*a2/w2 ) / ( f0/w0 + f1/w1 + f2/w2 )
QuantityHow it is interpolatedWhy
device depth (z)directly Already affine in screen space — the projection's depth row did the job.
uv, colour, normals, …perspective-corrected Linear over the surface, which the divide by w warps. a/w and 1/w are both affine, so interpolate those.
weights (f0, f1, f2)unbiased The top-left rule's −1 decides coverage, not position; leaving it in displaces the whole field. Lesson 2.4 §3.5.

vertex::inv_w stores 1/w, pre-divided, and defaults to 1 — the orthographic case, where the correction is the identity. Cost: one divide per pixel, shared by every attribute.

The blind spot to know about

If a triangle's plane is parallel to the screen, w is constant across it and affine interpolation is exactly correct. Sprites, UI quads, billboards and the front faces of axis-aligned boxes are all in that family — which is why both of Module 3's interpolation bugs survive any test scene made of them.

6dClipping — where, against what

Settled in Lesson 3.3. Two facts, and both of them are the kind that produce silent, hard-to-reproduce bugs when they are assumed rather than written down.

Where

Clipping happens in CLIP SPACE, before the perspective divide. The divide is the one information-destroying step in the pipeline: it turns a signed w into a ratio, and two points on opposite sides of the eye can produce the same ratio. Anything that needs to know which side a vertex was on has to run before it.

Against what

The near plane is z_clip ≥ 0, not w ≥ 0. w = −z_view, so w = 0 is the plane through the eye; the near plane is near units further out. The projection’s depth row (z_clip = A z_view + B) was built so that z_clip = 0 lands exactly at z_view = −near. Equivalently: w ≥ near.

PlaneClip-space testCategory
nearz_clip ≥ 0 correctness — the divide is undefined or sign-flipped without it
farz_clip ≤ w optimisation (and the depth test already handles it)
left / right|x_clip| ≤ w optimisation — the rasterizer’s bounding-box clamp is already correct
top / bottom|y_clip| ≤ w optimisation, same reason

This engine clips the near plane only, and the asymmetry is deliberate rather than unfinished. A triangle hanging off the left of the screen is drawn correctly today, just wastefully; a triangle straddling the eye cannot be drawn at all.

Crossing vertices. The parameter is t = da / (da − db), and every component of the new vertex — all four of the position, including w, plus every attribute — is lerped with that one t. It is a 3-D parameter: the crossing does not sit at fraction t along the segment as drawn on screen, for exactly the reason §6c gives. Colour is lerped in linear light.

Sutherland–Hodgman preserves convexity and winding. Both are relied on: the first lets a clipped polygon be fanned as (out[0], out[k−1], out[k]), the second keeps §7’s back-face test meaningful afterwards. A triangle against one plane yields 0, 3 or 4 vertices — never 1 or 2 — so k_clip_max_vertices = 4 is an exact bound, not a margin. Six planes would need 9.

7Winding and culling

Counter-clockwise winding, viewed from the front, means front-facing. We cull back faces. Everywhere: in the software rasterizer and on every GPU pipeline.

Winding is not an SDL-wide rule — it is per-pipeline state

Any claim that "SDL_GPU uses counter-clockwise" is wrong. Winding is a field you set on every graphics pipeline you create, via SDL_GPUFrontFace in SDL_GPURasterizerState. SDL has no opinion; we do.

Both relevant enums have their first entry at zero — SDL_GPU_FRONTFACE_COUNTER_CLOCKWISE and SDL_GPU_CULLMODE_NONE — so a zero-initialised rasterizer state means "CCW is front, cull nothing." Forgetting to set cull_mode therefore manifests as no culling at all, not as an error. Nothing warns you; you just quietly pay for the back faces. We set both fields explicitly, every time.

Determining winding is a signed-area computation, and its sign is the same cross product that defined handedness in §2. We derive this properly in Module 2 when we build the edge-function rasterizer, and reuse it for back-face culling in Module 3 — one idea, paid for once, used twice.

In the framebuffer, the sign is reversed — and that is not a contradiction

"CCW = front" is a statement about NDC, where +y points up. The viewport transform flips y on the way to pixels (§4), and flipping one axis reverses orientation. So in framebuffer coordinates a triangle that looks counter-clockwise on screen has a negative signed area, by the usual cross-product formula.

Measured, not assumed: the vertices (5,0) → (0,10) → (10,10), which trace counter-clockwise on screen, give −100; reversed they give +100.

Module 2's software rasterizer therefore did not cull by winding — fill_triangle accepted either and oriented its test to match. Lesson 3.4 makes the decision, in that space, for that reason: front-facing is edge_function < 0, read from the sign of the area the rasterizer was already computing, immediately before it destroys that sign by reorienting.

Mesh data: triangle indices, wound outward

Geometry is stored as a vertex array plus an index array, the indices taken in triples, one triple per triangle (Lesson 2.12) — never as an edge list, because triangles are what gets filled, culled and uploaded. Indices are std::uint16_t, which caps a mesh at 65,536 vertices; larger meshes need 32-bit indices, and choosing between them is an asset-pipeline decision.

Every triangle is wound counter-clockwise as seen from outside the solid. Nothing consumed that convention before Lesson 3.4 — it is what culling reads — but the data was authored to it from the start so the meshes never had to be re-authored. Mesh data is validated, not trusted: Euler's V − E + F = 2, every undirected edge in exactly two faces, every directed edge exactly once (consistent winding), and each face's normal pointing away from the centre (outward winding).

Culling: where the test lives, and what it assumes

Settled in Lesson 3.4.

Ask the question after the projection, never before it

Cull from the sign of the screen-space signed area. Do not cull with dot(normal, camera_forward) in view space: that asks whether a face points against the camera’s axis, and the question is whether it points against the ray from the eye to it. Measured, those differ on 15.46% of triangles at our 55° vertical field of view and 32.43% at 120° — and on exactly 0% under an orthographic projection, which is why the mistake survives so long.

The correct view-space form, if you ever need it, is dot(n, centroid) < 0. It is the same number as the screen test: twice the projected signed area is −det[a,b,c] / (wawbwc), and det[a,b,c] = dot(n, a). Clipping (§6d) is what keeps that divisor positive, so the sign is decided by the determinant alone.

Settled in Lesson 3.5, and binding for every loader the engine ever grows. Up to that point all geometry was typed into mesh.hpp, so its properties were true by construction. It is now the output of validate(), which is the difference between an engine that hopes and an engine that knows.

Specular — Lesson 3.7

The first view-dependent term in the course. Everything above 3.7 could be evaluated without knowing where the viewer was standing; a highlight cannot, and that changes the shape of the vertex pipeline as well as the arithmetic.

RuleValueWhy
Default modelBlinn-Phong, dot(n, h)p Phong is kept behind a key so it can be watched failing, but it is not the default. Blinn’s question is about the surface rather than about a reflected ray, and that is the question Module 6 answers properly.
Mirror direction2(n·l)n − l, and it is −reflect(l, n) Same operation as Lesson 1.8’s bounce with the arrow reversed: a velocity points into a surface, a light direction points out of it. Both names exist so neither caller has to remember the other’s convention.
Halfway vectornormalise(l + v), zero when v = −l Exactly the normal that would send l into v — derived, not approximated. The zero fallback makes the impossible configuration return no highlight instead of a maximal one.
Exponentsnot interchangeable: Blinn ≈ 4× Phong β = α/2 exactly, so dot(n,h) falls off half as fast. A near-peak match: measured 4.38× at p = 4, 4.01× at p = 128. Any comparison between the two models must convert first or it is measuring lobe width.
The cut-offPhong returns 0 when |a + b| ≥ 90° The light and the eye on the same side of the normal — on a floor, the sun behind you. Not “the mirror ray dips below the surface”: R is the same angle from the normal as l, so it never does. The lobe covers the hemisphere around R, which is not the visible hemisphere. Measured on a plane: at 35° sun elevation Phong highlights 0 of 30,806 lit pixels and Blinn all of them.
The incoming cosinen·l multiplies both terms The cosine law is about how much light arrives and says nothing about what the surface does with it. Omitting it (classic Phong) puts 0.608 of full strength onto geometry the light cannot reach. It also makes the “zero the specular past the terminator” guard unnecessary.
Specular coloura ratio, and not the albedo A dielectric mirrors light off a clear outer layer without tinting it, so its highlight is the colour of the lamp; a metal has no such layer and tints what it reflects. Module 6 names this F0.
Ambientgets no specular Ambient has no direction, so there is no mirror direction it could have come from. A reflection of the whole environment is image-based lighting, Module 6.
Energynot conserved, and knowingly so Doubling the exponent halves the reflected light (×0.515 from 32 to 64) while the peak stays at 1.0 — backwards, since a smoother surface should concentrate the same light. (m+8)/8π is the usual normalisation and needs HDR to be usable (10.5× at m = 256), so it waits for Module 6.
Surface parametersspecular{colour, shininess}, defaulting to black Black means no highlight, so a default specular reproduces Lesson 3.6 bit for bit (verified: 0 of 100,000 random configurations differ). These two fields are the first two fields of a material; Module 6 builds the rest.

Shading models — Lesson 3.8

Two independent axes, and conflating them is the mistake this section exists to prevent. Lesson 3.6 shipped them as one enum and could not extend it; 3.8 split it.

RuleValueWhy
Axis 1 — normal sourceface or vertex A property of the mesh: decided by how it was authored and where its vertices were split (Lesson 3.5). Nothing the renderer chooses.
Axis 2 — evaluation pointflat / Gouraud / per-pixel A property of the pipeline: how many times the shading equation is called and where. Identical for every mesh you draw.
Defaultvertex normals, per-pixel Per-pixel is the reference the other two are measured against, because it evaluates the equation where the answer is used.
The degenerate cellsface normal ⇒ all three evaluations agree exactly 0 px, not “close” — the normal is constant across the triangle and the albedo already was. Conditional on the shading being view-independent: a specular term needs eye − position, which varies across a face, and then the row separates (1,231 px and 761 px measured). This is the test of whether the two axes are straight in your head.

NamingPhong shading ≠ the Phong reflection model Same 1975 paper, one on each axis. This engine runs Phong shading with the Blinn-Phong reflection model, which is the standard modern pair and sounds contradictory until the axes are separated.
Interpolated normalsrenormalise in the fragment The average of two unit normals θ apart has length cos(θ/2) — 3.4% short at 30°, 13.4% at 60°. Zero at the corners, worst in the middle: the chord signature. shade() does it internally (a 3.6 decision), so this engine cannot exhibit the bug.

7dTextures and sampling

Settled in Lesson 3.9, and every field below mirrors SDL_GPUSamplerCreateInfo — same names, same enumerator order — so Module 4’s port is a rename rather than a re-education.

RuleValueWhy
What a texel isa sample, not a square. Its value lives at (i + 0.5) / N Everything else in this table follows from this one sentence, including the half-texel offset. A texel has a position and no extent; the little square you draw when you picture a texture is a rendering convenience.
Origintop-left, v increasing downwards Not a preference. SDL3/SDL_gpu.h, “Coordinate System”: “Texture Coordinates: The top-left corner has an x,y coordinate of (0, 0) and extends to the bottom-right corner at (1.0, 1.0). +Y is down.” Agrees with the framebuffer (1.5) and the viewport flip (2.11).
Texel spacex = u × N. Integers are texel boundaries; i + 0.5 is texel i’s centre Two questions, two answers. Which texel contains this point is floor(x) and the half plays no part; which two centres bracket it needs x − 0.5.
StorageUint32 ARGB8888, sRGB-encoded, row 0 at the top Byte-identical to a framebuffer pixel, so a 1:1 draw is a copy rather than a conversion — which is what makes the bit-identity test possible.
Decodeinside the sampler, before the filter. sample() returns linear_rgb Filtering encoded bytes does not filter light: black and white blended wrongly gives 42.8% of the light it should, and the worst pair over all 65,536 is off by 0.286 of full range. This is exactly what an _SRGB texture format does in hardware, for free.
Filternearest | linear, matching SDL_GPUFilter’s order One field where SDL has three (min / mag / mipmap). Without mipmaps there is nothing different for a minification filter to do, and that absence is this table’s last row.
Addressingrepeat | mirrored_repeat | clamp_to_edge, per axis, matching SDL_GPUSamplerAddressMode Per axis because a road strip repeats along its length and clamps across its width. i % n is not repeat — C++ truncates toward zero, so −1 % 4 is −1. Mirroring is one identity: index −1−k maps where index k does, which forces the doubled edge texel.
Where addressing is appliedto each of the four texel indices independently, after the neighbours are chosen Wrap the coordinate first and a repeating texture blends the last texel with itself — a hairline seam at every tile boundary, in the filtered mode only. Measured seamless: 0.0000000 across both u = 0 and u = 1.
Bilineartwo lerps along u, one along v; weights (1−tu)(1−tv) … Order of the axes does not matter (both routes expand to the same four weights), and the weights sum to 1 — so it is an average and cannot brighten or darken. Third appearance of that shape after barycentric (2.3) and Gouraud (2.4); the difference is that tutv is not affine, so bilinear is only piecewise smooth.
1:1 is the identitya texture drawn one screen pixel per texel is bit-identical to its source The strongest single check in the file: 0 of 4,096 texels differ under both filters; the control with the offset removed differs on 1,779. Note that the half-texel question exists at both ends — this rasterizer samples attributes at integer pixel coordinates, so a 1:1 quad’s uvs run 0.5/N to 1 + 0.5/N.
Minificationnot solved. Bilinear reads four texels however many the pixel covers Traced on the floor: 0.60 texels per pixel at the bottom of the frame, 62.46 two rows below the horizon — so the sampler sees about 6.4% of the footprint there. And aliasing is caused not by a large footprint but by a large footprint containing disagreement. Mipmaps are Module 6.

One consequence deserves stating on its own, because it is what makes the half-texel bug survive in real pipelines: nearest-neighbour sampling cannot see it. Sweeping 160,801 sample positions, removing the offset changes 0 of them under nearest and 160,632 under bilinear. A texture pipeline can therefore carry the bug for years looking perfectly sharp, and reveal it the day somebody enables filtering — at which point the filter gets blamed.

7eMeasurement

Settled in Lesson 3.10. These are rules about how this course states performance facts, and they exist because a performance number quoted the wrong way is worse than no number — it is a number somebody will act on.

RuleValueWhy
Which instrument budget for phases, differential benchmark for lines, counter for work Three different questions. A budget cannot resolve a line and a microbenchmark cannot rank a frame. The counter is the one people undervalue: it is not a timing, it is exactly reproducible, and it is what explains the other two.
The floor on instrumenting 100 × max(tick, timer) — 4.17 µs on the reference machine Derived from measurement, never assumed: the counter ticks every 41.667 ns (24 MHz) while a read costs 5.42 ns, so the cheaper operation is the limiting one. profiler exposes both so the number is computed on the machine being measured.
Batches, never iterations time N and divide One encode takes 9.3 ns and one tick is 41.667, so a single measurement reports 0 or 41.67 and never 9.3. At N = 1000 twelve trials agree to 0.12 ns.
Summary statistic median for a frame, minimum for a kernel, never the mean Timing noise is one-sided — the machine can be slower than your code and never faster. A kernel has one true cost and everything above it is interference; a frame genuinely varies and you want the typical one. One 40 ms hitch moves a mean of 120 frames by 0.3 ms and the median by nothing.
Zones disjoint and covering; the remainder is displayed Two live timers count the same nanoseconds twice, so nesting is an error rather than a feature (zones_overlapped() checks it). And six honest bars summing to 60% of a frame look complete until you double the biggest and gain 9%.
Frame boundaries start before the event drain, end before SDL_RenderPresent Draining events is work the frame does. Presenting blocks on vsync, and a bar reading “waiting for the monitor” says nothing about the renderer — which is also why an fps counter cannot tell you that you made anything faster.
Which numbers transfer ns per covered pixel and ns per triangle, never ms per frame The first two are properties of the fill loop and the vertex stage. Total milliseconds is a fact about one scene at one resolution on one computer, and it is the only one most people record. Reference values: 45.47 ns/px, 23.0 ns/triangle.
The axis pixels per triangle Per-vertex work scales with triangles, per-pixel work with covered pixels, and their ratio is this one number. Measured: 16× the pixels moved collect by 3.7% and fill by 15×; and at constant screen size the two curves cross near 1 px/triangle.
Before optimising compute the Amdahl ceiling 1/(1 − p) Use it twice: as a filter beforehand, and afterwards as an arithmetic check that the measured whole-frame speedup is one the parts could have produced. Verified: ceiling 1.284×, measured 1.287×.
Judging an approximation the error before rounding The worst-rounded-code column saturates — everything under half a code reports 1 — so it cannot separate 0.0115 from 0.4022, which is the whole question. At a 16-bit target those become 3.0 and 103.4.
Refactors a performance claim needs the same control as a feature's “It should be the same speed” is a prediction, and predictions get measured. Lesson 4.1 saw an apparent 10% gain from a behaviour-preserving extraction; two binaries differing only by it, run alternately, gave 2.5% faster on minimums and 1% slower on medians — i.e. nothing. The 10% was session drift.
Benchmark hygiene volatile sink, -O2, both variants in one run Without a sink the compiler deletes the work. A debug profile is a ranking of a different program (1.5 measured 5.1× at -O0 against 14.8× at -O2). And thermal and scheduling state drift between runs but not within one.

Two rules deserve stating on their own, because both were learned the expensive way. A differential benchmark needs a control. Isolating a feature by adding it works only if nothing else changed; where it cannot, isolate it by removing it from an otherwise identical loop. Lesson 3.10 first reported a texture fetch at 6.40× its microbenchmark cost, a figure produced by adding an encode and two stores alongside the fetch and attributing all three to it; with the control the honest answer is 2.27×. And a function’s cost is not a property of the function — the same fetch runs at 2.26 ns in a tight loop and 5.13 ns in situ, because consecutive fetches overlap in one and sit in a dependency chain in the other.

Lesson 4.2 adds a third, which costs nothing and has caught more errors than either: check that the number can be true. Bandwidth has a published ceiling; frame time has a floor set by the refresh rate; a speedup cannot exceed the fraction of time you changed. 4.2’s first bandwidth figure was 763 GB/s on a machine whose bus is 273, and the two causes behind it are both worth knowing: the driver had elided repeated identical work, and the textures were cleared flat, which lossless render-target compression squeezes to nearly nothing — so the copy was real and the bytes were not. Ping-ponging fixed the first and incompressible noise the second, after which the figure lands on 277.6 against a published 273. And the same lesson found a new axis for 3.10’s rule about comparing numbers taken hours apart: an unchanged binary measured 120 fps and then 60, because the window had opened on a different display.

7fThe GPU execution model

Established in Lesson 4.1, and measured rather than asserted — the software rasterizer can be made to behave the way the hardware does, which is how these numbers exist at all. Nothing here is an SDL_GPU convention; it is how the machine underneath works, and every decision from Module 4 onward is downstream of it.

RuleValueWhy
What a GPU is wide, not fast Per lane it is slower than a CPU core. Measured: one dependent chain runs at 3.124 ns/step, eight interleaved at 0.443 (7.05×) and 32 at 0.112 (27.88×) — same arithmetic, more independent work. Occupancy is that table, and it is why fewer registers per shader means faster.
Lane grouping 32 (a warp / wavefront; 32 or 64 on AMD) One decoder, one program counter and one scheduler for 32 lanes is what buys the width.
Branches a warp runs every side any lane takes, masked Measured against a warp that never diverges: 1.00× at 1024 px of coherence, 1.03× at 64, 1.93× at 8 and below — with the step exactly at the warp width. Coherence is a property of your data, not your code.
Fragment grouping aligned 2×2 quads, always Lanes the triangle misses (helper lanes) run the shader and are discarded, because ddx is lane 1 minus lane 0 and ddy is lane 2 minus lane 0. Every automatic mip selection is paid for out of them — and a derivative inside a divergent branch is undefined for the same reason.
Quad alignment to even coordinates in the render target Not to the triangle — so a triangle cannot be cheap by being positioned well, and the waste depends on its size.
Lane efficiency A / (A + cP) Covered lanes live in the area, helpers along the perimeter. Measured by circumradius: 64 px 96.3%, 16 px 86.7%, 4 px 67.8%, 1 px 25.0%. That is what “small triangles are expensive” means, and it is about size in pixels, not count.
Why 2×2 and not wider forced from both ends It is the smallest block containing a neighbour in x and one in y, so the cheapest shape that can produce a derivative; and every wider block wastes more — at r = 8, measured 75.5% for 2×2 against 8.9% for 16×16. A 32-lane warp is eight quads, possibly from eight triangles: scheduling width and derivative width are different things.
Render state an immutable pipeline object fill_style has 10 top-level fields and SDL_GPUGraphicsPipelineCreateInfo has 9 (53 expanded). The usual justification — saving the inner loop a branch — was measured and is false (0.93×, i.e. nothing). The real reason is that the driver must validate the combination and compile a shader specialised to it: milliseconds, ruinous per draw and free once.

One limitation of our own measurements is worth carrying: vertex::x and vertex::y are integers, so a sub-pixel triangle rounds away and draws nothing. Real hardware rasterizes at roughly 1/256 of a pixel and therefore draws them, at efficiencies below the 25% our smallest case reports. The right-hand end of every efficiency table in this course is the optimistic case.

7gTalking to the GPU — the SDL_GPU contract

Established in Lesson 4.2. Where §7f is how the hardware works, this is how we address it, and the whole section follows from one sentence: a call records work; it does not perform it. Every number below was measured on this course's machine, and the harness that produced them is scratch/verify_42.cpp.

RuleValueWhy
What a call does records, does not execute Measured: 0.1879 ms of CPU calls — acquire, 48 blits, submit — describe 4.7815 ms of GPU work, a factor of 25.45. The CPU is free for 96% of the time the work takes, and an engine that does not use that time is discarding most of its frame.
When a result may be read after the fence, never before A fence is one bit for one submission: not yet, or done. Reading a download before waiting was wrong 64 of 64 trials with the destination poisoned to 0xAB first, and 0 of 64 after. It says nothing about ordering or progress — only that this submission finished.
What a sync costs the overlap, not the wait Two regimes, both measured. Display-bound: a full sync every frame costs nothing — fence 0.761 ms, acquire falls 16.002 → 15.272, frame unchanged at 16.667. GPU-bound: 1.60×. Never learn one of those without the other.
Writing a per-frame resource cycle = true “If this is busy, give me a fresh one.” Pass false and the corruption appears only when the GPU falls behind — a flickering band of last frame, on someone else's machine. Never cycle a resource you intend to update only partially: cycling makes the whole resource undefined.
A clear colour always linear light The format decides what is stored. Measured: 0.5 → 128 into _UNORM (exactly round(255v)) and 188 into _UNORM_SRGB, matching our own linear_to_srgb_u8. RGB only — alpha stays linear (188 / 128 from one clear). Out of range is clamped, not wrapped. Never pre-encode.
The swapchain texture borrowed, write-only, may be NULL Asked for each frame, returned by submitting; cannot be sampled or read back; NULL on a minimised window is not an error. The acquire is where a vsynced frame waits — 16.002 of 16.667 ms — not the submit, and SDL_GPU has no present call at all.
Window size vs swapchain size points vs pixels Equal only without SDL_WINDOW_HIGH_PIXEL_DENSITY. Use the width and height the acquire fills in; assuming they match renders into a quarter of the window and looks like a projection bug.
Getting pixels to the device always via a transfer buffer A texture is tiled, possibly swizzled, possibly compressed, in a layout only the driver knows — so there is no pointer to it and cannot be. Three copies per frame in two time frames: memcpy (now), upload (recorded), blit (recorded). pixels_per_row is pixels, not a pitch; giving it width * 4 shears the image, exactly as in Lesson 1.5.
Frames in flight 2 (SDL's default; 1–3 allowed) throughput = 1/max(C, G) once F ≥ 2; latency ≈ F × max(C, G). Going from 1 to 2 buys throughput; 2 to 3 buys only latency. The call “will stall and flush the command queue” — once, at a settings change, never per frame.
Shader formats asked ≠ granted The mask passed to SDL_CreateGPUDevice says what we can supply; SDL_GetGPUShaderFormats answers what the device accepts. Measured here: asked SPIRV | DXIL | MSL, granted MSL | METALLIB. Lesson 4.3 needs the second.

The object model itself is five renames and four new ideas, and the four are one idea wearing four names: there are two processors now. A device is the connection, a command buffer the message, a transfer buffer the shared ground, a fence the acknowledgement. That the other five are renames is a test, not a claim — verify_42 §G asserts that engine::filter, engine::address_mode and engine::cull_mode still have SDL's enumerator values, so an inserted enumerator fails there rather than as a wrong picture six lessons later.

7hVertex layouts — the contract nothing checks

Established in Lesson 4.5, and the reason it earns its own section is the first row of the table: almost nothing here is validated by anything. A vertex layout is three numbers and one formula, evaluated by fixed-function hardware that has no way to know whether the numbers are right. Every measurement below comes from scratch/verify_45.cpp.

RuleValueWhy
The fetch base + i × pitch + offset Three numbers per attribute and one formula. Any pitch produces addresses, any addresses produce bytes, any bytes produce floats. The picture is the only place a mistake becomes visible.
Writing a layout sizeof for pitch, offsetof for every offset — never a literal A literal 12 is correct until somebody inserts a field above it, at which point every vertex reads the wrong bytes and nothing reports an error. gpu_mesh::describe and describe_instances are the only two places in the engine that name a layout.
What creation refuses one of six Measured: pitch four bytes short → created; four long → created; position/normal offsets swapped → created; an attribute the shader never declares → created. Only a shader input nothing supplies is refused — with an excellent message naming the location.
What our own check catches three of five, and it says so pipeline_desc::check_layout compares against the reflection JSON: it catches a too-short pitch, an undeclared location, an unsupplied location, duplicate locations and a base-type mismatch. It cannot catch a too-long pitch or swapped offsets. A checker that implies it caught everything is worse than none.
A wrong pitch shatters, progressively The error is i × (pitch error), so it accumulates: 4 bytes at vertex 1, 4,896 by vertex 1,224 — and zero at vertex 0, which is how the bug survives a three-vertex test. Too long and too short look the same; do not read the direction out of the picture.
A wrong offset deforms, coherently Each vertex is still read from its own record, just from the wrong bytes of it. Reading a normal as a position collapses the mesh onto a unit sphere. Scattered means the pitch; coherent but wrong means an offset.
A vertex element format answers two questions Bytes in the buffer and type in the shader are not the same question. UBYTE4_NORM is 4 bytes and a float4; the divide by 255 happens in the fetch unit, free. That gap made Lesson 4.4's vertex 43% smaller with the shader untouched.
Supplying fewer components FLOAT3 into a float4 → w = 1 Legal and defined. Measured on Metal by making the missing component the scale: the FLOAT3 draw covered 9,944 px, exactly equal to a FLOAT4 draw at scale 1.0. Matches Vulkan's and D3D12's (0, 0, 0, 1) rule. ⚠ VERIFY on other backends.
Attribute locations unique, and numbered across the pipeline SDL's header requires uniqueness and does not say what happens otherwise. They are numbered across the whole pipeline, not per buffer — slot 1's attributes start at 3 because slot 0 used 0, 1, 2.
Interleaved or separate interleaved by default; hybrid in production Measured on 1,225 vertices with 64-byte lines: one vertex costs 1 line interleaved and up to 5 separate, while a positions-only sweep costs 613 interleaved against 230. Both true. A “separate” layout is simply more vertex_buffer slots, so the hybrid costs no new concepts.
Index width 16-bit, ceiling 65,536 Where k_max_mesh_vertices comes from. On our torus, indices are 4.17× smaller than expanding, and the picture is identical to the pixel. The element size is passed at bind time, not baked into the pipeline: binding 16-bit indices as _32BIT reads pairs as single enormous values.
Vertex-shader invocations a range, not a figure Indexed: 1,225–6,912 on our torus, depending on the post-transform cache. Expanded: 6,912 exactly, with no reuse possible. This is what vertex-cache optimisation optimises.
Instancing input_rate = _INSTANCE — one enum value Same buffer type, same bind call, same attributes, same locations. The shader cannot tell. instance_step_rate is reserved and must be 0. And the default trap again: every enum in the description starts at 0, so a zero-initialised description means _VERTEX.
The viewport render-pass state, not pipeline state SDL_SetGPUViewport survives a pipeline change, so a second draw in the same pass inherits it. Put it back if the next draw wants the whole target.

9The simulation contract

Settled across Lessons 1.3, 1.4 and 1.8, and binding from here to the capstone. Every system added later — physics, animation, the ECS, networking — plugs into this shape rather than negotiating its own.

RuleWhy
The frame order never changes: drain events → clk.tick() → in.update() → N fixed steps → render Draining first is what refreshes SDL's state arrays (SDL_PollEvent pumps). Ticking each subsystem exactly once means the whole frame sees one coherent snapshot.
Simulation advances by a fixed h, never by a frame duration. Default h = 1/60 s. A frame-rate-dependent simulation gives different answers on different machines. Enforced by signature: step() takes h, so there is nowhere to pass dt in.
Rendering interpolates between the two most recent states by alpha ∈ [0,1). Trades a lag that swings between 0 and h for one that is always exactly h. Smoothness is consistency, not immediacy.
Interpolate quantities that were continuous before sampling. Nothing else. A position between two samples is meaningful; a score between two values was never true. Lesson 1.8 §4.6.
Never interpolate across a teleport — snap previous = current instead. The two states are not connected by motion, so the lerp draws a streak at a speed the object never had. Whatever teleports must say so.
The simulation is a pure function of (state, input, h). No globals, no clock reads, no hidden RNG — the seed lives in the state. This is what makes replays, deterministic tests, and (much later) lockstep networking possible at all. A single global read destroys it silently.
What "deterministic" does and does not promise

Determinism here means: same binary, same machine, same seed, same inputs, same step size produce a bit-identical run. It is not cross-platform — floating point differs across compilers and architectures through FMA contraction, x87 excess precision, differing libm implementations, and auto-vectorisation. It is not even step-size-independent: change h and the run diverges, because h is an input too. (Measured in Lesson 1.8: the same seed at 60 Hz and 120 Hz diverges within two simulated seconds.)

Sampling a continuous thing is where the artifacts come from

A discrete test of a continuous process is valid only within a bound, and that bound is worth computing and writing down every time. Lesson 1.8's case: an overlap test catches a moving object only while |v|·h < size_a + size_b. The same shape recurs as aliasing on triangle edges (Module 2), texture shimmer (Module 3), and shadow acne (Module 6) — one idea, four artifacts.

How to re-verify any of this yourself

Reading SDL's headers is a skill this course teaches in Module 0, and the header is the authority — the wiki lags it. When a detail matters, go to the source:
