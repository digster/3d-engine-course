Module 4 — To the GPU: SDL_GPU · Lesson 4.2

The SDL_GPU Mental Model

Nine objects, of which you have already built five. The four that are new all exist for one reason: from this lesson on, a function call no longer does the thing it names — it writes the thing down, and someone else does it later, on another processor. Everything difficult about GPU programming comes out of that one sentence.

1The Problem

Here is a piece of code that does exactly what it says. You have written thousands of lines like it since Lesson 1.5, and never once had to wonder about it:

The second line reads back what the first line wrote, because the first line happened. It happened on this processor, in this thread, before the next statement began. That is such a basic property of a program that it does not feel like a property at all — it feels like what a program is.

Now here is the same idea in SDL_GPU. Clear a texture to a known colour, copy it back to the CPU, and read it. Four calls, no shaders, nothing exotic:

It prints garbage. Not sometimes — 64 times out of 64 in this lesson's harness, which fills the destination with the byte 0xAB beforehand so that "nothing was written here yet" is visible rather than merely suspected. Every one of those 64 reads came back 0xAB. Add one call — a wait on a fence — and the same 64 trials are correct 64 times.

The failure mode, precisely

SDL_SubmitGPUCommandBuffer returned before the clear had happened. It returned before the copy had happened. It returned, in fact, before the GPU had necessarily looked at the command buffer at all — its job is to hand the work over, not to perform it. The read that followed was a read of memory nobody had written yet.

And notice the shape of this bug. It is not a crash, not an assertion, not an error return. Every call succeeded. On a slower GPU it would be wrong by more; on a faster machine, or a smaller texture, it might come back right often enough to look like working code. This lesson's harness reports "wrong 64 / 64", but a version of it that read one byte instead of a quarter of a megabyte would sometimes report zero, and that is much worse — because then you would ship it.

So the problem is not that SDL_GPU has nine new nouns in it. You could learn nine nouns in an afternoon. The problem is that the meaning of a function call has changed, and every one of the new nouns is there to manage the consequences. Learn the nouns without the sentence and you will write code that works on your machine and fails on someone else's, for reasons that never appear in a debugger.

Lesson 4.1 established what the GPU is: a wide, lockstep machine that is slower per lane and wins anyway. This lesson is about the wire between you and it. By the end you will have your own rasterizer's picture on screen, carried there entirely by SDL_GPU, with no shader anywhere in the program — and a graph, drawn by your own fill_rect, of exactly where the frame's 16.667 milliseconds went.

2Building Intuition

2.1A phone call, and a work order

Every graphics call you have made so far has been a phone call. You said "put a red pixel at (10, 20)"; by the time you stopped speaking, the pixel was red. The call and the effect were one event, and they were one event because the thing being asked and the thing doing the asking were the same processor.

From here, a graphics call is a work order. You are not doing the work and you are not talking to whoever will. You are filling in a sheet of paper: clear this target to grey; then copy those bytes over there; then draw these triangles. Filling in the sheet is fast, because writing "resurface the driveway" takes a second and resurfacing a driveway does not. When the sheet is complete you hand it over — SDL_SubmitGPUCommandBuffer — and that is a separate act from the work being done.

This is not an analogy that gets stretched until it breaks. It is very nearly the literal implementation: a command buffer is a chunk of memory into which the driver appends packets, and submitting it makes the GPU's front end start reading them. You can measure the difference between writing the order and doing the work, and you should, because the ratio is the most important number in this lesson:

Figure 1 is that table drawn to scale, and it is worth looking at until it stops being surprising. The block on the CPU lane is not small because the picture is stylised; it is small because 0.1879 is small next to 4.7815. That empty space to its right is the whole reason a GPU program is structured the way it is: the CPU is free during the work it just described, and an engine that does not use that time is leaving most of its frame on the floor.

It also shows the one arrow going the other way. The dashed line back up to the CPU lane is a fence, and its position is the answer to the failure in §1: the fence is where the work finished, and nothing about that work may be believed before it.

2.2Two memories, and the room between them

The second new idea is that there is more than one kind of memory, and you cannot reach the important one.

A GPU texture lives in memory arranged for the GPU's benefit. It is not a row-major array of Uint32 like engine::framebuffer; it is tiled, so that the four texels of a 2×2 quad (Lesson 4.1 §2.3) are adjacent rather than a row apart, and it may be losslessly compressed, and its exact arrangement is a trade secret that differs between vendors and between two GPUs from the same vendor. You cannot write to it with memcpy, and the reason is not that SDL is being protective — it is that you do not know where anything is.

So there is a third region: memory that both processors can address, laid out plainly, whose only purpose is to be a staging area. SDL calls it a transfer buffer. You memcpy into it; the GPU copies out of it into whatever arrangement it prefers. Every pixel that goes from your framebuffer to the screen takes both hops, and no API can remove that, because it is the shape of the machine rather than a wart in the interface.

Figure 2 is worth reading twice: once left to right, for the route, and once for the dashed vertical line. To the left of that line, work happens when you call it. To the right, calling it only writes it down. The memcpy into the transfer buffer is real work, now, on the CPU, and this lesson measures it at 0.0028 ms for a 320×180 frame. The upload and the blit are recorded in microseconds and performed later.

The ninety-percent picture

On a machine with unified memory — every Apple silicon Mac, every console, most phones — the CPU and GPU are looking at the same physical DRAM, and a hypothetical perfect API could sometimes skip the staging copy. SDL_GPU does not expose that, because it must also run on a discrete GPU across a PCIe bus, where the copy is a genuine journey across the motherboard. This is the ninety-percent picture; the missing ten percent is that on some hardware the transfer buffer's copy is cheaper than it looks, which the numbers in §4.6 will show.

2.3The nine objects, five of which you own

Here is the part that is much better news than it sounds. SDL_GPU's object model is not nine unfamiliar things. It is four unfamiliar things and five renames.

Count the two colours in Figure 3. Five rows are objects you designed and implemented, in some cases three modules ago, and Module 3 shaped several of them deliberately so that this moment would be an observation rather than a leap — Lesson 3.9's engine::sampler mirrors SDL_GPUSamplerCreateInfo field for field, and Lesson 4.1 counted fill_style's ten fields against SDL_GPUGraphicsPipelineCreateInfo's nine.

That mirroring is not a claim to be taken on trust; it is a test. This lesson's harness checks that our enumerators still have the same values as SDL's, which is what makes the "rename" language honest:

Keep that check. If SDL ever inserts an enumerator, this fails here, with a name and a line number, instead of failing as a mesh that culls the wrong faces in a lesson six weeks from now.

Now the four that are new — the device, the command buffer, the transfer buffer and the fence. Look at what they have in common. A device is a connection to another processor. A command buffer is a message to another processor. A transfer buffer is shared ground because the other processor's memory is not yours. A fence is how you learn that the other processor has finished. There is no fifth idea hiding: all four are the same idea, which is that there are two machines now, and your rasterizer never needed any of them because it was only ever one.

2.4Why the swapchain is borrowed

One object deserves separate treatment, because it behaves unlike the rest: the swapchain texture.

Since Lesson 1.5 you have owned your framebuffer. You allocated it, you kept it for the whole run, you cleared it at the top of each frame. A swapchain texture is the opposite in every respect. You do not create it; you ask for one each frame, and give it back by submitting the command buffer that referenced it. There are usually two or three of them and you do not choose which you get. It is write-only — you cannot sample it, and you cannot read it back. And you may be handed nullptr, which is not an error.

The reason is that the display owns these images, not you. At any instant one of them is being scanned out to a physical panel, sixty times a second, whatever your program is doing. Handing you that one would show the reader half of a half-drawn frame. So the display keeps a small set and lends you one that it is not currently scanning — and if the GPU has fallen behind and every image is spoken for, the honest answer to "may I have one?" is "wait", which is what SDL_WaitAndAcquireGPUSwapchainTexture does, and what a minimised window's nullptr means.

This is where a vsynced frame actually waits

Not in SDL_SubmitGPUCommandBuffer, and not in a present call — SDL_GPU does not have one, because presentation is implied by having acquired the image. In this lesson's probe, running at 60 Hz, 16.002 ms of a 16.667 ms frame is spent inside the acquire. Your program is not slow. It is waiting for a monitor, which is a completely different problem with completely different solutions, and knowing which one you are looking at is most of performance work.

2.5An honest sidebar: why not OpenGL

A fair question at this point is why we are learning fences and command buffers at all, when OpenGL would let us write glClear and be done. It deserves a straight answer rather than a fashion argument, and part of that answer is that OpenGL is genuinely still good at some things.

What OpenGL gets right: it is the easiest 3D API to start in, because the driver hides exactly the machinery this lesson is about. It runs on hardware from 2008. Its tutorial literature is the best-covered ground in graphics — LearnOpenGL is a superb resource and much of its content transfers directly to what we are doing. If your goal is a small tool, a visualiser, or a plot window, OpenGL is a perfectly professional choice today.

What it costs:

  • The state machine. OpenGL has one enormous global context; every call mutates it, and a function's behaviour depends on the last few hundred calls. Lesson 4.1 §3.4 argued the opposite design — state gathered into an immutable object, validated once — and measured the usual justification for it and found that one false. The real reason stands: a pipeline object is validated and compiled once, at creation, rather than re-checked at every draw.
  • The hidden asynchrony is still there. This is the important one, and it is widely misunderstood. OpenGL does not remove the two-processor problem; it hides it. Your glDrawArrays also returns before the work happens, and the driver silently inserts synchronisation when you touch a resource it is still using. That is convenient right up to the moment your frame time doubles for no visible reason, and then you are debugging a synchronisation you cannot see and did not write.
  • It is deprecated on macOS — frozen at 4.1, from 2011, and formally deprecated since 2018. It works today. Planning a five-year project around it does not.
  • SDL_GPU is SDL3's flagship path, and it maps onto Vulkan, D3D12 and Metal — the three APIs that current hardware is actually designed for. The concepts in this lesson are those APIs' concepts, so what you learn here transfers to all three.

The honest summary: OpenGL is a fine way to draw a triangle and a poor way to learn how the machine works, because its whole design is dedicated to not telling you. We are here to learn how the machine works.

3The Theory

3.1What a fence actually promises

A fence is an object that becomes signalled when every command in the submission that produced it has finished executing. That is the whole definition, and the useful part is what it does not say.

It does not say the commands ran in the order you wrote them — they may not have, as long as the result is as if they did. It does not tell you how far along the work is; there is no percentage. It is one bit: not yet, or done. And it applies to one submission, not to the device — a second command buffer submitted afterwards has its own fence and its own answer.

SDL gives you three ways to use that bit, and they are the three shapes of every synchronisation problem you will meet:

Now, the cost. Waiting on a fence is not expensive in itself; the wait in §1's fix takes under a millisecond. What is expensive is what waiting prevents: while the CPU is blocked, it is not recording the next frame, so the GPU will have nothing to start on when it finishes. You do not pay the duration of the wait. You pay the overlap you gave up.

Worked example — what a sync costs, in real numbers

This lesson's harness (§E) submits the same work 32 times — 8 blits of a 1024×1024 texture each, so about 0.184 ms of GPU work per submission — in two ways.

  • Waiting on every fence: 9.438 ms total, 0.295 ms per submission.
  • Waiting only on the last one: 5.904 ms total, 0.184 ms per submission.

The speedup is 1.60×, and read the pipelined figure again: 0.184 ms per submission is exactly the GPU time per submission. Pipelined, the GPU never idles, so the total is the GPU work and nothing else. Stalled, each round trip adds 0.111 ms of handshake — the CPU waiting for the GPU, then the GPU waiting for the CPU — and 32 of those is the 3.5 ms difference.

Note what this does not say: it does not say a sync costs 1.6×. It says a sync costs one round trip, and whether that matters depends entirely on whether the machine had anything else to do. §4.5 measures a case where the answer is nothing at all, which is exactly why this bug survives long enough to reach production.

3.2Cycling, and the bug it exists to prevent

Here is a problem you now have and did not have last lesson. You memcpy this frame's pixels into the transfer buffer and record an upload. Next frame you do it again. But is the GPU finished with the first upload? If it is not, your second memcpy is overwriting bytes that a pending command is going to read — and the image on screen becomes an interleaving of two frames.

Every low-level graphics API has this problem. Vulkan makes you solve it by hand, with per-frame resources and explicit barriers, and it is where most people's first Vulkan renderer goes wrong. SDL_GPU's answer is a single bool named cycle, and the header states the rule plainly enough to be worth quoting: when a resource is used in a pending command buffer it is bound, and if you write to a bound resource with cycle = true, SDL hands you a different internal copy instead.

So cycle means: if this is busy, give me a fresh one. The resource is a ring buffer wearing the disguise of a single object, and the handle you hold stays valid while the storage underneath rotates.

The failure mode, and why you will not see it

Pass false where you should pass true and everything looks perfect — on a machine where the GPU keeps up. The corruption appears only when the GPU falls behind far enough that last frame's upload has not been consumed, which means it appears on slower hardware, under load, in someone else's hands. It shows as a horizontal band of the previous frame, usually near the top, flickering.

Two rules keep you out of it. Cycle when you write to a resource that a previous frame may still be reading — which for a per-frame upload path means every frame. And never cycle a resource you are about to only partially update, because cycling makes the whole resource undefined, not just the part you touched.

3.3Frames in flight: latency against throughput

The swapchain has a small number of images, and SDL lets you set how many frames may be pending on the GPU at once — SDL_SetGPUAllowedFramesInFlight, minimum 1, maximum 3, default 2. This is one of the few knobs in the whole API that changes how the program feels rather than how fast it runs, and the reason is worth deriving rather than memorising.

Let the CPU take C milliseconds to prepare a frame and the GPU take G to execute it. With F frames allowed in flight:

\[ \text{throughput} \;=\; \frac{1}{\max(C,\,G)} \qquad\text{(for } F \ge 2\text{)}, \qquad \text{latency} \;\approx\; F \cdot \max(C,\,G) \]

throughput = 1 / max(C, G) once F ≥ 2; latency ≈ F × max(C, G)

In prose, because the equation must never be the only carrier of the fact: with two or more frames in flight the CPU and the GPU overlap, so the frame rate is set by whichever of them is slower — but the picture you are looking at was prepared F frames ago, so every extra frame of overlap is an extra frame of delay between moving the mouse and seeing the result.

Worked example — three settings, by hand

Take C = 4 ms and G = 6 ms, and a display fast enough not to be the limit.

  • F = 1. No overlap at all: the CPU prepares (4), hands over, waits for the GPU (6), and only then starts the next. A frame every 4 + 6 = 10 ms — 100 fps — and latency is one frame, 10 ms.
  • F = 2. The CPU prepares frame N+1 while the GPU runs frame N. Every 6 ms a frame completes — 1/max(4, 6), so 167 fps, a 1.67× throughput gain — and the CPU is idle 2 ms in every 6. Latency is about 12 ms.
  • F = 3. Throughput is unchanged at 167 fps, because the GPU was already saturated and a third queued frame cannot make it faster. Latency rises to about 18 ms.

That asymmetry is the whole design rule. Going from 1 to 2 buys real throughput; going from 2 to 3 buys only latency, and buys it in the wrong direction. Two is the default because two is where the gain stops. Raise it to three when frame times are erratic and you would rather absorb a spike than drop a frame; lower it to one when input latency is the product — a competitive shooter, or anything on a head-mounted display, where 18 ms of queue is the difference between a game and a nausea generator.

Not a per-frame call

SDL's documentation is explicit that SDL_SetGPUAllowedFramesInFlight "will stall and flush the command queue to prevent synchronization issues". Call it once at a settings change, never inside a loop — and expect the frame it runs in to produce nonsense measurements, which is why the probe's log says so out loud when you press 3.

3.4A float clear becomes bytes

SDL_GPUColorTargetInfo::clear_color is an SDL_FColor — four floats. Your framebuffer stores four bytes. Something has to convert, and the conversion is not the one most people assume, so let us predict it and then measure it.

An _UNORM format stores a number in [0, 1] spread evenly across the byte range: the stored byte is the float times 255, rounded. There is no transfer function anywhere. A _UNORM_SRGB format stores the same range, but applies the sRGB encode on write and the matching decode on read, so that shaders always work in linear light while memory holds an encoding that spends more of its 256 codes in the dark tones, where the eye can tell them apart. That is the argument of Lesson 1.6, implemented in hardware.

\[ \text{byte}_{\text{UNORM}} = \mathrm{round}(255\,v), \qquad \text{byte}_{\text{SRGB}} = \mathrm{round}\!\left(255\left(1.055\,v^{1/2.4} - 0.055\right)\right) \]

UNORM: byte = round(255 × v). sRGB: byte = round(255 × (1.055 × v^(1/2.4) − 0.055)), for v above 0.0031308.

Worked example — where does 0.5 land?

Into an R8G8B8A8_UNORM target.

  • 255 × 0.5 = 127.5, which rounds to 128.

Into an R8G8B8A8_UNORM_SRGB target.

  • 0.51/2.4 = 0.50.41667 = e0.41667 × ln 0.5 = e−0.28881 = 0.74915
  • 1.055 × 0.74915 − 0.055 = 0.79035 − 0.055 = 0.73535
  • 255 × 0.73535 = 187.51, which rounds to 188.

And the measurement, from clearing a 1×1 target of each format and downloading the byte: 128 and 188. Both predictions exact, and the sRGB one matches engine::linear_to_srgb_u8 — our function, written in Lesson 1.6 — to the code, at all five test values.

Figure 4 draws both answers. The single most useful sentence to take from it is this: the clear colour is always linear light, and the format decides what gets stored. You never encode a clear colour yourself. If you do — if you pass 188/255 to an sRGB target because you wanted mid-grey — the hardware encodes your already-encoded value and you get 226, which is the washed-out picture that Module 6 will teach you to recognise on sight.

Two smaller results from the same experiment, both worth knowing and neither worth guessing: values outside [0, 1] are clamped, not wrapped (−0.5 → 0, 1.5 → 255), and the _UNORM_SRGB transfer function applies to the three colour channels only. Alpha is linear in both formats, because alpha is a coverage fraction rather than a colour and encoding it would be meaningless.

3.5The letterbox, by hand

One piece of arithmetic stands between our 320×180 framebuffer and the window: they are not the same size, and the window can be resized to any shape at all. Stretching to fill would make every circle in the scene an ellipse, so we fit the largest rectangle of the source's aspect ratio inside the target and centre it.

The comparison is best done without dividing. The source is proportionally wider than the target when src_w / src_h > dst_w / dst_h, and multiplying both sides by the positive quantity src_h × dst_h turns that into src_w × dst_h > dst_w × src_h — the same question, in integers, with no rounding and no division by zero.

Worked example — 320×180 into a 1024×768 window
  • Is the source proportionally wider? 320 × 768 = 245,760 against 1024 × 180 = 184,320. Yes, so we fill the width.
  • w = 1024, and h = 1024 × 180 / 320 = 576.
  • x = (1024 − 1024) / 2 = 0, y = (768 − 576) / 2 = 96.

So the image lands at (0, 96) at 1024×576, with 96-pixel bars above and below. Check it: 1024/576 = 1.778 = 16:9, the source's aspect ratio, preserved exactly. fit_centred returns precisely this, and §H of the harness asserts it along with the two-bars-at-the-side case and both degenerate inputs.

4Implementation

Four new files, and one decision to make before any of them. Our window currently belongs to an SDL_Renderer, created in Lesson 0.5 and used ever since — including by every HUD in Modules 1 to 3, which are drawn with SDL_RenderDebugText. 4.1The device, and the claim

Two resources, acquired in one order and released in the other. Creating the device picks a backend and loads a driver; claiming the window creates the swapchain. On the way out, the claim must be released before the device is destroyed, because the swapchain belongs to the pairing rather than to either party.

An object whose destructor knows that order is strictly better than a comment asking you to remember it, so gpu_device owns both:

Creation is the two-phase pattern the C++ style guide fixes for fallible construction: a default constructor that cannot fail, and a create that reports what happened. Without exceptions a constructor has no way to say "no" (C++ Style §5), and the price is that valid() has to exist. The benefit is that every failure path is visible in a signature rather than in a stack unwind.

Note one detail in create that is easy to get wrong: if the claim fails, we destroy the device before returning.

C++ in place — why the raw handle is public

gpu_device::handle() hands out the raw SDL_GPUDevice*, which looks like a leak in the abstraction. It is deliberate. A wrapper that forwarded all ninety-odd SDL_GPU functions would hide exactly the API this course exists to teach, and every one of those forwarding methods would be a place for our names to drift from SDL's.

The wrapper exists for lifetime, not for concealment: it guarantees the device is created once, released once, and released in the right order relative to the window. Everything else is SDL's, spelled SDL's way. This is the same judgement engine::framebuffer made in Lesson 1.5 when it exposed data().

4.2Asking instead of assuming

Once the device exists, everything about it is a question with a real answer, and none of those answers may be assumed. gpu_report is a struct with a query behind every field, filled in at creation and logged at startup:

Read the third and fourth lines together, because they are the first genuine surprise of the API. We asked for SPIRV | DXIL | MSL and were granted MSL | METALLIB — one format we named and one we did not. That is not a negotiation failure. The mask you pass to SDL_CreateGPUDevice says here is what I am able to supply, and SDL uses it to pick a backend that can consume at least one of them; SDL_GetGPUShaderFormats then answers a different question — here is everything I accept. Lesson 4.3 needs the second answer, not the first, to decide which file to load.

The other lines matter for reasons that arrive later, and it is worth knowing which:

  • The swapchain format is not a constant and not ours to choose. In Lesson 4.4 a graphics pipeline whose colour-target format does not match this exactly will simply fail to create — so this line is load-bearing, not informational.
  • MAILBOX is missing from the present modes on this machine. That is the whole reason support is asked about rather than assumed: a program that hard-codes MAILBOX works on the developer's Linux box and fails at startup on a Mac.
  • The window and swapchain sizes agree here, at 1280×720, and it is worth knowing why they might not. A window is measured in points and a swapchain in pixels; they coincide because this window was created without SDL_WINDOW_HIGH_PIXEL_DENSITY. Ask for that flag on a Retina display and the swapchain comes back at twice the window's numbers. Code that assumed they were equal then draws into a quarter of the window and sends its author looking for a bug in the projection matrix. The acquire returns the real numbers; use those.

4.4The transfer-function trap

Now a trap that §3.4 has already armed. Our framebuffer holds sRGB-encoded bytes — that has been true since Lesson 1.6, and it is what every PNG an artist hands you holds too. The swapchain may be a plain _UNORM format, which applies no transfer function, or a _UNORM_SRGB one, which decodes on read and encodes on write.

Consider what a blit does: it samples the source and writes the destination. So with an sRGB destination and a plain source, our already-encoded bytes are read unchanged and then encoded again on the way in. Encoded twice. Mid-grey 128 becomes 188 becomes 226, and the picture goes pale and foggy — the classic gamma artifact, arriving three modules before the lesson that names it.

The fix is one line of thought and four of code: give the source texture the same sRGB-ness as the destination, so a decode on read cancels the encode on write and the pair is the identity.

The byte layout comes from asking SDL rather than from reasoning about it, and that is worth a sentence of its own. SDL_PIXELFORMAT_ARGB8888 is a packed 32-bit format: it describes the bits of a Uint32, not the order of four bytes in memory, so on a little-endian machine those bytes come out B, G, R, A. The answer is therefore endianness-dependent, and asking costs one call:

That second check is the one that makes the whole path trustworthy. 4.5The frame, and where the waiting really is

The probe's frame is nine steps, and their order is the argument:

The upload is recorded before the acquire, and that is deliberate. The acquire is where a vsynced frame blocks; every microsecond of work you can place above it is work done while the display is still busy with the previous frame. Move it below and nothing breaks — the frame just gets longer by exactly that much.

Then the swapchain is cleared by a render pass that draws nothing at all:

A render pass with no pipeline bound and no draw call is legal and useful, and it is the clearest possible illustration of what a load op is. Clearing is not a draw that happens to cover the screen; it is a property of beginning a pass. On tiled hardware — every mobile GPU, and Apple silicon — LOADOP_CLEAR costs less than LOADOP_LOAD, because loading means fetching the previous contents of each tile from memory and clearing means not bothering. That is the single easiest performance mistake to avoid in a mobile renderer, and it is available to you before you have written a shader.

Now the measurement. The probe times four things per frame and draws them as stacked columns, one per frame, using nothing but framebuffer::fill_rect. There is no text in this mode, because text needs a font and a shader and both are later lessons — so the graph is the HUD.

Figure 5 is the result, and the middle bar is the reason this section exists. Pressing 4 turns on a full GPU sync every single frame — the thing every guide tells you never to do. Watch what happens:

The full GPU sync is free. Not cheap — free, to the precision we can measure. And the reason is in the third row: at 60 Hz, 16.0 of the 16.667 ms was already being spent waiting for the display. There was nothing else for the CPU to do with the 0.76 ms the fence took, so taking it cost nothing. The wait simply moved from one blocking call to another.

Why this is the most dangerous result in the lesson

A beginner's renderer that syncs every frame will measure perfectly on a simple scene, ship, and fall apart the moment the GPU becomes the limit — because then there is no slack, the sync stops being absorbed, and every frame pays the full round trip. §3.1 measured that case and found 1.60×.

So do not learn "syncing is slow" and do not learn "syncing is free". Learn this: a sync costs you the overlap you had. When the frame is display-bound there is no overlap to lose; when it is GPU-bound there is nothing else. Which regime you are in is a measurement, and now you have the tool that makes it.

The third row is worth a moment too. IMMEDIATE present mode takes the frame from 16.667 ms to 4.816 — and the acquire is still 4.238 ms of it. Turning off vsync did not remove the wait; it moved the limit from the display to the frames-in-flight budget. There is always something pacing you. The question is only what.

4.6A number that could not be true

One more thing happened while measuring §2.1's table, and it is in the lesson because leaving it out would teach the wrong habit.

The first version of the harness copied a 2048×2048 texture 48 times and reported 763 GB/s. That is a good-looking number. It is also impossible: this machine is an Apple M4 Pro, whose published memory bandwidth is 273 GB/s. A copy cannot move bytes 2.8 times faster than the bus they travel on, so the measurement was wrong, and the only question was how.

The first cause was elision. Blitting the same source to the same destination 48 times is 48 copies of one answer, and a driver is entitled to notice. Fixing it took one line: ping-pong, so that blit i+1 reads what blit i wrote and the chain cannot be shortened or reordered. That brought the figure down — and not far enough.

The second cause was compression. Both textures were cleared to a flat colour, and every modern GPU stores render targets in a losslessly compressed form. A flat texture compresses to nearly nothing, so the copy was real but the bytes were not. Filling both textures with xorshift noise — which cannot compress — makes the copy move what it claims to move.

Figure 6 is both versions at four sizes, and it is the most useful chart in the lesson. Read the noise bars first: they converge on 277.6 GB/s at 4096², against a published bus of 273. The copy saturates the memory system, which is exactly the right answer for a copy, and finding a measurement that lands on an independently known number is the strongest evidence a benchmark can offer.

Then read the gap. Flat content copies at up to 2.87× the rate of noise, and the ratio grows with size, because compression saves more when there is more to save. That is not a measurement error once you know what it is — it is a real and useful property of the hardware, and it is why a cleared render target is cheaper to work with than a busy one. It only became an error when it was quoted as bandwidth.

The habit, not the number

Lesson 3.10 said: measure, then act. This section adds the step in between — check that the number can be true. Bandwidth has a ceiling you can look up. Frame time has a floor set by the refresh rate. A speedup cannot exceed the fraction of time you changed (Amdahl's law, 3.10 §6). Every one of those is a free sanity check, and each of them has caught a real error in this course's own harnesses.

7Common Pitfalls & Debugging

The downloaded data is garbage, or is last frame's

Symptom. A readback contains the fill pattern you poisoned the buffer with, or the previous frame's contents, or plausible-looking data that is subtly stale. Every SDL call returned success.

Cause. You read before the fence. SDL_SubmitGPUCommandBuffer hands the work over; it does not perform it.

Fix. Submit with SDL_SubmitGPUCommandBufferAndAcquireFence, wait with SDL_WaitForGPUFences, then map — and release the fence. This lesson's §D measured the unfixed version wrong 64 times out of 64. Be more suspicious, not less, when it happens to work: a race that usually wins is a race you will ship.

SDL_ClaimWindowForGPUDevice fails and the window looks fine

Symptom. The device is created, the claim returns false, and the window is on screen and perfectly healthy.

Cause. Something else already owns it — nearly always an SDL_Renderer created earlier, including one created by a helper you forgot about. A window has exactly one presentation owner.

Fix. Decide before the window is used. In this lesson the --gpu branch is taken before SDL_CreateRenderer is ever reached, which is why the flag is parsed at the top of main rather than read from a config file later. If you must switch at runtime, destroy the renderer first.

The image fills a quarter of the window

Symptom. Everything renders into the bottom-left (or top-left) quarter, as if the projection were scaled by two.

Cause. You used the window's size where the swapchain's was wanted. A window is measured in points; a swapchain in pixels. With SDL_WINDOW_HIGH_PIXEL_DENSITY on a Retina or 4K-scaled display they differ by the display scale.

Fix. Use the width and height that SDL_WaitAndAcquireGPUSwapchainTexture fills in. They are out-parameters precisely so you never have to compute them, and the probe logs both numbers once at startup so that a mismatch is visible before it is mysterious.

The picture is pale and washed out

Symptom. Everything looks foggy, blacks are grey, and the whole image appears to have had its contrast reduced.

Cause. A double sRGB encode. Your bytes are already encoded; the target's format encoded them again. Mid-grey 128 became 188. (The opposite mistake, a double decode, gives a picture that is far too dark and contrasty.)

Fix. Match the source texture's sRGB-ness to the destination's, as gpu_present_target::create does. And remember the rule from §3.4: a clear colour is always linear light, and the format decides what is stored — never pre-encode one yourself.

A flickering band of the previous frame, on some machines only

Symptom. Part of the image — often a horizontal strip — shows the previous frame, intermittently, usually under load. Never reproducible on the developer's machine.

Cause. You wrote to a transfer buffer or texture that a pending command buffer is still reading, with cycle = false.

Fix. Pass true for cycle on every per-frame write. The cost is memory, not time. And do not cycle a resource you intend to update only partially: cycling makes the whole resource undefined.

A benchmark result that is too good

Symptom. A copy or a clear reports bandwidth above the machine's memory bus, or a draw takes zero time.

Cause. The work did not happen. Two ways for that, both met in §4.6: the driver elided repeated identical work, or the content was compressible enough that the bytes never moved. A third, from Lesson 3.10: the optimiser deleted your benchmark's arithmetic because nothing consumed the result.

Fix. Chain the work so each step depends on the last, fill buffers with incompressible noise, and — before anything else — look up the ceiling. Every GPU measurement has one.

The same program measures 120 fps and then 60 fps

Symptom. Two runs of an unchanged binary, minutes apart, disagree by a factor of two on frame time.

Cause. The window opened on a different display. This happened while writing this lesson: the first run landed on a 120 Hz laptop panel and the rest on a 60 Hz external monitor, and for a few minutes there was a very exciting and completely false conclusion that fencing halved the frame rate.

Fix. The one Lesson 3.10 already gave, applied to a new axis: run the variants alternately, in one session, and change one thing at a time. The numbers in Table 3 were taken that way, twice, after the false result was found. If a vsynced measurement surprises you, check what the display is doing before you believe it.

8Exercises

4.2.1 — Make the double encode happen

Force the bug in §4.4 so you can recognise it later. In gpu_present_target::create, delete the is_srgb_format branch so the source texture is always the plain _UNORM layout. Then switch the swapchain to an sRGB one — SDL_SetGPUSwapchainParameters with SDL_GPU_SWAPCHAINCOMPOSITION_SDR_LINEAR, checking SDL_WindowSupportsGPUSwapchainComposition first — and describe precisely what changed about the picture.

Hint

Look at the dark checkerboard squares rather than the bright triangle. The encode is steepest near zero, so the damage is largest in the darks: byte 18 becomes 76.

Solution sketch

The whole image lifts, and the shadows lift most — the background stops reading as near black and becomes a flat mid-grey. Now restore the branch and watch it snap back. The habit worth taking away is that washed-out darks is a specific diagnosis with a specific cause, not a vague sense that the picture looks wrong.

4.2.2 — Find your own frame's limit

Using only the probe's keys, determine what is pacing your machine. Record the four timings at each of: VSYNC with 2 frames in flight; IMMEDIATE with 2; IMMEDIATE with 1; and IMMEDIATE with 3. Which setting changes the frame time and which changes only where the time is spent?

Hint

Compare the acquire band across the four. Then apply §3.3's formula: with F ≥ 2 the frame rate is 1/max(C, G), so if going from 2 to 3 changes nothing you have learned which of C and G is larger.

Solution sketch

On the machine in this lesson: VSYNC pins the frame at 16.667 ms with the acquire absorbing all the slack. IMMEDIATE drops it to about 4.8 ms, still mostly acquire — so the limit became the frames-in-flight budget rather than the display. Dropping to 1 frame in flight lengthens the frame, because CPU and GPU stop overlapping; raising it to 3 changes the frame time hardly at all, which is §3.3's prediction that the second frame buys throughput and the third buys only latency.

4.2.3 — A screenshot, without stalling the frame

Add a key that saves the framebuffer as it appeared on the GPU, by downloading the present target's texture — and do it without ever blocking the frame loop. Use SDL_QueryGPUFence rather than SDL_WaitForGPUFences: request the download this frame, check the fence each subsequent frame, and write the file on the frame it reports done.

Hint

You need three pieces of state that outlive the frame: the fence, the download transfer buffer, and a flag saying a capture is outstanding. Refuse a second request while one is pending — that is one line and saves you an entire class of bug. Lesson 3.5's save_obj shows the file-writing pattern this codebase uses; a .ppm is six lines to write.

Solution sketch

The capture typically completes on the very next frame, which is the point: the same result as a blocking wait, and no frame was delayed to get it. This is the shape of every good readback in a real engine — GPU-side histograms, auto-exposure, picking, occlusion queries — and it is exactly the "latency you can tolerate" trade the SDL_GPU header describes for SDL_DownloadFromGPUTexture. Watch for one trap: the texture you download must not be written again before the fence signals, so either cycle it or capture into a texture of its own.

4.2.4 — Prove the transfer buffer is necessary

Try to skip it. Attempt to memcpy straight into an SDL_GPUTexture, and then write down, in one paragraph, why the API gives you no way to express that — even on a unified-memory machine where the CPU and GPU are demonstrably looking at the same DRAM.

Hint

There is no function that returns a pointer to a texture's storage. Ask why that is a deliberate omission rather than a gap: what would such a pointer have to promise about the arrangement of the bytes behind it?

Solution sketch

A texture is not row-major. It is tiled so that a 2×2 quad's texels are neighbours (Lesson 4.1 §2.3), possibly swizzled, possibly losslessly compressed, and the exact scheme differs between vendors and between two chips from one vendor. A pointer to it would be a pointer to a layout you cannot know, so the only portable way to write a texture is to describe the pixels in a layout you can know and let the driver rearrange them. That is what the transfer buffer is. The unified-memory case does make the copy cheaper — 0.0028 ms for 320×180 here — but not expressible as a direct write.

4.2.5 — Find the compression ceiling yourself

Extend §C of the harness to sweep content rather than size: copy a 4096² texture that is flat, then a two-colour checkerboard, then four-bit noise, then full 32-bit noise, and plot the reported bandwidth. Where does the curve reach the bus, and what does that tell you about the compressor?

Hint

Keep every other variable identical — same size, same blit count, same ping-pong. Only the bytes change. And take the minimum of several runs rather than the mean, as Lesson 3.10 argued for kernels.

Solution sketch

You should find a curve that falls towards the bus figure as the content gets less compressible, flattening once it is genuinely incompressible. The interesting part is where the knee is, because that tells you what block size and what kind of redundancy the hardware's compressor exploits — and it is vendor-specific, undocumented, and measurable in fifteen minutes with the harness you already have. That last sentence is most of what graphics performance work is.

9Recap & Next

What the engine gained

  • A GPU device, owned properly — created, claimed to a window, and released in the correct order by a destructor rather than by discipline.
  • A report instead of assumptions. Driver, shader formats granted, swapchain format, present modes and frames in flight, every one asked for and logged at startup.
  • Your framebuffer on screen through SDL_GPU, by transfer buffer, texture and blit, bit-identical to what the rasterizer drew, with no shader anywhere in the program.
  • A frame graph drawn with fill_rect, showing the four places a frame's time goes — and four keys that move time between them while you watch.
  • A regression test on the object model: our enumerators are checked against SDL's, so "it is a rename" stays true rather than becoming folklore.

The sentence to carry forward is the one this lesson opened with, now with a number attached: a call records work rather than performing it, and on this machine describing 4.78 ms of work takes 0.19 ms — so the CPU spends 96% of that time free. Every object that was new in Figure 3 exists to manage the consequences: the device is the connection, the command buffer is the message, the transfer buffer is the shared ground, and the fence is how you find out it is done.

Two results are worth keeping in your hands rather than your notes. A full GPU sync on a display-bound frame costs nothing measurable — and on a GPU-bound one costs 1.60×; the difference is not the sync but the overlap you had to give up. And a measurement that beats the hardware's published ceiling is not a fast machine, it is a broken benchmark, twice over in our case.

What we have not done is draw anything. The GPU has cleared, copied and blitted, and every one of those is fixed-function work SDL performs on our behalf. To make the GPU compute a colour we need a program to run on it — and that program has to exist in three different binary formats, because Metal, Vulkan and D3D12 do not speak the same language.

Then, in 4.4, the first triangle the GPU has ever drawn for us — and §4.2's shaders granted line turns out to be the one that decides which file we load.
