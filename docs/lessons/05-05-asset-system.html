Module 5 — Becoming an Engine · Lesson 5.5

The Asset System v1

Last lesson built a reference that can be told it is out of date. That is the mechanism; today is the policy, and it answers three questions a pool does not: where a mesh comes from, how asking for it twice gives you the same one, and — the word this whole module has been building towards — how to unload it. Along the way we refuse to reference-count, and the argument for refusing is the same sentence that made handles worth having. We close the lifetime hole 5.4 deliberately left open. And we free a mesh out from under a scene that is still drawing it, on a keypress, to watch exactly one object disappear with a number next to it.

1The Problem

Lesson 5.4 ended with a pool that can say no. A handle resolves or it does not; a freed slot bumps its generation; a stale reference is a null pointer and a counter rather than undefined behaviour. That is a genuinely useful thing to own, and it answers exactly one question — is this reference still good?

Here are three it does not answer.

Take them one at a time, because each one has a receipt in the current source.

Loading. Here is what it took to put a model on screen before this lesson, with the comments removed so the shape is visible:

Assemble a path. Open a file. Parse it. Apply an import convention. Time it. Validate it. Free the previous one. Store the new one. Eight steps, in demo code, and only two of them — which file, and what to do if it is missing — are a program's business. The other six are the same six every program will write, slightly differently, until one of them forgets the uv flip.

Finding. There is no name-to-handle map anywhere in this engine, so there is no such thing as asking for an asset you might already have. Every request is a fresh load. Lesson 3.5 wrote a comment about this at the time, and it is worth quoting because it was a promissory note:

demos/sandbox/main.cpp, Lesson 3.5

“A real load, on a keypress, every time — not a cache lookup. It costs about half a millisecond for the torus and the HUD says so, which is the honest way to introduce the fact that asset loading is work. Module 5 caches; today we measure.”

Unloading. And this is the one that matters, because the other two are conveniences and this is a capability. Nothing in this engine has ever freed anything. Not once, in fifty-four lessons. Every mesh, texture and buffer ever created has lived until the process exited, which is why Lesson 5.4's whole argument had to be made in the abstract: the question "is this reference still valid?" had never once been answered no in a running program.

There is a fourth problem, smaller and more embarrassing. The engine currently has three answers to "where do files live", and none of them knows about the others: engine::asset_path in gfx/obj.cpp (whose own comment calls itself “a placeholder for Module 5's asset system”), shader_path in gfx/gpu_shader.cpp — written by copying the first — and the demo, which assembles std::strings around the first at three call sites. Three copies of one idea is the usual sign that the idea has no name.

2Building Intuition

2.1The lending library

Lesson 5.4's cloakroom took your coat and gave you a numbered ticket. A lending library is the same idea with three additions, and those additions are exactly this lesson.

First, you ask for a book by title, not by shelf. You do not walk in and say "give me whatever is in position 4,192"; you say "Dune", and somebody who knows where things are turns that into a shelf. That indirection is what lets the library reorganise, and it is what lets your library card from last year still work.

Second, there is one copy. If two people ask for the same title on the same afternoon, the library does not go and print a second one. This sounds obvious and it is the thing our engine currently gets wrong: press L twice and it reads the same 200 KB off disk twice, parses it twice, and hands you two unrelated meshes with identical contents.

Third — and this is the addition that changes the design rather than decorating it — books can be withdrawn. A library that only ever acquires is a warehouse. The moment withdrawal is possible, every card in every pocket becomes a question, and the library needs a policy: who is allowed to withdraw, what happens to somebody holding a card for a withdrawn book, and what happens to the photocopies somebody made of chapter four.

That last clause is not a joke. It is the derived-asset problem, and §3.2 is about it.

2.2A name is not a path

Before any of that, the smallest idea in the lesson and the one everything else stands on.

"torus.obj" is a name. It is stable, it is what a scene file records, it is what a level designer types, and it is the key an asset store caches on. /Users/…/build/demos/assets/torus.obj is a path: where that name resolved today, on this machine, with these roots. Store the first; compute the second.

Once names and paths are different things, the resolution step becomes a place you can put a policy — and the policy that earns its keep immediately is an ordered list of roots. A single directory needs no list. What a list buys is override: put a directory in front and everything in it shadows the shipped asset of the same name, without moving, renaming or deleting anything.

That one property is the mechanism behind four features that look unrelated:

  • Mods and user content. The mod folder goes in front.
  • Localisation and platform packs. assets_ja/ or assets_lowend/ goes in front, and every asset it does not contain falls through to the base.
  • Editing while the game runs. Your source tree goes in front of the copy CMake made beside the binary — which is half of Module 8's hot reload, arriving early and for free.
  • A test standing in for a real asset. Which is exactly what verify_55 §A does: it writes a deliberately different torus into an override root and proves, by file size, which one came back.

3The Theory

3.1Why not reference counting

"When may I free this?" has an obvious answer: count who is holding it, and free at zero. Reference counting is correct, it is well understood, and the standard library will do it for you. It is also the wrong answer here, and the reason is not performance. It is that reference counting requires a property our handles deliberately do not have.

Recall what a handle is, from Lesson 5.4: four bytes, trivially copyable, with no lifetime of its own. Every one of those words was load-bearing. It is four bytes so it fits in an ECS component; trivially copyable so it can be memcpy'd; without a lifetime so it can be written to a file and read back without pointer fixups.

Reference counting requires the opposite of all three. Copying must have a side effect, so the handle needs a copy constructor. Going out of scope must have one too, so it needs a destructor. And it must know whose count to touch, so it needs a pointer back to its store — which triples its size and makes it meaningless in a saved file.

A refcounted handle is a shared_ptr with extra steps, and we already know what shared_ptr costs. So the policy is explicit unload, and the interesting part is why that is safe to get wrong:

  • Forget to unload → a leak. A leak is found by a total, and asset_store::live_count() at shutdown is that total.
  • Unload too early → a lookup that returns null and a counter that goes up. Lesson 5.4 built exactly this: collect_stats::unresolved.

Neither is a crash, and neither is undefined. That is the trade, and it is the one most engines make at level granularity — load a level, play it, unload it, check that the count came back to zero.

This is not "refcounting is bad"

It is "refcounting is wrong for a reference that must stay a value". Where a reference is already an object with a lifetime, a count is often exactly right — gpu_texture's RAII wrapper is a count of one, honestly implemented. The question to ask is never "should this be refcounted?" but "what does this reference have to be able to do, and does a count take that away?"

3.2The one place a rule is unavoidable

Explicit unload works because a handle is held by somebody who can be told — a scene, a component, a piece of code with an owner. There is one class of asset for which that is not true, and Lesson 5.4 named it as an open hole rather than pretending otherwise.

with_normals takes a loaded mesh and produces a different mesh: a different vertex count, different normals, a different index buffer. It is a real asset, it occupies real memory, and it must be stored somewhere. But nobody asked for it. It has no name, nothing outside the system knows it exists, and it has no reason to exist except that its source does.

This shape is everywhere once you look: a texture and its mipmap chain, a shader and its per-backend variants, a mesh and its GPU upload, an animation and its compressed form. The general name is a derived asset, and the rule that governs it is not a reference count — it is a dependency edge:

The rule

A derived asset is owned by its source. Unloading a source unloads everything derived from it, transitively. Nothing outside the store can hold a derivation, so nothing outside the store has to be consulted.

Two words in that rule do real work. Transitively, because derivations chain — a mesh is imported, and the import is uploaded — and a cascade that stops after one hop leaks the tail. And owned rather than counted, because the relationship is one-directional and internal: there is exactly one source, it is known at the moment of creation, and it never changes.

There is a corollary worth stating, because it is the check that keeps the design honest: deriving from a source that is already gone must be refused. The result would be an asset with no name to find it by and no source to free it with — a thing nothing will ever release. Our derive_mesh returns a null handle in that case, which turns a guaranteed leak into a null the caller is already prepared to see.

3.3Import settings are identity

Here is a question that looks like bookkeeping and is not. Lesson 3.9 established that OBJ counts texture coordinates upward from the bottom left while a texture is addressed downward from the top left, and that reconciling the two belongs to the import step. The demo has a key that toggles it, so the disagreement can be looked at.

So: is torus.obj imported with the flip the same asset as torus.obj imported without it?

It is not, and the answer is not a matter of taste — the two have different vertex arrays. A store that keyed on the filename alone would hand the second requester the first one's geometry, silently, and the picture would be a mirror image of what was asked for. So the cache key is the name and the settings:

\[ \text{key} \;=\; \text{name} \;\Vert\; \text{settings} \] key = name + import settings

Every real pipeline does this. Unity writes a .meta file beside each asset and re-imports when it changes; Unreal keys its derived-data cache on a hash of the settings. Ours is one bool and a string, and the shape is the same. §4.4 has the subtlety that makes it work — and the bug that found it.

3.4Failure is the ordinary case

An asset system fails constantly, and not because it is badly written. Files are missing during development, misspelled in scene data, absent from a platform pack, corrupted by a partial download, or simply not shipped in a demo build. If a missing asset is an exception — in either sense — then a shipping game is a program in which the exceptional case is Tuesday.

Lesson 5.3 gave us the vocabulary and Lesson 5.4 gave us the mechanism, so 5.5 inherits an answer rather than inventing one:

  • An acquire that fails returns a null handle and a report — the report shape obj_report and image_report already converged on.
  • A null handle does not resolve, so collect_triangles skips that object and counts it (5.4 §4.7). One missing asset costs one object, never a frame.
  • The failure is logged once, at the point that knows why — which is 5.3's rule, and which this lesson broke on its first run and had to fix (§4.3).

Notice what is not in that list: no exception, no assertion, no fallback magenta mesh, no "return a default cube so something draws". A default that stands in for a missing asset is a decision only the game can make, and an engine that makes it has removed the game's ability to notice.

4Implementation

4.1The search path

Smallest piece first, and it is the one that dissolves §1's three copies. A search_path is a vector of roots and one function.

Two factories rather than one, and the second is the one that matters: beside_executable is now the only place in the engine that calls SDL_GetBasePath(). Assets, shaders and (Module 7) sounds each want their own root; they want the same rule for finding it, and one function is how you get one rule instead of one per subsystem.

resolve returns a report rather than a string, for Lesson 5.3's reason: the failure has to say enough to act on, and "" says nothing.

bytes is free and worth taking. SDL_GetPathInfo is documented as returning false when a path does not exist, and it fills in an SDL_PathInfo while it is there — so a store that wants to report how many bytes it read does not pay for a second look at the filesystem.

info.type == SDL_PATHTYPE_FILE is not defensive padding. Without it, resolve("shaders") reports success on the directory of that name and the caller fails later, inside a loader, with a much worse message. A directory that happens to share a name is not a hit.

The check that is not about correctness

Before any root is tried, a name containing .., an absolute name, and an empty name are all refused. Names come from scene files, from configuration, and eventually from users; a name that can climb out of every root is a name that can read /etc/passwd.

It is deliberately a syntactic check rather than a canonicalising one. Canonicalisation needs the filesystem, differs per platform, and is exactly the sort of clever code that grows a bypass. A name with .. in it is not a name we want to serve, whether or not it happens to resolve somewhere harmless today.

4.2The store, and what it holds

Now the store. Its state is five members and the interesting thing about them is how ordinary they are — Lesson 5.4 did the hard part.

That is worth pausing on. pool<T> was written knowing nothing about geometry, and images join it by naming it — no change to the container, no specialisation, no second implementation. Whether an abstraction is real is decided the second time it is used, and this is that second time.

Note also which type is the asset. image_data is what the file contained: RGBA8 rows, top row first, exactly as decoded, which is exactly what gpu_texture::create_sampled uploads. engine::texture — the sampler-ready form from Lesson 3.9 — is a different thing that you make from an image. Keeping them apart is the same distinction this lesson draws everywhere: what was loaded, versus what was derived from what was loaded.

4.3Loading, and the cache that is not a map

The map is not the truth. The pool is. That nested contains is the whole reason this cache can be trusted, and it is a direct dividend from Lesson 5.4: a map entry can be out of date, and a generational handle cannot lie about whether its asset is still there. So the map is treated as a hint — if it points at something the pool no longer has, the entry is dropped and the load proceeds.

A cache keyed on a raw pointer could never do this. It would have no way to ask.

Then the load itself, which is short because everything in it already existed:

The import step is here, and not in the parser, for the reason Lesson 3.5 settled and 3.9 restated: a loader stores what the file says, so that two loads of a file are diffable and a loader is never a place where data quietly differs from its source. Reconciling somebody else's convention with ours is a separate act, performed once, at the boundary where their data becomes ours. This function is that boundary.

A bug this lesson introduced and the first run caught

The failure path originally logged "asset_store: '%s' is in none of the roots" unconditionally — so a refused name (../../etc/passwd) produced two log lines: search_path's refusal, which says why, and the store's, which says less. That is precisely the double-reporting Lesson 5.3 forbade, reintroduced by the lesson after it.

The fix is the refused flag on resolved_path: the point that knows why logs it, and the point that only knows the name was wanted stays quiet. A rule you wrote down is not a rule you will follow; it is a rule you will notice breaking.

One naming hazard, worth a line because it produces a baffling error. engine::load_image is a free function in gfx/image.hpp, and asset_store::load_image is a member — so inside the class, the member hides the free function and an unqualified call fails with "too few arguments", which is a confusing way to be told about a name-lookup rule. The implementation calls engine::load_image fully qualified. (Lesson 5.4 hit the same shape with handle; it is the second time in two lessons.)

4.4One key space, and the bug that proved it

§3.3 said the cache key is the name plus the import settings. The obvious implementation is the one this lesson shipped first:

It passed everything except one check in verify_55 §D, one line after the check that stored the asset:

insert_mesh("cube", …) stored under "cube", because generated content has no import step and no settings to record. find_mesh("cube") looked up "cube|flip=1", because that is what the default settings encode to. Two key spaces wearing one name. Nothing crashed, nothing logged, and find_mesh simply answered "not resident" about an asset that was.

The fix is one line, and it generalises past this bug:

The general rule

The default configuration must serialise to nothing. asset_key("torus.obj", {}) is "torus.obj", and only a non-default import earns a suffix. Now generated and loaded content share one key space by construction rather than by discipline — which is the same shape of argument as Lesson 5.4 reserving generation 0 so that an all-bits-zero handle is null for free.

It also makes the key readable, which is not nothing: "torus.obj|flip=0" in a log tells you both what was loaded and that somebody imported it unusually.

4.5The cascade

Derived assets are stored as edges — a flat vector of {source, derived} handle bits — and released by walking them.

Collect first, then recurse, and the comment in the source says why: walking mesh_derivations_ while the recursion erases from it is the classic iterator-invalidation bug, and it shows up only for a mesh with more than one dependent — which the demo does not have and a real scene does. That is the worst kind of bug: correct in every test you would think to write.

The other half is the refusal:

An asset derived from a source that is already gone has no name to find it by and no source to free it with. Refusing turns a guaranteed leak into a null handle the caller is already prepared to see — which is the same move as pool::insert returning null when it runs out of slots.

And here is what the cascade did to the code that asked for it. Lesson 4.8's mesh cache used to own a private second pool with no rule connecting it to anything:

What the cache then has to do about an unloaded source is the part worth reading: nothing, except notice.

A hit whose geometry is gone is a miss, and its GPU buffers are this cache's to destroy — nobody else knows they exist. That is the only eviction this cache has, and it arrives for free: it is the same contains question a handle answers everywhere else. A cache keyed on a pointer could never have been told.

4.6Forty lines become one

The demo side is where the payoff is legible. §1's eight-step load is now:

Two behavioural changes hide in that diff and both are deliberate.

The flip is an import setting, not a step afterwards. §3.3's consequence: toggling it loads a second asset rather than silently rewriting the first, and the two coexist.

Loading no longer frees. The old load_model removed the previous mesh; the store keeps everything resident, because that is what a cache is. Cycling L round the five models reads five files once and is a hit for ever after. Freeing moved to its own function and its own key — because burying a free inside a load is how you get an engine where nobody can say what is resident.

That change broke a check in verify_54, written one lesson earlier, which asserted that loading a second model made the first handle stale. The harness was right to fail: it caught a real behavioural change. The check was updated to assert the new contract, with the reason written next to it — a test that is edited to match the code is only honest when the edit records what changed and why.

4.7The pressure to make it global

A handle is meaningless without its pool, so every function that resolves one needs the store — and the temptation to make it a singleton and stop passing it is real, and it is the single most common shape in engine code.

We refuse, and not for stylistic reasons. Lesson 5.4 ended with demos/sandbox holding two mesh pools in one frame, and 5.5's GPU probe adds a third store of its own. A store is a plain object precisely so that a program can have several:

  • a game and its editor, with different roots;
  • the level you are playing and the one streaming in behind it;
  • a test fixture and the real thing — which is exactly how verify_55 checks override ordering without touching the shipped assets.

Note also where a store is not: engine::platform and engine::app do not own one. Putting it there would be a singleton with better manners — every program would get exactly one, in one place, and the second store would be the awkward special case instead of the ordinary thing.

Read the torus row and there is only one number on it. The acquire is the parse. Finding the file is 0.0022 ms, reading 200 KB off disk is 0.0148 ms, flipping 2,352 texture coordinates is 0.0034 ms, and moving four vectors into the pool rounds to zero — together 0.55%. Parsing is the other 99.9%.

That is worth internalising because it is the opposite of the intuition. "Asset loading is slow because disks are slow" is a sentence from a different decade; on this machine the disk is a rounding error and the CPU work is everything. It is also why Module 8's cooked assets are a real optimisation and a faster file format would not be: the win is not reading fewer bytes, it is not parsing them.

And the starred column is a finding of its own. The demo validates every mesh it loads — Lesson 3.5's Euler characteristic, edge manifoldness, winding and signed volume — which is 2.45 ms, another 66% of the whole acquire, for a check the store does not perform and a shipping build would not. It is not a mistake; it is a development-time check that has been quietly doubling load times since Module 3, and it took separating the stages to see it. Cost you can see is cost you can choose.

And the cache: 3.693 ms → 0.00025 ms, about 14,771×. A hit is a hash of a short string, a map probe and one pool lookup. It is not "fast loading" — it is not loading, which is the only version of the idea that scales. A parser twice as fast would have moved 3.69 ms to 1.85.

7Build & Run

engine/CMakeLists.txt gains two sources and a new directory. The comment there is the reason it is not another file under gfx/: an asset system is not a graphics subsystem — it loads meshes, images, and in Module 7 sounds — and putting it under gfx/ would make the audio loader's home a joke six lessons before it is written.

What to look for. Run the software demo and watch the terminal:

  • Press L five times to cycle the models. The first lap says Loaded and files read climbs; the second lap says Cached and it stops. The HUD's load time goes from read 3.95 ms to cached 0.00 ms.
  • Press Bksp. The model vanishes. Nothing else changes, nothing crashes, and the HUD line becomes [Bksp] torus.obj UNLOADED handle 4:1 is stale, unresolved = 1. Press L to load something again.
  • Press 2 to toggle the uv flip, then L. Watch files read go up by one even for a model you have already loaded — that is §3.3, working: different import settings, different asset.
  • In the GPU demo (no flag), the mesh upload log now ends with [handle N:G], and the derived geometry is bound to it.

8Common Pitfalls & Debugging

1 · The asset is definitely there and find says it is not

Symptom. insert_mesh("cube", …) succeeded; find_mesh("cube") returns null.

Cause. Two key spaces. Whatever computes the key on the way in must be the same function that computes it on the way out — and it is startlingly easy for it not to be, because the two calls live in different functions with different parameters (§4.4).

Fix. One asset_key(), called by both, with the default configuration encoding to nothing. When debugging, print the key rather than the name: ours is readable on purpose for exactly this.

2 · A stale handle survives an unload

Symptom. You unloaded an asset and something still draws it, or a second load returns the old handle.

Cause. A name map treated as the truth. If load trusts its map entry without asking the pool, an asset freed by handle leaves a live-looking entry behind.

Fix. The nested contains in §4.3. The map is a hint; the pool is the truth. This is only possible because a generational handle cannot lie, which is the dividend Lesson 5.4 pays here.

3 · Memory climbs and every counter says zero

Symptom. live_count() is small and steady; RSS is not.

Cause. Almost always a derived asset with no edge recorded — something inserted directly rather than through derive_mesh, so nothing owns it and no cascade will ever reach it. The 5.4 version of this cache had exactly that shape and its own comment admitted it.

Fix. Anything the store produces from another asset goes in with derive_mesh. If you find yourself wanting to insert it with a name, ask who would ever ask for it by that name.

4 · remove during a walk of the derivations

Symptom. A crash or a missed release when unloading a source with two or more dependents. Works perfectly with one.

Cause. Recursing while iterating the vector the recursion erases from.

Fix. Collect the children into a local first, then recurse (§4.5). Note the shape of the bug: correct for every case a small test would cover. The demo has one dependent per mesh, so the demo would never have found it.

5 · Two log lines for one missing file

Symptom. A refused or absent name produces a pair of errors, the second less informative than the first.

Cause. Both layers logged. Lesson 5.3's rule is that the point which knows why logs, and callers propagate silently.

Fix. Give the report enough shape to distinguish the cases — resolved_path::refused — so the caller can tell "already reported" from "mine to report". This lesson broke the rule on its first run; the flag is the fix.

6 · It works from the build directory and nowhere else

Symptom. ./build/demos/sandbox finds its assets; cd /tmp && /path/to/sandbox does not.

Cause. A root relative to the working directory rather than to the executable. It is the oldest bug in asset loading and it is invisible to whoever wrote it, because they always run it the same way.

Fix. search_path::beside_executable, which is the only caller of SDL_GetBasePath(). If resolve is failing, print paths().roots() — the roots are the first thing to look at and the last thing people check.

9Exercises

  1. 9.1 — Ship a mod. Make a directory beside the executable, put a different torus.obj in it (save_obj(make_torus(8, 6, …)) will do), and prepend_root it in sandbox. Confirm the demo draws your torus without touching a single asset in assets/. Then move the root to the end with add_root and confirm the shipped one wins again.

    Hint

    assets.store.paths().prepend_root(…) before anything is loaded. If you do it after, nothing happens — and why nothing happens is the more interesting half of this exercise.

    Solution sketch

    It works, and doing it after the load does not, because the name is already resident: resolution happens once, at acquire. That is the correct behaviour and it is also the reason real engines make the search path immutable after start-up, or invalidate the cache when it changes. Adding asset_store::rescan() — unload everything whose resolved root has changed — is a genuinely good next step and is most of what Module 8's hot reload needs.

  2. 9.2 — Find the leak. Add a ~asset_store (or an explicit report_leaks()) that logs at warn if live_count() is not zero, listing the names. Run the demos. Then decide whether what it reports is a leak or a program that simply exits with assets loaded — and what the difference is.

    Hint

    Every demo will report non-zero, because none of them unloads at shutdown. Is that a bug?

    Solution sketch

    It is not a leak — the store owns everything and its destructor frees it — but it is the same shape as one, and that is the point. A leak check is only useful with a policy about when the count should be zero. The usual answer is a level boundary: assets loaded during a level must be gone after it, and anything surviving is either a bug or deliberately global. That distinction is what a real engine's asset tags or bundles encode, and it is the honest reason unload_all() exists.

  3. 9.3 — Make the flip a real import setting. Add a second field to mesh_import — a uniform scale, say, or "generate normals if absent" — and make it part of the key. How much code has to change? Then measure: how many bytes does a key cost at a thousand assets, and at what point would you hash it instead?

    Hint

    asset_key and mesh_import. Nothing else should need touching, and if it does, that is the finding.

    Solution sketch

    Two functions, because the defaulted operator== and the "default encodes to nothing" rule do the rest. At a thousand assets with readable keys you are spending a few tens of kilobytes on strings — nothing. The crossover is not size, it is settings count: once a key would be forty characters of encoded booleans it has stopped being readable, which was its only advantage over a hash, and Module 8's on-disk cooked-asset cache is where that happens.

  4. 9.4 — Unload during a frame. Call unload_mesh from inside the object loop of collect_triangles (temporarily; a non-const pool and a hack are fine). Predict what happens before you run it.

    Hint

    Lesson 5.4's one rule: resolve late, use immediately, never store. What does the loop hold across the call?

    Solution sketch

    The loop resolves once per object into a const mesh_data* and works through it for the whole object — so unloading mid-object invalidates that pointer and the rest of the object reads freed memory. The handle was fine; the resolved pointer was not. This is the strongest possible demonstration that handles do not make pointers safe, they make them unnecessary to keep, and it is why real engines defer asset destruction to a frame boundary rather than doing it inline. Deferring is a good thing to build next: queue the unload, drain the queue between frames.

  5. 9.5 — Images are not textures. §4.2 says image_data is the asset and engine::texture is something you make from one. Make one: write engine::texture to_texture(const image_data&), store it as a derived asset, and let the software rasterizer sample a loaded PNG for the first time in this course.

    Hint

    image_data is RGBA8 bytes, row-major, top row first; engine::texture is Uint32 ARGB. You will need a second pool — and deciding whether a pool<texture> belongs in the store or beside it is most of the exercise.

    Solution sketch

    The conversion is twenty lines. The design question is the real one, and the answer this course would give is: in the store, as a derived asset, because it satisfies the §3.2 test exactly — nobody asks for it by name, it exists only because its image does, and it should die with it. Which means derivation needs to record kinds as well as handles, and that is the honest limit of the v1 in this lesson: it derives meshes from meshes only, and the header says so.

10Recap & Next

The engine can now find, share and free the things it draws. Concretely: an ordered search path that turns a name into a path in one place (and is now the only caller of SDL_GetBasePath()); a store that loads an asset once and hands the same handle to every later request; derived assets whose lifetimes are bound to their sources, transitively; and an unload you can press a key to perform while a scene is drawing, which costs exactly one object and says so.

The two arguments worth carrying forward are both refusals. We did not reference-count, because a count would have required a handle to stop being a value — and being a value is the entire reason a handle is worth having. We did not make the store global, because sandbox holds three of them and a singleton would have made the second one the awkward case. In both, the argument was made from a property the code actually has rather than from a preference.

And two honest limits, recorded rather than hidden. Derivations are mesh-to-mesh only; a texture and its mipmaps need the edge to carry kinds, and Exercise 9.5 is where that starts. And unloading is immediate rather than deferred to a frame boundary, so it is safe between frames and Exercise 9.4 shows precisely what happens if you do it during one.

Next: 5.6 — Data-Oriented Design: Why Scene Trees Creak. Everything since 5.1 has been about structure — where code lives, who owns what, how things refer to each other. 5.6 is the first lesson in the module that is about speed, and it makes the argument the ECS will be built on: not with dogma, but with a cache-line diagram and a measurement taken on our own engine. Lesson 5.4 already handed it two numbers to start from — scene_object is 96 bytes, and pool::items() is a contiguous span of exactly the live objects. 5.6 asks what those two facts are worth, in nanoseconds, and the answer decides the storage design in 5.7.

11Further Reading

  • Game Engine Architecture, Jason Gregory — §7 (Resources and the File System) and §16.2. The standard treatment, and the one to read next: mount points, resource GUIDs, the offline/online split, and the argument for a cooked format that this lesson's measurement points straight at.
  • Yosoygames, “The Resource Manager” / Ogre's ResourceGroupManager docs. A production search-path implementation with named groups, worth reading for how far the "ordered roots" idea scales before it needs more structure.
  • Unity Manual — “Assets, Objects and serialization” and the .meta file format. §3.3's argument in a shipping tool: import settings live beside the asset, changes to them trigger a re-import, and the identity of an asset is file + settings.
  • Unreal Engine — the Derived Data Cache. The same idea as §3.2 at industrial scale: everything computed from a source asset is keyed on a hash of the source plus the settings, and invalidated together.
  • Niklas Frykholm, “Managing Decoupling Part 2: Data Compilers.” Why the expensive half of loading is parsing rather than reading, and what an offline compile step buys — the natural sequel to §5's timing table.
  • Sean Barrett, stb_image.h's header comment. Still worth reading for the "why we don't hand-roll this" argument, and for a decoder's-eye view of what load_image is doing while a mesh parse dominates everything around it.
  • SDL3 wiki — SDL_GetPathInfo, SDL_GetBasePath, SDL_GetPrefPath. The last of those is the root this lesson does not add: writable per-user storage, which is where saves and screenshots belong and which Module 8 will want.
