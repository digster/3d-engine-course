Module 4 — To the GPU: SDL_GPU · Lesson 4.3

The Shader Toolchain

One HLSL file has to become three different binaries, because Metal, Vulkan and D3D12 do not speak the same language — and then SDL has to be told four numbers about it that only the compiler knows. This lesson builds that pipeline into CMake, and finds out what the tool actually does rather than what its documentation implies.

1The Problem

Lesson 4.2 ended with your rasterizer's picture on screen, carried entirely by SDL_GPU. Every object in the API existed except one, and the reason we could get that far without it is that clearing and copying are things the hardware does without being told how. The moment you want the GPU to compute a colour, you need a program to run on it.

So write one. Here is a fragment shader, in about the smallest form that does anything:

Now hand it to SDL. The signature is the obvious one — SDL_CreateGPUShader(device, &info) — and the trouble starts with what info wants:

Read the first two fields again. code is a pointer to bytes, and format says which kind. Nowhere in this struct is there a place to put HLSL. There is no SDL_GPU_SHADERFORMAT_HLSL, and it is not an oversight:

The gap

A GPU does not run text. Metal wants MSL or a precompiled metallib; Vulkan wants SPIR-V; D3D12 wants DXIL. These are not dialects of one language — they are different binary formats produced by different compilers, and the API that has to work on all three cannot take sides. So SDL takes bytes and asks you which flavour they are.

That means something has to turn one source file into three binaries, and it is not SDL. It is not part of your program either, if you have any sense. It is a build step you do not have yet.

And then there is the second half of the struct, which is stranger. SDL wants to be told how many samplers, storage textures, storage buffers and uniform buffers the shader uses. You wrote the shader; you could count them. But look at what SDL's own FAQ says about that, from the header's overview:

"Another common issue is not setting the correct number of samplers, textures, and buffers in SDL_GPUShaderCreateInfo. If possible use shader reflection to extract the required information from the shader automatically instead of manually filling in the struct's values."

The API's own documentation names this as a leading cause of shaders that do not work, and tells you to have a machine count instead. That is a strong hint, and this lesson takes it — §4.4 shows the numbers being read out of a file the compiler writes. But first, the more interesting question: why is getting them wrong so easy to do and so hard to notice? §5 of this lesson measures the answer, and it is worse than you would guess.

2Building Intuition

2.1Why there is a hub in the middle

Three target formats from one source suggests three compilers: HLSL→SPIR-V, HLSL→DXIL, HLSL→MSL. That is not how it is built, and the reason is the same reason a compiler has an intermediate representation at all.

Writing n front ends and m back ends as n×m direct translators is a quantity of work nobody has ever finished. Put one neutral format in the middle and it becomes n+m. SPIR-V is that middle: a binary intermediate representation for shaders, designed by Khronos, and — importantly — a format with a good decompiler. SPIRV-Cross reads SPIR-V and writes MSL, HLSL, GLSL or a description of what the shader needs.

So the real pipeline has exactly two stages, and only the first is a compiler in the usual sense:

Figure 1 is worth reading for its shape before its numbers. Everything to the right of the hub is translation from SPIR-V. That has an immediate practical consequence that this lesson ran into head first: if the front end is missing, you do not lose one backend — you lose all of them, because there is no SPIR-V for the second stage to work from.

The numbers say the same thing from the other side. The HLSL→SPIR-V hop measured 12.3 ms and each SPIR-V→anything hop measured 1.5 ms. The front end is doing eight times the work of a translation, because it is the part that has to parse a language, resolve types, and optimise.

2.2Offline, and what that actually buys

SDL_shadercross ships as both a library and a command-line tool, so this pipeline can run inside your program at startup instead of at build time. That is genuinely convenient — edit a shader, relaunch, see it — and this course does not use it. The reason is worth stating precisely, because the obvious reason is wrong.

It is not about time. Compiling all four of this lesson's shaders through all three hops takes 61.2 ms. You could do that at every launch and no user would notice.

It is about what you would have to ship, and what could fail:

  • The compiler goes in the box. Runtime translation means shipping SPIRV-Cross — 6.7 MB on this machine — and, for HLSL input, DirectXShaderCompiler, which is a fork of LLVM. That is a large dependency to carry so that every copy of your game can redo a computation whose answer never changes.
  • A compile can fail on someone else's machine. An offline build fails on your machine, where you can read the message. The same failure at a customer's launch is a black screen and a bug report that says "it does not work".
  • You cannot inspect what you did not produce. When the picture is wrong, being able to open the generated MSL and read it is worth a great deal — §5.4 does exactly that to catch a renamed function.

So: compile offline, ship binaries, and keep the tool on the developer's machine. Runtime cross-compilation is the right answer for a shader editor, a material system with user-authored nodes, or a tool that must accept shaders it has never seen. It is the wrong answer for a game that knows its own shaders at build time.

2.3The tool, honestly described

SDL_shadercross is a separate libsdl-org project from SDL itself, and this lesson has to be careful about how it describes it, because the description that would be convenient is not accurate.

⚠ Verify

Checked while writing this lesson, and worth re-checking rather than trusting: the installed headers declare SDL_SHADERCROSS_MAJOR_VERSION 3, and the packaged metadata says Version: 3.0.0. But the upstream repository has no tags and no releases at all.

This matters practically. Our CMakeLists.txt pins SDL with GIT_TAG release-3.4.12, and the comment beside it says "never a branch name". You cannot do that here, because there is no tag to name. Pin a commit SHA instead — it is exactly as reproducible and rather less pretty. If you find tags have appeared since, prefer them.

Two more facts about the tool that follow from how it is built, and that decide what your machine can do:

  • It is two libraries in a coat. HLSL→SPIR-V is DirectXShaderCompiler; SPIR-V→everything is SPIRV-Cross. Both are optional at build time.
  • A build without DXC cannot read HLSL at all. Not "cannot produce DXIL" — cannot read the source language. The machine this lesson was written on has exactly such a build, and asking it to compile our vertex shader produces: ERROR: Failed to compile SPIR-V From HLSL: Shadercross was not built with DXC support.

That is not a disaster, and it is not a reason to write the lesson around a machine that does not exist. The first hop is a job several tools can do — glslc, from Google's shaderc, compiles HLSL to SPIR-V with one flag — so §4.2 builds a CMake step that asks the tool what it can do and picks a route accordingly. Which is a better habit than the one it replaces, so the accident is worth keeping.

3The Theory

3.1Register spaces, and why they are not yours to choose

In HLSL you declare where a resource lives with a register annotation: t0 for the first texture, s0 for the first sampler, b0 for the first constant buffer, and a space to disambiguate. Under SDL_GPU the space is not a free choice. The header states the layout, and it differs per stage:

The four rows of Figure 2 are the whole rule, and the right-hand column is what makes them checkable. When HLSL is compiled to SPIR-V, a register space becomes a descriptor set, and SDL's SPIR-V rules are stated in those terms — vertex uniform buffers in set 1, fragment textures in set 2, fragment uniform buffers in set 3. So the two halves of the header's documentation are one rule wearing two notations, and you can confirm your own shader landed correctly with a disassembler:

The texture and its sampler landed in set 2, the constant buffer in set 3 — which is what space2 and space3 in the source asked for, and what SDL requires of a fragment shader. Nothing here was taken on trust.

The failure mode, and why it is nasty

Put a fragment shader's constant buffer in space1 instead of space3 and everything still works: it is valid HLSL, it compiles, it translates, it loads, and it runs. At which point it reads whatever happens to be bound at the slot it named — usually nothing, sometimes the vertex stage's data.

There is no error anywhere in that chain, because every stage did what it was told. The symptom is a shader that returns black, or a constant that never changes. Check it with the disassembler above, at the moment you write the declaration, rather than debugging it later from the picture.

3.2Semantics, and the one that is different

HLSL attaches a semantic to every value crossing a stage boundary — the : TEXCOORD0 after a field. They exist because D3D matches a vertex buffer's contents to a shader's inputs by name rather than by position, and SDL_GPU has to say something about them since it targets D3D12 too:

"Shader semantics other than system-value semantics do not matter in D3D12 and for ease of use the SDL implementation assumes that non system-value semantics will all be TEXCOORD. If you are using HLSL as the shader source language, your vertex semantics should start at TEXCOORD0 and increment like so: TEXCOORD1, TEXCOORD2, etc."

So the practical rule is short: name every user-defined input and output TEXCOORDn, numbered from zero, in order. The names carry no meaning — a normal is not more "TEXCOORD" than a colour is — and the numbering is what actually binds. Skip a number and the attribute that arrives is not the one you meant.

System-value semantics are the exception, and they are the ones that do mean something. SV_Position names the clip-space position the rasterizer itself consumes — the vec4 our vertex pipeline has been producing since Lesson 2.10, complete with the w that Lesson 2.7 spent a lesson explaining. SV_Target0 names the first colour attachment of the render pass. These are not conventions you may rename; they are how the shader talks to the fixed-function hardware around it.

3.3The four counts

Now the fields SDL's FAQ warns about. Why does SDL need to be told what the shader plainly contains?

Because SDL does not read your shader. It receives an opaque blob in one of three formats and passes it to a driver. Parsing DXIL to count its registers would mean shipping a DXIL parser inside SDL, and doing the same for SPIR-V and MSL, for a fact the application already knows. So the API asks. The counts let SDL size the descriptor sets and validate the bindings you later make against what the shader claims to want.

Which raises the obvious question: what happens if you lie? Here is textured.frag, which genuinely has one sampler and one uniform buffer, created four times with four different sets of counts:

Figure 3 is that experiment, and all four were accepted. Ninety-nine samplers on a shader with one — created, no error, no warning. So SDL_CreateGPUShader validates nothing here, and the mistake the FAQ calls common is a mistake nothing in the creation path will catch for you. The damage shows up later, when something binds resources against a count that does not describe reality.

That is the argument for reflection, and it is not "it saves typing". It is that there is no other check. Every other error in this lesson is caught by something — a bad register space by the disassembler, a wrong entry point by SDL itself, a missing file by the loader. This one is caught by nobody, so the number must come from a machine that read the actual compiled code.

Which shadercross will do, in the same run that compiles the shader:

Worked example — counting by hand, and then checking

Count the resources in textured.frag.hlsl yourself before reading on. The file declares:

  • Texture2D<float4> albedo : register(t0, space2) — one sampled texture, which pairs with…
  • SamplerState albedo_sampler : register(s0, space2) — …one sampler. SDL counts the pair once, as num_samplers = 1.
  • cbuffer Tint : register(b0, space3) — one uniform buffer.
  • No storage textures and no storage buffers: those are the read-write resources of Module 8's compute work, and nothing here declares one.

So by hand: smp 1, tex 0, buf 0, uni 1. And the reflection file says samplers 1, storage_textures 0, storage_buffers 0, uniform_buffers 1. They agree — for all four shaders, as §B of the harness checks.

The agreement is the point, and so is doing it anyway. Hand-counting is right today and wrong the first time somebody adds a texture and forgets the struct. The file is regenerated by the build every time the shader changes, which is a property no amount of care gives you.

3.4The entry point you did not write

One field of the create-info remains, and it is the one that fails first for most people. entrypoint is the name of the function to call. Our HLSL says:

So the entry point is "main". Except that on this machine, it is not:

Figure 4 is the answer, and the top row is the cause: main is a reserved identifier in Metal Shading Language — MSL is C++-derived, and main means something there. SPIRV-Cross therefore renames it on the way through, and the generated MSL declares vertex main0_out main0(main0_in in [[stage_in]]). Pass "main" and SDL asks Metal for a function that does not exist.

The good news is in the bottom half of Figure 4: this failure is caught at creation. "main0" created a shader; "main" and a deliberate nonsense name were both refused, with SDL logging Creating MTLFunction failed. Compare that with §3.3's silent acceptance of nonsense counts and you have the two halves of this API's temperament in one page: it checks the name and not the numbers.

The ninety-percent picture

The rename is a property of the SPIRV-Cross MSL backend, not a law of nature, and the missing ten percent is that other paths differ: a metallib compiled by Apple's own tools keeps whatever name its source used, and the SPIR-V path keeps main because SPIR-V has no reserved words. Our loader therefore ties the entry point to the format rather than to the shader, which is the only place the knowledge belongs.

Why an unattached custom command does nothing

add_custom_command(OUTPUT ...) does not create a build rule that runs. It declares how to produce a file if somebody needs it. If no target lists that file as a dependency, nothing ever asks for it, and the command never runs — with no error, because nothing failed. You get a successful build and an empty output directory.

The fix is the three lines above: wrap the outputs in a target, and make the executable depend on it. The string(REPLACE) is there because our shader names contain a dot (triangle.vert) and CMake target names may not.

gpu_shader::load is four steps, and the first is the payoff of a line Lesson 4.2 logged and promised to use:

Note where the entry point lives: on the format, not on the shader. §3.4's rename is a property of how MSL was produced, so it belongs beside the format that says so. Store it per shader and you have four copies of one fact.

Then the file, the reflection, and the creation. One decision inside is worth defending:

A missing or malformed reflection file is a refusal, not a fallback to zeros. Given §3.3's measurement — that SDL accepts any counts you give it — falling back to zero would mean quietly building the exact bug the file exists to prevent. Failing loudly at startup is the better outcome by a wide margin.

C++ in place — a struct is not always a mirror

shader_resources holds four Uint32s: exactly the four fields of SDL_GPUShaderCreateInfo that this class cannot know for itself. It is deliberately not a mirror of the whole create-info, even though the rest of this engine mirrors SDL structs enthusiastically (Lesson 3.9's sampler, Lesson 4.1's fill_style).

The boundary is drawn at what must be discovered. The code, its size, the format, the stage and the entry point are all things the caller knows. These four are things only the compiled shader knows. Drawing a type's edge along that seam is what makes "read them from a file" the obvious implementation rather than a workaround.

4.4A parser that is allowed to be small

The reflection file is JSON, and this engine has no JSON parser. It gets one of about thirty lines, which scans for four known keys and reads the integer after each — and that is a decision that deserves defending rather than sliding past, because in Lesson 3.5 exactly the opposite decision was made for OBJ.

The difference is trust. parse_obj reads files a user supplies, from the internet, possibly hostile and certainly malformed — so it validates everything, reports a line number, and has a status enum. This file was written by a compiler we invoked ourselves, three seconds ago, into a directory we created. It is not a trust boundary, and building a general JSON parser to read it would be answering a question nobody asked.

What it must still do is refuse rather than guess, which is what §G of the harness checks: a missing key, a non-numeric value, an empty file and the substring trap ("num_samplers" must not satisfy a search for "samplers") are all rejected. Small is allowed; sloppy is not.

4.6Where the compile actually happens

One measurement remains, and it produced the most interesting result in the lesson. How long does SDL_CreateGPUShader take?

Figure 6 is the answer, and the middle bar is barely visible for a reason: eight microseconds. All four shaders created, cold, in 0.028 ms — against 61.2 ms to compile them at build time. And the first measurement of a shader is the same as the ninth, so this is not a cache.

Read that and disbelieve it

Eight microseconds cannot include turning MSL into machine code for a 20-core GPU. Lesson 4.2's rule applies — check that the number can be true — and it is not true. What is true is that the compile has not happened yet.

The prediction, which Lesson 4.4 is going to check: it happens at pipeline creation. Only there does the driver know the colour target's format, the depth state, the blend mode and the vertex layout — and machine code for a fragment shader must be specialised to all of them. That is exactly what Lesson 4.1 measured as the real reason immutable pipeline objects exist, and exactly what SDL_gpu.h means when it lists pipelines under things created once: "Render pipelines (precalculated rendering state)".

A shader object, then, is not a compiled program. It is a compiled-enough program — a validated blob plus the four counts — waiting to be told what it will be used with. We will find out in the next lesson whether that is right.

That reframes what this lesson bought, and the reframing is the honest summary of offline compilation. The 61.2 ms it moved out of your program's startup is the front end: the parse, the type checking, the optimisation, the megabytes of compiler that would otherwise be in the box. What it cannot move is the driver's own final step, which happens on the user's machine because only the user's machine knows what the user's GPU is.

7Common Pitfalls & Debugging

The build succeeds and the shader directory is empty

Symptom. No compile errors, no warnings, and no output files. The program then reports that it cannot read a shader.

Cause. An add_custom_command(OUTPUT ...) with nothing depending on its output. It describes how to make a file; if no target wants that file, the rule is never run and nothing has failed.

Fix. Wrap the outputs in an add_custom_target and add_dependencies(your_exe that_target), as §4.2 does. Remember that CMake target names cannot contain a dot, so triangle.vert needs string(REPLACE "." "_" ...) first.

Failed to compile SPIR-V From HLSL: not built with DXC support

Symptom. shadercross runs, prints that error, and produces a zero-byte file.

Cause. The tool was built without DirectXShaderCompiler — usually a clone without --recursive. Its version number does not reveal this; only running it does.

Fix. Rebuild with submodules, or install glslc and let the CMake fall back for the first hop. Note what you cannot do: produce DXIL. That hop is DXC.

dyld: Library not loaded: @rpath/libSDL3_shadercross.0.dylib

Symptom. The shadercross binary refuses to start, saying it cannot find its own library. Reason: no LC_RPATH's found.

Cause. An install that put the executable and the shared library in the right places but did not record where to look. Nothing to do with your project.

Fix. Add the sibling lib directory to the loader path. cmake/Shaders.cmake does this for you, deriving the prefix from the executable's own location and using the right variable per platform (DYLD_LIBRARY_PATH, LD_LIBRARY_PATH, PATH).

SDL_CreateGPUShader fails with "Creating MTLFunction failed"

Symptom. The file loads, the format is right, and creation still returns null.

Cause. The entry point name. Your HLSL says main; the generated MSL says main0, because main is reserved in Metal Shading Language.

Fix. Tie the entry-point string to the format, as choose_shader_target does. And be glad about this one: §3.4 measured it being refused at creation with a message, which is the kindest failure in the lesson.

The shader loads, runs, and reads nothing

Symptom. A texture samples as black, or a constant never changes. Everything created successfully and no call returned an error.

Cause. Either a wrong register space (§3.1) or wrong resource counts (§3.3). Both are silent: the space is valid HLSL that names the wrong slot, and the counts are accepted by SDL without validation — measured, including 99 samplers on a shader with one.

Fix. For the space, spirv-dis | grep DescriptorSet and compare with Figure 2. For the counts, never type them: read them from the reflection file the compiler wrote, and refuse to load if it is missing.

The vertex attributes arrive scrambled

Symptom. Geometry is inside out or a colour appears where a normal should be. Nothing errors.

Cause. Semantic numbering. SDL assumes every non-system-value semantic is TEXCOORDn numbered from zero, so a gap or a repeat maps an input to the wrong buffer element.

Fix. Number them from TEXCOORD0 upwards with no gaps, in the same order as the vertex layout you will describe in Lesson 4.5. The reflection file's inputs array lists what the compiler thinks the locations are — read it when in doubt.

Editing a shader changes nothing

Symptom. You edit the HLSL, rebuild, run, and see the old behaviour.

Cause. Usually the copy step rather than the compile: the shader was rebuilt into build/shaders/ but the program is reading a stale copy next to an executable somewhere else.

Fix. Check the timestamps of both. Our POST_BUILD copy runs on every successful link, so the usual culprit is running an old binary from a different directory. And note that the dependency chain is real: touching a .hlsl re-runs all three hops for that shader and nothing else.

Move textured.frag.hlsl's cbuffer Tint from space3 to space1. Rebuild. Predict, before you look, what will fail: the compile, the reflection, the load, or nothing. Then check with spirv-dis and with the running program.

Hint

Ask what each stage of the chain knows. Does the HLSL compiler know which stage this shader will be? Does shadercross? Does SDL, at creation?

Solution sketch

Nothing fails. It compiles, reflects, translates and loads — the uniform-buffer count is still 1, because there is still one buffer; only its set changed. The error is undetectable until something binds a uniform buffer and the shader reads a slot nobody filled. That is why this lesson's answer to register spaces is a disassembler rather than a compiler flag.

4.3.2 — Make the counts lie, and find out when it matters

Hard-code num_samplers = 0 in gpu_shader::load, ignoring the reflection, and run. Then keep the lie in place through Lesson 4.4 and 4.7, and record the first moment anything notices.

Hint

§3.3 already tells you creation will not notice. The candidates are pipeline creation (4.4), the bind call (4.7), and the picture.

Solution sketch

This is a genuinely open exercise and worth keeping notes on, because the answer is backend-specific: a validation layer may object at bind time, or nothing may object at all and the sampled texture comes back black. The transferable result is the shape of the bug — a lie told at creation, detected at use, on a machine that may not be yours. That is why the reflection file is not a convenience.

4.3.3 — Add DXIL, or prove you cannot

Get a shadercross with DXC support: clone it with --recursive and rebuild. Reconfigure our CMake and read the -- Shaders: line. If DXIL appears, compare the file sizes with Figure 3; if it does not, find out from the build output which dependency is missing.

Hint

The probe in cmake/Shaders.cmake is the fastest way to test: it is one execute_process whose exit code is the whole answer. You can run the same command by hand.

Solution sketch

With DXC present the configure line becomes "shadercross reads HLSL directly (built with DXC)" and the format list gains dxil. DXIL is a bitcode format and is typically several times the size of the equivalent SPIR-V — a fact worth measuring rather than believing, since it decides how much of your package is shaders on Windows.

4.3.4 — Read the whole reflection

Our scanner reads four integers and ignores the inputs and outputs arrays. Extend shader_resources to record the vertex inputs — name, type and location — and log them at startup. Then, in Lesson 4.5, use them to check the vertex layout you describe by hand.

Hint

The arrays make the file no longer a flat list of key–integer pairs, so the thirty-line scanner will not stretch to them honestly. Decide deliberately: a slightly larger scanner for a known shape, or a real JSON parser. §4.4's trust argument still applies.

Solution sketch

The payoff arrives next lesson but one: a vertex layout that disagrees with the shader is another silent failure, and the compiler already knows the right answer. Checking a hand-written layout against the reflection at startup turns a class of "why is my mesh inside out" into an assertion with a name in it.

4.3.5 — Time the front end against the back end

Measure each hop yourself — HLSL→SPIR-V, SPIR-V→MSL, SPIR-V→JSON — over ten runs, taking minimums. Then make the shaders substantially bigger (unroll a loop, add a hundred lines of arithmetic) and measure again. Which hop grows, and what does that tell you about where the work is?

Hint

Lesson 3.10's rules apply to processes as much as to functions: warm up first, take minimums for anything compiler-shaped, and change one thing at a time.

Solution sketch

On this machine the front end is 12.3 ms against 1.5 for each translation — an eight-to-one split before you make anything bigger. Growing the shader should widen it, because parsing and optimising scale with the source while a SPIR-V-to-MSL translation is closer to a walk over instructions. The reason this matters: it is the front end that offline compilation removes from your program, and it is the expensive half.

9Recap & Next

What the engine gained

  • A shader toolchain in the build. Four HLSL sources become SPIR-V, MSL and a reflection file at build time, with a configure-time probe that finds out what the installed tool can actually do instead of assuming.
  • A shader loader that chooses. The format comes from what the device says it accepts, the entry point comes from the format, and the resource counts come from the compiler's own reflection.
  • A refusal to guess. A missing or malformed reflection file fails the load rather than defaulting to zeros — because §3.3 measured that nothing downstream will catch the mistake.
  • A windowless device. gpu_device::create(nullptr, …) now gives a device with no swapchain, which is what a shader harness — and, later, any offscreen or compute work — actually wants.

Two findings are worth carrying rather than filing. SDL checks the entry-point name and not the resource counts — one failure arrives immediately with a message and the other arrives silently, much later, so they need completely different defences: for the name, just get it right; for the counts, never type them at all.

And the thing called CreateShader does not compile the shader. Eight microseconds says so. What we have built is a validated blob and the numbers that describe it, waiting to be told what it will be used with — which is a strange sort of object until you remember Lesson 4.1's conclusion about why pipelines exist, at which point it is exactly the object you would expect.

Next: 4.4 — The First Triangle. A pipeline object built from these two shaders, a render pass, and three vertices. It is more code than you expect and every line of it earns its place — and somewhere in it, the compile that did not happen in this lesson finally does. We will time it and find out.
