Module 6 — Advanced Rendering · Lesson 6.17

A Lightweight Frame Graph

The engine can now record seventeen render passes in a frame, and there is no single place where a frame happens. Three types begin their own passes, two are handed one, and the rules that keep them in the right order live in prose, in three different headers, checked by nothing. This lesson makes the frame a declaration instead of a sequence of calls — and the interesting part is what that buys, because the usual sales pitch turns out not to apply. Frame graphs are sold on memory aliasing. We measure it on this engine's own frame and find that perfect aliasing would save 14.3%, that SDL_GPU 3.4.12 has no primitive capable of expressing any of it, and that even with one the frame is a chain and a chain has almost nothing to alias. What the graph actually buys is sharper: four facts that a human currently maintains by hand become derived from one statement each — the pass order, every load op, every store op, and which passes run at all. The load op is the case that stings, because Lesson 6.13 wrote a whole paragraph warning what happens when you get one wrong and described the symptom as looking "like a tuning problem rather than a load op". Here it is not a decision. Then eleven bloom passes disappear because nothing reads them, five currently-silent mistakes become named compile errors, and the compiled frame comes out bit-identical to the hand-written one across 262,144 channels — with a control proving the comparison can tell the difference.

1The problem: seventeen passes and no author

Sixteen lessons of Module 6 have each added a capability and, quietly, a render pass. Lesson 6.8 added a depth-only pass that begins itself. Lesson 6.9 turned that one into four, one per cascade. Lesson 6.12 added a full-screen resolve that is handed a pass by its caller. Lesson 6.13 added eleven more and put them inside a single render() call. Every one of those decisions was right at the time, and the result is that this engine can record a modern frame and has nowhere that a modern frame is recorded.

That is not rhetoric. Run verify_617 and the first thing it does is count:

Seventeen passes across four owners, two of which open their own attachments and two of which expect somebody else to. And the count is the less interesting half. The interesting half is the list of things that have to be true for that frame to be correct, none of which any compiler, validation layer or test currently checks:

  • The shadow passes run before the scene pass, because the scene pass samples what they wrote. gpu_shadow.hpp says so in a comment.
  • render_bloom runs outside a render pass — it begins eleven of its own — and resolve_into runs inside one. gpu_post.hpp says so in a comment, and it has to, because the two functions look interchangeable from their names.
  • The bloom runs before the tonemap curve, because it is looking for values above 1 and the curve is what removes them. gpu_post.hpp says so in a comment, at length, and correctly.
  • The scene's depth attachment stores DONT_CARE; the shadow map's stores STORE. Lesson 4.7 reasoned the first out in a comment and explicitly predicted the second, which Lesson 6.8 then wrote — also in a comment.

A comment is not a mechanism. Every rule above is correct, well argued, and invisible to the program. Get one wrong and the failure is not a compile error: it is a picture that is subtly wrong, or a driver validation message emitted from inside a function three call levels below the mistake. Lesson 6.13's own comment says it best about the one it was most worried about — the symptom "looks like a tuning problem rather than a load op".

So the question this lesson asks is not "how do we schedule passes efficiently". It is: which of these facts is a decision, and which is a consequence? That turns out to be a much better question, because almost all of them are consequences, and a consequence that is written down by hand is a second copy of the truth.

And a warning about the sales pitch

If you have read about frame graphs before, you have read about memory aliasing: two transient targets whose lifetimes do not overlap can share one allocation, so a frame with twenty intermediates pays for the peak rather than the sum. That is the headline in every talk on the subject, and it is genuinely why Frostbite built theirs.

We are going to measure it, in §7, on this engine's own frame — and it is going to come out at zero. Not "small". Zero. The reasons are worth knowing before you build one of these for the wrong motive, and they are two separate reasons that must be told apart. Building the thing anyway is still right, and §4 is why.

2Count the passes before proposing anything

There is a failure mode in architecture lessons where the architecture arrives first and the problem is retrofitted to fit it. The defence is cheap: enumerate what exists, with numbers, before proposing anything. Lesson 6.13 did this when it counted its own eleven passes and said plainly that the bloom issues more render passes than the entire rest of the frame. That sentence is the reason this lesson has something concrete to justify itself against.

Two things jump out of that table and neither is the seventeen.

The first is the split ownership. Two entries begin their own passes and two do not, and there is a real reason for each: gpu_shadow_map owns an attachment nothing else can ever share, while gpu_scene_renderer draws into a target the caller chose and might want to share with a skybox or a debug overlay. Both arguments are sound and the result is an API where you cannot tell, from a call site, whether you are inside a render pass or not. That is exactly the condition under which people write SDL_BeginGPURenderPass inside a render pass and get a null back.

The second is eleven. Lesson 6.13 derived that number — a pyramid of n levels needs one bright pass, n−1 downsamples and n−1 upsamples, because a render pass writes one set of colour targets and no pass may read the texture it writes. Eleven passes for one effect is the number any proposed architecture has to earn its keep against, and it is also the reason this lesson has a real test case: eleven passes with genuine dependencies between them is enough structure to be wrong in interesting ways.

3Building intuition: a resource is a sequence of values

Here is the observation the whole lesson rests on, and it is worth sitting with before any code, because everything else is bookkeeping once you have it.

When we say "the HDR target", what do we mean? Today we mean an SDL_GPUTexture* — one object, written by the scene pass, then written again by the skybox, then read by the bloom and the resolve. And that is why we cannot say anything precise about it. "The bloom reads the HDR target" is ambiguous: does it read the image the scene produced, or the image after the skybox filled in the background? Both are "the HDR target". They are different pictures.

So stop letting the name mean a texture. Let it mean a variable, and let a variable have values over time:

hdr@0 — undefined.
hdr@1 — what the scene pass produced.
hdr@2 — what the skybox produced from hdr@1.

Now "the bloom samples hdr@2" is unambiguous, and — this is the part that pays — it is a statement with consequences a program can compute. It says the bloom must run after whoever produced hdr@2. It says hdr@2 must be written out to memory rather than discarded, since somebody reads it. It says the resource is alive from the skybox pass through the bloom. None of those three facts had to be stated; all three follow.

If this feels familiar, it should. This is single static assignment — the form every optimising compiler converts your code into before it does anything clever with it — applied to render targets instead of to registers. A variable that is assigned once and never mutated makes "who produced this value" a question with exactly one answer, and almost every dataflow analysis becomes easy once that is true. Frame graphs are, structurally, a tiny SSA compiler whose instructions are render passes. Yuriy O'Donnell's 2017 GDC talk on Frostbite's is where this framing entered graphics, and it is the single best thing to read after this lesson.

The one rule that makes it work

A version is produced by exactly one pass. That is not an implementation restriction, it is what makes the model mean anything: if two passes both claimed to produce hdr@2, then "reads hdr@2" would not identify a picture. So when the API sees two passes both writing from hdr@1, it does not pick one and it does not schedule around it. It reports that the author has said something ambiguous, names both passes, and refuses. §5 of verify_617 is that check firing.

Why not simply "pass B depends on pass A"?

You could imagine a simpler API: let each pass name the passes it must follow. It would be less machinery, and it would be worse, for a reason worth stating because it is the same reason Lesson 5.10 gave for actions over keycodes and Lesson 6.16 gave for extracting planes from the matrix rather than from the camera.

A hand-written dependency is a second copy of a fact that already exists in the code. The bloom's bright pass reads the scene target; that is true in the shader, in the binding, and in the author's head. Writing "bright depends on scene" beside it creates something that can disagree with it — and when it does, the symptom is a correct-looking declaration and a wrong picture. Declaring reads and writes states the fact once, in the place the pass already had to know it, and the ordering is then derived rather than asserted. Everything in §4 is downstream of that choice.

4One statement, four derived facts

Take the single hardest line in the engine's existing post stack — the upsample's load op — and watch what happens to it. Here is how it reads today, in gpu_post.cpp, with Lesson 6.13's comment attached:

"LOAD, NOT DONT_CARE, and this is the one load op in the chain that is load-bearing. The upsample blends src + dst, so the destination's existing contents are an operand; discard them and the additive blend has nothing to add to, which turns the pyramid from a sum of every level into just the widest one. The symptom is a bloom that is far too soft and far too dim, and it looks like a tuning problem rather than a load op."

Every word of that is right, and it is a warning rather than a mechanism. Under the graph, the upsample pass says one thing instead: 

level[i - 1] = fg.keep(up_pass, level[i - 1]);

keep means: my output depends on what was already in this target. It is a statement about data, not about SDL — a pass author can answer it without knowing what a load op is. And four separate facts fall out of it.

4.1 — The ordering edge

keep consumes the incoming version and produces the next one. Consuming a version means depending on whoever produced it, so an edge appears from that pass to this one. Nobody wrote "the upsample runs after the downsample"; the upsample said it reads what the downsample wrote, which is the same fact stated where it is actually known.

4.2 — The load op

keep → SDL_GPU_LOADOP_LOAD
clear → SDL_GPU_LOADOP_CLEAR
discard_write → SDL_GPU_LOADOP_DONT_CARE

Three spellings, one per answer to "what does this pass do with what was already there?" — build on it, replace it with a known value, or overwrite every texel of it. Note that this has not abolished the decision; it has moved it, from an API enum to a dataflow statement. That is the honest description and it is still a large win, because the dataflow statement is one the author can answer correctly without knowing the API, and because the same statement then pays for the three facts below.

discard_write is a promise, and it is the one spelling that can still betray you. DONT_CARE means "I write every texel", and a pass that writes only some of them reads undefined memory in the rest. The graph cannot check that — it would have to know what the shader covers. What it can check, and does, is the other half: a keep on a version nobody produced is caught at compile time (§9's validation rule (a)), which is the mistake that actually happens.

4.3 — The store op of the other pass

This is the one that surprises people, because it is a consequence for a pass other than the one that made the statement. If the upsample reads level[i]@1, then whoever produced level[i]@1 must actually write it out to memory rather than discarding it at the end of its pass. So:

STORE if and only if some live pass consumes this version, or the resource is imported. DONT_CARE otherwise.

One rule, and it reproduces two decisions this course argued about at length, four lessons and nine lessons apart. Lesson 4.7 gave the scene's depth buffer DONT_CARE and wrote: "nothing reads this buffer after the pass ends… Module 6's shadow maps and depth-based post-processing are where this has to become STORE." Lesson 6.8 duly wrote STORE and cited that prediction. Both sentences are now unnecessary: verify_617 §D checks the derived ops against the hand-written ones and every one matches, including those two.

4.4 — The lifetime

A resource is alive from the first scheduled pass that touches it to the last. That interval is what §7 colours, and it is also what tells the pool whether a texture can be handed to somebody else. It is the fourth thing you get for free from the same sentence.

A worked example, small enough to check by reading

Three passes and two resources. out is imported — a texture somebody outside the graph owns, such as the swapchain image. 

const fg_texture tmp0 = fg.create("tmp", desc);
const fg_texture out0 = fg.import("out", swapchain, desc);

const int blur    = fg.add_pass("blur",    &exec_blur,    &blur_ctx);
const int combine = fg.add_pass("combine", &exec_combine, &comb_ctx);
const int unused  = fg.add_pass("unused",  &exec_unused,  &un_ctx);

const fg_texture tmp1 = fg.discard_write(blur, tmp0);      // tmp@0 -> tmp@1
fg.sample(combine, tmp1);                                  // reads tmp@1
const fg_texture out1 = fg.clear(combine, out0, black);    // out@0 -> out@1
const fg_texture tmp2 = fg.discard_write(unused, tmp1);    // tmp@1 -> tmp@2

Push the numbers through by hand before reading the answer. blur produces tmp@1. unused consumes tmp@1 and produces tmp@2. combine consumes tmp@1 and produces out@1. Nobody consumes tmp@2.

So: combine writes an imported resource, which makes it a root. blur produced a version combine reads, so blur is reachable. unused is reachable from nothing — it produces a value that nothing consumes — so it does not run, and neither would anything that existed only to feed it. The schedule is blur, combine, and the frame issues two render passes for three declared ones.

That is the entire compiler, on three passes. The real one runs on fourteen and does the same four things.

5Culling: what feeds the outside world

The worked example used a word without defining it. out was imported, and that made combine a root. Why that and not something else?

Because an import is the only thing in a frame whose value is observable after the frame ends. A transient exists to feed something; if nothing it feeds reaches the outside world, it was computed for nobody. So:

A pass survives if and only if it transitively feeds a write to an imported resource.

That is one sentence, it needs no present() call and no "this pass has side effects" flag, and it is computed by backward reachability iterated to a fixed point — at most P rounds for P passes, which is fourteen here and finishes in two.

What it does to the bloom

Now watch it do something real. gpu_post_stack::render_bloom begins today with: 

if (!s.enabled) { return; }

That line is correct and it is also a second place where a dependency is written down. The first place is in the tonemap shader, which samples t1 and multiplies by bloom_intensity. When the intensity is zero the shader does not need the bloom, and somebody had to notice that and add the flag.

Under the graph, the resolve pass either samples the bloom's finished level 0 or it samples the 1×1 stand-in. Nothing else changes. Here is what verify_617 §E reports when it declares exactly the same fourteen passes and changes only that one sample call: 

declared: 14 passes
live:     3
culled:   11

culled, by name:
  bloom bright
  bloom down 1 .. bloom down 5
  bloom up 5 .. bloom up 1

Eleven passes disappeared, along with the six pyramid textures they needed, because nothing reads them. No flag exists anywhere in the graph; nothing in frame_graph.cpp knows what a bloom is. And the same mechanism handles the cases nobody wrote a flag for: a debug overlay whose output is not composited, a depth prepass nobody samples, a shadow cascade for a light that got switched off this frame.

The first time a pass you wanted gets culled, it will look like the pass is broken. You will see no draws, an empty RenderDoc capture, and a black target. The diagnosis is always the same and it is always upstream: nothing reads what this pass produced. That is why dump_frame_graph exists and why it prints the culled list by name — the answer is one function call away, and without it you will spend the afternoon in the pass body.

6The schedule, and why determinism is correctness

With edges and a live set, ordering is Kahn's algorithm: repeatedly emit a pass whose dependencies have all been emitted. It is six lines. Two details about it are not incidental.

6.1 — Ties are broken by declaration order, always

At any point several passes may be ready. Which one you pick is free — any topological order is legal — and that freedom is a trap. Pick by iterating a hash map, or by whichever pass a std::sort happened to leave first, and the same declarations can produce different schedules on different runs.

Does that matter, if every order is legal? Yes, and the reason is worth generalising well beyond frame graphs. A legal reordering changes floating-point rounding the moment two passes write to the same target, changes which texture the pool hands to whom, and changes what a capture looks like. The symptom is a golden-image test that fails one run in five. By the time anyone has noticed the pattern, the scheduler is the last thing they suspect — they are three days into the shader.

So the loop scans passes in declaration order and takes the first ready one. It is the slowest possible implementation of "pick a ready pass" and it is the right one, because the property it buys is that the same declarations always produce the same schedule. §3's check compares the compiled order against the hand-written order name for name, and that check would be meaningless against a scheduler that was allowed to wander.

6.2 — A cycle must be named, not merely detected

If no pass is ready and passes remain, there is a cycle. Kahn's algorithm detects this for free: the loop simply runs out of candidates. What it does with the detection is the design decision.

Returning false is useless. The graph knows exactly which passes never became ready and how many dependencies each is still waiting on, so it logs them: 

ERROR: frame_graph: cycle - these passes never became ready:
ERROR: frame_graph:   'A' (waiting on 1)
ERROR: frame_graph:   'B' (waiting on 1)

It is worth noticing how hard a cycle is to write. You cannot do it by accident with this API, because write returns the new handle and you can only pass a handle you already hold — so to build one, verify_617 §F has to construct a version handle by hand for a pass that has not been declared yet. That is a feature of the API rather than of the detector, and it means the cycle check is cheap insurance rather than a core mechanism.

7The memory claim, measured

Now the promise from §1. Lifetimes are computed; a pool can hand one texture to two resources whose intervals do not overlap. How much does that save on this engine's frame?

The bars answer it, and the answer is nothing. Descriptor-keyed reuse saves 0 bytes of 1,223,296. That is not a disappointing result to be buried in a footnote — it is the most useful thing in this lesson, provided the two reasons behind it are kept apart, because they have completely different consequences.

7.1 — Reason one: SDL_GPU cannot express aliasing at all

Memory aliasing, as the literature means it, is two resources placed at the same offset in one allocation. Vulkan has vkBindImageMemory onto a VkDeviceMemory you allocated; D3D12 has CreatePlacedResource onto a heap. SDL_GPU has neither. Checked against SDL3/SDL_gpu.h at version 3.4.12: there is no placed resource, no heap, no aliasing flag, and no way to ask for a texture that shares storage with another.

So the strongest form of reuse available here is handing back a whole texture whose descriptor matches exactly — same width, height, format, sample count, layer count, depth-ness, sampled-ness. That is strictly weaker, and in this frame it is weaker by everything. Look at the Gantt chart: shadow is 256×256 sampled depth, 262,144 bytes, and it dies at pass 1. bloom 0 is 128×128 RGBA16F, 131,072 bytes, and is born at pass 2. Those 262,144 dead bytes could comfortably hold 131,072 live ones, and there is no call in the API that asks for it.

7.2 — Reason two: a chain has nothing to alias

Suppose SDL_GPU grew placed resources tomorrow. How much would we then save? That number is computable from the lifetimes alone: it is the largest total of simultaneously-live bytes, the peak rather than the sum.

StrategyBytes (256×256 frame)ShareWhat it is
no sharing at all1,223,296100.0% one texture per transient — today

So the entire prize is 174,720 bytes — 14.3%, and we collect none of it. At a resolution anybody actually renders at, the same frame declared at 1920×1080 with a 2048 shadow map gives 45.00 MB unshared against 39.73 MB with perfect aliasing: an unreachable 5.27 MB. Which, if you work out what is in it, is exactly the bloom pyramid — the whole chain would fit inside the shadow map's memory after the shadow map dies, and cannot be asked to.

And 14.3% is small for a reason that is structural rather than accidental:

Read the Gantt bars again. hdr spans the entire schedule, because the resolve reads it at the very end. All six pyramid levels are live simultaneously at the turn between the down chain and the up chain — which is not a quirk of our implementation, it is what an additive pyramid means: every level must survive until the upsample that adds it back. Our frame is a chain, and in a chain almost nothing is dead while anything else is alive.

7.3 — And the mechanism does work, on a frame shaped for it

It would be easy to conclude from the above that the pool is dead code, so §7 of the harness builds the smallest graph that uses it: a scene, two half-resolution effects applied one after the other, and a composite. Effect A's scratch target dies before effect B's is born. 

effect A scratch -> pool slot 1   live [1, 2]
effect B scratch -> pool slot 1   live [3, 4]
one texture per transient :    786432 B
pooled                    :    655360 B  (saved 131072)

Both land on one texture and the saving is real. That is the shape a post-processing stack takes as it grows past two effects — SSAO, screen-space reflections, depth of field and motion blur each want scratch targets they finish with — and it is the shape to watch for. Until then, the pool costs a dozen lines and saves nothing, and both halves of that sentence should be said out loud.

The general problem here has a name and it is worth knowing you are not solving it. Assigning intervals to the fewest resources is interval graph colouring, which for intervals on a line is solvable optimally by a greedy sweep — and that is what the pool does, visiting resources in order of first use. What makes real frame-graph allocators hard is not the colouring; it is that with true aliasing the "resources" have different sizes and alignments, which turns it into bin packing with lifetimes, and that is where the published work goes.

8What a frame graph must never reorder

A scheduler that moves work around is a scheduler that can move work that was not allowed to move. Two things in this engine are ordered for reasons that are semantic rather than data-dependent, and a graph that reordered either would be silently wrong. They are worth stating precisely, because the reasoning is the interesting part and it generalises.

8.1 — The blended tail (Lesson 6.11)

Lesson 6.11 established that opaque geometry may be drawn in any order, because the z-buffer resolves visibility, and that blended geometry must be drawn back to front, because over is not commutative. order_draws sorts the transparent bucket by view depth and the renderer issues it in that order.

Could this graph break that? No, and the reason is structural rather than lucky: the graph orders passes, not draws. Everything inside a pass body is recorded by the callback, in the order the callback issues it, and the graph has no visibility into it at all. The blended tail lives inside gpu_scene_renderer::render, one pass, and is untouchable from here.

That is a real architectural boundary and it is worth naming as one. The unit of scheduling is the render pass. If you ever find yourself wanting the graph to reorder draws, you are proposing something much more dangerous, and the first thing it would need is a way to know which draws commute — which is exactly the knowledge blend_style encodes and exactly the knowledge a pass callback has and the graph does not.

8.2 — Instanced batching (Lesson 6.16)

One lesson ago, batch_instances started permuting the opaque draw list so that objects sharing a mesh, material, texture, normal map and style could be issued as one instanced draw. That permutation is legal because the z-buffer makes opaque order free — the same property, used the other way round. And 6.16 refuses to batch blended geometry, which is the same rule again.

Again the graph cannot touch it, for the same reason. But notice what would happen if the boundary were drawn one level lower: a scheduler that could reorder draws would happily interleave a batched opaque run with a blended one, and the failure would be a transparent surface compositing against a background that had not been drawn yet. The symptom is a window showing the skybox through a wall.

The general rule, which is worth carrying past this lesson: a dependency graph can only respect the constraints you declared. Ordering that comes from data (this pass reads what that one wrote) is safe to hand over. Ordering that comes from semantics (this composite is not commutative) is not, unless you have found a way to declare it — and until you have, it must live inside an atom the scheduler cannot open. Here the atom is the render pass.

9Implementation: the compiler

Everything above is now about six hundred lines, most of which is comment. The types come first, because they are the design.

9.1 — A handle is a resource and a version

struct fg_texture
{
    static constexpr Uint16 k_none = 0xFFFFu;

    Uint16 index = k_none;   ///< which resource
    Uint16 version = 0;      ///< which value of it

    [[nodiscard]] bool valid() const { return index != k_none; }
};

Four bytes, copied by value everywhere, and the version is what makes the type earn its keep. hdr@1 and hdr@2 are different C++ values, so sampling the pre-skybox image where you meant the post-skybox one is a different variable name rather than an identical pointer. That is Lesson 5.4's handle argument — an index is not a pointer, and being unable to dereference it is the feature — with a second field carrying time.

9.2 — Three verbs for a write, one for a read

void       sample(int pass, fg_texture h);
fg_texture discard_write(int pass, fg_texture h, Uint32 layer = 0);
fg_texture clear(int pass, fg_texture h, SDL_FColor colour, Uint32 layer = 0);
fg_texture keep(int pass, fg_texture h, Uint32 layer = 0);

A write takes a version and returns the next one. That return value is the entire ordering mechanism: you cannot name a version you were not handed, so the only way for a later pass to read this pass's output is to have received the handle from it. The dependency graph is built out of ordinary C++ data flow, which is why it is hard to write a cycle and impossible to write a dangling read.

The version bump lives on the resource, not on the handle — it counts writes to the resource rather than adding one to whatever the caller passed. That matters in exactly one case and it is the case you want caught: writing an old version, hdr@0 after hdr@1 already exists, means "throw away the scene and start again", and counting on the resource makes it a second producer rather than two passes both claiming to have made hdr@1.

9.3 — compile is four passes over two arrays

Step 1 — validate. Three rules, each of which is a currently-silent bug:

  • A sample or a keep on version 0 of a transient. Version 0 is undefined contents; today that reads whatever the pool's previous tenant left behind, which in a real engine is last frame's bloom, faintly, in this frame's image.
  • Two writes from the same input version — the ambiguity §3 defined the model to exclude. Both passes are named in the message, because "there is an ambiguity" is useless.
  • Attachments that disagree about dimensions or sample count. Lesson 6.14 established that every attachment in a pass shares its sample positions, so a 4× colour target beside a 1× depth target is a pass that cannot begin. The driver says so too — at SDL_BeginGPURenderPass, by which point the frame is half recorded.

Step 2 — cull, by backward reachability from imported writes (§5).

Step 3 — order, by Kahn with a declaration-order tie-break (§6).

Step 4 — derive. Load ops from the declared fg_init; store ops from "does any live pass consume this version"; lifetimes from first and last scheduled touch; and then the pool.

9.4 — Why a function pointer and not std::function

using fg_execute_fn = void (*)(const fg_pass_context& ctx, void* user);

std::function is the obvious choice and it is the wrong one here, for a reason that is measurable rather than stylistic. std::function type-erases: it stores any callable, which means it must either fit the callable in a small internal buffer or put it on the heap. The buffer is typically two or three pointers. The lambdas you would actually write here — capturing a renderer, a settings block, a draw list, a handle or two — do not fit, so every one of them allocates.

A frame graph is rebuilt every frame. That is one allocation per pass per frame, invisible, inside something whose whole purpose is organisation. §8 of the harness replaces the global operator new and counts: 

heap allocations across 200 declare+compile cycles : 0

Zero, because the graph's arrays are fixed-capacity members of an object the caller keeps across frames, and because a function pointer plus a void* is two words that never allocate. The cost of that choice is real and should be stated: the context structs must outlive the graph, because it points at them. In the harness they live in one frame_decl beside the graph, for exactly one frame.

The compile itself costs 8.62 µs in the steady state — 0.05% of a 16.67 ms frame, and roughly one three-hundredth of what Lesson 6.16's culling test costs on a scene of 45,512 boxes. It is O(P² × A²), because producer_of is a linear scan called from inside two more loops. That is fine at fourteen passes and would not be at two hundred; the fix is an index from (resource, version) to its producer, built once per compile, and it is Exercise 3.

9.5 — The declaration, in full

Here is the fourteen-pass frame as verify_617 declares it, with the bloom chain trimmed to one representative stage of each kind. Read it for what is not in it. 

// ---- Pass 1: the shadow map -------------------------------------------
d.pass_shadow = fg.add_pass("shadow", &exec_shadow, &d.shadow);
const fg_texture shadow1 = fg.clear_depth(d.pass_shadow, shadow0, 1.0f);

// ---- Pass 2: the scene -------------------------------------------------
d.pass_scene = fg.add_pass("scene", &exec_scene, &d.scene);
fg.sample(d.pass_scene, shadow1);
const fg_texture hdr1   = fg.clear(d.pass_scene, hdr0, black);
const fg_texture depth1 = fg.clear_depth(d.pass_scene, depth0, 1.0f);

// ---- Pass 3: the bright pass -------------------------------------------
fg.sample(bright, hdr1);
level[0] = fg.discard_write(bright, level[0]);

// ---- Passes 4..8: the downsamples --------------------------------------
fg.sample(down_i, level[i - 1]);
level[i] = fg.discard_write(down_i, level[i]);

// ---- Passes 9..13: the upsamples ---------------------------------------
fg.sample(up_i, level[i]);
level[i - 1] = fg.keep(up_i, level[i - 1]);

// ---- Pass 14: the resolve ----------------------------------------------
fg.sample(resolve, hdr1);
fg.sample(resolve, level[0]);
d.h_ldr = fg.clear(resolve, ldr0, black);

No SDL_BeginGPURenderPass. No load op. No store op. No statement of order — and yet the order is fully determined, because level[i] is a C++ variable that gets reassigned by each write and every pass names the value it actually wants. The one line carrying real judgement is fg.keep in the upsample, and it says something about arithmetic rather than about SDL.

10Two functions that had to be cut in half

A pass under the graph is recorded into an attachment the graph opened. Two of this engine's types opened their own, so both needed splitting — and how that split was done matters more than it looks.

10.1 — gpu_shadow_map::render_into

The easy one. Everything from the viewport onwards moved into a new render_into(cb, pass, items, count, cam, log), and the old render became a begin, a call to it, and an end. One copy of the viewport, the pipeline bind and the draw loop.

The interesting detail is what did not come along: the layer parameter. Under the graph, which cascade a pass writes is part of the write declaration, because that is the only place that can also know whether the previous cascade's contents must survive. Pulling it out of the function signature is the split doing its job.

10.2 — gpu_bloom::record_stage

The harder one, and the more instructive. The bloom's eleven passes are three kinds — a bright pass, n−1 downsamples, n−1 upsamples — differing in pipeline and source. So: 

enum class bloom_stage { bright, down, up };

void record_stage(SDL_GPUCommandBuffer* cb, SDL_GPURenderPass* pass,
                  bloom_stage kind,
                  SDL_GPUTexture* source, Uint32 source_w, Uint32 source_h,
                  const bloom_settings& s, float exposure) const;

Note what is absent: the destination. A stage does not know where it is writing, because the destination is the pass's attachment. A function that never sees a load op cannot get one wrong, which is the same move as the shadow map's missing layer and is the whole shape of this refactor.

The source's dimensions are parameters rather than being read off the texture, and that is not fussiness. The bright pass's texel_size is the scene's — one texel of the thing being sampled, not of the thing being written, and its target is half its source's size. Confusing the two produces a glow of the wrong radius and no error, so the signature keeps the distinction explicit exactly where 6.13's uniform packing did.

10.3 — And the old path now goes through the new one

gpu_bloom::render was not left alone beside record_stage. It was rewritten to call it eleven times, with a begin and an end around each. That is not tidiness, it is what makes §11's comparison mean anything: if the hand-written chain and the graph chain were two separate copies of the same draw code, a bug in one would probably be in both, and a bit-identical result would prove nothing. Sharing the draw code means the comparison tests exactly what it claims to test — the assembly, not the drawing.

This is the rule this engine has now paid for three times. Lesson 5.1 found four hand-transcribed test harnesses that had drifted. Lesson 6.15 found two spellings of one ARGB packing. Lesson 6.16 split begin_frame out rather than copy ninety lines into a second draw loop. Two copies of one rule is how a shadow behaves differently on two renderers for a reason nobody can find.

11The instrument, and proving it can fail

A refactor this size needs a test whose failure would be unmissable, and the course's usual one is no use here. golden_617 renders through the software rasterizer, and this lesson touched frame_graph.*, gpu_shadow.* and gpu_post.* — none of which soft_renderer.cpp or raster.cpp includes. So it is structurally incapable of noticing anything, for the third lesson running. It was run anyway, and it is byte-identical for the twenty-sixth lesson, and that is a null result rather than a pass.

The real instrument had to be built, and its shape is the obvious one once stated: render the same frame twice — once assembled by hand exactly as Lesson 6.13's harness did, once compiled from the declaration in §9.5 — and compare the pixels. 

channels compared : 262144
differing         : 0
largest delta     : 0
centre pixel      : hand 252   graph 252

Bit-identical, which is the strongest result available: not "within tolerance", not "looks the same", but every one of 262,144 channels equal. Fourteen passes, four of them with load ops that differ from their neighbours', eleven of them bloom, and the compiled schedule produced exactly the frame the hand-written one did.

And the control, which is the part 6.16 taught us to add

One lesson ago, golden_615.cpp was found to compare two files as strings and print identical=YES when both reads failed — two empty strings are equal. It had been run from the right directory every time, so the bug never fired, and it had been reported as evidence for a whole lesson.

So this comparison is made to fail on purpose. The same routine is pointed at the graph frame rendered with the bloom disabled: 

control: the same comparison against a bloom-less frame
differing         : 196608

196,608 of 262,144 channels differ — three quarters, which is the RGB channels of every pixel, the alpha channel being 255 in both. The instrument can report a difference. Now the zero above means something.

A test that can pass without testing anything is worse than no test, because it is believed. The habit worth taking from this — and it is the third member of a family this course has been building since 6.14 — is: establish what your instrument can see before you read it. 6.14 checked that a measurement could produce a non-null result; 6.15 checked that a non-null result had converged; 6.16 checked that a swept axis could show the effect at all. This one checks that a comparison can report a difference.

12The ninety-percent picture

Four things this graph deliberately does not do. Each is a real limitation with a real consequence, and knowing them is what separates using one of these from being surprised by one.

12.1 — No subresource versions

A version covers the whole texture. So four cascade passes writing four different layers of one array serialise into sm@1 → sm@2 → sm@3 → sm@4, even though they are completely independent — each has its own camera and writes its own slice.

It costs nothing today, because a command buffer submits its passes in order regardless and the driver is free to overlap them. It would cost something on an API with parallel queues, where the graph's false serialisation would prevent real overlap. The fix is a version per (layer, mip) rather than per resource, and it roughly doubles the bookkeeping — it is Exercise 4.

12.2 — No async compute, no queues, no split barriers

SDL_GPU presents one graphics timeline to this API, so there is nothing to schedule across. A Vulkan or D3D12 frame graph spends much of its complexity deciding what can run on the compute queue alongside the graphics queue and where the semaphores go. None of that exists here, and pretending otherwise would be building machinery for a capability the API does not have.

12.3 — Textures only

Every cross-pass resource in this engine is a texture. Buffers would be the same machinery with a different descriptor and a different creation call; nothing about versions, culling or ordering changes. When Module 9's job system and compute work arrive, that is the extension to make.

12.4 — One command buffer

execute records into the command buffer it is handed. Splitting a frame across several buffers, for parallel recording, is a Module 9 concern and it interacts with the job system rather than with this file.

15Common pitfalls & debugging

A pass you wrote does not run, and its body never executes

Symptom: a black target, an empty RenderDoc capture for that pass, breakpoints in the callback never hit.
Cause: it was culled. Nothing reads what it produced, transitively, all the way out to an imported resource.
Fix: call dump_frame_graph and look for it in the culled list. The usual mistake is sampling the wrong version downstream — reading hdr1 when the pass you care about produced hdr2 — which leaves the producing pass feeding nothing.

The picture has last frame's content faintly in it

Symptom: ghosting, or a target that is almost right but tinted.
Cause: a discard_write on a pass that does not in fact cover every texel. DONT_CARE is a promise, and a pooled texture's previous tenant is whatever was there.
Fix: use clear. It costs a full-target write and it is the right default until you have checked the coverage claim. This is the one load-op mistake the graph cannot catch for you, and §4.2 says so.

compile returns false and the log says "which result did later passes mean?"

Symptom: two passes named, both writing one resource.
Cause: you reused a handle. Both passes wrote from the same input version, so each produced a different output and nothing downstream can say which it wanted.
Fix: thread the handle through. The second writer should take the first writer's return value, not the value they both started from — which also tells the graph the order you meant.

The bloom is far too soft and far too dim

Symptom: a glow that looks like one wide blur instead of a sum of scales.
Cause: the upsample declared discard_write instead of keep. The additive blend had nothing to add to, so the pyramid collapsed to its widest level.
Fix: keep. This is exactly Lesson 6.13's warning surviving into the new world in a new spelling — with the improvement that the symptom now has a named cause you can grep for, and that a keep on an unwritten version is caught at compile time.

Everything renders, then the app crashes or renders garbage next frame

Symptom: the first frame is correct; later frames are not, or it crashes in execute.
Cause: a context struct went out of scope. The graph stores a void* and calls back into it; nothing keeps those objects alive.
Fix: put the contexts in one struct that lives beside the graph, as frame_decl does. This is the cost of the function-pointer design and it is worth knowing rather than discovering.

A pass cannot begin, and the driver blames the attachment

Symptom: SDL_BeginGPURenderPass returns null mid-frame.
Cause: attachments that disagree about dimensions or sample count.
Fix: compile now catches this before anything is recorded and prints both sizes. If you see the driver's version instead, you are on a path that bypasses the graph.

The golden fails one run in five

Symptom: intermittent pixel differences with no code change.
Cause: a non-deterministic schedule. Ties between ready passes were broken by something that is not stable across runs.
Fix: break ties by declaration index, as §6.1 does. If you replace the ready scan with a priority queue for speed, the comparator must be a total order, and declaration index is what makes it one.

16Exercises

1 — Make a pass disappear, then explain it (guided)

Take the declaration in §9.5 and delete the fg.sample(resolve, level[0]) line without touching anything else. Predict, before running, how many passes will be culled and which. Then run it and check with dump_frame_graph.

Hint: the answer is not eleven. Solution sketch: it is eleven, but only because the six pyramid textures are transient. Ask yourself what would happen if bloom 3 had been imported — because somebody wanted to inspect it in a debug view — and then try it. One import re-roots half the chain, and the passes that come back are exactly the downsamples.

2 — Add a depth prepass (guided)

Declare a pass before the scene pass that writes only the depth target with the same draw list, then have the scene pass keep_depth instead of clear_depth. Check what the derived store op on the prepass's depth becomes, and why.

Solution sketch: STORE, because the scene pass now consumes that version — where before the depth's only version was consumed by nobody and got DONT_CARE. You have just made the engine pay a tile-memory write-out, automatically, because you declared a dependency. That is the store rule doing exactly its job, and it is also the honest cost of a prepass on tiled hardware that nobody mentions.

3 — Kill the quadratic (engine challenge)

producer_of is a linear scan called from inside two loops, making compile O(P² × A²). Build an index from (resource, version) to producing pass once at the start of compile and use it everywhere. Measure before and after with §8's timing, and then measure again with a synthetic 200-pass graph.

Hint: k_max_fg_resources × k_max_fg_versions is 384 entries — a flat Uint8 array, no hashing. Watch for: the index must be rebuilt if you ever let a pass be added after compilation begins, which is why compile should assert that it is not.

4 — Subresource versions (engine challenge)

Give the four cascade passes independent versions by keying a version on (resource, layer) rather than on the resource. Confirm that the compiled schedule no longer serialises them, and then explain — in writing, honestly — what that bought on SDL_GPU. §12.1 has the answer and it is "nothing yet"; the exercise is worth doing for the bookkeeping, and the write-up is worth doing because knowing when an optimisation buys nothing is the harder skill.

5 — A graph that actually saves memory (engine challenge)

Add a second post effect — a cheap radial blur, or a downsampled depth-of-field — that needs its own half-resolution scratch target and finishes before the bloom begins. Predict from the lifetimes how many bytes the pool will save, then measure it with transient_bytes_naive() and transient_bytes_pooled().

Watch for: "finishes before the bloom begins" has to be true of the schedule, not of your intentions. If the composite reads both, the graph is free to order them either way, and it will pick declaration order — so the saving depends on a tie-break. Making it depend on a real dependency instead is the actual lesson.

6 — Break the determinism on purpose (guided)

Change the ready-pass scan in step 3 to iterate backwards. Confirm the compiled schedule changes, confirm §I is still bit-identical, and then say why both of those are true at once. Then find a change to the frame that would make the second one stop being true.

Solution sketch: any topological order is legal, so the picture survives. It stops surviving the moment two passes write the same resource without one reading the other's output — which §5's validation forbids, so you will have to reach for an imported resource to build it. That is the validation rule earning its place.

17Recap & next

The engine gained a frame graph, and lost four sets of hand-maintained facts.

  • A resource is a sequence of versions, not a texture. Every deduction in the lesson is downstream of that one move, and it is single static assignment applied to render targets.
  • One statement yields four facts. keep, clear and discard_write say what a pass does with what was already in a target; the ordering edge, the load op, the producer's store op and the resource's lifetime all follow. Every derived op matches what the engine chose by hand across eight attachments.
  • Culling is backward reachability from imports. Eleven bloom passes vanish because nothing reads them, with no flag anywhere.
  • Determinism is correctness. Ties broken by declaration index, because a scheduler that wanders produces a golden that fails one run in five.
  • The memory pitch does not apply here, and the two reasons are different. SDL_GPU 3.4.12 cannot express aliasing at all, and our frame is a chain with a peak equal to 88% of its sum. The prize is 14.3% — 5.27 MB at 1920×1080 — and we collect none of it. The pool works, on a frame shaped for it, and §7 builds one to prove it.
  • The graph orders passes, not draws, which is why 6.11's back-to-front tail and 6.16's batching are structurally out of its reach.
  • 8.62 µs and zero allocations per frame, measured with a replaced global operator new, which is why the arrays are fixed-capacity.
  • Bit-identical across 262,144 channels, with a control proving the comparison can report a difference.

Declaring it will take one line, and the fact that it is the last writer of an imported resource is now something the frame says rather than something you remember.
