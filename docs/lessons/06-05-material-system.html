Module 6 — Advanced Rendering · Lesson 6.5

A Material System

Lesson 6.4 changed a surface description and had to edit forty-four call sites across the engine, four demos and six test harnesses. That number is not a complaint — it is a measurement, and what it measures is a type that does not exist. Three places in this codebase have independently grown the same struct-shaped hole, one of them a demo that invented the type because the engine did not offer it. This lesson fills the hole, and the interesting part is not the struct: it is the question that decides what goes in it, which turns out to be a question about hardware rather than about taste. Everything here is a refactor, so there is exactly one claim to make at the end — the reference render must be byte-identical.

1The Problem, Which the Codebase Already Wrote Down

Most lessons in this course open by showing you something broken. This one opens by showing you something the code has been saying for three modules, in comments, without anybody acting on it.

Here is scene_object, as Lesson 3.7 left it, with the comment that has sat on its last field ever since: 

struct scene_object
{
    transform xform;
    mesh_handle geometry;
    const char* name;
    Uint32 tint;
    bool closed;
    microsurface surface;   // <- and on this field:
};

// "Look at what just happened to this struct. `tint` was enough while a surface
//  was one colour; then 3.4 needed `closed`; now 3.7 needs two more numbers, and
//  all four describe the same thing — THE SURFACE — while `xform` and `geometry`
//  describe where it is and what shape it is. That is two different kinds of data
//  wearing one struct, and the second kind has a name: a material."

And here is fill_style, from Lesson 3.8, whose comment says the same thing about itself in different words: "`fill_style` is now two structs wearing one name."

Two structs, written a lesson apart, each of which noticed it was accumulating a second kind of data and each of which declined to fix it. That was the right call at the time, and 3.7 said why: a material invented before three lessons have asked for one is a guess.

Three lessons have now asked. And Lesson 6.4 put a number on it.

What the absence cost, measured

Lesson 6.4 replaced specular::colour and shininess with roughness, metallic and F0 — a change to the surface description and nothing else. It touched forty-four call sites across the engine, four demos and six harnesses.

Not because the change was large. Because the description had no single home, so every place that used a surface had assembled one out of loose fields.

2The Demo That Invented It

The third panel of that figure is the one worth stopping on, because it is a different kind of evidence from the other two.

ecs_swarm is a demo. Since Lesson 5.1 the boundary has been law: demos link the engine and may use only its public headers. And in Lesson 5.7, needing to give its entities an appearance, it wrote this: 

/// What an entity looks like: `scene_object`'s `tint` and `surface`, which have
/// always described the same thing and never been the same thing.
struct material
{
    Uint32 tint = 0xFFFFFFFFu;
    engine::microsurface surface{};
};

Read that comment again. The demo knew. It named the type, gave the reason, and built it anyway, because the engine offered nothing to build on.

A signal worth learning to read

When a consumer restricted to your public API has to invent one of your types, the type is missing. Not "would be nice"; missing. A demo cannot reach into the engine to work around a gap, so what it builds instead is a direct measurement of what the API does not provide.

This is the strongest form of the pressure Lesson 3.7 said to wait for — and it is why the first thing this lesson's diff does is delete that struct's fields.

3The Question That Draws the Line

So we are writing a material. The temptation now is to sweep everything surface-shaped into it — the tint, the roughness, the texture, the cull mode, the blend mode, eventually the shader — because all of those are, in ordinary English, "what the surface is like".

That would produce a type that cannot work, and the reason is not stylistic. Ask a sharper question instead:

The rule

Can this be a number in a buffer?

If yes, it is per-draw data. The fragment stage reads it, the GPU pushes it as a uniform, and two objects that differ only in it can be drawn back to back with no state change between them.

If no, it is pipeline state. It is baked into a pipeline object at creation time, and two objects that differ in it need two pipelines and a sort between them.

This is not a rule we are inventing. It is the shape of the hardware, and Lesson 4.8 already paid for the knowledge: porting the scene to SDL_GPU produced three pipeline objects and a sort of the draw list, precisely because cull mode and fill mode cannot be uniforms. The stats that lesson added — pipeline_binds against ideal_pipeline_binds — exist to measure the cost of getting the sort wrong.

So the material gets four fields, and every one of them passes the test:

And cull_mode, surface_style and specular_model stay exactly where they are — in fill_style, in gpu_draw_item, in render_options. A material that swallowed them would be a material that cannot be a uniform, which is not a material at all.

verify_65 §A asserts the rule rather than describing it, in the bluntest way the language allows: 

checkf(std::is_trivially_copyable_v<engine::material>,
       "a material is TRIVIALLY COPYABLE (%zu bytes) — which is the machine's "
       "way of saying it can be pushed as a uniform");

If a field ever arrives that breaks that, it belongs on the other side of the line, and the assertion is where you find out.

4Handles, Pointers, and the Step Between

One field in that struct is doing something the old code did not, and it is the one worth the most argument: albedo_map is a handle, where the engine has always used a const texture*.

Here is what it replaces. fill_style has held this since Lesson 3.9: 

struct texture_binding
{
    const texture* image = nullptr;
    sampler samp{};
};

…and the sandbox's comment beside it made the case for the pointer, honestly and, at the time, correctly:

"texture_binding holds a non-owning pointer, and textures lives for the whole program, so there is nothing here that can dangle."

Read that argument carefully, because it is an argument about this demo rather than about the type. It is true. It is also unavailable to anyone else: it depends on a container that happens never to grow, owned by a function that happens to outlive every user. A material is going to be stored in scenes, copied into components, and — from Lesson 6.6 — loaded from files. None of those can make that argument.

So the material stores a handle. But a handle is the wrong thing to have in a fill loop: it is an index and a generation, and resolving it costs a bounds check and a compare. Lesson 5.4 measured that cost precisely so we would not have to guess about it — and per pixel is exactly where you cannot afford it.

Both facts are true at once, which is why the answer is neither one type nor the other but a named step between them:

Four lines, and the whole architecture is in the shape of them:

  • a handle is how you STORE a reference — durable, checkable, four bytes, safe across a reallocation, cheap to copy into a component or a file;
  • a pointer is how you USE one in an inner loop — one dereference, no lookup, no branch;
  • and the resolve happens once per draw, between the two.

Getting that boundary wrong is a real cost in either direction, and it is worth naming both failures because they look nothing alike. Store pointers and the scene dangles the first time a pool grows — a crash, or worse, silently wrong pixels. Resolve inside the loop and you have added a bounds check and a generation compare to every pixel, for a value that could not have changed between two pixels of the same triangle.

4.1The case a pointer cannot express

There is a third state, and it is the one that makes handles worth the trouble. A handle can be perfectly well-formed and name something that no longer exists — Lesson 5.4's distinction between valid() and contains(). A pointer has no way to be asked.

verify_65 §C exercises all three states, and the middle one is the demonstration:

[PASS] a live handle resolves to a bound binding (8x8)
[PASS] after 64 more insertions the SAME handle still resolves — pointer was
       0x928c03500, is now 0x928c16000. A raw pointer stored in a material would
       have had to be right about which of those it was
[PASS] a STALE handle resolves to an unbound binding, not to freed memory

The pool moved. Sixty-four insertions reallocated it, the storage is at a different address, and the handle did not care — because it names a slot rather than an address. Any pointer taken before that growth is now pointing at freed memory, and nothing about it would say so.

And a stale handle resolves to nothing: bind_albedo returns an unbound binding, and the surface falls back to its tint — exactly what it would have done with no image at all. That is not a special case bolted on; it is the same code path as "this material has no texture", which is why there is no error handling in those four lines.

5One Field, One Answer

Look at what the material does not have. Here is the GPU's material block, which Lesson 4.8 wrote and 6.4 re-laid-out: 

struct material_uniforms
{
    vec3  albedo;
    float roughness;
    float metallic;
    float f0;
    float textured;   // <- 0 = use `albedo`, 1 = sample the bound texture
    float pad0;
};

textured is a flag. Beside it, in gpu_draw_item, sits a SDL_GPUTexture* chosen somewhere else entirely. Two fields, two opinions, and nothing keeping them in agreement.

The two ways that goes wrong

textured = 1 with no image bound: the shader samples an unbound slot and gets the sampler's debug magenta.

textured = 0 with an image bound: the surface silently ignores its own texture and draws flat.

Neither fails at the point of the mistake. Both render something plausible, which is the failure mode this course keeps running into and keeps naming.

The material has one field, and the flag is derived from it: 

[[nodiscard]] bool textured() const { return albedo_map.valid(); }

That is not a convenience accessor. It is the removal of a state the program could previously represent and should never have been able to. There is no longer any way to say "textured, but with no image" — and a bug you cannot express is better than a bug you detect.

The GPU still needs the flag as a number, of course. So one function computes it, in one place:

Before this lesson that block was assembled by hand at three sites — the sandbox, verify_48 and verify_49 — five assignments each, each free to get the fifth one wrong. Now there is one, and it derives.

A trap this lesson walked into, and what it cost to notice

Replacing the sandbox's hand-assembly with uniforms_of(obj.mat) compiled cleanly and was wrong. The sandbox chooses its floor texture from a keypress and a scene test, and never wrote that decision onto the material — so the derived flag would have been 0 while a texture was bound, and every GPU texture would have vanished.

The fix is the lesson rather than a patch: the decision now lands on the material, and everything downstream reads it from there. Writing the flag separately, next to a pointer chosen separately, is precisely the pair of opinions this section exists to collapse — and I nearly re-created it while removing it.

6When a Pool Earns Its Place

A "material system" implies more than a struct. It implies materials having identity — being stored somewhere, shared, referred to. So: a pool, material_handle, the same machinery Lesson 5.4 built for meshes and 5.5 for images.

But a pool is not automatically right, and it is worth being able to say when it is. scene_object holds its material by value. It has exactly one; a handle would add a lookup to save nothing.

The swarm is the other case. Look at what it actually builds:

entitiesdistinct materialswhy
96 ring drones6tint_for(i) cycles six colours; all share roughness 0.53
32 moons1identical
sparks1identical
the sun1the one genuinely unique material

Ninety-six entities, six materials. Storing a copy in each stores the same thirty-six bytes sixteen times over — 3,456 bytes against 600, a 5.8× reduction on that component, measured in verify_65 §E.

And then the argument that actually matters, which is not about bytes at all:

What sharing buys

With copies, "make the drones rougher" is a loop over the registry that has to find every entity carrying that appearance and hope none was missed.

With handles it is one write. verify_65 §E does exactly that and checks all ninety-six users see it.

So the rule that decides between a value and a handle is about sharing, not about size. That is worth stating plainly because "use handles for big things" is the folk version and it gets this case backwards: a material is small, and the handle is still right — because ninety-six things point at six.

7The Field That Was Not a Material After All

One field looked like it belonged in the material and does not, and finding that out was the most useful thing building the type did.

scene_object::closed has carried this comment since Lesson 3.4:

"In a real engine this lives on the material, because cull mode is pipeline state and pipeline state is what a material is (Module 6)."

It is Module 6, and that sentence is wrong twice over.

First, by §3: a material is explicitly not pipeline state. That was the whole line we just drew. Cull mode belongs to the pipeline object, and a material that carried it could not be a uniform.

Second, and more interestingly: closed is not cull mode anyway. It is a claim about the geometry — a cube is closed whatever colour you paint it — and the engine already computes it, from the mesh, without asking anyone: 

// mesh.hpp, since Lesson 3.4 — on the REPORT, not on the mesh
[[nodiscard]] bool closed() const
{
    return boundary_edges == 0 && nonmanifold_edges == 0 && triangles > 0;
}

So there are two different questions wearing one name, and separating them is the fix:

  • The fact belongs to the mesh: is this surface closed? validate() counts the edges and answers it.
  • The decision belongs to the caller: should we cull its back faces? Usually yes when closed — but a closed mesh may still be drawn two-sided on purpose, to look inside it or to debug a winding.

Two arguments, because there are two questions. Culling is only valid on closed geometry, and that constraint now lives in exactly one function instead of being re-remembered at every call site.

Worth noticing about the comment

It was written in 3.4, repeated the reasoning for three modules, and was wrong the whole time — and nothing caught it, because a comment predicting a future design cannot be tested. It was only building the thing it predicted that showed it up.

That is not an argument against writing such comments; 3.7's identical prediction about the material was exactly right and is why this lesson exists. It is an argument for re-reading them when you arrive, rather than treating them as instructions.

8Where cull_mode Lives, and an Argument I Had to Withdraw

cull_of returns a cull_mode, which lives in raster.hpp — a 700-line header holding the whole software rasterizer. Should material.hpp include it?

Lesson 5.1 already answered this, in projector.hpp, and stated the rule: a type two components share is a header, not a section of whichever one happened to define it first. Two components now share cull_mode, so it gets gfx/cull.hpp: thirty lines, one enum.

That is the whole justification, and this section exists because I did not think it was enough.

The claim I wrote, and the measurement that killed it

The comment I first wrote said the split was about compile time: raster.hpp is 700 lines, Lesson 5.1 measured it at 0.97 s for everyone who includes it, and pulling that in for a three-value enum is indefensible. Quantitative, concrete, persuasive.

Then I measured it on the machine actually doing the build:

cull.hpp        0.038 s
raster.hpp      0.258 s
material.hpp    0.261 s   <- already, via texture.hpp

The marginal saving is approximately zero. material.hpp already costs more than raster.hpp, because texture.hpp dominates both.

Two things went wrong there, and the second is the more embarrassing.

The 0.97 s was measured three modules ago, on a different build, in a different state — and Lesson 5.1's own note says, in capitals, "THE RATIO IS WHAT TRAVELS, NOT THE SECONDS." I read past the caveat to the number I wanted. A recorded warning does not protect you if the figure beside it is more useful.

And the deeper mistake: the physical-design rule never needed a performance argument. "Two components share the type, so it gets a header" stands entirely on its own. Reaching for a second, quantitative justification felt like making the case stronger, and it was the only part of the case that was false.

The split ships. The reason it ships is the rule. And cull.hpp does cost 0.038 s, which is the one figure in that comment measured before it was written down.

9Implementation

Four steps, and the order matters because the last one is what makes the whole thing verifiable.

9.1Step one: the texture gets a pool

Before a material can reference a texture by handle, textures need somewhere with stable identity. That is two lines in texture.hpp: 

using texture_handle = handle<texture>;
using texture_pool   = pool<texture>;

Note where it is not. asset_store already owns pools of meshes and images (5.5), and adding a third would have been the obvious move — but the asset store is about files: a search path, a name, a cache, a load count. Every texture in this engine so far is generated in memory. Lesson 6.6 is where textures start arriving from disk, and that is the lesson that gets to decide whether they become assets. Inventing that answer now would be guessing, which is the same call 3.7 made about the material itself.

9.2Step two: the material, and what it displaces

material.hpp is new and small. The interesting part of the diff is what shrinks: scene_object loses two fields and gains one, and ecs_swarm's invented struct loses its body entirely.

It stays a distinct type rather than becoming engine::material outright, and that is deliberate: an ECS component is an identity, not just a payload. view<geometry, material> names this component, and two components that happened to share a layout would be indistinguishable to the registry. Lesson 5.7 made the same call about placement.

9.3Step three: one packing site

uniforms_of (§5) replaces the hand-assembly at three call sites. The sandbox's version went from five statements to one — and, as §5 records, that substitution was wrong until the texture decision was moved onto the material, which is the point the function is making.

10The Refactor, in Two Halves

Everything above is a refactor, which means it gets exactly one correctness claim: the picture does not change. Lesson 5.1 built the machinery for making that claim and stated the rule for using it:

5.1's rule

Move without changing, then change without moving, verifying separately.

"Separately" is the load-bearing word. If you move code and change behaviour in one step and the output shifts, you have two candidate causes and no way to tell them apart. Worse, if the two changes have compensating errors, the output can come out right and both bugs survive.

So this lesson ran the golden three times:

afterwhat changedhash
the movetint and surface into mat, nothing elseE917C06C
the texture handlestexture_set became a pool; the shot resolvesE917C06C
the GPU packinguniforms_of; the swarm's handle componentE917C06C

The swarm has its own shot, and it got the same treatment — rendered before and after from clean builds on both sides, byte-identical.

A false alarm worth having, because the symptom was not a crash

Capturing that "before" render meant stashing the work, rebuilding, and shooting. The rebuild was incremental, and scene_object had changed size (96 → 112 bytes) — so some objects were compiled against the old layout and some against the new.

The result was not a crash. It was a shot with the wrong scenes in it: frame 1 rendering solids instead of cycle, triangle counts of 20 where 44 was right, and one frame's name printing as ?. Plausible garbage, which took a minute to distinguish from a real regression.

The fix was cmake --build build --target clean, and the rule is: after any change to a struct's layout, an incremental build is not evidence. That is the same failure class as a uniform block disagreeing with its shader, arriving on the CPU side.

11What It Cost

A material system is not free, and one of the existing harnesses said so immediately. verify_56 — Lesson 5.6's cache-behaviour work — asserts the size of scene_object, and it failed: 

[FAIL] scene_object is 112 bytes (1.5 cache lines)

It was 96. The material added 16 bytes net, and the assertion is worth keeping rather than relaxing, because 5.6 is the lesson that measured why object size matters at all.

Where the bytes went:

fieldbytes
Uint32 tint4was already there
texture_handle albedo_map4new — and it replaces an 8-byte pointer elsewhere
sampler samp16the whole growth
microsurface surface12was already there
material36

The sampler is where it went — four enums, stored per object, identical for every object in every scene this engine has. A real engine interns those into a handle exactly as this lesson interns the texture, which would put scene_object back under a hundred bytes.

That is named as a debt rather than paid, on the same grounds as everything else here: nothing yet needs two materials to share a sampler, and the rule from §6 is about sharing. Exercise 14.4 does it anyway and measures what comes back.

14Common Pitfalls & Debugging

The scene renders the wrong objects entirely after a struct change

Symptom: wrong meshes, wrong counts, garbage names — but no crash.

Cause: an incremental build after a layout change. Some translation units have the old sizeof and some the new, so every field after the change is read at the wrong offset.

Fix: cmake --build build --target clean. And treat it as a rule: after a struct's layout changes, an incremental build is not evidence.

Textures vanish after switching to uniforms_of

Symptom: everything draws flat-coloured; the GPU path lost its images.

Cause: the material's albedo_map was never set, because the texture was still being chosen somewhere else. The derived flag correctly reports "no image" — the material was simply not told.

Fix: move the decision onto the material. If two places both have an opinion about whether a surface is textured, deriving the flag has not helped; it has just picked the uninformed one.

A material renders as debug magenta

Symptom: one surface is bright magenta.

Cause: a stale handle — well-formed, naming a slot whose occupant is gone — or a texture bound at a slot the shader declares but nothing filled.

Fix: pool::contains() answers the first, and it is a different question from handle::valid() (5.4). Note that bind_albedo already degrades a stale handle to "no image" rather than to magenta — so magenta means the binding was made another way.

Objects sharing a material change together, unexpectedly

Symptom: tweaking one entity's roughness changes ninety-five others.

Cause: that is the feature. They share a handle.

Fix: if an object needs its own appearance, give it its own material — pool.insert() a copy. The decision "shared or unique" is now explicit at the point of creation, which is exactly the improvement: before, everything was unique and nothing said so.

15Exercises

15.1 — Break the split on purpose

Add cull_mode cull; to material and wire it through. Then count the pipeline objects the GPU renderer needs, and the pipeline binds per frame with and without the draw-list sort.

Solution sketch

Nothing stops you compiling it — that is the point. What breaks is the batching: two objects differing only in cull mode can no longer be drawn back to back, and draw_stats::pipeline_binds climbs away from ideal_pipeline_binds. The field is legal C++ and a category error, and the only thing that tells you is the stat Lesson 4.8 added.

15.2 — Make a handle go stale, and watch what happens

Give an object a material with a valid albedo_map, then remove that texture from the pool while the scene is still rendering. Predict the result before you run it.

Hint

bind_albedo returns {nullptr, samp} for a handle the pool no longer contains, and texture_binding::bound() is false.

Solution sketch

The surface falls back to its tint and keeps rendering. Now do the same thing with the pre-6.5 code, which stored a const texture*: you get freed memory, and whether that crashes depends on the allocator's mood. The handle turned undefined behaviour into a defined fallback, and that is worth more than the four bytes it saved.

15.3 — Find the next invented type

§2 argued that a demo inventing an engine type is a measurement of a missing API. Read the demos for others. What has sandbox declared that the engine should own?

Solution sketch

scene_mesh_cache and orbit_camera are both strong candidates — one is an asset-derivation cache the engine plausibly wants, the other is a camera the engine definitely does. Note that the argument is not "move everything": a demo is allowed demo-specific types. The signal is a demo type that other demos also declare.

15.4 — Intern the sampler (engine challenge)

§11 measured the sampler as 16 of the material's 36 bytes, identical for every object. Replace it with a sampler_handle into a small pool and measure sizeof(scene_object) again.

Hint

The pool will hold two or three entries for the whole program. That is itself the interesting result: it is what "identical for every object" looks like once it is measured.

Solution sketch

material drops to 24 bytes and scene_object back under 100. Then ask the §6 question honestly: does anything share a sampler in a way that matters, or is this only about bytes? If it is only about bytes, the case is weaker than the texture's — and knowing which argument you are making is the exercise.

16Recap & Next

The engine has a material: one type for what a surface is, referenced by handle where it refers to assets, packed to the GPU in one place, and shared where sharing is real.

What the engine gained:

  • A rule that decides membership — can this be a number in a buffer? — which is the hardware's line rather than a matter of taste, and which verify_65 asserts with a trivially_copyable check.
  • Handles for stored references, pointers for inner loops, and bind_albedo as the named step between. A stale handle now degrades to "no image" instead of to freed memory.
  • A derived flag instead of a stored one — removing a state the program could previously represent and never should have been able to.
  • Sharing, measured: 3,456 bytes to 600 for the swarm's ring, and, more importantly, one write where there was a loop.
  • Two corrections to comments that had been repeating for three modules — closed was never material state, and the compile-time argument for cull.hpp did not survive being measured.

And one deletion worth more than anything added: ecs_swarm's hand-written struct material. A demo built it because the engine had a hole; the hole is filled, so the demo stops needing to.

The reference render is byte-identical, hash E917C06C, across all three stages of the refactor. That is the only claim a refactor is entitled to make, and making it in separately-verified halves is what stops two compensating bugs from cancelling into a passing test.

Next: 6.6 — glTF 2.0 Loading. Everything this lesson deferred, 6.6 forces. Textures start arriving from files, which is when the question "should the asset store own the texture pool?" stops being premature. glTF files define materials, which is when a material needs a name, a cache and an identity that survives a reload. And the glTF specification defines its own reference BRDF using the 1 − F(v·h) coupling that Lesson 6.4 measured at 1.3395 and declined to ship — so the interoperability question this engine has been able to avoid arrives with an asset attached.

17Further Reading

  • Lakos, J., Large-Scale C++ Software Design (1996), chapters 0–3. Where "physical design" as a discipline comes from, and the source of the rule cull.hpp follows.
  • Filament's material system documentation (Google). The clearest public description of a shipping material model, including exactly which parameters are uniforms and which are compile-time variants — the same split §3 draws.
  • The glTF 2.0 specification, §3.9 "Materials". Worth reading now, before 6.6: notice how little it defines, and that everything it defines is per-draw data.
  • Bitsquid / Our Machinery, "Managing Decoupling" and the handle articles. The handle-versus-pointer argument made at engine scale rather than at struct scale.
  • Real-Time Rendering, 4th ed., §18.4. Pipeline state, sorting and batching — why the right-hand column of Figure 2 is expensive.
  • Fabien Sanglard's Quake and Doom 3 source reviews. Both engines' material systems are worth reading precisely because they draw the line differently, and both explain why.
