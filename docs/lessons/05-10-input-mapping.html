Module 5 — Becoming an Engine · Lesson 5.10

Input Mapping: Actions, Not Keycodes

Every program in this course reads input by switching on a scancode, which is fine for a demo and wrong for a game in four separate ways — none of them about speed. This lesson puts a name in the middle. It measures nothing, and says so: the argument is entirely about what the code can express. Two things in it are worth the price of admission on their own — why an edge must be derived from an action's level rather than from any binding's, and why a fixed-timestep engine needs a second kind of edge that the first cannot provide.

1The Problem

Here is how ecs_swarm read input at the end of Lesson 5.9, and how every program in this course has read it since Lesson 1.2:

That is not slow, and it is not wrong in any way a compiler or a profiler will tell you about. It is wrong in four ways that only show up when somebody tries to use the program.

It cannot be rebound. The scancode is compiled in. A left-handed player, a player whose keyboard puts that key somewhere awkward, a player with a disability that makes it unreachable — every one of them is out of luck, and the fix is a recompile. This is the one that matters most and gets thought about least.

It is about one device. A gamepad has no scancodes. Adding one means a second switch, which must be kept in step with the first by hand, for the life of the program. The third device makes it three.

It cannot be recorded. A replay system, a demo recording, an automated test that drives the game — all of them want to store what the player meant. Storing SDL_SCANCODE_SPACE records a fact about a keyboard; if the binding changes between the recording and the playback, the replay does something else.

And it says the wrong thing. if (key_pressed(SDL_SCANCODE_SPACE)) inside a jump handler is a sentence about hardware in a file about jumping. That is not a performance problem or a portability problem; it is code failing to describe what it does, which is the kind of problem that compounds quietly for years.

This lesson measures nothing, and that is deliberate

Lessons 5.6, 5.7 and 5.9 each turned on a benchmark, because each was choosing between designs that differed in cost. This one is not: the alternatives differ in what they can express, and every one of them is far too cheap to matter — an action map's per-frame work is a loop over a couple of dozen bindings, which is nanoseconds.

Producing a benchmark anyway would be worse than useless. It would attach a number to a decision the number did not make, and the next reader would think the number was the reason. A design lesson should say it is a design lesson.

2Building Intuition

2.1 A name in the middle

All four problems have the same shape — the code names a signal where it means an intention — and therefore the same fix. Put a name in the middle:

The three pieces

An action is a name. "jump", "camera_yaw". It is what the game means.

A binding maps a signal onto it. Space contributes +1 to "jump". There may be several, on several devices.

A frame publishes the values. Once per frame, jump = 1.0, held, pressed this frame.

That is the entire idea, and every one of the four problems dissolves against it. Rebinding edits the middle row. A second device adds a row. A replay records the left column. And the game code reads actions.pressed(jump), which is a sentence about jumping.

The indirection is one level deep and it is worth being suspicious of it anyway, because "add a layer" is the answer to everything and is usually wrong. What makes it right here is that the layer is not hiding the thing below it — it is naming it. A wrapper that renamed key_pressed to button_pressed would be pure cost. This one changes what can be said.

2.2 Who owns the map

The engine could own one. It owns exactly one input, after all — platform creates it and publishes it once per frame, and that is right, because there is one keyboard and one mouse and no program wants two views of them.

An action map is different, and the difference is the same one this course has now hit three times. Lesson 5.5 refused to make asset_store a singleton because sandbox holds three in one program. Lesson 5.8 refused to make registry one because the harness holds four in one function. Here: a two-player local game needs two maps, with different bindings, and a game that wants per-entity input puts one in a component and lets view<player_input> find it.

The rule, stated once and applied for the third time

The engine does not know how many of a thing a game needs, so it declines to decide. action_map is a value: construct one on the stack, hold several, put one in a component, throw one away. There is no global, no get_instance(), and nothing in the engine holds a pointer to yours.

What the engine does provide is the moment at which updating one is correct, which turns out to be the interesting part — see §5.1.

3One Mechanism

3.1 Every binding contributes a signed value

An input system has to do two jobs that look different. It has to answer "is the player jumping" — a yes or no — and "how hard is the player steering" — a number between −1 and 1. The obvious design gives those two jobs two mechanisms: button actions and axis actions, declared differently and queried differently.

There is a better one, and it is smaller:

The rule

Every binding contributes a signed float to its action. An action's value is the sum of its bindings' contributions.

Work the three cases through and notice that nothing special happens in any of them.

Worked example — three actions, one rule

jump is bound to Space with scale +1. Space down → value 1. Space up → value 0. Ask held().

steer is bound to A with −1 and D with +1. A alone → −1. D alone → +1. Both held → −1 + 1 = 0. Ask value().

look_x is bound to the mouse's x delta with scale 0.5. A ten-pixel move → 10 × 0.5 = 5. No movement → 0. Ask value().

The third line of the middle case is the one that pays for the design. A system with two mechanisms would have needed a rule for "what does holding both halves of an axis mean" — and would have had to write it, document it and test it. Here there is no rule, because −1 + 1 is 0 and arithmetic already knew that.

It also means an action's value is not clamped, and that is deliberate rather than an oversight. Two keys both bound to jump with +1, both held, gives 2. For a button that is meaningless and harmless — you asked held(), which does not care. For a mouse delta scaled by 0.5 it is the whole point, since a fast flick should produce a big number. Clamping would have had to know which kind of action it was looking at, and knowing that is precisely what this design avoids.

3.2 The threshold, and what it is for

held() is not "value is non-zero". It is:

A digital binding contributes ±1, so any threshold above 0 and at or below 1 would behave identically for keys. It exists for the sources that are not keys: a gamepad trigger resting at 0.02 because the spring is tired, a stick with a little drift. An analog source should have to be pushed, not brushed, and 0.5 is the conventional halfway point.

Note the fabs. A two-way axis is "held" when pushed either way, which is legal, occasionally useful — "is the player steering at all?" — and rarely the question you meant to ask of an axis. The header says so.

4Edges Come From the Level

Lesson 1.2 established the distinction this whole course has run on: a level is "is it down now", an edge is "did it change this frame", and confusing them produces two different bugs. That distinction survives into the action layer unchanged — held(), pressed(), released() — and there is exactly one new decision to make, which is where the edge is computed from.

It looks like it should not matter. Space goes down; the binding sees a rising edge; the action fires. Why would you compute it any other way?

Because an action may have more than one binding, and then the two answers differ.

Follow the five frames. jump is bound to Space and the left mouse button, which is an ordinary thing to want — a keyboard binding and a mouse binding for the same intention.

  1. Nothing held. No edges.
  2. Space goes down. The action becomes active: one press edge. Correct either way.
  3. The mouse button goes down while Space is still held. A binding-derived edge fires again — a second press, and the player jumps twice. A level-derived edge does not, because the action was already active and nothing changed.
  4. Space comes up, the mouse is still down. A binding-derived edge fires a release — while the action is plainly still active. A level-derived edge does not.
  5. The mouse comes up. The action goes inactive: one release edge.

So the rule is:

The decision

An edge is a change in the ACTION, not a change in a signal.

Compute the level first — sum the bindings, compare against the threshold — and derive the edges by comparing this frame's level against last frame's. Exactly as engine::input derives key edges from two snapshots, one layer up.

A bug that hides until the second binding

Everything about the wrong version works perfectly with one binding per action, which is what a first implementation has and what a first test writes. It fails the moment a player binds a controller button alongside their keyboard — in production, on somebody else's machine, as "sometimes it jumps twice".

§C of the verification harness binds two on purpose and walks the five frames above, asserting one rising edge and one falling edge for the whole sequence. It is four lines of setup and it is the only part of the harness that could have caught this.

5The Edge That Survives the Step

5.1 Where the map must run

An action map has to be updated once per frame, after input is published. Lesson 5.2's application layer offers seven hooks — configure, on_start, on_event, on_fixed_step, on_frame, on_overlay, on_stop — and it turns out that none of them is the right place, which is the sort of discovery that means either the design is wrong or something is missing.

Why each existing hook is the wrong place to update an action map.
hookrunswhy not
on_eventonce per event Several times a frame, or none. An update per event would publish a different answer to every event handler.
on_fixed_stepzero or more times The same problem, and worse — it is also where the answers get read.
on_frameexactly once The right frequency, the wrong place: it runs after the steps, so every step of the frame would read last frame's actions.

on_frame is the near miss, and it is worth being precise about why it fails, because "once per frame" sounds like the whole requirement. It is not. The requirement is once per frame, after input is published, and before anything reads it — and the simulation reads it. A map updated in on_frame is a map that is always exactly one frame stale from the simulation's point of view, which is invisible in a demo and is a real 16-millisecond input delay in a game.

So Lesson 5.10 adds an eighth. One virtual, with an empty default, in the one gap the other seven left:

Adding a hook to a framework is not free — every hook is a thing every future reader has to learn — so it is worth saying what else it is good for, because a hook that serves one caller is a smell. on_input is the once-per-frame, pre-simulation moment, and that is also where you would read a network snapshot, sample a debug scrubber, or latch a replay's recorded intentions. It was missing before this lesson happened to need it.

5.2 Two failures, one queue

Now the harder half, and it is Lesson 1.4's trap in its most expensive form.

on_fixed_step runs zero or more times per frame — the accumulator decides, and Lesson 1.4 measured 0, 1, 2, 1, 2 across five consecutive frames on this machine. A frame-scoped edge read inside it fails in both directions:

A two-step frame reads pressed() twice, both times true, and the player jumps twice for one press. A zero-step frame reads it not at all, and by the next frame the edge is gone — the press is silently lost. Neither is fixable by the caller without keeping state across frames, so the map keeps it:

Every rising edge pushes one press onto a small per-action queue. consume_pressed pops one and returns true. A two-step frame takes it once and the second step finds the queue empty; a zero-step frame leaves it queued until a step actually happens.

Worked example — six presses and no steps

The queue is k_action_press_queue = 4 deep. Press and release six times with no step running: the harness finds 4 queued, and draining gives exactly 4. Two presses were dropped.

That is a decision, not an overflow bug. An unbounded queue turns a hitch into a burst of jumps arriving after the player has stopped asking, which feels worse than losing them. Four survives a stutter and is short enough not to feel like a recording.

A fighting game with a deliberate input buffer would raise that number and call it a design parameter — which is exactly what it is. The engine's job is to make the number visible and the behaviour predictable, not to guess the genre.

So the rule for a caller is two lines long:

Which edge query to use where.
whereusewhy
on_input, on_frame, on_event pressed() / released() runs once per frame; the frame-scoped edge is exactly right
on_fixed_step consume_pressed() for edges,
held() / value() for levels		 runs 0..N times; levels are frame-coherent and safe, edges are not

6A Concept, and the Test It Makes Possible

There is a problem with testing any of this, and it is worth meeting because the solution is a C++20 feature this course has not needed until now.

engine::input::update() samples SDL's live keyboard state — that is the whole point of Lesson 1.2's design, and it is right. It also means a test that wants a key held would have to persuade SDL that a key is held, which SDL offers no supported way to do. So a harness cannot construct an input in a chosen state, and every interesting behaviour above — the two-binding edge case, the queue across variable steps — would go untested.

Look at what update() actually needs, though. Six questions:

update is templated on that, and the whole test problem evaporates: the harness writes a struct with six functions and the mapping logic runs exactly as it ships.

C++ in place — a concept describes a shape, not a hierarchy

The alternative is an abstract base class: struct input_source { virtual bool key_down(...) = 0; };, with input inheriting from it. That would work, and it would cost three things a concept does not. It changes input — Lesson 1.2's header would have to know about a base class it has no other use for. It costs a virtual call per query, on a loop that runs per binding per frame. And it is closed: a type can only be an input_source if its author said so.

engine::input satisfies input_snapshot without knowing the concept exists. Not one character of input.hpp changed in this lesson. That is the property worth having: a concept describes a shape, and types that already have that shape are already members.

It is also free. The compiler instantiates one copy of update per source type and inlines the six accessors, so the production path compiles to exactly what a hand-written update(const input&) would have. The `static_assert` beside the concept keeps the claim honest: if input.hpp ever renames one of the six, the engine fails to build with a message naming the requirement rather than failing somewhere inside a template.

7The Device That Is Not Here

The second of §1's four problems was "it is about one device", and the natural way to prove that fixed would be to add gamepad support. This lesson does not, and it would be dishonest to let that pass without saying why.

There is no gamepad code here, and this is the reason

It could not be run on the machine this was written on. SDL3's gamepad API needs SDL_INIT_GAMEPAD, device add/remove events, an opened SDL_Gamepad* per controller, and axis values that need a deadzone whose right value is a matter of taste and hardware. Every one of those is easy to write and impossible to be confident about without a controller in your hand.

Untested device code in an engine is a liability rather than a feature. It looks like support, it compiles, it appears in the API — and the first person to plug in a controller finds out it was never run. Shipping the enum with an unimplemented arm would be worse still.

What the design does demonstrate, with hardware this machine has, is the property the gamepad claim actually rests on: one action, several bindings, on more than one device. The demo binds spawn_sparks to Space and to the left mouse button, and §4's five-frame walk is exactly the multi-device case in miniature. A gamepad is a third device that behaves like the second.

And here is what adding one would take, so the claim is checkable rather than asserted:

  1. Two enumerators on input_source: gamepad_button and gamepad_axis.
  2. Two arms in update()'s switch, reading SDL_GetGamepadButton and SDL_GetGamepadAxis. ⚠ VERIFY both signatures and the axis range against SDL3/SDL_gamepad.h before typing them: SDL3 renamed this whole family from SDL2's SDL_GameController*, and the axis value is a signed 16-bit integer that has to be normalised before it can be scaled.
  3. Two more accessors on the input_snapshot concept, which is the only part that touches existing code — and it touches it additively.
  4. A deadzone, which belongs on the binding rather than the action, because two sticks on the same pad can want different ones.
  5. Device connect/disconnect handling, which is the part that is actually hard: an action bound to a controller that has been unplugged must go inactive, and the release edge must fire.

Exercise 11.2 does it. Point 5 is the one worth thinking about before you start.

10Common Pitfalls & Debugging

The player jumps twice, but only sometimes

Symptom. One press, two jumps — on some machines, on some frames, and never while you are watching.

Cause. Two possibilities, and they need different fixes. Either the edge was read inside on_fixed_step on a two-step frame, or the action has two bindings and the edges were derived from the bindings instead of the level.

Fix. For the first, consume_pressed(). For the second, derive from the level. To tell them apart: unbind everything but one key. If it stops, it was the second; if it persists, it was the first.

An input is occasionally ignored entirely

Symptom. A press does nothing, roughly once in a hundred, more often when the machine is busy.

Cause. A zero-step frame. The accumulator had not built up a full step's worth of time, so on_fixed_step did not run, and a frame-scoped edge came and went with nothing listening.

Fix. consume_pressed(), which queues it until a step happens. This one is genuinely hard to reproduce deliberately, which is why the harness simulates the frame structure directly rather than hoping to catch it.

Every step of the frame reacts to input one frame late

Symptom. The game feels slightly mushy. Nothing is broken; everything is 16 ms behind.

Cause. action_map::update() is being called in on_frame, which runs after the steps.

Fix. on_input(). It exists for exactly this, and the symptom is worth knowing because it is the kind that gets attributed to the display, the driver, or the mouse.

A key held while alt-tabbing is still held on return

Symptom. Come back to the window and the character is walking.

Cause. The level was true when focus was lost, and nothing said otherwise while the window was in the background.

Fix. reset() on SDL_EVENT_WINDOW_FOCUS_LOST. It clears levels, edges and the queue, so the next update sees a fresh rising edge if the key really is still down. Note that it also forgets the mouse origin, deliberately — otherwise the first frame back delivers the entire distance the cursor travelled while you were away.

An axis reads a huge value on the first frame

Symptom. The camera snaps somewhere absurd exactly once, at start-up or after a scene change.

Cause. A mouse delta computed against a previous position that was never set, so the first frame's "delta" is the cursor's absolute position.

Fix. The map tracks whether it has a previous sample and reports zero until it does. §F of the harness asserts exactly this, and also that reset() puts it back into that state.

An action silently does nothing after editing a config file

Symptom. A control stops working, with no error anywhere.

Cause. A typo in an action name. If lookup declared on miss, the typo would create a brand-new action with no bindings and no code reading it — a perfectly functioning thing that does nothing.

Fix. find() returns an invalid id and does not declare; declare() is the only thing that creates. Check the return. The harness asserts that find of an unknown name leaves the action count unchanged.

11Exercises

  1. 11.1 — Save and load the bindings. Write the binding table to a text file and read it back, so a player's rebinds survive a restart. Actions by name, not by id — the ids are assignment order and will change the moment somebody adds a declare call.

    Hint

    One line per binding: action name, source, code, scale. Loading is declare(name) — which is idempotent, so it does the right thing whether or not the program declared it first — then the matching bind_*.

    Solution sketch

    The interesting part is not the parsing, it is what to do when a file names an action the program does not have. Declaring it is wrong (it will never be read); refusing to load the file is wrong (one stale line should not lose every rebind). Skip the line and log it — the same shape Lesson 5.3's log/error rules produce everywhere else.

  2. 11.2 — Add the gamepad. §7 lists the five steps and marks the SDL3 signature as needing verification against the headers. Do all five. Then unplug the controller while an action bound to it is held, and make sure the release edge fires.

    Hint

    The first four are mechanical. The fifth is the exercise: a disconnected device stops answering, and "stops answering" must become "contributes zero" rather than "keeps its last value". Where does that belong — in the binding, or in whatever owns the SDL_Gamepad*?

    Solution sketch

    In the snapshot, not in the map. A disconnected pad's key_down equivalent returns false, the sum drops to zero, the level goes false, and the release edge falls out of §4's existing machinery with no new code at all. If you found yourself adding a special case to action_map, the abstraction boundary is in the wrong place — and noticing that is worth more than the feature.

  3. 11.3 — Record and replay. Record the action values of every frame to a buffer, then play them back through a snapshot type that reads from the buffer instead of from a device. Check that the demo reproduces itself exactly.

    Hint

    You do not need to record inputs at all — record the action values, and make the playback source a type satisfying input_snapshot whose six functions are backed by the recording. This is §1's third problem, solved.

    Solution sketch

    It will not reproduce exactly, and finding out why is the exercise. The simulation is deterministic (Lesson 1.4 verified that) but the number of steps per frame is not — it depends on wall-clock time. A replay has to record and replay the step count as well as the input, or drive the loop at a fixed step count. That is why replay systems and fixed timesteps are always discussed together.

  4. 11.4 — Conflict detection. Add action_map::conflicts(SDL_Scancode), returning every action already bound to a key, so a settings screen can warn before a rebind silently shadows something. Then decide: should bind_key refuse a conflict?

    Solution sketch

    It should not. Two actions on one key is often deliberate — "accept" and "shoot" in different contexts, a modifier-free chord — and a binding layer that refuses it forces the caller to work around it. Report the conflict and let the caller decide, which is the same shape as Lesson 5.5's asset store reporting a load failure instead of substituting a default. The flat binding list this exercise walks is the reason §8's table is flat rather than per-action.

  5. 11.5 — Put the map in a component. §2.2 claims a two-player game holds two maps and a per-entity game puts one in a component. Prove it: add a player_input component holding an action_map, give two entities one each with different bindings, and drive them from a single view<player_input, placement>.

    Hint

    action_map holds vectors, so it is movable but not trivially copyable — which is fine, because Lesson 5.8's pool<T> requires only movability. Worth checking that claim rather than assuming it.

    Solution sketch

    It works, and the interesting discovery is where update() goes: once per map, per frame, in on_input — which is a view<player_input> walk, and therefore a system like any other. Lesson 5.7's rule 1 (components stay small) argues against it at scale, since an action_map is several vectors; the honest alternative is a component holding an index into a small array of maps.

12Recap & Next

The engine can now be told what the player meant. What it gained:

  • Actions, bindings and values — one name in the middle, and the four things §1 could not do all become possible. No gameplay code in the demo names a key.
  • One mechanism for buttons and axes. Every binding contributes a signed value; an action's value is the sum. Holding both halves of an axis gives exactly zero, and no rule anywhere says so.
  • Edges derived from the action's level. The bug this avoids is invisible with one binding per action and fires as "sometimes it jumps twice" the moment somebody binds a second device.
  • A second kind of edge for the fixed step. consume_pressed() fires exactly once per press however many times the step runs — including zero — which is Lesson 1.4's trap closed rather than documented.
  • The hook that was missing. on_input(): once per frame, after input, before the simulation. Nothing else in the frame is that.
  • A concept instead of an interface. input_snapshot makes the mapping logic testable without a base class, without a virtual call, and without one character changing in Lesson 1.2's header.

And what it did not gain, said plainly: a gamepad. §7 gives the reason — it could not be run here, and untested device code is a liability — along with the five steps and the one that is actually hard. What is demonstrated is the property the gamepad claim rests on: one action, several bindings, more than one device.

The reference shot from Lesson 5.1 is byte-identical for the tenth lesson.

  • Unity's Input System package — the same three-layer shape (actions, bindings, control schemes) at production scale, with the composite bindings this lesson's signed-sum rule replaces. Their “1D Axis” composite is exactly §3's two keys with opposite scales, given a name and a UI.
  • Unreal's Enhanced Input — the other production answer, and interestingly different: modifiers and triggers are first-class objects in the binding chain rather than a scale. Worth reading against §3 to see what a richer mechanism buys and costs.
  • SDL3 SDL_gamepad.h — the header to read before attempting Exercise 11.2, and the authority for the signatures §7 declines to guess at.
  • Glenn Fiedler, “Fix Your Timestep!” — the source of the accumulator this lesson's queue exists to survive. Re-read the variable-step-count section with §5.2 in mind; the input problem is a consequence of the loop and is rarely mentioned alongside it.
  • Lesson 1.2 for the level-versus-edge distinction this builds on, 1.4 for the accumulator, and 5.2 for the application layer that gained a hook.
