Module 5 — Becoming an Engine · Lesson 5.8

The ECS Runtime

Lesson 5.7 chose the sparse set by measurement and left four rules behind. This lesson builds it: an entity id minted once and honoured by every pool, a component pool that is three arrays and about twenty lines of logic, a registry that ties them together without RTTI, and a query that leads with the smallest pool because 5.7 measured what leading with the biggest one costs. Then it runs the result at a hundred and twenty-one entities and says plainly what that buys — which is not speed, and the lesson opens by admitting it.

1The Problem

Let us begin by throwing away the argument you were probably expecting.

The demo this course has been carrying since Lesson 2.12 holds its objects in an array of four. Lesson 5.6 measured what that costs, at five world sizes, with the optimiser on and off, and the answer for four objects was nothing — every storage layout it tried came within one percent of every other below a thousand objects, and the knee where layout starts to matter sat between 1,000 and 10,000. Lesson 5.7 then measured the two ECS storage designs against each other and found the same shape again: below a thousand entities every arm was within 16% of every other, and the interesting numbers only appeared at 100,000.

So an ECS is not going to make this engine faster today, and a lesson that opened by implying otherwise would be teaching the exact folklore this course exists to argue with. The reason to build one now is that scene_object has been quietly failing for five lessons, and the failure is about expression rather than speed.

Here is the whole history, and it is short. In Lesson 2.12 a scene_object was a transform and a mesh — the smallest honest definition of a renderable thing. Lesson 3.1 filled the triangles, so it needed a colour, and gained a tint. Lesson 3.4 added back-face culling, which is only valid on closed surfaces, so it gained closed. Lesson 3.7 added specular highlights, so it gained a whole specular surface sub-struct. Lesson 5.4 turned the mesh into a handle. And at every one of those steps the comment in scene.hpp said some version of the same uncomfortable thing:

“Look at what just happened to this struct. tint was enough while a surface was one colour; then 3.4 needed closed; now 3.7 needs two more numbers, and all four describe the same thing — the surface — while xform and geometry describe where it is and what shape it is. That is two different kinds of data wearing one struct.”

Two kinds became four. And because a struct is a promise that every instance has every field, each addition was paid for by every object whether or not it meant anything: the ground plane carries a shininess it never uses, and an object that should not be drawn at all has no way to say so except a null handle and a branch in the renderer.

Read the lower half of Figure 1 and notice what is not in it. There is no empty cell to explain, because an entity that has no material does not have a blank material — it has no row in the material pool, and the material pool has never heard of it. The render query in §5 names placement, geometry and material, and a waypoint entity that carries only the first is skipped by the query rather than filtered by the renderer. Nobody wrote that skip. It falls out of asking the right question.

That is what this lesson buys, and it is worth having at 121 objects. The performance argument is Lesson 5.7's, it is real, and it applies at ten thousand — we will build the thing that is ready for it, and we will not pretend it is why.

What this lesson does not do

Nothing renders through the ECS yet. collect_triangles still takes a span of scene_object, and the demo's render system walks a view and fills one — a bridge, six lines long, marked temporary in the source. Converting the renderer is Module 6's job, and doing it here would mean changing the architecture and the picture in the same lesson, with no way afterwards to tell which change broke what. The reference shot from Lesson 5.1 is still byte-identical after this lesson (§6), and that is a fact worth having rather than a coincidence.

2Building Intuition

2.1 What we already have, and the one thing it lacks

Open engine/include/engine/core/pool.hpp — Lesson 5.4's container — and read its member list with Lesson 5.7's vocabulary in your head:

The three arrays of Lesson 5.4's pool, and what each one is called in sparse-set terms.
pool<T> calls ita sparse set calls it what it does
slots_the sparse array one entry per slot ever created, indexed by a handle's index field, never moves
items_the dense data live objects only, packed, no holes, order unspecified
owners_the dense id list which slot each dense element belongs to — the way back

That is a sparse set. It has generations, it has swap-and-pop removal, it has O(1) insert, remove, lookup and a contiguous iteration span. Lesson 5.7 noticed this out loud and then refused to let it decide the architecture, on the grounds that choosing a design because you happen to own something shaped like it is choosing by accident. Now that the design has been chosen on the evidence, the resemblance is simply useful: most of this lesson's storage code is code you have already read once.

So what is missing? One thing, and it is structural rather than incremental:

Every pool<T> mints its own keys. Insert a mesh and you get handle<mesh_data>{index 7, generation 1}; insert a texture into a different pool and you get handle<texture>{index 7, generation 1}. Two sevens. They came off two different free lists, they refer to two unrelated slots, and the phantom type parameter exists precisely to stop you confusing them. Ask “does the thing in mesh slot 7 also have a texture?” and you do not get a slow answer — you get no answer, because the question is not well formed.

An ECS is the arrangement in which that question is well formed. Mint the id once, from one allocator, and hand the same id to every pool. That is all. Everything else in this lesson — the views, the systems, the composition argument — is a consequence of that single inversion.

2.2 A component is a struct; a system is a loop

Before any code, it is worth being precise about how little an ECS asks of you, because most of the reputation for complexity comes from frameworks rather than from the idea.

A component is a plain struct. No base class, no virtual functions, no registration macro, no header of its own. Our registry requires exactly one thing of a component type — that it be movable — and it does not even require that it be default-constructible. The demo in §5 uses engine::transform, written in Lesson 2.8 by somebody who had never heard of an ECS, as a component without modifying or recompiling it.

A system is a free function that takes the world and runs one query:

Not a class, not a virtual update(), not a base System. There is nothing for such a base to hold, because a system's entire state is the query it runs — and Lesson 5.6 measured what a virtual call costs on an iteration (1.5–1.7× at every world size, including four objects sitting in L1) and concluded that ECS iteration must not be virtual. Free functions are not a stylistic preference here; they are that measurement, obeyed.

There is a second thing to notice about that signature, and it will matter in Module 8. The query declares the data flow: orbit_system writes placements and reads orbits, and you can see that from the first line without reading the body. A job system deciding whether two systems may run concurrently needs exactly that information, and here it is legible for free.

2.3 The useful thing is the absence

The mental shift that makes an ECS click is small and slightly counter-intuitive: an entity is not a thing that has components. It is an id, and the components are filed under it.

The difference sounds like philosophy and is entirely practical. If an entity had components, an entity would need to be an object, that object would need to know what it holds, and adding a component would mean modifying it. Because components are merely filed under the id, adding one touches exactly one pool and nothing else in the world learns about it — which is precisely the 4.2 ns structural change Lesson 5.7 measured, and precisely why that number did not move when the entity grew from four component types to twelve.

It also means the interesting queries are the ones about absence. “Every entity with a placement and an orbit but no geometry” is a sentence about a set difference, and in a world of structs it is a sentence about a flag somebody remembered to set. We will not build exclusion queries in this lesson — Exercise 10.2 does — but the reason they are easy is visible already: the pools are sets, and set operations are what sets are for.

3The Theory

3.1 One shared id space

Lesson 5.7's rule 2 says the entity id must be minted once and handed to every pool. Two consequences follow immediately, and both shape the code.

First: the id space must stay compact. Every pool's sparse array is indexed by an entity's index field, so it must be at least as long as the largest index in use. If ids were handed out by an ever-increasing counter, a game that spawned and killed a thousand bullets a second would push that counter past three million in an hour, and every component type in the world would carry a three-million-entry sparse array — twelve megabytes each, almost all of it meaning “absent”.

A free list fixes this, and the fix is worth stating as an equation because it is the whole reason Lesson 5.7 could rule out paged sparse arrays:

The high-water mark

high-water mark = peak simultaneously live entities, not entities ever created.

Reuse a slot before minting a new one and the index space never grows past the largest number of entities that were alive at one instant. The verification harness in §6 makes this concrete: 200 frames of churn create 518 entities and destroy 301, and the id space ends at 220 slots — the peak live count, not the 518.

Second: reuse means an old id can name a new occupant, which is Lesson 5.4's aliasing failure arriving in a world where it happens constantly. Entities die every frame in a way that meshes and textures do not, so the generation is not a nicety here; it is the difference between “that entity is gone” and “that entity is now somebody else's spaceship”.

3.2 The entity word, and what a generation check costs

We reuse Lesson 5.4's bit budget exactly — 20 bits of index, 12 of generation, generation 0 reserved so that the null entity is all-bits-zero — and we include those constants from core/handle.hpp rather than restating them, so the budget has one home.

Work Figure 3 through with real numbers. Three entities are minted, so slots 0, 1 and 2 each carry generation 1, and b = {index 1, generation 1}, which packs to:

Packing b

bits = (generation << 20) | index = (1 << 20) | 1 = 1,048,576 + 1 = 1,048,577

Now destroy(b). Slot 1 is marked free, its generation becomes 2, and index 1 goes onto the free list. b still holds 1,048,577, and the slot now says generation 2, so:

Testing the stale id

alive(b) = (1 < 3) && slots[1].live && (slots[1].generation == 1)

= true && false && false = false

Then create() pops slot 1 off the free list and returns b2 = {index 1, generation 2}, packing to 2,097,153. Both ids name slot 1; only one of them is alive; and the test that separates them is a single 32-bit comparison. That is the entire mechanism, and it costs one integer compare on a value already in a register.

Bump on removal, never on insertion

Lesson 5.4 derived this and it is worth re-stating because entities are the case that makes it matter. If the generation were bumped when a slot was taken, there would be a window — between the free and the next create — during which a freed slot still carried the generation an outstanding id holds, and alive() would say yes. Bumping on removal closes the window to zero width: from the instant of the free, every id that ever named that slot is stale.

The 12-bit budget, and why entities are the case it worries about

4,095 usable generations means a slot's generation repeats after 4,095 frees of that same slot, and a LIFO free list hammers one slot rather than spreading the load. core/handle.hpp did the arithmetic: at one recycle per frame that is 68 seconds. For assets — loaded at level boundaries, counted in hundreds — this is unreachable. For entities in a bullet-hell it is not, and §A of the harness drives one slot through 4,096 create/destroy pairs and confirms the wrap counter reads exactly 1. The counter exists so the assumption is monitored; if it ever leaves zero, the two fixes are a FIFO free list (which multiplies time-to-wrap by the slot count) or a 64-bit id split 32/32.

3.3 The sparse set, walked by hand

One component type's storage is three arrays. Let us fill them with actual numbers and then take one apart.

Five entities — ids 7, 4, 91, 30 and 12 — each get a component, inserted in that order. Insertion appends, so:

The three arrays of a sparse set holding five components.
01234
dense_[i]e=7e=4e=91e=30 e=12
data_[i]T(7)T(4)T(91)T(30) T(12)

…and sparse_ is indexed by entity, not by position, so it is a 92-entry array of which five entries are set: sparse_[7] = 0, sparse_[4] = 1, sparse_[91] = 2, sparse_[30] = 3, sparse_[12] = 4, and the other 87 hold the “no component” sentinel.

A lookup is then two array reads: data_[sparse_[e.index()]]. The second read's address depends on the first read's value, which is the two-deep dependent chain Lesson 5.7 spent a whole figure on, and 5.7's finding was that it is latency rather than work — free until the working set leaves cache and the pools' orders diverge.

Removal is where the design earns its keep and where implementations go wrong. Erase entity 4's component:

Step by step. sparse_[4] is 1, so the hole is at dense position 1. The last element (position 4, entity 12) moves into it: dense_[1] = 12 and data_[1] = T(12). Then both arrays are popped, and sparse_[4] is set to “absent”.

And one more thing has to happen, which is the line people forget. Entity 12 did not ask to move. Its sparse entry still says 4 — a position that no longer exists — so it must be patched to 1. Miss that line and the pool is not obviously broken: it is silently broken, and the symptom appears an arbitrary number of frames later, in a different system, as one entity reading another's data. Lesson 5.7 hit exactly this bug in the archetype arm of its probe, and found it only because the test churned two hundred frames before checking.

Worked edge case — erasing the last element

Erase the element at the end, and the “element that moves” is the element being erased. Trace it: at equals last, so the swap is skipped entirely; both arrays pop; then sparse_[e] is set to absent. If the swap were not skipped, it would copy the element onto itself and patch its own sparse entry to the position it already occupies — harmless, and then immediately overwritten by the final line. Either way the order saves us, and it is the order rather than the branch that is load-bearing. §B of the harness tests this case on its own, because a test that only ever erases from the middle passes forever.

Finally, contains() is three tests and the third is the one that costs a line and buys the whole design:

dense_ stores the full 32-bit entity word, generation included, so an id naming the same slot with an older generation is rejected. Store a bare index there instead — which is what a naïve sparse set does, and it saves nothing — and that third test cannot be written at all. Lesson 5.4's aliasing failure walks straight back in.

3.4 A query is a set intersection

view<placement, geometry, material> asks for the entities in all three pools. That is an intersection of three sets, and the classic result about intersecting sets is that you should iterate the smallest one: the cost is O(smallest × lookups), not O(largest).

Lesson 5.7 turned that into a measurement rather than an assertion. At one-in-four selectivity and 100,000 entities, leading with the big pool cost 1.73× a real archetype and leading with the small one cost 1.46× — identical code, differing only in which array the outer loop walks. A fifth of the walk for the same six answers, and the gap widens as the component gets rarer: a query for “entities with a placement and a player_input” in a world of 10,000 entities and one player walks one candidate if it leads correctly and 10,000 if it does not. The decision is one comparison in a constructor, made once per query rather than once per entity, so it is free in every sense that matters.

There is a second, smaller prize in leading with a pool, and it is easy to miss. For the lead pool, the dense position is the loop counter — we are walking its dense array in order — so the lead's own component needs no sparse lookup at all. Only the other K−1 pools pay the redirect.

3.5 Type erasure without RTTI

One problem remains, and it is the only genuinely hard one in the file. registry::destroy(e) must erase e's row from every pool, and those pools have different types. C++ offers two ways to hold a heterogeneous collection like that.

The obvious one is RTTI: key the pools by std::type_index and recover the concrete type with dynamic_cast. It is not available to us — the engine core is built with RTTI off since Lesson 5.1 — and that turns out to be a mercy rather than a constraint, because dynamic_cast is a runtime walk of the type graph and a type_index lookup is a hash on a path that ought to be an array index.

The alternative is to assign the numbers ourselves:

Each component type gets a small integer the first time anybody asks, from a counter behind a function-local static. That integer indexes a std::vector<std::unique_ptr<pool_base>>, and the concrete type is recovered with a plain static_cast — which is safe for a reason worth saying out loud: the id is what created the pool. The object at index component_id_of<T>() was constructed as a pool<T> and nothing else can ever be stored there, so the downcast is justified by construction rather than checked at use. That is the difference between a cast that is safe and a cast that is merely usually right.

The cost of not keeping a per-entity component mask is visible in the lower half of Figure 6: destroying an entity that had three components makes five virtual calls, two of which return after a single array read. At the five types in that figure — or the six the demo uses — that is nothing. An engine with three hundred component types would keep the mask, and Lesson 5.7 §9 said so.

C++ in place — the function-template static

component_id_of<T>() works because of two guarantees the language makes. A static local inside a function template is one object per instantiation, shared across every translation unit — which is what makes the id for placement the same number in the demo and in the test harness, without a registration step. And since C++11 its initialisation is thread-safe (“magic statics”), so two threads calling it simultaneously cannot both run the initialiser.

What is not thread-safe is the counter increment behind it, so the honest rule is the one in the header: touch each component type once before the job system starts. That constraint is shared by every container in this engine until Module 8 revisits all of them at once.

4The Implementation

Four headers, all of them header-only, none of them adding a line to engine/CMakeLists.txt. They are deliberately separable: each of the first two is testable without the others, and the dependency runs one way only.

That split is why the harness in §6 can test the allocator with no components in sight (§A) and the pool with no registry (§B). A design whose pieces can only be tested together is a design whose pieces are not really pieces.

4.1 entity.hpp — minting ids

The type first. An entity is one 32-bit word with the same layout as handle<T>, and it reuses that header's constants rather than restating them:

Why is this not just handle<entity_tag>? It was the first thing tried, and the reason it is not here is worth a paragraph, because it is not “handles are wrong”. Everything core/handle.hpp argues is argued again here — index plus generation, twenty bits and twelve, generation zero reserved, the bump on removal. What differs is what the type means:

What a handle names compared with what an entity names.
namesthe thing it names
handle<mesh_data>an item in a pool<mesh_data>lives in exactly one container

Aliasing them would compile, and then pool<T>::get(handle<T>) and a component lookup would be spelled the same way while meaning opposite things. The phantom type parameter in handle.hpp exists precisely so that two ids which must not mix cannot mix; spending it to make them mix would be an odd use of it.

The allocator is Lesson 5.4's slot machinery with the payload deleted. create() pops the free list or grows; destroy() bumps the generation and pushes the slot back:

Note what this function does not do: it does not touch a single component, and it cannot, because the allocator has never heard of one. registry::destroy is the operation that erases the rows and then calls this. Calling this one directly on an entity that still has components leaves those rows filed under an id nothing will ever look up again — a leak with no symptom — which is why the registry is the public door.

Eight bytes for five bits, and the arithmetic that says it is fine

A slot holds a 12-bit generation and one live flag, so a packed slot fits in two bytes; ours takes eight, because { std::uint32_t; bool; } pads. At the 10,000 peak entities Lesson 5.7 budgeted for, the difference is 80 KB against 20 KB — both of which vanish beside the 400 KB of component sparse arrays that the same 10,000 entities imply across ten component types. Packing this would buy 0.4 KB per thousand entities and cost every reader a shift and a mask. The fields are private, so if a profile ever disagrees the change is local.

4.2 pool.hpp — one component type's storage

The three arrays from §3.3, and about twenty lines of logic. The insert is unremarkable — resize the sparse array if this entity's index is a new high-water mark, write the sparse entry, push both dense arrays. The erase is the one to read carefully:

Three things about those eighteen lines.

The patch is line three of the if, and it is the entire subject of Figure 4. Without it the pool is silently corrupt: the entity that got swapped into the hole still believes its component is at the old position, so the next lookup returns somebody else's data. It is one line, it is easy to leave out, and it produces the least debuggable class of bug there is.

The last-element case is handled by the if, and the reason the guard exists is subtler than “skip a redundant copy”. When at == last, the entity that “moves” is the entity being erased — so the patch would write its sparse entry back to the position it already occupies, immediately before the final line marks it absent. Harmless either way. The order is what saves us, not the branch, and §B of the harness tests this case separately because a test that only ever erases from the middle passes forever.

data_[at] = std::move(data_[last]) is a move, not a copy. A component might own a buffer; assigning a moved-from value into the hole and then popping means the erased component's resources are released with it rather than kept alive by a copy nobody is looking at. This is the same care engine::pool::remove takes for the same reason.

One more piece, and it is the piece the view is built on:

Every function there is cold, and that is a constraint rather than an accident. erase runs once per pool per entity destruction; clear once at teardown; entities() once per view, not once per entity. Nothing on the hot path goes through this interface — a view holds concrete pool<T>* and calls non-virtual members — which is Lesson 5.6's measurement being obeyed rather than quoted. pool<T> is final besides, so even the cold calls devirtualise wherever the static type is known.

entities() deserves its own sentence. It returns std::span<const entity> for every T — a type-independent window onto a type-dependent container. That one signature is what lets the view in §4.4 choose the smallest of four pools with a plain loop rather than a pile of template machinery.

Two containers called pool, on purpose

engine::pool<T> (Lesson 5.4) and engine::ecs::pool<T> (this lesson) are different containers with the same name. Same three arrays, same swap-and-pop, same generational check — opposite jobs: one mints its own keys, the other is keyed by an id it did not mint. Calling this one component_storage would hide a relationship the course spent two lessons drawing out, so the namespace keeps them apart instead. Inside engine::ecs, bare pool is this one. The one arrangement that breaks is using namespace engine; and using namespace engine::ecs; in the same scope, which makes bare pool ambiguous — and an ambiguity the compiler reports is the good kind.

4.3 registry.hpp — the world

The registry is an entity_allocator and a vector of type-erased pools, and its interesting method is the one from §3.5:

There is a second, non-creating version — storage_if<T>() — and every read path uses it. That is not a micro-optimisation; it is a correctness property. If has<T>() went through storage<T>(), then merely asking whether an entity had a component would allocate a pool and grow the pool vector, which makes a query a mutating operation and makes a const registry impossible. Views use storage_if too, so a view naming a component type nobody has ever attached is simply empty — the right answer, arrived at without a special case.

destroy is where the type erasure earns itself:

Every pool, every time, because the registry keeps no record of which components an entity holds — such a record would be a second source of truth and the pools are the first. The cost is one virtual call per component type, not per component, and most of them return after a single array read. At the demo's five types that is nothing; an engine with three hundred component types would keep a per-entity bitmask, and Lesson 5.7 §9 said as much.

Two smaller decisions worth naming. add<T> to a dead entity asserts in debug and is refused in release — refusing rather than filing it, because a component filed under a dead id is invisible to every query and will never be erased, which is a leak whose only symptom is a pool that keeps growing. And has<T> deliberately does not check liveness first: a stale entity fails pool::contains anyway (the full-word comparison from §3.3), so an alive() call would be a second, slower route to the same answer on the hottest path in the engine.

4.4 view.hpp — the query, and rule 3

Here is rule 3, in the form it actually takes:

Five lines, no metaprogramming, no dispatch. The trick is entirely in entities() returning the same type for every pool: a pack of pool<Ts>* becomes an ordinary array of spans, and choosing the smallest is a for loop a beginner could write. The (... || ...) fold at the top is a C++17 fold expression — “is any of these null?” — and a null pool means the type has never been used, so nothing can have it and the view is empty.

The walk itself:

The && fold short-circuits, so the first pool that says no stops the rest from being asked, and I == lead_ skips the lead entirely — it contains e by construction, since that is where e came from. The if constexpr lets a callback take the entity or not; most systems never use the id, and a parameter that is always (void)-cast is a parameter that should not have been there.

And fetch, which is where the lead pool earns its keep a second time:

For the lead pool the dense position is the loop counter, so its component is data_[i] — the next element of an array we are already walking, with no sparse read and no random access. Only the other pools pay the redirect. I == lead_ compares a compile-time constant against a value fixed for the whole loop, so the branch predicts perfectly after the first iteration.

The one rule a view imposes

Do not add or erase components of a type this view names while iterating it. The walk is over the lead pool's dense array by position, and both insert and erase move elements of that array — so a callback that destroys the entity it was just handed will skip whichever entity got swapped into its place, and one that inserts may reallocate the array outright.

This is exactly how mutating a std::vector inside a range-for behaves, and it is no more forgivable here. The assertion in fetch catches it in a debug build the moment the dense position stops matching the entity. The two safe patterns are the familiar ones: collect, then act (which is what lifetime_system in the demo does, and why it takes a scratch vector), or defer the change to a command list — Module 8 builds one for the job system.

4.5 What is deliberately not here

Groups. Lesson 5.7's decisive measurement was that two pools sorted to agree on dense order let a query read no sparse entry at all, and run at 0.99× a real archetype on the archetype's own best case. That number is why this course chose a sparse set: it means the migration only ever runs one way — a sparse set can be given an archetype's query later, one group at a time, and an archetype can never be given O(1) structural change, because moving between archetypes is what an archetype is.

So the door is deliberately left open and deliberately not walked through. Building a group now would be optimising before there is a profile, on an engine whose demo has 121 entities and whose renderer does not read the ECS at all. pool::components() documents that its dense order is nobody's business precisely so that a future group may sort it, and Exercise 10.4 builds one for a reader who wants to see the 0.99× for themselves.

Also absent, and each for a stated reason: exclusion queries (view<A>().without<B>(), which is Exercise 10.2 and about fifteen lines); const views, which need a second class template or a const T spelling and have no caller yet; signals (on-construct, on-destroy callbacks), which every mature ECS grows and none of which we can design without a user; and thread safety, which Module 8 addresses for every container in the engine at once rather than one at a time.

The seam, named rather than hidden

That is a copy of six fields per visible entity — about 8 KB at 97 objects, which is nothing, and which stops being nothing at 10,000. It is in the source with a comment saying exactly that, because a temporary bridge that nobody wrote down is a permanent bridge. Module 6 removes it by teaching the renderer to read pools directly.

6Verification

scratch/verify_58.cpp is 101 checks in seven sections. Three of them are worth describing, because they are the ones that could actually fail.

§D checks a design decision, not a behaviour. The other sections check that the view returns the right answer — but a view that walked the biggest pool would also return the right answer, more slowly, and no correctness test would notice. So view exposes lead() and size_hint(), and §D asserts that a view over pools of 60, 30 and 12 leads with the 12 and considers twelve candidates. A rule nothing can observe is a rule that quietly stops being true.

§E is 200 frames of churn against an independent model. Three std::maps track what the world should hold, and share not one line of code with the thing under test; after two hundred frames of spawning, killing, adding and removing, every entry in the model must resolve to the right value and no pool may hold a row the model does not know about. This is the shape that found a real bug in Lesson 5.7 — a single-frame test of swap-and-pop passes forever, because the failure needs the moved element to be the element being removed, which is one iteration in N.

The run reports the numbers as it goes, and two of them are the theory from §3.1 measured:

220 slots for 518 entities created. That is rule 4's premise, measured: the id space is sized by peak live, so every component pool's sparse array is too, and the paged sparse arrays that real ECS libraries need can wait until the 12 MB line above becomes a number somebody minds.

§G is the one that has run for eight lessons. The reference shot written in Lesson 5.1 is still byte-identical — 1,209,616 bytes, unchanged. That is not a decoration: the ECS is purely additive this lesson, nothing renders through it, so the picture cannot have moved, and if it had we would know immediately that the change was not where we thought it was.

The full run

101 checks, 0 failures at -O2 -DNDEBUG (99 in a debug build, where two checks are skipped because an assertion fires before the release-path refusal can be observed — the harness says so rather than silently passing). All twelve earlier harnesses, verify_45 through verify_57, are still green.

9Common Pitfalls & Debugging

One entity reads another's component, hours after the bug

Symptom. Everything works for a while. Then an object teleports, or takes on another object's colour, or a system writes into the wrong row — and it starts happening only after entities have been destroyed for a bit.

Cause. The missing sparse patch in erase. The entity that got swapped into the hole still has a sparse entry pointing at its old dense position.

Fix. sparse_[dense_[at].index()] = at; after the swap. To find it, do what §E does: churn for a few hundred frames, then walk every pool and assert sparse_[dense_[i].index()] == i for every i. That one invariant catches the entire class.

A loop over a view skips every other entity

Symptom. A system that destroys entities — a lifetime system, a damage system — only ever kills about half of what it should, and the survivors change from run to run.

Cause. Destroying inside the callback. The erase swap-and-pops the lead pool's dense array, the entity that moved into position i is never visited, and the loop moves on to i + 1.

Fix. Collect, then act — see lifetime_system. In a debug build the assertion inside view::fetch fires on the first occurrence and names the position and both entities.

A recycled entity inherits a dead one's components

Symptom. A freshly created entity already has a velocity nobody gave it.

Cause. Either entity_allocator::destroy was called directly instead of registry::destroy (so the rows were never erased), or dense_ stores bare indices instead of full entity words (so the generation cannot be compared).

Fix. Go through the registry, and store the whole word. Note that these are two independent defences and either alone would prevent the symptom — which is precisely why §E's shadow-model check exists rather than a single targeted test: a test that passes with one of the two broken is not testing much.

A stored T* points at the wrong component

Symptom. A pointer from get<T>(), cached across a call that adds or removes a component, starts writing into somebody else's row — or into freed memory if the vector reallocated.

Cause. The same one Lesson 5.4 abolished, wearing new clothes. Resolve late, use immediately, never store.

Fix. Hold the entity, not the pointer. Under a sanitiser (-fsanitize=address) the reallocation case is caught instantly; the swap-and-pop case is not, because that memory is still validly owned by the vector — which is exactly why the rule is a rule rather than a suggestion.

Memory climbs and never comes back down

Symptom. A level that spawns a hundred thousand short-lived entities leaves every component pool holding a hundred-thousand-entry sparse array for the rest of the process.

Cause. High-water marks do not fall. The free list keeps the id space compact against peak live, and if peak live was once 100,000 then that is the size for ever.

Fix. The same answer Lesson 5.4 gave and Lesson 5.7 repeated: things that exist in millions and die in seconds should not be entities. A particle system owns its own array. Entities are for things a designer would name.

Ambiguous pool

Symptom. error: reference to 'pool' is ambiguous.

Cause. using namespace engine; and using namespace engine::ecs; in the same scope, which drags both engine::pool and engine::ecs::pool into one name.

Fix. Qualify, or drop one of the usings. The engine's own code never writes using namespace at all, which is why this cannot happen inside the library.

10Exercises

  1. 10.1 — Make the lead choice observable in the demo. The HUD prints lead pool for the render view. Add a second readout that prints what the walk would have cost with the worst lead — that is, the size of the largest named pool — so the saving is on screen as a ratio rather than as a claim. Then press M and watch it move.

    Hint

    view already stores every pool pointer. Add a size_worst() beside size_hint() that takes the max instead of the min — the array of spans in the constructor has everything you need.

  2. 10.2 — Exclusion. Add view<Ts...>::without<Us...>(), so a query can ask for “every entity with a placement and an orbit but no geometry” — which is exactly the demo's waypoints, and currently not expressible. Then use it to draw the waypoints as debug-draw crosses, and watch twenty-four invisible things become visible without a single new component.

    Hint

    The excluded pools do not participate in choosing the lead — they can only make the result smaller, never the walk. One more fold in the filter: (... && !excluded->contains(e)), with a null excluded pool meaning "nothing has it", which is trivially satisfied.

    Solution sketch

    Store a second tuple of pool<Us>*. In each_impl, after the inclusion fold passes, run if ((... || (ex<J> != nullptr && ex<J>->contains(e)))) continue;. Roughly fifteen lines including a second index_sequence. Note that a null excluded pool must mean “nobody has this component”, so the fold must test the pointer first — getting that backwards makes every exclusion query empty.

  3. 10.3 — Break it on purpose, then catch it. Delete the line sparse_[dense_[at].index()] = at; from pool::erase and run verify_58. Which sections fail, and after how many frames of §E? Then put it back, and instead delete the dense_[at] == e term from contains. Which sections fail now? Write down, in one sentence each, what class of bug each line prevents.

    Solution sketch

    The missing patch fails §B immediately (the “entity swapped into the hole still resolves” check is aimed straight at it) and §E's value comparison. The missing generation term is more interesting: §A and §B's early checks still pass, and the failure shows up in §B's impostor test and in §C's “recycled id inherits nothing”. The first line prevents a wrong row; the second prevents a wrong entity.

  4. 10.4 — Build a group and measure the 0.99×. Lesson 5.7 measured that two pools sorted to agree on dense order let a query skip the sparse read entirely. Implement registry::group<A, B>(), which maintains that ordering on insert and erase, and a group_view that walks both dense arrays by index with no lookups. Benchmark it against the ordinary view with engine/core/bench.hpp at 100, 10,000 and 100,000 entities, obeying all four of the measurement rules — alternate the arms, report median and spread, stop the optimiser deleting the work, and check both arms computed the same answer.

    Hint

    Maintaining a group is a swap: when an entity joins the group, swap its row in each pool down to a boundary index, and keep a count of how many rows are “grouped”. Both pools' sparse entries need patching, twice each.

    Solution sketch

    Expect three regimes and be suspicious if you do not get them: no measurable difference below a thousand entities (the working set is in cache and the redirect is free); a growing win above that; and a cost on every insert/erase of a grouped type that you must measure too, or you have benchmarked half the trade. That last number is the one that decides whether a group is worth it, and it is the one this lesson declined to pay in advance.

  5. 10.5 — What does a 16-bit entity buy, and what does it cost? Change the id to 16 bits — say 12 index, 4 generation — and work out, without running anything: the maximum live entities, the number of frees before a slot's generation repeats, and the memory saved on a 10,000-entity world with ten component types. Then decide whether any real game could use it, and say which of the three numbers rules it out.

    Solution sketch

    4,096 live entities; 15 frees before a repeat; and the saving is 2 bytes per sparse entry per component type — 10 × 10,000 × 2 = 200 KB, except that the world cannot hold 10,000 entities in the first place. The killer is the generation: fifteen reuses is about a quarter of a second of one recycled slot at 60 Hz, so stale ids would resolve routinely. This is the same arithmetic core/handle.hpp does for 12 bits, run at a scale where the answer flips — which is the point of the exercise.

11Recap & Next

The engine now has an ECS, and it is about four hundred lines of logic under a great deal of commentary. What it gained, concretely:

  • One id space. engine::ecs::entity is minted by one allocator and honoured by every pool, which is the single thing Lesson 5.4's pool<T> could not offer — not because it was badly built, but because each of its pools mints its own keys and two sevens from two pools mean nothing to each other.
  • O(1) structural change that does not scale with the world's complexity. Adding a component touches one pool and writes three values. It costs the same whether the entity has two other components or twelve, which is the property Lesson 5.7 measured at 4.2 ns and made the deciding argument.
  • Queries that lead with the smallest pool. Rule 3, five lines in a constructor, worth a fifth of the walk on the harness's own 60/30/12 world and more as the component gets rarer.
  • Composition. Four kinds of entity in the demo, distinguished by nothing but which of six component types they carry, with no enum, no flags and no branch in the renderer. Twenty-four of them are invisible because they lack a component, not because anything hid them.
  • Staleness that survives reuse. A destroyed entity fails every lookup in every pool, and a vector of destroyed ids is safe to keep and skip — which the demo does, on purpose, in ordinary code.

And what it did not gain, said plainly: any speed at all. The demo is 121 entities; Lesson 5.6 measured that layout is worth nothing below a thousand. Nothing renders through the ECS, the reference shot is byte-identical for the eighth lesson running, and the render system copies through a scene_object bridge that Module 6 will delete.

Next: 5.9 — Transform Hierarchy and the Camera System. Every placement in this lesson is in world space, which is fine for a swarm orbiting an origin and useless the moment a turret needs to sit on a tank. A hierarchy on top of an ECS is a genuinely interesting problem — the parent link is a component, but the order in which transforms must be resolved is a property of the graph rather than of any pool's dense order, and the two want different things. That tension, and what it costs to resolve it once per frame instead of once per query, is the next lesson — along with the observation that a camera, once there is an ECS, stops being a special object and becomes an entity with a component like everything else.

  • Michele Caini, “ECS back and forth” — a series that walks from a naïve component array to sparse sets to groups, with the reasoning kept visible. Parts 1–3 cover exactly this lesson's ground.
