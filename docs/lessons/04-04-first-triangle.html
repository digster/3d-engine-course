Module 4 — To the GPU: SDL_GPU · Lesson 4.4

The First Triangle

Three vertices, one pipeline object, one draw call — and the first pixel in this course whose colour was computed by hardware rather than by code you wrote. It is more machinery than you expect, every piece of it earns its place, and at the end we check the result against your own rasterizer, pixel by pixel.

1The Problem

In Lesson 2.2 you drew your first triangle. Here is the entire call:

One function, five arguments, and the pixels appear. You have three GPU objects now — a device, four shaders, a way to get bytes onto the hardware — so the corresponding call ought to be about as short. It is not. There is no SDL_DrawTriangle, and the call that does exist cannot be made yet:

Read it for what is missing. No vertices. No colours. No shader. No target. Four integers and a render pass, and every one of those integers is an index into something the call does not mention.

The gap

fill_triangle takes its arguments at the call. A GPU draw call takes almost none of them: everything it needs was bound beforehand — the geometry to a slot, the shaders and all the render state to a pipeline object, the output to a render pass. The draw call says only "three vertices, once, from the start", and the answer to "which three, drawn how, into what" is state you set up earlier.

So the work of this lesson is not the draw. It is assembling everything the draw refuses to ask for, and doing it in an order where each piece is legal.

That is genuinely more code than a beginner expects, and it is the reason "my first triangle" is a rite of passage in every modern graphics API rather than a five-minute exercise. It also has a second, quieter difficulty. Lesson 4.3 established that SDL checks a shader's entry point and not its resource counts; this lesson finds the same temperament in pipeline creation, where most wrong descriptions are accepted without complaint and the triangle simply does not appear.

And there is a debt to settle. Lesson 4.3 measured SDL_CreateGPUShader at eight microseconds, observed that this cannot possibly include compiling a shader, and wrote down a prediction about where the compile really happens. §4.4 of this lesson answers it — and the answer comes with a second finding that nearly went into print as a fact.

2Building Intuition

2.1Why so much machinery for one triangle

Count what fill_triangle actually needed, by the end of Module 3. It took a framebuffer, three vertices and a fill_style — and that fill_style had grown to ten fields: interpolation mode, shading mode, blend space, cull mode, a light, a material, a specular model, an eye position, a texture binding, an encode mode.

Lesson 4.1 counted those ten against SDL_GPUGraphicsPipelineCreateInfo's nine and observed that they are the same object. This lesson is where that observation becomes a call. The machinery is not new; it is your own fill_style, plus the two things a second processor forces you to make explicit: where the geometry lives, and what the output looks like.

So the honest way to read this lesson's code is as a translation. Everything in it existed in Module 3, in a form you wrote:

2.2The pipeline is the missing argument list

Here is the shortest way to think about a pipeline object, and it survives contact with the details: it is the argument list of fill_triangle, hoisted out of the call and frozen.

Our fill took its style per call, so it could change per triangle — and Lesson 3.8 used exactly that, rebinding a material per triangle, while noting in the code that a GPU cannot do this. Now you can see why not. The state is not a parameter the hardware reads; it is compiled into the machine code that runs. Changing it means a different program, which means a different pipeline object.

Lesson 4.1 measured the usual justification for that design — that baking state in spares the inner loop a branch — and found it false: hoisting our own per-pixel branch on draw-constant state measured 0.93×, which is nothing. The real reason was validation and compilation, and this lesson is where you can finally watch that happen, with a stopwatch.

2.3A struct full of pointers

One practical hazard, worth meeting before it costs you an afternoon. SDL_GPUGraphicsPipelineCreateInfo does not contain its vertex layout; it points at it:

Three of the create-info's fields are arrays reached through pointers — the buffer descriptions, the attributes, and the colour target descriptions. Which means the obvious helper function is a bug:

The compiler says nothing. The returned struct is a set of perfectly valid-looking fields and a pointer into a dead stack frame, and what happens next depends on what the next function call happened to write there. That is why this lesson's pipeline_desc is a class rather than a function: it owns the arrays, so the pointers live exactly as long as the description does.

C++ in place — returning a struct that points at yourself

This is the same hazard as returning a std::string_view of a local std::string, or a std::span of a local array, and it is worth recognising as a shape rather than as three separate rules: a type that holds a non-owning reference must not outlive what it refers to, and returning it by value is the easiest way to make it try.

C++ gives you no help here. The fix is to make ownership explicit — put the arrays and the struct that points at them in one object, so they have one lifetime. Our mesh_data/mesh pair from Lesson 3.5 solved the same problem the same way.

3The Theory

3.1Nine fields, and what each decides

Figure 1 is the whole create-info. Nine fields at the top level and fifty-three once the nested state structs are expanded — which is the count Lesson 4.1 arrived at from the other direction, by asking what fill_style would have to become.

Three of them deserve attention now, because they are the three that produce silence rather than errors when they are wrong.

The rasterizer state holds the cull mode and the winding, and every enum in it has its first enumerator at zero. So a zero-initialised rasterizer state means "counter- clockwise is front-facing, cull nothing" — which is why a forgotten cull_mode shows up as no culling at all rather than as a mistake. We set all three explicitly, every time, and §3.3 measures what happens when the winding disagrees with them.

The target format is not a choice. It must equal the format of the texture the pipeline will render into, and for the swapchain that is negotiated between the display, the compositor and the driver — which is why Lesson 4.2 asked for it and logged it. Note that our pipeline_desc takes it from the device rather than accepting it as a parameter: a value that must match something is better read from that something than passed in by a caller who might be guessing.

The vertex input state is the subject of §3.2, and of the whole of Lesson 4.5.

Now the more interesting question: which of these does SDL check? The bottom of Figure 1 is four creation attempts, and the answer is one of them.

One mistake that is worse than an error

Two of these trials are missing from the harness, and the reason is worth knowing. Swapping the two shaders between slots is not caught either — but it does not fail politely. A vertex shader in the fragment slot is refused with a Metal error about an interrupted compiler connection, after which the next pipeline creation in that process crashed; and a fragment shader in the vertex slot segfaults immediately.

Both were reproduced three times in an isolated one-trial program before being written down. SDL_GPU does not validate which stage a shader was compiled for, so keep the two straight yourself — the type system will not, because both are SDL_GPUShader*.

3.2The layout, and the contract nothing checks

The GPU receives a block of bytes and a shader that declares typed inputs. Something has to say which bytes are which, and that is the vertex input state: a pitch per buffer, and an attribute per shader input.

Worked example — our vertex, byte by byte

The struct is seven floats:

  • sizeof(gpu_vertex) = 7 × 4 = 28 bytes, and that is the pitch: the distance from one vertex to the next.
  • x sits at offset 0, is three floats, and feeds shader input location 0 — which is TEXCOORD0, which is position in triangle.vert.hlsl.
  • r sits at offset 12 (three floats in), is four floats, and feeds location 1 — TEXCOORD1, colour.

Which is exactly what the description says, with offsetof doing the arithmetic so that inserting a field later cannot silently invalidate a hand-written 12:

Now notice what has just happened. The same vertex is declared in two places, in two languages, and nothing checks that they agree. The HLSL says float3 position : TEXCOORD0; float4 colour : TEXCOORD1;. The C++ says 28 bytes, FLOAT3 at 0, FLOAT4 at 12. If those descriptions drift apart — a field inserted, a semantic renumbered, a float3 that became a float4 — you get geometry that is wrong rather than absent, which is much harder to diagnose.

Lesson 4.3's reflection file already knows the shader's half of this contract; its inputs array lists every location with its type. Exercise 4.4.4 uses it to check the C++ half against it at startup, which is the sort of assertion that turns a mystery into a line number.

4Implementation

4.1Describing the pipeline

pipeline_desc's constructor fills in every field with the course's conventions, so that the parts a caller varies are the parts a caller thinks about. Two of those defaults are load-bearing:

The arrays are pointed at in the constructor rather than in a later build step, so the create-info is coherent at every moment rather than only after someone remembers to call something. And info() returns a const reference — handing out a copy would hand out §2.3's bug in a box.

4.2Three vertices on the device

gpu_buffer is the smallest thing that can hold geometry, and its upload is the path Lesson 4.2 built for textures with the destination changed: CPU memory → transfer buffer → device buffer, the first hop now and the second recorded. Two details are worth pausing on.

Lesson 4.2 §3.2 introduced cycling as the answer to "am I overwriting something the GPU has not read yet?" — and the answer here is no, because nothing has read it at all. Cycling is not a good-luck charm; it costs memory, and passing true reflexively means every static mesh in your engine quietly exists twice.

That one looks wrong the first time you read it and is not. The staging buffer is released while a pending command buffer still references it, which in any ordinary API would be a use-after-free — and here it is the documented contract, because "release" in an API where work is deferred means "stop wanting this", not "free this now".

4.3The draw, in the frame

The probe's frame already cleared the swapchain and blitted the software rasterizer's picture onto it. The triangle goes on top, in a second render pass:

A second pass rather than the first one, because the blit must happen outside a pass and we want the triangle over it — so the order is clear, blit, then load-and-draw. The LOADOP_LOAD is the whole reason both pictures share a window; Lesson 4.2 §4.5 noted that LOAD costs more than CLEAR on tiled hardware, and this is the case where you pay it deliberately.

Note the binding order too: pipeline first, then vertex buffers, then the draw. The pipeline describes what a vertex is, so binding a buffer before there is a description of how to read it is not a thing the API lets you express.

4.4Where the compile was hiding

Now the debt. Lesson 4.3 measured SDL_CreateGPUShader at eight microseconds, said plainly that this could not include compiling anything, and predicted that the compile happens at pipeline creation because only there does the driver know the target format, the blend state and the vertex layout the machine code must be specialised to.

Confirmed, and Figure 2 is the answer — though getting to a version of that figure worth printing took three attempts, and the two wrong ones are the more useful lesson.

Creating a shader costs 0.031 ms, and does so in every run, in every configuration, on every attempt. Creating a pipeline never costs that little. Somewhere between those two calls, milliseconds appear — which is where the compile is, and that is the prediction settled.

How many milliseconds is a more interesting question than it looks:

Two wrong versions of this section, and what confounded both

The first draft timed one pipeline, then timed the same description again, and called the difference the compile. The second compared a release run against a debug = true run — 0.5 ms against 33.5 — and concluded that the validation layer costs sixty-six times the compile it checks. That claim was written out in full, with a figure, before it was tested.

Both were the same confound: Metal caches compiled pipelines on disk. The "second" measurement of anything is a cache hit, and the 33.5 ms release-versus-debug gap was not validation at all — it was that the debug run happened to be the first time those shaders had ever been compiled on this machine. Measured properly, with the same permutation freshly generated in both configurations, validation costs almost nothing: 31.8 ms against 34.5 for a first pipeline, and ~2.5 against ~2.4 for each one after.

What caught it was running the engine again the next day and seeing 0.077 ms where the log had said 42. A number that changes by five hundred times between runs of an unchanged binary is not a property of the call; it is a property of what happened before it. This is Lesson 3.10's rule about comparing numbers taken hours apart, and 4.2's about checking that a number can be true, arriving together — and the reason the harness now varies its blend state with a run-unique seed is to make "new" mean new.

Two consequences survive all that, and they are what an engine actually needs. Build every pipeline you will need at load time — 2.4 ms of compilation is fifteen percent of a 60 Hz frame, and the first one in the process is thirty. And state permutations are compilations: a material system with five booleans is thirty-two pipelines, which is about eighty milliseconds of startup on this machine and rather more on a phone. That is why shipped engines cache compiled pipelines to disk themselves, and why "shader compilation stutter" is a phrase you will meet in patch notes.

4.5Checking it in pixels

A triangle on screen is not evidence. A window cannot be asked what it contains, screenshots are unavailable on a machine without screen-recording permission, and "it looks right" has never once caught an interpolation bug. So the harness draws the same triangle into an offscreen texture and downloads it — which Lesson 4.2's readback path already made possible, and which Lesson 4.3's windowless device made convenient.

Figure 3 is what came back. Two numbers in it are worth dwelling on.

Worked example — is that the right number of pixels?

The triangle spans x ∈ [−0.8, 0.8] and y ∈ [−0.8, 0.8] in clip space, drawn into a 256×256 target. Clip space is two units wide, so one clip unit is 128 pixels:

  • base = 1.6 × 128 = 204.8 pixels
  • height = 1.6 × 128 = 204.8 pixels
  • area = ½ × 204.8 × 204.8 = 20,972 pixels

Measured: 20,808. The ratio is 0.9922 — short by 164 pixels, or 0.8%, which is about what you would expect from a boundary roughly 600 pixels long being resolved one way rather than the other. The hardware filled the triangle the geometry describes, and now you know that rather than believing it.

Worked example — the centroid, and Lesson 2.4

The centroid of a triangle is the average of its vertices, and its barycentric coordinates are (⅓, ⅓, ⅓) by definition. With corners of pure red, green and blue, the colour there must be one third of each:

  • predicted: 255 × ⅓ = 85 in every channel
  • measured: 85, 86, 85

That is Lesson 2.4's interpolation — the one you derived from signed areas and implemented by hand — performed by silicon, agreeing to one code out of 255. The single unit of difference is the pixel centre not landing exactly on the geometric centroid.

This is the most satisfying check in the module. You did not learn a new kind of interpolation to use a GPU; you learned the same one, and the hardware happens to do it faster.

The third check is winding, and it is the one that will save you an evening:

Figure 4 is the answer, and it is blunter than expected. Swapping two vertices does not flip the triangle, or darken it, or turn it inside out. It deletes it — 20,808 pixels become 0. And the third panel is what makes that a diagnosis rather than a guess: with cull_mode set to NONE, the same "wrong" vertices produce exactly 20,808 pixels again, identical to the first panel. The geometry was never the problem.

That gives you a two-minute test for the most common first-triangle failure there is. If your triangle is missing, set the cull mode to NONE. If it appears, your winding disagrees with your front_face; if it does not, look elsewhere — at the pipeline's target format, at whether the buffer was uploaded, at whether the draw is inside the pass.

4.6Against your own rasterizer

And now the comparison this module has been heading towards since Lesson 2.2. The same three vertices, carried through the same viewport transform, filled by fill_triangle — your code, from Module 2 — and by the hardware, and compared pixel for pixel:

Figure 5 is drawn from the actual comparison rather than from an idea of what a fill rule looks like, and it shows exactly where those 102 pixels are: single squares along one edge, one per row, never two together, never anywhere but the boundary.

That pattern is a fill rule. Every rasterizer has to decide what happens when a pixel centre lands exactly on an edge — include it, exclude it, or include it only on some edges — because a pixel shared between two triangles must be drawn exactly once or the seam shows. Hardware uses a "top-left" rule; our fill_triangle uses the >= 0 test that Lesson 2.2 wrote, which includes every boundary pixel. On a lone triangle that difference is 102 pixels; on two triangles sharing an edge it is a visible seam, and it is why Lesson 2.2's edge function had that comparison written the way it was.

What this comparison actually establishes

Zero interior disagreements over twenty thousand pixels means your rasterizer and a twenty-core GPU are computing the same triangle. Not approximately — identically, everywhere except a boundary convention that both are entitled to choose.

That is the strongest possible answer to the question Module 2 opened with. You did not write a toy version of a rasterizer; you wrote a rasterizer, and the difference between it and the hardware is a documented tie-breaking rule and about eight orders of magnitude of throughput.

Finally, the composition — because the window shows both pictures at once and that claim deserves the same treatment as the others:

Figure 6 is the engine's own frame, rebuilt offscreen and counted: 22,364 pixels of clear, 22,364 of the software rasterizer's picture, 20,808 of triangle, and the three sum to 65,536, which is 256² exactly. Every pixel in the window is attributable to exactly one of the three operations that produced it.

7Common Pitfalls & Debugging

The triangle is not there, and nothing errored

Symptom. Everything created successfully, the frame completes, and the screen shows no triangle.

Cause. Most often winding: your vertices are clockwise on screen and the pipeline says counter-clockwise is front-facing with back faces culled. §4.5 measured that this is not a subtle effect — it is 20,808 pixels becoming 0.

Fix. Set cull_mode = SDL_GPU_CULLMODE_NONE and run again. If it appears, reverse two vertices (or change front_face) and put the culling back — you want it on, and Lesson 3.4 explains why. If it does not appear, the cause is elsewhere: check that the buffer was uploaded and submitted before the draw, that the draw is inside a render pass, and that the vertices are actually in clip space.

Wildly wrong geometry, or triangles stretching to infinity

Symptom. Something is drawn, but it is nothing like the shape you described — often a smear reaching off-screen.

Cause. The vertex layout and the actual struct disagree. A wrong pitch makes the hardware walk the buffer at the wrong rate, so each vertex is read from the middle of two others; a wrong offset feeds colour bytes into a position.

Fix. Use sizeof and offsetof, never literals — §3.2. And remember that nothing checks this contract: the shader declares its inputs in HLSL, the pipeline describes bytes in C++, and the two are only joined by your care. Exercise 4.4.4 automates the check.

SDL_CreateGPUGraphicsPipeline fails, mentioning the vertex descriptor

Symptom. "Vertex function has input attributes but no vertex descriptor was set."

Cause. The pipeline has no vertex_input_state, but the vertex shader declares inputs. This is one of the few mistakes creation actually catches — and the message is exact.

Fix. Describe at least one vertex buffer and the attributes the shader expects. If you genuinely want a shader with no vertex inputs, the technique is to generate positions from SV_VertexID — common for full-screen passes, and Module 6 uses it.

The process crashes inside pipeline creation

Symptom. A segfault with no SDL error, or a Metal message about an interrupted compiler connection followed by a crash on the next creation.

Cause. A shader in the wrong slot. Both are SDL_GPUShader*, so the type system cannot help, and SDL does not check which stage a shader was compiled for.

Fix. Keep the two straight at the point of construction — pipeline_desc's constructor takes them in the order (vertex, fragment) and nothing else in the codebase touches those fields. If you are already crashing, this is the first thing to check, because it produces no useful diagnostic at all.

A pipeline that "works" but renders into nothing

Symptom. Creation succeeds, the draw is recorded, and the target is unchanged — or the colours are wrong in a way that suggests a different format.

Cause. The pipeline's colour target format does not match the texture the render pass is writing. §3.1 measured that this is not refused at creation on this backend, and the frame even completed.

Fix. Take the format from the thing you will render into, never from memory — pipeline_desc reads it from the device's report, and colour_target_format() exists for offscreen targets. Other backends are stricter than Metal here, so a program that works on one may fail loudly on another; that is a reason to be careful, not a reason to relax.

Pipeline creation is alarmingly slow

Symptom. Creating a pipeline takes tens of milliseconds, and creating several makes startup visibly stutter.

Cause. Compilation, and where you are in the driver's cache. §4.4 measured ~32 ms for the first pipeline in a process, ~2.4 ms for each new state permutation, and under a millisecond for anything already compiled — including in a previous run, because the cache is on disk.

Fix. Create every pipeline at load time, never on demand mid-frame. And do not conclude anything from a single measurement of this call: it was the source of two wrong claims in a draft of this lesson, both caused by comparing a cold cache with a warm one.

The create-info's arrays are garbage by the time SDL reads them

Symptom. Intermittent nonsense: creation fails with an incoherent message, or succeeds and draws something impossible. Behaves differently in debug and release.

Cause. §2.3 — a helper that built an SDL_GPUGraphicsPipelineCreateInfo and returned it by value, leaving its pointers aimed at a dead stack frame.

Fix. Keep the arrays and the struct that points at them in one object with one lifetime, as pipeline_desc does. The general shape — a non-owning view outliving what it views — is worth recognising: it is the same bug as a dangling string_view.

8Exercises

4.4.1 — Break the winding, then diagnose it

Swap two vertices in k_triangle and run. Before changing anything else, use only the pipeline's cull_mode to prove what went wrong, then fix it properly. Write down the two-step test you used; it is the one you will reach for every time a mesh is invisible for the rest of this course.

Hint

The measurement in §4.5 is the test: NONE brings it back identically, which rules out geometry, transforms, buffers and formats in one step.

Solution sketch

Setting CULLMODE_NONE makes the triangle reappear unchanged, so nothing about the geometry is wrong and the disagreement is between the winding and front_face. The proper fix is to reorder the vertices rather than to change front_face: the convention is course-wide (conventions §7), and flipping it for one mesh means every other mesh is now wrong.

4.4.2 — Find the fill rule

§4.6 found 102 pixels our rasterizer covers and the hardware does not, all on the boundary. Work out the rule. Modify fill_triangle's edge test to exclude pixels on some edges rather than including all of them, and see how close you can get the disagreement to zero — then draw two triangles sharing an edge and check that neither seams nor double-draws.

Hint

Look up the "top-left rule". The question a fill rule answers is not "is this pixel on the edge?" but "which of the two triangles sharing this edge owns it?", and the answer has to be decidable from one triangle at a time.

Solution sketch

The standard rule includes a boundary pixel when the edge it lies on is a top edge or a left edge, which is a property of the edge's direction and so can be decided without knowing the neighbour. Implementing it exactly will not reach zero disagreement, because sub-pixel precision differs too (our vertices are integers; hardware rasterizes at roughly 1/256 of a pixel, as conventions §7f notes). Getting from 102 to single digits is a good result, and the two-triangle test is the one that matters.

4.4.3 — Draw a second triangle without touching the pipeline

Add three more vertices to the buffer and draw six. Then draw the two triangles as separate draw calls from the same buffer, using first_vertex. Which approach would you use for a scene of a thousand objects, and why?

Hint

Count the state changes. What does the second draw call cost that the extra three vertices did not? Lesson 4.1's note that "binding a pipeline is relatively cheap, but doing it hundreds of times when you don't need to will slow performance significantly" comes from SDL's own performance notes.

Solution sketch

One draw of six vertices is strictly cheaper than two draws of three: same bytes, same pipeline, one command instead of two. That generalises into the single most important renderer optimisation there is — batch — and it is why Module 6 sorts draws by material and Module 8 measures what that saves. The counter-argument is that objects need different transforms, which is what Lesson 4.6's uniforms and instancing exist to solve.

4.4.4 — Check the layout against the shader, automatically

§3.2 pointed out that the vertex layout is declared twice, in two languages, with nothing checking that the halves agree. Lesson 4.3's reflection JSON contains the shader's half in its inputs array. Extend parse_shader_reflection to read it, and assert at startup that every attribute in the pipeline description matches the shader's location and type.

Hint

The reflection gives {"name": "input.position", "type": "float3", "location": 0}. Map SDL_GPU_VERTEXELEMENTFORMAT_FLOAT3 to "float3" and compare. Decide deliberately what to do on mismatch — Lesson 4.3 refused to load rather than guessing, for reasons that apply here too.

Solution sketch

The check costs a few dozen lines and turns "my mesh renders inside out" into a startup message naming the attribute. It is also the first piece of a material system: once the program can read what a shader needs and verify what it is given, binding resources by name rather than by number becomes possible, which is where Module 6 goes.

4.4.5 — Make the pipeline expensive

§4.4 measured ~2.4 ms per new state permutation. Find out what that number depends on: time it for a trivial shader and for a deliberately heavy one (unroll a long loop, add a hundred lines of arithmetic), and time creating ten pipelines that differ only in cull_mode. Then run the whole experiment a second time and see which numbers changed.

Hint

Take minimums, warm up first, and control for the caching §4.4 found — ten pipelines that differ in one field are ten different compilations or one cached one, and which it is, is the experiment. Remember the cache is on disk: your second run is not a fresh start.

Solution sketch

You should find creation cost tracking shader complexity, which is the direct evidence that the compile is here. The ten-variants case is the more useful result for an engine: if state permutations each cost a compile, a material system with five booleans has thirty-two pipelines to build at load time, and that is a real startup budget to plan for — the reason shipped engines cache compiled pipelines to disk.

9Recap & Next

What the engine gained

  • A pipeline object, with the course's conventions filled in once — CCW-front, cull-back, and a colour format read from the device rather than remembered.
  • Geometry on the device, uploaded through a staging buffer that is released while the copy it feeds is still only recorded.
  • A draw call, and with it the first pixel in this course whose colour was computed by hardware.
  • A lifetime holder for a struct full of pointers, which is a small class preventing a bug that produces no diagnostic at all.

Two results are worth carrying. The compile happens at pipeline creation — predicted in 4.3, confirmed here at roughly eighty times the cost of creating a shader, with a disk cache behind it that outlives the process. And the alarming numbers this call can produce are almost never what they look like — two separate wrong conclusions were drawn from them in drafts of this lesson, both from comparing a cold cache with a warm one, and both caught only by repeating the measurement.

But the result to keep is the comparison. Your rasterizer and a twenty-core GPU, given the same three vertices, agree about every single interior pixel — twenty thousand of them — and differ only on 102 boundary pixels where each is entitled to its own tie-breaking rule. Module 2 was not a simplified rehearsal for this. It was the same computation.

What we cannot do yet is move anything. triangle.vert applies no matrix, because there is nowhere to put one: a matrix would have to arrive as a uniform, and uniforms need the register spaces Lesson 4.3 set up and the binding calls we have not met. Nor can we draw a mesh — three vertices are a special case that hides every interesting question about how vertices are stored, shared and indexed.
