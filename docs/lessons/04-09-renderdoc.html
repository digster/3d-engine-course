Module 4 — To the GPU: SDL_GPU · Lesson 4.9

Debugging a Frame with RenderDoc

The screen is black. Every call returned success, every pointer is non-null, and the debugger you learned in Lesson 0.6 has nothing to tell you — because the work has not happened yet, and when it does it will happen on another processor. This lesson is about the tool that can see it, about making your frame legible enough to be worth capturing, and about the honest boundary between what a tool shows you and what you have to already know.

1The Problem

Here is a bug you are going to have. The window is black. Or one object is missing. Or everything is lit from the wrong side, or the texture is a smear, or the depth test seems not to be happening. You did not change much. You reach for the tool that has solved every problem in this course so far — the debugger from Lesson 0.6 — and you set a breakpoint on the draw call.

It hits. pass is non-null. item.mesh is non-null. The index count is 60, which is right. Step over it. No error. SDL_GetError() is empty. Submit returns true. The window is still black.

This is not a hard bug you are handling badly. It is a bug that the tool you are using cannot see, and the reason was stated in Lesson 4.2 and has been true of every line of GPU code you have written since:

Nothing below this line executes when it is written.

Every SDL_GPU call you make appends to a list. The list runs later, on another processor, after a submit, in an order and a timeframe you do not control. A breakpoint stops the recording. By the time the picture is wrong, the recording finished long ago and the stack that produced it is gone.

So this lesson is about the class of tool that can see it, and about a thing people skip: a capture of an uninstrumented frame is a list of two hundred numbered events referring to Buffer 47 and Texture 12, and you will spend your debugging time working out which is which rather than what is wrong. Making a frame legible is engine work, it is cheap, and it is what most of this lesson's code does.

Why this lesson is here and not at 4.4

A frame debugger shows you everything, which is useless if you do not know what you expect to see. Open a capture with no idea what a vertex buffer's contents should look like and it is a wall of hexadecimal.

You are not in that position. You know this frame has three draws, one pipeline bind, 560 bytes of uniform pushes, a depth attachment and a blit, because Lesson 4.8 printed those numbers. You know what is in the vertex buffer, because you wrote gpu_vertex_pnu and the interleaver. You know what the matrices should be. Every object in the capture is one you created and — as of this lesson — named.

You are checking a tool against a frame you already understand, which is the only way to learn to trust one.

2Building Intuition

2.1The submit is a wall

Four lanes, one timeline. Your code records; the command buffer holds; the GPU executes; the display shows. A debugger operates entirely in the top lane. The bug manifests in the third and is observed in the fourth, and between them is a submit that your breakpoint cannot follow.

Notice what this means for the kinds of bug you now have. In Modules 1 to 3, a wrong picture was a wrong number in a function you could step into. Here the wrong picture is usually one of:

  • a resource that was never bound (and binding nothing at a declared slot is silent);
  • a resource bound with the wrong contents, uploaded correctly to the wrong place;
  • pipeline state that does not match what the pass expects;
  • a matrix that is right in C++ and arrives transposed, or at the wrong offset;
  • geometry that is correct and entirely outside the frustum.

Every one of those is a state question rather than a control-flow question, and a debugger is a control-flow instrument. What you want is something that can answer "what was bound at event 47, and what was in it".

2.2Record, then replay

Here is the trick that makes a frame debugger possible, and it is worth understanding because it explains both the tool's power and its limits.

The tool inserts itself between your program and the graphics driver. During a captured frame it records every call and every byte of every resource — not the results, the inputs: the full contents of each buffer and texture at the moment the frame began, plus the ordered list of calls that followed. That is a complete, self-contained description of the frame.

Which means the tool can replay it. Want to know what the depth buffer looked like after the second draw? It re-executes the frame from the start, stops after the second draw, and shows you. Want the framebuffer before and after one triangle? Same mechanism. Want to know which pipeline was bound at event 47? Replay to 47 and read the state.

That is why a capture can answer questions your own logging never will: it does not describe the frame, it can re-run it. And it is also exactly why the capture is large, why capturing is slow, and why the tool needs to sit underneath your program at the driver level — which is the constraint that decides, in §3.1, whether the tool exists for you at all.

2.3A capture is only as good as your names

Everything above is true of an uninstrumented program too. The difference between a capture you can use and one you cannot is almost entirely whether the things in it have names.

3The Theory

3.1Which tool is yours, and why it is not your choice

The awkward fact first, because burying it would waste your time. RenderDoc does not support Metal. Its own front page says what it does support:

"…a graphics debugger currently available for Vulkan, D3D11, D3D12, OpenGL, and OpenGL ES development on Windows, Linux, Android, and Nintendo Switch."

SDL_GPU chooses its backend from what the platform offers: Vulkan or D3D12 on Windows, Vulkan on Linux, Metal on macOS. So on a Mac the lesson's title names a tool you cannot run, and the tool you can run is Xcode's Metal Debugger. This is not a temporary gap to wait out; RenderDoc's author has been clear for years that Metal support is not planned.

SDL says the same thing, in the header on your disk. SDL_gpu.h has a Debugging section — worth reading in full, it is a page long — that begins:

"For debugging such cases, there are tools that allow visually inspecting the whole GPU frame, every drawcall, every bound resource, memory buffers, etc. They are the following, per platform: For Windows/Linux, use RenderDoc. For MacOS (Metal), use Xcode built-in debugger…"

Every concept in this lesson transfers exactly. Both tools have an event browser, a texture viewer, a pipeline-state panel and a mesh viewer; both replay to an event; both show you the bytes of a uniform push. What differs is the menus and the screenshots. §5 walks through both.

And the third one

PIX is Microsoft's, D3D12-only, and worth knowing about for one reason: it is considerably better than RenderDoc at GPU timing — where the time in a frame actually went, per draw, on the hardware. RenderDoc is the better state inspector; PIX is the better profiler. Module 8's profiling lessons come back to that distinction.

3.2The frame you already understand

This is the frame, printed by the engine itself — engine --trace, which §4.4 builds. Read it before you ever open a tool, because it is what the tool is going to show you and you can check it against what you know.

Four groups, because §4.2 puts one around each phase. One render pass with a depth attachment. Two per-frame uniform pushes of 64 bytes each. Then, three times: two per-draw pushes (112 and 32 bytes), a vertex buffer, an index buffer, and a draw. Thirty-three events, three draws, 560 bytes.

Every one of those numbers was in Lesson 4.8's log. 128 bytes per frame plus 144 per draw times three is 560; three objects is three draws; one pipeline bind because all three objects are solids. Nothing here is new information — and that is the point. When you open a capture in §5 and see thirty-three events, you will know immediately whether the tool is showing you the frame you think you wrote.

3.3The naming API SDL tells you not to use

SDL offers two ways to name a buffer or a texture, and this course used the wrong one for six lessons. The story is worth telling because the mistake has a shape you will make again.

The two ways:

Lesson 4.2 found the setter first, used it, and Lesson 4.3 — which had to name a shader, and discovered that shaders have only the property — wrote a comment explaining the asymmetry:

"note the asymmetry: buffers and textures have SDL_SetGPUBufferName / SDL_SetGPUTextureName, and a SHADER DOES NOT. It is named through a creation property instead, because a shader is immutable the moment it exists — there is no later at which to set anything on it."

That is a tidy, plausible, confidently-reasoned explanation, and it is wrong. Here is the documentation of the function that comment was reasoning about, four lines above the declaration it had already read:

"You should use SDL_PROP_GPU_BUFFER_CREATE_NAME_STRING with SDL_CreateGPUBuffer instead of this function to avoid thread safety issues."

"This function is not thread safe, you must make sure the buffer is not simultaneously used by any other thread."

There was no asymmetry to explain. The creation property is the recommended path for all three resource types; the setters are simply the older API, kept working and steered away from. A shader never got the worse option, which is not a consolation prize — it is the absence of a mistake.

The shape of the error, which is the transferable part

The comment was written by somebody who had just read SDL_CreateGPUShader's documentation carefully and had not read SDL_SetGPUBufferName's at all. They observed a difference between two APIs and inferred a reason, and the inference was internally consistent, memorable, and false.

A confident explanation of why an API is shaped the way it is, is a hypothesis. The cheapest place to test it is the documentation of the function you are already calling. Note also that the wrong explanation survived four lessons and a code listing appearing in full on a published page — because it was never load-bearing until this lesson made it so.

And a limitation of both APIs that is worth knowing before you go looking: there is no getter. No SDL_GetGPUBufferName exists. A name is write-only from the program's point of view — it is for the debugger and cannot be read back or asserted on. So verify_49 can prove the calls are accepted and cannot prove the names arrived; only a capture can, and that check is done by eye in §5.

3.4Debug groups, and the Metal rule

A name makes a resource legible. A debug group makes the frame legible: it turns a flat list of events into a tree with your own headings on it, which is the difference between navigating a capture and scrolling one.

Three calls, and one of them has a caveat that decides the API's shape:

The caveat, quoted:

"On some backends (e.g. Metal), pushing a debug group during a render/blit/compute pass will create a group that is scoped to the native pass rather than the command buffer. For best results, if you push a debug group during a pass, always pop it in the same pass."

So a group has a scope, and getting the scope wrong does not crash — it produces a capture whose tree is subtly wrong, at exactly the moment you least want to be debugging your debugging. That is an argument for expressing it as a C++ scope, which is what §4.2 does: an RAII type whose destructor pops. A block cannot be unbalanced, and a type that is neither copyable nor movable cannot be stashed somewhere it would outlive its pass.

Two portability notes worth knowing before you are surprised

On D3D12, all three of these functions require WinPixEventRuntime.dll to be in your PATH or next to your executable — SDL's header says so for each one. Without it they are inert, not broken: your groups silently do not appear. If you are on Windows with the D3D12 backend and your capture has no tree, that is the first thing to check.

And a group is a debugging construct with no rendering meaning whatsoever. It does not begin a pass, does not affect state, and does not synchronise anything. It is a label on a range of the command stream, and nothing more.

3.5What it costs, measured against its noise floor

Instrumentation that ships has to justify itself. Three costs, and the middle one pays off a promise src/main.cpp has carried since Lesson 4.2 — "the validation layer costs real time … Lesson 4.9 turns it off to measure".

Read the chart from the left. The first measurement is not any of the three costs: it is the noise floor, measured by running the identical workload five times and taking the spread of the medians. It comes out at 2.46 µs, and it is the thing every other number in this section has to beat before it counts as a result.

Why that step is not optional, and what happens without it

The first version of this measurement skipped it and compared one instrumented frame against one bare frame. The answer it produced was:

Adding work made the frame faster. That is not a surprising result about debug groups; it is the measurement telling you it has nothing to say. The effect is smaller than the machine's own variation, and any number you print there — positive or negative — is a fluctuation wearing four decimal places.

The fix is to make the effect bigger until it clears the floor. Push 1, 8, 32 and 128 groups per frame, changing nothing else, and divide:

So: about 183 ns per push-label-pop. The engine issues four groups a frame, which is 0.73 µs, which is 0.004% of a 16.7 ms frame. They ship on, in every build, and the decision took one measurement rather than an argument.

The validation layer

Recording one three-draw frame: 0.0267 ms with debug mode on, 0.0228 ms off — a ratio of 1.17×. Measured on the recording rather than the whole frame, on purpose: validation runs on the CPU as each call is recorded, so a whole-frame number would dilute it with GPU time the layer cannot affect.

Do not read 1.17× as "validation is cheap"

This scene has three draws. The layer's cost is per API call, so it scales with how chatty your frame is — a frame with two thousand draws pays roughly a thousand times what this one does, and there the ratio would not be 1.17.

The useful form of the finding is not a ratio at all: it is "validation costs about X per call, and I know how many calls I make". Which is a number you now have both halves of, because the frame log counts the calls.

Keep it on while developing regardless. Lesson 4.2's reasoning stands: the alternative to a validation message is a black window with no message at all, and that trade is not close.

Naming

Creating a 256-byte buffer: 0.0011 ms unnamed, 0.0018 ms named — 0.7 µs, paid once per resource, at load time, never per frame. There is no version of this trade worth taking the other way.

3.6The number this machine cannot measure

Lesson 4.5 introduced best_case_invocations() and worst_case_invocations() — 1,225 and 6,912 for our torus — and said, in a doc comment that is still there:

"Hardware lands somewhere between, nearer the bottom for well-ordered geometry, and Lesson 4.9's RenderDoc capture is where the real number finally shows up."

It does not show up here. This course is written on a Mac, SDL_GPU gives it Metal, RenderDoc does not capture Metal, and Metal's pipeline-statistics counters are not reachable through SDL_GPU. Writing a plausible number here would be the single worst thing this lesson could do, so instead: a model, with its assumptions stated, and the exact place to read the truth on hardware that will tell you.

The model is a post-transform vertex cache: hardware remembers the last N vertices it shaded, and an index that hits the cache costs no invocation. Simulate a FIFO cache of several sizes over the index order torus.obj actually ships with, and you get the staircase above — which is more interesting than the number would have been.

Why a staircase and not a slope

make_torus(48, 24) emits quads ring by ring: for i in major, for j in minor. So each quad shares two vertices with the quad next to it — a few index positions back, which any cache catches — and two with the quad one ring away, about 2 × 24 = 48 positions back. There is nothing reused at a distance between those two, so a cache of 8 and a cache of 32 catch exactly the same reuse: 2,400 invocations, both. Only at about 50 does the second kind start landing, and then it drops straight to 1,225.

Which surfaces the finding that is worth more than the original question. Vertex reuse is a property of the index ORDER, not only of the cache. The control makes it a measurement rather than a story: take the same 2,304 triangles, the same vertices, the same everything, and shuffle the order the triangles are listed in.

ordered, cache 32: 2,400 invocations · shuffled, cache 32: 6,784 — 2.83× worse, with nothing about the geometry changed.

That is why real pipelines run an index-buffer optimiser as a build step — Tom Forsyth's linear-speed vertex-cache optimiser, or meshoptimizer — and why a mesh exported straight out of a modelling tool is often leaving half its vertex throughput on the floor. Module 8's asset pipeline is where that becomes ours.

Everything this model assumes, each of which is a way it can be wrong

That the cache is FIFO (some hardware is LRU, some is neither); that it holds whole vertices (some hold post-transform outputs of a fixed size, so a fatter vertex means fewer entries); that indices are processed strictly in order (modern hardware batches them into primitive groups and may reorder within one); and that there is one cache (there are usually several, one per geometry unit).

Where to read the true number: in RenderDoc, the Pipeline State viewer's statistics, or a VK_QUERY_TYPE_PIPELINE_STATISTICS query for VERTEX_SHADER_INVOCATIONS. On D3D12, D3D12_QUERY_TYPE_PIPELINE_STATISTICS → VSInvocations. In Xcode, the Metal Debugger's per-pipeline counters. Exercise 4.9.5 is to run it and report how far off this table is — that number is worth more than the table.

3.7What a capture can do that a log cannot

§4.3 builds a frame log: 150 lines that print the command stream as a tree. It is worth being precise about why that is worth writing when the real tools exist, and equally precise about where it stops.

The top six rows are the case for writing it. It runs on every backend, including the one RenderDoc does not support. It runs in CI, where a GUI cannot — engine --trace is a headless frame dump you can diff between commits and fail a build on. And it can be cross-checked: verify_49 §D asserts that the log's draw count, uniform bytes and triangle count match draw_stats, which are two independent readings of the same frame.

That last one deserves a sentence, because it is the thing a capture genuinely cannot give you. A capture is a picture of what happened; it has no second, independent account of what should have happened to compare against. Two counters incremented from the same statements do — which is also why the log is recorded from inside render() rather than described from outside it. Instrumentation that can drift from the code it describes is worse than none, because it is believed.

The bottom six rows are why the tools exist and why this lesson is not "and therefore you do not need RenderDoc". Every one of them requires the frame to be replayed, and replaying needs the driver: the contents of a buffer at a given event, the framebuffer as it stood after one particular draw, which pipeline state was live, the compiled shader disassembled, per-draw GPU timing, stepping a single fragment through your shader. No amount of logging reaches any of that.

The log tells you what you asked the GPU to do. The capture tells you what the GPU had.

All of it lands in one new pair of files, src/gfx/gpu_debug.{hpp,cpp}, plus a correction applied across four existing ones.

What changed, across the engine

Every SDL_SetGPU*Name call is gone, replaced by the creation path — and the transfer buffers, which had never been named at all, got names for the first time. That last one matters more than it sounds: a load-time capture of this engine used to show four identical anonymous transfer buffers, and working out which upload was which is exactly the time a debugger is supposed to save you.

C++ — a doc comment is code that cannot be tested

Two comments in this codebase asserted the wrong reason for the naming asymmetry (§3.3) and survived four lessons, a full code listing on a published page, and several readings. They survived because nothing depends on a comment being right — there is no compiler, no test, and no reviewer whose job it is. gpu_shader.cpp's version is now rewritten to quote the wrong version first, which is the only form of correction that inoculates the reader.

The practical rule: be most suspicious of comments that explain why an API is shaped the way it is. Comments about what your own code does are checked constantly by people reading the code beside them. Comments about somebody else's design are checked by nobody.

4.2A group that is a scope

Deleting the move constructor is unusual in this engine — every resource type so far has been movable — and it is the §3.4 rule expressed in the type system. A movable group could be returned from a function, stored in a container, or handed across a pass boundary, and on Metal that produces a capture whose tree is quietly wrong. Making it immovable means the pop happens in the same block as the push, which on every backend is the safe case.

A null cb is legal and does nothing, so a caller never has to branch on whether it has a command buffer this frame — which is what lets verify_49 §C turn the groups off without a second code path to keep in sync with the first.

4.3The frame log

frame_log records the events a capture would show. Three decisions in it are worth defending, because they are what separate instrumentation that helps from instrumentation that lies.

A fixed name buffer, not a std::string. This is not premature optimisation: the log runs inside the frame it is measuring, and an allocation per event would make the thing being measured different from the thing that ships. Forty-eight bytes holds every name this engine uses; longer ones truncate, which is the right failure for a debugging aid. Note the copy uses SDL_strlcpy, which always null-terminates — strncpy famously does not, and that one-line difference is how a truncated name becomes a buffer overrun.

Fixed capacity, and full is not an error. It stops recording and sets overflowed(), which print() reports. Silently dropping events would be worse than truncating a name, because a missing event is indistinguishable from a call you forgot to make.

Recorded from inside render(), not described from outside. The tempting design is a function that walks the draw list and prints what it believes the renderer will do. That design drifts the first time somebody changes the renderer, and it drifts silently, and the result is a log that is believed and wrong. So the events are emitted from the same statements that issue the calls:

Which is what makes §D of the harness possible, and it is the test a capture cannot give you: draw_stats and the frame log are two counters incremented from the same statements, so asserting they agree catches an instrumentation bug that would otherwise be invisible.

4.4Wiring it in, and --trace

Four groups per frame — upload, clear, blit, scene — chosen to match the phases Lesson 4.8 already thinks in. Note where the scene's group opens:

Before the pass, closing after it. That is legal everywhere and is the shape §3.4's Metal caveat is happiest with; a group that begins inside a pass must also end inside it, and a group that spans a pass boundary is the case to avoid.

Recording is armed by P for exactly one frame and disarms itself as soon as it prints. That is not laziness about a toggle — it is how a capture works, and for the same reason: an instrument that runs continuously is one you stop reading and keep paying for.

And one flag, which is the piece that outlives the lesson:

Arms the log on the first frame, prints it, and exits. A headless frame dump — no window to click, no GUI, no driver hooks — which means it runs in CI, and the output can be diffed between commits. "This commit added a draw call" is a thing a build can now notice.

5Taking a Capture

An honest note about this section

This course is written on a Mac, so the RenderDoc walkthrough below is assembled from RenderDoc's own documentation rather than from a session the author ran. The steps and the panel names are quoted from its Quick Start guide; the judgements about what to look at are transferable and are the part that matters. The Xcode walkthrough follows SDL_gpu.h's own instructions.

Where a UI detail may have moved since, treat the panel names as reliable and the menu paths as a starting point. ⚠ VERIFY against your installed version.

5.1RenderDoc, on Windows or Linux

  1. Build with debug mode on. The engine passes true to gpu_device::create, which is what you want here: validation messages and a capture are complementary, and §3.5 measured the cost at 1.17× on a three-draw frame.
  2. File → Launch Application. Fill in the Executable field (browse, or drag the binary in). Leave Working Directory empty — it defaults to the executable's directory, which is where assets/ and shaders/ live, so this is the right default for us. Add command-line arguments if you want a particular mode.
  3. Click Launch. The engine starts with RenderDoc underneath it.
  4. Press F12 (or Print Screen) to capture the next frame. Take the capture on a frame you have arranged deliberately — orbit so that two objects overlap, or press C to a scene that is misbehaving.
  5. Close the application. The capture opens in the RenderDoc UI automatically; several captures give you thumbnails to choose from.

The panels you will use, by their documented names:

RenderDoc's main panels and what each answers
panelthe question it answers
Event Browser what happened, in order — your debug groups are the tree here
Texture Viewer what any texture or render target contained at this event
Pipeline State everything bound at this event: shaders, buffers, uniforms, cull mode, depth state
Mesh Viewer your geometry, before and after the vertex shader
API Inspector the individual API calls behind one event
Timeline Bar the frame's events laid out by time

5.2Xcode's Metal Debugger, on macOS

SDL_gpu.h gives the procedure directly, and it is worth quoting because it is the one place a Mac reader is likely to give up:

"Open XCode, go to Debug > Debug Executable…, select your application, set 'GPU Frame Capture' to 'Metal' in scheme 'Options' window, run your app, and click the small Metal icon on the bottom to capture a frame."

You do not need an Xcode project — Debug Executable… attaches to a binary CMake already built, which is the whole reason that menu item exists. The header adds one more thing for Mac readers: "For Metal, it should be enough just to run the application from XCode to receive detailed errors or warnings in the output" — which is the Metal equivalent of a validation layer, and is free.

The Metal Debugger's vocabulary differs and its concepts do not. Its navigator is the event browser and your debug groups are its tree; selecting a draw shows bound resources, attachments and pipeline state; it has a geometry viewer and a shader profiler. If you have read §3.7's table, you know what to expect from it.

5.3Four questions to ask a capture

Opening a capture and browsing is how people conclude the tool did not help. Arrive with questions. These four cover most of what goes wrong, and each one has an expected answer you already know from the frame log.

1. Is my draw there at all? Count the draws in the event browser against the frame log's count. If the draw is missing, the problem is on the CPU and happened before submission — a bad conditional, a null mesh, a skipped item. If it is present and nothing changed on screen, the geometry was culled, clipped, depth-rejected, or drawn somewhere you are not looking. Those are two completely different searches, and one glance separates them.

2. Is the right thing bound? Select the draw, open Pipeline State, and read the resource names — which exist now. This is where a missing sampler binding shows up as a blank slot, and it is the fastest possible answer to the failure that has cost this project three debugging sessions (Lessons 4.6, 4.7 and 4.8's harness).

3. Are the bytes what I think? Inspect the uniform buffer contents at b0 and b1. Lesson 4.6 had to build an entire probe shader to read a matrix back one component at a time; the tool shows all sixteen floats. If your matrix is transposed, this is where it is visibly transposed.

4. Where did the geometry go? The Mesh Viewer shows your vertices before and after the vertex shader. Post-transform positions outside the clip volume mean a projection problem; positions that are NaN mean an uninitialised uniform; a correct-looking mesh that does not appear means the fragment stage or the depth test.

The habit worth forming

Predict, then look. Before you inspect anything, say out loud what you expect: "b1 should be a model matrix with 1.4 in the translation column". Then look. If it matches, you have eliminated something; if it does not, you have found it. Browsing without a prediction generates the feeling of investigating and no information, and it is the difference between people who find frame debuggers useful and people who do not.

8Common Pitfalls & Debugging

The capture is a flat list with no tree

Symptom: your debug groups are nowhere in the event browser, though the draws are all there.

Cause: on D3D12, SDL_PushGPUDebugGroup, SDL_PopGPUDebugGroup and SDL_InsertGPUDebugLabel all require WinPixEventRuntime.dll. Without it they are inert — not an error, just silence.

Fix: put the DLL in your PATH or beside the executable. SDL's header says so on each of the three functions, and this is the only cross-platform difference in this lesson that produces no diagnostic at all.

The tree is wrong: groups nest where they should not

Symptom: events appear under the wrong heading, or a group swallows the rest of the frame. Usually on Metal.

Cause: a push and its pop straddle a render-pass boundary. On Metal a group pushed inside a pass is scoped to that pass, so popping it outside leaves the tree inconsistent.

Fix: open the group either entirely outside the pass (what this engine does) or entirely inside it. An RAII scope makes the second case automatic and the first case a matter of where you put the brace.

The capture is enormous, or capturing takes forever

Symptom: pressing F12 hangs the application for several seconds and produces a file measured in gigabytes.

Cause: a capture serialises the full contents of every live resource so the frame can be replayed (§2.2). It is proportional to how much you have allocated, not to how much you drew.

Fix: expected behaviour, not a bug — but capture a small window and a small scene when you can. It is also the reason capturing is a keypress rather than something you leave running.

Your instrumentation says one thing and the renderer says another

Symptom: the frame log reports two draws and draw_stats reports three.

Cause: a code path that issues a call without recording it — almost always an early continue or a second draw added later next to a record() that was not.

Fix: record from the same statement that issues, and keep the cross-check. Note the failure mode you are protecting against: the log would have been wrong and believed, which is worse than having no log — and the assertion costs one line.

Measuring instrumentation and getting a negative cost

Symptom: adding debug groups makes the frame measurably faster.

Cause: the effect is below the noise floor, and you measured a fluctuation.

Fix: measure the floor first — run the identical workload several times and take the spread — then require any claimed effect to beat it by a factor of two. If it does not, scale the work up until it does and divide (§3.5). A negative cost for added work is the clearest possible signal that a measurement has nothing to say, and it is worth learning to recognise as good news rather than as a puzzle.

Everything is named, and the capture still shows "Buffer 12"

Symptom: names appear for some resources and not others.

Cause: the unnamed ones are created somewhere that never took a name — transfer buffers were the whole of this category in our engine until this lesson.

Fix: grep for every creation call rather than every named one; the ones that never had a name parameter will not show up in a search for names. And remember there is no getter (§3.3), so this cannot be asserted in a test — a capture is the only place it is visible, which is an argument for looking at one early rather than once.

9Exercises

  1. 4.9.1 — Break something, then find it. Pick one: bind no texture, use the wrong pitch (8 in --probe still does this), reverse the winding, or push the camera matrix transposed. Do not tell yourself which. Capture a frame and find it using only §5.3's four questions.

    Hint: time yourself, and do it again a week later. The value of a frame debugger is almost entirely in how quickly you reach for it, and the only way to make that reflex is to use it on a bug whose answer you already know.

  2. 4.9.2 — Diff a frame in CI. engine --trace is deterministic. Commit its output, add a script that re-runs it and diffs, and make an unexpected change fail. Then add a draw call and watch it fail.

    Hint: strip the timestamps SDL_Log prepends. The interesting design question is what should be allowed to change: a golden file that fails on every legitimate edit gets deleted within a month. Consider asserting on the counts rather than the whole tree.

  3. 4.9.3 — Name everything, then check. Take a capture and list every object in it that still has no name. Fix them. There are more than you think — the swapchain textures, for instance, belong to SDL rather than to you.

    Hint: the honest finding here may be that some cannot be named because you did not create them. Report that rather than working around it; knowing which objects in a capture are yours is itself worth having.

  4. 4.9.4 — Groups that mean something. Four groups is the minimum. Add one per object inside the scene group, named from scene_object::name, and re-take the capture.

    Hint: §3.5 measured a group triple at ~183 ns, so a hundred objects is ~18 µs — about 0.1% of a 60 Hz frame. That is affordable and it is not free, which is exactly the sort of judgement this lesson is trying to make routine. Consider making it conditional on a debug build and then argue with yourself about whether that is wise.

  5. 4.9.5 — Pay the debt this lesson could not. On hardware RenderDoc or PIX can capture, read the real vertex-shader invocation count for the torus draw and compare it against §3.6's simulated table. Report how far off the model is.

    Hint: the prediction is 2,400 against a best case of 1,225 and a worst of 6,912. If the hardware beats 2,400 substantially, its cache is bigger or smarter than FIFO; if it is worse, the batching assumption is the suspect. Either way you will have learned something about your GPU that no documentation states, which is the whole reason the counters exist.

  6. 4.9.6 — Optimise the index order. §3.6 showed reuse collapsing 2.83× when triangle order is shuffled. Go the other way: implement Tom Forsyth's linear-speed vertex-cache optimiser and re-run the simulation on the reordered indices.

    Hint: the torus is already emitted in a good order, so expect a small win — which makes it a poor test. Optimise the shuffled indices instead and see how much of the 2.83× you recover; that is the number that tells you whether your implementation works.

10Recap & Next

  • A breakpoint cannot catch a GPU bug, and the reason is when work happens rather than any deficiency in the debugger. Recording and executing are separated by a submit, and the bug lives on the far side of it.
  • A frame debugger records inputs and replays them, which is why it can show you any resource at any event — and why captures are large, capturing is slow, and the tool must sit at the driver level.
  • RenderDoc does not support Metal. Vulkan, D3D11, D3D12, GL and GLES on Windows, Linux, Android and Switch. On macOS the tool is Xcode's Metal Debugger, and every concept transfers.
  • Name resources at creation, not with the setter. SDL's own docs say so, and a comment in this codebase spent four lessons confidently explaining an asymmetry that did not exist. A confident explanation of somebody else's API is a hypothesis; the documentation of the function you are already calling is where to test it.
  • Debug groups are a scope — literally, because Metal scopes a group pushed inside a pass to that pass, and an RAII type is how you never get that wrong. On D3D12 they need WinPixEventRuntime.dll and are silent without it.
  • Measure the noise floor before you measure anything against it. The first version of §3.5 reported a negative cost for adding work. Scaling the workload until the effect clears the floor turned "unmeasurable" into 183 ns per group triple, converging across two independent estimates. The validation layer costs 1.17× on a three-draw frame, which is a per-call figure wearing a misleading ratio.
  • Some numbers you cannot measure, and saying so is the job. Lesson 4.5's vertex-invocation debt is unpayable on this machine, so §3.6 models it instead, states every assumption, and points at the counter that answers it. The model turned up something better anyway: reuse is a property of the index order, and shuffling triangle order costs 2.83× with nothing about the geometry changed.
  • Your own instrumentation earns its place where the tools cannot go — every backend, CI, and a cross-check against a second counter. It stops exactly where replay begins.

11Further Reading

  • SDL3/SDL_gpu.h, the "Debugging" section. A page long, on your disk, and the authoritative answer to "which tool do I use" for every platform SDL supports. It is the first place to look and the last place most people do.
  • RenderDoc's documentation — the Quick Start, and then the How do I…? pages. Short, well written, and the source of §5.1's steps and panel names.
  • Apple, "Metal debugger" and "Optimizing GPU performance" (WWDC sessions and the Xcode documentation). The macOS half of this lesson, from the people who wrote the tool.
  • Tom Forsyth, "Linear-Speed Vertex Cache Optimisation" (2006). The algorithm behind Exercise 4.9.6, and still the standard reference — notable for being a heuristic that beats more principled approaches and for the author being clear about why he thinks that is.
  • meshoptimizer (Arseny Kapoulkine). The library everyone actually uses for index-order optimisation, and its README is a good short course in what else a mesh can be optimised for — overdraw, vertex fetch, quantisation.
  • Fabian Giesen, "A trip through the Graphics Pipeline 2011", part 3, on the post-transform cache. What §3.6's model is modelling, from somebody who has read the hardware documentation you have not.
  • Aras Pranckevičius, "Every Possible Way to Debug Graphics" and similar practitioner write-ups. Worth reading for the techniques that are not a frame debugger — printf-to-a-buffer, colour-coding intermediate values, bisecting a frame by commenting out draws — several of which are faster than a capture when you already have a hypothesis.
