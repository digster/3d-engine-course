Module 5 — Becoming an Engine · Lesson 5.12

Checkpoint: A Small 3D Game on the Public API

Eleven lessons ago we drew a line and called it law: engine/ is a library, demos/ are programs, and a program may include nothing but <engine/…>. Since then we have built an application layer, a logger, a handle system, an asset store, an ECS, a transform hierarchy, a camera, an action map, a debug drawer and a debug UI — and every single program that used them was written by the person who had just built them, in the same afternoon, to show them off. That is not a test of an API. A demo can stop at the edge of the one subsystem it demonstrates; a game has to cross every edge there is — load an asset, spawn an entity, parent a camera, read a button, move a body, test an overlap, tell the player what happened — and the seams between subsystems are exactly where a public API is weakest, because nobody has ever stood on them. So this lesson writes a game. It is small on purpose: drive a rover round an arena and collect twelve orbs, half of them riding a carousel. What it is not is forgiving. Every time the published headers could not do something, this file did it itself, in the open, with a comment naming what was missing — and there are seven. Two of them turn out to be promises the engine had already made and not kept: the header that calls itself “the whole public API, in one include” lists 40 of 55 public headers and is missing the entire ECS, the asset store, the action map and the logger; and scene.hpp has said since Lesson 5.1 that “Module 5's ECS replaces the struct with components”, which Module 5 never did. Both are fixed here, one of them against this engine's own three-caller rule and owing a reason. The other five are named, measured, and handed to the module that owns them. Along the way a camera parented to a rolling car produces a matrix that is not rigid, an assertion fires, and a headless run hangs for ever — which is one composition order written the way it reads in English rather than the way the algebra says.

1. The problem: a boundary nobody has stood on

Lesson 5.1 made a claim with a mechanism behind it. The claim was that engine/ is a library with a public API; the mechanism was the include path, so that #include "gfx/raster.hpp" — the spelling every file in this repository had used for four modules — stopped resolving. A demo that reaches for an internal does not get a review comment, it gets a compile error. That was the right mechanism and it has held perfectly.

But look at what has actually stood on it.

sandbox predates the boundary and owns its own loop. pong is Module 1's game, relocated. hello_cube is a hundred lines that draw one cube. ecs_swarm was written in Lesson 5.8 to demonstrate the ECS — by the person who had written the ECS that morning. gltf_view shows off the importer, by the person who wrote the importer.

There is a specific kind of blindness in that arrangement, and it is not about competence. When you write the demo for a subsystem you have just built, you already know where everything is. You do not discover that the function you want is not exported, because you know it is not, and you reach for the one that is without ever noticing you made a choice. You do not discover that a header is missing from the umbrella, because you never use the umbrella — you type the include you know is correct. You do not discover that two subsystems have no path between them, because you are only using one of them.

A public API is a promise made to somebody who does not know where everything is. The only way to find out whether the promise holds is to have that person write something. We do not have that person. What we have is the next best thing, which is a program with requirements that were not chosen to flatter the engine.

Why now, and not at the capstone

Module 9 ends with a complete game built solely on the public API, and that is the real proof. The trouble with waiting for it is arithmetic: the capstone sits at roughly hour 434 of this course with about ten hours of budget around it, and anything it finds has to be absorbed by an engine that eighty more lessons have been built on top of. We are at hour 62. A design bug found here costs a header; found there it costs a refactor of everything that has since depended on the bug. The cheapest moment to discover that your API does not work is the first moment somebody could have discovered it.

2. What a game asks that a demo does not

The game is called collector and it fits in one sentence: drive a rover round a 14 × 14 metre arena and collect twelve orbs before a ninety-second clock runs out. Six orbs sit still and bob; six ride a carousel, so they move while you chase them. Eight pillars stand in the way. That is the whole design, and it was chosen to be ordinary rather than interesting — a game with an unusual requirement would exercise an unusual part of the API, and the question here is whether the usual parts work together.

3. Finding one: the table of contents that was not one

Before writing a line of the game, I did what a newcomer does: I opened engine/include/engine/engine.hpp, because its first line says “the whole public API, in one include” and its comment goes on to say something stronger and more useful:

It is also a TABLE OF CONTENTS: this file is the shortest complete statement of what the engine offers, and the fastest way to see whether something is public is to look for it here.

That is a testable claim, so let us test it. Count the .hpp files under engine/include/engine/ — other than engine.hpp itself, which is the set it could possibly list — then count the #include lines in engine.hpp, and compare.

Forty of fifty-five. One of the fifteen absences is correct and documented — platform/main.hpp defines a program's entry point, and an umbrella whose selling point is “include everything, it is harmless” must not be a way to acquire a main by accident. The other fourteen are not absences with reasons. They are the entire ECS, the entire asset system, handles, pools, the logger, the assertion macros, the benchmark harness and the action map: very nearly everything Module 5 built.

The file's own history is the whole explanation, and you can read it with one command:

Three commits. Lesson 5.1 created it. Lesson 5.2 added platform/ and app/. Lesson 5.11 added debug_lines and debug_ui. Lessons 5.3, 5.4, 5.5, 5.6, 5.8, 5.9 and 5.10 shipped fourteen public headers between them and touched this file zero times.

Notice that this is not carelessness in the ordinary sense — 5.2 and 5.11 did remember. It is a rule kept by memory, and a rule kept by memory is kept about half the time. Which is precisely the thing Lesson 5.1 said out loud when it moved the boundary into the include path: enforced by the include path, not by the style guide. We applied that reasoning to one rule and not to the one three lines below it.

3.1 Why it rotted: the file has no consumer

Here is the mechanism, and it is worth more than the bug. Search the repository for anything that includes <engine/engine.hpp>:

Nothing. Not one demo, not one engine source. Every program in this repository includes what it uses, because that is what the umbrella's own comment advises for anything built more than a few hundred times. So the file is never compiled, and a header that is never compiled cannot be kept correct by being used. It can only be kept correct by being checked.

That gives the fix a shape. Adding the fourteen missing lines takes a minute and buys nothing durable, because the next lesson to add a header will forget for the same reason the last seven did. What is worth building is the check, and it belongs where a new header is noticed — at configure time, in engine/CMakeLists.txt:

A glob used as a lint, not as a source list

Every CMake guide tells you not to file(GLOB), and every one of them is talking about globbing sources: adding a new .cpp does not re-trigger CMake, so the build silently omits it and you get a link error you cannot explain. That objection does not transfer here. A stale glob in a lint can only fail to notice a header added since the last configure — it can never drop a translation unit, never change a flag, and never break a build. Weigh that against what it replaces: a silent wrong answer that stood for thirteen lessons. CONFIGURE_DEPENDS asks the generator to re-glob on each build, which most generators honour and none are required to; it is belt and braces, not the argument.

The comparison itself has one trap in it, and the first draft fell in. Grepping the whole file for the header's name passes on headers that are only mentioned in a comment — and the single documented exception, platform/main.hpp, is named in prose precisely to say that it is absent. A check that reads its own excuse as compliance is worse than no check, so the match is anchored to a whole #include line.

3.2 The measurement, which comes out the other way round

Completing the umbrella makes it bigger, and bigger means slower. So before doing it, the obvious prediction: the umbrella is the expensive way to include the engine, the explicit list is the cheap way, and completing the umbrella widens the gap. Lesson 5.1 measured header costs on this project rather than asserting them; let us do the same here. One translation unit, compiled with c++ -std=c++20 -c, best of five.

The prediction is wrong, and it is wrong in an informative direction. The umbrella as shipped (0.28 s) was cheaper than including exactly what the game uses (0.37 s) — because the fourteen headers it was missing are the templated ones. registry.hpp, view.hpp, pool.hpp, asset_store.hpp and actions.hpp are where this engine's compile time actually lives, and an umbrella that omits them is not cheap, it is incomplete, and the two look identical on a stopwatch.

Worked: what completing it costs

umbrella, as shipped (40 headers)   0.28 s
umbrella, completed (55 headers)    0.39 s

change        (0.39 − 0.28) / 0.28 = +39.3%
against explicit  (0.39 − 0.37) / 0.37 =  +5.4%

baseline (an empty file)      0.01 s

So the corrected umbrella costs 39% more than the broken one and 5.4% more than including what you use. The honest headline is that the one-translation-unit cost of an umbrella is not the reason to avoid it. The reason is the one Lesson 5.1 measured and this lesson does not re-measure: with explicit includes, editing gpu_scene.hpp recompiles the files that use the GPU scene; with an umbrella it recompiles everything. That is a property of the dependency graph, and it does not show up in a single-file benchmark at all.

Both facts go in the header's comment, because a reader who finds only the first number will conclude the umbrella is fine and a reader who finds only the second will conclude it is a disaster.

4. Finding two: a promise Module 5 made and did not keep

Now the eleventh row of §2's table. The game has entities; the renderer draws scene_objects; what connects them?

Nothing public. collect_triangles takes std::span<const scene_object>, and a scene_object is a struct with a transform in it — not an entity, not a component, not a registry. So the game must walk the registry itself and build the span. That loop already exists, once, in ecs_swarm, and it is twenty lines. Writing it a second time is the obvious move and the wrong one, because of what those twenty lines contain.

Open gfx/scene.hpp and read its opening paragraph, which has been there since Lesson 5.1:

It is deliberately NOT the final answer. Module 5's ECS replaces the struct with components, and Module 6 pulls the surface fields out into a material. Both of those are named in the comments below where the seams already show.

Module 5 is this module. It built the ECS in 5.8 and the hierarchy in 5.9, and it never took the second step — so the seam the comment points at is still open, and the twenty lines in ecs_swarm are what fills it by hand. This lesson is Module 5's last, so it is the last chance for that sentence to be true.

4.1 Hoisting at two callers, against our own rule

There is a complication, and it deserves to be argued rather than waved past. This engine's own stated rule — written twice, in scene.hpp — is that a type invented before three callers have asked for one is a guess. We have two: ecs_swarm, and the game about to be written. Hoisting now breaks our rule.

The reason to do it anyway is not “two is close to three”. It is that what is duplicated is not an idiom, it is a known-broken workaround. Here are the four lines at the heart of ecs_swarm's render_system:

The hierarchy produced a mat4; scene_object wants a transform; and a transform has no field for “a general linear map”. So the whole 3 × 3 linear part is dropped into the field called rotation and the scale is set to 1. It works — exactly, as §4.2 proves — and it works only because that field happens to be a bare mat3 with no orthonormality requirement. ecs_swarm's own comment says so, and predicts the end of it:

It abuses the fact that the field is named rotation and typed mat3, which is precisely why it is a bridge and not a design. Module 6 gives the renderer a matrix directly and this function loses its last four lines.

A stable idiom repeated twice is a coincidence. A workaround repeated twice is two places to fix on the day somebody finally changes scene_object — and one of those two places is inside a demo, which nobody thinks of as engine code and nobody greps when they change an engine type. That is the argument, and it is narrow: we are hoisting a conversion, not inventing a type. renderable is not speculative either — it is scene_object with the placement removed, and scene_object has existed since Lesson 3.1.

4.2 The conversion is exact, and that has to be checked

“It works exactly” is the sort of claim that is either true to the bit or quietly false by a thousandth. Let us derive why it is the former, and then measure it.

parent_from_local builds a mat4 from a transform by scaling each basis column and putting the position in the fourth:

\[ M \;=\; \begin{bmatrix} s_x\,\mathbf{r}_0 & s_y\,\mathbf{r}_1 & s_z\,\mathbf{r}_2 & \mathbf{p} \\ 0 & 0 & 0 & 1 \end{bmatrix} \;=\; \begin{bmatrix} R\,S & \mathbf{p} \\ \mathbf{0}^{\!\top} & 1 \end{bmatrix} \] M = [ R*S | p ; 0 0 0 1 ], where S = diag(sx, sy, sz)

Reading that backwards is the question: given M, find a transform that reproduces it. The obvious route — decompose RS into a rotation and a scale — is a polar decomposition, it is iterative, it is lossy, and it fails outright on a shear. The route the code takes is to notice that the equation has an easier solution if you stop insisting that R be a rotation. Put S = I and let R absorb everything:

\[ R' \;=\; \text{linear}(M), \qquad S' \;=\; I, \qquad \mathbf{p}' \;=\; \text{translation}(M) \quad\Longrightarrow\quad R'S' \;=\; R'\;=\;\text{linear}(M) \] R' = linear(M), S' = I, p' = translation(M) => R'*S' = linear(M), exactly

No arithmetic is performed at all. The nine numbers are copied, the three are copied, and the multiply by I that parent_from_local performs on the way back is a multiply by one. That is why the round trip is exact in the strongest sense available: not “within 1e-6”, but zero.

Worked: one transform, out and back

Take a deliberately awkward one — a non-uniform scale, three rotations, an off-axis position:

position = (1.25, −3.5, 7.75)
rotation = Ry(0.7) · Rx(−0.31) · Rz(1.9)
scale    = (2.5, 0.125, 1.75)

Resolve it through the hierarchy, collect it, and recompose the result. verify_512 §B compares all sixteen elements:

ok   max |element difference| = 0 (expected exactly 0)
ok   CONTROL: a 1.0 nudge is reported as 1 (must be > 0.5)

The control is not decoration. “The difference is zero” is also what you get from comparing something with itself, from comparing two empty matrices, or from a comparison function that returns zero. Perturbing one element by 1.0 and requiring the same code to report it is what makes the first line mean something.

5. Where the new header goes, and what it may include

Two decisions, and both are physical design rather than taste.

5.1 Should the engine define a component at all?

Publishing a system is uncontroversial. Publishing a component is a real commitment: every program that wants this loop must store its mesh handle in the engine's struct rather than its own, and an engine that publishes components is taking a position on how a game is laid out. Some engines do (Unity's MeshRenderer); some deliberately do not (EnTT ships a registry and no components at all).

The precedent is already set, and by this same module. ecs/hierarchy.hpp defines parent and world_transform, and it had to, for a reason that is mechanical rather than philosophical: hierarchy::resolve cannot be written against “whatever component you happen to call parent”. A system the engine owns must name the data it reads or it cannot be compiled. That gives a rule you can apply:

The rule

The engine defines a component when, and only when, an engine system reads it. Everything else is the game's.

So renderable is the engine's, and rover, collectible, spinner, bobber, carousel and pillar are not — nothing under engine/ will ever look at them, and nothing in the game had to ask permission to invent them.

5.2 gfx/ or ecs/?

The struct holds a mesh_handle and the function takes a registry, so it touches both. Put it under ecs/ and every program that includes the ECS compiles mesh.hpp, light.hpp and their transitive closure — to store a component that no simulation code will ever read. Put it under gfx/ and graphics knows about entities while entities know nothing about graphics.

The deciding principle is the direction of the arrow: a dependency should point towards the more general and the more stable. A registry has no opinion about meshes and a great deal of future code — Module 8's physics, a save system, an editor — wants entities and will never want a mesh_handle. So: engine/gfx/renderable.hpp, and the ECS stays clean.

5.3 And the registry is named, not included

Lesson 5.11's rule was that a header's include list is its interface. This header names ecs::registry in one signature and never dereferences it, which is exactly the case a forward declaration covers:

C++ in place: incomplete types

A declaration like class registry; introduces the name of a type without its definition. You may then form pointers and references to it, declare functions that take and return them, and nothing more — you cannot create one, call a member, take sizeof, or inherit from it, because none of those can be answered without the layout. That is the whole trade: a reference parameter needs only a name, so the definition can stay in the .cpp. gpu_scene.hpp already does this for instance_batch, and says why in a comment.

The cost of getting this wrong is not hypothetical. §3.2 measured the templated ECS headers as the expensive half of this engine's public surface; every file that merely stores a renderable would pay for them.

6. The camera boom, and an assertion that hangs

Lesson 5.9 made the camera an entity, and one consequence is so convenient it is easy to take the wrong lesson from it: parent the camera to the player and you have a follow camera, for free, with no system and no code. It rides along because riding along is what “my placement is relative to my parent” means.

It is also wrong, and specifically so. The rover leans into its turns — a cosmetic roll of up to 22°, which looks good on a car and is poison to a camera. A camera parented straight to the rover inherits the entire basis, roll included, so the horizon see-saws. Viewers do not read that as the car leaning; they read it as the world tilting, because the camera is the viewer's inner ear. And there is a second inheritance that is worse than cosmetic: the rover is a scaled box, 0.60 × 0.44 × 0.84 metres, so a camera parented to it inherits a non-uniform scale.

The fix is not a special case in the renderer and not a “camera follow” system. It is one more link in the chain — a boom, an entity with a transform and no components of its own, whose only job is to be a place where the two unwanted factors can be cancelled.

Now the algebra, which is short and has exactly one trap in it. The rover's world basis is its heading H, times its roll Rz(bank), times its scale S. We want the boom's world basis to be H alone. Since world(boom) = world(rover) · local(boom):

\[ L \;=\; \bigl(H\,R_z(\beta)\,S\bigr)^{-1} H \;=\; S^{-1} R_z(-\beta)\,H^{-1} H \;=\; S^{-1} R_z(-\beta) \] L = (H * Rz(bank) * S)^-1 * H = S^-1 * Rz(-bank) * H^-1 * H = S^-1 * Rz(-bank)

The inverse of a product reverses the order of its factors, so the unscale comes first and the unroll second. Read that sentence again, because the English description of what we are doing — “undo the roll, then undo the scale” — produces Rz(−β)·S−1, which is the other one. And a rotation and a non-uniform scale do not commute, so the two are genuinely different matrices.

Worked: why the wrong order is not a small error

Take the rover's actual scale S = diag(0.60, 0.44, 0.84) and a bank of 0.31 rad (17.8°). Consider what each candidate does to the boom's x axis, (1, 0, 0):

S⁻¹ · Rz(−β) · (1,0,0)  = S⁻¹ · (0.9523, −0.3051, 0)
                    = (1.5872, −0.6934, 0)

Rz(−β) · S⁻¹ · (1,0,0)  = Rz(−β) · (1.6667, 0, 0)
                    = (1.5872, −0.5085, 0)

The x components agree to four decimal places and the y components differ by 36%. That is what makes this bug expensive: the result is close enough to look like a tuning problem. And the first version of this file shipped the second one.

6.1 What actually happened when it was wrong

The program did not draw a tilted horizon. It hung, in a headless --shot run, for ever, with no output at all — and that is a more instructive failure than the wrong picture would have been.

Lesson 5.9's view_from_camera asserts its input is rigid, because a view matrix is the inverse of a camera's placement and the fast inverse it uses (rigid_inverse) is only an inverse when the basis is orthonormal. The boom with its factors swapped leaves a basis that is neither, so the assertion is entirely correct and fires on the first frame. What happens next is the part nobody had met yet:

Lesson 5.3 shipped SDL_assert and made a point of the fact that it expands to a while loop so that its RETRY option genuinely re-tests the condition. That is exactly right at a desk with a dialog box in front of you. In a headless run on a build server, with no display to put a dialog on and no terminal to prompt at, the handler's default answer keeps arriving and the loop keeps retrying a condition that cannot change. The assertion that would have taken one second to diagnose interactively became a hang with no message.

The general shape of this

An assertion is a developer-facing control flow, and --shot is the one configuration in this repository that has no developer in front of it. That is not a reason to remove the assertion — it caught a real bug on the first run, which is precisely its job — but it is a reason to know the failure mode before you meet it at three in the morning on CI. Lesson 5.12 does not change SDL's handler; it reports the behaviour, and Exercise 5 installs a handler that aborts instead of retrying when there is no video subsystem.

The fix is one line, and verify_512 §E keeps it fixed by building all three chains — right order, wrong order, and no boom at all — and asserting the rigidity of each. Note the third: without a control that also fails, “the wrong order is not rigid” would be equally consistent with the boom doing nothing whatsoever.

7.1 One word, two conventions

The first thing the game had to get right, and the first thing it got wrong — three times. The arena came out a quarter of its intended area with the pillars floating beside it in the void, which reads as a camera bug for a good ten minutes before it reads as what it is.

cube_mesh()'s eight corners are at ±0.5, so a transform's scale is the box's full size. icosahedron_mesh()'s twelve vertices are at distance 1.0, so its scale is a radius. Both are documented and both are reasonable in isolation; together they mean that scale = 1 gives you a one-metre cube and a two-metre ball.

The trap is not the asymmetry, it is that a half-extent is exactly what the rest of the program wants. A collision test wants a half-extent. debug_lines::box takes a half-extent. So the value you have in your hand is the wrong one by a factor of two precisely when you reach for scale. The game's answer is one four-line function, and the factor of two is the entire content of it:

The third instance is the one that survived longest, because it looked plausible. A pillar's debug box is drawn through its world matrix — which already carries the scale — so the half-extent passed alongside it is in the cube's own space, where it is 0.5 by definition. Passing metres draws a box exactly twice the size of the thing it outlines, and a box slightly too big around a collision proxy looks like a deliberate margin.

7.2 The order the step runs in, and the one line that must not move

Five systems, and four of them could run in any order. The fifth cannot:

pickup_system tests distances in world space, and six of the twelve orbs are children of a carousel that carousel_system just turned. Put the resolve after the pickup and every riding orb is tested against where it was last step. At 0.45 rad/s and a radius of 4.0 m that is 3 cm of error per step — far too small to see, and far too small to blame on anything. It would present as “the moving orbs are slightly harder to catch than the still ones”, which is a sentence a designer would try to fix by changing the pickup radius.

Symptom → cause → fix

Symptom: a moving object's interactions feel subtly, inconsistently late.
Cause: a system read world_transform before the hierarchy resolved it this step, so it read last step's composition.
Fix: one resolve, after everything that writes a local transform and before everything that reads a world_transform. If you cannot arrange that, you need two resolves and you should say why in a comment.

The other ordering constraint is inside pickup_system and the ECS tells you about it rather than letting you find out: view::each asserts if its lead pool changes during iteration, so an orb cannot be destroyed inside the lambda that found it. Collect ids into a scratch vector, destroy after. That is a restriction the ECS chose deliberately in 5.8, and it is the good kind — a guaranteed assertion instead of an iterator that is sometimes fine.

7.3 A screenshot of frame zero is a screenshot of a spawn function

Every demo in this course has a --shot mode, and for a game the naive version is useless: the first frame is the world before anything has happened. So collector --shot runs 240 fixed steps with two constants held down before it draws:

8. What the game could not find

Seven findings. Two are fixed in this lesson and five are not, and the five are more useful than the two — a gap you have named and dated is a gap that stops surprising you.

8.1 There is no collision, and the wall is a lie

The rover stops at the arena edge because six lines of arithmetic in drive_system clamp its position. There are four kerbs drawn at that edge, and they are scenery — nothing tests against them, and if you deleted them the rover would still stop. The wall is a picture of a rule enforced somewhere else.

Meanwhile the eight pillars have no clamp, so you drive straight through them. Press G and you can see exactly what is missing and exactly what is not: every pillar is outlined with an oriented box, drawn from the same world matrix a collision test would use. The geometry is present, correctly placed, and already in the ECS. That is why struct pillar is a tag with no data in it — a unit cube under a world_transform is an oriented bounding box, so storing the half-extent a second time would only have created a copy that drifts.

What is missing is not the data. It is the solver — and the gulf between the pickup test and a pillar response is the whole of Module 8. A pickup needs a boolean: are these two spheres overlapping. A pillar needs a contact point, a normal, a penetration depth, and a response that slides rather than sticks, applied one normal at a time so that a corner does not stop you dead in both axes at once. That is why the easy one is in the game and the hard one is thirteen lessons away.

And the quadratic nobody can see

pickup_system is O(rovers × orbs). There is one rover and there are twelve orbs, so the quadratic is hidden by the constants — which is exactly how this shape survives into a shipped game and then falls over on the level with four hundred pickups. Lesson 8.9's uniform grid is the answer; naming it here is cheaper than discovering it later.

8.2 The engine cannot put a character on the screen

A game has to say “8 of 12”, and “0:43”, and “you won”. Search engine/ for a font, a glyph, or a text call: there is nothing. So the HUD is drawn by SDL, with SDL_RenderDebugTextFormat and its built-in 8 × 8 bitmap font — a debugging facility that happens to be in the window.

Three consequences follow, and they are why this is a finding rather than a shrug:

  1. It exists only on surface::renderer. A --shot run is headless and has no SDL_Renderer, so the expected result in §11 is a picture of the game with no score on it — the number you most want is the one thing missing.
  2. It is unavailable on the GPU path for the same reason, so the engine's real renderer is the one that cannot show a number.
  3. It is not composited with the world. It is drawn on top, by a different renderer, at a different scale — so it cannot be tinted, faded, placed in the scene, or measured.

Dear ImGui does not rescue this, and the reason is the one Lesson 5.11 gave when it integrated ImGui in the first place: ImGui is tooling. A panel of live counts for a developer is exactly what it is for; a player-facing scoreboard is not. Using it for the latter would be shipping a debug library as a product feature, which is a decision that is very hard to walk back.

8.3 A pickup is silent

The single most conspicuous absence when you actually play it. Collecting an orb is the only thing the game rewards you for, it takes about a second to set up, and it produces no sound, because SDL3's audio-stream model arrives in Lesson 7.8 and the engine has no audio layer at all. This one needs no analysis; it is recorded because a checkpoint's job is to record what it found, and “the game feels dead” is a finding even when the cause is obvious.

8.4 There is no public path from an entity to the GPU renderer

The one that decided how this game is rendered. gpu_scene_renderer::render consumes gpu_draw_items; the ECS produces components; and no public function connects them. sandbox crosses that gap, in about seven hundred lines, inside its own main.cpp — which is why nobody had noticed: the only program that ever crossed it was written before the boundary existed and keeps its bridge to itself.

So collector renders on the CPU, through the software rasterizer, like every program written from outside the boundary since the refactor. That is a sentence worth sitting with. Three lessons after moving the renderer to the GPU, the GPU renderer is the one a game cannot reach. Module 9's renderer facade is where this is answered, and §5's collect_renderables is deliberately shaped so that the GPU version is a sibling function rather than a redesign.

8.5 view() has no const overload

A small one with a wide blast radius. Look at the signature this lesson had to write:

That first parameter is a mutable reference and the function writes nothing through it. registry::view() is non-const and ecs::view hands out Ts&, so there is no way to spell “I am going to walk this registry and change nothing”. Every read-only system in this engine has to ask for write access it will not use, and const stops being able to tell a reader anything.

The fix is the one EnTT reaches for — allow view<const renderable> and propagate the constness into each's parameters — and it is a genuine change to two published headers, so this lesson reports it instead of smuggling it in. The signature is left looking wrong on purpose, with the reason in its doc comment: a comment nobody reads is a worse bug report than a parameter everybody trips over.

8.6 A program cannot name its own log category

The smallest finding, and it half-works in an interesting way. Lesson 5.3's five categories name engine subsystems, and correctly so — a category called log_app inside the library would be the library naming something it knows nothing about. What makes the game's own category possible anyway is the last member of that enum:

log_category_count is documented as “not a category; the count, for iteration”, and it is also exactly where a program's own categories begin — an enum that publishes its own end leaves room after it. The half that does not work: the --log spec is parsed against name_of(log_category), which returns "?" for anything outside the five, so this category can be filtered in code and cannot be named on the command line.

Which is why the --shot summary is a printf and not a log call at all. A log is a diagnostic: off by default, filtered, aimed at whoever is debugging. The shot's summary is the program's output, and a tool whose result only appears if you pass the right --log spec is a tool with a trapdoor.

9. The instrument, and proving it can fail

verify_512 is six sections and 27 checks. Three of them are controls, and it is worth saying what each control is there to rule out, because “a test that passes” and “a test that can only pass” are indistinguishable from the outside.

And the harness compiles the umbrella

A list of 55 includes is not obviously correct just because each line is spelled right.

12. The golden, and why it is blind to this lesson

The reference render is byte-identical, as it has been for every lesson since 5.1. Run it anyway — “I am confident it cannot have changed” is what a test is for — but be clear that it is a null instrument here, and say so structurally rather than hopefully:

  • demo::write_reference_shot renders through soft_renderer.cpp, raster.cpp and framebuffer.cpp, driven by demos/common/demo_scene.cpp.
  • renderable.cpp is a new translation unit that nothing in that list calls. It reads a registry, and the reference scene has no registry.
  • engine.hpp gained fifteen #include lines and no declarations, and nothing under demos/common includes it — §3 established that nothing anywhere did.
  • The CMake lint emits a message and never a compile flag.

So the picture cannot move, and a byte-identical result is evidence of nothing except that nobody edited a file they did not mean to. That is worth ninety seconds and no more. The real instrument for this lesson is verify_512 §B — the matrix round trip every object drawn through collect_renderables depends on — and it carries a control that fires at 1.0.

A second shot now exists

collector --shot is itself a characterization test, and a better one than the golden for anything the ECS touches: it runs 240 deterministic simulation steps and prints four numbers derived from them. If a future lesson changes the hierarchy's resolve order, the view's lead-pool choice, or the pool's swap-and-patch, the triangle count will move and this line will say so.

13. Common pitfalls & debugging

Everything is half the size it should be, and some of it is floating

Symptom: the arena is a quarter of its intended area, the pillars stand beside it in the void, and the whole thing reads as a broken camera.
Cause: cube_mesh() spans ±0.5, so a transform's scale is the box's full size. A half-extent passed straight through — the natural thing to do, because a half-extent is what everything else wants — halves every dimension, and using the half-extent as the centre height puts the box half underground.
Fix: one helper that takes a centre and a half-extent and does the doubling (box_at, §7.1). Do not fix the call sites individually; you will miss one.

A debug box is exactly twice the size of the thing it outlines

Symptom: collision proxies look like they have a generous margin.
Cause: debug_lines::box(const mat4&, vec3 half_extent, …) takes the half-extent in the matrix's local space, and the world matrix already carries the scale. Passing metres scales them again.
Fix: pass {0.5f, 0.5f, 0.5f} — the unit cube's own half-extent. The tell is that the error is exactly 2×, never 1.8×: a plausible-looking margin that is exactly a factor of two is never a margin.

A headless run hangs for ever and prints nothing

Symptom: --shot never returns, no output, no crash. CI times out.
Cause: an SDL_assert fired. It expands to a while loop so that RETRY genuinely re-tests, and with no display to put a dialog on and no terminal to prompt at, the default answer keeps arriving and the condition cannot change.
Fix: attach a sampling profiler or debugger and read the top frame — sample <pid> on macOS, gdb -p elsewhere — and the assertion's own function is sitting at the top of the stack. Exercise 5 installs a handler that aborts instead.

Moving objects are subtly harder to interact with than still ones

Symptom: the carousel's orbs feel like they need a bigger pickup radius than the stationary ones.
Cause: something read a world_transform before hierarchy::resolve ran this step, so it saw last step's composition. At 0.45 rad/s and a 4 m radius that is 3 cm — invisible, and far too small to blame on anything.
Fix: one resolve per step, after everything that writes a local transform and before everything that reads a world_transform. If two resolves are genuinely needed, write down why.

An entity exists, looks right in the debugger, and does not draw

Symptom: you spawned it, alive() is true, the component is there, nothing appears.
Cause: it has a renderable and no world_transform. hierarchy::resolve never creates components (5.9, deliberately), so add<renderable> without add_hierarchy_components is silently invisible.
Fix: read renderable_report::unresolved, which exists for exactly this and is on the debug panel for exactly this reason. Before that counter the only symptom was “the orb is not there”.

The first keystroke after clicking into a panel also reaches the game

Symptom: type into the ImGui field and the rover lurches once.
Cause: debug_ui::begin_frame() was called beside the panels in on_overlay rather than first in on_input. The capture flags are computed inside NewFrame, so every read is one frame stale.
Fix: begin_frame() is the first statement of on_input, before gate_.update(...). Lesson 5.11 argued this at length; it is here because a new program is exactly where the ordering gets re-invented.

Your program's log lines never appear, whatever --log spec you pass

Symptom: --log '*=info' shows the engine's messages and none of yours.
Cause: a category past log_category_count is not in name_of's table, so the spec parser cannot address it and it keeps SDL's default floor (§8.6).
Fix: set it in code with SDL_SetLogPriority, or — for anything that is the program's output rather than a diagnostic — use printf and stop calling it a log.

14. Exercises

  1. 1 — A second carousel. Add another pivot at a different radius and a different rate, with the remaining orbs parented to it, and make one of them turn the other way. Then parent the second carousel to the first and predict what the orbs do before you run it.

  2. 2 — A trail with a lifetime. Give the rover a trail: queue one debug line per step from its last position to its current one, with a lifetime of 1.5 s. Then pause the game (add a paused action) and check the trail is still there. Lesson 5.11's expiry rule says it should be; confirm it, and say what would have happened with a subtract-then-test rule and dt == 0.

  3. 3 — Actually interpolate. on_frame takes alpha and throws it away. Keep the previous step's world_transform for every renderable and lerp — position linearly, and the basis by whatever you can justify — then run at a fixed step of 20 Hz and compare. Report the extra memory in bytes per entity.

  4. 4 — const views (open). Make world.view<const renderable>() compile and hand out const renderable&, then change collect_renderables to take a const ecs::registry&. Count how many other functions in this repository could then say what they mean.

  5. 5 — An assertion that does not hang (open). Install an SDL_AssertionHandler that returns SDL_ASSERTION_ABORT when SDL_WasInit(SDL_INIT_VIDEO) is false, and SDL_ASSERTION_ALWAYS_IGNORE never. Decide where it belongs — the engine, or each program — and defend the choice.

Hints

1. set_parent returns a parent_status; read it. A cycle is reported, not crashed, and the second half of this exercise is a good way to see that happen on purpose.

2. The lifetime argument is the last parameter of debug_lines::line and defaults to k_debug_this_frame, which is 0.0. Look at how advance() compares before it subtracts.

3. Interpolating a basis is the hard half and Module 7 is where it is done properly. For this exercise, interpolating position and taking the newer basis is a defensible answer if you say so — and it is what a great many shipped games do for objects that do not rotate quickly.

4. The blocker is that view stores pool<Ts>* and pool<const T> is not instantiable. std::remove_const_t in the storage and the original Ts in each's parameter pack is the shape of the answer.

5. SDL_SetAssertionHandler takes a function pointer and a void*. Note that it must be installed before anything can assert, which is a constraint on where more than on what.

Solution sketches

1. Parenting carousel B to carousel A composes the rotations, so B's orbs sweep an epicycle — the same picture Lesson 5.9's moons drew, arrived at from the other direction. If B turns the other way at the same rate, its orbs travel in a straight line relative to the world, which is a satisfying thing to watch and a genuinely useful sanity check on the composition.

2. It survives, because advance() tests before it subtracts. With subtract-then-test and a strict <, a line whose remaining lifetime is exactly 0 and a dt of 0 never expires — so on a paused clock, a single-frame --shot, or any frame you are stopped in the debugger for, the queue fills and never drains.

3. Two mat4s per entity is 128 bytes, which at this scale is nothing and at a hundred thousand entities is 12.8 MB — precisely the arithmetic Lesson 5.6 measured, arriving in a new place. The usual production answer is to interpolate only what is visible, which needs the culling that Module 6 builds.

4. The change is small and it touches two published headers, which is why this lesson reported it rather than making it. Expect the count in the second half to be larger than you guess: hierarchy_debug_system, every gizmo pass, every serializer, and every query a future editor makes.

5. It belongs in the engine, installed by platform::start, because the property it depends on — “is there a video subsystem” — is the platform layer's business and no program should have to know to ask. The counter-argument worth weighing is that an engine which aborts on your behalf has taken a decision away from you; the answer is that in a headless run there was never a decision to take.

15. Recap & next

The engine now has a game built on it, written from outside the boundary Lesson 5.1 drew, by a program that was not designed to flatter it. That is the capability this lesson adds, and it is a capability of the project rather than the engine: from here on, “does the public API suffice?” is a question with a program attached to it.

Two things in the engine changed. engine.hpp now lists every public header, and a configure-time lint keeps it that way — because §3 established that the file has no consumer, and a header nobody compiles cannot be kept correct by being used. And gfx/renderable.hpp keeps the promise scene.hpp made in Lesson 5.1: Module 5's ECS does now replace the struct with components, the mat4-to- transform conversion lives in exactly one place, and it is exact to the bit rather than nearly so.

Five things did not change, and they are the more valuable half. There is no collision, so a wall is a clamp and a pillar is scenery. There is no text, so the score is drawn by SDL's debug font and vanishes the moment you run headless. There is no audio, so the only rewarding thing in the game is silent. There is no public path from an entity to the GPU renderer, so the engine's real renderer is the one a game cannot reach. And view() has no const overload, so no system in this engine can say that it only reads. Each of those is now named, dated and pointed at the module that owns it — at hour 62 rather than hour 434.

Module 5 is complete. Twelve lessons ago engine was the name of an executable; it is now a library with a public API, an application layer, a logger, handles, an asset store, an ECS, a transform hierarchy, a camera, an input map, a debug drawer, a debug UI — and a game that uses all of them and nothing else.

Which makes the next thing the right next thing. Look again at the arena: the floor is matte because a specular term revealed the triangulation of a 14-metre quad, and the pillars are almost black on the side facing you. Both of those are shading, and Module 6 opens by explaining that the single largest error in every picture this engine has ever produced is not the shading model at all. It is that the numbers have been added up in the wrong space.
