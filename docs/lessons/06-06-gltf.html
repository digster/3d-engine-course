Module 6 — Advanced Rendering · Lesson 6.6

glTF 2.0 Loading

Lesson 3.5 wrote an OBJ parser by hand, three hundred lines of it, and that was the right call — OBJ is six keywords of text and writing it taught the index problem, fan triangulation and vertex unification. This lesson does the opposite and takes a library, and the interesting part is why the two answers differ. It is not that glTF is harder. It is that glTF is a container, and the hard part of a container is byte offsets. What the format gives back is the thing OBJ never could: materials that mean something — base colour, metallic and roughness, in physical units, which are precisely the four numbers Lesson 6.4 built microsurface out of. Along the way this lesson settles a claim the engine has been carrying, unverified, since 6.4.

1The Problem: A Format Nobody Hand-Writes

Open assets/torus.obj in a text editor and you can read it. Lines beginning v are positions, vt are texture coordinates, f are faces. If a model came out wrong you could find the bad line by eye. That readability is not incidental — it is why Lesson 3.5 could write a parser for it in an afternoon and learn something from every line.

Now try to get a model out of Blender, or Maya, or Substance Painter, or Sketchfab, or a photogrammetry scanner, or any asset store on the internet. You will be handed a .glb. Open it in a text editor and you will see the four bytes glTF followed by a screenful of mojibake.

That, on its own, is not an argument for anything. Plenty of binary formats are worth writing a reader for. The argument is in what the two formats are describing, and it is worth looking at before writing a line of code.

An OBJ file is a bag of triangles. It has exactly one thing in it and the thing has no structure: no placement, no hierarchy, no notion that this run of faces is the windscreen and that one is the bonnet. It has a usemtl keyword, and usemtl names a string that OBJ cannot itself define — you are supposed to go and find a .mtl file, in a format nobody agrees about, whose parameters (Ns, Ks, illum) belong to a lighting model from 1992.

A glTF file is a scene. There is a node tree with transforms; each node may hold a mesh; each mesh is a list of primitives; each primitive names a material out of a table the file itself defines, in units that mean something. Loading one does not produce a mesh. It produces several objects, in several places, wearing several materials.

Why this lesson is here, and here specifically

Module 6's curriculum puts glTF after the PBR arc rather than before it, and after Lesson 6.5's material system, and both orderings are load-bearing.

Before 6.4 there was nowhere to put a metallic-roughness material: the engine's surface description was a specular colour and a shininess, and importing physical values into it would have required a fitted conversion curve — a guess, applied to every asset forever. Before 6.5 there was no material type at all, so the loader would have had to invent one, which is exactly the failure 6.5 diagnosed in ecs_swarm.

Coming after both, the import is a copy. That is what it feels like when the parameters were derived rather than chosen.

2Write It or Take It: The Test

This course has now made the call four times, and it is worth writing down the rule it has actually been using, because it is not the rule people usually state.

The usual rule is "is it hard?" That rule is useless here. The software rasterizer was hard and we wrote it. The ECS was hard and we wrote it. Perspective-correct interpolation is subtle enough that most people get it wrong once, and we derived it.

The rule this course actually uses

Is the hard part the subject?

If the difficult, time-consuming, error-prone core of the problem is a thing you came here to learn — geometry, transforms, shading, memory, architecture — write it. If the difficult core is a thing from a different discipline that happens to stand between you and the subject, take the library and understand what you took.

Run the four decisions through it:

The four library-or-hand-roll decisions this course has made, and the hard part of each
ProblemThe hard partIs it the subject?Verdict
OBJ parsing (3.5)unifying v/vt/vn triples into vertices Yes — that is the index problemwrite it
PNG decoding (4.7)DEFLATE, five filter modes, interlacing, palettes No — compressionstb_image
Debug UI (5.11)text layout, input routing, focus and capture No — four other disciplinesDear ImGui
glTF parsing (here)strided, typed, optionally-sparse views into buffers No — byte offsetscgltf

The last row deserves the detail, because "byte offsets" sounds like something you could knock out in a morning. Here is what a single POSITION attribute actually is.

An accessor says "eight elements, each a VEC3 of float". It points at a buffer view, which says "bytes 0 through 96 of buffer 0, and by the way they might be interleaved with two other attributes at a stride of 32". The buffer view points at a buffer, which might be an external .bin file, a base64 data: URI embedded in the JSON, or a binary chunk glued onto the end of a .glb.

And every one of the accessor's fields is a choice. The component type may be float32, uint8, uint16, int8 or int16. Any of the integer ones may be normalized, meaning the value is a fixed-point fraction rather than an integer. The data may be tightly packed or interleaved. And the accessor may be sparse, which means the values you want are a base array plus a patch list of index/value pairs applied on top.

Multiply those out and there are roughly forty legal encodings of the same eight positions, every one of which some exporter somewhere emits. A loader that handles only the ones you happened to test is worse than no loader at all, because it fails on a customer's file rather than on yours. cgltf_accessor_read_float is one function that collapses the whole matrix, and writing our own version of it would teach byte offsets, not rendering.

Why cgltf and not tinygltf

Both are approved by this course's conventions. cgltf is one C header with no dependencies. tinygltf is C++ and pulls in a JSON library and stb — and we already have stb, pinned at a different commit, so we would end up with two copies of stb_image in one binary. That is a diagnosable problem, but it is a problem we can decline to have.

cgltf also matches the shape we already use: header-only, PRIVATE to exactly one translation unit, wrapped behind our own types. Look at engine/CMakeLists.txt and you will see the same three lines stb got, with the same justification — the dependency stops at the library boundary, so swapping the glTF library is a one-file change.

3The Anatomy of a glTF File

Before writing the loader it is worth reading a whole file, in full, small enough to fit on a page. Here is assets/cube.gltf — generated by scratch/make_gltf_assets.py, which this course ships so that no third-party geometry is needed and every number below is reproducible.

Read it top-down and it is a chain of indirections, every link of which exists for a reason:

  • scene → nodes. The file may contain several scenes and a default; a node may have children. This is a tree, and a node's world transform is the product down from the root.
  • node → mesh → primitives. A mesh is a name for a group; a primitive is a draw. The split exists because one logical object usually needs more than one material, and a material is per-draw.
  • primitive → material, by index into the file's own table. Two primitives naming index 0 are the same material and must end up as one.
  • material → texture → image → sampler. Three levels for what feels like one thing, and they are three because the same image is legitimately read two ways in one frame (clamped for a decal, repeated for a floor). Lesson 3.9 made exactly this argument about texture_binding being a pair; here is the format agreeing.
  • attributes → accessors → buffer views → buffers. Figure 2.
Those numbers are GLenum values, and that is history showing through

"mode": 4 is GL_TRIANGLES. 9729 is GL_LINEAR. 33071 is GL_CLAMP_TO_EDGE. glTF was designed as a transmission format for WebGL, and its enumerants are literally OpenGL's.

Ours are SDL_GPU's, which is why filter_of and address_of in the loader are switches and not casts. A cast would compile and would be silently wrong for every value.

The .glb form is the same JSON with the buffer glued on. Twelve bytes of header (glTF, a version, a total length), then chunks: a JSON chunk and a BIN chunk, each with its own length prefix. Both chunks are padded to a four-byte boundary — and the padding byte differs, which is a detail worth knowing because it bites people: JSON pads with spaces so the chunk stays parseable text, BIN pads with zeros. A zero byte inside the JSON chunk is a parse error in most readers.

Our loader never has to care which form it was handed. cgltf sniffs the first four bytes, and load_gltf takes a path either way. verify_66 §C asserts that shapes.glb was detected as binary and cube.gltf as text, from the same call with no flag.

4Four Conventions, Three of Which Agree

Here is the part of importing a format that actually goes wrong. Not the parsing — the parsing either works or throws an error you can read. What goes wrong is the conventions, because a convention mismatch produces a picture that is plausible.

A cube with its z axis negated still looks like a cube. A model with its texture flipped vertically still looks textured. A mesh with its winding reversed still draws, until the day you turn on back-face culling and half of it vanishes. Every one of those failures survives review, because the reviewer is looking at a picture and the picture is fine.

So before writing any conversion code, we check. Four questions, and the answers come out of the specification rather than out of experiment.

Handedness. glTF §3.5 says, verbatim: "glTF uses a right-handed coordinate system. glTF defines +Y as up; the front side of a glTF asset faces +Z." Our world space (the Conventions page, §2) is right-handed, Y-up, −Z forward. The axes are identical. There is no conversion.

That is not luck. It is Lesson 2.6 having argued the choice rather than picking one, and it is worth appreciating how easily it could have gone the other way: FBX and 3ds Max are Z-up, Unity is left-handed, Unreal is left-handed and Z-up. Any of those would have cost a basis change here — and a basis change that mirrors, which reverses winding, which then needs a second correction, which is how importers acquire the reputation they have.

Winding. glTF: counter-clockwise is front-facing. This course, Conventions §7: counter-clockwise is front-facing. No index reversal.

Texture origin. This is the one that catches people, and it catches them in the opposite direction from the one they expect. glTF §3.9.3: "The origin of the texture coordinates (0, 0) corresponds to the upper left corner of a texture image." That is engine::texture's convention exactly (Lesson 3.9, which quotes SDL_GPU's header for the same rule).

The trap: mesh_import::flip_uv_v defaults to true

OBJ puts (0,0) at the lower left, so Lesson 3.9 established that the import step flips v, and the default in mesh_import is true because every mesh this engine had ever loaded was an OBJ.

Apply that flag to a glTF and every asset comes in upside down — for everyone who left the default alone, which is everyone. The flip belongs to the FORMAT, not to the caller's preference. So asset_store::load_model takes no import settings at all, and the header says why in as many words.

verify_66 §B asserts vertex 0's uv arrives as (0.0, 1.0), exactly as the file wrote it. If anything had flipped it we would read (0.0, 0.0).

Asset facing. The fourth row is the one that differs, and the useful thing about it is that it is not a conversion. glTF says an asset's front faces +Z; our camera looks down −Z. So a model dropped into the world unrotated presents its back to you.

That is a fact about how content is authored, not about how numbers are stored. The fix is a yaw on the object. Putting it in the loader — negating x and z, say — would also mirror the geometry, which turns every asymmetric model into its own reflection and reverses every triangle. Two wrongs, and the second one hides the first.

The receipt

engine/src/gfx/gltf.cpp contains zero conversion code. No negated coordinate, no swapped axis, no basis matrix, no 1 - v. The three floats of a position are copied into a vec3 in the order they were written.

verify_66 §B asserts it bit-exactly: vertex 6 of the loaded cube is (+0.5, +0.5, +0.5), and every one of the eight positions matches k_cube_vertices to the last bit — no tolerance, because every coordinate in the file is exactly representable.

And now a file arrives saying baseColorFactor = (1.00, 0.71, 0.29) with metallicFactor = 1, and f0_of returns (1.00, 0.71, 0.29) verbatim while diffuse_albedo_of returns exactly black. verify_66 §D asserts both. The engine was already speaking the format's language before it had ever read the format.

The one number in a glTF material that everybody gets wrong

The factor is linear. The texture is sRGB-encoded. They are multiplied together after the texture is decoded.

So gltf_material_desc::base_colour is a linear_rgb and there is no to_linear call anywhere near it — while material::tint is encoded, because Lesson 6.5 decided a tint is authored data that decodes at the input edge. The one conversion in the whole importer therefore runs in the direction nobody expects: linear → encoded, in load_model.

Get it backwards and gold's green channel comes in at 0.4624 instead of 0.7100, every imported asset is darkened by the gamma curve, and the result looks like a plausible lighting problem for years. verify_66 §D asserts the 0.71 and prints the 0.4624 beside it, so the failure mode is in the test output rather than in somebody's memory.

One more thing the file says that we can honour immediately: doubleSided. Lesson 6.5 split back-face culling into two questions — is this mesh closed?, a fact about the geometry that validate() answers, and do we want it culled?, an intent the caller supplies. doubleSided is exactly that second half, arriving from the person who authored the asset. cull_of(mesh_is_closed, want_two_sided) already had the parameter waiting.

6The ⚠ VERIFY, Discharged

Lesson 6.4 shipped this comment, and it has sat in the engine for two lessons:

This is that lesson, so the marker gets discharged. Here is Appendix B's complete model, quoted from the specification:

The claim in the comment turns out to be true in substance and imprecise in a way that matters. mix(a, b, F) is (1−F)·a + F·b, so the diffuse really is scaled by 1 − F(v·h). But the same F scales the specular up, and our cook_torrance_specular already carries it. Reading "the glTF reference uses 1 − F(v·h)" as a statement about the diffuse alone misses half the sentence.

Laid out term by term against what Lessons 6.3 and 6.4 derived:

The metallic blend is not even a difference

Look at the fifth row of the figure. The spec lerps two whole BRDFs by metallic; this engine lerps the F0 and evaluates one BRDF (f0_of). Those look like two different models. They are the same model, and the reason is one line of algebra.

Schlick's approximation is affine in F0. Write w for (1 − |v·h|)5:

\[ F(f_0) \;=\; f_0 + (1 - f_0)\,w \;=\; f_0\,(1 - w) \;+\; w \]

That is a straight line in f0, so lerping the inputs and lerping the outputs commute. Work the spec's specular coefficient through, writing m for metallic and c for the base colour:

\[ \begin{aligned} (1-m)\,F(0.04) + m\,F(c) &= (1-m)\big[0.04(1-w) + w\big] + m\big[c(1-w) + w\big] \\ &= \big[(1-m)\,0.04 + m\,c\big](1-w) + w \\ &= F\big((1-m)\,0.04 + m\,c\big) \end{aligned} \]

And (1−m)·0.04 + m·c is exactly what f0_of computes. The specular halves of the two models are not close; they are the same expression.

Measured, because a derivation that has not been run is a conjecture

verify_66 §E evaluates both routes over 21 metallic values × 11 base colours × 21 view angles = 4,851 points. Worst difference: 1.192 × 10−7, which is float rounding and nothing else.

So f0_of is not an approximation of the spec's mix. It is the spec's mix, rearranged into one Fresnel evaluation instead of two.

The one factor that does differ

Everything reduces to a single term. The spec applies one Fresnel crossing, at the half vector; this engine applies two, at the light angle and the eye angle:

\[ k_d^{\text{glTF}} = 1 - F(v \cdot h) \qquad\text{against}\qquad k_d^{\text{ours}} = \big(1 - F(n \cdot l)\big)\big(1 - F(n \cdot v)\big) \]

Lesson 6.4 §7 gave the physical argument for two: light crosses the interface on the way in and on the way out, and each crossing reflects its own Fresnel fraction. The one-sided form describes what got in and says nothing about the light that fails to get out, so at grazing angles it lets out more than went in.

How much does that matter in practice? That is the question two lessons never asked, and it is the number verify_66 §E exists to produce. Sweeping the light and eye over a quadrant on shapes.glb's own red plastic:

That first row explains why the imprecision survived two lessons: the difference hides in the middle of every surface and only appears at the rim, which is exactly where nobody checks.

So which do we ship?

The specification answers this itself, in two places, and the answers point the same way.

On variation, §3.9.6: "Implementations of the bidirectional reflectance distribution function (BRDF) itself MAY vary based on device performance and resource constraints." The BRDF is explicitly not the conformance surface — the material parameters are.

On correctness, Appendix B's "Complete Model": "In a physically accurate light simulation, the BRDFs MUST follow some basic principles: the BRDF MUST be positive, reciprocal, and energy conserving."

The resolution, and it is not the one Lesson 6.4 expected

Lesson 6.4 kept half_vector around on the assumption that asset interchange might one day require it. It does not. The spec permits the variation outright, and the property it actually requires — energy conservation — is the one two_crossing has at 0.9255 and half_vector lacks at 1.3395.

So the engine loads glTF materials and shades them with its own coupling, and is conformant in doing so. half_vector stays in the enum, named, measured, and selectable — because it is what the student will find in every engine they read next, and because 6.3's two geometry terms set the precedent: a choice you can run beats a choice you can read about.

And the design question 6.5's rule turns into a real one

The obvious alternative is to let each material carry its own coupling, so an imported glTF could be shaded the spec's way and everything else ours.

Lesson 6.5's membership rule refuses it, and the refusal is instructive: can this be a number in a buffer? A coupling is a branch in the shader. Two objects differing in it need two pipelines and a sort between them — it is pipeline state by definition, so it does not belong on material however convenient that would be.

Which leaves exactly one honest place for it: a renderer-wide choice, measured and documented. That is where it is.

7Where a Reference Stops Being a String

Now the architecture question, and it is the one that decides whether this code is still useful in Module 9.

A glTF material says "uri": "uv_grid.png". A engine::material holds a texture_handle. Somewhere between those two a string becomes a handle. Where?

The tempting answer is "in the loader" — parse_gltf could take an asset_store& and hand back finished materials. It would be fewer types and fewer lines.

Three things that answer would cost, and none of them is style

1. The parser could no longer be tested without a filesystem. Lesson 3.5 split parse_obj from load_obj for exactly this reason and §8 of that lesson used the split to test a dozen malformed inputs from string literals. A parser that needs a search path needs a disk.

2. Module 9's asset cooker could not use it. An offline importer runs at build time and writes its output to a cache. A handle is meaningless outside the pool that issued it, so a parser that returns handles produces output that cannot be serialised.

3. The policy would end up in two places. "Is this the same image we already loaded?" and "where do images live?" are questions asset_store already answers for OBJ and PNG. A second answer inside the glTF loader is a second answer that will eventually disagree.

So the layers are as the figure shows them. gltf.cpp turns bytes into descriptions — a gltf_material_desc holds a std::string base_colour_uri and an int material index, and knows nothing about pools, handles, caches or search paths. asset_store::load_model turns descriptions into handles. And the renderer turns a handle into a pointer, once per draw, through bind_albedo — which is Lesson 6.5's rule, unchanged.

8Implementation

8.1 — cgltf, wired in the same way stb was

Three lines in the root CMakeLists.txt and one in the engine's, matching the shape Lesson 4.7 established for stb_image. Pinned to a tag this time, because cgltf has releases — stb has none, which is why it had to be pinned to a commit.

PRIVATE is the whole of the boundary argument, and it is checkable rather than aspirational: no demo can include <cgltf.h>, because the directory is not on its include path. Swapping to tinygltf would be a one-file change.

One macro, in exactly one place

#define CGLTF_IMPLEMENTATION before the include compiles the parser into that translation unit. Putting it in a header would compile a copy into every file that included it and then fail to link on the duplicate symbols — which is the good outcome. The bad one is a build system that quietly picks one.

Same rule as STB_IMAGE_IMPLEMENTATION in image.cpp. Worth noticing that the whole cgltf implementation compiled clean at -Wall -Wextra on the first try, which stb did not — and that the macro is what confines the difference.

8.3 — The ceiling, and why it is reported rather than fixed

mesh_data::indices is std::uint16_t, decided in Lesson 2.12. So a primitive can name at most 65,536 distinct vertices.

OBJ never made this fire, because the files this course ships are small. glTF will, because real exported assets routinely exceed it — a single .glb out of Blender may hold one 200,000-vertex primitive.

Why a counter and not a narrowing cast

The lazy version is static_cast<uint16_t>(index) and let it wrap. That version renders: you get a spray of triangles connecting the wrong corners of the model, which looks like a corrupt file rather than like a loader limit, and there is nothing anywhere saying what happened.

Widening the index type is a real answer and it costs real bytes on every mesh in the engine. Splitting the primitive is the other real answer and it costs real code. Both are exercises; neither is a thing to guess at inside a loader. What the loader owes you is skipped_too_large = 1, max 197,346 — a number you can act on.

8.4 — Walking the node tree

A glTF scene is a forest, so the walk is a recursion, and there is one decision inside it worth arguing.

The transform is not baked into the vertices. A loader that bakes produces a scene that can never be re-parented, instanced or animated, and the loss is silent — the picture is identical on frame one and the capability is simply gone. Lesson 5.9 built a transform hierarchy precisely so that placement stays data, so the geometry is what the file said and world_from_local is what the node tree said, kept apart.

verify_66 §C checks both halves. shapes.glb's "group" node translates by (1, 0, 0) and its child "gold octahedron" by (0, 2, 0), so the octahedron's world translation must be (1, 2, 0) — a product down the tree, not the local transform. Two levels deeper, the tetrahedron lands at (1, 3.5, 0). And the octahedron's own vertices still top out at y = 0.60 rather than 2.60, which is the assertion that nothing was baked.

A layout agreement worth noticing

cgltf_node_transform_world writes sixteen floats column-major, which is exactly mat4's own storage (Lesson 2.5). So to_mat4_column_major is a copy and not a transpose.

Three independent decisions landed on one layout: glTF stores matrices column-major because its matrix property says so; mat4 is column-major because its columns are where the basis vectors land; and HLSL constant buffers want the same, which is why Module 4 uploads a mat4 with a plain memcpy. The transpose that catches out every second importer never arises.

8.5 — The bridge that had never been built

Here is a gap this lesson found by walking into it, and it is a good example of a hole that no test could see because no code path crossed it.

The engine has been able to decode a PNG since Lesson 5.3: load_image produces an image_data of RGBA bytes. It has been able to sample a texture since Lesson 3.9: sample(texture, sampler, u, v) returns linear light. Nothing has ever joined them.

Every CPU texture in this engine was generated — make_checker, make_uv_grid — and every loaded image went straight to the GPU as bytes through gpu_texture::create_sampled. Two complete halves with no middle. glTF is what forces the join, because a material names an image file and the software renderer has to be able to sample it.

It is a channel shuffle, not a memcpy

image_data::pixels is R, G, B, A in that byte order, as stb hands it over. texture stores Uint32 in ARGB8888 — the framebuffer's own format (Lesson 1.5) — which on a little-endian machine is the bytes B, G, R, A.

Copy the buffer wholesale and red and blue swap, which is the single most recognisable wrong-looking texture there is. Writing it through pack_argb means the memcpy version is not even expressible. verify_66 §F asserts texel (3,3) comes out 0xFFDE463C and prints 0xFF3C46DE beside it as the shape of the failure.

There is no vertical flip in that loop, and there must not be: image_data stores the file's rows top-first (5.3) and texture puts row 0 at the top (3.9). Those are the same convention. The v flip that OBJ needs lives in the geometry import, which is the only place it can be decided from — it is the format of the mesh that disagrees about which way v points, not the image.

9Textures and Materials Become Assets

Lesson 6.5 put texture_pool in texture.hpp and explicitly kept it out of asset_store, with this reasoning:

That grounds expire here, in the most direct way possible: a glTF material arrives naming an image on disk, two materials in one file routinely name the same one, and "load it once and hand out the same reference" is precisely the store's job description. So the answer to 6.5's deferred question is yes, and the interesting part is what had to be added around a pool that did not itself change.

9.1 — A texture is a DERIVED asset

A mesh is loaded. An image is loaded. A texture is made from an image — and Lesson 5.5 already had a name and a mechanism for that shape.

Everything about resolving a name against the search path, reading bytes, decoding them and counting the read is load_image's job and is not repeated. That is what makes "the same image loaded twice is decoded once" true for textures as well, without load_texture knowing anything about it.

derive_texture records an edge — image → texture — and that edge is the whole reason the function exists rather than being a plain insert:

A dependency edge, not a reference count

Lesson 5.5 refused reference counting at length: a handle is a value, four bytes, trivially copyable, and refcounting requires copying to have a side effect, which costs every property Lesson 5.4 was written to obtain.

A derivation edge is different in kind. Nobody outside the store can hold one. The store made the texture, nobody asked for it by a name of its own, and it has no independent reason to exist — so unloading the image takes it, transitively, and the rule is enforced by a private member rather than by a contract.

verify_66 §F unloads uv_grid.png and gets 2 back: the image and the texture built from it. The material's handle is then stale, which is not a crash — bind_albedo returns an unbound binding and the surface falls back to its tint. Lesson 5.4's bargain, arriving at last with a real dependency behind it.

One detail that is easy to get wrong and silent when you do

The cascade must remove the texture's name entry as well as the texture. Miss it and find_texture("uv_grid.png") keeps handing out a handle to a slot the pool has already recycled.

It would not crash — 5.4's generation counter catches it and contains() returns false — so the symptom is an object that silently loses its texture some arbitrary number of frames later. Correct behaviour, and still a bug worth not having. verify_66 §F asserts the name entry went.

One more thing about the edge lists, worth a sentence because the tempting shortcut is wrong. There are now two of them — mesh_derivations_ and texture_derivations_ — rather than one generic list of {uint32, uint32} pairs. A single untagged list would compile, and would happily resolve a texture's handle bits against the mesh pool: Lesson 5.4's aliasing failure in a new costume. Two lists, two types, no tag.

9.2 — A material is a named asset with no file

Materials get the other half: insert_material(name, m), find_material(name), unload_material(h), and a material_by_key_ map.

There is deliberately no load_material, and there never will be, because a material is not a file. It arrives as part of one. But naming it anyway is what buys the property glTF needs: a file whose four primitives share one material must produce one material, and two loads of the same file must not produce eight.

The names are derived and deterministic, which is what makes the cache work without a second map:

The derived names asset_store::load_model stores a model's parts under
PartStored asWhy
primitive i"shapes.glb#2" ordinal, because a primitive has no name of its own
material "gold""shapes.glb:gold" namespaced — two models may both call a material "Metal"

verify_66 §F loads cube.gltf twice and asserts the second call returns the same handles with files_read unchanged at 2. It also asks the store directly for uv_grid.png and gets back the texture the material already holds — one decode, one copy, however many materials name it.

Why models_loaded is its own counter

One model file reads many files: the .gltf, its .bin, and one per texture. cube.gltf reports models_loaded = 1 and files_read = 2.

Conflate the two and "did the cache work?" becomes unanswerable, because you can no longer tell one cached model from two uncached textures. A counter that measures two things measures neither.

10The One Thing We Cannot Represent

Every importer has a conformance gap. What separates a good one from a bad one is whether the gap is reported.

Ours is one sentence of the specification, §5.19.4: "If both factors and textures are present, the factor value acts as a linear multiplier for the corresponding texture values."

Our material does not multiply. Lesson 3.9 established that a bound albedo image replaces the tint, on the grounds that both of them are the albedo and a surface has one albedo. That rule is defensible and it is what the rasterizer implements — and it disagrees with glTF whenever a material has a base colour texture and a non-white base colour factor.

Note precisely how narrow that is. It is not "the factor". A material with a coloured factor and no texture imports exactly; a material with a texture and a white factor imports exactly, because multiplying by white is replacing. The gap is only the combination.

Where a conformance gap belongs

At the only point that knows both halves. The parser sees the factor and the URI but not whether the image resolved; the renderer sees a bound texture but has long since lost the factor. load_model is the one place holding both, so the warning lives there and the count travels back in model_load.

And it is a count as well as a log line, because a log line scrolls past and a number can be asserted. verify_66 §F asserts factor_texture_conflicts == 0 for shapes.glb — where the coloured material has no texture — which is a test of the detector as much as of the asset.

Making them multiply is a one-line change in raster.cpp and a matching one in scene.frag.hlsl. It is Exercise 2, and it is deliberately not made here — because the demo scene's textured surfaces carry a non-white tint, so the change would move the reference render, and this lesson's whole claim is that adding a format does not move the picture.

Named, not fixed: two textures glTF offers that we do not read

metallicRoughnessTexture and normalTexture are counted in gltf_material_desc (wants_metallic_roughness_texture, wants_normal_texture) and not loaded.

The reason is one concrete thing rather than lack of time: they are linear data in an image, and texture stores sRGB-encoded texels because sample decodes on read (3.9). A roughness map read through an sRGB decode is wrong by the gamma curve everywhere except 0 and 1. Fixing that means giving a texture a colour space — which is Lesson 6.7's problem, because normal maps need exactly the same thing.

The factors import completely, so a material's metallic and roughness are correct; what is missing is per-texel variation. This is the ninety-percent picture, and the missing ten percent has a lesson number.

12Build & Run, and What You Should See

The first configure after this lesson fetches cgltf, which is one header and takes a second.

The picture

--model cube.gltf is the one to look at first, because three separate things are being asserted by one image:

  • The arrow points up. uv_grid.png is an orientation chart with a mark in its top-left corner and an arrow along +v; a checkerboard could not tell you this, because a checkerboard is symmetric under every flip. The arrow pointing up means v was not flipped, which is the trap in §4.
  • There is an image at all. The .gltf said "uri": "uv_grid.png", and the store resolved that against its own search path, decoded it, shuffled the channels and cached it. Every step of that is new this lesson.
  • The highlight has the file's shape. roughnessFactor: 0.4 came out of the JSON and went into microsurface::roughness untouched. Nothing in gltf_view types a colour, a shininess or a specular value.

Then shapes.glb, which is four primitives, four placements from a three-deep node tree, and four materials — three from the file plus the specification's default on the plinth, which names none.

What you will actually see, and why it is right

The metals are nearly black, except where they are pure white. The gold octahedron reads gold at some orbit angles and clips to white at others; the silver cube is dark from most directions.

That is not a bug and it is not the importer. A conductor has no diffuse lobe — diffuse_albedo_of returns exactly black at metallic = 1, which Lesson 6.4 derived — so the only light leaving it is the mirrored part. A metal with nothing to reflect but one directional light therefore has exactly two states.

And the bright state is very bright. Evaluating the BRDF in the mirror direction under this engine's reference irradiance:

A polished metal's highlight is sixty-four times what the framebuffer can hold, so to_encoded clamps it and you get a white facet. That number is the quantitative case for two lessons still to come: image-based lighting (6.15) gives a metal something to reflect other than one point light, and a tonemapper (6.12) gives the highlight somewhere to go. The materials in the asset are chosen at defensible values (0.40 and 0.45 — brushed, not polished) so the clipping is a facet rather than an object, and --pose exists so you can sweep past it and watch.

The claim this lesson has to make

58 checks, 0 failures, debug and release. verify_45 through verify_65 all still green.

And the reference render is byte-identical, hash E917C06C — fifteenth lesson at that hash. A whole second asset format, a texture pool inside the store, a material cache and a channel shuffle, and not one pixel moved. Loading a new format adds a path; it must not move the existing picture.

13Common Pitfalls & Debugging

Symptom, cause and fix for the failures this lesson's code can produce
SymptomCauseFix
The model loads, but every texture is upside down. You applied flip_uv_v. It is correct for OBJ and wrong for glTF; the two formats disagree about where (0,0) is. Do not flip. load_model takes no import settings for this reason. Check with the uv grid, not a checkerboard — a checkerboard cannot show you.
missing_buffer on a file that opens fine in a viewer. A .gltf names an external .bin, and it was not copied alongside — or the base directory handed to parse_gltf lost its trailing separator. Copy both files. The base dir must end in /; load_gltf derives it with find_last_of("/\\") and keeps the separator.
The model draws as a spray of triangles connecting the wrong corners. An index was narrowed to uint16 and wrapped. Check report.skipped_too_large and report.max_primitive_vertices. Do not cast — the loader refuses the primitive and says so.
Every imported asset is noticeably darker than in a reference viewer. to_linear applied to baseColorFactor. The factor is already linear; only the texture is encoded. Remove it. Gold's 0.71 becoming 0.4624 is the fingerprint.
Textures come out with red and blue swapped. memcpy from image_data::pixels into texture's texels. RGBA bytes are not ARGB8888 words. pack_argb, per texel. It is the only spelling that cannot get this wrong.
A cube imports with 36 vertices when the file wrote 8. Not a bug. The primitive had no NORMAL, so flat normals were generated, and flat shading forces one vertex per face-corner. Nothing — but know it, because it makes an index-for-index comparison against the source impossible. This is the failure the first run of verify_66 §A produced, and the fix was to make the test asset ship normals.
A model is invisible, or you are looking at the inside of it. glTF says an asset's front faces +Z; our camera looks down −Z. Yaw the object. Do not negate coordinates in the loader — that mirrors the geometry and reverses every triangle, so you fix the facing and break the winding.
Half a model vanishes once back-face culling is on. The primitive is an open shell, and glTF is full of them. cull_of(validate(mesh).closed(), desc.double_sided). The mesh supplies the fact, the file supplies the intent (6.5).
An object silently loses its texture some frames after a level change. An image was unloaded and the derived texture's name entry outlived it, so find_texture handed out a recycled slot. Erase the name in the cascade. It does not crash — 5.4's generation counter sees it — which is exactly why it takes so long to notice.
A duplicate-symbol link error mentioning cgltf_parse. CGLTF_IMPLEMENTATION defined in more than one translation unit, usually because it reached a header. Define it in gltf.cpp and nowhere else. This is the good failure; the bad one is a build that picks one silently.

14Exercises

14.1 — Break the ceiling on purpose guided

Edit scratch/make_gltf_assets.py to emit a grid mesh with more than 65,536 vertices (a 260 × 260 lattice will do it), and load it. Confirm you get gltf_status::too_many_vertices and a max_primitive_vertices that names the real number.

Then make it work, twice. First widen mesh_data::indices to uint32_t and measure what that costs on torus.obj: index bytes before and after, and total mesh bytes. Then revert, and instead split the primitive into chunks of 65,536 with a vertex remap per chunk.

Hint. The split is the harder and more useful one, and the awkward part is that a triangle's three indices must land in the same chunk — so you cannot cut on a vertex boundary, you have to walk triangles and emit vertices on demand. That is the same "unify as you go" loop parse_obj already contains, run backwards. Note which answer a real engine picks and why it depends on the target: SDL_GPU supports both index widths, mobile GPUs used to prefer 16.

14.2 — Make the factor multiply guided

Close this lesson's conformance gap. In raster.cpp's lit path, multiply the sampled albedo by the interpolated vertex colour instead of replacing it; do the same in shaders/scene.frag.hlsl. Then run verify_48 §F to confirm the CPU and GPU still agree, and verify_66 to see the golden move.

Hint. It will move — the demo scene's textured floor carries an amber tint, so the change is visible. Re-baseline properly, the way Lesson 6.4 did: report the number of pixels that moved, the direction they moved in, and the old hash beside the new. "It looks fine" is not a re-baseline. Then argue with yourself about whether the engine should adopt glTF's rule or keep 3.9's, and write the argument down — both are defensible and the point is that you can say which you chose.

14.3 — Frame from the accessors engine challenge

gltf_view computes its camera distance by walking every vertex. The specification requires min and max on a POSITION accessor — precisely so a viewer does not have to. Surface those bounds through gltf_primitive, transform them by the node matrix, and frame from them instead.

Hint. The subtlety is that transforming an axis-aligned box by a rotation and taking the corners' bounds gives you a larger box than the geometry needs — the AABB of a rotated AABB is not the AABB of the rotated geometry. Measure the difference on shapes.glb. This is the same conservative-bounds problem Lesson 6.16's frustum culling has to live with, and meeting it here first is the point of the exercise.

14.4 — Strips and fans open

build_geometry counts and skips any primitive that is not cgltf_primitive_type_triangles. Convert TRIANGLE_STRIP and TRIANGLE_FAN into triangle lists at import so those files load.

Hint. A strip of n vertices is n − 2 triangles, and the winding alternates: triangle i is (i, i+1, i+2) for even i and (i+1, i, i+2) for odd. Get that backwards and every other triangle is back-facing, which is invisible until culling is on — so test it with validate()'s reversed_edges rather than by looking.

14.5 — Prove the coupling difference on screen open

§6 measured the two diffuse couplings as 1.036× apart at normal incidence and 5.62× apart at 88°. Make that visible: render shapes.glb's red tetrahedron twice, once with each coupling, and difference the two framebuffers.

Hint. fill_style has no coupling field, and adding one is the exercise's real content — it is pipeline state by 6.5's rule, so think about where it can legitimately live and what that implies about a scene mixing the two. Then predict, before you run it, where in the image the difference will be largest. If your prediction is "the middle of the bright face", re-read §6.

15Recap & Next

The engine can now read the format the industry actually ships. Concretely, it gained:

  • A glTF 2.0 loader, text and binary, handling node hierarchies, multi-primitive meshes, external and embedded buffers, and the full metallic-roughness material model — behind our own types, with cgltf confined to one translation unit that no demo can reach.
  • Textures as assets. load_texture resolves, decodes, shuffles and caches; the result is a derived asset whose lifetime is bound to its image, so unloading the image takes it.
  • Materials with identity. Named, cached, shared — so a file's four primitives sharing one material produce one material, and loading the file twice produces none extra.
  • to_texture, the twelve-line bridge between "decoded a PNG" and "can sample it" that should have existed since Lesson 5.3 and did not, because no code path had ever crossed the gap.
  • A settled question. The ⚠ VERIFY from 6.4 is discharged with a citation and a measurement: our BRDF differs from glTF's reference in exactly one factor, the specification permits the variation explicitly, and the property it does require — energy conservation — is the one our form has.
  • A conformance gap that reports itself, rather than one you find out about from an artist.

And three things this lesson deliberately did not do, each with a reason and a lesson number: it did not read the metallic-roughness or normal textures (they are linear data and texture has no colour space — 6.7); it did not make the base colour factor multiply (it would move the golden — Exercise 2); and it did not widen the index type (it costs bytes on every mesh — Exercise 1).

The through-line, if you take one thing from this lesson

Almost none of the work here was parsing. It was deciding what agrees with what — four conventions, six BRDF terms, three material parameters — and the answer was overwhelmingly "nothing to do".

That is what it feels like to import into an engine whose conventions were argued rather than picked, and whose parameters were derived rather than tuned. An engine with a Z-up world and a hand-fitted gloss curve would have needed a basis change, a winding fix and a conversion table here, every one of which is a place for a plausible-looking bug to live forever.

Next: 6.7 — Normal Mapping and the TBN Derivation. Every surface in this engine is as flat as its triangles, and the fix is to perturb the normal per pixel from an image — which needs a per-vertex tangent frame, derived from the uv parameterisation, and it needs the thing this lesson deferred: a texture that knows it holds linear data rather than colour. A normal map read through an sRGB decode is wrong everywhere except at its extremes, and it looks almost right, which is the worst possible way to be wrong. glTF has been telling us about normalTexture the whole time; 6.7 is where we listen.
