Dear ImGui and the Debug Draw System

Two subsystems, and they are one lesson because they are one thing: the tooling. ImGui is the tooling interface; debug draw is the tooling in the world. This is the first library in the course whose vocabulary we let through the engine's public boundary, and the argument for that is not "it is hard" — the rasterizer was hard and we wrote it. Along the way, a debug-draw header that has been quietly wrong since Module 3 gets the rework it has been owed, and a text field turns out to be the hardest input problem in the engine.

1The Problem

Lesson 5.9 built a transform hierarchy and made a claim about it: a moon's world placement is computed by nobody, because world(moon) = world(planet) × local(moon) is what "relative to my parent" means. The demo has been running ever since with 154 entities in a three-level tree, and you have had exactly two ways to believe that claim — read the code, or read a line of text that says hierarchy 154 rows, 2 roots, 3 levels.

Both are fine. Neither is seeing it. And the difference matters enormously the first time something is wrong, because a count of 154 rows is equally consistent with a correct tree and with a tree in which forty-eight entities are parented to the wrong planet.

We have had the tool to fix that since Module 3. engine/gfx/debug_draw.hpp can draw a world-space line:

Now try to call it from the place that knows about parents. That code is a system: it takes a registry and walks a view. It does not have a framebuffer, it does not have a projector, and — this is the part worth sitting with — it should not have them. The moment you hand a framebuffer to an ECS pass so it can draw a diagnostic line, every caller of that pass needs one too, and their callers, and the "debug feature" has become an architecture.

So the tool exists and cannot be used by the code that needs it. That is a design problem rather than a missing feature, and it has two siblings hiding behind it, which §3 takes apart.

The second half of the lesson comes from the same demo, five lines further down. This is what ecs_swarm has been calling a HUD:

Look at the y coordinates: 6, 20, 34, 48, 62. That is a layout engine, implemented as arithmetic in your head, and it has all the properties you would expect of one. Inserting a line in the middle renumbers everything below it. Nothing can be collapsed, scrolled or sorted. No value can be changed — you can print the light's elevation but you cannot drag it. And every column is aligned by counting spaces in a format string.

Neither of these is a performance problem, and this lesson — like 5.10 — measures nothing. Both are limits on what the code is able to say.

2Why We Do Not Hand-Roll This

2.1 The test, and where the line falls

This course has a rule about third-party libraries, stated in the master prompt and applied four times so far: every dependency arrives with an explicit justification for not writing it ourselves. The rule is easy to state badly. It is not "we write the easy things and buy the hard ones" — we wrote the rasterizer, and a rasterizer is harder than a PNG decoder. The test is:

The test

Is the hard part the subject? If the difficulty is the thing the course is about, we write it, however long it takes. If the difficulty is somewhere else entirely, we take the library and spend the time on the subject.

Apply it to a debug UI. What is actually hard about one? Four things, and they are four different fields:

  • Text. A font rasterizer, an atlas, kerning, and — the moment anybody types a character outside ASCII — shaping. Module 6's text-rendering lesson does this properly, and even that is the drawing — the shaping is a library there too.
  • Layout. Where does the next widget go? What happens when the window is narrower than the label? What are the rules for a table column that wants to stretch? This is the y-coordinate arithmetic above, generalised — and generalising it correctly is an entire discipline.
  • Input routing. Which widget has focus, what happens when you drag from inside one widget to another, what a click means when two windows overlap, how the keyboard moves between fields.
  • Widget state across frames. A slider being dragged is a state machine that spans frames, and so is a text field with a cursor and a selection, and so is a collapsing header that remembers it is open.

Not one of those is graphics, engine architecture, or maths. And a half-built version of all four is worse than useless: it is the tool you stop trusting the first time it misreports a number, at which point you are debugging your debugger.

The numbers make the trade concrete. Dear ImGui's core is 41,385 lines across four files. Its SDL3 backends are another 1,232. Our integration — the file that owns the whole lifecycle — is 182 lines, and you will read all of it in §8.

2.2 What immediate mode actually means

"Immediate mode" gets used as a slogan, so it is worth being precise, because the property it names is exactly why this is the right library for a debug tool rather than merely a convenient one.

In a retained-mode UI — every desktop toolkit, every game-engine editor built on one — you construct objects. A Label, a Slider, a TreeView. They live in a tree, they persist between frames, and your job is to keep them in sync with the world: when an entity is destroyed you must remember to remove its row; when a value changes you must remember to push it to the label. Every one of those "must remember"s is a bug waiting to happen, and the bug's symptom is a UI that shows something that is no longer true.

In an immediate-mode UI there are no objects. There is a function that runs every frame:

There is no Label object holding a stale copy of world_.size(), because there is no object at all — the number is read from the world during the frame it is displayed in. The panel cannot be stale, because there is nowhere for staleness to live. Destroy every entity and the panel says zero on the very next frame, with no invalidation, no observers, and no code that anybody had to remember to write.

The Checkbox line is the same trick running the other way: it takes the address of the program's own boolean and toggles it. The panel is not a second copy of the program's state that must be reconciled; it is a window onto the state itself.

That model has real costs — it rebuilds all its geometry every frame, and it makes animation and complex layout awkward — which is exactly why the rule "tooling only, never gameplay UI" is a binding one in this course rather than a stylistic preference. A game's HUD needs a font the art director chose, a layout that survives translation into German, controller focus, and safe areas on a television. ImGui offers none of that and does not pretend to.

2.3 A public dependency, for the first time

Lesson 4.7 took this project's first non-SDL dependency, stb_image, and hid it completely. Exactly one translation unit includes it; engine::image is our own type; and engine/CMakeLists.txt links it PRIVATE, so a demo can neither see stb nor accidentally start depending on it. The dependency stops at the library boundary. That is what a good wrapper buys.

ImGui gets the opposite treatment, and the reason is not laziness.

Why one was wrapped and the other is not

With stb_image we wrapped a concept — "decode these bytes into pixels" — which is one function and one type. The wrapper is small because the concept is small.

ImGui's value is its vocabulary: Begin, Text, SliderFloat, BeginTable, Checkbox, and several hundred more, each with overloads, flags and an interaction model. A wrapper around that surface is a re-spelling with no content in it — and it has to be re-spelt again for every widget, forever, by somebody who is not the person who wrote the widget.

So demos/ includes <imgui.h> directly and calls ImGui:: functions, and the engine links imgui PUBLIC. Say the cost out loud rather than discovering it later: the engine's public API now contains a second third-party vocabulary, and if ImGui were ever replaced, every panel in the project would be rewritten.

What makes that acceptable is containment. The only code allowed to speak ImGui is tooling code, and tooling code is code that can be rewritten without the game changing behaviour by one pixel. Compare Lesson 5.1 §6 on SDL in our public headers: the same admission, made for the same reason, with the same eyes open.

One more thing the build teaches, because it is a small surprise the first time: ImGui ships sources, not a build. There is no CMakeLists.txt in that repository — deliberately, on its author's part, because the library is a handful of .cpp files and every project wants to compile them its own way. FetchContent_MakeAvailable notices the absence and only populates; the target is ours to declare. Being forced to declare it is how you find out exactly which files you are compiling, which is a better position to be in than the alternative.

imgui_demo.cpp is 11,299 lines of showcase and it is in that list on purpose: ImGui::ShowDemoWindow() is the fastest widget reference in existence, and its source is the documentation — every widget in the window is a few lines away in a file you already have. Drop it when a real game ships.

Note also what is not in the build: engine_set_warnings(imgui). Our -Wall -Wextra discipline applies to our targets and never to somebody else's, for the reason cmake/EngineHelpers.cmake gave in Lesson 5.1 — warnings you cannot act on train you to ignore the ones you can.

3The Rework: Saying and Doing

3.1 Three problems wearing one coat

Back to line3_world(fb, view, pr, a, b, colour). §1 found one problem with it. There are three, they all come from the same root, and they are worth separating because two of them are invisible until later modules.

  1. The caller must be the renderer. Two of the six parameters are renderer state, so only code holding renderer state can call it. §1's collision system, ECS pass and mesh loader are all locked out.

  2. It works on one surface. framebuffer is the software renderer's target. Under surface::gpu — the path Module 4 spent nine lessons building, and the path Module 6 lives on — there is no framebuffer at all. Every one of these calls is simply unavailable there.

  3. A line lives exactly one frame. This one is the most easily dismissed and the most important. A collision normal exists for one simulation step. At 60 Hz that is 16.7 milliseconds on screen. Human visual processing needs something on the order of 250 ms to register that a small thing appeared and vanished — so a single-frame marker for a single-frame event is, for the person the debug drawing exists to serve, invisible.

That third point deserves to be stated as a design principle, because it is the one that justifies building a system rather than adding a function:

The reason debug geometry has lifetimes

The events you most need to see are the ones that happen in a single frame — a contact, a re-parent, a spawn, a raycast hit. Those are precisely the events a per-frame drawing cannot show you. A debug view without lifetimes can only show you state, never events, and it is usually the events you are hunting.

One change fixes all three: separate saying what to draw from doing it. A debug_lines queue holds world-space segments with lifetimes. Anybody can queue. A backend flushes the queue through whatever it has — a framebuffer today, an SDL_GPU render pass in Module 6 — and the queue never learns which.

Notice that the queue makes nothing faster. It removes an argument from every call site, and that argument was the entire reason the caller had to be the renderer.

3.2 The include list is the interface

Here is where the design could quietly fail. It is tempting to put the queue in debug_draw.hpp, which is after all the debug-drawing header. Do that and everything compiles, everything works, and the promise is broken — because debug_draw.hpp includes the framebuffer, the depth buffer, the projector, the viewport and mesh, and C++ include dependencies are transitive.

A physics system that includes it to draw one box compiles the renderer. Not links — that is the linker's business and it is fine — compiles, in every translation unit, forever.

So the rework is two files, and the direction between them is the design:

FileJobIncludesWho may include it
gfx/debug_lines.hpp says what to draw colour, mat4, vec3, <span>, <vector> anybody
gfx/debug_draw.hpp draws it the above, plus framebuffer, depth buffer, mesh, projector, viewport code that already owns a framebuffer

That constraint has one visible consequence in the API, and it is worth defending because it looks like fussiness. wire_mesh does not take a mesh:

mesh lives in gfx/mesh.hpp, which pulls in core/pool.hpp and the whole handle system — none of which a collision routine should compile in order to draw a wireframe. Taking the two arrays costs a caller nine characters (m.vertices, m.indices) and keeps the promise at the top of the file intact. Take the data, not the type is a general move, and this is a clean example of when it earns its keep.

Everything in debug_draw.hpp survives unchanged. It was never wrong as a backend — it was wrong as an interface. So the flush is four lines and reuses six lessons of well-tested clipping:

line3 and line3_world gained a bool return in this lesson, and it changes no pixel: both places that now return false were already return, and both already drew nothing. What is new is that the fact is reported, so a HUD reading queued 152, drawn 151 names a real event — one line went behind the near plane — instead of printing the queue size twice. A number in a HUD is a checkable claim, and a claim the code cannot actually back is worse than no number at all.

4Lifetimes, and the Frame That Has No Time

A queued line carries a remaining in seconds, and the default is zero. Zero has to mean "draw me on this frame and then forget me", because that is what almost every debug drawing wants: the hierarchy is re-queued from the live data every frame, so a copy that survived would be a copy that could be wrong.

Ageing the queue is one function, and it is the single easiest thing in this lesson to get subtly wrong — twice over, in two different ways.

4.1 The order

The frame has three debug-draw events in it and their order is fixed:

Put advance() first — which is where "clear the buffer at the start of the frame" instinct puts it — and every line queued this frame with the default lifetime is deleted before it is ever drawn. The symptom is not a crash or a warning. It is a debug system that draws nothing, which reads as "my code did not run", which sends you looking in entirely the wrong place. verify_511 §B asserts this as a measurement rather than leaving it as a warning: three lines queued, aged, and zero left to draw.

4.2 The rule, and the frame with dt == 0

Now the expiry rule itself. The obvious version is two lines, and it is worth being precise about what is wrong with it, because the honest answer is not "it is broken" — it is "whether it is broken depends on a comparison operator and on dt, and neither of those should be load-bearing."

The first line works. A default-lifetime line has remaining == 0, subtracting any dt leaves it at or below zero, and it is dropped. Good.

The second is what you write the moment you want a line to survive the frame on which its clock runs out — a reasonable thing to want, and a one-character change. Now put dt = 0 through it: 0 − 0 = 0, which is not less than zero, so the line is kept. And so is every line queued on every subsequent frame. The queue fills, reaches its bound, and starts refusing the lines you are queueing now.

And dt == 0 is not exotic. It is a paused clock, a single-frame --shot, a program stopped on a breakpoint while you look at it, or a frame the OS delivered in under a microsecond. Those are exactly the moments you are looking hardest, which makes this a leak that only appears while you are using the tool.

Putting the test before the subtraction removes the dependency rather than getting it right. "Has this line had its frame?" is then answered by the stored value alone, with dt playing no part in it:

A zero-second line is queued, drawn, and dropped at the next advance whatever dt is — and so is a two-second line, 120 frames later. The visible cost is that a line asked to live two seconds lives two seconds plus one frame: the frame on which its clock reaches zero is still a frame it is drawn on. That is the right way round to be wrong for a thing whose entire purpose is to be seen.

verify_511 §B pins the behaviour, not the implementation — it asserts that a default line dies with dt = 0 and that a half-second line is drawn on 31 frames. A future simplification back to subtract-first with <= would pass the first and fail the second, which is the correct amount of pressure: it says "you changed something observable" without pretending there is only one acceptable answer.

Worked example — how many frames is half a second?

Queue a line with seconds = 0.5 and call advance(1/60) until it is gone. After 29 advances remaining is about 0.0167 — still positive. The 30th advance therefore keeps it and takes remaining to approximately zero. The 31st sees a value that is no longer positive and drops it.

So the line is present for 31 flushes: 30 frames of the time it asked for, plus the one on which its clock ran out. verify_511 §B counts exactly 31.

And the same experiment run against the alternatives, in float: subtract-first with <= gives 30 and correctly drops a default line when dt = 0; subtract-first with < also gives 30 but keeps the default line for ever at dt = 0 — the run was cut off at 500 advances. Two rules differ by one frame; the third differs by infinity.

4.3 The bound, and the counter that makes it honest

The queue is capped — 4,096 lines by default — and refuses rather than grows. A debug system that allocates without limit is a debug system that turns "why is this frame 200 ms" into a question whose answer is the debug system.

A bound on its own would be worse than none, though, because the failure is silent: the 4,097th line simply is not there, and a missing line looks exactly like a thing that does not exist. So the queue counts what it refused, and the panel prints it. Three numbers together — queued, drawn, dropped — are what tell you whether the picture you are looking at is the whole picture.

Every primitive funnels through one private push(), which is where the bound is checked. That is not tidiness: it means a twelve-edge box arriving with two free slots leaves two edges and ten drops, and it means that adding a primitive next month cannot forget to ask.

5ImGui in the Frame

5.1 Two backends, and which one first

ImGui separates "what a window looks like" — the core — from two backends you choose independently:

  • a platform backend, which turns OS events into ImGui's input state: imgui_impl_sdl3;
  • a renderer backend, which turns ImGui's vertex and index draw lists into actual drawing: imgui_impl_sdlrenderer3 or imgui_impl_sdlgpu3.

This engine has two surfaces (Lesson 4.2), so which renderer backend goes first is a real decision rather than a coin flip. The SDL_Renderer pair goes first, for two reasons that are both about scope rather than difficulty:

  • ecs_swarm — the demo that needs a panel today, because it is the one with a hierarchy to inspect — is on surface::renderer.
  • Under surface::renderer the platform already owns the presentation, so on_overlay() is a hook that exists at exactly the right moment: after the framebuffer has been blitted, before the frame is presented. On surface::gpu the program owns the device, the command buffer and the render pass, so the UI has to be handed all three by code the engine does not control.

§7 says precisely what the GPU path would need, with the real signatures, and why it is not in this lesson.

5.2 Where each call goes

Six calls, and one of them has a placement that is not negotiable.

start() in on_start, stop() in on_stop, handle_event() per event, and the panels plus render() in on_overlay — all of those are where you would guess. The interesting one is begin_frame(), which wraps ImGui's NewFrame.

NewFrame is where ImGui computes WantCaptureKeyboard and WantCaptureMouse — the flags that say "the UI is using this device right now" — from the events processed since the last NewFrame. They are the flags §6 masks the game's input with. So the ordering constraint is:

The constraint, and the symptom of breaking it

begin_frame() must run before anything reads a capture flag, which means before the action map is updated, which means at the top of on_input().

Put it in on_overlay next to the panels — where it looks like it belongs, since that is where the UI is — and every read during the frame answers about the previous frame. The symptom is one frame of leakage: the first keystroke after you click into a text field also reaches the game. One frame, every time, and invisible unless you are looking for it.

Lesson 5.10 added on_input() for a completely different reason — it needed a hook that runs exactly once per frame, after input is published and before the simulation reads it. That is precisely the property this needs, so 5.11 adds no hook. It is worth noticing when a previous lesson's decision pays for itself; it is the second time in two lessons that 5.10's work has been reused without modification, and §6 is the other.

One more ordering detail, inside begin_frame itself, because ImGui fixes it and the reason is not obvious:

Renderer, then platform, then core — because the core's computation depends on what the two backends just filled in. Get this order wrong and the failure is not a compile error; it is a frame of stale input or a font texture that is one frame behind.

5.3 The surface with no renderer

Every --shot in this repository runs headless: no window, no renderer, no video subsystem. A UI cannot start there, and the design question is what "cannot start" should feel like from the outside.

The answer is: like nothing at all. start() returns false, running() answers false, and every other call is a safe no-op — including wants_keyboard(), which answers false, so the mask in §6 blocks nothing and the game behaves exactly as it did before this lesson existed. That is what lets one program be written once and run correctly on all three surfaces, and it is what lets Lesson 5.1's reference image survive an eleventh lesson unchanged.

Note also that start() logs this at info, not error. A program built for a build server is not failing; it is running the way it was asked to. Logging it as an error would put a red line in every headless run in this repository and train the reader to ignore red lines — which is the same argument engine_set_warnings made about compiler warnings in §2.3, one layer up.

The one genuine wart is worth naming rather than hiding. Every other system Module 5 built is a value: asset_store, registry, action_map and debug_lines can all be held as many times as a program needs, because the engine does not know how many of a thing a game wants and declines to decide. debug_ui cannot be, because ImGui keeps its context in a library global that every ImGui:: call reads. Two live instances would silently share one set of windows. We do not pretend otherwise: start() refuses a second instance and says so in the log, because an enforced limit you can read beats an undocumented one you discover.

6The Input Seam

Here is the situation the whole of Lesson 5.10 was quietly waiting for. There is now a text field on screen. Click into it and type spawn. The s must reach the text field. It must not reach the game, where — in a demo with a spawn action bound to the space bar and toggles on half the alphabet — it would fire several of them.

Two consumers, one keyboard. Somebody has to arbitrate.

6.1 Arbitrate on levels, never on events

The obvious design is to route events: hand each event to the UI first, and if the UI took it, do not hand it on. It is obvious, it is what a lot of code does, and it is wrong in a way that takes a week to find.

The key that is held down forever

Symptom. After using the debug panel, the character keeps walking forward. Nothing is pressed. Tapping the key again fixes it.

Cause. A key-up event was routed to the UI and not passed on. engine::input tracks levels — is this key down — and a level is only ever corrected by the event that contradicts it. Withhold that event and the level is stuck, permanently, and no later event will fix it because the key is not going to be released twice.

Fix. Never withhold events. Feed every event to every consumer, and arbitrate one layer later, on the levels.

So on_event gives every event to ImGui, and the engine has already given the same event to engine::input before the hook runs (Lesson 5.2's ordering guarantee). Both see everything. The arbitration happens in on_input, where the action map is updated — and this is where Lesson 5.10's design pays for itself a second time.

Recall that action_map::update is a template constrained by a concept rather than a function taking const input&:

That was written for testability: it let a harness build a six-function fake instead of persuading SDL that a key was held. It turns out to buy something else entirely. A masked input is just another type satisfying the same concept — one that wraps a real snapshot and lies about the parts the UI has claimed:

Not one character of action_map changed. Had update taken a const input&, the only two ways in would have been an if inside the map — the input mapper learning what a UI is — or a copy of input with fields cleared, which is a second source of truth about the keyboard. Depending on a shape rather than a type is what made a third option exist.

One subtlety that looks like a bug and is not: the map is still updated while the UI has focus. It would seem cheaper to skip the update entirely, but a level that stops being updated is a level that is frozen — hold [Left], click into the filter box, and the camera would yaw forever. Updating through the mask reports every masked key as up, which produces the release edge. And that is not damage limitation, it is the behaviour you want: giving focus to a text field genuinely should let go of the movement keys.

6.2 You cannot mask a delta

Masking a key is a lie told about one frame, and it is complete: a key is a level, the level is false, done. The mouse is not so simple, and this is the subtlest thing in the lesson.

action_map derives a mouse delta by subtracting the previous frame's cursor position from this frame's. A delta is a difference between two frames — so suppressing one endpoint of a difference does not suppress the difference. Consider the cursor sitting at x = 100, the UI taking the mouse for three frames while the cursor travels to 160, and then letting go as it moves on to 170.

ApproachDelta while blockedDelta on the release frameWhat that is
report 0 while blocked0+170 the whole screen, in one frame
freeze the last position0+70 the whole excursion — the version that ships
virtual cursor0+10 one frame of real movement

The first is obviously wrong and you will catch it in a minute: reporting 0 makes the next real reading a difference against zero. The second looks right and is the one that ends up in shipped code, because it behaves perfectly until somebody drags a slider — at which point letting go of it whips the camera round by the distance they dragged.

The fix is to stop thinking of it as masking and start thinking of it as a change of frame of reference. The mask keeps a virtual cursor: it reports real − offset, and grows offset by exactly this frame's real movement on every blocked frame.

Worked example — the four frames, by hand

Frame 0 (unblocked, real 100): offset 0, reported 100. The map latches it; there is no previous, so no delta.

Frame 1 (blocked, real 120): offset becomes 0 + (120 − 100) = 20. Reported is 120 − 20 = 100. The previous reported value was also 100, so Δ = 0.

Frame 2 (blocked, real 145): offset becomes 20 + 25 = 45. Reported is 145 − 45 = 100. Δ = 0.

Frame 3 (blocked, real 160): offset becomes 45 + 15 = 60. Reported is 160 − 60 = 100. Δ = 0. The reported cursor has not moved since the block began.

Frame 4 (unblocked, real 170): the offset does not grow, because the frame is not blocked. Reported is 170 − 60 = 110, the previous reported was 100, so Δ = +10 — which is exactly how far the mouse moved during a frame the game was listening.

The cursor stays 60 pixels behind the real one from now until the program ends, and it is permanently right about how far it moved — which is the only question anybody asked it. verify_511 §E runs precisely these five frames.

The wheel needs none of this, and the reason is worth spotting because it tells you when the machinery is necessary. input publishes the wheel as a per-frame delta already — it is not a position anybody differences — so reporting zero for it is exact rather than a lie about a level. The elaborate treatment is required only where the consumer derives the delta itself.

7What We Did Not Build

Three things are deliberately absent, and each is named here rather than discovered later.

7.1 The SDL_GPU backend

ImGui ships one — imgui_impl_sdlgpu3 — and the engine's seam is already the right shape for it: debug_ui would grow a second start() overload and a render() that takes a command buffer and a render pass. The platform half (imgui_impl_sdl3) is shared; only the renderer half changes. These are the actual signatures, read from the header rather than remembered:

Note the shape of it: two calls rather than one, because uploading the vertex data and recording the draw happen at different points in a GPU frame — PrepareDrawData before the render pass begins, RenderDrawData inside it. That is Lesson 4.2's model, and the split is the same one Lesson 4.7 met with texture uploads.

It is not in this lesson because wiring it means threading a command buffer and a render pass out of sandbox's own frame — which is 4,700 lines of demo, and a lesson's worth of surgery on somebody else's program to demonstrate a call we can already read. Exercise 11.4 does it. Module 6, which lives on the GPU path, does it for real.

7.2 Depth-tested debug lines

draw_debug_lines draws over the scene, unconditionally. That is right nine times in ten: a contact normal buried inside the two objects that produced it is a contact normal you cannot see. The tenth time you do want occlusion — a hierarchy line passing behind a wall should say so — and that wants a per-line flag plus a depth buffer this function is not given.

A flag no backend honours is speculative design, so there is no flag. Exercise 11.3 adds one, and the interesting part of that exercise is not the flag: it is that a depth-tested line and an overlaid one must be drawn in two passes, which makes the queue's ordering guarantee suddenly load-bearing.

7.3 Batching

The flush walks the queue and draws one segment at a time. On the software renderer that is exactly right — there is nothing to batch into. On the GPU it will be badly wrong, and one draw call per line will dominate a frame.

Say plainly what has been bought anyway: the queue is what makes batching possible at all. You cannot batch calls that have already happened. An immediate-mode drawer forecloses the optimisation permanently; a queue defers the decision to the module that has a reason to care.

10Common Pitfalls & Debugging

The debug view draws nothing at all

Symptom. The queue reports a sensible size() in the debugger, the flush runs, and the screen is unchanged.

Cause. Almost always the order: advance() is running before the flush, so every default-lifetime line is deleted on the frame it was queued. It reads exactly like "my queueing code never ran", which is why people go and instrument the queueing code.

Fix. advance() is the last thing in the frame. Diagnose it in one step by queueing something with seconds = 5: if the five-second line appears and the default ones do not, it is the order and nothing else.

Debug lines pile up and the drop counter climbs

Symptom. dropped() is non-zero and rising; older markers stay on screen forever.

Cause. Either a real overflow — you are queueing more than the capacity every frame — or advance() is not being called on some path. The --shot path is the classic one: it returns early, and a queue aged only inside the "we have a camera" branch never ages on a frame with no active camera.

Fix. Age unconditionally, outside every branch. In this lesson's demo advance() sits outside the camera check for exactly this reason.

A key stays held after using the panel

Symptom. The camera keeps yawing after you interact with the UI. Tapping the key once fixes it.

Cause. The action map stopped being updated while the UI had focus — either by an if (!ui.wants_keyboard()) around update(), or by events being routed to ImGui and not passed on. Both leave a level stuck true, and a level is only corrected by the event that contradicts it.

Fix. Always update, always through the mask. Never withhold an event from engine::input.

The camera whips round when you let go of a slider

Symptom. Dragging an ImGui widget is fine; releasing it snaps the view by roughly the distance you dragged.

Cause. The mouse position was frozen during the block rather than rebased, so the first unblocked frame differences against a position from several hundred milliseconds ago.

Fix. The virtual cursor of §6.2 — and note that the diagnostic is already on screen: the offset readout should stop growing the instant you release, and the delta the frame after should be small.

One frame of input leaks into the game after clicking a text field

Symptom. The first character you type after clicking into a field also triggers whatever that key does in the game. Only the first.

Cause. begin_frame() is running after the capture flags are read — usually because it was placed next to the panels in on_overlay, which is where it looks like it belongs. Every read then answers about the previous frame.

Fix. begin_frame() first in on_input(). It is one line, and moving it is the entire fix.

ImGui asserts inside ProcessEvent on start-up or shutdown

Symptom. An IM_ASSERT firing with "Context or backend not initialized!"

Cause. Events arrive before on_start() has run and after on_stop() has torn the backends down. ImGui's backend functions are not total: they assume a live context.

Fix. The if (!running_) return; guard at the top of every forwarding function in debug_ui. That guard is not defensive decoration — it is what makes the class usable on a surface that never starts one.

The panel is invisible, or draws under the scene

Symptom. ImGui reports no errors and nothing is on screen.

Cause. render() is being called before blit_framebuffer() — so the framebuffer blit paints over it — or the render scale was left at something other than 1 by a previous overlay call.

Fix. on_overlay() is the hook, and it exists precisely because "after the blit, before the present" is a moment nothing else has. Restore any SDL_SetRenderScale you set before returning from it.

11Exercises

  1. 11.1 — Draw the thing you cannot see. Add a debug_lines::frustum(const mat4& view_projection, Uint32, float) that draws the camera's own frustum, and call it for the inactive camera in ecs_swarm — the one you are not looking through. Press [C] and watch the other camera's frustum swing past.

    Hint

    The eight corners of a frustum are the eight corners of the NDC cube pushed through the inverse of the view-projection matrix, then divided by w. The cube is x, y ∈ [−1, 1] and z ∈ [0, 1] — Lesson 4.2's depth range, not OpenGL's. Then reuse k_box_edges.

    Solution sketch

    Build the eight corners, transform, divide, and emit the twelve edges. The perspective divide is what makes it a frustum rather than a box, and it is worth stopping to notice: you have just run Module 2's pipeline backwards, and the shape that comes out is the shape that was mapped to a cube.

  2. 11.2 — A panel that edits the world. Add a table of entities with a selectable row, and an inspector that shows the selected entity's local placement with three DragFloat3 widgets writing straight into the component. Queue an axis triad on the selection so you can see what you are editing.

    Hint

    Store the selected entity, not a pointer to its components — the pointer dangles the moment a pool reallocates. registry::alive() is your check each frame, and it is exactly why Lesson 5.4 built generational handles.

    Solution sketch

    This is Module 8's inspector in miniature, and the shape you arrive at is the right one: the panel holds an id, re-resolves it every frame, and shows nothing when the resolve fails. That is the whole reason a handle is not a pointer.

  3. 11.3 — Depth-tested debug lines. Add a bool depth_tested to debug_line and honour it in the software backend, so a hierarchy line passing behind geometry is hidden. Then draw the same scene with the flag on and off and decide which you actually prefer.

    Hint

    draw_line does not consult a depth buffer, so the interesting work is deciding what a line's depth even is — it varies along the segment, so a per-pixel test needs the interpolated 1/w the rasterizer already computes for triangles (Lesson 3.2).

    Solution sketch

    Two passes: depth-tested lines first, overlaid lines second, so an overlaid line is never hidden by a tested one. That ordering requirement is the real content of the exercise — it is the first time the queue's order becomes part of its contract rather than an implementation detail.

  4. 11.4 — The other backend. Bring the debug UI up on surface::gpu in sandbox, using imgui_impl_sdlgpu3. §7.1 has the signatures.

    Hint

    debug_ui needs a second start() taking an SDL_GPUDevice* and the swapchain's texture format, and a render() taking a command buffer and a render pass. The platform backend does not change; only the renderer half does.

    Solution sketch

    The awkward part is not ImGui, it is that PrepareDrawData must be called with the command buffer before the render pass begins and RenderDrawData inside it. Your render() therefore splits into two functions, and the demo has to call them at two different points — which is a fair description of the difference between the two surfaces generally.

  5. 11.5 — Break the seam on purpose. Replace the mask with the two wrong designs from §6, one at a time: first skip actions_.update() while the UI has the keyboard, then freeze the reported cursor position instead of rebasing it. Reproduce both symptoms deliberately and write down the sequence of actions that exposes each.

    Hint

    The first needs a key held across the moment focus is taken. The second needs a long drag — the bug is proportional to how far you dragged, so a small drag hides it, which is exactly why it survives testing.

    Solution sketch

    Both are one-line changes and both produce a bug that a casual test passes. That is the point of the exercise: these are not mistakes you avoid by being careful, they are mistakes you avoid by knowing that a level and a delta fail in different ways.

12Recap & Next

The engine gained a debug-draw system and a tooling UI, and Module 5 is finished.

  • A queue that anybody can fill. debug_lines holds world-space segments with lifetimes, bounded and counted, and includes nothing that can draw — so a collision system in Module 7 will be able to queue a contact normal without compiling the renderer.
  • A backend, not a replacement. Everything in debug_draw.hpp survived; the queue was put in front of it. draw_debug_lines is four lines because six lessons of clipping were already correct.
  • Lifetimes, because events are invisible without them. A single-frame marker is on screen for 16.7 ms and a person needs about 250. The expiry rule tests before it subtracts, so a paused clock cannot leak.
  • Dear ImGui, taken publicly and contained. 41,385 lines we did not write, 182 lines that own the lifecycle, and a rule about which code is allowed to speak it.
  • An input seam that changed nothing it did not have to. masked_input is a new type satisfying 5.10's concept; action_map is unchanged to the character. The arbitration is on levels, never on events.
  • A virtual cursor, because a delta cannot be masked by masking one of its endpoints — the subtlest thing in the lesson and the one most likely to ship broken.

60 checks green in debug and release; verify_45 through verify_510 still green; and the reference shot from Lesson 5.1 byte-identical for the eleventh consecutive lesson, which is now a slightly stronger statement than usual: this lesson changed a function signature in the middle of the reference render's own call path and the output did not move by one bit.

Next: Module 6. The renderer stops being adequate and starts being correct. It opens with the lesson every graphics programmer needs exactly once and then has forever — linear versus sRGB — and the reason it opens there is that every lighting result in the module is wrong until it is settled. Lesson 1.6 promised that payment would come due; it is due now.

Both halves of this lesson get their return in that module and the two after it. The debug queue becomes the thing that makes shadow-map frustums, tangent frames and culling bounds visible instead of theoretical; the panel becomes how a BRDF's three terms get separate sliders. And Module 8's editor — hierarchy, inspector, gizmos — is built on exactly the two files this lesson added.
