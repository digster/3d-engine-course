Module 6 — Advanced Rendering · Lesson 6.10

Mipmaps, LOD, and Anisotropic Filtering

This lesson is a debt being paid. Lesson 3.9 measured the problem exactly — one screen pixel covers 0.60 texels at the bottom of the frame and 62.46 two rows below the horizon, while bilinear reads four texels whatever the pixel covers — then named the fix and moved on. So did 4.7, which created every texture with num_levels = 1 and a comment saying Module 6 would change it. So did texture.hpp's own sampler struct. The fix is one sentence: if a pixel covers sixty texels, read from a copy of the image in which those sixty have already been averaged. What makes it a lesson is the three questions that sentence hides — which copy, what about between copies, and what if the footprint is not square — and one famous bug that makes a surface darken as it recedes.

1The problem: a promise made six times

Lesson 3.9 built texture mapping and bilinear filtering, and it ended by measuring something it could not fix. On a floor running to the horizon:

One screen pixel covers 0.60 texels at the bottom of the frame and 62.46 texels two rows below the horizon. Bilinear filtering reads four — always, whatever the pixel covers. They cross near row 103, and past that the sampler is looking at a shrinking fraction of the truth: about 6.4% of it at the horizon. The gap is the aliasing, and mipmaps (Module 6) are what closes it.

That is a completely honest description of a bug, and then nothing happened for seven lessons. It is worth listing where the promise was repeated, because the list is the reason this lesson sits at 6.10 and not at the end of the module:

  • 3.9's prose, above.
  • 3.9's Exercise 8.5, which asks the student to build a chain and warns about the linear-light trap in its hint.
  • 3.9's Exercise 8.4, which asks how the sampler would know which filter applies — and answers "it is a fact about the derivative, and Module 6's job properly".
  • 4.7's exercise 4.7.5, naming SDL_GenerateMipmapsForGPUTexture.
  • 4.7's gpu_texture.cpp, which shipped ti.num_levels = 1; with the comment // no mipmaps yet — Module 6.
  • And worst, texture.hpp's public sampler struct, whose doc comment reads "Module 6's mipmaps are what fills the gap" — a promise made in a header the student is meant to read.
How this got found, which is itself the lesson

Two external reviewers read the published curriculum and independently flagged mipmaps as missing — from the outline alone, without access to the code. Neither could see that the engine had promised them six times; they simply noticed that a course teaching texture filtering had no lesson on minification.

A deferral is a debt, and a deferral repeated in a shipped header is a debt with the student's name on it. It is worth being deliberate about which ones you are carrying.

2Building intuition: average it in advance

The problem is a mismatch between how much of the image a pixel is responsible for and how much of it the sampler looks at. There are two ways to close a gap like that, and only one of them is affordable.

Read more texels. If the pixel covers sixty-two, read sixty-two and average them. This is exactly right and completely unusable: the cost per pixel would rise with distance, so the far half of your screen — the cheap half, the half that covers the least area — would become the expensive half. Worse, the count varies per pixel, so the inner loop gets a variable-length inner loop inside it.

Or average them in advance. The set of texels a distant pixel covers is not arbitrary: it is a contiguous square block. And the blocks that different pixels need are nested — a 4×4 block is four 2×2 blocks. So precompute the averages once, at load time, in a pyramid: the image at half size, then quarter size, and so on to a single texel. At draw time, pick the level whose texels are about the size of the footprint and take the same four taps you always took.

The cost moves from per-pixel-per-frame to per-texture-once, and the per-pixel cost becomes constant again — which is the whole reason this technique is universal rather than merely correct.

The memory is a geometric series and it is worth doing in your head once, because the number is quoted everywhere and almost never derived. Each level is a quarter the area of the one above, so the extra storage is

\[ \tfrac{1}{4} + \tfrac{1}{16} + \tfrac{1}{64} + \cdots = \sum_{k=1}^{\infty} 4^{-k} = \tfrac{1}{3} \]
1/4 + 1/16 + 1/64 + … = 1/3

33% more memory, for any image, at any size. The harness measures 65,536 texels becoming 87,381 — 33.33%, which is the series to four figures.

The three questions the one-sentence version hides

  1. Which level? The footprint is a derivative — how fast uv changes per screen pixel. On a GPU that is free, because fragments are shaded in 2×2 quads specifically so a neighbour is always available to subtract. A scanline rasterizer has no neighbour. The row above was finished and discarded; the pixel to the right has not happened yet. So the CPU has to compute the derivative from the triangle itself, and that is §3.3 — the most interesting arithmetic in the lesson.
  2. What about between levels? Level 3 and level 4 differ by a factor of two, so switching abruptly between them draws a visible line across the floor. You have met this shape of artefact before: it is 6.9's cascade seam, one lesson later and one dimension down, and it has the same cure — blend across the boundary.
  3. What if the footprint is not square? A floor at a grazing angle is compressed in one screen direction and not the other. One square average cannot represent that, so choosing a level forces a choice between blurring and aliasing. Anisotropic filtering refuses to choose.
And one bug, which is famous enough to have a shape

A mip chain built by averaging sRGB bytes gets darker at every level. Averaging is a linear operation; sRGB is not a linear encoding; the mean of two codes is not the code of the mean light, and it is always too dark because the curve is convex.

The symptom is that a textured surface dims as it recedes — and the usual diagnosis is "the lighting falls off too fast", which sends you to look in entirely the wrong file. §3.4 measures it: on the harshest case the naive chain delivers 42.2% of the light it should, at level 1 alone, and it compounds all the way down.

3The theory

3.1  Building the chain

Level 0 is the image. Level k+1 is level k with every 2×2 block replaced by its average, so each level is half as wide and half as tall. The chain stops at 1×1, which takes 1 + ⌊log₂(max side)⌋ levels — nine for a 256-square image, ten for 512.

Two details that only bite on textures that are not square powers of two:

  • Stop when both axes reach 1, not either. A 64×4 texture halves to 32×2, 16×1 — and if you stop there, you have thrown away four more halvings of width. The harness checks that a 64×4 strip reaches 1×1 in seven levels.
  • Odd sizes round down and lose a row. Real engines box-filter with weights that account for it; the difference is invisible and the code is twice as long, so this is the ninety-percent picture and the missing ten percent is a weighted resample.

3.2  Choosing the level

Level L has texels 2L times as wide as level 0, because each level halved them. We want the level whose texel is about the size of the footprint, so

\[ 2^{L} = \rho \qquad\Longrightarrow\qquad L = \log_2 \rho \]
2^L = footprint_in_texels  ⟹  L = log2(footprint_in_texels)

where ρ is the footprint measured in level-0 texels. The logarithm is not a trick — it is the direct consequence of the pyramid halving at each step, which is why the formula has no constants in it to tune.

Worked example. Push 3.9's own measurement through it.

That lesson measured 62.46 texels per pixel two rows below the horizon. So

L = log2(62.46) = 5.965

Level 5 of a 256-texture is 8×8; level 6 is 4×4. So the right answer is "level 5, almost all the way to level 6" — and the harness confirms mip_level_for returns 5.965 for that footprint.

Note what the level being fractional is telling you: there is no level whose texels are exactly 62.46 across, because the chain only offers powers of two. That fraction is precisely what trilinear filtering interpolates, and it is why the function returns a float rather than an int.

ρ is the longer of the two axes, and that one word is the whole of why plain mipmapping over-blurs. Taking the longer guarantees no aliasing along either axis, at the cost of blurring the shorter one. Taking the shorter would keep the detail and alias. Hold that thought until §3.6.

And magnification — ρ < 1, a pixel covering less than a texel — clamps to level 0. There is no level −1, and the honest answer is that the image simply has no more detail to offer.

3.3  The derivative, on a renderer with no neighbours

Now the part that is genuinely CPU-specific, and the reason 3.9 could measure the footprint in a demo but not compute it in the fill loop.

A GPU shades fragments in 2×2 quads. That is not an efficiency detail — it is why ddx and ddy exist: the neighbouring fragment's value is right there, so a derivative is a subtraction. (It is also why those functions cannot be called from divergent control flow: the neighbour might not have taken your branch.)

Our rasterizer walks a scanline one pixel at a time. The row above was finished and thrown away; the pixel to the right has not been computed. There is nothing to subtract. So the derivative has to come from the triangle, analytically — and it turns out to be both exact and nearly free.

Recall from Lesson 3.2 that perspective-correct interpolation computes

\[ u(x,y) \;=\; \frac{U(x,y)}{W(x,y)}, \qquad U = \sum_i f_i \frac{u_i}{w_i}, \qquad W = \sum_i \frac{f_i}{w_i} \]
u = U / W, with U = Σ f_i·(u_i/w_i) and W = Σ f_i·(1/w_i)

Both U and W are affine in screen space, because the normalised barycentrics fi are — they are edge functions, which are linear in x and y by construction (Lesson 2.2). An affine function has a constant gradient. So the quotient rule gives, per screen axis,

\[ \frac{\partial u}{\partial x} \;=\; \frac{\dfrac{\partial U}{\partial x} - u \cdot \dfrac{\partial W}{\partial x}}{W} \]
du/dx = (dU/dx − u · dW/dx) / W

and every ingredient is already lying around:

Where each term of the gradient comes from
TermWhere it already exists
df_i/dx step_x0/1/2 · inv_area — the edge increments the fill already walks, over the area it already reciprocated
dU/dx, dW/dx a weighted sum of those, constant over the triangle, so hoisted out of the pixel loop entirely
u the fragment's uv, which the loop just computed
1/W w_recip — the reciprocal Lesson 3.2 already pays one divide for

So the per-pixel cost is two multiplies and a subtract per axis, and only when a chain is bound. Everything else hoists.

It is exact, and the test says so

This is a closed form, not an approximation — which is a stronger claim than "it looks right", so it deserves a stronger test than looking at it. §D of the harness computes the gradient analytically and then computes a central difference of the real perspective-correct interpolation at the same point, on a triangle with genuinely different w at each vertex so the divide actually bends things.

They agree to 5.79 × 10−6, which is the finite difference's own truncation error rather than a disagreement. A test that only checked the analytic form against itself would have proved nothing.

3.4  The bug that makes things darker

Now the trap, and it is worth meeting with real numbers because "average in linear light" is advice that is very easy to nod at and not act on.

Take one 2×2 block of a black-and-white checker: two texels at code 255, two at code 0. What should their average be? Half the light — one of the two texels is emitting all of it and the other none, so the block as a whole emits half.

Lesson 6.1 established the two integers that answer this. Code 128 is not half the light; it is 0.2159 of it. Half the light is code 188. So:

Worked example. The two ways, side by side.

naive: (255 + 0 + 0 + 255) / 4 = code 127 → 0.2122 of white
correct: decode → (1 + 0 + 0 + 1)/4 = 0.5 → encode → code 188 → 0.5029 of white

The naive answer delivers 0.2122 / 0.5029 = 42.2% of the light it should. That is 57.8% too dark, at level 1, on one block.

And it compounds. Level 2 averages four level-1 texels that are already too dark, so the error accumulates down the chain — which is why the symptom is not "textures are dark" but "textures get darker with distance", and why it is so often mistaken for a lighting falloff problem.

Read the space from the data, not from a parameter

build_mips decides by asking the texture: texel_space::srgb decodes, texel_space::linear averages the bytes directly. That field exists because Lesson 6.7 needed normal maps to stop being decoded as colour, and it pays for itself again here — a roughness map or a normal map is linear data, so averaging its bytes is the correct operation rather than the lazy one.

Making it a parameter would put the decision back at the call site, which is exactly where 6.7 took it from. A caller who has to remember which of their textures is colour will get the third one wrong.

Alpha is averaged as bytes on both paths, incidentally: it is a coverage fraction rather than a colour, so it was never sRGB-encoded, and decoding it would be a second bug hiding behind the fix for the first.

The GPU gets this right for free, and it is worth knowing why

SDL_GenerateMipmapsForGPUTexture does not need telling about colour spaces, because the texture was created with an _SRGB format. The hardware decodes on read and encodes on write, so the blit chain that generates the levels is already averaging in linear light.

That is the clearest case in this course of a format flag doing real work: the same correctness the CPU path arranges by hand in twenty lines is, on the GPU, a consequence of having declared what the data means.

3.5  Trilinear, and a seam you have met before

The level is fractional and the chain is not. Round it, and every fragment on one side of an invisible line reads an image twice as detailed as the fragment next to it — so the line becomes visible, running across the floor at a fixed distance from the camera.

This is Lesson 6.9's cascade seam. Same cause: two representations of the same surface, each defensible, meeting at a boundary and disagreeing. Same cure: blend across it. Bilinear within a level, linear between two levels — trilinear.

The harness sweeps a footprint across a level boundary and measures the largest single-step change:

nearest: 0.3470   ·   trilinear: 0.0124   —   28× smaller

A 0.347 jump in one step of camera distance is a hard edge; 0.0124 is a gradient. The cost is one extra bilinear fetch, which is why trilinear is the default everywhere and mip_filter = nearest exists mainly so you can see what it is for.

3.6  Anisotropy: refusing to choose

Back to the word "longer" in §3.2. Consider a floor seen at a grazing angle. Moving one pixel across the screen moves you a long way across the texture; moving one pixel up the screen moves you much further still, or much less, depending on the geometry. The footprint is a long thin ellipse, not a circle.

Take the harness's case: 32 texels along one screen axis, 2 along the other — a 16:1 ratio.

  • Choose by the long axis (32 texels ⟹ level 5). No aliasing, but the short axis only needed level 1, so it is blurred by a factor of 16. This is why distant ground in a game without anisotropy looks like it has been smeared.
  • Choose by the short axis (2 texels ⟹ level 1). The detail survives, and the long axis aliases exactly as it did before we started.

Anisotropic filtering refuses the choice. Take the level the short axis asked for — so no detail is thrown away — and then take several samples along the long axis and average them, which supplies the averaging the long axis needed. The number of samples is the ratio, clamped: "16× anisotropic" is that clamp, and it is why the setting is quoted as a number rather than on/off.

It costs only where it buys

On a square footprint the ratio is 1, so there is no long axis and the code takes a single tap. The harness checks this rather than assuming it: with max_anisotropy = 16 and a 1:1 footprint the result is identical to the isotropic one to six decimal places.

That is worth verifying because the failure would be invisible and expensive — sixteen taps of the same place, on every surface facing the camera squarely, which is most of them.

4Implementation

4.1  The decision that keeps the golden

Before any code, one design decision, made deliberately and early because it constrains everything after it.

The reference render — the fixture that has been byte-identical for eighteen lessons — draws a textured floor. So unlike Lesson 6.9's cascades, mipmapping is not automatically an opt-in path: build a chain for every texture and the reference picture changes, and the regression test that has caught four real bugs stops meaning anything.

There were two honest options: re-baseline the golden and say so, or make the chain opt-in. Opt-in wins on its own merits, not just to protect the test. A chain costs 33% more memory; a 1×1 white fallback has nothing to average; a UI atlas is never minified. Building one unconditionally would be paying everywhere to fix somewhere.

So texture is untouched, mip_chain is a separate type, and texture_binding grows a nullable pointer — the same bargain lights, albedo and 6.9's cascades already make.

4.4  The GPU chain, and the assert you will not see

4.7's ti.num_levels = 1; // no mipmaps yet — Module 6 becomes a level count, and the usage flags grow one bit:

⚠ VERIFY, discharged — and one thing worth reading the source for

Checked against the configured SDL3 tree rather than remembered. SDL_GenerateMipmapsForGPUTexture(SDL_GPUCommandBuffer*, SDL_GPUTexture*) returns void, takes exactly those two arguments, and its header says "This function must not be called inside of any pass."

SDL_gpu.c validates three things: that no pass is in progress, that num_levels > 1, and that the usage carries both SAMPLER and COLOR_TARGET. All three checks live inside if (COMMAND_BUFFER_DEVICE->debug_mode). On a release device you get no assert, no log line, and undefined behaviour — so the requirement 4.7's exercise stated is real, and the diagnostic that would tell you about it is conditional.

This course has met SDL's assert gating before, from the other side: they key on __OPTIMIZE__ rather than NDEBUG, so -O2 alone is enough to switch them off.

What it costs, stated as a number

33% more memory, always, whether the texture is ever minified or not. On a surface that was never undersampled, mipmapping buys nothing: §G checks that a fetch at one texel per pixel is byte-identical to the unmipped one, because level 0 is the original image.

And over-eager level selection has a cost of its own. A mip_bias of +2 moves the same fetch from 0.4488 to 0.4872 — visible blurring on a surface that asked for none, which is why the bias is exposed rather than hidden, and why "just add a bit of bias" is a poor fix for aliasing you have not measured.

The same shape of judgement as 6.9's: cascades cost 29% of their resolution to buy stability and lose outright on a small scene. Reach for the technique when you have measured the problem. 3.9 measured this one seven lessons ago.

7Common pitfalls & debugging

The chain is built, the sampler is set, and nothing changes

Symptom. Mipmapping appears to do nothing on the GPU. The floor aliases exactly as before.

Cause. SDL_GPUSamplerCreateInfo::max_lod is 0, which clamps every lookup to level 0. It is a perfectly legal request, so there is no error and no warning.

Fix. Set it above the chain's top level. And check enable_anisotropy at the same time: max_anisotropy alone is a silent no-op for the same reason.

Textures get darker with distance

Symptom. A textured surface dims as it recedes. Usually reported as "the lighting falls off too fast" or "the fog is too strong".

Cause. The chain was averaged in sRGB bytes rather than linear light (§3.4). Each level is darker than the one above, and it compounds.

Fix. Decode, average, re-encode. To confirm it before fixing it, build a chain from a pure black-and-white checker and read level 1: it must be code 188, not 127.

Normal maps look wrong only in the distance

Symptom. Lighting is correct up close and subtly wrong further away.

Cause. The opposite error — a linear-data texture decoded as sRGB while being averaged. 6.7's bug arriving through a different door.

Fix. Read texel_space from the texture. This is precisely why that field is on the data rather than at the call site.

A visible line across the floor at a fixed distance

Symptom. A hard boundary in sharpness, following a contour of constant distance from the camera.

Cause. mip_filter = nearest: the level is being rounded rather than blended. Exactly Lesson 6.9's cascade seam.

Fix. Trilinear. The harness measures the step at 0.3470 rounded against 0.0124 blended.

Distant ground looks smeared rather than sharp

Symptom. No aliasing, but the far floor has lost all its detail.

Cause. Isotropic filtering choosing the level from the long axis of a grazing footprint (§3.6). At 16:1 that blurs the short axis by a factor of 16.

Fix. Anisotropic filtering. This is the single most visible quality setting in most games, and now you know exactly what it is buying.

Mipmap generation asserts, or does nothing at all

Symptom. An assert about usage flags — or, on a release device, silently wrong texture contents.

Cause. The texture lacks COLOR_TARGET, or num_levels is 1, or the call is inside a pass. SDL checks all three only in debug mode.

Fix. All three, and develop against a debug device. A validation layer you have switched off is a validation layer you do not have.

8Exercises

8.1 — See the bug you were warned about guided

Change build_mips to average bytes regardless of texel_space, run the demo with --floor-tex 512 --mips, and look at the far floor. Then read level 1 of a black-and-white checker and confirm it is code 127. Put it back.

Hint

The visual tell is that the floor's average brightness falls with distance while its contrast also falls — two things changing at once, which is what makes it read as a lighting problem rather than a texturing one.

8.2 — Visualise the level guided

Tint each mip level a different colour — level 0 red, 1 green, 2 blue, and so on — and render the floor. You will see the level bands directly, which makes --mip-nearest and trilinear a before/after you can point at, and makes anisotropy's effect on level choice obvious.

8.3 — Check the gradient against the GPU engine challenge

§D checks the analytic gradient against a finite difference of our own interpolation. Check it against a different implementation: render the same triangle on the GPU with a shader that outputs log2(length(ddx(uv) * textureSize)) as a colour, read it back, and compare against the CPU's level for the same fragments.

Hint

Expect them to agree closely but not exactly, and the reason is interesting: the GPU's ddx is a finite difference across a 2×2 quad, so it is the approximation and ours is the closed form. Disagreement will be largest where the derivative changes fastest — near a silhouette, or on a steeply foreshortened triangle.

8.4 — Measure the cost open

Use Lesson 3.10's timing harness to measure the software rasterizer's fill rate with the chain bound and without, on a floor that fills the frame. Separate the cost of the level arithmetic from the cost of the second bilinear fetch by testing mip_filter = nearest as a middle point.

Solution sketch

Three configurations, one variable each: unmipped (one fetch, no arithmetic), nearest (one fetch, plus the log2 and the gradient), trilinear (two fetches, same arithmetic). The gap between the first two is the derivative; between the second and third is the extra tap. Predict which is larger before you measure — most people guess wrong.

8.5 — Non-power-of-two, honestly open

§3.1 admits that odd sizes round down and lose a row. Build a 100×100 checker, mip it, and find the artefact. Then implement a weighted box filter that accounts for the partial row and measure whether you can see the difference.

9Recap & next

What the engine gained.

  • Mipmapping in both renderers, with trilinear filtering and anisotropy, and a level derived from an exact analytic derivative rather than a finite difference — agreeing with a numerical check to 5.79 × 10−6.
  • A debt cleared. Six promises, one of them in a shipped public header, made good.
  • The sampler 3.9 described. That lesson collapsed SDL's three filter fields into one and said exactly why it could; the other two are now real.
  • A famous bug, quantified rather than merely named: an sRGB-averaged chain delivers 42.2% of the light it should at level 1, and compounds.
  • The golden held for the nineteenth lesson — and this time by design rather than by luck, because the reference scene samples textures and the chain had to be made opt-in deliberately.

What it still does not do. No weighted filtering for non-power-of-two sizes; no mip generation for the CPU's normal maps (only albedo is chained); no negative LOD bias clamping worth the name. And anisotropy is a fixed sample count along one axis rather than the elliptical footprint the literature describes.

Next — 6.11, Transparency: Alpha Modes, Blending, and Draw Order. The pipeline has said no blending since 4.4, and 6.6's glTF importer reads alpha and ignores alphaMode entirely — so every downloaded asset with foliage or glass currently renders as opaque cardboard. That is the one gap in that importer which fires no status code, and 6.6 §10 says so in as many words.

It also matters to this lesson. Alpha-masked foliage and mipmapping interact badly in a way that is famous in its own right: averaging an alpha channel makes cutout edges dissolve with distance, and the fix has a name.

10Further reading

  • Lance Williams, "Pyramidal Parametrics" (SIGGRAPH 1983) — the original mip paper. "MIP" is multum in parvo, "much in a small space", and the paper is short and readable.
  • Paul Heckbert, "Survey of Texture Mapping" (IEEE CG&A, 1986) — 3.9 already sent you here; §3 on resampling and filtering is the part that pays off now.
  • Real-Time Rendering, 4th ed., §6.2.2 "Mipmapping" — the standard treatment, including the ripmap and summed-area alternatives this lesson skips.
  • Real-Time Rendering, 4th ed., §6.2.3 — anisotropic filtering, and the elliptical weighted average our fixed-sample version approximates.
  • SDL3, SDL_GenerateMipmapsForGPUTexture and SDL_GPUSamplerCreateInfo — and, worth reading rather than trusting, SDL_gpu.c's validation of that call, which is conditional on debug mode.
