Module 5 — Becoming an Engine · Lesson 5.2

The Platform and Application Layer

Every demo this course has written opens with the same forty lines — initialise SDL, make a window, make a renderer, make a texture, check all four — and closes with the same four, backwards. None of it is what any demo is about. Today we ask the question those lines are really hiding: who owns the loop? Your program, calling into a library? Or the engine, calling into you? SDL3 has a considered answer on disk, and it is not the one we have been using. We are going to build both, decide which each program deserves, and finish with Lesson 1.8's Pong as its own executable — 87 lines of code, with no main in it at all.

1The Problem

Lesson 5.1 ended by pointing at a file and refusing to fix it. demos/sandbox/main.cpp was 5,721 lines, and five separate demos lived inside it as branches of a switch on a [Tab] key. The lesson said, in §12, that splitting them was not a job for a refactor about include paths: each of those demos would be its own small executable if there were an application layer to hang a loop on.

That is a strange sentence when you first read it. A loop is four lines. Why would anybody keep five unrelated programs welded together for want of something so small?

Here is the answer, and it is not really about the loop. Open the last program you wrote in this course — demos/hello_cube/main.cpp as it stood at the end of Lesson 5.1 — and count what it had to say before it could put one lit cube on screen:

Seventeen calls, out of 160 lines of code. Every one of them is correct, every one of them is necessary, and not one of them is about a cube. The same seventeen appear, in the same order, in sandbox. They appeared in every single-file demo from Lesson 1.5 onward. When we wrote the second one we copied the first, and when we wrote the third we copied the second, and the row-by-row texture upload — the one with the comment explaining that SDL's returned pitch may exceed width * 4 and that one big memcpy would shear the image on machines you do not own — existed verbatim in two files by the end of Lesson 5.1.

The failure mode

Duplicated start-up code does not fail loudly. It fails by divergence: one copy gains a fix and the other does not. We already have a documented instance of exactly this pattern in this repository — Lesson 5.1's §1 describes four verification harnesses that each transcribed build_scene by hand, and notes that copy number four could have drifted from the original with nothing in the build to say so. The presentation path is the same shape of hazard, and it is worse, because a subtly wrong texture upload does not fail on your machine at all.

1.1   The tell

But the real tell is not the duplication. It is what the duplication prevented.

Pong has been finished since Lesson 1.8. It is a complete game: serve, rally, score, an AI opponent, two collision rules to compare. Its simulation lives in demos/common/pong.{hpp,cpp}, a clean 700 lines that knows nothing about SDL. And for four modules, the only way to play it has been:

Why? Not because anybody thought that was right. Because a demo needs a loop to exist in, and there was exactly one loop in the repository. Writing a Pong executable meant writing those seventeen calls again, plus an event drain, plus a clock, plus an accumulator — about eighty lines of program that is not Pong — and so it was cheaper to add a branch to a file that already had all of it. Every demo after that made the same calculation. That is how a 5,700-line main.cpp gets built: not by one bad decision, but by eighty small correct ones.

So the missing thing is not a loop. It is somewhere for a program to be. And the moment you start designing that, you run straight into a question the course has been quietly answering the same way since Lesson 0.5 without ever putting it to a vote.

2Building Intuition

2.1   Who owns the loop?

Think about two ways a person can be given a job.

In the first, you are handed a toolbox and a task. You decide what to do and when; you reach into the box for a hammer when you want a hammer. The box does not know you exist. If you stop working, nothing happens — the box just sits there.

In the second, you are on a production line. The line moves. Something arrives in front of you, you do your bit, and it moves on. You do not decide when the next thing comes; you decide what to do with it when it does. If you stop working, the line notices.

Both are real jobs and both get things built. The difference is not competence or freedom — it is who has the clock. And that difference has a name in software: a library is a toolbox, and a framework is a production line. The one-line version, which is worth memorising because it survives every argument about the terms:

The distinction

You call a library. A framework calls you. Everything else — how big it is, how many files, whether it is "opinionated" — is decoration on top of that one fact.

Everything this course has built is a library. Look at any demo: main() is yours, while (running) is yours, and inside it you call collect_triangles and draw_triangles and clk.tick(). The engine has never once called you. It does not know your program exists.

The alternative is that you write no loop at all. You write a handful of functions with agreed names — here is how to start; here is one frame; here is one event; here is how to stop — and something else runs them in the right order for the life of the program. That is the production line. Figure 1 puts the two side by side.

Notice what Figure 1 does not show: any difference in the phases. Both columns contain the same six boxes, in the same order, doing the same work. Nothing about drawing a frame changes. The only thing that moves is the dashed outline — which box the word while is written inside.

You might reasonably ask why anybody would give up control of their own loop for that. On a desktop, the honest answer is "convenience, and not much else". But there is a second answer that is not about convenience at all, and it is the one that decides the question:

Where while (true) is illegal

In a web browser, JavaScript and WebAssembly run on a single thread that also draws the page and handles input. A loop that never returns does not just make your program unresponsive — it freezes the tab. The browser owns the clock and hands out frames through requestAnimationFrame; a program that will not give the thread back cannot run at all. iOS and Android are the same shape of problem for a different reason: the OS owns the application lifecycle, needs to suspend you when a call comes in, and expects a delegate it can call.

So on those platforms the framework arrangement is not a nicety. It is the only arrangement that exists. This is exactly why SDL3 grew the callback entry points, and it is why an engine that intends to reach a browser should have a callback-shaped spine even while it only ever runs on desktops.

2.2   The forty lines nobody reads

Set the loop aside for a moment and look at the other half of what a program has to say. Here is the shape of every demo's start-up, with the error handling folded away:

Read the two halves against each other. They are a mirror: the last thing created is the first thing destroyed, and the reason is a chain of dependencies. The texture belongs to the renderer, so it must not outlive it. The renderer belongs to the window. The window belongs to the library. Reverse any two of those lines and you get undefined behaviour — which on your machine will very likely appear to work, because the memory it touches has not been handed to anyone else yet.

That is the first thing worth noticing. The second is what happens between the halves. Each creation can fail, and each failure has to unwind exactly what has been built so far and no more. Written out honestly, with four resources, you get four different teardown sequences — and the pre-5.2 sandbox had precisely that, five exit paths from main each unwinding a different amount, and one of them (the --shot path) unwinding correctly by luck because it happened to run before anything was built.

A mirror with a dependency chain and a set of partial unwind paths is not "boilerplate". It is a small, exacting, well-understood problem with one right answer, being solved from scratch in every file. That is precisely the sort of thing a library should own — and Figure 3 will show the ladder in full.

2.3   Hiding a library, and owning one

So we are going to write something called a platform layer. Before we write a line of it, we have to decide what it is for, because the phrase "platform layer" gets used for two completely different things and picking the wrong one costs years.

The first meaning is a layer that hides a dependency. You invent your own vocabulary — engine::window, engine::key, engine::event — and translate at the boundary. The code above the layer never names an SDL type. The prize is portability: swap SDL for GLFW, or for a hand-rolled Win32 backend, and nothing above the layer changes.

The second meaning is a layer that owns a lifetime. It does not invent a vocabulary. It hands you the SDL_Window* quite happily. What it owns is the order things are created in, the order they are destroyed in, and the fact that all of it happens exactly once.

Lesson 5.1 already made this decision once, and got it right, and said so out loud in engine/CMakeLists.txt:

From Lesson 5.1

target_link_libraries(engine PUBLIC SDL3::SDL3) — "PUBLIC because SDL is in our public headers: framebuffer.hpp says Uint32, gpu_device.hpp takes an SDL_Window*, and input.hpp reads SDL_Event. … It is also an admission. A renderer whose public API names another library's types has adopted that library's vocabulary permanently."

5.1 flagged that as residue and left the argument for today. Here is the argument, and the conclusion is that it is not residue at all.

A wrapper that hides a library you have no intention of replacing is cost with no benefit. Count what the hiding option actually buys us. We chose SDL3 in Lesson 0.3 for reasons that have not changed: it is the cross-platform layer, it is where SDL_GPU lives, and Module 4 built the entire GPU renderer on it. There is no world in which this engine drops SDL and keeps gpu_device. So the swap-ability we would be paying for is a benefit we will never collect.

And it is not cheap. A hiding layer means inventing an event type, a key enum with 240-odd values, a window-flags bitfield, a translation function for each, documentation for all of it, and — the part people forget — a permanent tax on every new SDL feature, which must be surfaced through your vocabulary before anyone above the line can use it. Every one of those is a place for a bug that SDL does not have.

So we take the second meaning, deliberately, and we say why in the header rather than leaving a reader to wonder whether we simply did not think of it. platform::window() returns an SDL_Window*. platform::handle() takes an SDL_Event. What the class owns is the ladder in Figure 3 and nothing else.

When the other answer is right

Engines that do hide their platform layer generally have a concrete reason: a console SDK under NDA that cannot appear in shared headers, a second backend that already exists, or a public API that ships to customers who must not be forced to install your dependency. If any of those is true for you, hide it. The rule is not "never abstract" — it is never abstract for a benefit you cannot name. We can name ours, and it is empty.

3The Theory

3.1   Inversion of control, stated precisely

The production-line picture is the intuition. Here is the precise version, because "inversion of control" is a phrase that gets used loosely and the loose version is not useful.

Take any program as a set of things that must happen — start up, handle an event, advance the simulation, draw, shut down — plus a schedule saying when each happens. In the library arrangement, your code contains both: the operations and the schedule that sequences them. In the framework arrangement, your code contains only the operations. The schedule lives somewhere else and refers to your operations by name.

That is the whole of it. Inversion of control is separating a program's operations from its schedule, and giving the schedule to somebody else. Nothing is added and nothing is removed; a boundary is drawn through the middle of what used to be one thing.

Two consequences follow immediately, and both matter today.

First: your operations can no longer share local variables. When one function did all of it, state that spanned phases could live on main's stack — which is exactly how sandbox came to declare 109 locals before its loop even starts. Split the phases into separate functions and anything crossing a phase boundary needs a home that outlives a call. That home is what an object is for, and it is why engine::app is a class you derive from rather than four free functions you register. Those locals become members, and the lifetime question — "how long does this live?" — becomes visible instead of implicit.

Second: control returns. Under a library, your loop keeps the thread; under a framework, you hand it back at the end of every frame. That is what makes the arrangement work in a browser, and it is also a discipline: a function that must return cannot contain a modal loop. If you have ever written a "quick" blocking dialog in the middle of a render, you have met the version of this that goes wrong.

Now the mechanism, because it explains a rule we will have to obey. What does defining SDL_MAIN_USE_CALLBACKS actually do? Follow the includes. SDL_main.h ends by including SDL_main_impl.h, and that header emits this:

Look carefully at what that is. It is not a declaration; it is a function definition, in a header, and it is not inline. Then, a few lines later, SDL_main_impl.h emits the platform's real entry point — main on Unix, WinMain on Windows — which calls SDL_main. Two facts fall out of that immediately, and both will bite somebody:

  • The header may be included in exactly one translation unit per program. Two inclusions are two definitions of SDL_main and of main, and the linker will say duplicate symbol _main. This is the One Definition Rule, not an SDL quirk.
  • The file that includes it must not define main. SDL_main.h ends with #define main SDL_main, so a main() written below the include is quietly renamed and collides with SDL's own. The header says it in capitals: the app "SHOULD NOT ALSO SUPPLY" one.
C++ in place — why the entry point cannot live in the library

This is worth pausing on, because it is a genuinely instructive constraint rather than an annoyance. We are building a static library, and it is tempting to put those four callbacks inside it so no program has to write them. You cannot, and the reason is not about linkers being fussy.

An entry point is not a library's property. If libengine.a defined main, then every program linking the engine would have that main imposed on it, with no way to opt out — and sandbox, three files away, deliberately wants its own. A library's job is to be usable by programs it did not anticipate; claiming the entry point is the one act that makes that impossible.

So the four callbacks are written by a macro, in the program's own .cpp, and the header carrying that macro is the one file in engine/include/ that is not in the umbrella header — because an umbrella whose promise is "include everything, it is harmless" must not be a way to acquire a main by accident.

3.3   The frame survives the inversion

Now the question that should be worrying you. Lesson 1.4 derived a loop with a specific shape, and Lesson 1.2 established a contract about the order of two calls inside it:

\[ \text{drain} \;\rightarrow\; \text{tick} \;\rightarrow\; \text{update} \;\rightarrow\; N \times \text{step} \;\rightarrow\; \text{render}(\alpha) \] drain events -> tick clock -> update input -> N fixed steps -> render(alpha)

Lesson 1.2 was emphatic that the drain must come before input::update(), because SDL's internal keyboard state is only refreshed by pumping the queue, and sampling it early reads a frame-stale snapshot. In our loop that ordering was ours to enforce — the drain was five lines above the update, in code we wrote.

Under callbacks there is no drain. Events arrive one at a time in SDL_AppEvent, from a function SDL calls whenever it feels like it. So: does the contract still hold?

It does, and we can do better than trusting the doc comment. SDL's implementation is in the source tree we already fetched:

Pump, then dispatch every queued event to SDL_AppEvent, then call SDL_AppIterate. The drain still happens, in the right place, before the frame. It is just that SDL performs it instead of us. Figure 2 lays one frame out on a timeline.

The point

The contract survived the inversion; its enforcer changed. That is the single most useful thing to take from this section. Inverting control does not alter what must be true about a frame — it moves the responsibility for making it true. And when a guarantee moves out of your code, the right response is not to assume it holds: it is to go and read the three lines that now provide it, which is what we just did.

One consequence is worth stating because it looks like a rule and is not. Under callbacks, SDL_AppEvent is called per event and SDL_AppIterate per frame. So anything that must be answered once per frame — the input snapshot, the clock tick, the accumulator — belongs in iterate. Anything that is genuinely about a single event — a file drop, a text input character, a discrete key press with its repeat flag — belongs in the event callback. That split is the same one Lesson 1.2 drew between levels and edges, arriving from a different direction.

3.3.1   A worked example: how many steps is N?

The one thing about this loop that reliably surprises people is that N is not 1. Under a library loop that is easy to overlook, because the while is right there in front of you. Under callbacks, on_fixed_step is a function somebody else calls, and the temptation to assume it runs once per frame is much stronger. So let us push real numbers through the accumulator and watch.

At 60 Hz the fixed step is

\[ h = \frac{1}{60} = 0.01666667\ \text{s} \] h = 1/60 = 0.01666667 seconds

Now feed it five frames from a machine running at very close to — but not exactly — 60 frames per second, which is the normal case, not a pathological one. Each frame adds its real elapsed time to the accumulator, then takes whole steps of h out for as long as a whole step remains. What is left over is α, expressed as a fraction of a step:

frame 1:  acc = 0.000000 + 0.0161 = 0.016100  →  0.016100 < h
          0 steps,   α = 0.016100 / 0.01666667 = 0.9660
frame 2:  acc = 0.016100 + 0.0172 = 0.033300  →  one step leaves 0.016633
          1 step,    α = 0.016633 / 0.01666667 = 0.9980
frame 3:  acc = 0.016633 + 0.0170 = 0.033633  →  two steps leave 0.000300
          2 steps,   α = 0.000300 / 0.01666667 = 0.0180
frame 4:  acc = 0.000300 + 0.0165 = 0.016800  →  one step leaves 0.000133
          1 step,    α = 0.000133 / 0.01666667 = 0.0080
frame 5:  acc = 0.000133 + 0.0333 = 0.033433  →  two steps leave 0.000100
          2 steps,   α = 0.000100 / 0.01666667 = 0.0060

Five frames, all within 1.6 milliseconds of each other in length, and the step counts are 0, 1, 2, 1, 2. Nothing went wrong; that is the accumulator working. Frame 1 drew a picture with no simulation behind it at all, and frame 3 advanced the world twice before drawing once.

The bug this predicts

Put a [Space]-was-pressed check inside on_fixed_step and act on it, and on a frame with 2 steps the player fires twice from one keypress. Put a ++frame_counter in there and your "frame" counter is now a step counter that sometimes stalls. Both are real bugs, both are invisible at a locked 60 fps on your machine, and both have exactly this table as their cause.

The rule that falls out: edges belong to the frame, levels belong to the step. "Is W held?" is safe in a step — input is frame-coherent, so every step in a frame sees the same answer. "Did Space go down?" is not, and belongs in on_event or in on_frame. Lesson 1.2 drew this line for a different reason; here is the same line arriving as a consequence of the accumulator.

Those numbers are not hand-computed. They come from running the engine's own engine::fixed_step — the arithmetic in a lesson should be produced by the code the lesson is about, or it is one transcription error away from teaching something false.

3.4   Order, and its mirror

Back to §2.2's ladder, now with the third surface added. Figure 3 draws the whole thing.

Two things in that figure are worth drawing out.

The two arrows are the same ladder read in opposite directions. That is the invariant a lifetime-owning layer exists to hold, and in C++ it is not something you have to remember — it is what destructors already do. Members are destroyed in reverse declaration order; locals in reverse construction order. Our stop() writes the reverse order explicitly anyway, because the three handles are raw SDL_* pointers rather than RAII members, and because a reader should be able to see the mirror rather than infer it.

The three dashed markers are the interesting part. Each surface is a point at which you stop climbing:

  • surface::headless — stop before the window, and before video. There is no display to talk to, which is the entire point: this is what makes a build server a valid place to run the engine.
  • surface::gpu — stop after the window. The window is claimed by nobody, ready for gpu_device::create.
  • surface::renderer — the whole ladder, which is Module 1's presentation path.

That middle one encodes a constraint we have been carrying since Lesson 4.2 as a comment and a hope: a window is claimed by an SDL_GPU device or driven by an SDL_Renderer, and there is no order of operations in which it is both. Until today that rule lived in main() as an if with a paragraph above it. Now it is the difference between two enum values, chosen before anything exists — which is the only time it can be chosen, because by the time you could regret the answer the window already belongs to somebody.

3.5   Ownership across a C boundary

One piece of theory left, and it is the fiddliest thing in the lesson.

SDL_AppInit gives you a void** appstate. Whatever pointer you store there is handed back to SDL_AppIterate, SDL_AppEvent and SDL_AppQuit for the rest of the program. That is a perfectly sensible C design: SDL cannot know your type, so it carries an opaque pointer and stays out of the way.

But we have a C++ object with a destructor, and C++'s entire answer to lifetime is "an owner whose destructor runs". A void* has no destructor. So there is a gap, and the question is how to cross it without a leak and without a double free. Figure 5 is the shape of the answer.

C++ in place — unique_ptr::release() and reset()

std::unique_ptr<T> is the course's default owner: it holds a pointer, and when it dies it deletes what it holds. Two members exist specifically for handing ownership to and from code that does not speak unique_ptr:

  • release() returns the raw pointer and forgets it. The unique_ptr is now empty and will delete nothing. You have taken ownership back, and you are on the hook.
  • The constructor unique_ptr<T>(raw) does the reverse: it adopts a raw pointer, and will delete it at end of scope.

Together they are the sanctioned way to pass an object through an API that only understands raw pointers. The pointer is genuinely unowned in between, and the discipline is to make that interval as short and as branch-free as you can manage.

Now the part that looks wrong and is not. Our init publishes the pointer to SDL before anything that can fail:

The instinct is to publish only on success — build everything, and hand the pointer over once you know it worked. Follow that through. If start() fails, the unique_ptr destroys the instance here, and *appstate stays null. SDL then calls SDL_AppQuit(nullptr, SDL_APP_FAILURE) — the header is explicit that quit runs "in all cases, even if SDL_AppInit requests termination at startup" — and our quit function receives a null pointer with no way to distinguish "never built" from "already cleaned up". Two cleanup paths, and a null that means two different things.

Publishing first collapses that: there is one owner, one teardown path, and one function that deletes. The window in which the raw pointer is unowned contains no branches at all — three statements, none of which can fail, and the last of them hands it to SDL. That is the trade, and it is worth being able to make it deliberately rather than by instinct.

§4 builds all of this. But there is one design rule to state before we write code, because it is the thing that keeps offering two arrangements from becoming two engines — and Figure 5 is the whole of it.

The rule that keeps this from becoming two engines

engine::app is implemented on engine::platform, never beside it. Every service the framework offers is reachable from the library path, and nothing in app.cpp does anything a hand-written main() could not. The moment that stops being true, the framework has begun growing a private engine inside itself and the library path has quietly become second-class — which is how a "convenience wrapper" ends up being the only supported way to use a system.

§5 measures this rather than promising it: verify_52 renders six frames down each path and compares the framebuffers byte for byte.

4.2   surface: a constraint made structural

Now start(). Read it as the ladder from Figure 3, with the surface deciding how far up it climbs:

Three things about that are deliberate.

Every failure calls stop() and returns false. Not a goto cleanup, not four bespoke unwind sequences — one function that destroys whatever exists, guarded per handle, and is safe to call on a platform that has barely started. The renderer branch is the one that matters, and it matters by omission. Lesson 4.2's rule used to be a comment above an if; it is now the difference between two enum values, and — this is the part that makes it structural rather than documented — the choice must be made in the config, before start() is called, which is the only moment at which it can still be made.

Three lines, and the ordering inside them is Lesson 1.2's contract and Lesson 1.3's. Putting them here does not make them more correct — it makes them correct once. A demo can no longer sample input before the drain, or read dt() from a clock it forgot to tick, because those calls are no longer written in the demo.

Then the seam. This is the single most load-bearing design decision in the file:

handle() takes one event and knows nothing about where it came from. In the library path, pump() — or your own drain, if you have per-event business — feeds it from SDL_PollEvent. In the framework path, SDL_AppEvent feeds it. One implementation, two ways in, and that is precisely what makes the two arrangements the same engine rather than two.

Never call pump() from a callback

Under SDL_MAIN_USE_CALLBACKS, SDL pumps and dispatches the queue itself. Calling SDL_PollEvent from inside SDL_AppEvent or SDL_AppIterate means racing SDL for the same events: you would consume some of them, SDL would deliver the rest, and input would go intermittently missing in a way that looks like a hardware fault. The header says so, and so does pump()'s doc comment.

Finally, presentation is deliberately two calls rather than one:

Lesson 3.10 needed that split to make the frame budget honest: on a vsynced frame SDL_RenderPresent blocks, and a profiler bar that is 90% "waiting for the monitor" says nothing about your renderer. It turns out the same split is exactly the gap a HUD wants — after our pixels are on the screen, before the screen is shown. One seam, two reasons, which is usually the sign of a seam in the right place.

4.4   app, app_runner and ENGINE_MAIN

Now the framework half, which after all that is small. engine::app is a base class with seven virtuals — one per phase of Figure 2 — and one of them is pure:

C++ in place — virtual functions, and the destructor that must be one

A virtual function is a call that is resolved by the object's type rather than the pointer's. app_runner holds an app* and calls on_frame; the object is really a pong_app, so pong_app::on_frame runs. That indirection is the entire mechanism by which "the engine calls you" is possible without the engine knowing your type.

= 0 makes on_frame pure: app cannot be instantiated, and a subclass that does not override it will not compile. That is the right shape here — a program that draws nothing is not a program — while every other hook has a default that does the right nothing.

And virtual ~app() = default; is not optional. app_runner::quit destroys the instance through an app*. If the destructor were not virtual, only app's part would run — the derived class's members would never be destroyed, silently, with no diagnostic. A base class with virtual functions and a non-virtual destructor is one of the few C++ mistakes that leaks by design.

The four callbacks themselves live in app_runner, a struct of four static functions. And iterate is the payoff of the whole lesson — read it against Lesson 1.4's loop:

Nine lines. That is the entire framework. Everything else in the file is guards, ownership and logging.

Two of those guards are worth a sentence because they are not redundant. iterate checks running() both before and after the frame. The check at the top declines to start a frame after a quit has been requested. The check at the bottom refuses to abandon one — a quit requested during a frame still lets the frame finish, which is exactly what --shot depends on: draw, write the file, then exit.

The top guard was found by the harness, not by design

Honest history: iterate originally had only the bottom check, and verify_52 §D failed on the assertion that no further frame is drawn after request_quit(). SDL's own loop happens to guard this — it reads its result atom before calling iterate — so the gap would never have appeared in a running program. But a callback should be total: safe to call at any moment, including one SDL would not have chosen. That property is what lets a test drive the four functions directly, which is how §D works at all.

Last, the macro. It contains no logic — four one-line forwards — and that is on purpose:

A macro is code the debugger struggles to step through and the compiler reports odd line numbers for, so the only thing worth putting in one is the part that genuinely cannot be a function — here, the four fixed C symbol names SDL is going to look up. Everything else is an ordinary function in an ordinary .cpp, breakpointable and testable. That is not fastidiousness: it is why verify_52 can call app_runner::init directly, with no entry point and no window, and drive a whole program's lifecycle from a test.

4.6   pong, extracted

And here is the thing the lesson exists for. Pong leaves sandbox and becomes demos/pong/main.cpp: 87 lines of code, five overrides, zero SDL lifecycle calls.

Two of those overrides are worth reading, because they are the practical form of §3.3's rule about edges and levels.

Note event.key.repeat. Holding a key produces a stream of key-down events with repeat = true, and ignoring those is how you get one toggle per physical press — without maintaining an edge table of your own. That information exists only on the event; input::key_pressed() gives you the edge but not the reason. Which is a fair summary of when the event hook earns its place.

Reading the keyboard inside the step loop looks careless and is not. Lesson 1.2 made input frame-coherent: the snapshot is published once per frame and does not change until the next update(). So on the frame that takes two steps, both steps see the same keyboard — which is what you want, and is why this needs no "read the intent once before the loop" dance. The frame-coherence guarantee is being used, not worked around.

The last line is Lesson 1.4's rule about teleports: after a point is scored the ball jumps to the centre, and a renderer asked to draw 40% of the way between "past the paddle" and "at the centre" draws a smear across the whole court. It moved from sandbox unchanged.

4.7   sandbox, which keeps its loop

Now the decision that will look, at first glance, like the lesson losing its nerve.

sandbox adopts engine::platform. Its forty lines of start-up and four teardown paths become one object; its texture upload becomes blit_framebuffer(); SDL_Init, SDL_CreateWindow, SDL_CreateRenderer, SDL_CreateTexture and every matching Destroy are gone. Thirty-one lifecycle calls become three.

It does not adopt engine::app. It keeps main() and it keeps while (plat.running()). Here is the argument, and it is not "we ran out of time":

  • It runs three incompatible loops and picks between them at runtime. run_gpu_scene, run_gpu_probe and the software demo are three different programs with three different loops, chosen by a command-line flag. Expressing that as one app subclass means a class whose every hook opens with a three-way branch — the framework fighting the program rather than carrying it.
  • It is the instrument. Every measured claim in Modules 2 through 4 was taken with this binary. An instrument should have its control flow visible in front of you, not distributed across seven overrides and a base class.
  • Somebody has to prove the library path still works. If every program in the repository used app, then platform's standalone usability would be a claim nobody tests. sandbox is that test, and it runs on every build.
The general rule

A framework you built is still a framework, and the question "should this program use it?" does not get a free pass because you own it. The pressure to make everything adopt the new thing is strong and mostly vanity: a codebase where every program uses the framework looks more finished. What it actually means is that the layer underneath has no independent users, and a layer with no independent users drifts into being an implementation detail of the layer above it — at which point you no longer have two layers, you have one with a confusing internal split.

The one-line version, for deciding this on your own code: use the framework when your program wants a loop; write your own when your program wants this loop.

4.8   A small promotion: save_ppm

One more thing came out of the demos. Both hello_cube and demo_scene.cpp had hand-rolled the same PPM writer, so it moves into engine/gfx/image.hpp beside load_image. It is fifteen lines, and the only interesting part is why the format is PPM rather than PNG when stb_image_write is one #define away:

Why a test artifact should be a dumb format

PPM is an ASCII header followed by raw RGB bytes. No compression, no filter modes, no metadata, no timestamp. Two runs that drew the same picture produce byte-identical files, so cmp is a valid renderer test. A PNG of the same picture may differ in bytes for reasons that have nothing to do with pixels — encoder version, filter heuristics — which takes the cheapest possible check away exactly when you need it. Every --shot in this repository, and the golden image Lesson 5.1's refactor was verified against, is a PPM for this reason.

It writes one buffered row at a time rather than one SDL_WriteIO per pixel: at 320×180 that is 180 crossings of an I/O boundary instead of 57,600, and the rule generalises — a boundary is expensive per crossing, not per byte.

5.1   What is still on the wrong side

Lesson 5.1 ended with a list of things it had not fixed, on the grounds that a refactor lesson ending "and now it is clean" is lying. The same applies here.

  • sandbox is still 5,625 lines. Pong left; four demos remain welded together. The mechanism to separate them now exists and the argument for doing so is unchanged — but each extraction is a real piece of work, and doing four of them in one lesson would have buried the layer that makes them possible. Expect them to leave one at a time as later lessons need them.
  • No window-resize handling. The platform creates a resizable window and then ignores SDL_EVENT_WINDOW_RESIZED. Today that is harmless — the framebuffer is scaled to fit by the renderer — but the GPU path will care, and on_event is where it will be handled.
  • The GPU surface gives you a window and wishes you luck. surface::gpu stops at the window; creating the device, the swapchain and the present target is still the program's job. That is honest for now, and it is the seam where a future gpu_app would sit.
  • Nothing here is thread-aware. SDL's own documentation notes that SDL_AppEvent may be called concurrently with SDL_AppIterate for events pushed from other threads. We have no other threads yet, so the hazard is theoretical — and Module 8's job system is where it stops being theoretical.

8Common Pitfalls & Debugging

1 · duplicate symbol _main

Symptom. The link fails with duplicate symbol _main or _SDL_main, naming two of your own object files.

Cause. <engine/platform/main.hpp> is included in two translation units. It emits a real, non-inline definition of SDL_main and of the platform entry point, so two inclusions are two definitions.

Fix. Include it in exactly one .cpp per program — the one with ENGINE_MAIN at the bottom. Every other file includes <engine/platform/app.hpp>, which has no entry point in it.

2 · The same error, from a main() you did write

Symptom. duplicate symbol again, but you are certain the header is included once.

Cause. The file also defines main(). SDL_main.h ends with #define main SDL_main, so your main is renamed to SDL_main and collides with the one the header just emitted.

Fix. Delete it. Under ENGINE_MAIN your program has no main; that is the arrangement. If you want a main, use engine::platform directly and do not include main.hpp at all.

3 · The window opens and closes instantly, exit code 0

Symptom. A flash, and the process is gone. No error printed.

Cause. Almost always on_start() returning false — often by falling off the end of an if chain, since it returns bool and false is a legitimate answer. Look for app: on_start() failed in the log.

Fix. Return true. And note that on_stop() still ran, so a partially built program did get to clean up — which is why the contract is "runs whenever on_start ran, whatever it returned".

4 · Input works, but sometimes misses keys

Symptom. Under the callback path, occasional dropped keypresses; the longer the frame, the worse it gets.

Cause. Something in your code is calling SDL_PollEvent — directly, or through platform::pump() — from inside a callback. SDL already pumps and dispatches the queue; your poll steals events that would have been delivered to on_event.

Fix. Never poll inside a callback. If you need to see raw events, override on_event; it is handed every one.

5 · A key press fires twice

Symptom. One tap on the fire button spawns two bullets, intermittently.

Cause. An edge query inside on_fixed_step. §3.3.1's table: a frame can take two steps, and key_pressed() is true for the whole frame, so both steps see it.

Fix. Edges in on_event or on_frame; levels (key_down) in on_fixed_step. If a step genuinely must consume an edge, latch it in on_event and clear the latch in the step that used it.

6 · SDL_CreateGPUDevice fails with a message about the window

Symptom. The GPU path dies at device creation, having worked yesterday.

Cause. The config said surface::renderer. That creates an SDL_Renderer, which claims the window, and a claimed window cannot host an SDL_GPU device (Lesson 4.2).

Fix. surface::gpu. And note the fix has to be in configure() — by the time on_start() runs it is too late, which is exactly why the choice lives in the config.

7 · --shot works locally, hangs or fails in CI

Symptom. SDL_Init failed: No available video device, or a silent hang.

Cause. A surface that asks for video on a machine with no display.

Fix. surface::headless, chosen in configure() from the same flag that turns on the shot. Check the first log line: it prints surface= and the answer.

9Exercises

  1. 9.1 — Prove the ODR rule to yourself. Add a second .cpp to the pong target that includes <engine/platform/main.hpp> and does nothing else. Build it. Read the error carefully and identify which symbols are duplicated and which object files they came from. Then change the include to app.hpp and confirm it links.

    Hint

    Two symbols are duplicated, not one, and neither is SDL_AppInit. Use nm -g build/demos/CMakeFiles/pong.dir/*.o | grep " T " (or dumpbin /symbols) to see them.

    Solution sketch

    SDL_main and main (or WinMain). Both come from SDL_main_impl.h, which SDL_main.h includes at its end when SDL_MAIN_USE_CALLBACKS is defined. The four SDL_App* functions are not duplicated, because ENGINE_MAIN is only in one file — a useful demonstration that the rule is about the header, not about the macro.

  2. 9.2 — Make the step count visible. Add a counter to pong_app that records how many times on_fixed_step ran this frame, and print it in on_overlay alongside the fps. Run it, then hold a key that makes the frame expensive (or add an SDL_Delay(30) to on_frame) and watch the number move.

    Hint

    Reset the counter at the top of on_frame, not at the top of on_fixed_step — by the time a step runs, the frame's steps are already under way. Or read steps().steps_this_frame(), which fixed_step has been maintaining since Lesson 1.4.

    Solution

    steps().steps_this_frame() in on_overlay is the whole answer; the exercise is really about noticing that fixed_step already tracked it. At vsynced 60 Hz you will see a steady 1 with occasional 0s and 2s — exactly §3.3.1's table. With a 30 ms delay you will see a steady 2, and if you push past 133 ms you will see the step cap bite and dropped_seconds() go non-zero.

  3. 9.3 — A second surface for hello_cube. Add a --frames N flag that runs headless for N frames and reports the average frame time, without opening a window. This is a micro-benchmark, and the point is that the app layer makes one nearly free.

    Hint

    Parse it in configure beside --shot. Count in on_frame and request_quit() when you reach N. For the timing, time().elapsed() gives you seconds since the platform started.

    Solution sketch

    Roughly six lines. The thing to notice while writing it: with no vsync and no display, SDL_AppIterate is called as fast as the CPU allows, so this measures your renderer rather than your monitor — which is the whole reason a headless surface is useful for more than screenshots. Compare the number against the fill figure the sandbox's Lesson 3.10 budget reports.

  4. 9.4 — Handle a resize. §5.1 lists window resizing as unfinished. Add it: override on_event in hello_cube, catch SDL_EVENT_WINDOW_RESIZED, and log the new size. Then decide — and write down — what the engine should do about it: reallocate the framebuffer to match, keep it fixed and let the renderer scale, or something else.

    Hint

    The event carries the new size in event.window.data1 and data2. Before you write any reallocation, ask what breaks: the projector's aspect ratio is baked in at construction, and so is the depth buffer's size.

    Solution sketch

    There is no single right answer, which is why this is the open one. Reallocating on every resize event means a 230 KB allocation per mouse-move during a drag; a real engine debounces, or reallocates only on the final size. Keeping the framebuffer fixed (what we do today) costs nothing and is correct for a deliberately-low-resolution renderer, but would be wrong for the GPU path, where the swapchain really does change size. Write down which you chose and why — that note is the actual deliverable, and Module 6's render targets will make you glad you have it.

  5. 9.5 — The engine challenge: a third arrangement. Some engines offer a third shape — a run() function you call, which owns the loop but returns when the program ends:

    Implement engine::run in terms of platform — it is about fifteen lines — and then argue, in a comment, whether it should exist. Which platforms does it work on? What does it buy over ENGINE_MAIN, and what does it cost?

    Hint

    Write it as configure, start, on_start, then the same while body as app_runner::iterate, then on_stop. You will find you can call app_runner::iterate itself, which is a hint about how thin the difference really is.

    Solution sketch

    It works everywhere main works — and nowhere main does not, which is the answer to "which platforms": a browser is exactly the case it fails, and that is the case ENGINE_MAIN exists for. What it buys is a program that has a visible main and can do work before and after the loop (parse a config file, write a report), and an app that is a local rather than a heap allocation handed to C — so §3.5's whole ownership dance disappears.

    A defensible conclusion either way. Ours: not yet. Three arrangements need three sets of documentation and three things to keep working, and the case for the third is "slightly nicer on desktop" — real, but not yet worth a third supported path. Revisit when something actually needs work done after the loop ends.

10Recap & Next

The engine gained:

  • A platform layer that owns SDL's lifecycle — initialise, window, renderer, streaming texture, and the mirror image on the way down — with one stop() that every failure path and the destructor both use.
  • Three surfaces, which turn Lesson 4.2's "a window is claimed by one or the other" from a comment into an enum chosen before anything exists — and add headless, which makes a machine with no display a valid place to run the engine.
  • An application layer on top of it: seven hooks, four SDL callbacks, and a macro with no logic in it. Lesson 1.4's loop, with the while handed to SDL.
  • A second executable that is a game. Pong is a program now.

And you gained a distinction that is going to keep coming up:

The through-line

Inverting control does not change what must be true about a frame. It changes who is responsible for making it true. Lesson 1.2's ordering contract still holds under the callbacks — SDL enforces it now, in three lines of SDL_main_callbacks.c we went and read. When a guarantee moves out of your code, the correct response is never to assume it survived; it is to find the code that now provides it.

Next: we have been logging with SDL_Log since Lesson 0.5, and platform::start() alone has six calls to it — some of which report a fatal error and some of which report a curiosity, at the same volume, to the same place. Lesson 5.3 fixes that: levels, categories, an assertion macro that survives a release build in the form we actually want, and — the part that takes a whole lesson to argue rather than to write — a coherent error-handling strategy for an engine core that has no exceptions.

That last one has been accumulating debts since Lesson 3.5. image_status, gpu_status, bool plus a log line, and now app_config's "returns false and has already logged" are four different answers to the same question, all of them defensible in isolation and none of them the same. It is time to pick one.
