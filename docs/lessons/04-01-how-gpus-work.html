Module 4 — To the GPU: SDL_GPU · Lesson 4.1

How GPUs Actually Work

A GPU is not a fast CPU. Per lane it is slower — and it finishes first anyway, for three reasons you can measure using the rasterizer you already own. By the end of this lesson your software rasterizer shades in 2×2 quads like the hardware does, wastes lanes like the hardware does, and can tell you exactly how many.

1The Problem

Lesson 3.10 finished Module 3 with a number: 45.47 nanoseconds per covered pixel. A 1280×720 frame of the capstone scene covers about 475,000 pixels, so that is 21.6 ms of fragment work — over the 16.7 ms budget, from one torus and a floor.

A GPU renders scenes with a thousand times that geometry, at four times that resolution, in a fraction of the time. The obvious explanation is that it is faster. It is not. Take any single lane of a GPU and compare it against one core of your CPU: the GPU lane runs at a lower clock, has a shorter pipeline, no branch predictor worth the name, and far less cache. Per lane, per instruction, it loses.

So the interesting question is not "how is it faster" but "what is it doing instead" — and the answer is three specific architectural choices, each of which has a cost as well as a benefit. This lesson is about those three, and about the fact that you can demonstrate all of them on the machine in front of you, in code you already wrote.

This lesson writes no SDL_GPU code, and that is deliberate

Lesson 4.2 introduces the device, the swapchain, command buffers and render passes; 4.3 does the shader toolchain; 4.4 draws the first triangle. Reaching for the API before the model is in place is how people end up with a working triangle and no idea why any of it is shaped the way it is. Today's job is the model — and by the end of it you will have measured most of it rather than been told it.

2Building Intuition

2.1Wide, not fast

Start with the choice that shapes everything else. Consider a chain of work in which each step needs the previous step's answer:

This runs at the latency of a square root and no faster, however many execution units your processor has, because none of them can start until the previous one has finished. Measured on the reference machine: 3.124 ns per step. The processor is mostly idle, waiting for its own results.

Now run several independent chains, interleaved. Nothing about the work changes — same instruction, same count, same data — but now there is always something else to issue while a result is in flight.

Eight chains run at 0.443 ns per step: a 7× speedup from adding no capability whatsoever, only independent work. That is the entire GPU architecture in one table. A GPU is a machine that has decided, at every level of its design, to be the one with something else to do:

  • a memory read that misses cache costs hundreds of cycles — and the GPU simply switches to another group of lanes and comes back;
  • it keeps thousands of lanes resident so there is always another group ready;
  • and it spends its transistor budget on more lanes rather than on the branch predictors and out-of-order machinery a CPU uses to make one lane fast.

This also explains a piece of shader advice that otherwise sounds superstitious: a shader that uses fewer registers runs faster. Registers are the resource that limits how many lane groups can be resident at once. Fewer registers per lane means more groups in flight, which means more independent work available, which means more latency hidden. The word for that ratio is occupancy, and it is the table in Figure 4.

2.2Lanes in lockstep

Having decided to be wide, a GPU makes a second choice: the lanes are not independent processors. They are grouped — 32 on NVIDIA hardware (a warp), 32 or 64 on AMD (a wavefront), typically 32 on Apple and Intel — and every lane in a group executes the same instruction at the same time, on its own data.

That is a huge saving: one instruction decoder, one program counter and one scheduler for 32 lanes instead of 32 of each. The transistors saved go into more lanes. The name for this model is SIMT — single instruction, multiple threads — and it is why a GPU can afford to be as wide as it is.

It also has a consequence that governs how shaders must be written, and §2.4 is that consequence. But first, a smaller group than 32, and one you cannot escape at all.

2.3The 2×2 quad

Every GPU ever built shades fragments in aligned 2×2 blocks of pixels. If a triangle covers one pixel of such a block, all four lanes run the fragment shader; the three that the triangle misses are called helper lanes, and their results are discarded.

That sounds like waste to be engineered away, and it is not, because of a feature you have used without noticing. A fragment shader can ask how fast is this value changing across the screen? — ddx and ddy in HLSL. And the only way to know how a value changes between neighbouring pixels is to have the neighbouring pixel's value. So the hardware computes it: ddx is lane 1 minus lane 0, ddy is lane 2 minus lane 0, and a subtraction is all a derivative ever costs.

This is where mipmapping comes from

Lesson 3.9 ended with a gap it named honestly: bilinear filtering cannot fix minification, because a pixel covering 62 texels reads four of them. The fix is mipmaps — but choosing which mip level requires knowing how many texels one pixel covers, which is ddx(uv) and ddy(uv), which is a difference between neighbouring lanes. Every automatic mip selection on Earth is paid for by helper lanes. Module 6 spends them; today you find out what they cost.

2.4What a branch costs

Back to lockstep. Thirty-two lanes share one program counter, so what happens when a branch sends them different ways?

The hardware cannot run two instructions at once, and it cannot leave half the group behind. So it runs both sides, with the lanes that did not take a side switched off — masked — for its duration. A warp in which even one lane disagrees pays for every path any of its lanes takes.

The measured curve underneath is the part worth dwelling on, because it says the cost is not a property of the branch at all. The same shader, the same branch, the same amount of work — and the cost steps from 1.00× to 1.93× depending only on how the two sides are arranged across the screen. And the step happens exactly where the run length crosses the warp width of 32, which is what tells you the model is right rather than merely plausible.

Hence a piece of real advice that sounds like nonsense until you have seen this: a branch is cheap if it is coherent and expensive if it is not. Branching on a material id is fine when whole objects share materials and ruinous when the id comes out of a texture. Branching on "is this pixel in shadow" is expensive precisely at shadow edges, which is where it looked worth doing.

3The Theory

3.1Lane efficiency, from area and perimeter

How much do helper lanes actually cost? The answer is derivable before it is measured, and the derivation is one sentence: covered lanes live in the triangle's area, and helper lanes live along its edge.

A quad is wasted in proportion to how much of the triangle's boundary passes through it, so the number of helper lanes grows with the perimeter while the number of covered lanes grows with the area. For a shape scaled by a factor k, area grows as k² and perimeter as k. So:

\[ \text{efficiency} \;=\; \frac{\text{covered}}{\text{covered} + \text{helpers}} \;\approx\; \frac{A}{A + cP} \]

efficiency ≈ area / (area + constant × perimeter) — so it falls as the triangle shrinks

For an equilateral triangle of circumradius r, area is (3√3/4)r² and perimeter is 3√3·r, and taking the constant as 1 lane per pixel of edge gives r/(r+4). Here is that prediction against 32 rotations of a real triangle through the real rasterizer:

Our rasterizer understates this, and it is worth knowing why

vertex::x and vertex::y are integers, so a triangle smaller than about a pixel rounds away to zero area and draws nothing at all. Real hardware rasterizes with sub-pixel precision — typically 1/256 of a pixel — so it happily draws triangles far smaller than one pixel, at an efficiency far below 25%. The right-hand end of Table 1 is therefore the optimistic case.

3.2Why 2×2 and not wider

If lanes are grouped for efficiency, why not group pixels in 4×4 blocks and save more scheduling? Because the argument from §3.1 runs the other way too: a wider block has more perimeter per unit area, so it wastes more.

Figure 2 sweeps all four widths over the same triangles. At a circumradius of 8 pixels, 2×2 keeps 75.5% of its lanes and 16×16 keeps 8.9%. Every doubling costs more than the last, and the collapse is worst exactly where modern content lives — small triangles.

So the choice is forced from both ends. 2×2 is the smallest block that can produce a screen-space derivative at all — you need one neighbour in x and one in y, which is three lanes minimum, and a 2×2 square is the cheapest shape containing them. And every larger block wastes more. The hardware picks the smallest block that satisfies a requirement it cannot drop.

Wider SIMT groups still exist, of course — a warp is 32 lanes, not 4. But a warp is built from eight separate quads, which may come from eight different triangles. The grouping for scheduling and the grouping for derivatives are different things, and only the second one is 2×2.

3.4Why state is baked into an object

One structural thing remains, and it is the one that most surprises people coming from older APIs. In OpenGL you set render state with calls: glEnable(GL_DEPTH_TEST), glCullFace(GL_BACK), glBlendFunc(…). In SDL_GPU — and Vulkan, D3D12 and Metal — you cannot. You describe the entire state up front, build an immutable pipeline object from it, and bind that.

You have been doing this since Lesson 3.2 without the name.

fill_style has ten fields; SDL_GPUGraphicsPipelineCreateInfo has nine, which expand to 53 once its nested state structs are counted. They are the same object. That is not a coincidence — Lesson 3.2 adopted the shape deliberately, and 3.4 and 3.9 kept mirroring SDL's field names and enumerator orders — but seeing the two side by side is still the moment the port stops feeling like a leap.

Now, why does the hardware require this? The usual explanation is that it saves the inner loop from branching on state that never changes. That explanation is testable, and our fill loop is the test: it branches per pixel on style.shade, on a value that is constant for an entire draw. Hoisting that branch should be worth something.

Nothing. Slightly worse than nothing. A branch on a value that never changes is predicted perfectly and effectively free, so the folk explanation is wrong.

The real reason is that the driver has to do two expensive things with that state, and both of them are the kind of expensive that is measured in milliseconds. It must validate the combination — is this blend mode legal with this target format, does this vertex layout match what the shader declares — and it must compile a machine-code shader specialised to it, because a real GPU has no runtime "depth test on/off" switch; that decision is compiled in. Doing that once per pipeline is free. Doing it once per draw call would be ruinous.

SDL says so in its own header, in the list of things an application prepares up front:

Render pipelines (precalculated rendering state): use SDL_CreateGPUGraphicsPipeline()

— SDL3/SDL_gpu.h, under “things that are created once and used over and over”

And this is the sixth pressure, arriving on schedule

Lesson 3.10 noted that encode_mode is a per-fragment branch on a draw-constant value — “a compile-time shader variant in a runtime disguise”. Now you can see what it is a disguise for. Our fill_style has four shading modes, two encode modes, two interpolation modes, two blend spaces and now three traversals: 96 combinations, every one of which our fill loop decides at runtime, per pixel. A GPU compiles the one you asked for. That is what a shader is, and Lesson 4.3 is where you get one.

4.4What the helpers cost

Now the same scene at six tessellations, timed both ways — and the prediction, made first: if shading dominates, the quad traversal should be slower by exactly 1 / efficiency.

Note what this means for the number Lesson 3.10 ended on. Our scene is 87.4% efficient, so on hardware roughly one fragment shader invocation in eight would be thrown away — and at 36,866 triangles, more than one in four. That is the real content of "small triangles are expensive", and it is why Nanite-style renderers and every LOD system ever shipped care so much about triangle size rather than triangle count.

4.5A 10% speedup that was not there

One thing happened while building this lesson that belongs in it.

After extracting the fragment into a lambda, the Module 3 harness reported the capstone fragment at 40.46 ns/px against the 46.46 Lesson 3.10 published. A behaviour-preserving refactor with a free 10% is a result, so it got measured properly: two binaries differing only by the extraction, run alternately in one session.

The minimums say 2.5% faster and the medians say 1% slower, which together say no measurable difference. The 10% was session drift — and you can see the drift in the data, because both columns climb monotonically as the machine warms up.

This is Lesson 3.10's own pitfall, violated within a day

3.10 §7 says it in as many words: never compare two numbers taken hours apart; measure both variants in the same run, back to back. It took one day to break that rule, on the very code that lesson was written about. Two things follow. Lesson 3.10's published numbers stand, unchanged. And a refactor's performance claim needs the same control as a feature's — "it should be the same speed" is a prediction, and predictions get measured.

4.6Seeing it: one key

5 cycles the traversal: scanline, quads, and quads with the helper lanes written in debug magenta instead of discarded. That third mode is not a rendering mode, it is a picture of the waste — every triangle grows a magenta fringe, and the fringe is the same width whatever the triangle's size, which is precisely why small triangles suffer.

Magenta is this engine's "this value is not real" convention, used for the third time — checker_at in 3.2, an unbound sampler in 3.9, helper lanes now. No real surface is ever that colour by accident.

The budget panel gains a line reporting lanes shaded, lanes wasted, and the efficiency — and it appears only under a quad traversal, because under scanline every lane is covered by construction and a row reading "100% efficient" would be announcing that the feature is switched off, dressed up as a result.

7Common Pitfalls & Debugging

"Small triangles are expensive" taken as folklore

Symptom. An LOD system that reduces triangle counts and does not get faster, or a tessellation setting nobody can justify.

Cause. Triangle count is not the axis. Lesson 3.10 measured a 2-triangle floor costing eight times a 2,304-triangle torus; today's numbers say the cost of a small triangle is its lane efficiency, which is a function of its size in pixels.

Fix. Reason in pixels per triangle, and pick LOD levels so that triangles stay above a few pixels across at the distance they are shown. Below one pixel you are paying full price for lanes you throw away.

A branch that was cheap in testing and expensive in the game

Symptom. A shader branch benchmarks fine on a test scene and costs 30% in production.

Cause. Coherence, not the branch (§2.4). The test scene had large uniform regions; the real one has the two sides interleaved at pixel scale.

Fix. Measure with realistic data, and where possible move the branch out of the shader entirely — sort draws by material, or use separate pipelines. That is the same "specialise rather than branch" move §3.4 describes, and on a GPU it is the whole reason shader variants exist.

Expecting ddx/ddy to work inside a branch

Symptom. A texture sampled inside an if shows garbage mip selection, or the compiler refuses outright.

Cause. A derivative needs the neighbouring lane's value at the same point in the program. If that lane took the other side of the branch, it does not have one.

Fix. Sample outside the branch and select afterwards, or compute the gradient outside and use an explicit-gradient sample. This is a real constraint you will meet in Module 6, and it falls straight out of Figure 1.

A traversal change that "looks the same"

Symptom. You add a quad walk, the image looks right, and something subtle is wrong three lessons later.

Cause. "Looks the same" is not a test. A helper lane that writes depth, or a coverage rule that differs by one pixel at a shared edge, is invisible until it is not.

Fix. Compare buffers, not impressions: zero pixels differing and zero depth values differing, over a scene with thousands of shared edges. Lesson 3.9's bit-identical blit made the same argument, and both were caught by the same kind of check.

Comparing a benchmark against a number from yesterday

Symptom. A refactor appears to gain or lose 10%.

Cause. Thermal and scheduling drift between sessions (§4.5). It happened in this lesson.

Fix. Build both variants, run them alternately in one session, and report both the minimum and the median. If they disagree about the direction, you have no result.

8Exercises

8.1  Predict before you measure

Before running anything: what lane efficiency would you expect for the floor alone — two enormous triangles — and for a 192-segment torus? Write both down, then use 5 and C to check.

Solution sketch

The floor is close to 100%: two triangles covering tens of thousands of pixels have almost no perimeter relative to their area. The torus at 192 segments measures 72.6%. The gap between those two is the whole of §3.1, and it is why "how many triangles" is the wrong question and "how big are they" is the right one.

8.2  Make the block size a parameter

Generalise the quad walk to an arbitrary power-of-two block and reproduce Figure 2's four curves from the real rasterizer rather than from the coverage-only sweep in verify_41 §D. Do the timings track the lane counts?

Hint

The alignment mask & ~1 becomes & ~(block - 1), and the four hard-coded lane offsets become two nested loops. Everything else is unchanged, which is itself worth noticing.

8.3  Implement ddx

Give the fragment function access to its quad's four uv values and compute ddx(uv) and ddy(uv). Then use them: colour each pixel by log2(max(|ddx|, |ddy|) · texture_size), which is exactly the mip level a GPU would select. Compare it against Lesson 3.9's traced footprint down the floor.

Hint

You will have to shade all four lanes before writing any of them, which means computing the quad's four fragments into a small array first. That restructuring is not incidental — it is why the hardware works in quads in the first place.

Solution sketch

The level should rise steadily toward the horizon and match 3.9 §H's traced footprint of 0.60 texels per pixel at the bottom of the frame to 62.46 near the horizon — i.e. about six mip levels. You have now built the input to mipmapping, three modules before Module 6 builds the mipmaps.

8.4  Find the divergence cliff on your own machine (engine challenge)

verify_41 §E assumes a warp of 32. Sweep the assumed warp width — 8, 16, 32, 64 — against coherence and find where your curve steps. Then look up your GPU's actual wavefront width and compare.

Hint

The step happens where the run length crosses the group width, so the curve for an assumed width of W should turn at a coherence of W. That is a falsifiable prediction about a parameter you chose, which makes it a good test of whether the emulation models anything at all.

8.5  Occupancy, by hand (engine challenge)

Extend §F's chain experiment so each chain carries a small array of live values — 2, 4, 8, 16 floats — standing in for a shader's register usage. Plot throughput against chains × registers. Where does it fall off, and why?

Solution sketch

It falls off when the working set exceeds the physical register file and the compiler starts spilling to the stack. That is exactly what happens on a GPU when a shader's register count reduces occupancy: fewer groups fit, less latency is hidden, throughput drops. You have reproduced an occupancy cliff on a CPU.

9Recap & Next

Module 4 opens not with an API but with a model, and the model is now measured rather than asserted:

  • Wide, not fast. Eight independent chains of identical work run 7× faster than one dependent chain, and 32 run 27× faster. A GPU is a machine built to always have something else to do, and occupancy is that table.
  • Lockstep, and what it costs. A warp executes both sides of a branch its lanes disagree about. Measured: 1.93× when incoherent, 1.00× when coherent, with the step exactly at the warp width.
  • 2×2 quads, and why they cannot be avoided. Derivatives are differences between neighbouring lanes, so the neighbours must run. Efficiency falls from 96.3% on a 64-pixel triangle to 25.0% on a 1-pixel one, and it falls faster for every wider block.
  • Eleven pipeline stages, all of which you have written.
  • A pipeline object with ten fields against SDL's nine — and the measured finding that the usual justification for it (branch cost) is wrong, while the real one (validation and compilation) is exactly why shaders exist.

The engine gained one enum and about a hundred lines, and produced a bit-identical image while doing measurably more work. That is an unusual kind of change and worth naming: it is not a feature, it is an instrument — a way of asking your own renderer a question about a machine it is not running on.

        discarded.
        NOT WASTE TO BE ENGINEERED AWAY — it is where ddx/ddy come from. ddx is
        lane 1 minus lane 0, ddy is lane 2 minus lane 0, so a lane needs its
        neighbours to have run the same code. EVERY AUTOMATIC MIP SELECTION ON
        EARTH IS PAID FOR BY HELPER LANES (and 3.9's minification gap is what they
        buy). Consequence: a derivative inside a divergent branch is undefined,
        because the neighbouring lane has no value at that point in the program.
        ALIGNED TO EVEN COORDINATES IN THE RENDER TARGET, not to the triangle — so
        a triangle cannot arrange to be cheap by being positioned well, and the
        waste depends on its SIZE, not its placement.
        LANE EFFICIENCY ~ A/(A + cP): covered lanes live in the AREA, helpers along
        the PERIMETER. MEASURED over 32 rotations, circumradius -> efficiency:
        64 px 96.3% · 32 px 93.0% · 16 px 86.7% · 8 px 78.5% · 4 px 67.8% ·
        2 px 41.5% · 1 px 25.0%. The r/(r+4) model is optimistic by a few points
        throughout but gets the shape right.
        OUR NUMBERS UNDERSTATE IT: vertex::x/y are INTEGERS, so a sub-pixel
        triangle rounds away and draws nothing. Real hardware rasterizes at ~1/256
        px, so it draws them, at efficiencies below 25%.
        WHY 2x2 AND NOT WIDER, measured at r = 8: 2x2 75.5% · 4x4 48.7% ·
        8x8 30.4% · 16x16 8.9%. 2x2 is the SMALLEST block that can produce a
        screen-space derivative (one neighbour in x, one in y) and every wider one
        wastes more — forced from both ends. A 32-lane warp is EIGHT QUADS, possibly
        from eight different triangles: the grouping for SCHEDULING and the grouping
        for DERIVATIVES are different things, and only the second is 2x2.
        THE COST, MEASURED on the capstone scene: 87.4% efficient, and the quad
        traversal is 1.04x - 1.38x slower than scanline as tessellation rises from
        66 to 36,866 triangles. 1/efficiency PREDICTS every row to within 0.09x;
        where measurement exceeds prediction the gap is the quad walk's own
        overhead (four coverage tests and a mask per block), not the shading.
        THIS IS WHAT "SMALL TRIANGLES ARE EXPENSIVE" ACTUALLY MEANS, and it is a
        statement about SIZE IN PIXELS, not about count (3.10's floor-vs-torus).
  traversal: fill_style::traverse {scanline, quad, quad_debug}, defaulting to
        SCANLINE — what a CPU rasterizer should do, and what every measurement
        before 4.1 was taken against. `quad` is an INSTRUMENT, not a feature: it is
        here to be measured, not used.
        IT MUST CHANGE NOTHING IT WRITES. Verified bit-identical in BOTH colour and
        depth over 2,306 triangles at 640x360 — 0 of 230,400 px, 0 of 230,400
        depths — while shading 21,005 lanes whose results went nowhere. The line
        that guarantees it: THE DEPTH TEST IS FOR COVERED LANES ONLY, because a
        helper lane is not on the surface.
        ONE EARLY-OUT, the one hardware has: a quad with no covered lane is never
        issued. Without it the cost would be the bounding box, not the triangle.
        THE FRAGMENT IS NOW A FUNCTION (a lambda from three barycentric weights to
        a colour, with pipeline state captured) — WHICH IS A FRAGMENT SHADER, and
        has been since 3.6. The only thing separating it from one is that the
        CALLER CANNOT SUPPLY IT. It must now be TOTAL, because it runs for lanes
        outside the triangle: negative barycentrics (2.3 called that useful), a
        w_recip that can be enormous or negative, a uv anywhere at all. Nothing
        reads out of bounds — wrap_texel folds any index (3.9), linear_to_srgb_u8
        refuses a NaN (3.3) — and both guards were written for other reasons.
        quad_stats is an OUT-PARAMETER, not a fill_style field: a pipeline object
        describes how to draw, and this describes what happened. It ACCUMULATES,
        because a per-triangle lane efficiency is not a number anybody wants.
  pipeline-object: RENDER STATE IS AN IMMUTABLE OBJECT, and we have had one since
        3.2 without the name. fill_style has 10 top-level fields;
        SDL_GPUGraphicsPipelineCreateInfo has 9 (53 once its nested state structs
        are expanded). THEY ARE THE SAME OBJECT — deliberately, since 3.2/3.4/3.9
        mirrored SDL's field names and enumerator orders.
        THE FOLK EXPLANATION IS WRONG, AND IT WAS MEASURED. "State is baked in so
        the inner loop need not branch on it" — our loop branches per pixel on
        draw-constant state, and hoisting that branch is worth 0.93x, i.e. nothing.
        A perfectly predicted branch is free.
        THE REAL REASON is that the driver must VALIDATE the combination and
        COMPILE a shader specialised to it — milliseconds, ruinous per draw and
        free once. SDL's own header calls pipelines "precalculated rendering
        state", under things "created once and used over and over".
        OUR fill_style ALREADY HAS 96 COMBINATIONS (4 shading x 2 encode x 2
        interp x 2 blend space x 3 traversal), every one decided at runtime, per
        pixel. A GPU compiles the one you asked for. THAT IS WHAT A SHADER IS.
  pipeline-stages: ELEVEN, AND THE STUDENT HAS WRITTEN ALL ELEVEN.
        vertex shader -> collect_triangles (2.8-2.10) · primitive assembly ->
        index triples (2.12) · clipping -> clip_polygon_near (3.3) · perspective
        divide -> /w (2.10) · viewport -> viewport::to_screen (2.11) · face culling
        -> is_front_facing (3.4) · rasterization -> edge functions + quads (2.2,
        4.1) · interpolation -> barycentric x 1/w (2.4, 3.2) · depth test ->
        depth_buffer (3.1) · fragment shader -> the fragment lambda (3.6-3.9) ·
        blend/write -> row[x] = colour (1.5).
        MODULE 4 DOES NOT TEACH A PIPELINE. It hands yours to hardware, and the
        port is a rename because of the NDC-parity decision taken in Module 2.
  measurement: A REFACTOR'S PERFORMANCE CLAIM NEEDS THE SAME CONTROL AS A
        FEATURE'S. Extracting the fragment into a lambda appeared to gain 10%
        (46.46 -> 40.46 ns/px) against 3.10's published figure. Two binaries
        differing ONLY by the extraction, run alternately in one session: minimums
        say 2.5% faster, medians say 1% slower — i.e. NO MEASURABLE DIFFERENCE. The
        10% was session drift, visible in the data as both columns climbing
        monotonically as the machine warmed.
        THIS BROKE 3.10's OWN PITFALL ("never compare two numbers taken hours
        apart") WITHIN A DAY, on the code that lesson was written about. 3.10's
        published numbers STAND; nothing needed restating.
