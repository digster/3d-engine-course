10Instanced submission

Culling turns a draw list into a set: the survivors. An instanced draw wants exactly that — a set of things differing only in where they are. The two compose directly, and that composition is why they share a lesson:

draw list → cull → visible indices → batch → runs → one draw each

The mechanism has existed since Lesson 4.5. pipeline_desc::instance_buffer, gpu_mesh::draw(pass, instances), an instance-rate vertex binding — all built, demonstrated on a ring of seven tori, and then fed by nothing for eleven lessons. demos/sandbox still carries a hand-rolled 28-byte gpu_instance struct whose only job is to prove the API works. This lesson is the engine learning to produce instances rather than to display them.

10.1 The constraint is stricter than "same mesh"

One instanced draw issues one SDL_DrawGPUIndexedPrimitives with one pipeline, one set of bound textures and one set of pushed uniforms. Everything that is not per-instance vertex data is therefore shared by every instance in the batch. So a batch key is not the mesh. It is

That is the correct answer, and it is in the lesson rather than a claim that instancing helps, because it says the true thing: instancing is a content decision before it is a renderer one. A forest instances beautifully because somebody authored one tree and placed it four hundred times. A hand-built scene of a dozen distinct props instances not at all, and no amount of renderer work changes that.

The third line is the composition working: culling the forest to 200 survivors still yields one batch. Culling narrows the set; it does not fragment it.

10.2 The bytes do not move. The calls do.

gpu_instance is 112 bytes — exactly sizeof(object_uniforms), and a static_assert keeps it that way. It carries the same mat4 and the same three padded normal columns, because the vertex shader needs the same things whichever road they arrive by.

So instancing a hundred objects does not reduce the per-object bytes crossing the bus by one byte. What it removes is a hundred SDL_PushGPUVertexUniformData calls, a hundred vertex-buffer binds and ninety-nine draw calls. Instancing saves submission, and submission is a CPU cost. "Instancing saves bandwidth" is a very common and very wrong summary.

The measured accounting, from §K's sixteen cubes:

Work it through. Per-frame blocks (camera, lighting, cascades) are 592 bytes either way. The uniform road then pushes 112 + 48 per object, sixteen times: 2,560 bytes. The instanced road uploads 16 × 112 = 1,792 instance bytes and pushes the 48-byte material once.

3152 − 2432 = 720 = 15 × 48. The entire byte saving is fifteen material blocks that did not need pushing. The 112-byte matrix block did not shrink by a single byte; it changed road.

10.3 What refuses to batch, and why that is correctness

batch_instances never merges blended draws. Lesson 6.11 established that over is not commutative, so the back-to-front order order_draws produced is part of the picture; sorting by mesh would destroy it, and an instanced draw has no way to express "these hundred copies, in this order, interleaved with those". They come back as single-instance batches in the caller's original relative order, and §I checks that ordering survives rather than assuming it.

Note also what the sort comparator does: it compares pointers. That makes the grouping non-deterministic across runs, since allocation addresses move. For opaque geometry that is harmless — the z-buffer resolves visibility per pixel and does not care what order the draws arrived in, which is Lesson 3.1's property being cashed in one more time. It would be unacceptable for anything order-dependent, which is exactly why blended draws never reach the comparator.

11The tenth pipeline

scene_instanced.vert.hlsl computes the same four outputs as scene.vert.hlsl from the same inputs. The difference is where world_from_model and the normal matrix come from: a constant buffer there, seven vertex attributes here.

There is no instanced fragment shader. scene.frag.hlsl is bound unchanged beside it, because instancing is a question about the vertex stage and the fragment stage never asked. Every Module 6 feature — Cook–Torrance (6.4), normal mapping (6.7), cascaded shadows (6.9), alpha modes (6.11), image-based lighting (6.15) — arrives for free, neither ported nor duplicated. The Output struct is field-for-field and semantic-for-semantic identical to scene.vert's, because it has to be: SDL validates the stage interface at pipeline creation, so a mismatch is a clean failure rather than a wrong picture.

11.1 A 4×4 is four attributes, and the transpose is real

A vertex attribute carries at most four components in every backend SDL_GPU targets, so a matrix cannot be one. It arrives as four float4 at consecutive locations and the shader reassembles it — and which way round matters:

float4x4(a, b, c, d) builds from four rows. Our attributes are columns — engine::mat4's members are literally named c0… c3 and its storage is column-major (conventions §3). So the constructor produces the transpose of what we want, and we say so and transpose it back. The alternative — quietly reordering the attributes until the picture looks right — also works, and leaves the next reader unable to tell a convention from a coincidence. The transpose is free: the compiler folds it into the following mul.

11.2 Eleven attributes, and a cap that had never been reached

The instanced pipeline declares four attributes from gpu_mesh::describe (position, normal, uv, tangent) at locations 0–3, and seven from describe_instances at 4–10. Eleven. pipeline_desc held an array of eight.

Attributes past the eighth were dropped silently. No error, no log line, no assertion — the ninth, tenth and eleventh simply were not there, and the vertex shader would have read undefined values for the last three rows of its matrices.

What caught it was Lesson 4.5's check_layout, which compares the declared attributes against the shader's reflected inputs and reports missing. That is the entire argument for that function's existence, arriving eleven lessons later: a limit that has never been reached cannot tell you it is wrong. Nothing in Modules 4 or 5, and nothing in eight lessons of Module 6, had ever declared a ninth attribute.

The cap is now 16 and the function asserts before refusing, so the next program to overflow it finds out at the call site. The refusal stays for release builds: a missing attribute is a wrong picture, a buffer overrun is worse.

11.3 One new pipeline, not nine

gpu_scene_renderer has held k_styles × k_blends = 9 pipelines since Lesson 6.11, and that header's comment already named where this ends: "Add MSAA (6.14) and it is 18. Add a depth-only variant and 27. Nobody enumerates that; they build the state, hash it, and create on miss."

Instancing is a third axis, and crossing it in would make eighteen. We build one — solid, opaque — and say plainly what is unavailable. That is not laziness dressed as restraint: a wireframe instanced draw is a debugging nicety, and a blended instanced draw is something batch_instances refuses to produce anyway for the ordering reasons in §10.3. So one of the two gaps is a rule rather than a shortcut. The general answer is Module 9's pipeline cache.

Failure to create it is logged and not fatal. A device that cannot build this pipeline can still draw the whole scene through render; losing instancing costs draw calls, not pixels, and returning false would turn an optimisation into a hard requirement.

11.4 The prologue, extracted rather than copied

render_batched needs every one of the ninety lines that precede render's loop — the per-frame uniform pushes, the cascade fallback, the shadow and environment fallback resolution — and none of the loop itself. Copying them would have produced two copies of one rule, which this engine has already paid for twice (Lesson 5.1's four hand-transcribed harnesses; 6.15's two spellings of an ARGB packing).

So they became begin_frame, returning a frame_setup. The split is exactly at "does this change within a frame?" — the same line Lesson 4.6 drew for uniform blocks: data grouped by rate of change, not by what it describes. And because the prologue now has one implementation, the two paths cannot drift.

Adding a member to that class found three that were missing. destroy() had never been taught about black_cube_, black_lut_ or cube_sampler_, all added in Lesson 6.15. It is not a leak — they are RAII members whose destructors run, and each create_* destroys first — but after destroy() the object reported valid() == false while holding three live GPU objects, so "destroyed" and "empty" had quietly stopped meaning the same thing. It was found by adding a member and reading the list, which is the only way a teardown function is ever checked. An argument for having few members, and, in Module 9, for an arena that makes teardown one operation instead of eight.

11.5 One buffer, many batches, addressed by offset

Each batch binds the same instance buffer at a different byte offset:

first is an index into the instance array, so the byte offset is first × sizeof(gpu_instance), and the hardware's instance index counts from zero inside the binding. A separate buffer per batch would also work and would cost an allocation per batch per frame; this costs a different value in an existing field.

11.6 The proof: the same picture, the other way round

§9 established that the golden cannot see any of this. So the instanced path needed its own correctness instrument, and the claim it tests is strong: for a scene of identical opaque objects, render and render_batched must produce bit-identical pixels. Not close — identical. They run the same fragment shader over the same geometry with the same matrices, and neither road changes a float.

Note the middle line, and note that it is a check rather than a comment. The first run of this section reported 0 of 76800 channels differ over two black images and happily declared success — because cube_mesh() carries no normals, every surface was lit by albedo × ambient alone, and the brightest pixel in the frame was 10 against a background of 5. Lesson 4.8 had already found that a vertex shader cannot invent a face normal and added with_normals for exactly this; the fix was one line. But the reason it was caught is that the section counts lit pixels before believing a null difference.

14Common pitfalls & debugging

The entire scene disappears the moment culling is switched on.
Symptom: a black frame, or just the skybox. Cause: a sign error in the row combination — almost always putting the scale on the wrong row, so r₃ − r₀ becomes r₀ − r₃ and the plane's normal points outward. Diagnosis: print the signed distance of the camera's target to all six planes. It must be positive for all six. If left and right report exactly opposite values, that is the tell.
The near plane is in the wrong place, and nothing on screen says so.
Cause: the OpenGL near plane. You wrote r₂ + r₃, which is correct for a −w ≤ z ≤ w depth range and wrong for SDL_GPU's 0 ≤ z ≤ w: it puts the plane at nf/(2f − n), about half the near distance, so the culler keeps a sliver the clipper then removes and the picture never changes. Diagnosis: signed_distance(near, eye) must be −near. If it is about −near/2 (−0.150 for our camera), this is it.
Objects pop out of view at the edge of the screen.
Cause: comparing a sphere's centre distance against 0 instead of −radius. Diagnosis: the popping happens exactly when the object's centre crosses the frame edge, not when its silhouette does.
Instanced objects are all drawn on top of each other at the origin.
Cause: the instance buffer was written into a different command buffer from the one that draws from it, or was not written at all this frame — so the shader reads whatever the buffer last held, or zeros. Fix: record the gpu_stream_buffer::write into the same command buffer, before the render pass begins.
Instanced objects are sheared, or rotate about the wrong axis.
Cause: the matrix was reassembled from rows when the attributes are columns, or vice versa. Diagnosis: a pure translation still works (the translation lands in the last row instead of the last column, so objects move along the wrong axis), while any rotation shears. Fix: the transpose in §11.1.
A pipeline draws nothing, and validation says nothing either.
Cause: more vertex attributes than pipeline_desc holds, silently dropped — before this lesson, anything past the eighth. Diagnosis: run check_layout against the shader's reflection JSON and look for missing. As of this lesson it also asserts at the call site.
expand({1, 2, 3}) will not compile.
Cause: aabb::expand is overloaded on vec3 and const aabb&, and brace elision makes {1, 2, 3} a candidate for both — an aabb whose first member is initialised from three floats. Fix: write expand(vec3{1, 2, 3}). Every existing call site happened to pass a named variable, which is why this has never come up before.
std::vector<int> v(std::size_t(n)); declares a function.
The most vexing parse. std::size_t(n) reads as a parameter named n, so v becomes a function returning a vector — and the error appears forty lines later, at the first use, as an impossible conversion. Fix: static_cast<std::size_t>(n). Braces also work but change the meaning to a one-element vector.

15Exercises

  1. 6.16.1 — The eight corners, the slow way. Implement the naive test from §5 (reject only when all eight corners are outside one plane) and run it against intersects over §D's 50,000 boxes. Prove they agree on every box — not by running it, but on paper, in one sentence — and then measure how much the eight-corner version costs.
    Hint"All eight corners are outside plane P" and "the positive vertex is outside plane P" are the same statement, because the positive vertex is by construction the corner with the largest n · c. If the largest is negative, all eight are. So the two tests are identical in outcome and differ only by a factor of eight in dot products — which is the honest reason to prefer one: not that it is more correct, but that it does one eighth of the work for the same answer.
    Solution sketchThe proof is the hint's sentence: the positive vertex maximises n · c over the eight corners, so "it is outside" and "all eight are outside" are the same statement. Predict the cost before timing it, because it is not simply 8×: the eight-corner loop can stop at the first corner that is inside a plane, so for a box wholly inside (25,859 of §5's 45,512 kept) it does one dot product per plane — the same count as the positive vertex, minus the three selects that find it. It pays all eight only on the plane that rejects a box, and partially on boxes that straddle. So the measured ratio depends on the scene's mix of inside, straddling and rejected boxes, and a number well under 8× on §D's boxes is the expected result, not a mistake.
  2. 6.16.2 — An OpenGL near plane. Change k_near_z's extraction to r₂ + r₃ and run §A. Which checks fail, and which still pass? Then predict, before running §H, what happens to the measured cull rate.
    Solution sketchSolve it before running it. The OpenGL condition is zclip + wclip ≥ 0; with zclip = (f/(f − n))(d − n) and wclip = d, it holds for d ≥ nf/(2f − n) = 0.150 — half the near distance, in front of the camera. So exactly one of §A's checks fails: the eye's signed distance to the near plane reads −0.150 instead of −0.300. The apex still lies on all four side planes (they do not involve row 2), the target is still inside all six, opposite planes are still not negatives, and every normal is still unit length. The cull rate does not move: the only objects the new plane keeps are ones between 0.15 and 0.3 metres from the eye, and §H's scenes have none. That is the lesson of the exercise — the wrong plane is invisible to every picture and every rate, and only the check against a fact finds it. (This lesson's §3.2 originally predicted a plane a far distance behind the camera; working this exercise is what corrected it.)
  3. 6.16.3 — Reversed-Z and the far plane. §4 claims that A + 1 does not cancel under a reversed-Z projection. Build one (swap near and far in perspective), extract its planes, and measure the far plane's error. Does the claim hold? What happens to the near plane's error?
    Solution sketchUnder reversed-Z the far plane is zclip ≥ 0 — row 2 on its own, like our near plane now — and the near plane becomes w − z ≥ 0, a difference of two rows. The far plane's position no longer comes from dividing by A + 1: with near and far swapped the corresponding term is n/(f − n) ≈ 0.003, a small number computed directly rather than as a difference of two nearly equal ones, so §4's 332× amplification is gone. A float32 model of the matrix builder, which reproduces §4's −99.998217257 exactly for the ordinary mapping, puts the reversed far plane at −99.999996905: an error of 3.1 × 10⁻⁶ instead of 1.8 × 10⁻³, about 580× smaller. The claim holds. And the near plane does not inherit the problem: it is now r₃ − r₂, a difference, but of −1 and 0.003 — magnitudes that add rather than cancel — so it stays exact to the last digit. Reversed-Z removes the cancellation from both planes rather than moving it.
  4. 6.16.4 — Cull to the shadow frustum. Lesson 6.8 renders every object into the shadow map. Its light camera is an orthographic projection, so frustum_of works on it unchanged. Wire it up and measure how many objects the shadow pass was drawing for nothing.
    HintCareful: an object outside the view frustum may still cast a shadow into it. The correct volume is not the view frustum.
    Solution sketchThe volume to cull against is the light's frustum — the orthographic box fit_directional builds — because that is exactly the region whose depth the shadow map records; an object inside it can cast into the view even when the camera cannot see it, which is the hint's warning. Extract its planes with frustum_of(light_clip_from_world) and cull the caster list against them. How much it saves depends on how tightly the box is fitted: 6.8 fits it around the whole scene, so on the demo it rejects almost nothing, and that null result is worth reporting with the same care as §9's — then move an object far outside the box and confirm the count goes to 1. The saving becomes real with 6.9's cascades, where each cascade's box covers a slice of the view.
  5. 6.16.5 — Where does collect_triangles want the cull? Wiring the culler into collect_triangles as a default would move the golden — §9 says it cannot, because nothing is ever off screen, but the demo's scene viewport is a 172×97 rectangle inside a 320×180 framebuffer, and the software rasterizer clips to the framebuffer. Construct a scene where those two facts combine to make a correct cull change the picture, and say which of the two behaviours is the bug.
    Solution sketchMake an object that is inside the camera frustum but falls entirely outside the 172×97 viewport rectangle inside the framebuffer — impossible, since the viewport transform maps the frustum onto exactly that rectangle. So go the other way: an object outside the frustum, just beyond a side plane, whose projected triangles land outside the viewport but still inside the 320×180 framebuffer. Uncull'd, the software rasterizer clips only to the framebuffer and draws it in the margin around the scene; culled, it vanishes. The cull is right and the rasterizer is the bug: geometry outside the frustum is outside the viewport by construction, and a rasterizer that draws there is ignoring the viewport's scissor. The fix belongs in the rasterizer — clip to the viewport rectangle — and then the cull becomes invisible, as a correct cull should be.
  6. 6.16.6 — A better sphere. Implement Welzl's algorithm for the minimal enclosing sphere of a mesh's vertices and use it instead of bounding_sphere. Does the pre-test now pay? Measure with §G, not with intuition.
    Solution sketchWelzl's algorithm finds the minimal enclosing sphere in expected linear time by recursing on a random order with up to four support points. It shrinks the radius from the box's half-diagonal to the true minimum — for a sphere-like mesh, from √3 times the box's half-extent down to about 1× — which makes the pre-test's volume much closer to the box's. Measure with §G's two scenes and expect the mostly-off-screen case to improve (fewer boxes survive the sphere and get tested twice) and the mostly-on-screen case not to, because there the pre-test is pure added work whatever its selectivity. §5.2's condition for a cascade to pay — much cheaper and nearly as selective — may now be met in one regime and still not in the other, and that split verdict is the answer.
  7. 6.16.7 — A hierarchy. §5 reports that 25,859 of 45,512 kept boxes were wholly inside. Build a two-level grid over the draw list, classify each cell, and accept whole cells on an inside. Predict the saving from that ratio before you measure it.
    Solution sketchPredict from §5's ratio: 25,859 of 45,512 kept boxes, 57%, were wholly inside. A cell classified inside accepts its boxes without testing them, so the saving is bounded by that 57% of the kept boxes' tests, minus the cost of classifying the cells, and it is only realised to the extent that inside boxes cluster in inside cells — boxes near the frustum's edges share cells with outside ones and still get tested. Expect a saving somewhat below the ratio, growing as the cells shrink until the per-cell cost catches up. The general shape is a hierarchy's promise: test the parent, and skip the children when the answer is unanimous.
  8. 6.16.8 — A material handle. batch_key compares 32 bytes of material with memcmp. Give material_uniforms a handle and compare one pointer. Measure the batching pass on a 10,000-object scene both ways — and then say what the handle costs elsewhere.
    Solution sketchA handle turns a 32-byte memcmp into one integer compare, and the batching pass should speed up in proportion to how much of its time was the compare. What it costs elsewhere is the real answer: two materials with identical values but different handles no longer batch together, so the draw count can go up — equality by value becomes equality by identity. The handle also needs a table (and a lifetime) somewhere, which is 5.4's lesson again. Deduplicate at creation (hash the 32 bytes once, return the existing handle for identical values) and you get both: the cheap compare and the old batching.

16Recap & next

The engine gained two things, and they compose:

  • It knows what it cannot see. Six planes, extracted from the matrix the renderer actually uses so they cannot drift from it, tested against per-object boxes at 58 ns each. Conservative in two directions, both measured, and wrong only in the direction that is allowed.
  • It submits what is left in fewer calls. A visible set becomes runs sharing a batch key; each run becomes one instanced draw reading its matrices from a vertex buffer instead of a constant buffer. Sixteen draws became one, and the picture came back bit-identical.

Four things are worth carrying forward beyond the technique:

  1. Derive from what the system already knows. The planes come from clip_from_world rather than from a camera, so there is no second copy of the truth to fall out of step.
  2. Verify against facts, not against a reference. The eye is the apex; four zeros follow. And four zeros were not enough, because the bug we actually made would have passed them.
  3. Sweep the axis the effect depends on. Six confident data points along the wrong axis look exactly like a measurement.
  4. Know which instruments are blind to your change. The golden did not move, and that meant nothing at all.

Next, Lesson 6.17 — A Frame Graph. Module 6 has accumulated passes: a shadow pass, a cascade loop, the scene pass, the bloom chain's downsamples and upsamples, the tonemap resolve, the skybox. Each was wired in by hand where it was built, and each knows the names of the targets it reads and writes. That is eight passes with hand-managed dependencies between them, and this lesson just added a ninth path through the scene pass. The frame graph is what turns "the renderer runs these in this order because that is the order they were written in" into a structure that can say why — and can then notice that two targets never overlap in time and share the memory.
