4Implementation

4.1The handle

Start with the layout constants, because every other line in the file is derived from them and putting them first means the split is stated once rather than open-coded five times.

The static_assert is not decoration. Change one constant to experiment with the budget — Exercise 9.2 asks you to — and the assertion fires at compile time rather than letting the two fields overlap and produce handles that alias in a way that would take a very long evening to find.

The handle itself is a struct with one member and four accessors. It has no invariant to defend, so the member is public: a handle is a value, and Module 9's serializer wants exactly that word.

C++ in place — = default on a comparison, and why it matters here

C++20 lets you ask the compiler to generate operator== memberwise. For a one-member struct that is a single 32-bit compare, which is the cheapest possible implementation and also the correct one — two handles are equal exactly when they name the same occupant of the same slot.

Writing it by hand would be four lines that do the same thing until the day somebody adds a member and forgets one of them. The friend keyword makes it a non-member found by argument-dependent lookup, which is the modern idiom: it treats both operands symmetrically and it is what =default is designed for.

Note also explicit on operator bool. Without it, h1 + h2 would compile — two handles quietly converting to bool and adding up to 2. explicit keeps if (h) working and makes the nonsense a compile error.

And the packing primitive. Note that it masks rather than rejects out-of-range input: the range check belongs to whoever is allocating slots, and mixing the two would mean this function needed a way to fail.

Push a number through it by hand. Slot 2, generation 3: the generation shifts left by twenty to become 0x0030_0000, the index contributes 0x0000_0002, and the handle is 0x0030_0002 — 3,145,730 as an integer, which is a perfectly useless number and exactly why index() and generation() exist. Reading it back: bits & 0x000F_FFFF is 2, and bits >> 20 is 3.

4.2The pool: three arrays

Now the container. There is a fifteen-line version of this — one array of items indexed directly by slot, plus an array of generations — and it fixes all three failures. We are not going to write it, and the reason is worth having in front of you before the code.

A slot-indexed array is sparse. Free slots are holes in it. Iterating means walking every slot and testing each one, touching cache lines that contain nothing you want, and the ratio of waste to work grows with every object you ever destroyed. Lesson 5.6 is going to measure exactly this and Lesson 5.8's ECS is going to live or die on it, so the right shape is worth thirty extra lines today.

So: three arrays, and one indirection between them.

@@FIG_ANATOMY@@

Read the roles rather than the types. slots_ is stable — one entry per slot ever created, never moved, indexed directly by a handle's index field. items_ is mobile — a plain std::vector of live objects with no holes, which reallocates as it grows and moves everything it owns, and that is a feature rather than a hazard because nothing outside this class holds an address. owners_ is the way back: owners_[d] is the slot that items_[d] belongs to.

And note the small piece of design in slot::dense. It is the item's position and the occupancy flag: k_no_dense means "this slot holds nothing". A separate bool occupied would have been a byte per slot, a second thing to keep in sync, and a second thing to forget to check. One sentinel does both jobs and cannot disagree with itself.

4.3insert, and the free list

Three things in here are decisions rather than mechanics.

The reused slot's generation is not touched. It was bumped on the way out (§4.4), so it already holds a value no outstanding handle carries, and the insert simply hands it out. This is §3.3's "bump on removal" paying off: the free path did the work, so the allocate path has nothing to remember.

Running out of slots returns null, it does not assert. Lesson 5.3 gave us one question for this: could a correct program, on a working machine, encounter this? Loading a scene with a million and one meshes in it is something the world can do to correct code, so it is an error that ships, not an assertion that is compiled out. The caller tests the handle exactly as it would test a failed allocation.

The free list is LIFO. A vector used as a stack is the cheapest structure there is, and the most recently freed slot is the one still warm in cache. The cost is the one §3.4 named: hot allocate/free pairs hammer one slot's generation, which is what makes wrap-around reachable at all. We take the trade and monitor it.

4.4remove: swap and patch

Removal is where a dense container earns its keep and where the interesting bug lives. The dense array must stay packed, so the hole has to be filled — and the only element we can move without disturbing anything else is the last one.

@@FIG_REMOVE@@

The line marked the patch is the one to stare at. Having moved the last item down into the hole, its old dense position is gone — so the slot that owns it must be told where it lives now, and owners_ is the only way to find that slot without searching. Delete that one line and the pool still compiles, still passes a casual smoke test, and corrupts itself the first time you remove anything other than the last element.

The if (dead != last) guard is not an optimisation; it is correctness. Self-move-assignment (items_[d] = std::move(items_[d])) is not required to leave an object in any particular state, and a std::vector member is entitled to end up empty. Removing the last element without the guard would occasionally be fine and occasionally clear the wrong mesh.

items_[last] = T{} deserves a sentence too. pop_back alone would shrink the vector, but a moved-from mesh_data is not required to have released its four buffers — the standard says "valid but unspecified", and a vector that keeps its capacity is a perfectly valid unspecified state. Assigning a default-constructed T releases it for certain. A pool quietly holding a freed mesh's megabytes is a leak with a clean bill of health.

Removal invalidates more than you removed

The item that moved also changed address. So remove invalidates pointers into the pool generally, not just the one you destroyed. This surprises people, it is unavoidable in any packed container, and it is exactly the class of hazard handles exist to make survivable: the moved item's handle is untouched, because its slot was patched.

4.5contains, get, and the one rule

Three tests, and §3.3 said which failure each one rejects. The range test rejects a fabricated handle or one from a pool with fewer slots. The dense test rejects a slot that is currently free. The generation test rejects the interesting case — a slot that is live again with a different occupant. The null handle needs no special case: its generation is 0 and no live slot ever carries 0.

The one rule

Resolve late, use immediately, never store. The T* that get() returns is valid until the next insert or remove and not one instruction longer. Caching one across a call that mutates the pool re-creates precisely the bug this whole file was written to abolish — with the extra insult that it now looks like modern, handle-based code.

That rule has a consequence worth pointing at, because it is the thing that makes handles cheap as well as safe. get() costs about 0.13 ns more than a dereference (§5). Do it once per object per frame and it disappears into the noise; do it once per vertex and you have built something slower for no reason. So the shape of correct code is: resolve at the boundary, work through the view. §4.7 is that sentence applied to the renderer.

4.6Converting the mesh subsystem

We convert one subsystem end to end, as Lesson 5.3 did — meshes, because scene_object::geometry is a borrowed view today and is the thing that breaks first. No new container was needed: pool<T> knows nothing about geometry, so the whole of the mesh side is two aliases and a copy helper.

to_mesh_data is the bridge from Lesson 2.12's inline constexpr arrays to storage the pool controls, and it is a genuine copy: eight positions and thirty-six indices for the cube, 636 bytes for all three built-ins, once at start-up. It would have been possible to let the pool hold views instead — and that would be a pool handing out handles to memory it does not control, which is the problem this lesson is solving rather than a clever way around it. The built-in shapes are the one case that would have been safe to borrow, and they go in the pool anyway, because "this particular mesh is safe to borrow and that one is not" is exactly the distinction a caller should never have to keep in their head.

4.7The renderer resolves at the boundary

collect_triangles gains one parameter and eight lines. Here is the shape:

Three things are happening in eight lines, and all three are the point of the lesson.

The failure has a location. Before, an object whose geometry had been freed read through a dangling span somewhere inside a per-vertex loop; now it fails on a named line, at the top, before any work. That is the difference between a bug and a symptom.

One missing asset costs one object, never the frame. We continue rather than bail, because a renderer that refuses to draw anything because one mesh is missing is worse than one that draws the rest and says so.

The resolution is hoisted. The old code wrote objects[i].geometry.vertices[v] inside the per-vertex loop. Resolving per vertex would have made handles cost something real — a lookup on the torus's 1,225 vertices instead of one. Resolve at the boundary, work through the view. This is not a micro-optimisation we happened to notice; it is the rule from §4.5 applied at the one place it matters most.

The new parameter deserves a defence, because Lesson 5.1 spent a whole section celebrating collect_triangles going from fifteen parameters to eight, and this takes it to nine.

The parameter is not clutter, it is the cost of the design made visible. A handle is half a reference; the pool is the other half; and a function that resolves handles needs both. The alternatives are worse. A global mesh pool would remove the parameter and replace it with an invisible dependency that cannot be tested, cannot be swapped, and makes two pools impossible — and this lesson has two pools by the end of §4.8. A pool pointer stored inside each handle would make handles twelve bytes and put us back where we started.

Module 5's ECS will eventually fold the pools into a world object that carries them together, at which point this becomes one parameter again. But a context object invented before three callers have asked for one is a guess, and Lesson 5.1's rule stands: let the pressure accumulate until the shape is obvious.

A dangling std::span is not detectable, so an object whose geometry had been freed either drew garbage or crashed, and in neither case was there anything to count. 4.8Five tests become two

Finally, back to §1's worst offender. Lesson 4.8's mesh cache compared five things to decide whether it had seen a mesh before, and its own comment admitted that four of them were scaffolding around an address that could not be trusted.

The first test is a single 32-bit equality, and it is correct rather than approximately correct. Rebuild the floor and the handle changes, so the cache misses and re-uploads — which is what you wanted, and which the old key could only achieve by comparing vertex counts and hoping two different meshes never had the same shape.

The cache also gains a second pool, and this is a small design point worth naming. Its entries hold geometry it produced — with_normals output, a different vertex count and a different index buffer from the mesh it came from. That is a mesh in its own right, so it goes in a pool of its own rather than being carried around as a struct member:

meshes holds what was authored or loaded; derived_ holds what an import step made from it. Lesson 5.5 gives that relationship a name and a lifetime policy; today it is enough that both are addressed the same way, and that the software path can draw the derived geometry by being handed meshes.derived() — which, note, is a second pool in the same frame, and therefore the concrete reason §4.7 refused a global.

8Common Pitfalls & Debugging

1 · A cached T*, which is the whole bug coming back

Symptom. Everything works until a level loads, then one object draws garbage — and it is not the object you just loaded.

Cause. Somebody resolved a handle once, stored the mesh_data* in a struct, and used it next frame. insert reallocated; remove moved an item. The pointer is stale and it looks like modern handle-based code, which makes it harder to spot than the pointer it replaced.

Fix. Store the handle, resolve at the point of use. grep -n "mesh_data\*" across your own code and check every result against the rule: resolve late, use immediately, never store. If a hot loop genuinely needs the pointer, hoist it above the loop and take care that nothing inside the loop mutates the pool.

2 · error: explicit qualification required to use member 'handle'

Symptom. Writing handle<mesh_data> h; inside a class that has a member function called handle() — which several of ours do, since gpu_device::handle() and friends return the underlying SDL object — produces a baffling error about a dependent base class.

Cause. Name lookup finds the member first. This is not a hypothetical; it reproduces in four lines.

Fix. Use the alias (mesh_handle) or qualify (engine::handle<mesh_data>). The aliases exist partly for this reason, which is why every line of engine and demo code in this lesson uses one.

3 · Everything resolves, but you are drawing the wrong mesh

Symptom. get() never returns null and the picture is still wrong.

Cause. Almost always a handle stored in two places, one of which was updated on reload and one of which was not — a copy of a scene_object taken before the rebuild, say. The handle is not stale; it is a valid handle to a mesh you no longer mean.

Fix. A handle is a value, so treat it like one: derive it from a single source each frame rather than copying it forward. build_scene is the pattern — it rebuilds the whole object array from the library every frame and never carries a handle across.

4 · remove() corrupts the pool for everything but the last element

Symptom. Remove from the middle, and some other handle starts resolving to the wrong item or to nothing.

Cause. The patch line in §4.4 is missing or wrong: slots_[owners_[dead]].dense = dead;. The moved item's slot still points at where it used to be.

Fix. The test that catches it is §C of the harness — remove from the middle, then check every surviving handle. A smoke test that only ever removes the last element will pass forever with this bug in place.

5 · A handle from the wrong pool

Symptom. A handle that is definitely valid resolves to null, or worse, resolves to something unrelated.

Cause. Two pools of the same type — which §4.8 now has — and the handle was minted by the other one. The type system cannot help: both are mesh_handle.

Fix. Keep the pool and its handles together structurally, as mesh_library and scene_mesh_cache both do. If you have several pools of one type and they are genuinely interchangeable at call sites, a per-pool id compiled into debug builds and checked in contains() is the standard next step — Exercise 9.4.

6 · generation_wraps() is not zero

Symptom. The warning fires: pool: generation wrapped on slot 3.

Cause. One slot has been recycled 4,095 times. Almost always a remove/insert pair in a per-frame path — updating an asset in place by replacing it, once a frame, forever.

Fix. First ask whether the churn is necessary; a mesh that is rebuilt every frame probably wants to be mutated through get(), not replaced. If the churn is real, switch the free list to FIFO (§3.4) or widen the handle. Do not ignore it: it is the one failure mode this design does not close.

9Exercises

  1. 9.1 — Break it on purpose. In demos/hello_cube/main.cpp, add a line to on_start() that removes the cube from the pool immediately after inserting it. Predict what you will see before you run it, then run it. Now do the same experiment against the pre-5.4 code (git stash is your friend) by clearing cube_'s vectors after taking the view.

    Hint

    Ask collect_triangles for its stats — pass a collect_stats and print unresolved.

    Solution sketch

    After: a black window, unresolved == 1, and no crash — the failure is reported and localised. Before: on most machines, a perfectly normal cube, because the freed vector's memory has not been reused yet and still contains the vertices. That second result is the important one. The old code is not broken in a way you can see, which is precisely why it survived four modules and would have survived into a shipped game.

  2. 9.2 — Move the split. Change the bit budget to 24 index / 8 generation and run the harness. Which checks fail, and are they failing because the code is wrong or because the test encoded the old budget? Then compute the new wrap time at 60 Hz and decide whether you would ship it.

    Hint

    Only the two constants at the top of handle.hpp should need touching. If anything else needs touching, that is a finding worth writing down.

    Solution sketch

    §A's explicit 1048576 / 4095 check fails, and §D's "4,095 recycles" fails — both because the test hard-codes the budget, which is the right way round: a test that adapts silently to a changed constant is not testing the constant. Nothing in the pool needs changing, which is the real result. 8 bits gives 255 generations, so one slot recycled at 60 Hz wraps in 4.25 seconds — comfortably reachable by a reload key held down, so no, not for entities. For a pool of at most a few hundred long-lived assets it would be fine, and the freed twelve bits buy nothing anybody needs. That is the shape of the argument either way: what churns, how fast, and for how long is a handle held?

  3. 9.3 — FIFO free list. §3.4 claims that reusing the oldest freed slot multiplies the time-to-wrap by the number of slots. Implement it — a std::deque, or a head/tail index into a ring — and change §D of the harness to prove the claim on a pool of 16 slots.

    Hint

    With N slots in rotation, a given slot is recycled once every N frees, so its generation advances N times more slowly.

    Solution sketch

    free_slots_.front() plus pop_front() on a std::deque is the whole change. With 16 slots the wrap takes 16 × 4,095 = 65,520 recycles instead of 4,095. Now measure insert: LIFO is faster, because the slot you just freed is in L1 and the one you freed 65,000 operations ago is not. That is the trade, and it is a real one — which is why the choice is a comment in the header rather than an accident.

  4. 9.4 — Catch the foreign handle. Pitfall 5 is the one hole the type system does not close: two mesh_pools, and a handle from the wrong one. Close it. Give each pool a small id, steal a few bits or add a debug-only field, and make contains() reject a handle whose pool id does not match.

    Hint

    Stealing bits is the interesting version, because it forces you to say which budget pays for it. A debug-only std::uint16_t alongside is the version you would actually ship, and Lesson 5.3's SDL_ASSERT_LEVEL is how you gate it.

    Solution sketch

    A static counter handing out pool ids, an id stored in each pool, and — in a build with assertions — a parallel std::vector<std::uint16_t> of the id each handle was minted with, checked in contains(). Stealing 4 bits from the generation instead gives 255 generations and 16 pools, which §3.4's arithmetic says is a bad trade for assets. The general lesson: when a check cannot be made free, make it free in release and present in development, which is exactly the shape of ENGINE_ASSERT.

  5. 9.5 — Compact it. §3.6 claims that handles make storage relocatable. Cash the claim: add pool::shrink_to_fit() that releases unused capacity, and then the harder one — a defragment() that reorders items_ into handle-index order so that iteration matches allocation order. Prove with the harness that every outstanding handle still resolves afterwards.

    Hint

    Reordering the dense array means recomputing every slot::dense and every owners_ entry. Sort the dense indices by their owner, then walk once and patch. There is no way to do this at all with raw pointers, which is the point of the exercise.

    Solution sketch

    Build a permutation of [0, size) sorted by owners_[d], apply it to both items_ and owners_, then walk owners_ once setting slots_[owners_[d]].dense = d. Every handle keeps working because no handle ever named a dense index. Whether it is worth doing is a Lesson 5.6 question — the answer depends entirely on whether your iteration order correlates with anything, and measuring is the only way to know.

10Recap & Next

The engine gained a way to refer to things that can be wrong and know it. Concretely: a 32-bit typed handle split 20 index / 12 generation, a generational pool with dense storage and O(1) swap-and-patch removal, and one subsystem — meshes — converted end to end, with scene_object 40% smaller and the sandbox's five-test cache key down to two.

The three failures, one last time, because they are the thing to carry forward and the rest is implementation. Dangling: the object was freed. Aliasing: the object was freed and something took its place — the one a bare index makes worse, and the reason the generation exists. Relocation: nothing was freed, the container just moved. A raw pointer loses all three. An index survives one and detects half of another. An index plus a generation handles all three, in four bytes, for a third of a nanosecond.

And the honest limit, restated so it is not lost: 12 bits of generation is a budget, not a guarantee. 4,095 recycles of one slot and an old handle starts resolving again. We measured the time that takes at four plausible rates, decided it is unreachable for assets, wrote down the two known fixes, and made the pool count its own wraps so the assumption is monitored rather than believed.

Next: 5.5 — The Asset System v1. Everything today was the mechanism; next lesson is the policy. Loading, owning, and finding resources — a mesh you can ask for by name rather than by handle, loaded once however many times it is requested, and unloaded when nothing wants it any more. All three of those questions have been unanswerable until today, for the same reason: you cannot free something safely until you can say what happens to the references. Now you can.

It also inherits a specific piece of unfinished business. scene_mesh_cache now holds two pools, one of loaded geometry and one of geometry derived from it by an import step, with no rule connecting their lifetimes — free the source and the derived mesh lives on, keyed by a handle that no longer resolves. That is not a bug today, because nothing frees. It is exactly the bug 5.5 has to be designed against.
