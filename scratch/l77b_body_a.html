Module 7 — Motion: Rotation, Animation, Audio · Lesson 7.7b

Animated Characters from glTF: Skins and Clips

Lessons 7.6 and 7.7 built every part of a character player and fed every part data the course wrote itself: a skeleton laid out joint by joint, a tube weighted by a formula, clips baked from functions. That proves the arithmetic and says nothing about content, because data you write yourself agrees with your code by construction. This lesson loads a character somebody else's tool wrote — a mannequin authored in Blender and exported by Blender's glTF exporter — and turns its node tree, its skin, its weights and its animation channels into the skeleton, skinned meshes and clips 7.6 and 7.7 already know how to play. The importer is five hundred lines of translation between index spaces and between curve types, and nearly every line exists because the file did something the engine's own data never had to: a node that is not a joint sitting above the hip, inverse binds that are data rather than something to derive, rotations written x, y, z, w, key frames joined by slerp, held by STEP or bent by cubic Hermite tangents, and — in the first export — twenty-five vertices the exporter quietly attached to a joint it invented. Four predictions Lesson 7.7 made about this lesson are tested and two of them are refused. The character plays within 40 µm of an independent double-precision evaluation of the specification's own formula.

1The problem: a character you did not build

Every skinned thing the engine has drawn so far, the engine built. Lesson 7.6's tube is six joints one unit apart up the y axis, weighted to its two nearest joints by a straight line; Lesson 7.7's clips are functions of time sampled thirty times a second and then reduced. Both lessons measured everything, and both measurements share a weakness that Module 8 named after it had cost several sections: data you write yourself agrees with your code by construction. The person who wrote the skeleton also wrote the code that reads it; any misunderstanding of what a joint's parent index means is in both, and the two agree.

A game does not ship characters written by its engine programmers. They come from a modelling tool, through an exporter somebody else wrote, in a format somebody else specified. Every one of those three has made decisions the engine never made for itself — about the order joints are written in, about where the character's transform lives, about how a rotation is written down, about what happens between two keys, about what to do with a vertex nobody weighted. An importer is the place those decisions are met, and the only way to meet them honestly is with a file the engine did not write.

So this lesson's character is not generated by a script of ours that writes glTF bytes, the way Lesson 6.6 wrote its cube. It is authored in Blender — a skin modifier grown over a stick figure, nineteen bones, Blender's own automatic weights, a walk and a wave keyed with Blender's default curves — and exported by Blender's glTF exporter, with its default settings. The authoring is a script too (scratch/make_mannequin.py), so anyone with Blender can rebuild the file byte for byte; but every decision the importer has to cope with is the exporter's. The file is assets/mannequin.glb, 193,000 bytes.

Lesson 7.7's last exercise sketched this lesson and made four predictions about it. Stating them here, where they can be wrong:

  1. the importer must topologically sort skins.joints and apply the same permutation to the tracks;
  2. a channel that targets a node which is not a joint is legal and must be dropped;
  3. the duration is not in the file, and is the maximum input time across the samplers;
  4. rotations arrive x, y, z, w, and a blind copy "turns into a 180° error about a diagonal axis" — and a real exporter's clips will contain sign flips.

The first and third hold. The second is wrong in a way that moves a character a metre (§3.3). The fourth is wrong twice: the error of a blind copy is not a fixed rotation at all (§7), and Blender's exporter produced no sign flips (§9.4). None of that could have been learned from a file the course wrote.

2Building intuition: a tree, and three lists that point into it

Lesson 6.6 described a glTF file as a scene rather than a shape: a tree of nodes, each with a local transform, some of them pointing at meshes. That lesson flattened the tree — it multiplied each mesh node's chain of transforms into one matrix and threw the chain away — and said so: "right for a static prop and wrong for anything with a skeleton". A skeleton is that tree. So the first thing to see is that nothing new has been added to the file to make it animated. Everything animated is a list that points into the tree:

  • A skin is a list of node indices, skins[k].joints. Being named there is what makes a node a joint; a node object "does not specify whether it is a joint" (spec §3.7.3.2). The position of a node in this list is its slot.
  • The inverse bind matrices are a second list, parallel to the first: slot r's matrix belongs to slot r's joint.
  • Each vertex's influences (JOINTS_0, WEIGHTS_0) point into the slots, not into the nodes.
  • Each animation channel points at a node and a property of it — translation, rotation or scale.

Three address books, in other words, each written in a different numbering, and none of them in ours. The engine's skeleton (7.6) has one numbering of its own, and it has a rule the file does not have to obey: a joint's parent must come before it. An importer's job is to build that one numbering and translate every other index into it, all in the same pass. Figure 1 is the mannequin's three orders, side by side.

Look at the first column before reading on. Blender wrote its node array children first — the head is node 0 and the Armature object, the root of everything, is node 20 — so every one of the nineteen joints has a parent with a larger index. A loader that built the skeleton by walking the node array would have every parent after its child. The second column is the skin's own list, and there Blender wrote parents first: hips, spine, chest, neck, head, then each arm and each leg from the top down. The third is what the importer builds, and it contains a joint the skin never named.

3What a glTF skin says

3.1 — The formula is Lesson 7.6's

The specification defines skinning in words (§3.7.3.3): "a transformation matrix is computed for each joint. Then, the per-vertex transformation matrices are computed as weighted linear sums of the joint transformation matrices", and the inverse bind matrices "MUST be applied before the base node transforms". Written down:

\[ \mathbf{v}' \;=\; \sum_i w_i\, \big(G_{j_i}\, B_{j_i}\big)\, \mathbf{v} \] v' = sum over i of w_i * (G[j_i] * B[j_i]) * v

where Gj is joint j's global transform — its local transform multiplied by every ancestor's, up to the root of the scene — and Bj is its inverse bind matrix. That is Lesson 7.6's palette entry exactly: palette[j] = model_from_joint[j] * joint_from_model[j], "where the joint is now" times "where it was when the mesh was bound to it". The only question is what "model space" means for a file, and the answer falls out of the next two sentences of the specification.

3.2 — The mesh node's own transform is ignored

A skinned mesh in glTF hangs from a node like any other mesh, and that node has a transform. The specification (§3.7.3.2) is explicit about what happens to it: "Only the joint transforms are applied to the skinned mesh; the transform of the skinned mesh node MUST be ignored." The reason is the formula above. A skinned vertex's position is decided entirely by the joints it is bound to — Gj already carries it all the way to the scene's root — so there is nothing left for the mesh node to do. A viewer that applied the node's transform as well would move the character twice.

3.3 — The common root, and the nodes above it

Here is the sentence prediction (2) overlooked. Gj is a global transform, and a global transform includes every ancestor, whether it is a joint or not: "The global transformation matrix of a node is the product of the global transformation matrix of its parent node and its own local transformation matrix" (§3.5.3). The specification requires that each skin's joints "MUST have a common parent node (direct or indirect) called common root, which may or may not be a joint node itself" — and in Blender's file it is not: the hip's parent is the Armature object, node 20, which no skin names. Converters from other tools routinely hang a 0.01 scale or a quarter turn about x on exactly that node.

So the importer does not drop the nodes above the joints. It carries them into the skeleton as joints — joints no vertex is weighted to, whose only job is to be in every joint's chain. With every ancestor carried, the skeleton's roots are the scene's roots, and "model space" in the engine is exactly the file's scene space. A channel that animates the Armature node — Blender will export one if the object itself is keyed — then animates a joint like any other, which is what the file meant.

3.4 — The specification's own example, with numbers

The specification illustrates the rule with a five-node example and a sentence: "the translation of node_0 and the scale of node_1 are applied while the translation of node_3 and rotation of node_4 are ignored". It gives no mesh and no numbers. The harness completes it into a file (§B), and Figure 2 is the result.

At rest every palette matrix is the identity and the triangle is exactly where the file put it. Now the two wrong answers. An importer that applied the mesh node's transform, T(1,0,0) · Ry(180°), sends v0 to (1, 1, 0) — the rotation fixes a point on the y axis and the translation moves it a metre. An importer that dropped the non-joint node_0 computes GA = S(0.5), so the palette entry is S(0.5) · S(2) · T(0,−1,0) = T(0,−1,0), and v0 lands at (0, 0, 0) — a metre under the floor, from a rule that sounded like tidiness.

node_1 turns 90° about z over one second:
BBv1 = S(2)·((0.5,1,0) − (0.5,1,0)) = (0,0,0)    v1 is B's origin
t = 1:   T(0,1,0)·S(0.5)·Rz(90°)·(1,0,0) = T(0,1,0)·(0,0.5,0) = (0, 1.5, 0)
t = 0.5: (0.5 cos 45°, 1 + 0.5 sin 45°) = (0.35355, 1.35355, 0)

The engine's answers, from the harness:

  rest: v0 (0.000, 1.000, 0.000)  v1 (0.500, 1.000, 0.000)
  control, mesh node applied: v0 -> (1.000, 1.000, 0.000)
  control, node_0 dropped: v0 -> (0.000, 0.000, 0.000)
  t=1    v1 (0.00000, 1.50000)   predicted (0, 1.5)
  t=0.5  v1 (0.35355, 1.35355)   predicted (0.35355, 1.35355)
  t=0.25 v1 (0.46183, 1.19160)   spec (0.46194, 1.19134)

Two things in that transcript are worth a sentence now and a section later. The quarter-second line is not exact: the specification says a rotation between two keys is slerped, our sampler nlerps, and the importer inserted two keys so that the difference stays under 0.05° — at this joint's half-metre lever, 0.28 mm (§8.2). And the t=1 line needed the importer to be told the clip does not loop. glTF has no loop flag; with the importer's default the time 1 s wraps to 0 and v1 is back at rest (§9.2).

4The skeleton: every node above the joints, parent first

4.1 — Which nodes

The joints, and every node on the path from each joint up to its scene root. The walk up is the parent pointer the parser records for every node (gltf_node_desc::parent), bounded by the node count so that a malformed file cannot make it loop — cgltf's validator already refuses a cycle, and the bound costs nothing.

4.2 — Which order: a sort that moves nothing it does not have to

Lesson 7.6 put one requirement on a skeleton — joints[i].parent < i — so that compose_pose could be a single loop with no sorting, and left the sort to "whoever imports a rig", paid once. Any topological order satisfies it. The importer uses a particular one: 

for each joint, in the skin's order:
    walk up from it until a node already placed (or the root),
    and place that chain top-down.

Every node is placed after its parent, because a chain is placed from the top. Ancestors land immediately before their first descendant. And a skin that was already parent-first comes out in exactly its own order, because each joint's parent was placed by the time the joint is reached. That last property is the reason for choosing this sort over a textbook one: it makes a number meaningful. rig_import_report::resorted counts the skin joints whose rank among the skin's joints changed, and on a file that needed no sorting it reads zero — so a non-zero value means the exporter really did write children first, rather than that the sort shuffled things for its own reasons. The cost is O(joints × depth) with a small constant; the mannequin's depth is 8.

The mannequin, and a four-joint chain the harness writes tip first:

  skin joints 19; parents AFTER child in node order: 19
  import ok: 20 joints = 19 skin + 1 ancestor
  file-order breaks 0, resorted 0
  root joint 'Armature', identity IBMs no
  ...
  file-order breaks 3, resorted 4, identity IBMs yes
  our order: root lower upper tip

On Blender's file the sort does nothing at all. That is the most dangerous kind of result a test can give: an importer that forgot to sort would pass every test run against Blender's output and fail on the first file from a tool that writes children first. The hand-written chain is there so that the sort is tested on a file that needs it — three of its four joints come before their parents in the skin, and after the sort all four have moved.

4.3 — What the sort prevents, and a correction to Lesson 7.6

Lesson 7.6's skeleton.hpp described what an out-of-order joint does, and the description was vivid: the parent's matrix "has not been written yet when the child reads it, so the child composes against last frame's value — which looks like a one-frame lag that grows with depth". Build a skeleton in a file's child-first order and compose it twice, with a joint turned between the two, and the harness reports: 

  control, file order: out_of_order 3; tip y 1.000, then 1.000
  [PASS] C.5 unsorted, the tip is a root at y = 1 on BOTH frames

No lag. The tip sits at y = 1 — its own one-unit offset, measured from the model's origin — on both frames, and the turn of its grandparent never reaches it. The comment described what an unguarded loop would do. compose_pose has a guard: a parent index at or after the child's is treated as no parent at all, so the child composes as a root. The chain is cut, not delayed, and it is cut on every frame. Figure 3 is the mannequin built in the node array's order, where nineteen of twenty joints are out of order: every limb is composed as a root at its local offset from the origin, and the character is a pile of parts at its own feet.
