5The Edge That Survives the Step

5.1 Where the map must run

An action map has to be updated once per frame, after input is published. Lesson 5.2's application layer offers seven hooks — configure, on_start, on_event, on_fixed_step, on_frame, on_overlay, on_stop — and it turns out that none of them is the right place, which is the sort of discovery that means either the design is wrong or something is missing.

@@FIG_FRAME@@
Why each existing hook is the wrong place to update an action map.
hookrunswhy not
on_eventonce per event Several times a frame, or none. An update per event would publish a different answer to every event handler.
on_fixed_stepzero or more times The same problem, and worse — it is also where the answers get read.
on_frameexactly once The right frequency, the wrong place: it runs after the steps, so every step of the frame would read last frame's actions.

on_frame is the near miss, and it is worth being precise about why it fails, because "once per frame" sounds like the whole requirement. It is not. The requirement is once per frame, after input is published, and before anything reads it — and the simulation reads it. A map updated in on_frame is a map that is always exactly one frame stale from the simulation's point of view, which is invisible in a demo and is a real 16-millisecond input delay in a game.

So Lesson 5.10 adds an eighth. One virtual, with an empty default, in the one gap the other seven left:

Adding a hook to a framework is not free — every hook is a thing every future reader has to learn — so it is worth saying what else it is good for, because a hook that serves one caller is a smell. on_input is the once-per-frame, pre-simulation moment, and that is also where you would read a network snapshot, sample a debug scrubber, or latch a replay's recorded intentions. It was missing before this lesson happened to need it.

5.2 Two failures, one queue

Now the harder half, and it is Lesson 1.4's trap in its most expensive form.

on_fixed_step runs zero or more times per frame — the accumulator decides, and Lesson 1.4 measured 0, 1, 2, 1, 2 across five consecutive frames on this machine. A frame-scoped edge read inside it fails in both directions:

@@FIG_QUEUE@@

A two-step frame reads pressed() twice, both times true, and the player jumps twice for one press. A zero-step frame reads it not at all, and by the next frame the edge is gone — the press is silently lost. Neither is fixable by the caller without keeping state across frames, so the map keeps it:

Every rising edge pushes one press onto a small per-action queue. consume_pressed pops one and returns true. A two-step frame takes it once and the second step finds the queue empty; a zero-step frame leaves it queued until a step actually happens.

Worked example — six presses and no steps

The queue is k_action_press_queue = 4 deep. Press and release six times with no step running: the harness finds 4 queued, and draining gives exactly 4. Two presses were dropped.

That is a decision, not an overflow bug. An unbounded queue turns a hitch into a burst of jumps arriving after the player has stopped asking, which feels worse than losing them. Four survives a stutter and is short enough not to feel like a recording.

A fighting game with a deliberate input buffer would raise that number and call it a design parameter — which is exactly what it is. The engine's job is to make the number visible and the behaviour predictable, not to guess the genre.

So the rule for a caller is two lines long:

Which edge query to use where.
whereusewhy
on_input, on_frame, on_event pressed() / released() runs once per frame; the frame-scoped edge is exactly right
on_fixed_step consume_pressed() for edges,
held() / value() for levels		 runs 0..N times; levels are frame-coherent and safe, edges are not

6A Concept, and the Test It Makes Possible

There is a problem with testing any of this, and it is worth meeting because the solution is a C++20 feature this course has not needed until now.

engine::input::update() samples SDL's live keyboard state — that is the whole point of Lesson 1.2's design, and it is right. It also means a test that wants a key held would have to persuade SDL that a key is held, which SDL offers no supported way to do. So a harness cannot construct an input in a chosen state, and every interesting behaviour above — the two-binding edge case, the queue across variable steps — would go untested.

update is templated on that, and the whole test problem evaporates: the harness writes a struct with six functions and the mapping logic runs exactly as it ships.

C++ in place — a concept describes a shape, not a hierarchy

The alternative is an abstract base class: struct input_source { virtual bool key_down(...) = 0; };, with input inheriting from it. That would work, and it would cost three things a concept does not. It changes input — Lesson 1.2's header would have to know about a base class it has no other use for. It costs a virtual call per query, on a loop that runs per binding per frame. And it is closed: a type can only be an input_source if its author said so.

engine::input satisfies input_snapshot without knowing the concept exists. Not one character of input.hpp changed in this lesson. That is the property worth having: a concept describes a shape, and types that already have that shape are already members.

It is also free. The compiler instantiates one copy of update per source type and inlines the six accessors, so the production path compiles to exactly what a hand-written update(const input&) would have. The `static_assert` beside the concept keeps the claim honest: if input.hpp ever renames one of the six, the engine fails to build with a message naming the requirement rather than failing somewhere inside a template.

7The Device That Is Not Here

The second of §1's four problems was "it is about one device", and the natural way to prove that fixed would be to add gamepad support. This lesson does not, and it would be dishonest to let that pass without saying why.

There is no gamepad code here, and this is the reason

It could not be run on the machine this was written on. SDL3's gamepad API needs SDL_INIT_GAMEPAD, device add/remove events, an opened SDL_Gamepad* per controller, and axis values that need a deadzone whose right value is a matter of taste and hardware. Every one of those is easy to write and impossible to be confident about without a controller in your hand.

Untested device code in an engine is a liability rather than a feature. It looks like support, it compiles, it appears in the API — and the first person to plug in a controller finds out it was never run. Shipping the enum with an unimplemented arm would be worse still.

What the design does demonstrate, with hardware this machine has, is the property the gamepad claim actually rests on: one action, several bindings, on more than one device. The demo binds spawn_sparks to Space and to the left mouse button, and §4's five-frame walk is exactly the multi-device case in miniature. A gamepad is a third device that behaves like the second.

And here is what adding one would take, so the claim is checkable rather than asserted:

  1. Two enumerators on input_source: gamepad_button and gamepad_axis.
  2. Two arms in update()'s switch, reading SDL_GetGamepadButton and SDL_GetGamepadAxis. ⚠ VERIFY both signatures and the axis range against SDL3/SDL_gamepad.h before typing them: SDL3 renamed this whole family from SDL2's SDL_GameController*, and the axis value is a signed 16-bit integer that has to be normalised before it can be scaled.
  3. Two more accessors on the input_snapshot concept, which is the only part that touches existing code — and it touches it additively.
  4. A deadzone, which belongs on the binding rather than the action, because two sticks on the same pad can want different ones.
  5. Device connect/disconnect handling, which is the part that is actually hard: an action bound to a controller that has been unplugged must go inactive, and the release edge must fire.

Exercise 11.2 does it. Point 5 is the one worth thinking about before you start.
