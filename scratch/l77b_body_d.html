16Build & run

One new translation unit in the engine, a new demo and a new asset. The asset is copied beside the demo by engine_use_assets — as a POST_BUILD step, which matters in §17. 

# Linux / macOS
cmake -S . -B build
cmake --build build --target mannequin -j

# Windows (MSVC)
cmake -S . -B build
cmake --build build --target mannequin --config Debug

Then the harness, and its timings against a Release library:

sh scratch/build_verify_77b.sh                          # every check
cmake -S . -B build-rel -DCMAKE_BUILD_TYPE=Release
cmake --build build-rel --target engine
ENGINE_BUILD=build-rel ENGINE_CFLAGS="-O2 -DNDEBUG" sh scratch/build_verify_77b.sh   # §L

The harness reads assets/mannequin.glb and two siblings in scratch/, so it runs from the repository root. To rebuild the character itself you need Blender 4.2 or later — it was written and run on 5.1 — and nothing else; without Blender, the committed file is the same bytes: 

blender --background --factory-startup --python scratch/make_mannequin.py
# macOS: /Applications/Blender.app/Contents/MacOS/Blender --background ...
blender --background --factory-startup --python scratch/verify_77b_blender.py

And the demo:

cd build/demos
./mannequin                               # the walk; [2] the wave, [Up]/[Down] cross-fade
./mannequin --order-file                  # joints in the node array's order
./mannequin --xyzw --wide                 # rotations read w-first, camera pulled back
./mannequin --no-bind                     # 7.6's classic bug, on a real character
./mannequin --clip wave --time 1.0 --shot out.ppm   # one frame, no window

Keys: 1/2 choose the walk or the wave, Space pauses, Left/Right scrub, Up/Down cross-fade to the other clip, O Q N toggle the three bugs, R plays the reduced clips, K hides the skeleton, T turns the character round.

17Common pitfalls & debugging

The character collapses into a pile at its own feet

Symptom: every part of the body is present and each is roughly the right shape, all of them near the model's origin.
Cause: joints built in an order where parents come after children — typically the node array's, which Blender writes children first. compose_pose treats each such joint as a root, so it is placed at its local offset from the origin (§4.3).
Fix: sort parent-first before building anything; check skeleton_report::out_of_order is zero.

The character is right but a metre off, or tiny, or lying down

Symptom: correctly posed and animated, wrongly placed as a whole.
Cause: a non-joint node above the skeleton was dropped — the Armature object, or a converter's 0.01 scale or quarter turn — so no joint's global transform includes it (§3.3).
Fix: carry every ancestor into the skeleton as a joint with no vertices.

The character appears twice as far out as it should, or turned

Symptom: skinned correctly, then moved by a transform nothing seems to own.
Cause: the skinned mesh node's own transform applied on top of the joints'. The specification says it MUST be ignored (§3.2).
Fix: ignore gltf_primitive::world_from_local for a primitive with a skin; place the character with its entity.

The character hangs upside down under the floor, every limb folded differently

Symptom: nothing is where it should be, and the errors differ from joint to joint.
Cause: rotations read w, x, y, z. The identity becomes 180° about z, and no single fixed rotation undoes the rest (§7).
Fix: read every file rotation through one function, quat_from_xyzw.

Every vertex collapses toward one point, or the limbs leave the frame

Symptom: a correct skeleton and a destroyed mesh.
Cause: the wrong inverse binds — none at all (7.6's classic bug), or baked from the rest pose for a file that gave none, where the specification says identity (§5.2).
Fix: use the file's matrices when present and the identity when absent, never anything computed.

The body shreds, or each limb moves like its neighbour

Symptom: the skeleton poses correctly; the mesh follows the wrong bones.
Cause: JOINTS_n read as node indices or as joint indices instead of skin slots (§6.1) — or influences not carried through a vertex split when normals were generated (§6.5).
Fix: map slot → joint through one table built with the skeleton; follow every renumbering of the vertices.

A clip snaps back to its first pose at the end

Symptom: a one-shot animation plays, then jumps to its start.
Cause: it was imported as a loop. glTF has no loop flag; past the end the specification clamps and a looping clip wraps (§9.2).
Fix: import_settings::loops = false for clips that are not cycles.

A cubic curve overshoots between its keys

Symptom: smooth, and wildly wrong between keys; worse the closer the keys are.
Cause: the Hermite tangents used without td, which makes every tangent 1/td times too steep — 40° of overshoot on Blender's four-frame keys (§8.3).
Fix: multiply both tangents by the interval's length in seconds.

A test for the slerp conversion passes, and the playback is still wrong

Symptom: nlerp and slerp "agree" in the check and disagree on screen.
Cause: the check samples the midpoint, where the two are equal by symmetry (§8.1).
Fix: probe near a fifth and four fifths of the interval, or at several points straddling them.

A small patch of the mesh does not move with the rest

Symptom: a nose tip, a fingertip or a strap stays still while the joint around it turns.
Cause: vertices the tool left unweighted, attached by Blender's exporter to its neutral_bone, which nothing animates (§10).
Fix: read frozen_vertices; paint the vertices onto a bone in the authoring tool.

You changed the asset and the demo still shows the old one

Symptom: a re-exported mannequin.glb makes no difference.
Cause: engine_use_assets copies assets/ beside the demo as a POST_BUILD step, which runs only when the target relinks. An asset is not a source, so changing one does not relink anything.
Fix: rebuild after touching the demo, or copy by hand: cmake -E copy_directory assets build/demos/assets.

18Exercises

1 — A joint table for any file (guided)

Write a small program that imports any glTF file's first skin and prints one line per joint: its index, name, parent, skin slot (or "ancestor"), the glTF node, how many vertices carry a non-zero weight on it, and whether any channel of any clip moves it. Run it on the mannequin and on the unfixed export.

Solution sketch: everything is already in imported_rig — joint_node gives the node, and the skin slot is the node's position in file.skins[0].joints. Count vertices by walking each mesh's influences and incrementing every joint with a non-zero weight. For "moves", repeat the importer's pass: a joint moves if any clip's track for it has a channel whose keys are not all equal, or if its parent moves. On the unfixed file the line to look for is neutral_bone, with 25 vertices and "no" — the table found §10's defect by printing it, which is the argument for writing one before anything else when a character looks wrong.

2 — Skinning on the GPU (engine challenge)

Move skin_positions and skin_directions into a vertex shader: upload the palette each frame to a storage buffer, and give the mesh's vertices their four joint indices and weights as attributes. Hold the result to the CPU's.

Solution sketch: Lesson 6.18b's rules decide the layout. A vertex stage reads storage at t[n] in space0, bound with SDL_BindGPUVertexStorageBuffers on a buffer created with GRAPHICS_STORAGE_READ; store each palette matrix as rows of float4 (6.17b's light record), so no default matrix packing can transpose it. Joint indices can be uint16×4 in an attribute; weights float4. The palette for the mannequin is 20 × 64 = 1,280 bytes a frame, against the 2,681 × 24 = 64,344 bytes of skinned positions and normals a GPU renderer would have to upload every frame if the skinning stayed on the CPU — the asymmetry 7.6 predicted. For the float contract, compare with the CPU's skinned positions on the same pose: the indices must agree exactly and the positions within a stated tolerance, and fused multiply-adds on the GPU mean "exactly" is the wrong expectation for the floats.

3 — Root motion on import (engine challenge)

Author a walk in make_mannequin.py that moves forward — key the hips' location along the character's forward — and make the importer (or a step after it) extract the travel: the entity moves by it each cycle and the pose does not.

Solution sketch: 7.7's clip_report::root_travel already measures it — the distance the root moves over a cycle — and excludes roots from the loop seam for exactly this reason. Decide which joint is the root carrier (here the hips, under the Armature ancestor), subtract its horizontal translation at time t from the translation at 0, and feed the difference to the entity. Remember §11: the character's forward in the file is +z, and the engine's is −z, so the travel needs the same yaw the entity has. The trap is the loop wrap — travel must accumulate across cycles rather than jump back.

4 — What four influences cost (measurement)

Raise Blender's "Bone Influences" to 8 (export_influence_nb=8) and re-export the mannequin. The exporter still writes a single JOINTS_0 set — verify_77b_blender.py prints INFL sets written with the limit at 8: 1 — because automatic weights on this body never give a vertex a fifth bone. So first make content that has one, then measure what keeping four costs.

Solution sketch: fifth influences appear where several bones meet in a small volume. In make_mannequin.py, smooth the vertex groups after binding (bpy.ops.object.vertex_group_smooth with group_select_mode='ALL', in weight paint mode — in the background it needs the body active and the mode set explicitly), or thicken the chest's skin radius so the shoulders and neck overlap it. Export at 8, import: the report's truncated and worst_dropped answer the first half. For the second, skin the same file at a few dozen poses twice — through the importer's four, and through §G's reference, which reads every set — and take the largest vertex distance. Write the prediction down before running it: a dropped weight w can move a vertex at most w times the distance between where its dropped joint and its kept joints would put it, so the answer is bounded by something you can compute from the report before you measure.

5 — One budget, not two

The importer spends a tenth of the reducer's tolerance and the reducer the rest (§8). Import Blender's cubic export at tolerances of 0.005°, 0.05° and 0.25°, reduce each at 0.5°, and measure the key count and the worst playback error against the file's curve.

Solution sketch: scratch/verify_77b_ex5.cpp is one answer. It takes an import at 0.0005° as the exact curve, then imports at each tolerance, reduces with 7.7's defaults and measures both clips at 481 times each: 

import at 0.005 deg: 3222 keys, 258 after reduce (capped 0)
  worst vs exact: imported 0.0048 deg, reduced 0.5013 deg
import at 0.050 deg: 1227 keys, 276 after reduce (capped 0)
  worst vs exact: imported 0.0495 deg, reduced 0.5121 deg
import at 0.250 deg:  723 keys, 329 after reduce (capped 0)
  worst vs exact: imported 0.2330 deg, reduced 0.5126 deg

The prediction written with this exercise's first draft was the opposite on both counts — that the reduced key count would barely move and the error would grow, because "the two errors add". They can add; here they barely do, because the reducer's worst points and the importer's are not the same points. What the import tolerance decides is how many keys survive reduction: a looser import leaves wiggles that the reducer must keep keys to follow. §8 and import.hpp were corrected to argue for a tenth on that basis.

19Recap & next

The engine can play a character it did not build. Concretely, it gained:

  • A glTF parser that describes the whole file — every node, every skin, every influence set, every animation — in the file's own indices, with one function for a file rotation's component order.
  • An importer that builds a parent-first skeleton from any node order, carries the non-joint nodes above it, and takes the file's inverse binds as data, with the specification's identity when there are none.
  • Influences mapped through three index spaces, kept to four with the loss reported, and held to the specification's weight rule.
  • LINEAR, STEP and CUBICSPLINE samplers converted into clips to a stated tolerance, measured with the sampler's own rule at seven probes.
  • A report that measures the file: how far its rest is from its bind, what was reordered, what was dropped, what no clip can move.
  • A Blender-authored character in assets/, reproducible from a script, and a demo that plays it and each classic import bug.

And three things worth carrying that are not code. A file you did not write is the only real test of a reader. Every correction in this lesson — 7.6's out-of-order comment, its two tolerances, 6.6's facing, 7.7's predictions — came from data nobody on this course chose. Ask the tool that made the file. Twice the first explanation of a number was plausible and wrong, and both times the refutation came from running the producer rather than reasoning about it: Blender's handles are at a third, and its exporter normalises a tangent. A check that fires on a healthy input is broken. Twelve of twenty joints flagged by an exact comparison was a false alarm about the check, not the rig.
