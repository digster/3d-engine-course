4.9   The sort, as a small file of its own

draw_order.hpp is forty lines of code and a page of argument. Two things about its shape are worth pausing on.

It sorts keys, not draws. A draw_key is twelve bytes — an index, a depth, a mode. gpu_draw_item is 140. Permuting the small records and then walking the caller's array in the order they name keeps the sort's memory traffic proportional to the number of objects rather than to the size of whatever a draw happens to be. It is the argument Lesson 5.6 made about the ECS, arriving in a much smaller place.

The partition is one line, and it is the line most likely to be written backwards: 

const auto first_blended = std::stable_partition(
    keys.begin(), keys.end(),
    [](const draw_key& k) { return k.mode != alpha_mode::blend; });

!= blend, not == opaque. Masked geometry goes with the opaque geometry, because a discarded fragment writes no depth and occludes nothing, so no order can be wrong. Reading alpha_mode as a scale from solid to see-through puts every leaf of every tree into a per-frame sort in exchange for precisely nothing.

stable_partition and not a two-pass copy, because the caller's opaque ordering is worth preserving — it is usually the pipeline-sorted order Lesson 4.8 worked for, and undoing it to make room for transparency would trade three pipeline binds for one per draw.

Finally, one counter, in the spirit of 4.8's ideal_pipeline_binds: out_of_order counts adjacent pairs that arrived wrong, measured before the sort runs. It is one pass rather than an O(n²) inversion count, so it is a lower bound on the work and says so — in the harness's six-item list it reports 1 while two entries actually have to move. What it answers exactly is "did this frame's draw list arrive already sorted", which is the question worth asking every frame: a scene whose objects barely move usually answers yes, and that is when a cached, re-validated order starts to look attractive.

7Common pitfalls & debugging

Only one pane of glass is visible, and the others have vanished

Symptom. Several transparent objects, and exactly one draws. The others are gone completely, not dim.

Cause. Depth writes are still enabled on the blended pipeline. The first transparent surface drawn wrote depth across its whole area, and everything behind it now fails the test.

Fix. desc.depth_write(false) on the GPU side; on the CPU side, depth_probe instead of depth_test. Note that this reads as a culling bug or a failed load, not as a depth bug — which is why it is worth recognising by shape.

Blending is configured perfectly and changes nothing

Symptom. Every blend factor and op is set, the material's alpha is 0.5, and the surface draws fully opaque.

Cause. enable_blend is false. Every other field of SDL_GPUColorTargetBlendState is ignored without it, and there is no error, because a state you have not enabled is a legal thing to describe.

Fix. The enable. And generalise the lesson: 6.10 hit the same shape twice (max_lod = 0, max_anisotropy without enable_anisotropy). When a feature does nothing at all, suspect an enable or a clamp before suspecting the arithmetic.

Cutouts have a dark outline that gets worse with distance

Symptom. Leaves, fences and decals are edged in black. It is barely visible up close and unmistakable a few metres away.

Cause. Straight-alpha filtering, worsened at every mip level. The transparent texels are black, and both the bilinear filter and the downsample average that black into the visible edge at full weight (§3.4).

Fix. Premultiply the image, or set mip_options::alpha_weighted. Distinguish it from a lighting problem by the tell: the darkening follows the alpha edge exactly, and is absent in the interior of the cutout where every neighbour is opaque.

Foliage thins out as the camera pulls back

Symptom. A tree loses leaves with distance. Walk toward it and they come back.

Cause. Averaging and thresholding do not commute (§3.5). Every mip level's alpha has been pulled toward its local mean, so a fixed cutoff rejects a growing fraction.

Fix. mip_options::coverage_cutoff, set to the same number the renderer will test against. Setting it to a different one preserves a coverage nobody is going to measure.

Transparent surfaces flicker between two appearances as the camera moves

Symptom. Two coplanar or near-coplanar transparent objects swap which is in front, every few frames, and the swap is visible as a colour change.

Cause. Two entries with equal or nearly-equal sort depths and an unstable sort, which is free to return either order and does — as their depths wobble in the last float bit.

Fix. std::stable_sort. It cannot make a tie correct, but it makes it consistent, which turns a flicker into a fixed (and possibly wrong) choice — a much easier thing to see and to fix at the content level.

A hand-written GPU harness segfaults on exit, after every check has passed

Symptom. All the output is correct; the process dies during teardown.

Cause. An explicit gpu.destroy() at the end of a scope, with shaders, meshes and samplers declared after the device. C++ destroys in reverse declaration order, which is already exactly right — device declared first, so destroyed last. Calling destroy() by hand runs the device's teardown in the middle of that sequence, and the shader destructors then release handles on a freed device.

Fix. Delete the explicit teardown and let RAII do what it was already doing. An explicit destroy() just before a scope ends is almost always a sign that somebody did not trust the ordering they already had. This one cost a real debugging session in this lesson.

An alpha test at the boundary behaves differently in two places

Symptom. coverage_of reports a coverage that does not match what the renderer draws, by a texel or two around the edge.

Cause. One of them uses > and the other >=. A cutoff is a comparison and comparisons have edges.

Fix. Pick one — ours discards on a < cutoff, so the boundary belongs to the visible side — and make the measurement use the same one. A coverage number measured with a different comparison from the renderer's describes an image the renderer never draws.

8Exercises

8.1 — Summon the wrong composite guided

Run the demo with --alpha --pose 1.3 and then again with --blend-encoded, and diff the two images. Predict, before you look, which pixels differ. Then verify the 42.9% number by hand: composite white over black at half coverage both ways and decode the two results.

Hint

Only pixels a blended surface covered can differ, because blend_encoded is read exactly once, in commit_transparent. If the leaf card's pixels differ too, the masked path is blending when it should be testing.

8.2 — Make the halo guided

Build a 64×64 cutout whose transparent texels are bright magenta rather than black, filter across the edge with straight alpha, and describe the artefact. Then set the texture's alpha_storage to premultiplied (premultiplying the texels first) and confirm it disappears.

Hint

Magenta is worth using precisely because it is not black: it proves that the halo is not "darkening" but "whatever colour the invisible texels happen to hold", which is a much more useful mental model — and it is why some assets have a bright fringe.

8.3 — The intersecting quads, for real engine

Add two blended quads to the demo that actually intersect, and confirm that neither draw order produces a correct picture. Then implement the cheapest genuine improvement: split each quad along the intersection line into two, and sort the four pieces.

Solution sketch

The split is a BSP-style operation and it is exactly what the Quake-era engines did with transparent surfaces. Note what it costs: geometry that depends on the other geometry in the scene, which cannot be built once at load time if either object moves. That cost is why OIT exists, and doing the split by hand once is the most convincing possible argument for it.

8.4 — A cutout shadow engine

The shadow pass ignores alpha entirely, so the leaf card casts a solid rectangular shadow and the glass panes cast opaque ones. Fix the first: make depth_only fills honour alpha_mode::mask, so a chain-link fence casts a chain-link shadow. Then decide what a blended surface should cast, and defend your answer.

Hint

The first half is small: depth_only currently skips the fragment entirely, and a masked shadow needs the alpha — so it needs the texture fetch but nothing else in the shading equation. The second half has no clean answer, which is the point: real engines either treat blended geometry as casting nothing (cheap, and glass mostly does not cast a hard shadow) or reach for coloured/translucent shadow maps, which is a different data structure.

8.5 — Sort by the right point engine

order_draws sorts by the object's origin. Find a scene arrangement where that is visibly wrong, then change the key to use the object's bounding-box centre (Lesson 6.8's aabb is right there) and confirm the fix. Report what out_of_order did in both cases.

Hint

A long thin object whose origin is at one end is the easy case — a wall of glass whose pivot is at its left edge. The deeper point is that no single point is right for an object with extent, which is the same limitation as §3.6's ceiling wearing a smaller hat.

9Recap & next

The engine gained four capabilities and lost one comfortable assumption.

  • Alpha masking, on both renderers, with the depth write moved after the fragment — the software rasterizer's version of the constraint that costs hardware its early-Z.
  • Alpha blending, on both renderers, composited in linear light. Nine pipelines where there were three, because a second axis of state multiplies rather than adds.
  • Premultiplied alpha, as a property of image data beside texel_space, plus a coverage-preserving mip chain — the two halves of "what happens when you average a half-covered texel".
  • A per-frame back-to-front sort, bucketed so that masked geometry stays out of it, and with the ceiling of the whole approach named rather than glossed.
  • And the glTF importer's last silent gap is closed: alphaMode and alphaCutoff are read, so a downloaded asset's foliage is foliage.

The assumption we lost is Lesson 3.1's, and it is worth stating as a loss because it was doing so much quiet work: the z-buffer is a sort, and it only sorts things that stop the light. Everything opaque in this course has been order-free for eight lessons. From here on, some of the frame is not.

Three numbers to carry forward. Half-coverage white over black is code 188 in linear light and code 127 if you let the hardware lerp sRGB codes — the same 42.2% shortfall 6.10 measured in a naive mip chain, because it is the same arithmetic wearing a different feature. An alpha-tested fill runs at 1.05× an opaque one while writing 36% of the pixels, because every discarded fragment was fully shaded first. And one composite costs 3.14× a byte lerp on the CPU, for a conversion a GPU with an _SRGB target performs for nothing.

Next: 6.12 — HDR and Tonemapping. This lesson clamped every composite into [0, 1] because an 8-bit target has nowhere to put the excess, and said so in linear_rgb's own doc comment back in Lesson 1.6. 6.12 is where that stops being true — and it arrives immediately after transparency for a reason worth noticing in advance: blending is the one operation whose result depends on what is already in the target, so the day the target stops being 8-bit sRGB is the day every blend factor has to be re-read with a clear head.

  • glTF 2.0 specification, §5.19 "Material". alphaMode, alphaCutoff and the exact wording of the double-sided normal rule. Worth reading the three paragraphs directly rather than through an importer.
