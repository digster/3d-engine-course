10Common Pitfalls & Debugging

The player jumps twice, but only sometimes

Symptom. One press, two jumps — on some machines, on some frames, and never while you are watching.

Cause. Two possibilities, and they need different fixes. Either the edge was read inside on_fixed_step on a two-step frame, or the action has two bindings and the edges were derived from the bindings instead of the level.

Fix. For the first, consume_pressed(). For the second, derive from the level. To tell them apart: unbind everything but one key. If it stops, it was the second; if it persists, it was the first.

An input is occasionally ignored entirely

Symptom. A press does nothing, roughly once in a hundred, more often when the machine is busy.

Cause. A zero-step frame. The accumulator had not built up a full step's worth of time, so on_fixed_step did not run, and a frame-scoped edge came and went with nothing listening.

Fix. consume_pressed(), which queues it until a step happens. This one is genuinely hard to reproduce deliberately, which is why the harness simulates the frame structure directly rather than hoping to catch it.

Every step of the frame reacts to input one frame late

Symptom. The game feels slightly mushy. Nothing is broken; everything is 16 ms behind.

Cause. action_map::update() is being called in on_frame, which runs after the steps.

Fix. on_input(). It exists for exactly this, and the symptom is worth knowing because it is the kind that gets attributed to the display, the driver, or the mouse.

A key held while alt-tabbing is still held on return

Symptom. Come back to the window and the character is walking.

Cause. The level was true when focus was lost, and nothing said otherwise while the window was in the background.

Fix. reset() on SDL_EVENT_WINDOW_FOCUS_LOST. It clears levels, edges and the queue, so the next update sees a fresh rising edge if the key really is still down. Note that it also forgets the mouse origin, deliberately — otherwise the first frame back delivers the entire distance the cursor travelled while you were away.

An axis reads a huge value on the first frame

Symptom. The camera snaps somewhere absurd exactly once, at start-up or after a scene change.

Cause. A mouse delta computed against a previous position that was never set, so the first frame's "delta" is the cursor's absolute position.

Fix. The map tracks whether it has a previous sample and reports zero until it does. §F of the harness asserts exactly this, and also that reset() puts it back into that state.

An action silently does nothing after editing a config file

Symptom. A control stops working, with no error anywhere.

Cause. A typo in an action name. If lookup declared on miss, the typo would create a brand-new action with no bindings and no code reading it — a perfectly functioning thing that does nothing.

Fix. find() returns an invalid id and does not declare; declare() is the only thing that creates. Check the return. The harness asserts that find of an unknown name leaves the action count unchanged.

11Exercises

  1. 11.1 — Save and load the bindings. Write the binding table to a text file and read it back, so a player's rebinds survive a restart. Actions by name, not by id — the ids are assignment order and will change the moment somebody adds a declare call.

    Hint

    One line per binding: action name, source, code, scale. Loading is declare(name) — which is idempotent, so it does the right thing whether or not the program declared it first — then the matching bind_*.

    Solution sketch

    The interesting part is not the parsing, it is what to do when a file names an action the program does not have. Declaring it is wrong (it will never be read); refusing to load the file is wrong (one stale line should not lose every rebind). Skip the line and log it — the same shape Lesson 5.3's log/error rules produce everywhere else.

  2. 11.2 — Add the gamepad. §7 lists the five steps and marks the SDL3 signature as needing verification against the headers. Do all five. Then unplug the controller while an action bound to it is held, and make sure the release edge fires.

    Hint

    The first four are mechanical. The fifth is the exercise: a disconnected device stops answering, and "stops answering" must become "contributes zero" rather than "keeps its last value". Where does that belong — in the binding, or in whatever owns the SDL_Gamepad*?

    Solution sketch

    In the snapshot, not in the map. A disconnected pad's key_down equivalent returns false, the sum drops to zero, the level goes false, and the release edge falls out of §4's existing machinery with no new code at all. If you found yourself adding a special case to action_map, the abstraction boundary is in the wrong place — and noticing that is worth more than the feature.

  3. 11.3 — Record and replay. Record the action values of every frame to a buffer, then play them back through a snapshot type that reads from the buffer instead of from a device. Check that the demo reproduces itself exactly.

    Hint

    You do not need to record inputs at all — record the action values, and make the playback source a type satisfying input_snapshot whose six functions are backed by the recording. This is §1's third problem, solved.

    Solution sketch

    It will not reproduce exactly, and finding out why is the exercise. The simulation is deterministic (Lesson 1.4 verified that) but the number of steps per frame is not — it depends on wall-clock time. A replay has to record and replay the step count as well as the input, or drive the loop at a fixed step count. That is why replay systems and fixed timesteps are always discussed together.

  4. 11.4 — Conflict detection. Add action_map::conflicts(SDL_Scancode), returning every action already bound to a key, so a settings screen can warn before a rebind silently shadows something. Then decide: should bind_key refuse a conflict?

    Solution sketch

    It should not. Two actions on one key is often deliberate — "accept" and "shoot" in different contexts, a modifier-free chord — and a binding layer that refuses it forces the caller to work around it. Report the conflict and let the caller decide, which is the same shape as Lesson 5.5's asset store reporting a load failure instead of substituting a default. The flat binding list this exercise walks is the reason §8's table is flat rather than per-action.

  5. 11.5 — Put the map in a component. §2.2 claims a two-player game holds two maps and a per-entity game puts one in a component. Prove it: add a player_input component holding an action_map, give two entities one each with different bindings, and drive them from a single view<player_input, placement>.

    Hint

    action_map holds vectors, so it is movable but not trivially copyable — which is fine, because Lesson 5.8's pool<T> requires only movability. Worth checking that claim rather than assuming it.

    Solution sketch

    It works, and the interesting discovery is where update() goes: once per map, per frame, in on_input — which is a view<player_input> walk, and therefore a system like any other. Lesson 5.7's rule 1 (components stay small) argues against it at scale, since an action_map is several vectors; the honest alternative is a component holding an index into a small array of maps.

12Recap & Next

The engine can now be told what the player meant. What it gained:

  • Actions, bindings and values — one name in the middle, and the four things §1 could not do all become possible. No gameplay code in the demo names a key.
  • One mechanism for buttons and axes. Every binding contributes a signed value; an action's value is the sum. Holding both halves of an axis gives exactly zero, and no rule anywhere says so.
  • Edges derived from the action's level. The bug this avoids is invisible with one binding per action and fires as "sometimes it jumps twice" the moment somebody binds a second device.
  • A second kind of edge for the fixed step. consume_pressed() fires exactly once per press however many times the step runs — including zero — which is Lesson 1.4's trap closed rather than documented.
  • The hook that was missing. on_input(): once per frame, after input, before the simulation. Nothing else in the frame is that.
  • A concept instead of an interface. input_snapshot makes the mapping logic testable without a base class, without a virtual call, and without one character changing in Lesson 1.2's header.

And what it did not gain, said plainly: a gamepad. §7 gives the reason — it could not be run here, and untested device code is a liability — along with the five steps and the one that is actually hard. What is demonstrated is the property the gamepad claim rests on: one action, several bindings, more than one device.

The reference shot from Lesson 5.1 is byte-identical for the tenth lesson.

13Further Reading

  • Unity's Input System package — the same three-layer shape (actions, bindings, control schemes) at production scale, with the composite bindings this lesson's signed-sum rule replaces. Their “1D Axis” composite is exactly §3's two keys with opposite scales, given a name and a UI.
  • Unreal's Enhanced Input — the other production answer, and interestingly different: modifiers and triggers are first-class objects in the binding chain rather than a scale. Worth reading against §3 to see what a richer mechanism buys and costs.
  • SDL3 SDL_gamepad.h — the header to read before attempting Exercise 11.2, and the authority for the signatures §7 declines to guess at.
  • Glenn Fiedler, “Fix Your Timestep!” — the source of the accumulator this lesson's queue exists to survive. Re-read the variable-step-count section with §5.2 in mind; the input problem is a consequence of the loop and is rarely mentioned alongside it.
  • Lesson 1.2 for the level-versus-edge distinction this builds on, 1.4 for the accumulator, and 5.2 for the application layer that gained a hook.
