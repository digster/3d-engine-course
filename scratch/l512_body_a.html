Module 5 — Becoming an Engine · Lesson 5.12

Checkpoint: A Small 3D Game on the Public API

Eleven lessons ago we drew a line and called it law: engine/ is a library, demos/ are programs, and a program may include nothing but <engine/…>. Since then we have built an application layer, a logger, a handle system, an asset store, an ECS, a transform hierarchy, a camera, an action map, a debug drawer and a debug UI — and every single program that used them was written by the person who had just built them, in the same afternoon, to show them off. That is not a test of an API. A demo can stop at the edge of the one subsystem it demonstrates; a game has to cross every edge there is — load an asset, spawn an entity, parent a camera, read a button, move a body, test an overlap, tell the player what happened — and the seams between subsystems are exactly where a public API is weakest, because nobody has ever stood on them. So this lesson writes a game. It is small on purpose: drive a rover round an arena and collect twelve orbs, half of them riding a carousel. What it is not is forgiving. Every time the published headers could not do something, this file did it itself, in the open, with a comment naming what was missing — and there are seven. Two of them turn out to be promises the engine had already made and not kept: the header that calls itself “the whole public API, in one include” lists 40 of 55 public headers and is missing the entire ECS, the asset store, the action map and the logger; and scene.hpp has said since Lesson 5.1 that “Module 5's ECS replaces the struct with components”, which Module 5 never did. Both are fixed here, one of them against this engine's own three-caller rule and owing a reason. The other five are named, measured, and handed to the module that owns them. Along the way a camera parented to a rolling car produces a matrix that is not rigid, an assertion fires, and a headless run hangs for ever — which is one composition order written the way it reads in English rather than the way the algebra says.

1. The problem: a boundary nobody has stood on

Lesson 5.1 made a claim with a mechanism behind it. The claim was that engine/ is a library with a public API; the mechanism was the include path, so that #include "gfx/raster.hpp" — the spelling every file in this repository had used for four modules — stopped resolving. A demo that reaches for an internal does not get a review comment, it gets a compile error. That was the right mechanism and it has held perfectly.

But look at what has actually stood on it.

@@FIG_BOUNDARY@@

sandbox predates the boundary and owns its own loop. pong is Module 1's game, relocated. hello_cube is a hundred lines that draw one cube. ecs_swarm was written in Lesson 5.8 to demonstrate the ECS — by the person who had written the ECS that morning. gltf_view shows off the importer, by the person who wrote the importer.

There is a specific kind of blindness in that arrangement, and it is not about competence. When you write the demo for a subsystem you have just built, you already know where everything is. You do not discover that the function you want is not exported, because you know it is not, and you reach for the one that is without ever noticing you made a choice. You do not discover that a header is missing from the umbrella, because you never use the umbrella — you type the include you know is correct. You do not discover that two subsystems have no path between them, because you are only using one of them.

A public API is a promise made to somebody who does not know where everything is. The only way to find out whether the promise holds is to have that person write something. We do not have that person. What we have is the next best thing, which is a program with requirements that were not chosen to flatter the engine.

Why now, and not at the capstone

Module 9 ends with a complete game built solely on the public API, and that is the real proof. The trouble with waiting for it is arithmetic: the capstone sits at roughly hour 434 of this course with about ten hours of budget around it, and anything it finds has to be absorbed by an engine that eighty more lessons have been built on top of. We are at hour 62. A design bug found here costs a header; found there it costs a refactor of everything that has since depended on the bug. The cheapest moment to discover that your API does not work is the first moment somebody could have discovered it.

2. What a game asks that a demo does not

The game is called collector and it fits in one sentence: drive a rover round a 14 × 14 metre arena and collect twelve orbs before a ninety-second clock runs out. Six orbs sit still and bob; six ride a carousel, so they move while you chase them. Eight pillars stand in the way. That is the whole design, and it was chosen to be ordinary rather than interesting — a game with an unusual requirement would exercise an unusual part of the API, and the question here is whether the usual parts work together.

Ten of those eleven rows are a pleasure. The engine has the piece, it is public, it is named what you would guess, and it composes with the piece next to it. That is worth saying plainly before the rest of this lesson goes looking for trouble: the boundary drawn in 5.1 mostly works, and the parts Module 5 built are mostly right. A checkpoint that found nothing but problems would be a checkpoint that had gone looking for them.

The eleventh row is the interesting one, and it is where we start.
