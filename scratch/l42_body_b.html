4Implementation

Four new files, and one decision to make before any of them. Our window currently belongs to an SDL_Renderer, created in Lesson 0.5 and used ever since — including by every HUD in Modules 1 to 3, which are drawn with SDL_RenderDebugText. A window can be claimed by an SDL_GPU device or driven by an SDL_Renderer. There is no ordering in which it is both.

Deleting the HUD from the five demos Tab cycles, to make room for this one, is not a trade worth making, so the GPU path becomes a second program inside the same executable, reached with a flag:

The flag is read before the window is created and the branch is taken before any renderer exists. From Lesson 4.8 the GPU path becomes the default and this branch inverts; the flag is scaffolding with a known removal date, which is the only kind worth building.

4.1The device, and the claim

Two resources, acquired in one order and released in the other. Creating the device picks a backend and loads a driver; claiming the window creates the swapchain. On the way out, the claim must be released before the device is destroyed, because the swapchain belongs to the pairing rather than to either party.

An object whose destructor knows that order is strictly better than a comment asking you to remember it, so gpu_device owns both:

Creation is the two-phase pattern the C++ style guide fixes for fallible construction: a default constructor that cannot fail, and a create that reports what happened. Without exceptions a constructor has no way to say "no" (C++ Style §5), and the price is that valid() has to exist. The benefit is that every failure path is visible in a signature rather than in a stack unwind.

Note one detail in create that is easy to get wrong: if the claim fails, we destroy the device before returning.

C++ in place — why the raw handle is public

gpu_device::handle() hands out the raw SDL_GPUDevice*, which looks like a leak in the abstraction. It is deliberate. A wrapper that forwarded all ninety-odd SDL_GPU functions would hide exactly the API this course exists to teach, and every one of those forwarding methods would be a place for our names to drift from SDL's.

The wrapper exists for lifetime, not for concealment: it guarantees the device is created once, released once, and released in the right order relative to the window. Everything else is SDL's, spelled SDL's way. This is the same judgement engine::framebuffer made in Lesson 1.5 when it exposed data().

4.2Asking instead of assuming

Once the device exists, everything about it is a question with a real answer, and none of those answers may be assumed. gpu_report is a struct with a query behind every field, filled in at creation and logged at startup:

Read the third and fourth lines together, because they are the first genuine surprise of the API. We asked for SPIRV | DXIL | MSL and were granted MSL | METALLIB — one format we named and one we did not. That is not a negotiation failure. The mask you pass to SDL_CreateGPUDevice says here is what I am able to supply, and SDL uses it to pick a backend that can consume at least one of them; SDL_GetGPUShaderFormats then answers a different question — here is everything I accept. Lesson 4.3 needs the second answer, not the first, to decide which file to load.

The other lines matter for reasons that arrive later, and it is worth knowing which:

  • The swapchain format is not a constant and not ours to choose. In Lesson 4.4 a graphics pipeline whose colour-target format does not match this exactly will simply fail to create — so this line is load-bearing, not informational.
  • MAILBOX is missing from the present modes on this machine. That is the whole reason support is asked about rather than assumed: a program that hard-codes MAILBOX works on the developer's Linux box and fails at startup on a Mac.
  • The window and swapchain sizes agree here, at 1280×720, and it is worth knowing why they might not. A window is measured in points and a swapchain in pixels; they coincide because this window was created without SDL_WINDOW_HIGH_PIXEL_DENSITY. Ask for that flag on a Retina display and the swapchain comes back at twice the window's numbers. Code that assumed they were equal then draws into a quarter of the window and sends its author looking for a bug in the projection matrix. The acquire returns the real numbers; use those.

4.4The transfer-function trap

Now a trap that §3.4 has already armed. Our framebuffer holds sRGB-encoded bytes — that has been true since Lesson 1.6, and it is what every PNG an artist hands you holds too. The swapchain may be a plain _UNORM format, which applies no transfer function, or a _UNORM_SRGB one, which decodes on read and encodes on write.

Consider what a blit does: it samples the source and writes the destination. So with an sRGB destination and a plain source, our already-encoded bytes are read unchanged and then encoded again on the way in. Encoded twice. Mid-grey 128 becomes 188 becomes 226, and the picture goes pale and foggy — the classic gamma artifact, arriving three modules before the lesson that names it.

The fix is one line of thought and four of code: give the source texture the same sRGB-ness as the destination, so a decode on read cancels the encode on write and the pair is the identity.

The byte layout comes from asking SDL rather than from reasoning about it, and that is worth a sentence of its own. SDL_PIXELFORMAT_ARGB8888 is a packed 32-bit format: it describes the bits of a Uint32, not the order of four bytes in memory, so on a little-endian machine those bytes come out B, G, R, A. The answer is therefore endianness-dependent, and asking costs one call:

That second check is the one that makes the whole path trustworthy. The harness draws a real picture with the Module 3 rasterizer, sends it up through the transfer buffer, into a texture, through a 1:1 nearest blit into a second texture, back down through another transfer buffer, and compares all 921,600 bytes against the original. Not one differs. Whatever else goes wrong later, it will not be the plumbing.

4.5The frame, and where the waiting really is

The probe's frame is nine steps, and their order is the argument:

The upload is recorded before the acquire, and that is deliberate. The acquire is where a vsynced frame blocks; every microsecond of work you can place above it is work done while the display is still busy with the previous frame. Move it below and nothing breaks — the frame just gets longer by exactly that much.

Then the swapchain is cleared by a render pass that draws nothing at all:

A render pass with no pipeline bound and no draw call is legal and useful, and it is the clearest possible illustration of what a load op is. Clearing is not a draw that happens to cover the screen; it is a property of beginning a pass. On tiled hardware — every mobile GPU, and Apple silicon — LOADOP_CLEAR costs less than LOADOP_LOAD, because loading means fetching the previous contents of each tile from memory and clearing means not bothering. That is the single easiest performance mistake to avoid in a mobile renderer, and it is available to you before you have written a shader.

Now the measurement. The probe times four things per frame and draws them as stacked columns, one per frame, using nothing but framebuffer::fill_rect. There is no text in this mode, because text needs a font and a shader and both are later lessons — so the graph is the HUD.

Figure 5 is the result, and the middle bar is the reason this section exists. Pressing 4 turns on a full GPU sync every single frame — the thing every guide tells you never to do. Watch what happens:

The full GPU sync is free. Not cheap — free, to the precision we can measure. And the reason is in the third row: at 60 Hz, 16.0 of the 16.667 ms was already being spent waiting for the display. There was nothing else for the CPU to do with the 0.76 ms the fence took, so taking it cost nothing. The wait simply moved from one blocking call to another.

Why this is the most dangerous result in the lesson

A beginner's renderer that syncs every frame will measure perfectly on a simple scene, ship, and fall apart the moment the GPU becomes the limit — because then there is no slack, the sync stops being absorbed, and every frame pays the full round trip. §3.1 measured that case and found 1.60×.

So do not learn "syncing is slow" and do not learn "syncing is free". Learn this: a sync costs you the overlap you had. When the frame is display-bound there is no overlap to lose; when it is GPU-bound there is nothing else. Which regime you are in is a measurement, and now you have the tool that makes it.

The third row is worth a moment too. IMMEDIATE present mode takes the frame from 16.667 ms to 4.816 — and the acquire is still 4.238 ms of it. Turning off vsync did not remove the wait; it moved the limit from the display to the frames-in-flight budget. There is always something pacing you. The question is only what.

4.6A number that could not be true

One more thing happened while measuring §2.1's table, and it is in the lesson because leaving it out would teach the wrong habit.

The first version of the harness copied a 2048×2048 texture 48 times and reported 763 GB/s. That is a good-looking number. It is also impossible: this machine is an Apple M4 Pro, whose published memory bandwidth is 273 GB/s. A copy cannot move bytes 2.8 times faster than the bus they travel on, so the measurement was wrong, and the only question was how.

The first cause was elision. Blitting the same source to the same destination 48 times is 48 copies of one answer, and a driver is entitled to notice. Fixing it took one line: ping-pong, so that blit i+1 reads what blit i wrote and the chain cannot be shortened or reordered. That brought the figure down — and not far enough.

The second cause was compression. Both textures were cleared to a flat colour, and every modern GPU stores render targets in a losslessly compressed form. A flat texture compresses to nearly nothing, so the copy was real but the bytes were not. Filling both textures with xorshift noise — which cannot compress — makes the copy move what it claims to move.

@@FIG_BANDWIDTH@@

Figure 6 is both versions at four sizes, and it is the most useful chart in the lesson. Read the noise bars first: they converge on 277.6 GB/s at 4096², against a published bus of 273. The copy saturates the memory system, which is exactly the right answer for a copy, and finding a measurement that lands on an independently known number is the strongest evidence a benchmark can offer.

Then read the gap. Flat content copies at up to 2.87× the rate of noise, and the ratio grows with size, because compression saves more when there is more to save. That is not a measurement error once you know what it is — it is a real and useful property of the hardware, and it is why a cleared render target is cheaper to work with than a busy one. It only became an error when it was quoted as bandwidth.

The habit, not the number

Lesson 3.10 said: measure, then act. This section adds the step in between — check that the number can be true. Bandwidth has a ceiling you can look up. Frame time has a floor set by the refresh rate. A speedup cannot exceed the fraction of time you changed (Amdahl's law, 3.10 §6). Every one of those is a free sanity check, and each of them has caught a real error in this course's own harnesses.

7Common Pitfalls & Debugging

The downloaded data is garbage, or is last frame's

Symptom. A readback contains the fill pattern you poisoned the buffer with, or the previous frame's contents, or plausible-looking data that is subtly stale. Every SDL call returned success.

Cause. You read before the fence. SDL_SubmitGPUCommandBuffer hands the work over; it does not perform it.

Fix. Submit with SDL_SubmitGPUCommandBufferAndAcquireFence, wait with SDL_WaitForGPUFences, then map — and release the fence. This lesson's §D measured the unfixed version wrong 64 times out of 64. Be more suspicious, not less, when it happens to work: a race that usually wins is a race you will ship.

SDL_ClaimWindowForGPUDevice fails and the window looks fine

Symptom. The device is created, the claim returns false, and the window is on screen and perfectly healthy.

Cause. Something else already owns it — nearly always an SDL_Renderer created earlier, including one created by a helper you forgot about. A window has exactly one presentation owner.

Fix. Decide before the window is used. In this lesson the --gpu branch is taken before SDL_CreateRenderer is ever reached, which is why the flag is parsed at the top of main rather than read from a config file later. If you must switch at runtime, destroy the renderer first.

The image fills a quarter of the window

Symptom. Everything renders into the bottom-left (or top-left) quarter, as if the projection were scaled by two.

Cause. You used the window's size where the swapchain's was wanted. A window is measured in points; a swapchain in pixels. With SDL_WINDOW_HIGH_PIXEL_DENSITY on a Retina or 4K-scaled display they differ by the display scale.

Fix. Use the width and height that SDL_WaitAndAcquireGPUSwapchainTexture fills in. They are out-parameters precisely so you never have to compute them, and the probe logs both numbers once at startup so that a mismatch is visible before it is mysterious.

The picture is pale and washed out

Symptom. Everything looks foggy, blacks are grey, and the whole image appears to have had its contrast reduced.

Cause. A double sRGB encode. Your bytes are already encoded; the target's format encoded them again. Mid-grey 128 became 188. (The opposite mistake, a double decode, gives a picture that is far too dark and contrasty.)

Fix. Match the source texture's sRGB-ness to the destination's, as gpu_present_target::create does. And remember the rule from §3.4: a clear colour is always linear light, and the format decides what is stored — never pre-encode one yourself.

A flickering band of the previous frame, on some machines only

Symptom. Part of the image — often a horizontal strip — shows the previous frame, intermittently, usually under load. Never reproducible on the developer's machine.

Cause. You wrote to a transfer buffer or texture that a pending command buffer is still reading, with cycle = false.

Fix. Pass true for cycle on every per-frame write. The cost is memory, not time. And do not cycle a resource you intend to update only partially: cycling makes the whole resource undefined.

A benchmark result that is too good

Symptom. A copy or a clear reports bandwidth above the machine's memory bus, or a draw takes zero time.

Cause. The work did not happen. Two ways for that, both met in §4.6: the driver elided repeated identical work, or the content was compressible enough that the bytes never moved. A third, from Lesson 3.10: the optimiser deleted your benchmark's arithmetic because nothing consumed the result.

Fix. Chain the work so each step depends on the last, fill buffers with incompressible noise, and — before anything else — look up the ceiling. Every GPU measurement has one.

The same program measures 120 fps and then 60 fps

Symptom. Two runs of an unchanged binary, minutes apart, disagree by a factor of two on frame time.

Cause. The window opened on a different display. This happened while writing this lesson: the first run landed on a 120 Hz laptop panel and the rest on a 60 Hz external monitor, and for a few minutes there was a very exciting and completely false conclusion that fencing halved the frame rate.

Fix. The one Lesson 3.10 already gave, applied to a new axis: run the variants alternately, in one session, and change one thing at a time. The numbers in Table 3 were taken that way, twice, after the false result was found. If a vsynced measurement surprises you, check what the display is doing before you believe it.

8Exercises

4.2.1 — Make the double encode happen

Force the bug in §4.4 so you can recognise it later. In gpu_present_target::create, delete the is_srgb_format branch so the source texture is always the plain _UNORM layout. Then switch the swapchain to an sRGB one — SDL_SetGPUSwapchainParameters with SDL_GPU_SWAPCHAINCOMPOSITION_SDR_LINEAR, checking SDL_WindowSupportsGPUSwapchainComposition first — and describe precisely what changed about the picture.

Hint

Look at the dark checkerboard squares rather than the bright triangle. The encode is steepest near zero, so the damage is largest in the darks: byte 18 becomes 76.

Solution sketch

The whole image lifts, and the shadows lift most — the background stops reading as near black and becomes a flat mid-grey. Now restore the branch and watch it snap back. The habit worth taking away is that washed-out darks is a specific diagnosis with a specific cause, not a vague sense that the picture looks wrong.

4.2.2 — Find your own frame's limit

Using only the probe's keys, determine what is pacing your machine. Record the four timings at each of: VSYNC with 2 frames in flight; IMMEDIATE with 2; IMMEDIATE with 1; and IMMEDIATE with 3. Which setting changes the frame time and which changes only where the time is spent?

Hint

Compare the acquire band across the four. Then apply §3.3's formula: with F ≥ 2 the frame rate is 1/max(C, G), so if going from 2 to 3 changes nothing you have learned which of C and G is larger.

Solution sketch

On the machine in this lesson: VSYNC pins the frame at 16.667 ms with the acquire absorbing all the slack. IMMEDIATE drops it to about 4.8 ms, still mostly acquire — so the limit became the frames-in-flight budget rather than the display. Dropping to 1 frame in flight lengthens the frame, because CPU and GPU stop overlapping; raising it to 3 changes the frame time hardly at all, which is §3.3's prediction that the second frame buys throughput and the third buys only latency.

4.2.3 — A screenshot, without stalling the frame

Add a key that saves the framebuffer as it appeared on the GPU, by downloading the present target's texture — and do it without ever blocking the frame loop. Use SDL_QueryGPUFence rather than SDL_WaitForGPUFences: request the download this frame, check the fence each subsequent frame, and write the file on the frame it reports done.

Hint

You need three pieces of state that outlive the frame: the fence, the download transfer buffer, and a flag saying a capture is outstanding. Refuse a second request while one is pending — that is one line and saves you an entire class of bug. Lesson 3.5's save_obj shows the file-writing pattern this codebase uses; a .ppm is six lines to write.

Solution sketch

The capture typically completes on the very next frame, which is the point: the same result as a blocking wait, and no frame was delayed to get it. This is the shape of every good readback in a real engine — GPU-side histograms, auto-exposure, picking, occlusion queries — and it is exactly the "latency you can tolerate" trade the SDL_GPU header describes for SDL_DownloadFromGPUTexture. Watch for one trap: the texture you download must not be written again before the fence signals, so either cycle it or capture into a texture of its own.

4.2.4 — Prove the transfer buffer is necessary

Try to skip it. Attempt to memcpy straight into an SDL_GPUTexture, and then write down, in one paragraph, why the API gives you no way to express that — even on a unified-memory machine where the CPU and GPU are demonstrably looking at the same DRAM.

Hint

There is no function that returns a pointer to a texture's storage. Ask why that is a deliberate omission rather than a gap: what would such a pointer have to promise about the arrangement of the bytes behind it?

Solution sketch

A texture is not row-major. It is tiled so that a 2×2 quad's texels are neighbours (Lesson 4.1 §2.3), possibly swizzled, possibly losslessly compressed, and the exact scheme differs between vendors and between two chips from one vendor. A pointer to it would be a pointer to a layout you cannot know, so the only portable way to write a texture is to describe the pixels in a layout you can know and let the driver rearrange them. That is what the transfer buffer is. The unified-memory case does make the copy cheaper — 0.0028 ms for 320×180 here — but not expressible as a direct write.

4.2.5 — Find the compression ceiling yourself

Extend §C of the harness to sweep content rather than size: copy a 4096² texture that is flat, then a two-colour checkerboard, then four-bit noise, then full 32-bit noise, and plot the reported bandwidth. Where does the curve reach the bus, and what does that tell you about the compressor?

Hint

Keep every other variable identical — same size, same blit count, same ping-pong. Only the bytes change. And take the minimum of several runs rather than the mean, as Lesson 3.10 argued for kernels.

Solution sketch

You should find a curve that falls towards the bus figure as the content gets less compressible, flattening once it is genuinely incompressible. The interesting part is where the knee is, because that tells you what block size and what kind of redundancy the hardware's compressor exploits — and it is vendor-specific, undocumented, and measurable in fifteen minutes with the harness you already have. That last sentence is most of what graphics performance work is.

9Recap & Next

What the engine gained

  • A GPU device, owned properly — created, claimed to a window, and released in the correct order by a destructor rather than by discipline.
  • A report instead of assumptions. Driver, shader formats granted, swapchain format, present modes and frames in flight, every one asked for and logged at startup.
  • Your framebuffer on screen through SDL_GPU, by transfer buffer, texture and blit, bit-identical to what the rasterizer drew, with no shader anywhere in the program.
  • A frame graph drawn with fill_rect, showing the four places a frame's time goes — and four keys that move time between them while you watch.
  • A regression test on the object model: our enumerators are checked against SDL's, so "it is a rename" stays true rather than becoming folklore.

The sentence to carry forward is the one this lesson opened with, now with a number attached: a call records work rather than performing it, and on this machine describing 4.78 ms of work takes 0.19 ms — so the CPU spends 96% of that time free. Every object that was new in Figure 3 exists to manage the consequences: the device is the connection, the command buffer is the message, the transfer buffer is the shared ground, and the fence is how you find out it is done.

Two results are worth keeping in your hands rather than your notes. A full GPU sync on a display-bound frame costs nothing measurable — and on a GPU-bound one costs 1.60×; the difference is not the sync but the overlap you had to give up. And a measurement that beats the hardware's published ceiling is not a fast machine, it is a broken benchmark, twice over in our case.

What we have not done is draw anything. The GPU has cleared, copied and blitted, and every one of those is fixed-function work SDL performs on our behalf. To make the GPU compute a colour we need a program to run on it — and that program has to exist in three different binary formats, because Metal, Vulkan and D3D12 do not speak the same language.

Next: 4.3 — The Shader Toolchain. One HLSL source, compiled offline through SDL_shadercross into SPIR-V, DXIL and MSL, wired into CMake so a shader edit is a build step rather than a ritual. Then, in 4.4, the first triangle the GPU has ever drawn for us — and §4.2's shaders granted line turns out to be the one that decides which file we load.
