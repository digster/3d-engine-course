Module 6 — Advanced Rendering · Lesson 6.18b

Compute Shaders: GPU Particles

Every program this engine has sent to the GPU went through a rasterizer: vertices in, fragments out, each fragment allowed to write exactly one pixel. This lesson takes the rasterizer away. A compute shader is a function run once per thread over a grid you size yourself, reading and writing any byte of any buffer it is handed — and with that freedom come the problems the rasterizer had been solving for you: the threads at the ragged end of the grid, two structs that mean different bytes to two compilers, randomness with no sequence to draw it from, two threads writing one address, and a flag that silently hands a pass a buffer full of nothing. The vehicle is a particle system of 65,536 sparks that the GPU creates, steps, counts and draws without a byte of it crossing back to the CPU, specified once in C++ so that a harness can run it on both processors and compare every particle. The integers agree bit for bit; the floats agree to within two micrometres after ten simulated seconds; and the frame graph of 6.17 learns what a buffer is, in the process deriving the one flag this lesson would otherwise have had to get right by hand.

1The problem: sixty-five thousand sparks and the bus between them

A grinder throwing sparks, a fountain, rain on a window, embers over a fire, the dust behind a car: each is thousands of tiny, short-lived things that move by simple rules and are drawn as little points of light. They are the classic particle system, and the engine already has every piece you would need to write one the way Module 1 would have. A std::vector of particles; a loop that gives each a velocity and a lifetime when it is born; a loop that adds gravity to the velocity and the velocity to the position every step; a loop that removes the dead. Then, to draw them, copy the whole array into a buffer the GPU can read, with 4.5's gpu_stream_buffer, and issue one instanced draw.

That works, and this lesson builds it — completely, as engine::particle_pool — because it is the thing everything else is compared against. Here is what it costs, measured on this course's machine with the engine built in Release, for a pool of 65,536 particles of which about two thirds are alive at any moment:

  • The step: 0.228 ms. About 3.5 nanoseconds a particle, which is fast: the loop is short, the data is contiguous, and there is nothing in it for the CPU to wait on.
  • The upload: 3.00 MB, every frame, 0.569 ms. Forty-eight bytes a particle — the record §4 designs — whether or not a single particle moved, because the GPU cannot draw what it does not have.

Neither number is alarming at 65,536. Now ask for a million, which a modern game will happily spend on a single explosion. The step becomes 3.75 ms and the upload 6.87 ms: between them 10.6 ms of a 16.7 ms frame, before a single pixel of the scene is drawn. And notice which of the two grew into the problem. It is not the simulation. It is the bus: moving the particles from where they are computed to where they are drawn costs nearly twice as much as computing them. (This machine's GPU shares the CPU's memory, so its "bus" is a copy within one RAM. A discrete GPU pays for the same bytes over PCIe as well.)

@@FIG_BUS@@

Figure 1 draws the two ways out. You could make the CPU faster — threads, SIMD — and it would help the first number and do nothing for the second. Or you could stop moving the particles at all: keep their state in a buffer that lives on the GPU, and have the GPU step it, in place, in the same memory the draw reads. Then the CPU's whole contribution per step is a handful of numbers — this lesson's comes to 144 bytes — describing what the emitter did, and the particles never cross the bus in either direction. The GPU step, measured the same way, is 0.029 ms for 65,536 particles and 0.39 ms for a million.

That requires a way to run arbitrary code on the GPU that is not attached to a triangle. It is called a compute shader, SDL_GPU has supported it since SDL 3.2, and this engine has never written one. And the moment you write one, five things the rasterizer quietly did for you stop happening, and each becomes a section of this lesson:

  • Nobody sizes the work for you. The rasterizer ran the fragment shader once per covered pixel. A compute dispatch runs as many threads as you ask for, in groups whose size is fixed in the shader, and the particle count is not a multiple of the group size. (§3)
  • Data layout becomes your problem. Vertex attributes were described to the pipeline field by field (4.5). A storage buffer is raw bytes, read through a struct declared in two languages and compiled by two compilers — which do not agree about where every field goes. (§4)
  • There is no sequence. A CPU particle system calls a random-number generator in a loop; sixty-five thousand threads running at once cannot share one generator's state. (§5)
  • Threads collide. A fragment wrote only its own pixel. A thread may write anywhere, and the first time two of them count the same thing, most of the counting is lost. (§9)
  • Order is not implied. A render pass's draws land in the order they were issued. Two dispatches in one compute pass are not ordered at all, and a buffer written by one pass and read by the next depends on a flag — cycle — whose wrong value costs every particle you have, every frame. (§10)

There is one more constraint, and it is the course's. CLAUDE.md §4 makes fixed-timestep simulation with render interpolation a law, not a preference. Particles are a simulation. So the GPU must step them at a fixed rate, the draw must interpolate between the last two steps, and §7 counts what that costs a particle system that most engines simply advance by the frame's delta time.

2Building intuition: a draw call with no triangles

Start from what the GPU already does for you, because a compute shader is best understood as that machine with one stage removed. Lesson 4.1 described a draw as a pipeline: vertices are fetched and transformed, triangles are assembled and rasterized, and the rasterizer produces a stream of fragments, each of which runs the fragment shader. The expensive, massively parallel part is the last one — a million fragment-shader invocations for a full-screen triangle — and 4.1's picture of it was lanes in lock-step: 32 or 64 invocations running the same instruction at the same time on different data, many such groups in flight to hide the latency of memory.

The rasterizer's job in all this is scheduling. It decides how many fragment-shader invocations there will be (one per covered pixel), it hands each one its coordinates, and it guarantees where each one's output goes (to its own pixel, blended in draw order). Those are three conveniences, and they are also three restrictions: you cannot run the fragment shader on something that is not a pixel, you cannot choose how many there are, and you cannot write anywhere but your own pixel.

A compute shader is the lanes without the rasterizer. You write a function; you say how many times to run it; each invocation receives an integer identifying which one it is; and it can read and write any element of any storage buffer the pipeline was given. Nothing else. There is no vertex, no primitive, no pixel, no blending, no depth test. If you want an invocation to do something with the 40,961st particle, it has to know it is the 40,961st invocation, and fetch the particle itself.

So the right mental model is not "a new kind of shader" but a for loop whose iterations all run at once: 

// What the CPU particle system does:
for (Uint32 i = 0; i < capacity; ++i) { step_slot(particles[i], i, u); }

// What a compute dispatch of `capacity` threads does, in effect:
//   thread i:  step_slot(particles[i], i, u);      // for every i, simultaneously

and the rule that makes that transformation legal is the one every parallel loop has: no iteration may depend on what another iteration does in the same loop. Iteration i reads particle i and writes particle i, and never touches i + 1. That is true of this lesson's step, and it is the entire reason the step ports to a GPU with no synchronisation at all.

It is not true of every loop a particle system has, and it is worth noticing which one breaks it now, before §9 depends on it. To draw only the living particles you want a list of them, and the obvious CPU loop is 

Uint32 n = 0;
for (Uint32 i = 0; i < capacity; ++i) { if (is_alive(particles[i])) { list[n++] = i; } }

Every iteration reads and writes n. Run those iterations at once and they all read the same n, write their slot to the same place, and increment it by one between them. §9 runs exactly this with a million threads and counts what survives. The fix is a hardware instruction — an atomic — and it is the only place in the lesson the threads have to cooperate.

Hold one more picture from Lesson 1.4, because it decides the shape of the GPU half. The engine's main loop runs the simulation in fixed steps of 1/60 s, zero or more per frame, and the renderer draws the state between the last two steps with a blend factor alpha. On the CPU the steps happen inside on_fixed_step. On the GPU a step is a dispatch, and a dispatch needs a command buffer, which does not exist until the frame begins. So a fixed step on the GPU is recorded — its uniform block written down — and the frame issues one compute pass per recorded step. §12 shows the few lines that do it.

3Threads, groups and the grid

3.1 — A group is the unit of the dispatch

A compute shader does not declare how many threads run it. It declares how many run together: 

[numthreads(64, 1, 1)]
void main(uint3 id : SV_DispatchThreadID) { /* ... */ }

That attribute fixes the size of a thread group at 64. The program then asks for some number of groups — SDL_DispatchGPUCompute(pass, groups_x, groups_y, groups_z) — and the GPU runs groups × 64 threads. The three dimensions are a convenience for work that is naturally two- or three-dimensional, an image or a volume; a particle pool is a list, so everything here is one-dimensional, and the y and z counts are 1.

Why groups at all, rather than just a thread count? Because a group is the unit the hardware schedules onto one of its cores, and threads within a group can share a small fast memory and wait for one another — features this lesson does not use, but which fix the group as the thing that exists physically. The group is also where 4.1's lock-step lanes come from: a group of 64 is run as two SIMD groups of 32 on hardware whose SIMD width is 32 (Apple GPUs and NVIDIA), or one of 64 where the width is 64 (many AMD GPUs). A group size that is a multiple of 64 wastes no lanes on any of them, which is the whole of why 64 is the conventional choice.

3.2 — Three IDs, and the one you want

Each thread can ask where it is in three ways. SV_GroupID is which group it belongs to; SV_GroupThreadID is its place within that group, 0 to 63; SV_DispatchThreadID is its place in the whole grid,

\[ \texttt{SV\_DispatchThreadID}.x = \texttt{SV\_GroupID}.x \times 64 + \texttt{SV\_GroupThreadID}.x \] dispatch id = group id x 64 + thread-in-group id

and that last one is the particle's slot. Thread 3 of group 2 is thread 2·64 + 3 = 131 of the dispatch, and it steps particle 131. Figure 2 draws the grid for 1,000 particles.

3.3 — The tail

Now size the dispatch. 1,000 particles at 64 a group is 15.625 groups, and there is no such thing as five-eighths of a group. So you ask for sixteen — the ceiling of the division — and the GPU runs 1,024 threads. Threads 1,000 to 1,023 exist, run the shader, compute a slot number, and there is no particle there.

@@FIG_GRID@@

What happens next depends entirely on the first line of the shader. With it: 

if (slot >= capacity) { return; }

the twenty-four idle threads do nothing. Without it they read and write past the end of the buffer. What lies there is undefined — on some backends the access is simply dropped, on others it lands in whatever memory follows — and the harness does not try the undefined case. Instead particles_probe.comp.hlsl runs the unguarded write into a buffer with a guard zone after the data, and counts: 24 writes past the end of a 1,000-element array, one per idle thread, every time (§H). Every kernel in this lesson begins with the check. The engine's pools are always powers of two of at least 64, so today the tail is empty; the check costs one comparison and is the one line nobody may delete, because the day somebody changes the pool size it is all that stands between the tail and the next buffer in memory.

3.4 — The ceiling, done carefully

The textbook ceiling division is (n + 63) / 64. It is correct for every n that anybody will ever dispatch, and wrong at the edge: for n within 63 of 232 the addition wraps, and (4,294,967,295 + 63) / 64 is zero groups (§B's control). engine::groups_for is written as n / 64 + (n % 64 != 0), which cannot wrap, and returns 67,108,864. No particle pool reaches four billion. The point is that a helper's job is to close an edge rather than document one, and that the fix costs nothing.

4Storage buffers: a layout two compilers agree on

4.1 — What a particle is

Before any buffer, decide what one particle holds. The simulation needs a position, a velocity, an age and a life span; the draw needs a position and enough to decide how the particle looks. Three more requirements pin the rest down:

  • Interpolation needs the previous position. Lesson 1.4's renderer draws lerp(previous, current, alpha), so the state must carry where the particle was at the start of the last step. That is twelve bytes a particle that an engine advancing by the frame's delta time would not pay — the fixed-step law, costed.
  • Variation needs a name. Sparks of slightly different sizes and brightnesses look like sparks; identical ones look like a texture. Rather than store a size and a tint, the particle stores its serial number — which birth it was — and the draw hashes that into whatever variation it wants (§5). Four bytes buy unlimited per-particle variety.
  • Dead must be representable, and cheap. A particle is alive while age < life. A record of all zeros has age 0 and life 0, so it is dead, and a buffer cleared to zero is a pool with nothing in it.

That is twelve floats' worth of data: three vec3s and three scalars. The question is how to arrange them, and it is not a question of taste.

4.2 — The tempting struct, and what it becomes

Take a smaller version first, because it shows the whole problem: 

struct Naive { float3 position; float3 velocity; float age; };

In C++, with the engine's vec3 of three floats, that is 28 bytes: position at 0, velocity at 12, age at 24. HLSL's own rules for a structured buffer — tightly packed, which is what DXC produces when it compiles to DXIL for Direct3D — agree: 12 and 24, stride 28. (That one is stated from Microsoft's packing rules rather than measured: this machine's shadercross has no DXC, 4.3's capability probe says so at configure time, and CI's Windows job is where it would be checked.) Now compile the same HLSL the way this course's toolchain does on macOS — glslang's HLSL front end, producing SPIR-V, which shadercross turns into MSL — and ask the SPIR-V where the fields went. spirv-dis on the compiled kernel says: 

OpMemberDecorate %Naive 0 Offset 0
OpMemberDecorate %Naive 1 Offset 16
OpMemberDecorate %Naive 2 Offset 28
OpDecorate %_runtimearr_Naive ArrayStride 32

Velocity at 16, age at 28, and a stride of 32. The SPIR-V rules this front end applies to a storage buffer give a three-component vector the alignment of a four-component one — sixteen bytes — so velocity cannot start at 12 and is pushed to 16. The same HLSL file describes two different memory layouts depending on which compiler reads it, and the C++ struct matches only one of them.

It is worth seeing the failure rather than imagining it, so verify_618b §A does exactly that. The probe kernel writes position = (1, 2, 3), velocity = (4, 5, 6), age = 7 into a buffer of Naive records; the harness reads the bytes back and looks at them through the C++ struct. It finds velocity = (0, 4, 5) and age = 6: the padding's zero, then two of the velocity's components, then the third one mistaken for the age. Nothing crashes and nothing warns. Every particle simply moves in the wrong direction at the wrong speed, and a second record starts four bytes later than C++ thinks, so the error is different for every particle in the buffer.

SDL knows about this. The documentation of its buffer usage flags says that storage data must follow std140 conventions, and spells out the practical consequence: "vec3 and vec4 fields are 16-byte aligned". That is the rule, and Figure 3 draws what it means.

4.3 — Three rows

The layout every compiler agrees on is one in which the question never arises: every float3 starts on a 16-byte boundary and is followed by exactly one four-byte scalar, so each float3-plus-scalar pair is one 16-byte row with no padding for anybody to disagree about. The particle has three vec3s and three scalars, and they pair up exactly: 

struct particle
{
    vec3 position{};   float age = 0.0f;      // row 0: bytes  0..15
    vec3 velocity{};   float life = 0.0f;     // row 1: bytes 16..31
    vec3 previous{};   Uint32 serial = 0;     // row 2: bytes 32..47
};
static_assert(sizeof(particle) == 48, "must match `Particle` in the particle shaders");

and particles.hpp static_asserts every one of the six offsets. The harness then checks the other half: the probe writes a Particle with the values 1 to 12 in its fields and finds them at C++'s offsets, the next record at byte 48, and the uint in row 2 arriving as the bits of 12 (§A). The two static assertions and the readback are the only things standing between a struct edited in one language and a simulation that is quietly wrong in the other — which is why 6.17b's light record was built of float4s for the same reason, and why this one is built of rows.

Note

"Just use float4 everywhere" is the other common answer, and it is equally safe. Rows are preferred here because they waste nothing: a particle as three float4s with unused fourth components would need its three scalars somewhere else. The rule to carry away is not "rows" but never let a compiler choose padding. If the layout has padding, write it as a named field on both sides.

4.4 — Where the buffers go: a third register layout

Lesson 4.3 met SDL_GPU's rule that a shader's resources must sit in particular registers, and Lesson 6.17b met it again when the fragment stage got its first storage buffer at t8, space2. Compute pipelines have a layout of their own, stated in SDL_gpu.h above SDL_CreateGPUComputePipeline (checked at 3.4.12):

Resource registers by stage in SDL_GPU's HLSL layout
StageTextures and read-only storageRead-write storageUniforms
vertext[n], space0— (none)b[n], space1
fragmentt[n], space2— (none)b[n], space3
computet[n], space0u[n], space1b[n], space2

Two things in that table are new. A compute shader is the only stage that can write a buffer: the graphics stages read storage and never write it, which is why the u column is empty for them. And a compute shader's uniform block is b0 in space2 — the space in which a fragment shader keeps its textures. It is the one number in this lesson that a muscle memory trained on graphics shaders will get wrong, and the symptom is a pipeline that creates, dispatches and computes with a uniform block full of zeros.

The read-write buffers are also bound differently. A read-only storage buffer is bound by a call inside the pass, SDL_BindGPUComputeStorageBuffers, like every binding the engine has made so far. A read-write buffer is not: it is named when the pass begins, SDL_BeginGPUComputePass(cb, textures, n, buffers, m), as an array whose index is the shader's u register. The reason is that the backend has to know, at the start of the pass, every resource the pass will write, so it can place the barriers that make those writes safe to read afterwards (§10). A read-write buffer is, to a compute pass, what an attachment is to a render pass — and §11 makes the frame graph treat it exactly that way.

4.5 — Six numbers where there were four

And the counts. SDL_GPUShaderCreateInfo asked for four numbers — samplers, storage textures, storage buffers, uniform buffers — and 4.3 read them out of shadercross's JSON so nobody had to count by hand. SDL_GPUComputePipelineCreateInfo asks for six, because it distinguishes read-only storage from read-write, plus the thread-group size, which "should match the value in the shader". shadercross reports all nine; for the step kernel: 

{ "samplers": 0, "readonly_storage_textures": 0, "readonly_storage_buffers": 0,
  "readwrite_storage_textures": 0, "readwrite_storage_buffers": 1, "uniform_buffers": 1,
  "threadcount_x": 64, "threadcount_y": 1, "threadcount_z": 1 }

Hand that file to 4.3's parse_shader_reflection and it refuses — correctly. The parser searches for each key with its quotes, and "storage_buffers" is not a key in a compute reflection; "readonly_storage_buffers" contains the letters but not the opening quote. A parser that had searched without quotes would have read the wrong count and succeeded, which is the bug 4.3 designed the quoting against, meeting a case 4.3 never saw. The new parse_compute_reflection sits beside it in gpu_shader.cpp, uses the same scanner, and demands all nine keys. The harness checks both refusals: each parser rejects the other's JSON (§B).

And there is no compute shader object to create. SDL_GPU builds a graphics pipeline out of two SDL_GPUShaders and fifty-odd fields of fixed-function state; a compute pipeline has no fixed-function state, so it is created straight from the code. That is why the new gpu_compute_pipeline owns a pipeline and nothing else, and why its load is gpu_shader::load with the stage decided for it — including 4.3's trap that under MSL the entry point is main0, which a kernel does not escape.
