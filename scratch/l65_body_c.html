9Implementation

Four steps, and the order matters because the last one is what makes the whole thing verifiable.

9.1Step one: the texture gets a pool

Before a material can reference a texture by handle, textures need somewhere with stable identity. That is two lines in texture.hpp: 

using texture_handle = handle<texture>;
using texture_pool   = pool<texture>;

Note where it is not. asset_store already owns pools of meshes and images (5.5), and adding a third would have been the obvious move — but the asset store is about files: a search path, a name, a cache, a load count. Every texture in this engine so far is generated in memory. Lesson 6.6 is where textures start arriving from disk, and that is the lesson that gets to decide whether they become assets. Inventing that answer now would be guessing, which is the same call 3.7 made about the material itself.

9.2Step two: the material, and what it displaces

material.hpp is new and small. The interesting part of the diff is what shrinks: scene_object loses two fields and gains one, and ecs_swarm's invented struct loses its body entirely.

It stays a distinct type rather than becoming engine::material outright, and that is deliberate: an ECS component is an identity, not just a payload. view<geometry, material> names this component, and two components that happened to share a layout would be indistinguishable to the registry. Lesson 5.7 made the same call about placement.

9.3Step three: one packing site

uniforms_of (§5) replaces the hand-assembly at three call sites. The sandbox's version went from five statements to one — and, as §5 records, that substitution was wrong until the texture decision was moved onto the material, which is the point the function is making.

10The Refactor, in Two Halves

Everything above is a refactor, which means it gets exactly one correctness claim: the picture does not change. Lesson 5.1 built the machinery for making that claim and stated the rule for using it:

5.1's rule

Move without changing, then change without moving, verifying separately.

"Separately" is the load-bearing word. If you move code and change behaviour in one step and the output shifts, you have two candidate causes and no way to tell them apart. Worse, if the two changes have compensating errors, the output can come out right and both bugs survive.

So this lesson ran the golden three times:

A false alarm worth having, because the symptom was not a crash

Capturing that "before" render meant stashing the work, rebuilding, and shooting. The rebuild was incremental, and scene_object had changed size (96 → 112 bytes) — so some objects were compiled against the old layout and some against the new.

The result was not a crash. It was a shot with the wrong scenes in it: frame 1 rendering solids instead of cycle, triangle counts of 20 where 44 was right, and one frame's name printing as ?. Plausible garbage, which took a minute to distinguish from a real regression.

The fix was cmake --build build --target clean, and the rule is: after any change to a struct's layout, an incremental build is not evidence. That is the same failure class as a uniform block disagreeing with its shader, arriving on the CPU side.

11What It Cost

A material system is not free, and one of the existing harnesses said so immediately. verify_56 — Lesson 5.6's cache-behaviour work — asserts the size of scene_object, and it failed: 

[FAIL] scene_object is 112 bytes (1.5 cache lines)

It was 96. The material added 16 bytes net, and the assertion is worth keeping rather than relaxing, because 5.6 is the lesson that measured why object size matters at all.

14Common Pitfalls & Debugging

The scene renders the wrong objects entirely after a struct change

Symptom: wrong meshes, wrong counts, garbage names — but no crash.

Cause: an incremental build after a layout change. Some translation units have the old sizeof and some the new, so every field after the change is read at the wrong offset.

Fix: cmake --build build --target clean. And treat it as a rule: after a struct's layout changes, an incremental build is not evidence.

Textures vanish after switching to uniforms_of

Symptom: everything draws flat-coloured; the GPU path lost its images.

Cause: the material's albedo_map was never set, because the texture was still being chosen somewhere else. The derived flag correctly reports "no image" — the material was simply not told.

Fix: move the decision onto the material. If two places both have an opinion about whether a surface is textured, deriving the flag has not helped; it has just picked the uninformed one.

A material renders as debug magenta

Symptom: one surface is bright magenta.

Cause: a stale handle — well-formed, naming a slot whose occupant is gone — or a texture bound at a slot the shader declares but nothing filled.

Fix: pool::contains() answers the first, and it is a different question from handle::valid() (5.4). Note that bind_albedo already degrades a stale handle to "no image" rather than to magenta — so magenta means the binding was made another way.

Objects sharing a material change together, unexpectedly

Symptom: tweaking one entity's roughness changes ninety-five others.

Cause: that is the feature. They share a handle.

Fix: if an object needs its own appearance, give it its own material — pool.insert() a copy. The decision "shared or unique" is now explicit at the point of creation, which is exactly the improvement: before, everything was unique and nothing said so.

15Exercises

15.1 — Break the split on purpose

Add cull_mode cull; to material and wire it through. Then count the pipeline objects the GPU renderer needs, and the pipeline binds per frame with and without the draw-list sort.

Solution sketch

Nothing stops you compiling it — that is the point. What breaks is the batching: two objects differing only in cull mode can no longer be drawn back to back, and draw_stats::pipeline_binds climbs away from ideal_pipeline_binds. The field is legal C++ and a category error, and the only thing that tells you is the stat Lesson 4.8 added.

15.2 — Make a handle go stale, and watch what happens

Give an object a material with a valid albedo_map, then remove that texture from the pool while the scene is still rendering. Predict the result before you run it.

Hint

bind_albedo returns {nullptr, samp} for a handle the pool no longer contains, and texture_binding::bound() is false.

Solution sketch

The surface falls back to its tint and keeps rendering. Now do the same thing with the pre-6.5 code, which stored a const texture*: you get freed memory, and whether that crashes depends on the allocator's mood. The handle turned undefined behaviour into a defined fallback, and that is worth more than the four bytes it saved.

15.3 — Find the next invented type

§2 argued that a demo inventing an engine type is a measurement of a missing API. Read the demos for others. What has sandbox declared that the engine should own?

Solution sketch

scene_mesh_cache and orbit_camera are both strong candidates — one is an asset-derivation cache the engine plausibly wants, the other is a camera the engine definitely does. Note that the argument is not "move everything": a demo is allowed demo-specific types. The signal is a demo type that other demos also declare.

15.4 — Intern the sampler (engine challenge)

§11 measured the sampler as 16 of the material's 36 bytes, identical for every object. Replace it with a sampler_handle into a small pool and measure sizeof(scene_object) again.

Hint

The pool will hold two or three entries for the whole program. That is itself the interesting result: it is what "identical for every object" looks like once it is measured.

Solution sketch

material drops to 24 bytes and scene_object back under 100. Then ask the §6 question honestly: does anything share a sampler in a way that matters, or is this only about bytes? If it is only about bytes, the case is weaker than the texture's — and knowing which argument you are making is the exercise.

16Recap & Next

The engine has a material: one type for what a surface is, referenced by handle where it refers to assets, packed to the GPU in one place, and shared where sharing is real.

What the engine gained:

  • A rule that decides membership — can this be a number in a buffer? — which is the hardware's line rather than a matter of taste, and which verify_65 asserts with a trivially_copyable check.
  • Handles for stored references, pointers for inner loops, and bind_albedo as the named step between. A stale handle now degrades to "no image" instead of to freed memory.
  • A derived flag instead of a stored one — removing a state the program could previously represent and never should have been able to.
  • Sharing, measured: 3,456 bytes to 600 for the swarm's ring, and, more importantly, one write where there was a loop.
  • Two corrections to comments that had been repeating for three modules — closed was never material state, and the compile-time argument for cull.hpp did not survive being measured.

And one deletion worth more than anything added: ecs_swarm's hand-written struct material. A demo built it because the engine had a hole; the hole is filled, so the demo stops needing to.

The reference render is byte-identical, hash E917C06C, across all three stages of the refactor. That is the only claim a refactor is entitled to make, and making it in separately-verified halves is what stops two compensating bugs from cancelling into a passing test.

Next: 6.6 — glTF 2.0 Loading. Everything this lesson deferred, 6.6 forces. Textures start arriving from files, which is when the question "should the asset store own the texture pool?" stops being premature. glTF files define materials, which is when a material needs a name, a cache and an identity that survives a reload. And the glTF specification defines its own reference BRDF using the 1 − F(v·h) coupling that Lesson 6.4 measured at 1.3395 and declined to ship — so the interoperability question this engine has been able to avoid arrives with an asset attached.
