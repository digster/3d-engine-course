Module 5 — Becoming an Engine · Lesson 5.11

Dear ImGui and the Debug Draw System

Two subsystems, and they are one lesson because they are one thing: the tooling. ImGui is the tooling interface; debug draw is the tooling in the world. This is the first library in the course whose vocabulary we let through the engine's public boundary, and the argument for that is not "it is hard" — the rasterizer was hard and we wrote it. Along the way, a debug-draw header that has been quietly wrong since Module 3 gets the rework it has been owed, and a text field turns out to be the hardest input problem in the engine.

1The Problem

Lesson 5.9 built a transform hierarchy and made a claim about it: a moon's world placement is computed by nobody, because world(moon) = world(planet) × local(moon) is what "relative to my parent" means. The demo has been running ever since with 154 entities in a three-level tree, and you have had exactly two ways to believe that claim — read the code, or read a line of text that says hierarchy 154 rows, 2 roots, 3 levels.

Both are fine. Neither is seeing it. And the difference matters enormously the first time something is wrong, because a count of 154 rows is equally consistent with a correct tree and with a tree in which forty-eight entities are parented to the wrong planet.

We have had the tool to fix that since Module 3. engine/gfx/debug_draw.hpp can draw a world-space line:

Now try to call it from the place that knows about parents. That code is a system: it takes a registry and walks a view. It does not have a framebuffer, it does not have a projector, and — this is the part worth sitting with — it should not have them. The moment you hand a framebuffer to an ECS pass so it can draw a diagnostic line, every caller of that pass needs one too, and their callers, and the "debug feature" has become an architecture.

So the tool exists and cannot be used by the code that needs it. That is a design problem rather than a missing feature, and it has two siblings hiding behind it, which §3 takes apart.

2Why We Do Not Hand-Roll This

2.1 The test, and where the line falls

This course has a rule about third-party libraries, stated in the master prompt and applied four times so far: every dependency arrives with an explicit justification for not writing it ourselves. The rule is easy to state badly. It is not "we write the easy things and buy the hard ones" — we wrote the rasterizer, and a rasterizer is harder than a PNG decoder. The test is:

The test

Is the hard part the subject? If the difficulty is the thing the course is about, we write it, however long it takes. If the difficulty is somewhere else entirely, we take the library and spend the time on the subject.

Apply it to a debug UI. What is actually hard about one? Four things, and they are four different fields:

  • Text. A font rasterizer, an atlas, kerning, and — the moment anybody types a character outside ASCII — shaping. Module 6's text-rendering lesson does this properly, and even that is the drawing — the shaping is a library there too.
  • Layout. Where does the next widget go? What happens when the window is narrower than the label? What are the rules for a table column that wants to stretch? This is the y-coordinate arithmetic above, generalised — and generalising it correctly is an entire discipline.
  • Input routing. Which widget has focus, what happens when you drag from inside one widget to another, what a click means when two windows overlap, how the keyboard moves between fields.
  • Widget state across frames. A slider being dragged is a state machine that spans frames, and so is a text field with a cursor and a selection, and so is a collapsing header that remembers it is open.

Not one of those is graphics, engine architecture, or maths. And a half-built version of all four is worse than useless: it is the tool you stop trusting the first time it misreports a number, at which point you are debugging your debugger.

The numbers make the trade concrete. Dear ImGui's core is 41,385 lines across four files. Its SDL3 backends are another 1,232. Our integration — the file that owns the whole lifecycle — is 182 lines, and you will read all of it in §8.

2.2 What immediate mode actually means

"Immediate mode" gets used as a slogan, so it is worth being precise, because the property it names is exactly why this is the right library for a debug tool rather than merely a convenient one.

In a retained-mode UI — every desktop toolkit, every game-engine editor built on one — you construct objects. A Label, a Slider, a TreeView. They live in a tree, they persist between frames, and your job is to keep them in sync with the world: when an entity is destroyed you must remember to remove its row; when a value changes you must remember to push it to the label. Every one of those "must remember"s is a bug waiting to happen, and the bug's symptom is a UI that shows something that is no longer true.

In an immediate-mode UI there are no objects. There is a function that runs every frame:

There is no Label object holding a stale copy of world_.size(), because there is no object at all — the number is read from the world during the frame it is displayed in. The panel cannot be stale, because there is nowhere for staleness to live. Destroy every entity and the panel says zero on the very next frame, with no invalidation, no observers, and no code that anybody had to remember to write.

The Checkbox line is the same trick running the other way: it takes the address of the program's own boolean and toggles it. The panel is not a second copy of the program's state that must be reconciled; it is a window onto the state itself.

That model has real costs — it rebuilds all its geometry every frame, and it makes animation and complex layout awkward — which is exactly why the rule "tooling only, never gameplay UI" is a binding one in this course rather than a stylistic preference. A game's HUD needs a font the art director chose, a layout that survives translation into German, controller focus, and safe areas on a television. ImGui offers none of that and does not pretend to.

2.3 A public dependency, for the first time

Lesson 4.7 took this project's first non-SDL dependency, stb_image, and hid it completely. Exactly one translation unit includes it; engine::image is our own type; and engine/CMakeLists.txt links it PRIVATE, so a demo can neither see stb nor accidentally start depending on it. The dependency stops at the library boundary. That is what a good wrapper buys.

ImGui gets the opposite treatment, and the reason is not laziness.

Why one was wrapped and the other is not

With stb_image we wrapped a concept — "decode these bytes into pixels" — which is one function and one type. The wrapper is small because the concept is small.

ImGui's value is its vocabulary: Begin, Text, SliderFloat, BeginTable, Checkbox, and several hundred more, each with overloads, flags and an interaction model. A wrapper around that surface is a re-spelling with no content in it — and it has to be re-spelt again for every widget, forever, by somebody who is not the person who wrote the widget.

So demos/ includes <imgui.h> directly and calls ImGui:: functions, and the engine links imgui PUBLIC. Say the cost out loud rather than discovering it later: the engine's public API now contains a second third-party vocabulary, and if ImGui were ever replaced, every panel in the project would be rewritten.

What makes that acceptable is containment. The only code allowed to speak ImGui is tooling code, and tooling code is code that can be rewritten without the game changing behaviour by one pixel. Compare Lesson 5.1 §6 on SDL in our public headers: the same admission, made for the same reason, with the same eyes open.

One more thing the build teaches, because it is a small surprise the first time: ImGui ships sources, not a build. There is no CMakeLists.txt in that repository — deliberately, on its author's part, because the library is a handful of .cpp files and every project wants to compile them its own way. FetchContent_MakeAvailable notices the absence and only populates; the target is ours to declare. Being forced to declare it is how you find out exactly which files you are compiling, which is a better position to be in than the alternative.

imgui_demo.cpp is 11,299 lines of showcase and it is in that list on purpose: ImGui::ShowDemoWindow() is the fastest widget reference in existence, and its source is the documentation — every widget in the window is a few lines away in a file you already have. Drop it when a real game ships.

Note also what is not in the build: engine_set_warnings(imgui). Our -Wall -Wextra discipline applies to our targets and never to somebody else's, for the reason cmake/EngineHelpers.cmake gave in Lesson 5.1 — warnings you cannot act on train you to ignore the ones you can.

3The Rework: Saying and Doing

3.1 Three problems wearing one coat

Back to line3_world(fb, view, pr, a, b, colour). §1 found one problem with it. There are three, they all come from the same root, and they are worth separating because two of them are invisible until later modules.

  1. The caller must be the renderer. Two of the six parameters are renderer state, so only code holding renderer state can call it. §1's collision system, ECS pass and mesh loader are all locked out.

  2. It works on one surface. framebuffer is the software renderer's target. Under surface::gpu — the path Module 4 spent nine lessons building, and the path Module 6 lives on — there is no framebuffer at all. Every one of these calls is simply unavailable there.

  3. A line lives exactly one frame. This one is the most easily dismissed and the most important. A collision normal exists for one simulation step. At 60 Hz that is 16.7 milliseconds on screen. Human visual processing needs something on the order of 250 ms to register that a small thing appeared and vanished — so a single-frame marker for a single-frame event is, for the person the debug drawing exists to serve, invisible.

That third point deserves to be stated as a design principle, because it is the one that justifies building a system rather than adding a function:

The reason debug geometry has lifetimes

The events you most need to see are the ones that happen in a single frame — a contact, a re-parent, a spawn, a raycast hit. Those are precisely the events a per-frame drawing cannot show you. A debug view without lifetimes can only show you state, never events, and it is usually the events you are hunting.

One change fixes all three: separate saying what to draw from doing it. A debug_lines queue holds world-space segments with lifetimes. Anybody can queue. A backend flushes the queue through whatever it has — a framebuffer today, an SDL_GPU render pass in Module 6 — and the queue never learns which.

Notice that the queue makes nothing faster. It removes an argument from every call site, and that argument was the entire reason the caller had to be the renderer.

3.2 The include list is the interface

Here is where the design could quietly fail. It is tempting to put the queue in debug_draw.hpp, which is after all the debug-drawing header. Do that and everything compiles, everything works, and the promise is broken — because debug_draw.hpp includes the framebuffer, the depth buffer, the projector, the viewport and mesh, and C++ include dependencies are transitive.

A physics system that includes it to draw one box compiles the renderer. Not links — that is the linker's business and it is fine — compiles, in every translation unit, forever.

That constraint has one visible consequence in the API, and it is worth defending because it looks like fussiness. wire_mesh does not take a mesh:

mesh lives in gfx/mesh.hpp, which pulls in core/pool.hpp and the whole handle system — none of which a collision routine should compile in order to draw a wireframe. Taking the two arrays costs a caller nine characters (m.vertices, m.indices) and keeps the promise at the top of the file intact. Take the data, not the type is a general move, and this is a clean example of when it earns its keep.
