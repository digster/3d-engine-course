4Lifetimes, and the Frame That Has No Time

A queued line carries a remaining in seconds, and the default is zero. Zero has to mean "draw me on this frame and then forget me", because that is what almost every debug drawing wants: the hierarchy is re-queued from the live data every frame, so a copy that survived would be a copy that could be wrong.

Ageing the queue is one function, and it is the single easiest thing in this lesson to get subtly wrong — twice over, in two different ways.

4.1 The order

The frame has three debug-draw events in it and their order is fixed:

Put advance() first — which is where "clear the buffer at the start of the frame" instinct puts it — and every line queued this frame with the default lifetime is deleted before it is ever drawn. The symptom is not a crash or a warning. It is a debug system that draws nothing, which reads as "my code did not run", which sends you looking in entirely the wrong place. verify_511 §B asserts this as a measurement rather than leaving it as a warning: three lines queued, aged, and zero left to draw.

4.2 The rule, and the frame with dt == 0

Now the expiry rule itself. The obvious version is two lines, and it is worth being precise about what is wrong with it, because the honest answer is not "it is broken" — it is "whether it is broken depends on a comparison operator and on dt, and neither of those should be load-bearing."

The first line works. A default-lifetime line has remaining == 0, subtracting any dt leaves it at or below zero, and it is dropped. Good.

The second is what you write the moment you want a line to survive the frame on which its clock runs out — a reasonable thing to want, and a one-character change. Now put dt = 0 through it: 0 − 0 = 0, which is not less than zero, so the line is kept. And so is every line queued on every subsequent frame. The queue fills, reaches its bound, and starts refusing the lines you are queueing now.

And dt == 0 is not exotic. It is a paused clock, a single-frame --shot, a program stopped on a breakpoint while you look at it, or a frame the OS delivered in under a microsecond. Those are exactly the moments you are looking hardest, which makes this a leak that only appears while you are using the tool.

Putting the test before the subtraction removes the dependency rather than getting it right. "Has this line had its frame?" is then answered by the stored value alone, with dt playing no part in it:

A zero-second line is queued, drawn, and dropped at the next advance whatever dt is — and so is a two-second line, 120 frames later. The visible cost is that a line asked to live two seconds lives two seconds plus one frame: the frame on which its clock reaches zero is still a frame it is drawn on. That is the right way round to be wrong for a thing whose entire purpose is to be seen.

verify_511 §B pins the behaviour, not the implementation — it asserts that a default line dies with dt = 0 and that a half-second line is drawn on 31 frames. A future simplification back to subtract-first with <= would pass the first and fail the second, which is the correct amount of pressure: it says "you changed something observable" without pretending there is only one acceptable answer.

@@FIG_LIFETIME@@
Worked example — how many frames is half a second?

Queue a line with seconds = 0.5 and call advance(1/60) until it is gone. After 29 advances remaining is about 0.0167 — still positive. The 30th advance therefore keeps it and takes remaining to approximately zero. The 31st sees a value that is no longer positive and drops it.

So the line is present for 31 flushes: 30 frames of the time it asked for, plus the one on which its clock ran out. verify_511 §B counts exactly 31.

And the same experiment run against the alternatives, in float: subtract-first with <= gives 30 and correctly drops a default line when dt = 0; subtract-first with < also gives 30 but keeps the default line for ever at dt = 0 — the run was cut off at 500 advances. Two rules differ by one frame; the third differs by infinity.

4.3 The bound, and the counter that makes it honest

The queue is capped — 4,096 lines by default — and refuses rather than grows. A debug system that allocates without limit is a debug system that turns "why is this frame 200 ms" into a question whose answer is the debug system.

A bound on its own would be worse than none, though, because the failure is silent: the 4,097th line simply is not there, and a missing line looks exactly like a thing that does not exist. So the queue counts what it refused, and the panel prints it. Three numbers together — queued, drawn, dropped — are what tell you whether the picture you are looking at is the whole picture.

Every primitive funnels through one private push(), which is where the bound is checked. That is not tidiness: it means a twelve-edge box arriving with two free slots leaves two edges and ten drops, and it means that adding a primitive next month cannot forget to ask.

5ImGui in the Frame

5.1 Two backends, and which one first

ImGui separates "what a window looks like" — the core — from two backends you choose independently:

  • a platform backend, which turns OS events into ImGui's input state: imgui_impl_sdl3;
  • a renderer backend, which turns ImGui's vertex and index draw lists into actual drawing: imgui_impl_sdlrenderer3 or imgui_impl_sdlgpu3.

This engine has two surfaces (Lesson 4.2), so which renderer backend goes first is a real decision rather than a coin flip. The SDL_Renderer pair goes first, for two reasons that are both about scope rather than difficulty:

  • ecs_swarm — the demo that needs a panel today, because it is the one with a hierarchy to inspect — is on surface::renderer.
  • Under surface::renderer the platform already owns the presentation, so on_overlay() is a hook that exists at exactly the right moment: after the framebuffer has been blitted, before the frame is presented. On surface::gpu the program owns the device, the command buffer and the render pass, so the UI has to be handed all three by code the engine does not control.

§7 says precisely what the GPU path would need, with the real signatures, and why it is not in this lesson.

5.2 Where each call goes

Six calls, and one of them has a placement that is not negotiable.

5.3 The surface with no renderer

Every --shot in this repository runs headless: no window, no renderer, no video subsystem. A UI cannot start there, and the design question is what "cannot start" should feel like from the outside.

The answer is: like nothing at all. start() returns false, running() answers false, and every other call is a safe no-op — including wants_keyboard(), which answers false, so the mask in §6 blocks nothing and the game behaves exactly as it did before this lesson existed. That is what lets one program be written once and run correctly on all three surfaces, and it is what lets Lesson 5.1's reference image survive an eleventh lesson unchanged.

Note also that start() logs this at info, not error. A program built for a build server is not failing; it is running the way it was asked to. Logging it as an error would put a red line in every headless run in this repository and train the reader to ignore red lines — which is the same argument engine_set_warnings made about compiler warnings in §2.3, one layer up.

The one genuine wart is worth naming rather than hiding. Every other system Module 5 built is a value: asset_store, registry, action_map and debug_lines can all be held as many times as a program needs, because the engine does not know how many of a thing a game wants and declines to decide. debug_ui cannot be, because ImGui keeps its context in a library global that every ImGui:: call reads. Two live instances would silently share one set of windows. We do not pretend otherwise: start() refuses a second instance and says so in the log, because an enforced limit you can read beats an undocumented one you discover.

6The Input Seam

Here is the situation the whole of Lesson 5.10 was quietly waiting for. There is now a text field on screen. Click into it and type spawn. The s must reach the text field. It must not reach the game, where — in a demo with a spawn action bound to the space bar and toggles on half the alphabet — it would fire several of them.

Two consumers, one keyboard. Somebody has to arbitrate.

6.1 Arbitrate on levels, never on events

The obvious design is to route events: hand each event to the UI first, and if the UI took it, do not hand it on. It is obvious, it is what a lot of code does, and it is wrong in a way that takes a week to find.

The key that is held down forever

Symptom. After using the debug panel, the character keeps walking forward. Nothing is pressed. Tapping the key again fixes it.

Cause. A key-up event was routed to the UI and not passed on. engine::input tracks levels — is this key down — and a level is only ever corrected by the event that contradicts it. Withhold that event and the level is stuck, permanently, and no later event will fix it because the key is not going to be released twice.

Fix. Never withhold events. Feed every event to every consumer, and arbitrate one layer later, on the levels.

@@FIG_SEAM@@

So on_event gives every event to ImGui, and the engine has already given the same event to engine::input before the hook runs (Lesson 5.2's ordering guarantee). Both see everything. The arbitration happens in on_input, where the action map is updated — and this is where Lesson 5.10's design pays for itself a second time.

Recall that action_map::update is a template constrained by a concept rather than a function taking const input&:

That was written for testability: it let a harness build a six-function fake instead of persuading SDL that a key was held. It turns out to buy something else entirely. A masked input is just another type satisfying the same concept — one that wraps a real snapshot and lies about the parts the UI has claimed:

Not one character of action_map changed. Had update taken a const input&, the only two ways in would have been an if inside the map — the input mapper learning what a UI is — or a copy of input with fields cleared, which is a second source of truth about the keyboard. Depending on a shape rather than a type is what made a third option exist.

One subtlety that looks like a bug and is not: the map is still updated while the UI has focus. It would seem cheaper to skip the update entirely, but a level that stops being updated is a level that is frozen — hold [Left], click into the filter box, and the camera would yaw forever. Updating through the mask reports every masked key as up, which produces the release edge. And that is not damage limitation, it is the behaviour you want: giving focus to a text field genuinely should let go of the movement keys.

6.2 You cannot mask a delta

Masking a key is a lie told about one frame, and it is complete: a key is a level, the level is false, done. The mouse is not so simple, and this is the subtlest thing in the lesson.

action_map derives a mouse delta by subtracting the previous frame's cursor position from this frame's. A delta is a difference between two frames — so suppressing one endpoint of a difference does not suppress the difference. Consider the cursor sitting at x = 100, the UI taking the mouse for three frames while the cursor travels to 160, and then letting go as it moves on to 170.

ApproachDelta while blockedDelta on the release frameWhat that is
report 0 while blocked0+170 the whole screen, in one frame
freeze the last position0+70 the whole excursion — the version that ships

The first is obviously wrong and you will catch it in a minute: reporting 0 makes the next real reading a difference against zero. The second looks right and is the one that ends up in shipped code, because it behaves perfectly until somebody drags a slider — at which point letting go of it whips the camera round by the distance they dragged.

The fix is to stop thinking of it as masking and start thinking of it as a change of frame of reference. The mask keeps a virtual cursor: it reports real − offset, and grows offset by exactly this frame's real movement on every blocked frame.

@@FIG_CURSOR@@
Worked example — the four frames, by hand

Frame 0 (unblocked, real 100): offset 0, reported 100. The map latches it; there is no previous, so no delta.

Frame 1 (blocked, real 120): offset becomes 0 + (120 − 100) = 20. Reported is 120 − 20 = 100. The previous reported value was also 100, so Δ = 0.

Frame 2 (blocked, real 145): offset becomes 20 + 25 = 45. Reported is 145 − 45 = 100. Δ = 0.

Frame 3 (blocked, real 160): offset becomes 45 + 15 = 60. Reported is 160 − 60 = 100. Δ = 0. The reported cursor has not moved since the block began.

Frame 4 (unblocked, real 170): the offset does not grow, because the frame is not blocked. Reported is 170 − 60 = 110, the previous reported was 100, so Δ = +10 — which is exactly how far the mouse moved during a frame the game was listening.

The cursor stays 60 pixels behind the real one from now until the program ends, and it is permanently right about how far it moved — which is the only question anybody asked it. verify_511 §E runs precisely these five frames.

The wheel needs none of this, and the reason is worth spotting because it tells you when the machinery is necessary. input publishes the wheel as a per-frame delta already — it is not a position anybody differences — so reporting zero for it is exact rather than a lie about a level. The elaborate treatment is required only where the consumer derives the delta itself.

7What We Did Not Build

Three things are deliberately absent, and each is named here rather than discovered later.

7.1 The SDL_GPU backend

ImGui ships one — imgui_impl_sdlgpu3 — and the engine's seam is already the right shape for it: debug_ui would grow a second start() overload and a render() that takes a command buffer and a render pass. The platform half (imgui_impl_sdl3) is shared; only the renderer half changes. These are the actual signatures, read from the header rather than remembered:

Note the shape of it: two calls rather than one, because uploading the vertex data and recording the draw happen at different points in a GPU frame — PrepareDrawData before the render pass begins, RenderDrawData inside it. That is Lesson 4.2's model, and the split is the same one Lesson 4.7 met with texture uploads.

It is not in this lesson because wiring it means threading a command buffer and a render pass out of sandbox's own frame — which is 4,700 lines of demo, and a lesson's worth of surgery on somebody else's program to demonstrate a call we can already read. Exercise 11.4 does it. Module 6, which lives on the GPU path, does it for real.

7.2 Depth-tested debug lines

draw_debug_lines draws over the scene, unconditionally. That is right nine times in ten: a contact normal buried inside the two objects that produced it is a contact normal you cannot see. The tenth time you do want occlusion — a hierarchy line passing behind a wall should say so — and that wants a per-line flag plus a depth buffer this function is not given.

A flag no backend honours is speculative design, so there is no flag. Exercise 11.3 adds one, and the interesting part of that exercise is not the flag: it is that a depth-tested line and an overlaid one must be drawn in two passes, which makes the queue's ordering guarantee suddenly load-bearing.

7.3 Batching

The flush walks the queue and draws one segment at a time. On the software renderer that is exactly right — there is nothing to batch into. On the GPU it will be badly wrong, and one draw call per line will dominate a frame.

Say plainly what has been bought anyway: the queue is what makes batching possible at all. You cannot batch calls that have already happened. An immediate-mode drawer forecloses the optimisation permanently; a queue defers the decision to the module that has a reason to care.
