Module 5 — Becoming an Engine · Lesson 5.5

The Asset System v1

Last lesson built a reference that can be told it is out of date. That is the mechanism; today is the policy, and it answers three questions a pool does not: where a mesh comes from, how asking for it twice gives you the same one, and — the word this whole module has been building towards — how to unload it. Along the way we refuse to reference-count, and the argument for refusing is the same sentence that made handles worth having. We close the lifetime hole 5.4 deliberately left open. And we free a mesh out from under a scene that is still drawing it, on a keypress, to watch exactly one object disappear with a number next to it.

1The Problem

Lesson 5.4 ended with a pool that can say no. A handle resolves or it does not; a freed slot bumps its generation; a stale reference is a null pointer and a counter rather than undefined behaviour. That is a genuinely useful thing to own, and it answers exactly one question — is this reference still good?

Here are three it does not answer.

@@FIG_QUESTIONS@@

Take them one at a time, because each one has a receipt in the current source.

Loading. Here is what it took to put a model on screen before this lesson, with the comments removed so the shape is visible:

Assemble a path. Open a file. Parse it. Apply an import convention. Time it. Validate it. Free the previous one. Store the new one. Eight steps, in demo code, and only two of them — which file, and what to do if it is missing — are a program's business. The other six are the same six every program will write, slightly differently, until one of them forgets the uv flip.

Finding. There is no name-to-handle map anywhere in this engine, so there is no such thing as asking for an asset you might already have. Every request is a fresh load. Lesson 3.5 wrote a comment about this at the time, and it is worth quoting because it was a promissory note:

demos/sandbox/main.cpp, Lesson 3.5

“A real load, on a keypress, every time — not a cache lookup. It costs about half a millisecond for the torus and the HUD says so, which is the honest way to introduce the fact that asset loading is work. Module 5 caches; today we measure.”

Unloading. And this is the one that matters, because the other two are conveniences and this is a capability. Nothing in this engine has ever freed anything. Not once, in fifty-four lessons. Every mesh, texture and buffer ever created has lived until the process exited, which is why Lesson 5.4's whole argument had to be made in the abstract: the question "is this reference still valid?" had never once been answered no in a running program.

There is a fourth problem, smaller and more embarrassing. The engine currently has three answers to "where do files live", and none of them knows about the others: engine::asset_path in gfx/obj.cpp (whose own comment calls itself “a placeholder for Module 5's asset system”), shader_path in gfx/gpu_shader.cpp — written by copying the first — and the demo, which assembles std::strings around the first at three call sites. Three copies of one idea is the usual sign that the idea has no name.

2Building Intuition

2.1The lending library

Lesson 5.4's cloakroom took your coat and gave you a numbered ticket. A lending library is the same idea with three additions, and those additions are exactly this lesson.

First, you ask for a book by title, not by shelf. You do not walk in and say "give me whatever is in position 4,192"; you say "Dune", and somebody who knows where things are turns that into a shelf. That indirection is what lets the library reorganise, and it is what lets your library card from last year still work.

Second, there is one copy. If two people ask for the same title on the same afternoon, the library does not go and print a second one. This sounds obvious and it is the thing our engine currently gets wrong: press L twice and it reads the same 200 KB off disk twice, parses it twice, and hands you two unrelated meshes with identical contents.

Third — and this is the addition that changes the design rather than decorating it — books can be withdrawn. A library that only ever acquires is a warehouse. The moment withdrawal is possible, every card in every pocket becomes a question, and the library needs a policy: who is allowed to withdraw, what happens to somebody holding a card for a withdrawn book, and what happens to the photocopies somebody made of chapter four.

That last clause is not a joke. It is the derived-asset problem, and §3.2 is about it.

2.2A name is not a path

Before any of that, the smallest idea in the lesson and the one everything else stands on.

@@FIG_SEARCH_PATH@@

"torus.obj" is a name. It is stable, it is what a scene file records, it is what a level designer types, and it is the key an asset store caches on. /Users/…/build/demos/assets/torus.obj is a path: where that name resolved today, on this machine, with these roots. Store the first; compute the second.

Once names and paths are different things, the resolution step becomes a place you can put a policy — and the policy that earns its keep immediately is an ordered list of roots. A single directory needs no list. What a list buys is override: put a directory in front and everything in it shadows the shipped asset of the same name, without moving, renaming or deleting anything.

That one property is the mechanism behind four features that look unrelated:

  • Mods and user content. The mod folder goes in front.
  • Localisation and platform packs. assets_ja/ or assets_lowend/ goes in front, and every asset it does not contain falls through to the base.
  • Editing while the game runs. Your source tree goes in front of the copy CMake made beside the binary — which is half of Module 9's hot reload, arriving early and for free.
  • A test standing in for a real asset. Which is exactly what verify_55 §A does: it writes a deliberately different torus into an override root and proves, by file size, which one came back.

3The Theory

3.1Why not reference counting

"When may I free this?" has an obvious answer: count who is holding it, and free at zero. Reference counting is correct, it is well understood, and the standard library will do it for you. It is also the wrong answer here, and the reason is not performance. It is that reference counting requires a property our handles deliberately do not have.

@@FIG_NO_REFCOUNT@@

Recall what a handle is, from Lesson 5.4: four bytes, trivially copyable, with no lifetime of its own. Every one of those words was load-bearing. It is four bytes so it fits in an ECS component; trivially copyable so it can be memcpy'd; without a lifetime so it can be written to a file and read back without pointer fixups.

Reference counting requires the opposite of all three. Copying must have a side effect, so the handle needs a copy constructor. Going out of scope must have one too, so it needs a destructor. And it must know whose count to touch, so it needs a pointer back to its store — which triples its size and makes it meaningless in a saved file.

A refcounted handle is a shared_ptr with extra steps, and we already know what shared_ptr costs. So the policy is explicit unload, and the interesting part is why that is safe to get wrong:

  • Forget to unload → a leak. A leak is found by a total, and asset_store::live_count() at shutdown is that total.
  • Unload too early → a lookup that returns null and a counter that goes up. Lesson 5.4 built exactly this: collect_stats::unresolved.

Neither is a crash, and neither is undefined. That is the trade, and it is the one most engines make at level granularity — load a level, play it, unload it, check that the count came back to zero.

This is not "refcounting is bad"

It is "refcounting is wrong for a reference that must stay a value". Where a reference is already an object with a lifetime, a count is often exactly right — gpu_texture's RAII wrapper is a count of one, honestly implemented. The question to ask is never "should this be refcounted?" but "what does this reference have to be able to do, and does a count take that away?"

3.2The one place a rule is unavoidable

Explicit unload works because a handle is held by somebody who can be told — a scene, a component, a piece of code with an owner. There is one class of asset for which that is not true, and Lesson 5.4 named it as an open hole rather than pretending otherwise.

with_normals takes a loaded mesh and produces a different mesh: a different vertex count, different normals, a different index buffer. It is a real asset, it occupies real memory, and it must be stored somewhere. But nobody asked for it. It has no name, nothing outside the system knows it exists, and it has no reason to exist except that its source does.

@@FIG_CASCADE@@

This shape is everywhere once you look: a texture and its mipmap chain, a shader and its per-backend variants, a mesh and its GPU upload, an animation and its compressed form. The general name is a derived asset, and the rule that governs it is not a reference count — it is a dependency edge:

The rule

A derived asset is owned by its source. Unloading a source unloads everything derived from it, transitively. Nothing outside the store can hold a derivation, so nothing outside the store has to be consulted.

Two words in that rule do real work. Transitively, because derivations chain — a mesh is imported, and the import is uploaded — and a cascade that stops after one hop leaks the tail. And owned rather than counted, because the relationship is one-directional and internal: there is exactly one source, it is known at the moment of creation, and it never changes.

There is a corollary worth stating, because it is the check that keeps the design honest: deriving from a source that is already gone must be refused. The result would be an asset with no name to find it by and no source to free it with — a thing nothing will ever release. Our derive_mesh returns a null handle in that case, which turns a guaranteed leak into a null the caller is already prepared to see.

3.3Import settings are identity

Here is a question that looks like bookkeeping and is not. Lesson 3.9 established that OBJ counts texture coordinates upward from the bottom left while a texture is addressed downward from the top left, and that reconciling the two belongs to the import step. The demo has a key that toggles it, so the disagreement can be looked at.

So: is torus.obj imported with the flip the same asset as torus.obj imported without it?

It is not, and the answer is not a matter of taste — the two have different vertex arrays. A store that keyed on the filename alone would hand the second requester the first one's geometry, silently, and the picture would be a mirror image of what was asked for. So the cache key is the name and the settings:

\[ \text{key} \;=\; \text{name} \;\Vert\; \text{settings} \] key = name + import settings

Every real pipeline does this. Unity writes a .meta file beside each asset and re-imports when it changes; Unreal keys its derived-data cache on a hash of the settings. Ours is one bool and a string, and the shape is the same. §4.4 has the subtlety that makes it work — and the bug that found it.

3.4Failure is the ordinary case

An asset system fails constantly, and not because it is badly written. Files are missing during development, misspelled in scene data, absent from a platform pack, corrupted by a partial download, or simply not shipped in a demo build. If a missing asset is an exception — in either sense — then a shipping game is a program in which the exceptional case is Tuesday.

Lesson 5.3 gave us the vocabulary and Lesson 5.4 gave us the mechanism, so 5.5 inherits an answer rather than inventing one:

  • An acquire that fails returns a null handle and a report — the report shape obj_report and image_report already converged on.
  • A null handle does not resolve, so collect_triangles skips that object and counts it (5.4 §4.7). One missing asset costs one object, never a frame.
  • The failure is logged once, at the point that knows why — which is 5.3's rule, and which this lesson broke on its first run and had to fix (§4.3).

Notice what is not in that list: no exception, no assertion, no fallback magenta mesh, no "return a default cube so something draws". A default that stands in for a missing asset is a decision only the game can make, and an engine that makes it has removed the game's ability to notice.
