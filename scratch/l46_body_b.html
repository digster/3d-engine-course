4.1 Two blocks, and an assertion that executes the rule

The engine needs two uniform blocks: a camera for the vertex stage and a lighting environment for the fragment stage. Both live in a new header, and the interesting part is not the structs — it is what sits underneath them.

That is §3.2's rule, executable. Eleven lines, and it exists so that the blocks below can assert their offsets against the rule rather than against numbers somebody worked out once:

This is the same discipline Lesson 4.5 applied to the vertex layout, aimed at a different boundary. There, the defence was sizeof and offsetof instead of literals. Here it is a constexpr function instead of a comment — and the difference matters, because a comment describing a layout cannot fail. Insert a field in the middle of that struct and the build breaks, at the line that is wrong, before anything renders.

Note the shape of the block itself: float3, float, float3, float. That is §3.2's habit, and the reward is visible in the assertions — every offset is exactly the cursor, because nothing ever needed to move.

C++ — why constexpr and not a macro or a comment

packed_offset is evaluated at compile time inside a static_assert, which means it costs nothing at runtime and cannot drift from the code it describes. It is also readable as an explanation: somebody who has never met the packing rule can read those eleven lines and know it exactly, which a comment saying "fields are 16-byte aligned" would not have given them. When a rule is simple enough to write as a function, writing it as a function is nearly always better than writing it as prose — the prose then gets to explain why instead of restating what.

4.2 An instrument for asking the GPU what it got

Everything measured in §3 needed a way to read a uniform back, and there is no such API — the data goes one way. So the shader has to be asked, and the only currency it has is the colour of a pixel.

Pixel (x, y) reports one field, encoded so that a value of n comes back as the byte n: divide by 255 in the shader, and the _UNORM target multiplies by 255 on the way in. Push a block whose fields are 201, 211, 212, 213…, download an 8×8 patch, and you have a complete map of which byte you wrote landed at which field the shader can name.

Two details in the instrument are worth more than they look. First:

Truncate, do not round

SV_Position in a fragment shader is the pixel centre, so the first pixel is at (0.5, 0.5). int(0.5) truncates to 0, which is what we want; rounding would give 1 and the entire probe would be shifted by one pixel — producing a table that looks perfectly plausible and is wrong in every entry. An instrument that can be subtly miscalibrated is worse than no instrument, so this is the line to check first if a probe ever disagrees with something you are confident about.

Second, the probe's vertex stage has no vertex buffer at all:

SV_VertexID is a system value the hardware fills in, so three vertices can be generated from arithmetic and the pipeline needs no vertex layout. That is partly convenience and mostly hygiene: Lesson 4.5 spent an entire lesson on how quietly a vertex layout goes wrong, and an instrument that has one might be measuring it by accident.

The corners (-1,-1), (3,-1), (-1,3) make a triangle twice the size of the target in each direction, so the target sits entirely inside it and the excess is clipped. One triangle rather than two quads' worth means no shared edge — no seam, and no pixel rasterised twice, which on a probe would mean reading a value that was written twice.

4.6 How much is too much to push

Uniform pushes are for small data. It is worth knowing why, with numbers rather than a feeling.

Cost of a uniform push by size
pushedper calleffective ratewhat dominates
108 bytes0.015 µs7.1 GB/sthe call itself
4 KB0.058 µs70.3 GB/sthe copy
16 KB0.259 µs63.4 GB/sthe copy

Read that as a fixed overhead of roughly 14 nanoseconds plus a memcpy at about 65 GB/s — which is exactly what "the bytes are copied into the command buffer" predicts, and a good sign the measurement is measuring the right thing. Our per-frame total is 96 bytes of uniforms, so the cost is two call overheads and nothing else.

There is a ceiling, and it is not documented

Repeating a large push into one command buffer kills the process with no message at all: no SDL error, no validation warning, no log line. Measured in an isolated program — this lesson's harness deliberately does not do it, because Lesson 4.4 settled that a test which destabilises the process is not a test — 16,000 pushes of 4 KB (62 MB) are fine, while 64 KB pushes die somewhere between 24 and 32 of them, and not at the same count twice.

Corrected after Module 8. This paragraph used to call that non-determinism "the signature of a pool being exhausted". The cause is in SDL's source, not in the count, and Exercise 4.6.5 is how it was found. Every backend carves pushes out of 32 KiB uniform blocks (UNIFORM_BUFFER_SIZE in src/gpu/SDL_sysgpu.h at release-3.4.12), and none of them checks length: a push that does not fit takes a fresh block and is copied into it whole, so a 64 KB push writes 32 KB past the end of its block. The crash is that overrun landing on something, which is why the count wanders — non-determinism is the signature of memory corruption. So the ceiling is per push, not per command buffer: any number of 32 KiB pushes is safe, and one byte more never is. On Vulkan the practical limit is lower still, because the descriptor SDL binds covers 4 KiB of each push (MAX_UBO_SECTION_SIZE), so a shader cannot see past that. Keep pushes small and none of this comes up; the point of knowing it is that the symptom is a silent crash, which you would otherwise spend a long time blaming on something else.

So: a camera, a material, a handful of parameters — push them. A hundred object transforms or a bone palette is a storage buffer: SDL_GPU_BUFFERUSAGE_GRAPHICS_STORAGE_READ, declared in HLSL as a StructuredBuffer in space0 or space2, and bound rather than pushed — so the bytes move once instead of once per draw. Module 6 builds one.

7Common Pitfalls & Debugging

The last few fields of a block are garbage; the first ones are fine

Symptom: a uniform block where early fields work and later ones are nonsense, or shifted.
Cause: a vector that straddles a register boundary in your C++ struct but not in the shader's. Everything before the divergence lands correctly, which is why this is confusing.
Fix: pair every float3 with a float. To find it exactly, spirv-dis your.spv | grep MemberDecorate and compare against offsetof for each field.

Nothing is drawn at all after adding a uniform

Symptom: the scene vanishes the moment the camera comes from a matrix.
Cause: the matrix is zero — you pushed before filling it, filled a copy, or declared it and never assigned. Every vertex collapses to the origin, so there is no triangle to draw.
Fix: push an identity matrix deliberately. If the mesh appears in clip space — huge, centred, unprojected — the plumbing is right and the matrix was the problem. That is a two-minute bisection and it is worth doing before anything cleverer.

The scene rotates but the camera never moves

Symptom: orbiting spins the world around a fixed point, and dollying does nothing.
Cause: float4(world, 0.0f) instead of 1.0f. Lesson 2.7: a w of 0 makes it a direction, and the matrix's fourth column — the translation, which is where the camera's position lives — is multiplied by zero.
Fix: the 1.0f. Worth recognising by sight, because the symptom is so specific.

Everything is inside out, or the scene is mirrored

Symptom: geometry visible but wrong in a way that is hard to name.
Cause: view * projection instead of projection * view. With column vectors, A*B applies B first.
Fix: swap them. If unsure which convention a piece of code uses, push an identity and a pure translation and see which one moves the scene.

The shader reads zeros, and the build was fine

Symptom: a uniform block that is entirely zero at runtime.
Cause: the push went to the wrong stage — SDL_PushGPUVertexUniformData where the block is declared in the fragment shader, or the reverse. The two are separate slot namespaces and nothing connects them.
Fix: match the push to the stage that declares the block. Note that this is a different mistake from the wrong space, which the build catches.

"Descriptor set index for graphics uniform buffer must be 1 or 3!"

Symptom: the build fails translating SPIR-V to MSL or DXIL.
Cause: the cbuffer is in the wrong register space. Vertex uniform buffers are space1; fragment ones are space3.
Fix: as the message says. And be glad of it — the JSON reflection is byte-identical either way, so nothing downstream of the build would have noticed.

The process dies with no message

Symptom: a silent crash, no SDL error, no validation output.
Cause: many large uniform pushes into one command buffer. §4.6 measured 64 KB pushes dying between 24 and 32 of them, non-deterministically.
Fix: keep pushes small; put bulk data in a storage buffer. If you are already there, the non-determinism is the tell — a reproducible crash is a bug in your code, an irreproducible one at a resource boundary is exhaustion.

8Exercises

  1. 4.6.1 — Break the block on purpose. Add a float3 to light_uniforms immediately after to_light, without padding. Predict which fields will still arrive correctly before you build, then check with the probe.

    Hint: the static_asserts will fail first, which is the feature working. Comment them out to see the runtime behaviour, and note that your prediction should be "everything up to the inserted field". Put them back afterwards.

    Solution sketch: add the field to the HLSL block too, as a real programmer would, and work both layouts out before building. C++ packs tightly: to_light 0, extra 12, ambient 24, sky 28, diffuse 40, and sizeof is 44. HLSL cannot start a float3 at 12 without straddling the boundary at 16, so it reads extra at 16, ambient at 28, sky at 32 and diffuse at 44. Only to_light survives. The shader's ambient is your sky.x, its sky is your (sky.y, sky.z, diffuse) — the tint's channels rotated by one, with the diffuse weight in blue — and its diffuse is byte 44, one float past the 44 you pushed, so it is whatever that block held before. The repair is §3.2's rule: pair the new float3 with a float and put the pair at the end, which makes the struct 48 bytes and the two layouts identical again.

  2. 4.6.2 — A layout check for uniforms. Lesson 4.5's check_layout compares a vertex layout against the reflection JSON. The reflection does not carry cbuffer member offsets — but the SPIR-V does. Write a tool that reads the OpMemberDecorate … Offset instructions out of a .spv and prints them, then compare by hand against your struct.

    Hint: §D of verify_46 already parses SPIR-V to find descriptor sets — twenty lines, no dependency. Member offsets are the same walk with opcode 72 (OpMemberDecorate) and decoration 35 (Offset). Making it a build step that fails the build is the version worth having.

    Solution sketch: a SPIR-V module is a five-word header (magic 0x07230203, version, generator, id bound, schema) followed by instructions whose first word is (word_count << 16) | opcode. Walk them; for opcode 72 with a third operand of 35, print the struct id, member index and offset; for opcode 6 (OpMemberName) record the same struct id and member index against the name, so the output reads Light.ambient @ 12 rather than %17[1] @ 12. On mesh.frag.spv it should print 0, 12, 16 and 28 — the four offsets the static_asserts already check. The build-step version writes those offsets into a generated header of constexpr values, and the C++ asserts offsetof against the header instead of against hand-typed numbers; a shader edit that moves a field then fails the C++ compile.

  3. 4.6.3 — Per-object transforms. Right now each instance carries an offset, a scale and a two-float rotation, because Lesson 4.5 had no uniforms. Replace it with a full float4x4 per instance and delete the cos/sin pair.

    Hint: a matrix in a vertex buffer is four separate FLOAT4 attributes at four consecutive locations — the vertex layout has no matrix type. That is 64 bytes per instance against 28, so measure the per-frame upload before and after and decide whether you would take that trade for seven instances, and for a thousand.

    Solution sketch: the instance becomes four FLOAT4 columns at locations 3–6, with the tint's four bytes moving to 7 (Lesson 4.3: the TEXCOORD numbers have no gaps): 68 bytes, not 64, against 28. Build the matrix on the C++ side from the same offset, scale and rotation, so the picture must not change — that is the test. In HLSL, float4x4(c0, c1, c2, c3) fills rows, so four columns go in transposed; either transpose it or write mul(float4(p, 1), m), which is the same numbers (§3.4's column-major point, met again from the other side). The upload goes from 196 to 476 bytes a frame for seven instances, and from 28 KB to 68 KB for a thousand — both nothing at 60 Hz. The real cost is elsewhere: the old shader reused the rotation for the normal because the scale was uniform, and a general matrix breaks that, so the normal now needs the inverse-transpose (Lesson 3.6) — three more columns per instance, or a promise that the matrix stays rotation × uniform scale.

  4. 4.6.4 — Two cameras, one frame. Draw the scene twice into two halves of the window from two different viewpoints, with one command buffer and one pipeline.

    Hint: this is what §2.2's measurement was really about — push, draw, push, draw. You will need SDL_SetGPUViewport between them (Lesson 4.5: viewport is pass state). No second pipeline, no second buffer, nothing rebound.

    Solution sketch: one render pass, then for each half: push that camera's clip_from_world, set an SDL_GPUViewport of {x, 0, w/2, h, 0, 1}, draw. The one thing to get right is the projection's aspect ratio, which is now (w/2)/h; with the full-window aspect both views are squashed horizontally by half, and that is the bug to recognise. Order is the only rule — §2.2's "a draw sees the most recent push before it" is doing all the work. If you want a hard guarantee that neither view draws into the other's half, add a matching SDL_SetGPUScissor per view; it costs nothing.

  5. 4.6.5 — Find the push ceiling on your machine. §4.6 reports 64 KB pushes failing between 24 and 32 repetitions on one Metal device. Write the isolated program that measures it on yours, and find out whether the number is stable, whether it scales with push size, and whether the validation layer says anything.

    Hint: keep it in a separate binary that is allowed to crash — that is the whole reason it is not in the harness. Bisect on repetition count for a fixed size, then on size for a fixed count, and plot the boundary. If it is a clean product of the two, you have found a pool size.

    Solution sketch: run each trial as a child process and record whether it exits cleanly, since the failure is a crash. The plot is not a product: every size up to 32 KiB should survive any count (memory permitting), and every size above it fails — sooner or later, at a count that wanders. That is a per-push limit, and the updated §4.6 shows where it lives: UNIFORM_BUFFER_SIZE is 32 KiB in SDL's source, and a longer push is copied whole into a block that size. The validation layer says nothing because SDL_PushGPU*UniformData never looks at length. The lesson's first version of §4.6 called this "a pool being exhausted"; this exercise is how that was found to be wrong.

9Recap & Next

  • Three rates of change, three mechanisms. Per-vertex and per-instance are buffer fetches differing by one enum value; per-frame is not a fetch at all, because there is one value and nothing to index.
  • SDL_GPU has no uniform buffer object. You push bytes onto a command buffer and every draw after them reads them. No lifetime, no binding, no cycling hazard — and the bytes are copied, which is why it is for small data.
  • The packing rule is HLSL's, not std140, despite what SDL's header says — but std140 is a superset, so following SDL's advice is safe. Pair every float3 with a float and the question stops arising.
  • A uniform layout bug corrupts the tail. Everything before the first straddling field arrives correctly. Measured: a trailing float3 arriving as (242, 243, 0) where (241, 242, 243) was written.
  • The matrix crosses untouched — all sixteen elements checked individually, no transpose. Lesson 2.6's column-major choice was right, and the SPIR-V's RowMajor decoration is an artefact rather than a contradiction.
  • A wrong register space is caught by the build, not by the reflection and not at runtime — on the paths that translate. On Vulkan there is nothing to translate and nothing to catch it.

The engine can now draw a real mesh, many times, from a camera that moves. What it cannot do is decide which of two surfaces is in front — you can see that for yourself by orbiting until two tori cross. It also cannot put an image on anything: the uv coordinate has been travelling through the vertex buffer since Lesson 4.5 and its only job so far has been to draw a grid so we could tell it arrived.

Next: 4.7 — Textures, Samplers, and Depth. Both of those, and both are re-encounters rather than introductions: the bilinear filtering you wrote by hand in Lesson 3.9 becomes a sampler object and costs nothing, and the depth test you wrote in Lesson 3.1 becomes three fields of a struct you have already been filling in. The interesting parts are the ones that are genuinely new — the depth format is a choice with precision consequences, and a texture has to get onto the device through the transfer path Lesson 4.2 built for the framebuffer.
