Module 6 — Advanced Rendering · Lesson 6.5

A Material System

Lesson 6.4 changed a surface description and had to edit forty-four call sites across the engine, four demos and six test harnesses. That number is not a complaint — it is a measurement, and what it measures is a type that does not exist. Three places in this codebase have independently grown the same struct-shaped hole, one of them a demo that invented the type because the engine did not offer it. This lesson fills the hole, and the interesting part is not the struct: it is the question that decides what goes in it, which turns out to be a question about hardware rather than about taste. Everything here is a refactor, so there is exactly one claim to make at the end — the reference render must be byte-identical.

1The Problem, Which the Codebase Already Wrote Down

Most lessons in this course open by showing you something broken. This one opens by showing you something the code has been saying for three modules, in comments, without anybody acting on it.

Here is scene_object, as Lesson 3.7 left it, with the comment that has sat on its last field ever since: 

struct scene_object
{
    transform xform;
    mesh_handle geometry;
    const char* name;
    Uint32 tint;
    bool closed;
    microsurface surface;   // <- and on this field:
};

// "Look at what just happened to this struct. `tint` was enough while a surface
//  was one colour; then 3.4 needed `closed`; now 3.7 needs two more numbers, and
//  all four describe the same thing — THE SURFACE — while `xform` and `geometry`
//  describe where it is and what shape it is. That is two different kinds of data
//  wearing one struct, and the second kind has a name: a material."

And here is fill_style, from Lesson 3.8, whose comment says the same thing about itself in different words: "`fill_style` is now two structs wearing one name."

Two structs, written a lesson apart, each of which noticed it was accumulating a second kind of data and each of which declined to fix it. That was the right call at the time, and 3.7 said why: a material invented before three lessons have asked for one is a guess.

Three lessons have now asked. And Lesson 6.4 put a number on it.

What the absence cost, measured

Lesson 6.4 replaced specular::colour and shininess with roughness, metallic and F0 — a change to the surface description and nothing else. It touched forty-four call sites across the engine, four demos and six harnesses.

Not because the change was large. Because the description had no single home, so every place that used a surface had assembled one out of loose fields.

2The Demo That Invented It

The third panel of that figure is the one worth stopping on, because it is a different kind of evidence from the other two.

ecs_swarm is a demo. Since Lesson 5.1 the boundary has been law: demos link the engine and may use only its public headers. And in Lesson 5.7, needing to give its entities an appearance, it wrote this: 

/// What an entity looks like: `scene_object`'s `tint` and `surface`, which have
/// always described the same thing and never been the same thing.
struct material
{
    Uint32 tint = 0xFFFFFFFFu;
    engine::microsurface surface{};
};

Read that comment again. The demo knew. It named the type, gave the reason, and built it anyway, because the engine offered nothing to build on.

A signal worth learning to read

When a consumer restricted to your public API has to invent one of your types, the type is missing. Not "would be nice"; missing. A demo cannot reach into the engine to work around a gap, so what it builds instead is a direct measurement of what the API does not provide.

This is the strongest form of the pressure Lesson 3.7 said to wait for — and it is why the first thing this lesson's diff does is delete that struct's fields.

3The Question That Draws the Line

So we are writing a material. The temptation now is to sweep everything surface-shaped into it — the tint, the roughness, the texture, the cull mode, the blend mode, eventually the shader — because all of those are, in ordinary English, "what the surface is like".

That would produce a type that cannot work, and the reason is not stylistic. Ask a sharper question instead:

The rule

Can this be a number in a buffer?

If yes, it is per-draw data. The fragment stage reads it, the GPU pushes it as a uniform, and two objects that differ only in it can be drawn back to back with no state change between them.

If no, it is pipeline state. It is baked into a pipeline object at creation time, and two objects that differ in it need two pipelines and a sort between them.

@@FIG_SPLIT@@

This is not a rule we are inventing. It is the shape of the hardware, and Lesson 4.8 already paid for the knowledge: porting the scene to SDL_GPU produced three pipeline objects and a sort of the draw list, precisely because cull mode and fill mode cannot be uniforms. The stats that lesson added — pipeline_binds against ideal_pipeline_binds — exist to measure the cost of getting the sort wrong.

So the material gets four fields, and every one of them passes the test:

And cull_mode, surface_style and specular_model stay exactly where they are — in fill_style, in gpu_draw_item, in render_options. A material that swallowed them would be a material that cannot be a uniform, which is not a material at all.

verify_65 §A asserts the rule rather than describing it, in the bluntest way the language allows: 

checkf(std::is_trivially_copyable_v<engine::material>,
       "a material is TRIVIALLY COPYABLE (%zu bytes) — which is the machine's "
       "way of saying it can be pushed as a uniform");

If a field ever arrives that breaks that, it belongs on the other side of the line, and the assertion is where you find out.
