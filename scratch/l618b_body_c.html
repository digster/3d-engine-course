9Counting on a GPU

9.1 — The number nobody on the CPU knows

The draw of §8 needs one number: how many instances. That is the count of living particles, and it exists nowhere. The ring decides births and the particles' own clocks decide deaths, both on the GPU, so after a step the CPU has no idea how many are alive. It could draw every slot — 65,536 instances, the dead ones collapsed to nothing in the vertex shader — and pay for about 20,000 wasted billboards a frame. It could read the pool back and count, which is a download of the 3 MB this lesson exists to stop moving, followed by a stall: the CPU waits for the GPU to finish, and the GPU then waits for the CPU to issue the next frame. Or it could read back only the count, a frame late, and draw last frame's number of particles against this frame's list.

None of those is necessary, because SDL_GPU, like every modern API, can take a draw's arguments from a buffer. SDL_DrawGPUPrimitivesIndirect(pass, buffer, offset, count) reads an SDL_GPUIndirectDrawCommand — four Uint32s: vertices, instances, first vertex, first instance — from the buffer when the GPU reaches the draw. If a compute pass earlier in the same frame wrote the instance count into that buffer, the draw uses it, and the number was produced, consumed and forgotten on the GPU. The CPU issues a draw whose size it never learns.

That leaves the problem of producing the count, and a list of the living slots for the vertex shader to index — §2's broken loop.

9.2 — The lost update

Here is that loop's increment written as a kernel, as literally as possible, in the probe: 

words[0] = words[0] + 1u;   // every thread, once

Run it with 1,048,576 threads and read words[0] back. Fifteen trials across five runs of the harness counted between 296 and 509. Over 99.9% of the increments vanished, and the survivors are a different number each time.

The line is three operations — read the value, add one, write the result — and nothing stops another thread from reading between the first and the third. Two threads that both read 7 both write 8: two increments, one counted (Figure 10). On a GPU it is worse than on a multicore CPU, because of 4.1's lock-step: the 32 lanes of a SIMD group execute the read together, see the same value, and write the same result, so a whole group contributes one increment at best, and many groups are in flight at once doing the same. The number that survives says how the hardware happened to schedule the groups, which is why it changes from run to run and why it is not a number to reason with.

The fix is an instruction that performs all three steps as one indivisible operation on the memory itself — an atomic: 

uint before;
InterlockedAdd(words[0], 1u, before);   // before = the value this thread replaced

With it the count is 1,048,576, every time (§H). And before is the part that turns a count into a list: each thread receives the value it replaced, which is a number no other thread received. It is this thread's place.

@@FIG_RACE@@

Atomics are not free. Every thread in the grid that performs one on the same address is serialised on that address, so a million threads adding to one counter wait on each other a million times. For this lesson's two-thirds-alive pool that is about 45,000 atomics a frame, which the measured compaction absorbs (§L's GPU step includes it). A production system at a million particles reduces it: a SIMD group counts its own survivors with a wave intrinsic and one lane performs a single atomic for the group — thirty-two times fewer. §14 names it and Exercise 5 points at it.

9.3 — The compaction

So the count and the list come from one kernel, one thread per slot: 

StructuredBuffer<Particle>  particles : register(t0, space0);   // read-only
RWStructuredBuffer<uint>    args      : register(u0, space1);   // the draw's arguments
RWStructuredBuffer<uint>    alive     : register(u1, space1);   // the list

[numthreads(64, 1, 1)]
void main(uint3 id : SV_DispatchThreadID)
{
    const uint slot = id.x;
    if (slot >= capacity) { return; }
    const Particle p = particles[slot];
    if (!(p.age < p.life)) { return; }
    uint place;
    InterlockedAdd(args[1], 1u, place);   // args[1] is num_instances
    alive[place] = slot;
}

Three things about it. The pool is bound read-only — the compaction only looks — so it goes in the t registers and is bound with SDL_BindGPUComputeStorageBuffers, and the buffer needs the COMPUTE_STORAGE_READ usage bit. The counter is the draw's instance count: the atomic adds straight into word 1 of the SDL_GPUIndirectDrawCommand, so there is no second pass to copy it. And the list's length is whatever the count is; nothing past it is ever read, so the rest of the list is garbage and nobody cares.

Measured against the CPU after §G's ten seconds: the arguments come back as {6, 44,915, 0, 0}, and 44,915 is exactly the CPU pool's live count; sorted, the list is exactly the CPU's living slots, each once (§H).

9.4 — Somebody has to set the counter to zero

The compaction adds to args[1], so something must set it to zero first — and it cannot be the compaction. Which of its sixty-five thousand threads would do it, and how would the others know it had happened before they started adding? The order in which threads run is not yours to decide. So the reset is its own one-thread kernel, particles_clear.comp, which writes all four words — six vertices, zero instances, and the two zeros SDL_gpu.h insists on: its note on the indirect command says the built-in vertex and instance IDs are only portable when the "first" arguments are zero, and the vertex shader uses both IDs.

And it runs in its own compute pass, which is §10's subject. The buffer holding the arguments needs three usage bits: INDIRECT to be read by the draw, and both COMPUTE_STORAGE_READ and _WRITE, because an atomic reads and writes — SDL's documentation of the buffer usage flags is explicit that, unlike textures, a buffer created with both may be read and written in the same shader.

9.5 — The order, and the last bits of the picture

The list's order is whatever order the hardware served the atomics in. §H compacts one unchanged pool twice: between 44,814 and all 44,915 places held a different slot the second time, across four runs — yet about 98% of neighbouring entries are in ascending order, which is what you would see if each SIMD group's lanes took consecutive places in lane order and only the groups arrived in a different order each time. The draw does not care: the blend is addition, and addition commutes.

Except in the last bits, which is worth measuring rather than asserting, because 6.13's header for blend_add asserted the opposite. §K draws one pool three times, each after its own compaction, into the 16-bit float HDR target: about 7,000 to 9,000 of 172,800 channels differ between two draws, by at most 8 to 11 units in the last place of a half-float, while the total light agrees to one part in ten thousand (Figure 11's histogram). Floating-point addition is commutative — a + b is always exactly b + a — and it is not associative: the blender rounds after every add, so which partial sums are formed decides which roundings happen. Nothing a viewer can see moves. A golden-image test does, which is why the harness's comparisons of the picture are tolerances and its comparisons of the pool are exact. 10What SDL synchronises, and cycle

10.1 — Between passes: everything. Within a compute pass: nothing.

The particle frame is a chain of dependencies: each step reads the step before; the compaction reads the last step and the clear; the draw reads the compaction. On the GPU each arrow is a hazard — the reading work must not start until the writing work's results are visible — and in Vulkan and Direct3D 12 somebody must insert a barrier to say so. SDL_GPU inserts them for you, and the rule for where is short: at pass boundaries. It tracks which resources each pass uses and how, and when a pass ends it transitions them so the next pass can use them. Reading the backends at 3.4.12 confirms the shape: VULKAN_EndComputePass walks the pass's read-write buffers and textures and transitions each back to its default usage, while VULKAN_DispatchCompute records the dispatch and nothing else; D3D12_DispatchCompute likewise binds and dispatches with no barrier between dispatches.

SDL_gpu.h states the consequence in capitals under SDL_BeginGPUComputePass: reads and writes in a compute pass are not implicitly synchronised, and work that depends on a previous dispatch's output "MUST end the current compute pass and begin a new one". Hence the particle frame's shape: one compute pass per step, a pass for the clear, a pass for the compaction. Putting the clear and the compaction in one pass would race — the compaction's atomics against the clear's store of zero, in no defined order.

And on this course's machine it would work. §H does exactly the forbidden thing — clear and compact dispatched in one pass — twenty times, and gets the exact count 20 times out of 20. SDL's Metal backend opens a compute pass with computeCommandEncoder, an encoder with Metal's default settings, and on this machine that orders the two dispatches; Apple's MTLDispatchType documentation is where the serial and concurrent kinds are described. So the missing boundary is covered by behaviour SDL never promised. The harness cannot show the race on a Mac and says so; the claim that it exists elsewhere rests on SDL's contract and on the Vulkan and D3D12 source, not on an observation. This is the most dangerous kind of working there is — code that is correct on the machine it was written on and wrong on the other two backends — and it is why the frame graph of §11 derives the pass boundaries rather than trusting anybody to remember them.

10.2 — cycle, and what "undefined" costs

Lesson 4.5 met cycling as the thing that makes a per-frame upload safe. An SDL_GPU buffer is really a small ring of internal buffers; a write with cycle = true to a buffer that is still bound — referenced by work the GPU may not have finished — rotates to an unbound internal buffer instead of waiting, so this frame's write cannot land on a read last frame has not done yet. The price is in SDL_gpu.h's section on cycling: after a cycle, the resource's data is "considered to be undefined" until it is written again.

For every buffer the engine had before this lesson, that price was zero: a stream buffer is overwritten whole every frame, so its old contents were dead anyway. The particle pool is the first buffer whose contents outlive a frame — each step reads what the last one wrote — and every read-write binding at SDL_BeginGPUComputePass carries a cycle flag. §I sets it to true on the pool and runs 120 steps, one command buffer each:

  • cycle = false, submitted back to back: 38,284 alive, exactly the CPU pool.
  • cycle = true, back to back: 667 or 668.
  • cycle = true with a fence wait after every step: 334 — exactly one step's births.
  • cycle = true with SDL_WaitForGPUIdle after every step: 38,284, correct.

The third line refused a prediction. This section was drafted around the idea that cycling needs a busy GPU — that a fence wait, which proves the previous step finished, would leave nothing bound and nothing to cycle. It does not. Reading SDL's Metal backend explains why in one step: a buffer counts as bound while its reference count is non-zero, a command buffer takes a reference the first time it uses the buffer, and the reference is dropped only when SDL cleans up that command buffer — which METAL_Submit does for completed buffers during a later submit, and SDL_WaitForGPUIdle does for all of them. METAL_WaitForFences waits and cleans nothing. So at the next step's SDL_BeginGPUComputePass the pool is still referenced, and it cycles.

§I then asks which buffer each cycled step lands on, with a fresh pool and a readback after every step (Figure 12). Submitted back to back, steps 1 to 3 each start from an empty buffer, and then step 4 carries on from step 1's buffer — its survivors are serials 0–332 and its own 1,000–1,332 — step 5 from step 2's and step 6 from step 3's: the pool has become three pools, each advancing every third step. With a fence wait, every step starts from a buffer holding no live particle at all. Which buffer SDL picks is the backend's business and its timing's, which is precisely what "undefined" means; the harness asserts only that the pool is not the CPU's, and prints the pattern.

@@FIG_CYCLE@@

The consequence for a real frame is stronger than the harness makes it look. In the demo, the steps of one frame share one command buffer, so the second step's pass begins while the first step's pass in the same command buffer already holds a reference: cycle = true would cycle within the frame, not merely between frames. There is no frame rate, no machine and no amount of waiting short of idling the device after every pass at which the flag is right for the pool. It is wrong always — and it is right for the argument buffer's clear and for the list, which are overwritten whole. Which is to say: cycle is a buffer's load op. cycle = true is DONT_CARE; cycle = false is LOAD. The frame graph already derives a load op from whether a pass reads what it writes, and §11 teaches it to derive this one the same way.

11The frame graph learns buffers

11.1 — "The same machinery with a different descriptor"

Lesson 6.17's header listed what its graph deliberately did not do, and one line was "NO BUFFERS, ONLY TEXTURES. Every cross-pass resource in this engine is a texture. Buffers would be the same machinery with a different descriptor." The particle system is the first cross-pass buffer, so that sentence can now be checked. It turned out nine-tenths true.

What carried over unchanged is the idea the graph is built on: a resource is a sequence of versions, each produced by exactly one pass. The pool at the start of the frame is state@0; step 0 produces state@1 from it; the compaction reads state@3. Ordering (Kahn's algorithm over producer-to-consumer edges), validation (a read of a version nobody produced, two producers of one version, a cycle) and culling (a pass survives if it feeds an imported write) are all functions of versions, and none of them cared that the resource was a buffer. The buffers are imported — the pool outlives the frame, so the graph must not pool it — and an import's version 0 is its real contents, which is exactly "what the last frame left".

What did not carry over is the one-tenth, and both halves of it are the two facts of §4 and §10:

  • A compute pass is begun with its writable buffers. The graph already begins render passes for their callers, with the attachments they declared; a compute pass must be begun with the read-write buffers it declares, as an array in shader-slot order. So a buffer write declares its slot, and execute builds the array from the declarations exactly as it builds a render pass's colour targets. compile refuses slots with a gap or a repeat, because the array index is the u register and nothing else checks that the two agree.
  • A buffer's load op is cycle. The graph's three words for a texture write — discard_write, clear, keep — already say whether a pass depends on what was there. For a buffer there are two: write_buffer (overwrites, so cycle = true) and keep_buffer (reads what is there, so cycle = false, and the pass is ordered after the version's producer).

Plus the two things SDL_GPU forbids, which the graph now refuses at compile time rather than letting the driver refuse them halfway through a frame: a render pass that writes a buffer (graphics stages cannot write storage) and a compute pass with an attachment.

11.2 — The particle frame, declared

The demo's frame, minus the lines that fill in the callbacks' contexts:

11.3 — A cost the additivity check caught

The first version of these changes answered "is this a read?" and "is this imported?" with small helper functions, called in the graph's two innermost loops — producer_of and the two-producer check, both quadratic in passes and in accesses. The harnesses link the engine as the default build compiles it, with no optimisation, where an inline helper is a real call; and 6.17's own harness, rerun unchanged for §13's additivity check, reported its steady-state compile at 13.5 µs where it had been 8.1. The fix stores a one-byte writes flag on each access when it is declared — a load, as cheap as the single comparison it replaced — and repacks the three new fields into four bytes of the record. Rerun: 7.7 to 8.7 µs. Nothing about the answer had changed; a frame graph rebuilt every frame is exactly the code where "nothing changed but it is 60% slower" matters.

11.4 — Where the graph stops

The demo is the first program in the course whose frame is declared rather than recorded — and it declares only part of it. The steps, the clear, the compaction, the scene and the sparks go through the graph; 6.13's bloom and the display pass (the tonemap and 6.18's overlay) are recorded after execute, by hand, exactly as the sandbox records them. The line is where it is because those two already have owners: gpu_post_stack::render_bloom begins its own eleven passes, and the display pass belongs to the swapchain. Declaring them would mean rewriting the post stack's interface, which 6.17's harness did for itself in about sixty lines and which belongs to whoever next changes the post stack — not to a lesson about particles. The HDR target is imported, so the graph stores it for the bloom to read; the depth buffer is the graph's own, and the sparks' pass is the last to touch it, so the graph derives DONT_CARE for it.

12Implementation

12.1 — The specification: particles.hpp

Start on the CPU, with no SDL_GPU anywhere: the record, the hash, the clock, the step. Every function has a twin in particles_step.comp.hlsl, and the two are written in the same order of operations, because a floating-point expression is not a mathematical one — a compiler may not rearrange what the source did not arrange, and keeping the texts parallel is what makes the harness's comparison mean "the GPU did what the CPU did" rather than "two similar programs gave similar numbers".

The uniform block is the file's central idea. step_uniforms is nine 16-byte rows, built once per step by make_step_uniforms, and read unchanged by both the CPU's step_slot and the kernel: 

struct step_uniforms
{
    vec3 origin{};    float h = 0.0f;                    // row 0
    vec3 axis{};      float one_minus_cos_cone = 0.0f;   // row 1  (§5.5)
    vec3 tangent{};   float speed_min = 0.0f;            // row 2  (the cone's frame, computed once)
    vec3 bitangent{}; float speed_span = 0.0f;           // row 3
    vec3 gravity{};   float inv_drag_h = 1.0f;           // row 4  (1 / (1 + k h), §7.2)
    float life_min, life_span, ground, restitution;      // row 5
    float keep, drag, carry, inv_rate;                   // row 6  (1 − friction; §6.4's clock)
    Uint32 first, count, mask, seed;                     // row 7  (the emission window)
    Uint32 capacity, pad0, pad1, pad2;                   // row 8
};

Every number in it that is the same for every particle — the cone's cap height and frame, the drag factor, the friction complement — is computed here, once, in C++. So the CPU reference does not compute its own 1/(1 + kh): it reads the same float the GPU reads, and a disagreement between the processors can only come from arithmetic that follows. That is also why it is 144 bytes rather than the 80 of the emitter's own fields — and 144 bytes a step is still the CPU's entire contribution.

step_slot is one thread's work, and the CPU pool is a loop over it: 

void step_slot(particle& p, Uint32 slot, const step_uniforms& u)
{
    const Uint32 d = (slot - u.first) & u.mask;         // distance round the ring (§6.2)
    if (d < u.count)
    {
        p = spawn_particle(u.first + d, birth_age(d, u.carry, u.inv_rate, u.h), u);
        return;
    }
    if (!is_alive(p)) { return; }                       // dead stays dead, byte for byte
    p.previous = p.position;                            // §7.5
    integrate_particle(p, u, u.h, u.inv_drag_h);        // §7.1–7.3
    p.age = p.age + u.h;
}

Dead particles are left exactly as they died, not zeroed — which the harness relies on when it compares whole buffers, and which saves the kernel a store for the one slot in three that is dead.

12.2 — The kernel

particles_step.comp.hlsl is that function transliterated: the same struct of three rows, the same cbuffer of nine at b0, space2, pcg_hash and unit_float character for character, and a main that is step_slot with the tail check in front. The pool is RWStructuredBuffer<Particle> at u0, space1. Read the two files side by side; the listing is in §15.

12.3 — Loading a compute pipeline

gpu_compute_pipeline::load follows gpu_shader::load step for step: choose the format this device accepts (MSL here, entry point main0), read the code, read the reflection with the new parse_compute_reflection, refuse to guess if it is not a compute reflection, then fill SDL_GPUComputePipelineCreateInfo — six counts and three thread dimensions, all read from the file — and name the pipeline at creation through SDL_PROP_GPU_COMPUTEPIPELINE_CREATE_NAME_STRING, as 4.9 taught every resource to be named. groups_for_items(n) sizes a dispatch from the pipeline's own threadcount_x, so a kernel whose group size changes cannot be dispatched with the old one.

12.4 — gpu_particles: three buffers and four recordings

create makes the pool, the list and the arguments with the usage bits §8.2 and §9.4 argued for, loads the three kernels by name, builds the draw pipeline — no vertex input, additive, depth-tested without writes — and then zeroes the pool with one upload, because SDL_gpu.h promises nothing about a new buffer's contents, and "whatever the allocator last held" is a pool of particles with random ages, some alive, drawn on the first frame at random positions. A zeroed record is a dead particle (§4.1), so the pool starts empty by construction.

Then four recording functions, one per kind of pass, and none of them begins a pass — the shape 6.18's overlay settled on, made non-negotiable here by §4.4: whoever begins a compute pass must know which buffers it writes, so each function's comment says exactly which buffer goes in which slot and whether it may cycle: 

void record_step   (cb, compute_pass, const step_uniforms&);   // slot 0: state, cycle = false
void record_clear  (compute_pass);                              // slot 0: args,  cycle may be true
void record_compact(cb, compute_pass, SDL_GPUBuffer* state);    // slots: args (false), alive (true)
void record_draw   (cb, render_pass, const particle_draw_uniforms&, SDL_GPUBuffer* state);

and simulate / count_living, which begin those passes themselves, for a program with no frame graph and for the harness's hand-recorded control. The draw is one call, SDL_DrawGPUPrimitivesIndirect(pass, args, 0, 1), after binding the pool and the list to the vertex stage and pushing the camera.

12.5 — The frame graph

frame_graph.hpp gains fg_buffer — fg_texture's twin, a different type so a buffer cannot be passed where a texture was meant — and import_buffer, add_compute_pass, read_buffer, write_buffer and keep_buffer. A buffer is a resource slot like any other, with its SDL_GPUBuffer* where a texture keeps its pointer; two new uses, buffer_read and buffer_write, join sample, colour and depth. In compile, the store-op loop derives cycle = (init == discard) for a buffer write and continues, and a new validation block enforces §11.1's rules. In execute, a compute pass gathers its declared writes into an SDL_GPUStorageBufferReadWriteBinding array indexed by slot, begins the pass, and hands the callback ctx.compute. Every texture-only graph takes exactly the path it took before, which §13 checks.

12.6 — The demo, and the fixed step on the GPU

demos/particles is an engine::app on surface::gpu. The one piece of it worth reading closely is how a fixed step reaches the GPU: 

void on_fixed_step(float h) override
{
    // (abridged: the listing adds the pause, the --shot guard and the step timer)
    if (cpu_mode_) { (void)cpu_pool_.step(emitter_, h); return; }   // the "before"

    // No command buffer exists yet, so the step is RECORDED, not run.
    const emission_window w = clock_.advance(emitter_.rate, h, particles_.capacity());

}

and on_frame declares one compute pass per recorded step (at most eight — Lesson 1.4's spiral-of-death cap), then the rest of the frame, with alpha in the draw's uniforms. Both paths advance the same emission clock at the same steps, so they emit the same particles at the same times; the CPU path adds one line before the graph, upload_cpu_state, and hands the graph the uploaded buffer instead of the GPU's pool. [C] switches live, and the HUD reports what the CPU path costs.

13The instruments: two processors held to one specification

13.1 — What must be exact, and what cannot be

§G runs the CPU pool and the GPU pool from the same empty state through the same 600 uniform blocks — ten simulated seconds — and compares them particle by particle at seven checkpoints. Before looking, it is worth deciding what "agree" can mean, because the answer is different for different parts of the record.

  • Integers must agree exactly. Serials, the hash, the emission window, the ring: integer arithmetic has one right answer. After ten seconds every serial is in the same slot on both processors, and 1,048,576 hashes match bit for bit.
  • Floats cannot, in general. The kernel calls sin, cos and sqrt, which the GPU approximates; its compiler may fuse a multiply and an add that C++ rounds twice. After one step, the 333 new particles' lives are identical — a multiply-add of exact values — but only 93 of their 333 velocities are bit-identical, the worst 4 units in the last place.
  • So floats are held to a tolerance, and the tolerance is stated. After ten seconds, 44,889 of 44,915 live particles are within a micrometre of their twin and the worst is 1.38 µm; the worst at any checkpoint was 1.67 µm. Only 5,264 — 12% — are bit-identical.
  • Which particles are alive must agree exactly anyway, because the count drives a draw. It does: zero disagreements at every checkpoint, and the GPU's count equals the CPU's, 44,915.
@@FIG_AGREE@@

That last line refused a prediction too, and the refusal is instructive. The expectation was that the floor would be where the two processors part: a particle a few ULPs above the plane on one and a few below on the other bounces a step earlier on one of them, and from then on they are centimetres apart. Over ten seconds, 44,915 living particles and several bounces each, it never happened — no live particle is even a millimetre from its twin. The floor turns out to be a contraction: a bounce sets the height to exactly ground on both processors, so whatever vertical error had accumulated is discarded at every impact. Divergence would need a particle to end a step within a few ULPs of the plane, which is a one-in-millions coincidence per impact.

13.2 — Which CPU is the reference?

There is a harder question underneath §13.1: the CPU reference is compiled too. The harness links the engine library, and the default build compiles it with no optimisation while a Release build optimises it — and the optimiser may fuse a multiply and an add in the reference exactly as the GPU's compiler may. §G dumps the CPU pool's bytes after ten seconds from each build and compares them: 897 of 44,915 live particles differ between the debug and Release builds of the same C++, the worst by 0.60 µm, with no disagreement about which are alive. So a bit-exact float reference does not exist even on one processor unless the compiler is forbidden to contract, and the honest contract for float state is a tolerance: exact integers, exact alive/dead decisions, positions within a stated number of micrometres.

13.3 — The budget

§L times both paths against a Release library — which the harness's build script insists on naming, because a harness's own -O2 never reaches the library it links, and the default library's CPU step is six times slower (21 ns a slot against 3.5). The CPU step costs 3.3 to 3.6 ns a slot, flat from 16,384 to a million — the loop streams through memory in order, which is the access pattern a CPU is best at. The upload costs about 0.14 ms per megabyte plus about 0.14 ms of submission; it overtakes the step at every size and reaches 6.87 ms at a million. The GPU step, sixty steps in one command buffer so the launch cost is shared, costs 0.31 to 0.79 ns a slot including that launch — the smallest pool pays most per slot because 16,384 particles do not fill the GPU (Figure 15).

14The ninety-percent picture

This is a complete GPU particle system of the simplest useful kind. Here is the rest of the field, and what each part would cost this engine.

  • Sorting. Additive sparks need no sort. Smoke, dust and anything drawn with 6.11's over operator do — back to front, per frame, on the GPU, which means a parallel sort (bitonic, or a radix sort) of tens of thousands of keys: another set of compute passes, each depending on the last. Or order-independent transparency, which avoids the sort at the price of memory per pixel.
  • A dead list instead of a ring. Gareth Thomas's GDC 2014 talk describes the design most production systems use: a stack of free slots that births pop and deaths push, so no living particle is ever overwritten and an emitter can burst. It costs two atomics per particle per frame and a CPU reference that can only check counts, not slots (Exercise 5).
  • Wave intrinsics. §9.2's atomics can be cut thirty-two-fold by counting a SIMD group's survivors with WaveActiveCountBits and one atomic per group. That needs Shader Model 6 wave operations through every hop of this toolchain — HLSL, SPIR-V subgroups, MSL SIMD-group functions — and is left as research: ⚠ VERIFY that glslc and SPIRV-Cross carry them before depending on it.
  • Colliding with the world. The only thing a particle knows about is one plane. Colliding with the scene's depth buffer — sampling it in the step kernel and bouncing off whatever the camera can see — is cheap and convincing and wrong off-screen (Exercise 4). A signed distance field of the level is right everywhere and costs a 3D texture.
  • Lighting, and sparks as lights. The sparks emit and are not lit, which suits sparks. Smoke must be lit — 6.17b's lamps through a volume — and a shower of sparks would, in a real scene, light the floor under it: the brightest few thousand as 6.17b's point lights, which is what clustered shading (6.17b §12) exists for.
  • Soft particles. A billboard crossing the floor is cut by a hard line where it meets the depth buffer. Fading each fragment by its distance to the depth behind it removes the line, and needs the depth buffer as a sampled texture in the draw — a declaration the frame graph already knows how to make.
  • Async compute. On hardware with a separate compute queue the particle steps could overlap the previous frame's post-processing. SDL_GPU exposes one queue, and 6.17's graph says so in its own header.
  • Indirect dispatch. The step runs over every slot, dead or alive. A system that steps only the living would dispatch ceil(count / 64) groups — a number only the GPU knows — through SDL_DispatchGPUComputeIndirect, the dispatch twin of §9's indirect draw.
