4Refactoring With a Net

Everything above is about what to build. This section is about how to get there without breaking anything, and it is the part most refactoring advice skips.

4.1   The characterization test

A refactor makes exactly one claim: the observable behaviour is unchanged. That is a falsifiable claim, which means it is only worth anything if something can falsify it. If the only check is "I looked at the window and it seemed fine", the claim is not a claim. It is a hope with a commit message.

So the first act of this lesson — before a single file moves — is to build the thing that could prove it wrong. A characterization test: not a test of what the code should do, but a record of what it does, pinned so precisely that any change shows up as a difference.

Ours is a flag on the demo. --shot PATH renders a fixed set of frames from fixed inputs and writes them to one binary PPM, then exits. Everything that could vary — the time, the camera, the light's angle, every mode — is a constant inside the function, so the only remaining thing that can change the output is the code:

Seven frames, one per scene the demo can build, each driven through every stage that was about to cross the boundary: build_scene → collect_triangles → cull/sort → draw_triangles, with draw_world's grid overlay on top so the line and clip paths are covered too. Run it on the pre-refactor binary and you get a golden file: 1,209,600 bytes, hash 905BF27E.

The seventh frame exists because the first six were not enough, and the way we found out is the reusable part. The first version had six frames, and all six reported straddle = 0 in the log — meaning no triangle in any of them crossed the near plane, meaning Lesson 3.3's clipper was never called. Several hundred lines of code about to be moved, with no coverage at all.

A characterization test that does not reach a branch cannot pin it. Frame 6 puts the camera at ankle height on the ground plane: 32 triangles in, 8 straddling, 36 out. Read your instrument's own counters and ask them what you missed.

4.2   Move without changing; change without moving

There are two different jobs in this lesson. One is relocation: 2,425 lines leave main.cpp for six new files in two new directories. The other is redesign: fifteen parameters become eight. Both are risky, and they are risky in completely different ways — relocation breaks on a missing include or a namespace slip, redesign breaks on a mis-ordered argument.

Doing them in one edit means that when the picture changes you have two suspects and no way to separate them. So: move first, verify, then redesign, verify again. Two passes, two checks, and each check answers a question the other cannot.

The two verifications

That third row is the one this lesson was for. verify_50 shares no source file with the demo, includes only public headers, links engine and demo_common, and produces the sandbox's picture down to the byte: 1,209,616 bytes compared, 0 differ. Four harnesses transcribed the scene; the fifth links it.

The alias is not cosmetic. A name with a double colon in it cannot be mistaken for a file: ask to link engine::engine and, if no such target exists, CMake stops at configure time with target not found. Ask to link plain engine with no such target and CMake cheerfully passes -lengine to the linker, and you find out much later, in a different language, from a different tool. Every library worth using exports a namespaced alias; SDL3::SDL3 is one; now so are we.

demos/common/ deserves a word, because it looks suspiciously like a second engine. It is a static library so that several programs — the sandbox, and any harness — can share the content instead of copying it, which is the whole grievance this lesson opened with. What keeps it honest is one rule: nothing in demos/common/ may be needed by a shipped game. The moment something is, it is not demo content; it is an engine feature nobody has named yet.

5.3   Four new headers, and why each exists

scene.hpp is the one with the most interesting argument behind it. Lesson 4.8 rendered the same scene two ways, CPU and GPU, in a split view — and "the same scene" was two code paths kept in step by hand. Making scene_object the engine's type, that both renderers consume, is what turns that promise into a structure. verify_50 checks the sharp end of it: given one scene_object, the model matrix the CPU pipeline builds and the one the GPU draw item carries are bit-identical. If they ever diverged you would see one object in two places and neither renderer would look wrong on its own.

debug_draw.hpp is a grouping by purpose rather than by shape. A wireframe, an axis triad, a depth-buffer visualisation and a pixel-difference count have nothing in common as code; they have everything in common as intent. All of them exist so a human can see inside the renderer, all of them ship disabled, and all of them are budgeted separately (Lesson 3.10's zone::overlay). Debug code is a component, not a leftover — and Lesson 5.10 turns this header into a real debug-draw system with a command queue behind it.

5.4   A name collision the split created

The demo content went into namespace demo. The sandbox already had this:

An enum in an anonymous namespace hides a namespace of the same name, so demo::build_scene would not compile — the compiler would look inside the enum and find no such enumerator. The fix is to rename the vaguer of the two names, which is the enum; it is screen now. Twenty call sites, five minutes, no behaviour change.

It is a trivial problem and it is in this lesson for one reason: names only collide once they can see each other. Everything in that file had been living in a private namespace where no name it chose could ever conflict with anything, and the day it acquired neighbours, it acquired the possibility of a clash. The same is true of every symbol the engine now exports. That is what a namespace is for, and it is why the engine's is called engine and not something shorter.

5.5   The redesign, with the net still attached

Three small types, and then the signature falls out:

std::span is the C++20 answer to the (pointer, count) pair, and it is worth a sentence in its own right. A span is a non-owning view — a pointer and a length, no allocation, no ownership — so it costs exactly what the two parameters cost and cannot be passed inconsistently. It also accepts an array, a std::vector, or {&one_object, 1} without the caller thinking about it, which turned out to matter: two of our eight call sites draw a single object.

At the call site, the payoff is the comparison renders. The sandbox draws the scene, then draws it again with one setting changed and counts the pixels that differ — that is how Lessons 3.4, 3.6 and 3.7 make their claims. Before, each of those was a fifteen-argument call that had to match the real one in fourteen places and differ in one. Now:

The reference render can no longer differ from the real one in a field somebody forgot. That is not a tidier call; it is a class of bug that has stopped being possible.

Then run the golden. Byte-identical, second time.

5.6   hello_cube — the acceptance test

A library you can only use from inside is not a library. So the second executable exists purely to ask the question from the outside: 160 lines of code, every symbol from <engine/…>, a lit cube spinning.

Notice what is absent. No triangle, no edge function, no barycentric weight, no perspective divide, no clip plane. Every one of those is something we built by hand and can explain in detail, and none of them appears here, because that is what the engine is for. The sandbox demo — whose entire job is to show you the insides — is a terrible advertisement for the API. This file is the honest one.

It also takes --shot PATH: one frame, no window, straight to a PPM. Eight lines, and the same argument Lesson 4.9 made for --trace — a program that can only be checked by a human looking at a window cannot be checked by a build server. It reports 12 triangles, 2,760 pixels painted, which is how this lesson knows the picture below is the picture you will get.

7What Is Still on the Wrong Side

A refactor lesson that ends "and now it is clean" is lying to you. Four things are still on the wrong side of the line, we knew about all four while writing it, and each is left for a specific reason.

@@FIG_RESIDUE@@

The first is a genuine design defect and it is worth understanding. cull_choice appears in render_options, and collect_triangles reads exactly one of its four values — back_by_forward, Lesson 3.4's deliberately wrong facing test, which has to be applied before the perspective divide. The other three are applied by draw_triangles through fill_style::cull. So the cull mode is specified in two places and a caller who sets only one gets a picture that is right by accident.

verify_50 pins this rather than papering over it, and the check reads oddly on purpose:

A test that asserts current behaviour is the current behaviour, even when the current behaviour is wrong, is not a mistake. It is how you stop a known defect from quietly becoming two defects, and it is a note to whoever fixes it that the fix will need to change this line. The real repair is a material system, where cull mode is pipeline state because pipeline state is what a material is — and that is Lesson 6.5.

The third row is the uncomfortable one. render_options ships trs_order::tsr and correct_normal_matrix = false: switches that exist so a lesson can show a bug on a keypress. No shipping engine would export them, and we export them because this engine's job includes being read. It is a real cost of the course's own design, it is stated rather than hidden, and Exercise 5.1.4 is the way out for anybody who wants it.

9Build & Run

The paths changed, and so did the executable's name. Through Lesson 4.9 the program was build/engine. That name now belongs to the library — to the thing it links — which was exactly the confusion the old name was papering over. It is build/demos/sandbox from here on.

Expected result. Three things, in order:

One. The build produces four targets where there was one: libengine.a (1,201 KB), libdemo_common.a, sandbox and hello_cube. Nothing about the first two is runnable, and that is the point.

Two. ./build/demos/sandbox --software looks exactly as it did at the end of Lesson 4.9. Every key still does what it did, every HUD number still reads what it read, the frame budget still shows the same zones. If anything at all is different, something is wrong — that is the whole claim of the lesson.

Three. ./build/demos/hello_cube opens a window with an amber cube turning about its y axis, its three visible faces at three distinct brightnesses because a directional light is falling on them from up and to the left. It is 160 lines and it never mentions a triangle.

Section C found two of its own probes to be worthless, and both are instructive. correct_normal_matrix = false reported 0 px on the stock scene, because Lesson 4.8's theorem still holds: a box's model-space normals are its axes, a diagonal scale sends an axis to a multiple of itself, and normalize() throws the length away — so the bug is invisible on crates by construction. The probe needed a squashed icosahedron, which is not a box and is non-uniformly scaled; then it reports 454 px.

And normals = face reported 0 px because the stock scene's meshes carry no vertex normals at all, so both settings fall back to the face normal — fell_back = 132 says so, which is why that counter exists. The probe was wrong twice, not the code. A measurement taken on content that cannot express the effect is not a measurement.

10Common Pitfalls & Debugging

Symptom. fatal error: 'engine/gfx/raster.hpp' file not found, from a demo, after everything looks correctly placed.

Cause. The include directory was declared PRIVATE on the library, so it never propagated to anything that links it. This is the single most common CMake mistake in this shape of project, and it fails at the consumer rather than at the library, which sends people looking in the wrong file.

Fix. target_include_directories(engine PUBLIC include). Read the keyword as "who else gets this", not as "how visible is this".

Symptom. Undefined symbols at link time for functions that plainly exist, often engine::collect_triangles or similar.

Cause. The .cpp was added to the tree but not to the add_library source list. We list every source by hand — CMake will glob for you, and you should not let it, because a glob is evaluated at configure time and a new file is silently ignored until someone reconfigures.

Fix. Add the line. The one-line cost is the price of a build that never lies about what it contains.

Symptom. error: redefinition of default argument in a .cpp the moment a function's declaration moves to a header.

Cause. A default argument may be specified once per scope. When the function lived only in a .cpp the default lived on the definition; now that there is a declaration, the default belongs there and the definition must not repeat it.

Fix. Defaults on the declaration, never on the definition. This bit us on draw_triangles within minutes of the split.

Symptom. A previously fine name no longer compiles: no member named 'build_scene' in namespace 'demo'.

Cause. Something else in a nearer scope is called demo — for us, an enum class demo in an anonymous namespace, which hides the namespace entirely.

Fix. Rename the nearer, vaguer one. And expect this: names that were private for four modules have never had to be distinct from anything.

Symptom. The refactor "works" but a comparison render in the demo now shows a difference that was not there before.

Cause. Almost always a gathered options struct copied from the wrong baseline — render_options{} where the code meant opts. The defaults are all correct, so the reference render silently becomes a render of the correct settings rather than of the current ones, and the difference count turns into something else entirely.

Fix. Comparison renders copy opts and change one field. If a call site writes {}, that must be a deliberate statement that this render is the reference.

Symptom. Everything builds, the golden matches, and a week later a colleague's build fails on a header you did not touch.

Cause. A header that is not self-sufficient — it compiled for you only because of what came before it in your translation unit.

Fix. Check them all, mechanically. It is a four-line loop that compiles each public header alone, and it should live in CI: for h in engine/include/engine/**/*.hpp; do echo "#include <$h>" | c++ -fsyntax-only -x c++ -; done.

11Exercises

  1. 5.1.1 — Break the boundary on purpose. Add #include "gfx/raster.hpp" to the top of demos/hello_cube/main.cpp and build. Read the error. Now add engine/src to hello_cube's include directories and build again. Then remove both and write two sentences on what the second build proved about the strength of the boundary.

    Hint / answer. It compiles. The boundary is exactly as strong as the CMake file, which is to say: strong against accident, and no defence at all against intent. That is the correct amount. An architecture that tries to defeat a determined colleague ends up defeating everybody.

  2. 5.1.2 — Find a header that is not self-sufficient. Pick any public header, delete one of its #include lines, and confirm the whole build still succeeds. Then compile that header alone and watch it fail. Add the four-line self-sufficiency check from §10 to a script and run it on every header.

    Hint. Delete <engine/math/mat3.hpp> from scene.hpp. Everything builds, because every current consumer includes mat4.hpp first and that drags mat3.hpp in. The bomb goes off for the person who writes the first consumer that does not.

  3. 5.1.3 — Give the harness its own reason to exist. Extend verify_50 §D: build a full gpu_draw_item from a scene_object and check that its normal_from_model matches the matrix collect_triangles uses, for a non-uniformly scaled object. Then break it deliberately by using the model matrix instead of its inverse transpose, and confirm the check fails.

    Hint. Use the squashed icosahedron from §C. On a box it will pass with the wrong matrix, for the reason in the callout above — which is itself worth putting in a comment.

  4. 5.1.4 — Take the teaching switches out of the public API. Design a way to keep the demos' failure modes without exporting them. Two approaches worth trying: a separate header <engine/gfx/soft_renderer_teaching.hpp> that the demos include and a game would not; or a compile-time flag that removes the wrong branches entirely. Implement one, measure what it costs in code size and in the readability of collect_triangles, and write down which you would ship.

    Solution sketch. The separate header cannot work as stated — the wrong branches are inside collect_triangles, so the enum has to be visible to it. The honest options are a policy parameter (a template or a callback, paid for at every call) or #ifdef ENGINE_TEACHING around the enum values and their branches. The second is ugly and is what real engines actually do with their debug modes. Discovering that the obvious answer does not work is the exercise.

  5. 5.1.5 — Make the boundary a test. Add a CMake target that is expected to fail to compile: a source file using the old include spelling, built with add_test and WILL_FAIL. Now the boundary is checked by ctest rather than by this lesson's prose.

    Hint. add_executable(boundary_probe EXCLUDE_FROM_ALL …) plus add_test(NAME boundary COMMAND ${CMAKE_COMMAND} --build . --target boundary_probe) and set_tests_properties(boundary PROPERTIES WILL_FAIL TRUE). A test that must fail is a strange thing to write and exactly right here.

  6. 5.1.6 — Attack the real compile cost. §3.5 found that SDL contributes nearly 73,000 preprocessed lines to a file that uses one Uint32. Replace that include in framebuffer.hpp with <cstdint> and std::uint32_t, and measure the preprocessed line count again. Then decide whether to keep it, and defend the decision either way.

    Hint. The measurement is easy and the decision is not. Uint32 is SDL's spelling and the rest of the engine is full of it; a framebuffer that speaks std::uint32_t while its neighbours speak Uint32 buys compile time and spends consistency. This is a real tradeoff and engines land on both sides of it.

12Recap & Next

The engine gained the thing that makes it an engine: an outside.

  • engine/ is a static library with 37 public headers under engine/include/engine/ and its sources private. The boundary is the include path, and a demo using the old spelling does not compile.
  • demos/ holds three targets that link it: the sandbox, a shared content library, and a 160-line acceptance test that proves the API can be used from outside.
  • The CPU render pipeline, the scene description, the projector and debug draw all moved out of main.cpp and into the engine — 1,325 lines that were never the demo's.
  • collect_triangles was designed, because publishing it forced the question: 15 parameters became 8, seven throwaway variables disappeared, and every default is now the correct answer.
  • The whole thing is verified twice against a characterization test written before any of it started: 0 bytes differ, from the demo and from a harness that links rather than copies.

And one thing did not get fixed on purpose. demos/sandbox/main.cpp is still 5,721 lines, because splitting it needs somewhere to split it into: every one of those demos would be its own small executable if there were an application layer to hang a loop on. Which is the next question, and it is a bigger one than it looks — who owns the loop? Does your program call the engine, or does the engine call your program? That single decision shapes the whole API, and every engine you have heard of has an opinion about it.
