The First Triangle

Three vertices, one pipeline object, one draw call — and the first pixel in this course whose colour was computed by hardware rather than by code you wrote. It is more machinery than you expect, every piece of it earns its place, and at the end we check the result against your own rasterizer, pixel by pixel.

1The Problem

In Lesson 2.2 you drew your first triangle. Here is the entire call:

One function, five arguments, and the pixels appear. You have three GPU objects now — a device, four shaders, a way to get bytes onto the hardware — so the corresponding call ought to be about as short. It is not. There is no SDL_DrawTriangle, and the call that does exist cannot be made yet:

Read it for what is missing. No vertices. No colours. No shader. No target. Four integers and a render pass, and every one of those integers is an index into something the call does not mention.

The gap

fill_triangle takes its arguments at the call. A GPU draw call takes almost none of them: everything it needs was bound beforehand — the geometry to a slot, the shaders and all the render state to a pipeline object, the output to a render pass. The draw call says only "three vertices, once, from the start", and the answer to "which three, drawn how, into what" is state you set up earlier.

So the work of this lesson is not the draw. It is assembling everything the draw refuses to ask for, and doing it in an order where each piece is legal.

That is genuinely more code than a beginner expects, and it is the reason "my first triangle" is a rite of passage in every modern graphics API rather than a five-minute exercise. It also has a second, quieter difficulty. Lesson 4.3 established that SDL checks a shader's entry point and not its resource counts; this lesson finds the same temperament in pipeline creation, where most wrong descriptions are accepted without complaint and the triangle simply does not appear.

And there is a debt to settle. Lesson 4.3 measured SDL_CreateGPUShader at eight microseconds, observed that this cannot possibly include compiling a shader, and wrote down a prediction about where the compile really happens. §4.4 of this lesson answers it — and the answer comes with a second finding that nearly went into print as a fact.

2Building Intuition

2.1Why so much machinery for one triangle

Count what fill_triangle actually needed, by the end of Module 3. It took a framebuffer, three vertices and a fill_style — and that fill_style had grown to ten fields: interpolation mode, shading mode, blend space, cull mode, a light, a material, a specular model, an eye position, a texture binding, an encode mode.

Lesson 4.1 counted those ten against SDL_GPUGraphicsPipelineCreateInfo's nine and observed that they are the same object. This lesson is where that observation becomes a call. The machinery is not new; it is your own fill_style, plus the two things a second processor forces you to make explicit: where the geometry lives, and what the output looks like.

2.2The pipeline is the missing argument list

Here is the shortest way to think about a pipeline object, and it survives contact with the details: it is the argument list of fill_triangle, hoisted out of the call and frozen.

Our fill took its style per call, so it could change per triangle — and Lesson 3.8 used exactly that, rebinding a material per triangle, while noting in the code that a GPU cannot do this. Now you can see why not. The state is not a parameter the hardware reads; it is compiled into the machine code that runs. Changing it means a different program, which means a different pipeline object.

Lesson 4.1 measured the usual justification for that design — that baking state in spares the inner loop a branch — and found it false: hoisting our own per-pixel branch on draw-constant state measured 0.93×, which is nothing. The real reason was validation and compilation, and this lesson is where you can finally watch that happen, with a stopwatch.

2.3A struct full of pointers

One practical hazard, worth meeting before it costs you an afternoon. SDL_GPUGraphicsPipelineCreateInfo does not contain its vertex layout; it points at it:

Three of the create-info's fields are arrays reached through pointers — the buffer descriptions, the attributes, and the colour target descriptions. Which means the obvious helper function is a bug:

The compiler says nothing. The returned struct is a set of perfectly valid-looking fields and a pointer into a dead stack frame, and what happens next depends on what the next function call happened to write there. That is why this lesson's pipeline_desc is a class rather than a function: it owns the arrays, so the pointers live exactly as long as the description does.

C++ in place — returning a struct that points at yourself

This is the same hazard as returning a std::string_view of a local std::string, or a std::span of a local array, and it is worth recognising as a shape rather than as three separate rules: a type that holds a non-owning reference must not outlive what it refers to, and returning it by value is the easiest way to make it try.

C++ gives you no help here. The fix is to make ownership explicit — put the arrays and the struct that points at them in one object, so they have one lifetime. Our mesh_data/mesh pair from Lesson 3.5 solved the same problem the same way.

3The Theory

3.1Nine fields, and what each decides

@@FIG_FIELDS@@

Figure 1 is the whole create-info. Nine fields at the top level and fifty-three once the nested state structs are expanded — which is the count Lesson 4.1 arrived at from the other direction, by asking what fill_style would have to become.

Three of them deserve attention now, because they are the three that produce silence rather than errors when they are wrong.

The rasterizer state holds the cull mode and the winding, and every enum in it has its first enumerator at zero. So a zero-initialised rasterizer state means "counter- clockwise is front-facing, cull nothing" — which is why a forgotten cull_mode shows up as no culling at all rather than as a mistake. We set all three explicitly, every time, and §3.3 measures what happens when the winding disagrees with them.

The target format is not a choice. It must equal the format of the texture the pipeline will render into, and for the swapchain that is negotiated between the display, the compositor and the driver — which is why Lesson 4.2 asked for it and logged it. Note that our pipeline_desc takes it from the device rather than accepting it as a parameter: a value that must match something is better read from that something than passed in by a caller who might be guessing.

The vertex input state is the subject of §3.2, and of the whole of Lesson 4.5.

Now the more interesting question: which of these does SDL check? The bottom of Figure 1 is four creation attempts, and the answer is one of them.

One mistake that is worse than an error

Two of these trials are missing from the harness, and the reason is worth knowing. Swapping the two shaders between slots is not caught either — but it does not fail politely. A vertex shader in the fragment slot is refused with a Metal error about an interrupted compiler connection, after which the next pipeline creation in that process crashed; and a fragment shader in the vertex slot segfaults immediately.

Both were reproduced three times in an isolated one-trial program before being written down. SDL_GPU does not validate which stage a shader was compiled for, so keep the two straight yourself — the type system will not, because both are SDL_GPUShader*.

3.2The layout, and the contract nothing checks

The GPU receives a block of bytes and a shader that declares typed inputs. Something has to say which bytes are which, and that is the vertex input state: a pitch per buffer, and an attribute per shader input.

Worked example — our vertex, byte by byte

The struct is seven floats:

  • sizeof(gpu_vertex) = 7 × 4 = 28 bytes, and that is the pitch: the distance from one vertex to the next.
  • x sits at offset 0, is three floats, and feeds shader input location 0 — which is TEXCOORD0, which is position in triangle.vert.hlsl.
  • r sits at offset 12 (three floats in), is four floats, and feeds location 1 — TEXCOORD1, colour.

Which is exactly what the description says, with offsetof doing the arithmetic so that inserting a field later cannot silently invalidate a hand-written 12:

Now notice what has just happened. The same vertex is declared in two places, in two languages, and nothing checks that they agree. The HLSL says float3 position : TEXCOORD0; float4 colour : TEXCOORD1;. The C++ says 28 bytes, FLOAT3 at 0, FLOAT4 at 12. If those descriptions drift apart — a field inserted, a semantic renumbered, a float3 that became a float4 — you get geometry that is wrong rather than absent, which is much harder to diagnose.

Lesson 4.3's reflection file already knows the shader's half of this contract; its inputs array lists every location with its type. Exercise 4.4.4 uses it to check the C++ half against it at startup, which is the sort of assertion that turns a mystery into a line number.
