Module 4 — To the GPU: SDL_GPU · Lesson 4.2

The SDL_GPU Mental Model

Nine objects, of which you have already built five. The four that are new all exist for one reason: from this lesson on, a function call no longer does the thing it names — it writes the thing down, and someone else does it later, on another processor. Everything difficult about GPU programming comes out of that one sentence.

1The Problem

Here is a piece of code that does exactly what it says. You have written thousands of lines like it since Lesson 1.5, and never once had to wonder about it:

The second line reads back what the first line wrote, because the first line happened. It happened on this processor, in this thread, before the next statement began. That is such a basic property of a program that it does not feel like a property at all — it feels like what a program is.

Now here is the same idea in SDL_GPU. Clear a texture to a known colour, copy it back to the CPU, and read it. Four calls, no shaders, nothing exotic:

It prints garbage. Not sometimes — 64 times out of 64 in this lesson's harness, which fills the destination with the byte 0xAB beforehand so that "nothing was written here yet" is visible rather than merely suspected. Every one of those 64 reads came back 0xAB. Add one call — a wait on a fence — and the same 64 trials are correct 64 times.

The failure mode, precisely

SDL_SubmitGPUCommandBuffer returned before the clear had happened. It returned before the copy had happened. It returned, in fact, before the GPU had necessarily looked at the command buffer at all — its job is to hand the work over, not to perform it. The read that followed was a read of memory nobody had written yet.

And notice the shape of this bug. It is not a crash, not an assertion, not an error return. Every call succeeded. On a slower GPU it would be wrong by more; on a faster machine, or a smaller texture, it might come back right often enough to look like working code. This lesson's harness reports "wrong 64 / 64", but a version of it that read one byte instead of a quarter of a megabyte would sometimes report zero, and that is much worse — because then you would ship it.

So the problem is not that SDL_GPU has nine new nouns in it. You could learn nine nouns in an afternoon. The problem is that the meaning of a function call has changed, and every one of the new nouns is there to manage the consequences. Learn the nouns without the sentence and you will write code that works on your machine and fails on someone else's, for reasons that never appear in a debugger.

Lesson 4.1 established what the GPU is: a wide, lockstep machine that is slower per lane and wins anyway. This lesson is about the wire between you and it. By the end you will have your own rasterizer's picture on screen, carried there entirely by SDL_GPU, with no shader anywhere in the program — and a graph, drawn by your own fill_rect, of exactly where the frame's 16.667 milliseconds went.

2Building Intuition

2.1A phone call, and a work order

Every graphics call you have made so far has been a phone call. You said "put a red pixel at (10, 20)"; by the time you stopped speaking, the pixel was red. The call and the effect were one event, and they were one event because the thing being asked and the thing doing the asking were the same processor.

From here, a graphics call is a work order. You are not doing the work and you are not talking to whoever will. You are filling in a sheet of paper: clear this target to grey; then copy those bytes over there; then draw these triangles. Filling in the sheet is fast, because writing "resurface the driveway" takes a second and resurfacing a driveway does not. When the sheet is complete you hand it over — SDL_SubmitGPUCommandBuffer — and that is a separate act from the work being done.

This is not an analogy that gets stretched until it breaks. It is very nearly the literal implementation: a command buffer is a chunk of memory into which the driver appends packets, and submitting it makes the GPU's front end start reading them. You can measure the difference between writing the order and doing the work, and you should, because the ratio is the most important number in this lesson:

It also shows the one arrow going the other way. The dashed line back up to the CPU lane is a fence, and its position is the answer to the failure in §1: the fence is where the work finished, and nothing about that work may be believed before it.

2.2Two memories, and the room between them

The second new idea is that there is more than one kind of memory, and you cannot reach the important one.

A GPU texture lives in memory arranged for the GPU's benefit. It is not a row-major array of Uint32 like engine::framebuffer; it is tiled, so that the four texels of a 2×2 quad (Lesson 4.1 §2.3) are adjacent rather than a row apart, and it may be losslessly compressed, and its exact arrangement is a trade secret that differs between vendors and between two GPUs from the same vendor. You cannot write to it with memcpy, and the reason is not that SDL is being protective — it is that you do not know where anything is.

So there is a third region: memory that both processors can address, laid out plainly, whose only purpose is to be a staging area. SDL calls it a transfer buffer. You memcpy into it; the GPU copies out of it into whatever arrangement it prefers. Every pixel that goes from your framebuffer to the screen takes both hops, and no API can remove that, because it is the shape of the machine rather than a wart in the interface.

@@FIG_HOPS@@

Figure 2 is worth reading twice: once left to right, for the route, and once for the dashed vertical line. To the left of that line, work happens when you call it. To the right, calling it only writes it down. The memcpy into the transfer buffer is real work, now, on the CPU, and this lesson measures it at 0.0028 ms for a 320×180 frame. The upload and the blit are recorded in microseconds and performed later.

The ninety-percent picture

On a machine with unified memory — every Apple silicon Mac, every console, most phones — the CPU and GPU are looking at the same physical DRAM, and a hypothetical perfect API could sometimes skip the staging copy. SDL_GPU does not expose that, because it must also run on a discrete GPU across a PCIe bus, where the copy is a genuine journey across the motherboard. This is the ninety-percent picture; the missing ten percent is that on some hardware the transfer buffer's copy is cheaper than it looks, which the numbers in §4.6 will show.

Keep that check. If SDL ever inserts an enumerator, this fails here, with a name and a line number, instead of failing as a mesh that culls the wrong faces in a lesson six weeks from now.

Now the four that are new — the device, the command buffer, the transfer buffer and the fence. Look at what they have in common. A device is a connection to another processor. A command buffer is a message to another processor. A transfer buffer is shared ground because the other processor's memory is not yours. A fence is how you learn that the other processor has finished. There is no fifth idea hiding: all four are the same idea, which is that there are two machines now, and your rasterizer never needed any of them because it was only ever one.

2.4Why the swapchain is borrowed

One object deserves separate treatment, because it behaves unlike the rest: the swapchain texture.

Since Lesson 1.5 you have owned your framebuffer. You allocated it, you kept it for the whole run, you cleared it at the top of each frame. A swapchain texture is the opposite in every respect. You do not create it; you ask for one each frame, and give it back by submitting the command buffer that referenced it. There are usually two or three of them and you do not choose which you get. It is write-only — you cannot sample it, and you cannot read it back. And you may be handed nullptr, which is not an error.

The reason is that the display owns these images, not you. At any instant one of them is being scanned out to a physical panel, sixty times a second, whatever your program is doing. Handing you that one would show the reader half of a half-drawn frame. So the display keeps a small set and lends you one that it is not currently scanning — and if the GPU has fallen behind and every image is spoken for, the honest answer to "may I have one?" is "wait", which is what SDL_WaitAndAcquireGPUSwapchainTexture does, and what a minimised window's nullptr means.

This is where a vsynced frame actually waits

Not in SDL_SubmitGPUCommandBuffer, and not in a present call — SDL_GPU does not have one, because presentation is implied by having acquired the image. In this lesson's probe, running at 60 Hz, 16.002 ms of a 16.667 ms frame is spent inside the acquire. Your program is not slow. It is waiting for a monitor, which is a completely different problem with completely different solutions, and knowing which one you are looking at is most of performance work.

2.5An honest sidebar: why not OpenGL

A fair question at this point is why we are learning fences and command buffers at all, when OpenGL would let us write glClear and be done. It deserves a straight answer rather than a fashion argument, and part of that answer is that OpenGL is genuinely still good at some things.

What OpenGL gets right: it is the easiest 3D API to start in, because the driver hides exactly the machinery this lesson is about. It runs on hardware from 2008. Its tutorial literature is the best-covered ground in graphics — LearnOpenGL is a superb resource and much of its content transfers directly to what we are doing. If your goal is a small tool, a visualiser, or a plot window, OpenGL is a perfectly professional choice today.

What it costs:

  • The state machine. OpenGL has one enormous global context; every call mutates it, and a function's behaviour depends on the last few hundred calls. Lesson 4.1 §3.4 argued the opposite design — state gathered into an immutable object, validated once — and measured the usual justification for it and found that one false. The real reason stands: a pipeline object is validated and compiled once, at creation, rather than re-checked at every draw.
  • The hidden asynchrony is still there. This is the important one, and it is widely misunderstood. OpenGL does not remove the two-processor problem; it hides it. Your glDrawArrays also returns before the work happens, and the driver silently inserts synchronisation when you touch a resource it is still using. That is convenient right up to the moment your frame time doubles for no visible reason, and then you are debugging a synchronisation you cannot see and did not write.
  • It is deprecated on macOS — frozen at 4.1, from 2011, and formally deprecated since 2018. It works today. Planning a five-year project around it does not.
  • SDL_GPU is SDL3's flagship path, and it maps onto Vulkan, D3D12 and Metal — the three APIs that current hardware is actually designed for. The concepts in this lesson are those APIs' concepts, so what you learn here transfers to all three.

The honest summary: OpenGL is a fine way to draw a triangle and a poor way to learn how the machine works, because its whole design is dedicated to not telling you. We are here to learn how the machine works.

3The Theory

3.1What a fence actually promises

A fence is an object that becomes signalled when every command in the submission that produced it has finished executing. That is the whole definition, and the useful part is what it does not say.

It does not say the commands ran in the order you wrote them — they may not have, as long as the result is as if they did. It does not tell you how far along the work is; there is no percentage. It is one bit: not yet, or done. And it applies to one submission, not to the device — a second command buffer submitted afterwards has its own fence and its own answer.

SDL gives you three ways to use that bit, and they are the three shapes of every synchronisation problem you will meet:

Now, the cost. Waiting on a fence is not expensive in itself; the wait in §1's fix takes under a millisecond. What is expensive is what waiting prevents: while the CPU is blocked, it is not recording the next frame, so the GPU will have nothing to start on when it finishes. You do not pay the duration of the wait. You pay the overlap you gave up.

Worked example — what a sync costs, in real numbers

This lesson's harness (§E) submits the same work 32 times — 8 blits of a 1024×1024 texture each, so about 0.184 ms of GPU work per submission — in two ways.

  • Waiting on every fence: 9.438 ms total, 0.295 ms per submission.
  • Waiting only on the last one: 5.904 ms total, 0.184 ms per submission.

The speedup is 1.60×, and read the pipelined figure again: 0.184 ms per submission is exactly the GPU time per submission. Pipelined, the GPU never idles, so the total is the GPU work and nothing else. Stalled, each round trip adds 0.111 ms of handshake — the CPU waiting for the GPU, then the GPU waiting for the CPU — and 32 of those is the 3.5 ms difference.

Note what this does not say: it does not say a sync costs 1.6×. It says a sync costs one round trip, and whether that matters depends entirely on whether the machine had anything else to do. §4.5 measures a case where the answer is nothing at all, which is exactly why this bug survives long enough to reach production.

3.2Cycling, and the bug it exists to prevent

Here is a problem you now have and did not have last lesson. You memcpy this frame's pixels into the transfer buffer and record an upload. Next frame you do it again. But is the GPU finished with the first upload? If it is not, your second memcpy is overwriting bytes that a pending command is going to read — and the image on screen becomes an interleaving of two frames.

Every low-level graphics API has this problem. Vulkan makes you solve it by hand, with per-frame resources and explicit barriers, and it is where most people's first Vulkan renderer goes wrong. SDL_GPU's answer is a single bool named cycle, and the header states the rule plainly enough to be worth quoting: when a resource is used in a pending command buffer it is bound, and if you write to a bound resource with cycle = true, SDL hands you a different internal copy instead.

So cycle means: if this is busy, give me a fresh one. The resource is a ring buffer wearing the disguise of a single object, and the handle you hold stays valid while the storage underneath rotates.

The failure mode, and why you will not see it

Pass false where you should pass true and everything looks perfect — on a machine where the GPU keeps up. The corruption appears only when the GPU falls behind far enough that last frame's upload has not been consumed, which means it appears on slower hardware, under load, in someone else's hands. It shows as a horizontal band of the previous frame, usually near the top, flickering.

Two rules keep you out of it. Cycle when you write to a resource that a previous frame may still be reading — which for a per-frame upload path means every frame. And never cycle a resource you are about to only partially update, because cycling makes the whole resource undefined, not just the part you touched.

3.3Frames in flight: latency against throughput

The swapchain has a small number of images, and SDL lets you set how many frames may be pending on the GPU at once — SDL_SetGPUAllowedFramesInFlight, minimum 1, maximum 3, default 2. This is one of the few knobs in the whole API that changes how the program feels rather than how fast it runs, and the reason is worth deriving rather than memorising.

Let the CPU take C milliseconds to prepare a frame and the GPU take G to execute it. With F frames allowed in flight:

\[ \text{throughput} \;=\; \frac{1}{\max(C,\,G)} \qquad\text{(for } F \ge 2\text{)}, \qquad \text{latency} \;\approx\; F \cdot \max(C,\,G) \]

throughput = 1 / max(C, G) once F ≥ 2; latency ≈ F × max(C, G)

In prose, because the equation must never be the only carrier of the fact: with two or more frames in flight the CPU and the GPU overlap, so the frame rate is set by whichever of them is slower — but the picture you are looking at was prepared F frames ago, so every extra frame of overlap is an extra frame of delay between moving the mouse and seeing the result.

Worked example — three settings, by hand

Take C = 4 ms and G = 6 ms, and a display fast enough not to be the limit.

  • F = 1. No overlap at all: the CPU prepares (4), hands over, waits for the GPU (6), and only then starts the next. A frame every 4 + 6 = 10 ms — 100 fps — and latency is one frame, 10 ms.
  • F = 2. The CPU prepares frame N+1 while the GPU runs frame N. Every 6 ms a frame completes — 1/max(4, 6), so 167 fps, a 1.67× throughput gain — and the CPU is idle 2 ms in every 6. Latency is about 12 ms.
  • F = 3. Throughput is unchanged at 167 fps, because the GPU was already saturated and a third queued frame cannot make it faster. Latency rises to about 18 ms.

That asymmetry is the whole design rule. Going from 1 to 2 buys real throughput; going from 2 to 3 buys only latency, and buys it in the wrong direction. Two is the default because two is where the gain stops. Raise it to three when frame times are erratic and you would rather absorb a spike than drop a frame; lower it to one when input latency is the product — a competitive shooter, or anything on a head-mounted display, where 18 ms of queue is the difference between a game and a nausea generator.

Not a per-frame call

SDL's documentation is explicit that SDL_SetGPUAllowedFramesInFlight "will stall and flush the command queue to prevent synchronization issues". Call it once at a settings change, never inside a loop — and expect the frame it runs in to produce nonsense measurements, which is why the probe's log says so out loud when you press 3.

3.4A float clear becomes bytes

SDL_GPUColorTargetInfo::clear_color is an SDL_FColor — four floats. Your framebuffer stores four bytes. Something has to convert, and the conversion is not the one most people assume, so let us predict it and then measure it.

An _UNORM format stores a number in [0, 1] spread evenly across the byte range: the stored byte is the float times 255, rounded. There is no transfer function anywhere. A _UNORM_SRGB format stores the same range, but applies the sRGB encode on write and the matching decode on read, so that shaders always work in linear light while memory holds an encoding that spends more of its 256 codes in the dark tones, where the eye can tell them apart. That is the argument of Lesson 1.6, implemented in hardware.

\[ \text{byte}_{\text{UNORM}} = \mathrm{round}(255\,v), \qquad \text{byte}_{\text{SRGB}} = \mathrm{round}\!\left(255\left(1.055\,v^{1/2.4} - 0.055\right)\right) \]

UNORM: byte = round(255 × v). sRGB: byte = round(255 × (1.055 × v^(1/2.4) − 0.055)), for v above 0.0031308.

Worked example — where does 0.5 land?

Into an R8G8B8A8_UNORM target.

  • 255 × 0.5 = 127.5, which rounds to 128.

Into an R8G8B8A8_UNORM_SRGB target.

  • 0.51/2.4 = 0.50.41667 = e0.41667 × ln 0.5 = e−0.28881 = 0.74915
  • 1.055 × 0.74915 − 0.055 = 0.79035 − 0.055 = 0.73535
  • 255 × 0.73535 = 187.51, which rounds to 188.

And the measurement, from clearing a 1×1 target of each format and downloading the byte: 128 and 188. Both predictions exact, and the sRGB one matches engine::linear_to_srgb_u8 — our function, written in Lesson 1.6 — to the code, at all five test values.

Figure 4 draws both answers. The single most useful sentence to take from it is this: the clear colour is always linear light, and the format decides what gets stored. You never encode a clear colour yourself. If you do — if you pass 188/255 to an sRGB target because you wanted mid-grey — the hardware encodes your already-encoded value and you get 226, which is the washed-out picture that Module 6 will teach you to recognise on sight.

Two smaller results from the same experiment, both worth knowing and neither worth guessing: values outside [0, 1] are clamped, not wrapped (−0.5 → 0, 1.5 → 255), and the _UNORM_SRGB transfer function applies to the three colour channels only. Alpha is linear in both formats, because alpha is a coverage fraction rather than a colour and encoding it would be meaningless.

3.5The letterbox, by hand

One piece of arithmetic stands between our 320×180 framebuffer and the window: they are not the same size, and the window can be resized to any shape at all. Stretching to fill would make every circle in the scene an ellipse, so we fit the largest rectangle of the source's aspect ratio inside the target and centre it.

The comparison is best done without dividing. The source is proportionally wider than the target when src_w / src_h > dst_w / dst_h, and multiplying both sides by the positive quantity src_h × dst_h turns that into src_w × dst_h > dst_w × src_h — the same question, in integers, with no rounding and no division by zero.

Worked example — 320×180 into a 1024×768 window
  • Is the source proportionally wider? 320 × 768 = 245,760 against 1024 × 180 = 184,320. Yes, so we fill the width.
  • w = 1024, and h = 1024 × 180 / 320 = 576.
  • x = (1024 − 1024) / 2 = 0, y = (768 − 576) / 2 = 96.

So the image lands at (0, 96) at 1024×576, with 96-pixel bars above and below. Check it: 1024/576 = 1.778 = 16:9, the source's aspect ratio, preserved exactly. fit_centred returns precisely this, and §H of the harness asserts it along with the two-bars-at-the-side case and both degenerate inputs.
