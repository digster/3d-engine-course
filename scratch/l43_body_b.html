Two pairs, and the second pair exists for a specific reason. The first pair is what Lesson 4.4 will draw with — a vertex stage that passes a colour through, and a fragment stage that returns it. Between them they declare no resources at all, so every count in their create-info is zero.

A shader with no resources cannot demonstrate the thing that most often goes wrong. So the second pair, which Lesson 4.6 will use, declares one uniform buffer in the vertex stage and a texture, sampler and uniform buffer in the fragment stage — enough to make every register space in Figure 2 appear in real code:

The vertex shader of that pair carries the other half of the mapping:

mul(M, v) treats v as a column vector — which is the convention this engine adopted in Lesson 2.5 and has never deviated from: v' = Mv, and AB means B first. 4.2A build step that asks first

Now the build. The naive version is four lines of add_custom_command and it works on the machine you wrote it on. §2.3 is the reason we are not writing that: the tool's capabilities depend on how it was built, and finding out at build time — as a confusing error inside a compile step — is much worse than finding out at configure time, in a message.

So cmake/Shaders.cmake opens by running the tool once and looking at the exit code:

This is a capability probe, and it is a technique worth having in your hands generally: when a tool's behaviour depends on how it was built, run it rather than reason about it. Version numbers cannot answer this question — the version is 3.0.0 whether or not DXC was linked in.

And then the piece that everybody forgets exactly once:

Why an unattached custom command does nothing

add_custom_command(OUTPUT ...) does not create a build rule that runs. It declares how to produce a file if somebody needs it. If no target lists that file as a dependency, nothing ever asks for it, and the command never runs — with no error, because nothing failed. You get a successful build and an empty output directory.

The fix is the three lines above: wrap the outputs in a target, and make the executable depend on it. The string(REPLACE) is there because our shader names contain a dot (triangle.vert) and CMake target names may not.

gpu_shader::load is four steps, and the first is the payoff of a line Lesson 4.2 logged and promised to use:

Note where the entry point lives: on the format, not on the shader. §3.4's rename is a property of how MSL was produced, so it belongs beside the format that says so. Store it per shader and you have four copies of one fact.

Then the file, the reflection, and the creation. One decision inside is worth defending:

A missing or malformed reflection file is a refusal, not a fallback to zeros. Given §3.3's measurement — that SDL accepts any counts you give it — falling back to zero would mean quietly building the exact bug the file exists to prevent. Failing loudly at startup is the better outcome by a wide margin.

C++ in place — a struct is not always a mirror

shader_resources holds four Uint32s: exactly the four fields of SDL_GPUShaderCreateInfo that this class cannot know for itself. It is deliberately not a mirror of the whole create-info, even though the rest of this engine mirrors SDL structs enthusiastically (Lesson 3.9's sampler, Lesson 4.1's fill_style).

The boundary is drawn at what must be discovered. The code, its size, the format, the stage and the entry point are all things the caller knows. These four are things only the compiled shader knows. Drawing a type's edge along that seam is what makes "read them from a file" the obvious implementation rather than a workaround.

4.4A parser that is allowed to be small

The reflection file is JSON, and this engine has no JSON parser. It gets one of about thirty lines, which scans for four known keys and reads the integer after each — and that is a decision that deserves defending rather than sliding past, because in Lesson 3.5 exactly the opposite decision was made for OBJ.

The difference is trust. parse_obj reads files a user supplies, from the internet, possibly hostile and certainly malformed — so it validates everything, reports a line number, and has a status enum. This file was written by a compiler we invoked ourselves, three seconds ago, into a directory we created. It is not a trust boundary, and building a general JSON parser to read it would be answering a question nobody asked.

What it must still do is refuse rather than guess, which is what §G of the harness checks: a missing key, a non-numeric value, an empty file and the substring trap ("num_samplers" must not satisfy a search for "samplers") are all rejected. Small is allowed; sloppy is not.

4.6Where the compile actually happens

One measurement remains, and it produced the most interesting result in the lesson. How long does SDL_CreateGPUShader take?

@@FIG_WHEN@@

Figure 6 is the answer, and the middle bar is barely visible for a reason: eight microseconds. All four shaders created, cold, in 0.028 ms — against 61.2 ms to compile them at build time. And the first measurement of a shader is the same as the ninth, so this is not a cache.

Read that and disbelieve it

Eight microseconds cannot include turning MSL into machine code for a 20-core GPU. Lesson 4.2's rule applies — check that the number can be true — and it is not true. What is true is that the compile has not happened yet.

The prediction, which Lesson 4.4 is going to check: it happens at pipeline creation. Only there does the driver know the colour target's format, the depth state, the blend mode and the vertex layout — and machine code for a fragment shader must be specialised to all of them. That is exactly what Lesson 4.1 measured as the real reason immutable pipeline objects exist, and exactly what SDL_gpu.h means when it lists pipelines under things created once: "Render pipelines (precalculated rendering state)".

A shader object, then, is not a compiled program. It is a compiled-enough program — a validated blob plus the four counts — waiting to be told what it will be used with. We will find out in the next lesson whether that is right.

That reframes what this lesson bought, and the reframing is the honest summary of offline compilation. The 61.2 ms it moved out of your program's startup is the front end: the parse, the type checking, the optimisation, the megabytes of compiler that would otherwise be in the box. What it cannot move is the driver's own final step, which happens on the user's machine because only the user's machine knows what the user's GPU is.

7Common Pitfalls & Debugging

The build succeeds and the shader directory is empty

Symptom. No compile errors, no warnings, and no output files. The program then reports that it cannot read a shader.

Cause. An add_custom_command(OUTPUT ...) with nothing depending on its output. It describes how to make a file; if no target wants that file, the rule is never run and nothing has failed.

Fix. Wrap the outputs in an add_custom_target and add_dependencies(your_exe that_target), as §4.2 does. Remember that CMake target names cannot contain a dot, so triangle.vert needs string(REPLACE "." "_" ...) first.

Failed to compile SPIR-V From HLSL: not built with DXC support

Symptom. shadercross runs, prints that error, and produces a zero-byte file.

Cause. The tool was built without DirectXShaderCompiler — usually a clone without --recursive. Its version number does not reveal this; only running it does.

Fix. Rebuild with submodules, or install glslc and let the CMake fall back for the first hop. Note what you cannot do: produce DXIL. That hop is DXC.

dyld: Library not loaded: @rpath/libSDL3_shadercross.0.dylib

Symptom. The shadercross binary refuses to start, saying it cannot find its own library. Reason: no LC_RPATH's found.

Cause. An install that put the executable and the shared library in the right places but did not record where to look. Nothing to do with your project.

Fix. Add the sibling lib directory to the loader path. cmake/Shaders.cmake does this for you, deriving the prefix from the executable's own location and using the right variable per platform (DYLD_LIBRARY_PATH, LD_LIBRARY_PATH, PATH).

SDL_CreateGPUShader fails with "Creating MTLFunction failed"

Symptom. The file loads, the format is right, and creation still returns null.

Cause. The entry point name. Your HLSL says main; the generated MSL says main0, because main is reserved in Metal Shading Language.

Fix. Tie the entry-point string to the format, as choose_shader_target does. And be glad about this one: §3.4 measured it being refused at creation with a message, which is the kindest failure in the lesson.

The shader loads, runs, and reads nothing

Symptom. A texture samples as black, or a constant never changes. Everything created successfully and no call returned an error.

Cause. Either a wrong register space (§3.1) or wrong resource counts (§3.3). Both are silent: the space is valid HLSL that names the wrong slot, and the counts are accepted by SDL without validation — measured, including 99 samplers on a shader with one.

Fix. For the space, spirv-dis | grep DescriptorSet and compare with Figure 2. For the counts, never type them: read them from the reflection file the compiler wrote, and refuse to load if it is missing.

The vertex attributes arrive scrambled

Symptom. Geometry is inside out or a colour appears where a normal should be. Nothing errors.

Cause. Semantic numbering. SDL assumes every non-system-value semantic is TEXCOORDn numbered from zero, so a gap or a repeat maps an input to the wrong buffer element.

Fix. Number them from TEXCOORD0 upwards with no gaps, in the same order as the vertex layout you will describe in Lesson 4.5. The reflection file's inputs array lists what the compiler thinks the locations are — read it when in doubt.

Editing a shader changes nothing

Symptom. You edit the HLSL, rebuild, run, and see the old behaviour.

Cause. Usually the copy step rather than the compile: the shader was rebuilt into build/shaders/ but the program is reading a stale copy next to an executable somewhere else.

Fix. Check the timestamps of both. Our POST_BUILD copy runs on every successful link, so the usual culprit is running an old binary from a different directory. And note that the dependency chain is real: touching a .hlsl re-runs all three hops for that shader and nothing else.

8Exercises

4.3.1 — Break a register space on purpose

Move textured.frag.hlsl's cbuffer Tint from space3 to space1. Rebuild. Predict, before you look, what will fail: the compile, the reflection, the load, or nothing. Then check with spirv-dis and with the running program.

Hint

Ask what each stage of the chain knows. Does the HLSL compiler know which stage this shader will be? Does shadercross? Does SDL, at creation?

Solution sketch

Nothing fails. It compiles, reflects, translates and loads — the uniform-buffer count is still 1, because there is still one buffer; only its set changed. The error is undetectable until something binds a uniform buffer and the shader reads a slot nobody filled. That is why this lesson's answer to register spaces is a disassembler rather than a compiler flag.

4.3.2 — Make the counts lie, and find out when it matters

Hard-code num_samplers = 0 in gpu_shader::load, ignoring the reflection, and run. Then keep the lie in place through Lesson 4.4 and 4.7, and record the first moment anything notices.

Hint

§3.3 already tells you creation will not notice. The candidates are pipeline creation (4.4), the bind call (4.7), and the picture.

Solution sketch

This is a genuinely open exercise and worth keeping notes on, because the answer is backend-specific: a validation layer may object at bind time, or nothing may object at all and the sampled texture comes back black. The transferable result is the shape of the bug — a lie told at creation, detected at use, on a machine that may not be yours. That is why the reflection file is not a convenience.

4.3.3 — Add DXIL, or prove you cannot

Get a shadercross with DXC support: clone it with --recursive and rebuild. Reconfigure our CMake and read the -- Shaders: line. If DXIL appears, compare the file sizes with Figure 3; if it does not, find out from the build output which dependency is missing.

Hint

The probe in cmake/Shaders.cmake is the fastest way to test: it is one execute_process whose exit code is the whole answer. You can run the same command by hand.

Solution sketch

With DXC present the configure line becomes "shadercross reads HLSL directly (built with DXC)" and the format list gains dxil. DXIL is a bitcode format and is typically several times the size of the equivalent SPIR-V — a fact worth measuring rather than believing, since it decides how much of your package is shaders on Windows.

4.3.4 — Read the whole reflection

Our scanner reads four integers and ignores the inputs and outputs arrays. Extend shader_resources to record the vertex inputs — name, type and location — and log them at startup. Then, in Lesson 4.5, use them to check the vertex layout you describe by hand.

Hint

The arrays make the file no longer a flat list of key–integer pairs, so the thirty-line scanner will not stretch to them honestly. Decide deliberately: a slightly larger scanner for a known shape, or a real JSON parser. §4.4's trust argument still applies.

Solution sketch

The payoff arrives next lesson but one: a vertex layout that disagrees with the shader is another silent failure, and the compiler already knows the right answer. Checking a hand-written layout against the reflection at startup turns a class of "why is my mesh inside out" into an assertion with a name in it.

4.3.5 — Time the front end against the back end

Measure each hop yourself — HLSL→SPIR-V, SPIR-V→MSL, SPIR-V→JSON — over ten runs, taking minimums. Then make the shaders substantially bigger (unroll a loop, add a hundred lines of arithmetic) and measure again. Which hop grows, and what does that tell you about where the work is?

Hint

Lesson 3.10's rules apply to processes as much as to functions: warm up first, take minimums for anything compiler-shaped, and change one thing at a time.

Solution sketch

On this machine the front end is 12.3 ms against 1.5 for each translation — an eight-to-one split before you make anything bigger. Growing the shader should widen it, because parsing and optimising scale with the source while a SPIR-V-to-MSL translation is closer to a walk over instructions. The reason this matters: it is the front end that offline compilation removes from your program, and it is the expensive half.

9Recap & Next

What the engine gained

  • A shader toolchain in the build. Four HLSL sources become SPIR-V, MSL and a reflection file at build time, with a configure-time probe that finds out what the installed tool can actually do instead of assuming.
  • A shader loader that chooses. The format comes from what the device says it accepts, the entry point comes from the format, and the resource counts come from the compiler's own reflection.
  • A refusal to guess. A missing or malformed reflection file fails the load rather than defaulting to zeros — because §3.3 measured that nothing downstream will catch the mistake.
  • A windowless device. gpu_device::create(nullptr, …) now gives a device with no swapchain, which is what a shader harness — and, later, any offscreen or compute work — actually wants.

Two findings are worth carrying rather than filing. SDL checks the entry-point name and not the resource counts — one failure arrives immediately with a message and the other arrives silently, much later, so they need completely different defences: for the name, just get it right; for the counts, never type them at all.

And the thing called CreateShader does not compile the shader. Eight microseconds says so. What we have built is a validated blob and the numbers that describe it, waiting to be told what it will be used with — which is a strange sort of object until you remember Lesson 4.1's conclusion about why pipelines exist, at which point it is exactly the object you would expect.

Next: 4.4 — The First Triangle. A pipeline object built from these two shaders, a render pass, and three vertices. It is more code than you expect and every line of it earns its place — and somewhere in it, the compile that did not happen in this lesson finally does. We will time it and find out.
