Module 5 — Becoming an Engine · Lesson 5.3

Logging, Assertions, and Errors Without Exceptions

This engine has 197 logging calls and every single one of them is SDL_Log — one category, one level, no way to turn any of it down. It also has five different answers to "how does a function report failure", each defensible on its own and none of them the same. Today we fix both, and the two turn out to be one problem: a message and a return value are the same statement told to two audiences. Along the way we will measure exactly what a release build removes — and find a real bug in a macro written earlier in this very lesson.

Each of these is defensible in isolation. None of them is the same. And a caller who has to remember which one a given function uses is a caller who will eventually get it wrong in the quiet direction — ignoring a status, or logging a failure the callee already logged.

What this lesson is not going to do

It is not going to invent a sixth. §3.4 is about noticing that the engine already converged on a good answer twice, independently, and that naming that answer is cheaper and truer than designing a new one. The road not taken — a hand-rolled result<T> in the shape of C++23's std::expected — is discussed honestly and then made Exercise 9.5, with the argument for why this codebase does not need it yet.

2Building Intuition

2.1   A log is a letter to your future self

Here is the situation logging exists for, and it is worth picturing concretely because every design decision below follows from it.

Somebody you have never met runs your engine on hardware you do not own. Something looks wrong — a texture is black, the frame rate halves after ten minutes, the program exits immediately on their machine and never on yours. They cannot attach a debugger, you cannot reproduce it, and the only channel between the two of you is whatever the program said while it was running.

That is the audience. Not you, at your desk, with a breakpoint available. You, in six months, reading a paste from a stranger. And it changes what a good message is:

  • Facts beat narration. "Loading texture…" tells you nothing. "uv_grid.png 256×256, 3→4 channels, 262144 bytes from 1359 on disk" tells you the file was found, was a PNG, had no alpha, and cost a quarter of a megabyte.
  • The reason travels with the failure. A line that says "could not create texture" and a line that says which texture, at what size, and what the driver said, are different tools.
  • Volume destroys value. A thousand lines a frame is not a log, it is a haystack. The stranger will paste the last twenty lines, and if those twenty are all "drew a triangle" you have learned nothing.

The last one is why this lesson exists at all. Everything else about logging is a detail; the thing that makes a log useful is being able to choose what is in it, at run time, without a rebuild, by somebody who is not you.

2.2   Two axes, not one

So we need to filter. Filter on what?

The instinct is a single dial: a "verbosity level" from 0 to 5. Turn it up, get more. That works for a program with one subsystem, and it breaks the moment you have two — because the interesting question is almost never "how much output do I want in total". It is "I am debugging the GPU path; show me everything it says and nothing else." A single dial cannot express that. Turn it up for the GPU and you get the asset system's chatter too.

So there are two independent questions about every message, and they are genuinely independent:

QuestionAnswer is a…Ours
Who is speaking?categorycore, platform, gfx, gpu, asset
How much does it matter?priority / leveltrace … critical

A filter is then a table: one threshold per category. "Show me GPU at debug, and everything else only if it is an error" is gpu=debug,*=error — a sentence a person can type, and one that a single dial cannot say at all.

The mistake that looks like the answer

The classic failure is to put severity into the category list: LOG_ERROR, LOG_WARNING, LOG_DEBUG as categories. It feels tidy and it destroys the whole mechanism, because you can then never say "errors from the GPU but not from assets" — the two axes have been collapsed back into one and you are holding a dial again.

A category answers who. It is a noun, and it names a part of your program. If one of your categories is an adjective, it is a level wearing a disguise.

2.3   An assertion is not an error

The third piece, and the one most often muddled. Two things go wrong in a program and they are different in kind:

An error is something the world does to you. A file is missing. A GPU refuses a format. A user typed a path that does not exist. None of this is your program being wrong — it is your program meeting a world that is under no obligation to cooperate. Errors are expected: not welcome, but anticipated, and the correct response is to hand the caller a failure they can act on. They survive into release builds, because the world does not become friendlier when you ship.

An assertion is a claim about your own code. This index is in range. This pointer is not null. This function was called after start(). If one of these is false, the program is in a state its author did not anticipate — and there is nothing sensible to do about it, because the code that would do the sensible thing was written by the same person who was already wrong.

One question separates them, and it settles almost every case:

The test

Could a correct program, running on a working machine, encounter this?

Yes → it is an error. Return it.  ·  No → it is an assertion. Stop.

load_image("missing.png") — yes, of course a correct program can ask for a file that is not there. Error. framebuffer::row(-1) — no correct caller does that; the only way to get there is a bug above. Assertion.

The reason this matters practically is that the two want opposite treatment in a shipping build. An error path must stay: delete it and your program corrupts data instead of reporting a bad file. An assertion may go: it is a development tool, its cost is paid on every call, and by the time you ship you have either fixed the bug or you have not. Figure 4, later, is this decision as a picture.

3The Theory

3.1   Levels as promises, and who makes them

A level is only useful if it means the same thing everywhere. "Warning" that sometimes means "fatal" and sometimes means "hmm" is a level nobody can filter on, because filtering it out might lose something important. So a level is a promise, and the promise has to be written down. Figure 2 is ours, with the count of how many of the engine's 92 messages landed at each:

@@FIG_LEVELS@@

Read the six meanings in that figure carefully; two of them do real work.

warn means we recovered. That is the whole distinction from error. If the operation happened — perhaps differently, perhaps worse — it is a warning. If it did not happen, it is an error. This is a mechanical test, not a judgement call, which is exactly what you want from a rule that 92 call sites have to follow.

debug means "what I did", info means "what I am". A texture reporting its size once at load is info — it is a fact about the program that somebody might want on a bug report. A texture reporting each load in a level with four hundred of them is debug: correct, useful when you are investigating loading, and intolerable otherwise.

3.1.1   Who logs a failure?

Now the question that is genuinely contested, and which the engine had been answering inconsistently. A failure happens deep — SDL_CreateGPUTexture returns null — and is reported upward through three or four layers. Which of them writes the log line?

There are two coherent answers, and it is worth stating both before choosing.

Answer A: the caller logs. Whoever decides what the failure means writes the line. Low-level code returns quietly. The argument: only the caller knows whether a missing texture is fatal or a fallback, so only the caller can pick a level honestly.

Answer B: the deepest point that knows why logs, and callers propagate silently. The argument: only the deepest point has the reason — the path, the byte count, the string in SDL_GetError() that is about to be overwritten by the next SDL call. Push the logging upward and every layer boundary loses detail, until the top-level line reads "startup failed" and helps nobody.

We take B, and the deciding argument is about which failure mode is worse. Under A, detail is lost quietly — you cannot tell from the log that it is missing, because the line you are reading looks fine. Under B, the cost is that a caller who recovers from a failure still gets an error line it did not deserve — which is visible, annoying, and fixable by demoting that particular call to debug. A cost you can see beats a cost you cannot.

The rule, and its corollary

Log the failure once, at the deepest point that knows why. Callers propagate silently, and add only the consequence — the thing they know that the callee does not.

In practice that reads like this, and the second line is the whole of what the demo adds:

load_image:  ERROR  "load_image: cannot read assets/uv_grid.png (No such file)"
the demo:   INFO   "texture: uv_grid.png did not load — [T] will do nothing"

Two lines, no repetition, and each says something the other could not. Compare the version where four layers each log "failed": four lines, one problem, and the informative one is at the top of a scroll.

3.2   Why the default costs nothing

Here is the part that decided the whole design, and it came from reading SDL rather than from a design meeting.

SDL keeps a per-category priority table, and it initialises that table from a documented default (SDL_HINT_LOGGING in SDL3/SDL_hints.h, implemented in src/SDL_log.c):

Read *=error again. Every category SDL does not know about defaults to error — and SDL does not know about ours, because SDL_LOG_CATEGORY_CUSTOM is precisely where SDL stops and applications begin.

So the behaviour we want — engine quiet, game loud — is not something we have to build. It falls out of moving the engine's messages off SDL_LOG_CATEGORY_APPLICATION. Figure 3 is the whole mechanism.

@@FIG_DEFAULTS@@

This is worth dwelling on because of what it says about the wrapper question. Lesson 5.2 settled a policy — a wrapper that hides a library you have no intention of replacing is cost with no benefit — and here is that policy paying out. A hand-rolled logging layer would have had to reimplement per-category thresholds, an environment-variable override, and a default table. It would have got a different default table, and the free behaviour above would have been a feature somebody had to think of.

What is left for us is genuinely small: names for our own categories, a compile-time floor SDL cannot provide, and a flag parser. That is the entire content of log.hpp and log.cpp.

3.3   SDL's assertions, and the loop inside them

Figure 4 is §2.3's test drawn as a decision, together with the three macros that follow from it.

@@FIG_ERROR_OR_ASSERT@@

C's assert() prints a message and calls abort(). SDL's does something considerably more interesting, and it is worth understanding before using it, because one of its behaviours will otherwise look like a bug.

An SDL assertion asks a handler what to do, and the handler may answer five ways (SDL3/SDL_assert.h):

SDL_AssertStateWhat SDL then does
SDL_ASSERTION_RETRYre-evaluate the condition, right now
SDL_ASSERTION_BREAKtrip the debugger's breakpoint
SDL_ASSERTION_ABORTterminate
SDL_ASSERTION_IGNOREcarry on, this once
SDL_ASSERTION_ALWAYS_IGNOREcarry on, and never ask about this assertion again

RETRY is the surprising one, and it is not a metaphor. Look at what the macro actually expands to:

It is a while loop over the condition. So RETRY genuinely re-tests: stop in a debugger, fix the state by hand, continue, and the program proceeds as though the bug had not happened. On an assertion that fires on frame 40,000 of a session you cannot reproduce, that is worth a great deal.

And note the static struct SDL_AssertData. It is per expansion site, it carries always_ignore and trigger_count, and SDL threads every one of them onto a list you can walk with SDL_GetAssertionReport(). Two consequences follow, one convenient and one to be careful about:

  • Assertions are testable. Install a handler that returns IGNORE, run the code that should trip, and read the report. §7's harness does exactly this — it proves an assertion fires on the input that should fire it, which most people assume is impossible and therefore never check.
  • ALWAYS_IGNORE latches. It sets a flag in that static, so the assertion fires once and then goes quiet for the rest of the run. That is a feature when you are grinding through a level with a known glitch, and a trap when you are counting.

3.3.1   Which survive a release build — and the gate that decides

SDL picks an assertion level for you unless you set one, and the condition it picks on is not NDEBUG:

__OPTIMIZE__ is defined by GCC and Clang whenever any -O above zero is in effect. So -O2 alone takes you to level 1, where SDL_assert is disabled and only SDL_assert_release survives — with no -DNDEBUG anywhere in sight.

That is the correct behaviour and it is also a trap, because most projects gate their own debug machinery on NDEBUG. Two gates, two different switches. §4.5 is where that mismatch produced an actual bug in this lesson's own code, and §5 measures the four resulting build configurations rather than reasoning about them.

3.4   The shape the engine already had

Back to §1.1's five conventions. The temptation is to design a sixth and convert everything to it. Before doing that, it is worth looking at the five properly, because two of them are the same thing — and they were written a module apart, by nobody trying to match the other.

@@FIG_REPORT@@

obj_report (Lesson 3.5) and gpu_report (Lesson 4.2) are both: a status enum that names the failure precisely, plus the facts you ask for next, plus a bool ok(). That convergence is evidence. Two independent attempts at the same problem reached the same shape because the shape fits the problem, and a design that a codebase keeps rediscovering is a design worth naming rather than replacing.

So the plan is not a new error type. It is:

  1. Name the pattern — status enum, facts, ok() — and write it down as the engine's answer for anything whose failure a caller might branch on.
  2. Convert the odd one out. image_status is the same problem solved worse: a bare enum, with the interesting numbers thrown away. It becomes image_report, and that is this lesson's one end-to-end conversion.
  3. Leave bool alone where it is honest. platform::set_vsync has exactly one failure mode and the caller's only sane response is to log and carry on. A report there is ceremony. A bool is honest when there is nothing more to say.
  4. Kill the fifth convention — "returns false and has already logged" — by making it a documented rule (§3.1.1) rather than a per-function surprise.
The road not taken, honestly

C++23 has std::expected<T, E>: a value or an error, in one return, with no out-parameter and no way to read the value without checking. It is the right long-term answer for a codebase with no exceptions, and we are on C++20, so we would hand-roll it — about 120 lines.

We are not going to, and the reason is not difficulty. It is that the engine has two working instances of a pattern that already solves the problem, and replacing them would mean touching 61 bool-returning functions to gain a type-system guarantee we can get today by reading a [[nodiscard]] warning. Adopt a new abstraction when the old one has failed you, not when the new one is elegant. Exercise 9.5 builds it anyway, because you should know what it costs — and because the day the engine does need it, you will want to have written one.
