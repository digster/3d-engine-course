Module 4 — To the GPU: SDL_GPU · Lesson 4.3

The Shader Toolchain

One HLSL file has to become three different binaries, because Metal, Vulkan and D3D12 do not speak the same language — and then SDL has to be told four numbers about it that only the compiler knows. This lesson builds that pipeline into CMake, and finds out what the tool actually does rather than what its documentation implies.

1The Problem

Lesson 4.2 ended with your rasterizer's picture on screen, carried entirely by SDL_GPU. Every object in the API existed except one, and the reason we could get that far without it is that clearing and copying are things the hardware does without being told how. The moment you want the GPU to compute a colour, you need a program to run on it.

So write one. Here is a fragment shader, in about the smallest form that does anything:

Now hand it to SDL. The signature is the obvious one — SDL_CreateGPUShader(device, &info) — and the trouble starts with what info wants:

Read the first two fields again. code is a pointer to bytes, and format says which kind. Nowhere in this struct is there a place to put HLSL. There is no SDL_GPU_SHADERFORMAT_HLSL, and it is not an oversight:

The gap

A GPU does not run text. Metal wants MSL or a precompiled metallib; Vulkan wants SPIR-V; D3D12 wants DXIL. These are not dialects of one language — they are different binary formats produced by different compilers, and the API that has to work on all three cannot take sides. So SDL takes bytes and asks you which flavour they are.

That means something has to turn one source file into three binaries, and it is not SDL. It is not part of your program either, if you have any sense. It is a build step you do not have yet.

And then there is the second half of the struct, which is stranger. SDL wants to be told how many samplers, storage textures, storage buffers and uniform buffers the shader uses. You wrote the shader; you could count them. But look at what SDL's own FAQ says about that, from the header's overview:

"Another common issue is not setting the correct number of samplers, textures, and buffers in SDL_GPUShaderCreateInfo. If possible use shader reflection to extract the required information from the shader automatically instead of manually filling in the struct's values."

The API's own documentation names this as a leading cause of shaders that do not work, and tells you to have a machine count instead. That is a strong hint, and this lesson takes it — §4.4 shows the numbers being read out of a file the compiler writes. But first, the more interesting question: why is getting them wrong so easy to do and so hard to notice? §5 of this lesson measures the answer, and it is worse than you would guess.

2Building Intuition

2.1Why there is a hub in the middle

Three target formats from one source suggests three compilers: HLSL→SPIR-V, HLSL→DXIL, HLSL→MSL. That is not how it is built, and the reason is the same reason a compiler has an intermediate representation at all.

Writing n front ends and m back ends as n×m direct translators is a quantity of work nobody has ever finished. Put one neutral format in the middle and it becomes n+m. SPIR-V is that middle: a binary intermediate representation for shaders, designed by Khronos, and — importantly — a format with a good decompiler. SPIRV-Cross reads SPIR-V and writes MSL, HLSL, GLSL or a description of what the shader needs.

So the real pipeline has exactly two stages, and only the first is a compiler in the usual sense:

@@FIG_TOOLCHAIN@@

Figure 1 is worth reading for its shape before its numbers. Everything to the right of the hub is translation from SPIR-V. That has an immediate practical consequence that this lesson ran into head first: if the front end is missing, you do not lose one backend — you lose all of them, because there is no SPIR-V for the second stage to work from.

The numbers say the same thing from the other side. The HLSL→SPIR-V hop measured 12.3 ms and each SPIR-V→anything hop measured 1.5 ms. The front end is doing eight times the work of a translation, because it is the part that has to parse a language, resolve types, and optimise.

2.2Offline, and what that actually buys

SDL_shadercross ships as both a library and a command-line tool, so this pipeline can run inside your program at startup instead of at build time. That is genuinely convenient — edit a shader, relaunch, see it — and this course does not use it. The reason is worth stating precisely, because the obvious reason is wrong.

It is not about time. Compiling all four of this lesson's shaders through all three hops takes 61.2 ms. You could do that at every launch and no user would notice.

It is about what you would have to ship, and what could fail:

  • The compiler goes in the box. Runtime translation means shipping SPIRV-Cross — 6.7 MB on this machine — and, for HLSL input, DirectXShaderCompiler, which is a fork of LLVM. That is a large dependency to carry so that every copy of your game can redo a computation whose answer never changes.
  • A compile can fail on someone else's machine. An offline build fails on your machine, where you can read the message. The same failure at a customer's launch is a black screen and a bug report that says "it does not work".
  • You cannot inspect what you did not produce. When the picture is wrong, being able to open the generated MSL and read it is worth a great deal — §5.4 does exactly that to catch a renamed function.

So: compile offline, ship binaries, and keep the tool on the developer's machine. Runtime cross-compilation is the right answer for a shader editor, a material system with user-authored nodes, or a tool that must accept shaders it has never seen. It is the wrong answer for a game that knows its own shaders at build time.

2.3The tool, honestly described

SDL_shadercross is a separate libsdl-org project from SDL itself, and this lesson has to be careful about how it describes it, because the description that would be convenient is not accurate.

⚠ Verify

Checked while writing this lesson, and worth re-checking rather than trusting: the installed headers declare SDL_SHADERCROSS_MAJOR_VERSION 3, and the packaged metadata says Version: 3.0.0. But the upstream repository has no tags and no releases at all.

This matters practically. Our CMakeLists.txt pins SDL with GIT_TAG release-3.4.12, and the comment beside it says "never a branch name". You cannot do that here, because there is no tag to name. Pin a commit SHA instead — it is exactly as reproducible and rather less pretty. If you find tags have appeared since, prefer them.

Two more facts about the tool that follow from how it is built, and that decide what your machine can do:

  • It is two libraries in a coat. HLSL→SPIR-V is DirectXShaderCompiler; SPIR-V→everything is SPIRV-Cross. Both are optional at build time.
  • A build without DXC cannot read HLSL at all. Not "cannot produce DXIL" — cannot read the source language. The machine this lesson was written on has exactly such a build, and asking it to compile our vertex shader produces: ERROR: Failed to compile SPIR-V From HLSL: Shadercross was not built with DXC support.

That is not a disaster, and it is not a reason to write the lesson around a machine that does not exist. The first hop is a job several tools can do — glslc, from Google's shaderc, compiles HLSL to SPIR-V with one flag — so §4.2 builds a CMake step that asks the tool what it can do and picks a route accordingly. Which is a better habit than the one it replaces, so the accident is worth keeping.

3The Theory

3.1Register spaces, and why they are not yours to choose

In HLSL you declare where a resource lives with a register annotation: t0 for the first texture, s0 for the first sampler, b0 for the first constant buffer, and a space to disambiguate. Under SDL_GPU the space is not a free choice. The header states the layout, and it differs per stage:

@@FIG_SPACES@@

The four rows of Figure 2 are the whole rule, and the right-hand column is what makes them checkable. When HLSL is compiled to SPIR-V, a register space becomes a descriptor set, and SDL's SPIR-V rules are stated in those terms — vertex uniform buffers in set 1, fragment textures in set 2, fragment uniform buffers in set 3. So the two halves of the header's documentation are one rule wearing two notations, and you can confirm your own shader landed correctly with a disassembler:

The texture and its sampler landed in set 2, the constant buffer in set 3 — which is what space2 and space3 in the source asked for, and what SDL requires of a fragment shader. Nothing here was taken on trust.

The failure mode, and why it is nasty

Put a fragment shader's constant buffer in space1 instead of space3 and everything still works: it is valid HLSL, it compiles, it translates, it loads, and it runs. At which point it reads whatever happens to be bound at the slot it named — usually nothing, sometimes the vertex stage's data.

There is no error anywhere in that chain, because every stage did what it was told. The symptom is a shader that returns black, or a constant that never changes. Check it with the disassembler above, at the moment you write the declaration, rather than debugging it later from the picture.

3.2Semantics, and the one that is different

HLSL attaches a semantic to every value crossing a stage boundary — the : TEXCOORD0 after a field. They exist because D3D matches a vertex buffer's contents to a shader's inputs by name rather than by position, and SDL_GPU has to say something about them since it targets D3D12 too:

"Shader semantics other than system-value semantics do not matter in D3D12 and for ease of use the SDL implementation assumes that non system-value semantics will all be TEXCOORD. If you are using HLSL as the shader source language, your vertex semantics should start at TEXCOORD0 and increment like so: TEXCOORD1, TEXCOORD2, etc."

So the practical rule is short: name every user-defined input and output TEXCOORDn, numbered from zero, in order. The names carry no meaning — a normal is not more "TEXCOORD" than a colour is — and the numbering is what actually binds. Skip a number and the attribute that arrives is not the one you meant.

System-value semantics are the exception, and they are the ones that do mean something. SV_Position names the clip-space position the rasterizer itself consumes — the vec4 our vertex pipeline has been producing since Lesson 2.10, complete with the w that Lesson 2.7 spent a lesson explaining. SV_Target0 names the first colour attachment of the render pass. These are not conventions you may rename; they are how the shader talks to the fixed-function hardware around it.

3.3The four counts

Now the fields SDL's FAQ warns about. Why does SDL need to be told what the shader plainly contains?

Because SDL does not read your shader. It receives an opaque blob in one of three formats and passes it to a driver. Parsing DXIL to count its registers would mean shipping a DXIL parser inside SDL, and doing the same for SPIR-V and MSL, for a fact the application already knows. So the API asks. The counts let SDL size the descriptor sets and validate the bindings you later make against what the shader claims to want.

Which raises the obvious question: what happens if you lie? Here is textured.frag, which genuinely has one sampler and one uniform buffer, created four times with four different sets of counts:

@@FIG_COUNTS@@

Figure 3 is that experiment, and all four were accepted. Ninety-nine samplers on a shader with one — created, no error, no warning. So SDL_CreateGPUShader validates nothing here, and the mistake the FAQ calls common is a mistake nothing in the creation path will catch for you. The damage shows up later, when something binds resources against a count that does not describe reality.

That is the argument for reflection, and it is not "it saves typing". It is that there is no other check. Every other error in this lesson is caught by something — a bad register space by the disassembler, a wrong entry point by SDL itself, a missing file by the loader. This one is caught by nobody, so the number must come from a machine that read the actual compiled code.

Which shadercross will do, in the same run that compiles the shader:

Worked example — counting by hand, and then checking

Count the resources in textured.frag.hlsl yourself before reading on. The file declares:

  • Texture2D<float4> albedo : register(t0, space2) — one sampled texture, which pairs with…
  • SamplerState albedo_sampler : register(s0, space2) — …one sampler. SDL counts the pair once, as num_samplers = 1.
  • cbuffer Tint : register(b0, space3) — one uniform buffer.
  • No storage textures and no storage buffers: those are the read-write resources of Module 9's compute work, and nothing here declares one.

So by hand: smp 1, tex 0, buf 0, uni 1. And the reflection file says samplers 1, storage_textures 0, storage_buffers 0, uniform_buffers 1. They agree — for all four shaders, as §B of the harness checks.

The agreement is the point, and so is doing it anyway. Hand-counting is right today and wrong the first time somebody adds a texture and forgets the struct. The file is regenerated by the build every time the shader changes, which is a property no amount of care gives you.

3.4The entry point you did not write

One field of the create-info remains, and it is the one that fails first for most people. entrypoint is the name of the function to call. Our HLSL says:

So the entry point is "main". Except that on this machine, it is not:

@@FIG_ENTRY@@

Figure 4 is the answer, and the top row is the cause: main is a reserved identifier in Metal Shading Language — MSL is C++-derived, and main means something there. SPIRV-Cross therefore renames it on the way through, and the generated MSL declares vertex main0_out main0(main0_in in [[stage_in]]). Pass "main" and SDL asks Metal for a function that does not exist.

The good news is in the bottom half of Figure 4: this failure is caught at creation. "main0" created a shader; "main" and a deliberate nonsense name were both refused, with SDL logging Creating MTLFunction failed. Compare that with §3.3's silent acceptance of nonsense counts and you have the two halves of this API's temperament in one page: it checks the name and not the numbers.

The ninety-percent picture

The rename is a property of the SPIRV-Cross MSL backend, not a law of nature, and the missing ten percent is that other paths differ: a metallib compiled by Apple's own tools keeps whatever name its source used, and the SPIR-V path keeps main because SPIR-V has no reserved words. Our loader therefore ties the entry point to the format rather than to the shader, which is the only place the knowledge belongs.
