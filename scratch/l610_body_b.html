3The theory

3.1  Building the chain

Level 0 is the image. Level k+1 is level k with every 2×2 block replaced by its average, so each level is half as wide and half as tall. The chain stops at 1×1, which takes 1 + ⌊log₂(max side)⌋ levels — nine for a 256-square image, ten for 512.

Two details that only bite on textures that are not square powers of two:

  • Stop when both axes reach 1, not either. A 64×4 texture halves to 32×2, 16×1 — and if you stop there, you have thrown away four more halvings of width. The harness checks that a 64×4 strip reaches 1×1 in seven levels.
  • Odd sizes round down and lose a row. Real engines box-filter with weights that account for it; the difference is invisible and the code is twice as long, so this is the ninety-percent picture and the missing ten percent is a weighted resample.

3.2  Choosing the level

Level L has texels 2L times as wide as level 0, because each level halved them. We want the level whose texel is about the size of the footprint, so

\[ 2^{L} = \rho \qquad\Longrightarrow\qquad L = \log_2 \rho \]
2^L = footprint_in_texels  ⟹  L = log2(footprint_in_texels)

where ρ is the footprint measured in level-0 texels. The logarithm is not a trick — it is the direct consequence of the pyramid halving at each step, which is why the formula has no constants in it to tune.

@@FIG_LEVEL@@

Worked example. Push 3.9's own measurement through it.

That lesson measured 62.46 texels per pixel two rows below the horizon. So

L = log2(62.46) = 5.965

Level 5 of a 256-texture is 8×8; level 6 is 4×4. So the right answer is "level 5, almost all the way to level 6" — and the harness confirms mip_level_for returns 5.965 for that footprint.

Note what the level being fractional is telling you: there is no level whose texels are exactly 62.46 across, because the chain only offers powers of two. That fraction is precisely what trilinear filtering interpolates, and it is why the function returns a float rather than an int.

ρ is the longer of the two axes, and that one word is the whole of why plain mipmapping over-blurs. Taking the longer guarantees no aliasing along either axis, at the cost of blurring the shorter one. Taking the shorter would keep the detail and alias. Hold that thought until §3.6.

And magnification — ρ < 1, a pixel covering less than a texel — clamps to level 0. There is no level −1, and the honest answer is that the image simply has no more detail to offer.

3.3  The derivative, on a renderer with no neighbours

Now the part that is genuinely CPU-specific, and the reason 3.9 could measure the footprint in a demo but not compute it in the fill loop.

@@FIG_GRADIENT@@

A GPU shades fragments in 2×2 quads. That is not an efficiency detail — it is why ddx and ddy exist: the neighbouring fragment's value is right there, so a derivative is a subtraction. (It is also why those functions cannot be called from divergent control flow: the neighbour might not have taken your branch.)

Our rasterizer walks a scanline one pixel at a time. The row above was finished and thrown away; the pixel to the right has not been computed. There is nothing to subtract. So the derivative has to come from the triangle, analytically — and it turns out to be both exact and nearly free.

Recall from Lesson 3.2 that perspective-correct interpolation computes

\[ u(x,y) \;=\; \frac{U(x,y)}{W(x,y)}, \qquad U = \sum_i f_i \frac{u_i}{w_i}, \qquad W = \sum_i \frac{f_i}{w_i} \]
u = U / W, with U = Σ f_i·(u_i/w_i) and W = Σ f_i·(1/w_i)

Both U and W are affine in screen space, because the normalised barycentrics fi are — they are edge functions, which are linear in x and y by construction (Lesson 2.2). An affine function has a constant gradient. So the quotient rule gives, per screen axis,

\[ \frac{\partial u}{\partial x} \;=\; \frac{\dfrac{\partial U}{\partial x} - u \cdot \dfrac{\partial W}{\partial x}}{W} \]
du/dx = (dU/dx − u · dW/dx) / W

and every ingredient is already lying around:

Where each term of the gradient comes from
TermWhere it already exists
df_i/dx step_x0/1/2 · inv_area — the edge increments the fill already walks, over the area it already reciprocated
dU/dx, dW/dx a weighted sum of those, constant over the triangle, so hoisted out of the pixel loop entirely
u the fragment's uv, which the loop just computed
1/W w_recip — the reciprocal Lesson 3.2 already pays one divide for

So the per-pixel cost is two multiplies and a subtract per axis, and only when a chain is bound. Everything else hoists.

It is exact, and the test says so

This is a closed form, not an approximation — which is a stronger claim than "it looks right", so it deserves a stronger test than looking at it. §D of the harness computes the gradient analytically and then computes a central difference of the real perspective-correct interpolation at the same point, on a triangle with genuinely different w at each vertex so the divide actually bends things.

They agree to 5.79 × 10−6, which is the finite difference's own truncation error rather than a disagreement. A test that only checked the analytic form against itself would have proved nothing.

3.4  The bug that makes things darker

Now the trap, and it is worth meeting with real numbers because "average in linear light" is advice that is very easy to nod at and not act on.

Take one 2×2 block of a black-and-white checker: two texels at code 255, two at code 0. What should their average be? Half the light — one of the two texels is emitting all of it and the other none, so the block as a whole emits half.

Lesson 6.1 established the two integers that answer this. Code 128 is not half the light; it is 0.2159 of it. Half the light is code 188. So:

@@FIG_LINEAR@@

Worked example. The two ways, side by side.

naive: (255 + 0 + 0 + 255) / 4 = code 127 → 0.2122 of white
correct: decode → (1 + 0 + 0 + 1)/4 = 0.5 → encode → code 188 → 0.5029 of white

The naive answer delivers 0.2122 / 0.5029 = 42.2% of the light it should. That is 57.8% too dark, at level 1, on one block.

And it compounds. Level 2 averages four level-1 texels that are already too dark, so the error accumulates down the chain — which is why the symptom is not "textures are dark" but "textures get darker with distance", and why it is so often mistaken for a lighting falloff problem.

Read the space from the data, not from a parameter

build_mips decides by asking the texture: texel_space::srgb decodes, texel_space::linear averages the bytes directly. That field exists because Lesson 6.7 needed normal maps to stop being decoded as colour, and it pays for itself again here — a roughness map or a normal map is linear data, so averaging its bytes is the correct operation rather than the lazy one.

Making it a parameter would put the decision back at the call site, which is exactly where 6.7 took it from. A caller who has to remember which of their textures is colour will get the third one wrong.

Alpha is averaged as bytes on both paths, incidentally: it is a coverage fraction rather than a colour, so it was never sRGB-encoded, and decoding it would be a second bug hiding behind the fix for the first.

The GPU gets this right for free, and it is worth knowing why

SDL_GenerateMipmapsForGPUTexture does not need telling about colour spaces, because the texture was created with an _SRGB format. The hardware decodes on read and encodes on write, so the blit chain that generates the levels is already averaging in linear light.

That is the clearest case in this course of a format flag doing real work: the same correctness the CPU path arranges by hand in twenty lines is, on the GPU, a consequence of having declared what the data means.

3.5  Trilinear, and a seam you have met before

The level is fractional and the chain is not. Round it, and every fragment on one side of an invisible line reads an image twice as detailed as the fragment next to it — so the line becomes visible, running across the floor at a fixed distance from the camera.

This is Lesson 6.9's cascade seam. Same cause: two representations of the same surface, each defensible, meeting at a boundary and disagreeing. Same cure: blend across it. Bilinear within a level, linear between two levels — trilinear.

The harness sweeps a footprint across a level boundary and measures the largest single-step change:

nearest: 0.3470   ·   trilinear: 0.0124   —   28× smaller

A 0.347 jump in one step of camera distance is a hard edge; 0.0124 is a gradient. The cost is one extra bilinear fetch, which is why trilinear is the default everywhere and mip_filter = nearest exists mainly so you can see what it is for.

3.6  Anisotropy: refusing to choose

Back to the word "longer" in §3.2. Consider a floor seen at a grazing angle. Moving one pixel across the screen moves you a long way across the texture; moving one pixel up the screen moves you much further still, or much less, depending on the geometry. The footprint is a long thin ellipse, not a circle.

@@FIG_ANISO@@

Take the harness's case: 32 texels along one screen axis, 2 along the other — a 16:1 ratio.

  • Choose by the long axis (32 texels ⟹ level 5). No aliasing, but the short axis only needed level 1, so it is blurred by a factor of 16. This is why distant ground in a game without anisotropy looks like it has been smeared.
  • Choose by the short axis (2 texels ⟹ level 1). The detail survives, and the long axis aliases exactly as it did before we started.

Anisotropic filtering refuses the choice. Take the level the short axis asked for — so no detail is thrown away — and then take several samples along the long axis and average them, which supplies the averaging the long axis needed. The number of samples is the ratio, clamped: "16× anisotropic" is that clamp, and it is why the setting is quoted as a number rather than on/off.

It costs only where it buys

On a square footprint the ratio is 1, so there is no long axis and the code takes a single tap. The harness checks this rather than assuming it: with max_anisotropy = 16 and a 1:1 footprint the result is identical to the isotropic one to six decimal places.

That is worth verifying because the failure would be invisible and expensive — sixteen taps of the same place, on every surface facing the camera squarely, which is most of them.
