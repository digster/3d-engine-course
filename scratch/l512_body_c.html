7.1 One word, two conventions

The first thing the game had to get right, and the first thing it got wrong — three times. The arena came out a quarter of its intended area with the pillars floating beside it in the void, which reads as a camera bug for a good ten minutes before it reads as what it is.

@@FIG_UNIT@@

cube_mesh()'s eight corners are at ±0.5, so a transform's scale is the box's full size. icosahedron_mesh()'s twelve vertices are at distance 1.0, so its scale is a radius. Both are documented and both are reasonable in isolation; together they mean that scale = 1 gives you a one-metre cube and a two-metre ball.

The trap is not the asymmetry, it is that a half-extent is exactly what the rest of the program wants. A collision test wants a half-extent. debug_lines::box takes a half-extent. So the value you have in your hand is the wrong one by a factor of two precisely when you reach for scale. The game's answer is one four-line function, and the factor of two is the entire content of it:

The third instance is the one that survived longest, because it looked plausible. A pillar's debug box is drawn through its world matrix — which already carries the scale — so the half-extent passed alongside it is in the cube's own space, where it is 0.5 by definition. Passing metres draws a box exactly twice the size of the thing it outlines, and a box slightly too big around a collision proxy looks like a deliberate margin.

7.2 The order the step runs in, and the one line that must not move

Five systems, and four of them could run in any order. The fifth cannot:

pickup_system tests distances in world space, and six of the twelve orbs are children of a carousel that carousel_system just turned. Put the resolve after the pickup and every riding orb is tested against where it was last step. At 0.45 rad/s and a radius of 4.0 m that is 3 cm of error per step — far too small to see, and far too small to blame on anything. It would present as “the moving orbs are slightly harder to catch than the still ones”, which is a sentence a designer would try to fix by changing the pickup radius.

Symptom → cause → fix

Symptom: a moving object's interactions feel subtly, inconsistently late.
Cause: a system read world_transform before the hierarchy resolved it this step, so it read last step's composition.
Fix: one resolve, after everything that writes a local transform and before everything that reads a world_transform. If you cannot arrange that, you need two resolves and you should say why in a comment.

The other ordering constraint is inside pickup_system and the ECS tells you about it rather than letting you find out: view::each asserts if its lead pool changes during iteration, so an orb cannot be destroyed inside the lambda that found it. Collect ids into a scratch vector, destroy after. That is a restriction the ECS chose deliberately in 5.8, and it is the good kind — a guaranteed assertion instead of an iterator that is sometimes fine.

8. What the game could not find

Seven findings. Two are fixed in this lesson and five are not, and the five are more useful than the two — a gap you have named and dated is a gap that stops surprising you.

@@FIG_FINDINGS@@

8.1 There is no collision, and the wall is a lie

The rover stops at the arena edge because six lines of arithmetic in drive_system clamp its position. There are four kerbs drawn at that edge, and they are scenery — nothing tests against them, and if you deleted them the rover would still stop. The wall is a picture of a rule enforced somewhere else.

Meanwhile the eight pillars have no clamp, so you drive straight through them. Press G and you can see exactly what is missing and exactly what is not: every pillar is outlined with an oriented box, drawn from the same world matrix a collision test would use. The geometry is present, correctly placed, and already in the ECS. That is why struct pillar is a tag with no data in it — a unit cube under a world_transform is an oriented bounding box, so storing the half-extent a second time would only have created a copy that drifts.

What is missing is not the data. It is the solver — and the gulf between the pickup test and a pillar response is the whole of Module 8. A pickup needs a boolean: are these two spheres overlapping. A pillar needs a contact point, a normal, a penetration depth, and a response that slides rather than sticks, applied one normal at a time so that a corner does not stop you dead in both axes at once. That is why the easy one is in the game and the hard one is thirteen lessons away.

And the quadratic nobody can see

pickup_system is O(rovers × orbs). There is one rover and there are twelve orbs, so the quadratic is hidden by the constants — which is exactly how this shape survives into a shipped game and then falls over on the level with four hundred pickups. Lesson 8.9's uniform grid is the answer; naming it here is cheaper than discovering it later.

8.2 The engine cannot put a character on the screen

A game has to say “8 of 12”, and “0:43”, and “you won”. Search engine/ for a font, a glyph, or a text call: there is nothing. So the HUD is drawn by SDL, with SDL_RenderDebugTextFormat and its built-in 8 × 8 bitmap font — a debugging facility that happens to be in the window.

Three consequences follow, and they are why this is a finding rather than a shrug:

  1. It exists only on surface::renderer. A --shot run is headless and has no SDL_Renderer, so the expected result in §11 is a picture of the game with no score on it — the number you most want is the one thing missing.
  2. It is unavailable on the GPU path for the same reason, so the engine's real renderer is the one that cannot show a number.
  3. It is not composited with the world. It is drawn on top, by a different renderer, at a different scale — so it cannot be tinted, faded, placed in the scene, or measured.

Dear ImGui does not rescue this, and the reason is the one Lesson 5.11 gave when it integrated ImGui in the first place: ImGui is tooling. A panel of live counts for a developer is exactly what it is for; a player-facing scoreboard is not. Using it for the latter would be shipping a debug library as a product feature, which is a decision that is very hard to walk back.

8.3 A pickup is silent

The single most conspicuous absence when you actually play it. Collecting an orb is the only thing the game rewards you for, it takes about a second to set up, and it produces no sound, because SDL3's audio-stream model arrives in Lesson 7.8 and the engine has no audio layer at all. This one needs no analysis; it is recorded because a checkpoint's job is to record what it found, and “the game feels dead” is a finding even when the cause is obvious.

8.4 There is no public path from an entity to the GPU renderer

The one that decided how this game is rendered. gpu_scene_renderer::render consumes gpu_draw_items; the ECS produces components; and no public function connects them. sandbox crosses that gap, in about seven hundred lines, inside its own main.cpp — which is why nobody had noticed: the only program that ever crossed it was written before the boundary existed and keeps its bridge to itself.

So collector renders on the CPU, through the software rasterizer, like every program written from outside the boundary since the refactor. That is a sentence worth sitting with. Three lessons after moving the renderer to the GPU, the GPU renderer is the one a game cannot reach. Module 9's renderer facade is where this is answered, and §5's collect_renderables is deliberately shaped so that the GPU version is a sibling function rather than a redesign.

8.5 view() has no const overload

A small one with a wide blast radius. Look at the signature this lesson had to write:

That first parameter is a mutable reference and the function writes nothing through it. registry::view() is non-const and ecs::view hands out Ts&, so there is no way to spell “I am going to walk this registry and change nothing”. Every read-only system in this engine has to ask for write access it will not use, and const stops being able to tell a reader anything.

The fix is the one EnTT reaches for — allow view<const renderable> and propagate the constness into each's parameters — and it is a genuine change to two published headers, so this lesson reports it instead of smuggling it in. The signature is left looking wrong on purpose, with the reason in its doc comment: a comment nobody reads is a worse bug report than a parameter everybody trips over.

8.6 A program cannot name its own log category

The smallest finding, and it half-works in an interesting way. Lesson 5.3's five categories name engine subsystems, and correctly so — a category called log_app inside the library would be the library naming something it knows nothing about. What makes the game's own category possible anyway is the last member of that enum:

log_category_count is documented as “not a category; the count, for iteration”, and it is also exactly where a program's own categories begin — an enum that publishes its own end leaves room after it. The half that does not work: the --log spec is parsed against name_of(log_category), which returns "?" for anything outside the five, so this category can be filtered in code and cannot be named on the command line.

Which is why the --shot summary is a printf and not a log call at all. A log is a diagnostic: off by default, filtered, aimed at whoever is debugging. The shot's summary is the program's output, and a tool whose result only appears if you pass the right --log spec is a tool with a trapdoor.
