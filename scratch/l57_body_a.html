Module 5 — Becoming an Engine · Lesson 5.7

An ECS from Scratch: Storage Design

Lesson 5.6 measured what a scene layout costs and came out with three constraints an ECS has to satisfy — dense and compactable, systems that declare what they touch, no virtual dispatch on the hot path. It then refused to choose between the two designs that satisfy all three, because nothing it measured distinguishes them. Both are dense. Both are contiguous. Both let a system touch a subset. This lesson takes the measurement that does distinguish them — and it takes it before either is built, because the two designs differ in exactly two operations and both of those can be simulated in three hundred lines. Then it chooses, argues the choice from the numbers, and states plainly the scene at which the choice becomes the wrong one.

1The Problem

Lesson 5.6 ended by handing this lesson three constraints, each with a number attached: storage must be dense and compactable (a decayed pointer tree cost 6.47× a flat array at 100,000 objects); a system must declare which components it touches (a loop reading 12 of 96 bytes ran 5× faster when the other 84 were stored elsewhere, and a loop reading 60 of 96 gained nothing); and iteration must not be virtual (a flat 1.5–1.7× at every size, including four objects sitting in L1).

Those constraints are real and they were earned. They also do not decide anything, and 5.6 said so on its last page. The two storage designs that every production ECS is built out of both satisfy all three:

The two candidate ECS storage designs and the engines that use each.
designthe idea in one sentenceused by
Archetype Entities with the same component set are stored together, so the components a query wants are parallel dense arrays walked by one shared index. Unity DOTS, Flecs, Unreal Mass
Sparse set Each component type gets one dense array, plus a sparse map from entity to position in it; a query walks one pool and looks the rest up. EnTT

Both are dense. Both are compactable — each keeps its live data packed and moves the last element into any hole. Both let a system name the components it touches and fetch nothing else. Neither uses a virtual call to iterate. Every number 5.6 published applies equally to both, which is exactly why 5.6 was told not to let this lesson inherit them.

The trap this lesson is built to avoid

There is a third way to decide, and it is the one that would be easiest here: we already own something shaped like a sparse set. Lesson 5.4's pool<T> has exactly three arrays — slots_ sparse and stable, items_ dense and packed, owners_ the way back — which is a sparse set with generations bolted on. Adopting sparse sets because that is what is lying around is choosing an architecture by what is convenient, and §3.4 explains why the resemblance is a hint and not an argument.

So this lesson does what 5.6 did: it measures. The unusual part is when. Normally you cannot compare two architectures without building both, which costs weeks and produces a sunk cost that then argues for itself. Here you can, because the two designs differ in exactly two operations — reading K components of every matching entity, and adding or removing one component from one entity — and both of those are access patterns that fit in a few hundred lines with no entity manager, no component registry, no type erasure and no scheduler around them. Everything else about the two designs is orthogonal to the question.

Five measurements follow, and one of them changed the recommendation from "sparse set, reluctantly, because it is less code" to "sparse set, confidently, because the migration only runs one way". No engine source changes this lesson; the output is a decision, and 5.8 builds it.

2Building Intuition

2.1What a query actually is

Strip away the vocabulary and an ECS does one thing over and over: for every entity that has all of these components, run this code on them. That is a query, and the engine's existing render loop already is one — it walks four scene_objects and, for each, reads a transform and a mesh handle. Written as a query it would say: for every entity with a transform and a mesh, build a model matrix and submit a draw.

Two numbers describe any query and they are the two axes of everything below. K is how many component types it names — one for "advance every particle's age", four for a render query that wants a transform, a mesh, a material and a bounding volume. The selectivity is what fraction of the world matches: a transform query matches everything, a "has a rigid body and is asleep" query matches almost nothing.

The reason those two numbers matter is that they are precisely where the two designs pull apart. Reaching K components is cheap for an archetype and costs a lookup per extra component for a sparse set. Matching a small fraction is cheap for an archetype, which never visits a non-matching entity, and awkward for a sparse set, whose dense arrays hold everything. So before any measurement: we should expect the archetype to win the query, and the interesting question is by how much, at what size, and what it charges for the privilege.

2.2The two answers, as memory

Draw both and the difference is one column wide.

@@FIG_SHAPES@@

The archetype's arrangement is a promise about identity: row i of the transform column and row i of the material column are the same entity, and that is true because the chunk was built to make it true. Every entity in the chunk has exactly the same component set. An entity with a transform but no material is not in this chunk; it is in another one, with its own columns. The consequence is that a query touching four components is four sequential streams and one loop counter — no lookups, no branches, no possibility of a miss that was not going to happen anyway.

The sparse set makes no such promise. Each component type owns one dense array holding every instance of that type in the world, in whatever order they were inserted. To find entity 17's velocity you read velocity.sparse[17], which gives an index into velocity.data. The dense array is still dense — 5.6's first constraint is satisfied — but its order is nobody's business, and in particular it is not guaranteed to be the same order as the transform pool's.

The sparse array is bigger than it looks

Note what sparse is indexed by: the entity id. So it has one slot for every entity that exists, not for every entity that has this component. A world with 100,000 entities of which 200 are lights still pays 400 KB for the light component's sparse array. §3.3 puts a number on that, and it is the sparse set's real structural cost — the one that is almost never quoted alongside the query ratios.

2.3The redirect, and why it is not a linked list

The instinct after Lesson 5.6 is alarm. sparse[e] and then data[idx] is a load whose address comes out of another load — the exact shape that made a linked list cost 6.47× while an array of pointers cost 2.38×. If a sparse-set query is a linked list, the argument is over before it starts.

It is not, and 5.6 already contains the reason. What made the linked list catastrophic was not the indirection; it was that the next address was inside the current node, so nothing could be issued until the previous miss returned and the latencies added up in series. An array of pointers, by contrast, has all its addresses available immediately, so a core can have a dozen dependent loads outstanding at once and the misses overlap. That is memory-level parallelism, and it is the whole difference between 2.4× and 6.5×.

@@FIG_REDIRECT@@

A sparse-set query is the second picture, twice over. The loop reads xf.dense[i] sequentially, so entity ids arrive by the cache line — sixteen at a time — and each one starts an independent two-deep chain. Nothing in entity 17's chain has to wait for entity 4's. So the cost is bounded by how many chains the core can keep in flight, not by the number of entities times the memory latency.

That reframes the question usefully. The redirect is latency, not bandwidth, and latency is the kind of cost a machine is good at hiding — if there is something else for it to be doing. Which raises the question §4.4 exists to answer: how much work does the body of the query do? If a system reads four components and does thirty nanoseconds of arithmetic per entity, several extra loads may cost literally nothing. If it does two nanoseconds, they will not.

3The Theory

3.1Four operations, and the two that differ

An ECS runtime has to be good at four things. Writing them down first is what keeps the comparison from becoming an argument about which design is nicer.

The four operations an ECS runtime performs, with each design's asymptotic cost.
operationarchetypesparse setdiffers?
Create / destroy an entity append a row / swap-and-pop append to each pool / swap-and-pop each no — both O(components)
Get one component of one entity two lookups: which archetype, which row one lookup: sparse[e] marginally, and both are O(1)
Query K components walk K parallel arrays, one index walk one array, K−1 redirects yes — §5.1
Add / remove a component move the entity to another archetype push or swap-and-pop in one pool yes — §5.3

Two rows out of four are identical in shape, which is worth noticing on its own: most of what an ECS does, both designs do the same way. The entire architectural argument lives in the other two rows, and they point in opposite directions — the archetype is faster at the one that happens thousands of times per frame, and the sparse set is faster at the one that happens when something spawns, dies, gets picked up, catches fire or goes to sleep.

Which means the answer cannot be a ratio. It has to be a rate comparison: how many queries per frame against how many structural changes per frame, weighted by what each costs. That is the shape of the decision, and §6 does the arithmetic with the measured numbers.

3.2What a structural change costs, on paper

Predict before you measure — a wrong prediction is worth more than no prediction, and this one turns out to be wrong in an instructive way.

@@FIG_MOVE@@

An entity gains a component. In the archetype design its component set just changed, so by definition it no longer belongs where it is: it must move from the chunk for {transform, velocity, bounds} to the chunk for {transform, velocity, bounds, material}. Everything it owns travels. Then the source chunk has a hole in it, which swap-and-pop fills by moving its last row down — so a second entity's data moves too, and that entity's row index has to be patched.

Worked example — the byte count

Our probe's entity carries a transform (60 B), a velocity (16 B) and a bounds (16 B), which is 92 bytes that must travel, plus a 16-byte material constructed at the destination.

Copy 92 B into the destination chunk. Move 92 B within the source chunk to close the hole. Write two index entries. Call it ≈ 200 bytes touched.

Now widen the entity to twelve components — eight more at 16 B each. The travelling payload becomes 92 + 128 = 220 B, and the total ≈ 456 bytes. So the byte model predicts the wide case costs 456 / 200 = 2.3× the narrow one.

Measured, at 100,000 entities: 13.10 ns narrow, 58.48 ns wide. That is 4.5×, twice what the model says.

The model is not merely imprecise, it is measuring the wrong thing, and the correction is worth having because it generalises. A column is a separate allocation. Eight extra components are eight more std::vectors, in eight unrelated places in the heap, and a move has to touch each of them twice — once to read the entity's row and once to move the chunk's last row into the hole. That is sixteen additional independent memory touches, most of them missing at this working-set size. 45.4 ns for sixteen touches is 2.8 ns each, which is about right for a partially-overlapped access to memory on this machine.

So the cost model is not "bytes moved", it is independent memory streams touched, and the count of those is two per column, per move. Write it down, because it is the sentence the decision rests on: an archetype's structural change costs a fixed price per component the entity has, whether or not that component has anything to do with the change.

The sparse set's version of the same operation is one paragraph shorter and that is the point. Push the component onto material.data, push the entity id onto material.dense, write material.sparse[e]. Three writes, two of them to the end of arrays that are already warm because the last insert touched them, and nothing else in the world is read or written. The entity's transform, velocity and bounds are not merely left alone; they are not known about. The cost has no term for how wide the entity is because the operation has no way to find out.

3.3What the index costs, on paper

The sparse set pays for that O(1) somewhere, and the bill arrives in memory. Per component type it keeps a dense array of entity ids (4 B per entity that has the component) and a sparse array of indices (4 B per entity in the world, present or not). The archetype keeps one entity id per row and nothing else.

Worked example — index overhead at two scales

Our probe: 100,000 entities, 4 component types, all present on all entities. Payload is 60 + 16 + 16 + 16 = 108 B each = 10.8 MB. Archetype adds 4 B per entity for the id: 400 KB. Sparse adds 4 B per type for the dense id and 4 B per type for the sparse slot: 8 × 4 × 100,000 = 3.2 MB. Overhead over the archetype: 25%.

A real game: 100,000 entities, 32 component types, of which an average entity has 6. The archetype still adds 400 KB. The sparse set's dense arrays scale with what is actually present — 6 × 4 × 100,000 = 2.4 MB — but its sparse arrays are indexed by entity id and so are sized by the world, not by the component: 32 × 4 × 100,000 = 12.8 MB, of which roughly 80% is the value meaning "this entity does not have this component".

Twelve megabytes of mostly-nothing is not a rounding error; it is three times this machine's L2. This is why EnTT pages its sparse arrays — allocating them in 4,096-entry blocks and only materialising a block when something in its range gets the component — which costs one more indirection on every lookup to save the memory.

Whether this course needs paging is a question with a pleasant answer, and it is another dividend from Lesson 5.4. A sparse array's size is set by the highest entity id ever issued, and 5.4's pool<T> issues indices from a free list, reusing the most recently freed slot first. So the id space stays compact: its high-water mark is the largest number of entities that were ever simultaneously alive, not the number ever created. At ten component types and a ten-thousand-entity high-water mark that is 400 KB of sparse array in total, and paging would be complexity spent on nothing.

…with one failure mode, and it is the same one 5.4 documented

High-water marks do not come back down. A level that spawns a million particles as entities and then destroys them leaves a million-slot sparse array per component type for the rest of the process — 4 MB each, whether or not anything is alive. 5.4 said the same thing about slots_, and the answer is the same: things that exist in millions and die in seconds should not be entities. A particle system owns its own array and is one entity.

3.4The one we already own, and why it does not decide this

Look again at what Lesson 5.4 built, with §2.2's picture in mind:

The three arrays of engine::pool<T> mapped onto the three arrays of a sparse set.
engine::pool<T>a sparse setrole
slots_sparse indexed by key, one entry per key ever issued, stable
items_data the components, packed, no holes, order not guaranteed
owners_dense the way back: which key owns element d

That is not a resemblance, it is the same data structure. pool<T> is a sparse set with a generation counter welded to each sparse slot — which is exactly what an ECS wants, because an entity id has to survive the entity being destroyed and the slot being reused.

And it still does not settle the question, for two reasons worth being explicit about. The first is that pool<T> mints its own keys. A handle from the mesh pool is meaningless to the texture pool, because both hand out slot 0 to their first occupant. An ECS needs the opposite: one id space, minted once, with every pool keyed by it. That is a real change, not a reuse — §6 says exactly what it amounts to.

The second is the one that matters more. If owning a sparse set is allowed to decide that we should build a sparse-set ECS, then the architecture was chosen by an accident of what Lesson 5.4 happened to need for meshes. The archetype design would not use pool<T> at all, and "we would have to write more code" is a reason to prefer something, not a reason to believe it is faster. The convenience is admissible as a tiebreaker and inadmissible as evidence. So we measure first, and §6 is allowed to reach for it only after the numbers are in.
