8. Implementation

Three new files and a handful of edits. The order matters: the interface first, because it is the piece that decides what the algorithm is allowed to know.

8.1 convex.hpp: a shape, reduced to one question

GJK needs to ask two shapes for support points and nothing else. The C++ question is how to hand it two different shape types without teaching it what they are. Four answers were available and three of them are wrong for this engine:

  • A virtual base class. Ruled out by 5.2: no RTTI and no virtual dispatch in the engine core.
  • A template. GJK would live in a header and be instantiated once per pair of shape types — ten instantiations for four shapes, growing as the square, and a hundred-line algorithm recompiled into every translation unit that touches physics.
  • A switch on shape_kind, like 8.4's. Workable, and it means every new shape edits the algorithm. A hull is not a shape_kind (§8.2 explains why), so this one cannot reach it at all.
  • A function pointer plus a context pointer. Which is what 6.17's frame graph chose, and chose with a number.
struct convex
{
    using support_fn = vec3 (*)(const void* data, vec3 d);

    support_fn support = nullptr;
    const void* data = nullptr;
    vec3 origin{};

    [[nodiscard]] vec3 world_support(vec3 d) const { return origin + support(data, d); }
};

Twenty-four bytes, no allocation, no vtable, and one indirect call per support query. §I.3 prices it: 1.908 ns direct against 1.906 ns through the pointer, with both arms producing bit-identical floats. It is a tie, and the reason is structural rather than lucky — within one query the target never changes, so the branch predictor learns it on the first call and is right for the rest.

The adapters use a C++ feature worth naming the first time it appears: a captureless lambda converts to a plain function pointer. A lambda with no captures has no state, so the language lets it decay to vec3(*)(const void*, vec3), and the leading + forces that conversion: 

[[nodiscard]] inline convex as_convex(const obb& box)
{
    return convex{
        +[](const void* data, vec3 d) { return support_local(*static_cast<const obb*>(data), d); },
        &box,
        box.centre,
    };
}

That is how a modern C++ codebase writes a C-style thunk without writing one. And because convex holds a pointer it does not own, it is a view, with the same contract std::span has: it must not outlive what it views. The failure mode is a temporary, and it is worth turning into a compile error rather than a Tuesday afternoon: 

convex as_convex(obb&&) = delete;
convex as_convex(engine::sphere&&) = delete;
convex as_convex(capsule&&) = delete;
convex as_convex(hull&&) = delete;

An rvalue argument prefers the && overload, which is deleted, so as_convex(world_obb(s, p, q)) does not compile. An lvalue cannot bind to && at all, so the ordinary case is untouched. Four deleted functions, no runtime cost, and a class of dangling-pointer bug that now names its own line number.

8.2 support_local, and why the centre is kept out of it

Notice that convex::support returns a point relative to origin rather than a world point. That split is numerical, and it is 8.4 §11's finding turned into an interface. §12 measures what it buys; the short version is that a box's support point is centre + axes·s — three additions — and doing them in world space rounds each one to half an ulp of the position. GJK does two of those per iteration and then subtracts them, so it would pay the cancellation once per step rather than once per query.

So shape.cpp grows a support_local for each primitive that never forms the centre at all, and the old support becomes a one-line wrapper: 

vec3 support_local(const obb& box, vec3 d)
{
    const float sx = (dot(box.axes.c0, d) >= 0.0f) ? box.half_extents.x : -box.half_extents.x;
    const float sy = (dot(box.axes.c1, d) >= 0.0f) ? box.half_extents.y : -box.half_extents.y;
    const float sz = (dot(box.axes.c2, d) >= 0.0f) ? box.half_extents.z : -box.half_extents.z;
    return box.axes.c0 * sx + box.axes.c1 * sy + box.axes.c2 * sz;
}

vec3 support(const obb& box, vec3 d)
{
    return box.centre + support_local(box, d);
}

And gjk.cpp forms the one large subtraction exactly once, outside the loop: 

const vec3 delta = b.origin - a.origin;

8.3 Two new shapes, to prove the point

An interface that claims to work on any convex shape should be handed a shape the previous lesson could not test. shape.hpp gains two.

A capsule joins shape_kind, because it is fixed-size data — a radius and a half-height — and because 8.3 already shipped inertia_capsule, so it arrives able to simulate as well as collide. The half-height is half the segment, not half the capsule, for the same reason half_extents are halves: it is what appears in the support function.

A hull does not join shape_kind, and the reason is worth stating because it is a physical-design decision rather than an oversight: 

struct hull
{
    vec3 centre{};                       ///< World space.
    mat3 axes = mat3::identity();        ///< Columns are the unit body axes in world space.
    std::span<const vec3> points{};      ///< Body axes, relative to `centre`.
};

A shape is a 24-byte value that Module 9 will write to a save file, and a pointer is not a value. A hull's geometry is an asset: loaded once, shared by every instance, outliving any particular placement, exactly like a mesh. There is a second reason and it is sharper — inertia_of(shape) would have to answer for a hull, and it cannot: the tensor of a point set needs faces, a point set has none, and a function that returns a plausible wrong answer is worse than one that does not exist. §14 says so out loud.

Its support function is a brute-force scan, and that is a decision rather than a placeholder: 

vec3 support_local(const hull& h, vec3 d)
{
    if (h.points.empty()) { return vec3{}; }

    const vec3 dl = transpose(h.axes) * d;

    const vec3* best = &h.points[0];
    float best_dot = dot(*best, dl);
    for (const vec3& p : h.points)
    {
        const float v = dot(p, dl);
        if (v > best_dot) { best_dot = v; best = &p; }
    }
    return h.axes * *best;
}

One change of basis, not one per vertex: dot(axes·p, d) == dot(p, axesᵀ·d) because the axes are orthonormal and a rotation's inverse is its transpose — 2.5's identity, doing real work. So the loop is n dot products rather than n matrix-vector products, and the single winner is carried back out.

8.4 The loop, and the four ways it can stop

With all of that in place the search itself is short. The exits are the interesting part, and there are four:

  1. The bounds met — the answer is proven to the tolerance. The normal finish.
  2. The origin is enclosed — reduce_simplex reports containment and no lower bound contradicts it. The shapes overlap, and 8.6 takes over from the terminal simplex.
  3. No progress — either the support function returned a vertex the simplex already has, or |v| failed to decrease. On a polytope the first is how the search finishes exactly; on a curved shape both mean float has run out.
  4. The iteration cap — measured at zero firings in 200,000 capsule pairs even at tolerance 1e−7, and still the only reason this function returns at all on a curved shape.

The duplicate test in (3) deserves one note, because its threshold is not the user's tolerance and the first draft made it so: 

constexpr float k_duplicate_rel2 = 1e-12f;

A polytope's support function returns the same vertex when there is nothing better, so an exact-repeat test is all that is needed. A capsule's moves continuously with the direction, so two consecutive iterations produce points a fraction of a millimetre apart — "duplicates" by a 1e−4 relative measure — and the loop exited before the bounds had converged. Measured: capsule gaps reported with a certificate slack of 2.4% where the tolerance promised 0.01%, on results that were not flagged as stalled and therefore looked trustworthy. The threshold belongs at float's own resolution, where an exact repeat still trips it and a genuine small step does not.

8.5 The façade

collide.hpp gains one overload, because a caller wants one function: 

[[nodiscard]] separation collide(const convex& a, const convex& b);

It returns the same separation as every other test in that file, so a caller can swap the specialised test for the general one without touching anything downstream. Three fields are filled differently and the header states the contract: axis_index is −3 so source_of reports witness; axes_tested is the GJK iteration count rather than a candidate count — same meaning, different unit; and depth is exact when negative and a placeholder when not. A gap is the true distance. An overlap reports +0, because GJK cannot measure penetration: the origin is inside A ⊖ B and depth is a distance to its boundary, which the search never looks at.

That is the honest state of the engine after this lesson, and naming it is the point. The general test answers the question the specialised one could not — how far apart, exactly — and cannot yet answer the one it could.

One small thing the compiler could not have caught. The first draft gave GJK axis_index = −2, which read naturally next to −1 for radial. But collide.cpp already had constexpr int k_no_axis = −2, and source_of mapped it to none by falling off the end of the function rather than through a named case. A sentinel only reachable by fallthrough is a sentinel waiting to be reused by mistake. GJK is −3, and both values are named cases now.

9. What 8.6 will actually be handed

Every description of the Expanding Polytope Algorithm — 8.6's subject — begins the same way: start from the tetrahedron GJK terminated with. Before writing a lesson on that premise it seemed worth checking that GJK produces one.

§C.4 takes the arrangement 8.4 §F already identified as the commonest thing a game ever produces: two objects standing on the same floor, so their up axes are parallel whatever their yaw. A hundred thousand such pairs, unit cubes, centres within 1.2 m of each other, so most of them overlap.

@@FIG_FLAT@@

Not one tetrahedron. Zero, out of a hundred thousand — including all 65,633 pairs overlapping by more than 10 cm. Tilt one box by a single degree and 77,326 appear.

The cause is not subtle once you look for it. Both boxes have the same up axis, so their y half-extents multiply the same world direction, and support_local chooses the same sign on that axis for both — the tie-break is >= 0, so a zero component picks + deterministically for either box. Every vertex of the difference set therefore comes out with

w.y = pa.y − pb.y − delta.y = (+h) − (+h) − 0 = 0

exactly. All 100,000 simplices lay entirely in the plane y = 0, and a search confined to a plane cannot build a tetrahedron. The difference set is perfectly three-dimensional; it is the search that never leaves its equator, because every direction it asks about is itself in that plane. Preset 3 of the demo shows it happening, one keystroke at a time.

This is 8.4 §F's finding from the other side. There, a shared axis made one of the nine candidate cross products degenerate and the folklore about guarding it turned out to be about a different formulation. Here, the same shared axis collapses the entire search by a dimension. A shared axis is not a coincidence in a game — it is what "standing on the floor" means — and every algorithm in this module has to survive it.

So 8.6 will have to build its own starting polytope rather than inherit one. That is what real EPA implementations do, and it is usually presented as defensive programming for a rare case. It is not rare. It is the default.
