Module 5 — Becoming an Engine · Lesson 5.8

The ECS Runtime

Lesson 5.7 chose the sparse set by measurement and left four rules behind. This lesson builds it: an entity id minted once and honoured by every pool, a component pool that is three arrays and about twenty lines of logic, a registry that ties them together without RTTI, and a query that leads with the smallest pool because 5.7 measured what leading with the biggest one costs. Then it runs the result at a hundred and twenty-one entities and says plainly what that buys — which is not speed, and the lesson opens by admitting it.

1The Problem

Let us begin by throwing away the argument you were probably expecting.

The demo this course has been carrying since Lesson 2.12 holds its objects in an array of four. Lesson 5.6 measured what that costs, at five world sizes, with the optimiser on and off, and the answer for four objects was nothing — every storage layout it tried came within one percent of every other below a thousand objects, and the knee where layout starts to matter sat between 1,000 and 10,000. Lesson 5.7 then measured the two ECS storage designs against each other and found the same shape again: below a thousand entities every arm was within 16% of every other, and the interesting numbers only appeared at 100,000.

So an ECS is not going to make this engine faster today, and a lesson that opened by implying otherwise would be teaching the exact folklore this course exists to argue with. The reason to build one now is that scene_object has been quietly failing for five lessons, and the failure is about expression rather than speed.

Here is the whole history, and it is short. In Lesson 2.12 a scene_object was a transform and a mesh — the smallest honest definition of a renderable thing. Lesson 3.1 filled the triangles, so it needed a colour, and gained a tint. Lesson 3.4 added back-face culling, which is only valid on closed surfaces, so it gained closed. Lesson 3.7 added specular highlights, so it gained a whole specular surface sub-struct. Lesson 5.4 turned the mesh into a handle. And at every one of those steps the comment in scene.hpp said some version of the same uncomfortable thing:

“Look at what just happened to this struct. tint was enough while a surface was one colour; then 3.4 needed closed; now 3.7 needs two more numbers, and all four describe the same thing — the surface — while xform and geometry describe where it is and what shape it is. That is two different kinds of data wearing one struct.”

Two kinds became four. And because a struct is a promise that every instance has every field, each addition was paid for by every object whether or not it meant anything: the ground plane carries a shininess it never uses, and an object that should not be drawn at all has no way to say so except a null handle and a branch in the renderer.

Read the lower half of Figure 1 and notice what is not in it. There is no empty cell to explain, because an entity that has no material does not have a blank material — it has no row in the material pool, and the material pool has never heard of it. The render query in §5 names placement, geometry and material, and a waypoint entity that carries only the first is skipped by the query rather than filtered by the renderer. Nobody wrote that skip. It falls out of asking the right question.

That is what this lesson buys, and it is worth having at 121 objects. The performance argument is Lesson 5.7's, it is real, and it applies at ten thousand — we will build the thing that is ready for it, and we will not pretend it is why.

What this lesson does not do

Nothing renders through the ECS yet. collect_triangles still takes a span of scene_object, and the demo's render system walks a view and fills one — a bridge, six lines long, marked temporary in the source. Converting the renderer is Module 6's job, and doing it here would mean changing the architecture and the picture in the same lesson, with no way afterwards to tell which change broke what. The reference shot from Lesson 5.1 is still byte-identical after this lesson (§6), and that is a fact worth having rather than a coincidence.

2Building Intuition

2.1 What we already have, and the one thing it lacks

Open engine/include/engine/core/pool.hpp — Lesson 5.4's container — and read its member list with Lesson 5.7's vocabulary in your head:

The three arrays of Lesson 5.4's pool, and what each one is called in sparse-set terms.
pool<T> calls ita sparse set calls it what it does
slots_the sparse array one entry per slot ever created, indexed by a handle's index field, never moves
items_the dense data live objects only, packed, no holes, order unspecified
owners_the dense id list which slot each dense element belongs to — the way back

That is a sparse set. It has generations, it has swap-and-pop removal, it has O(1) insert, remove, lookup and a contiguous iteration span. Lesson 5.7 noticed this out loud and then refused to let it decide the architecture, on the grounds that choosing a design because you happen to own something shaped like it is choosing by accident. Now that the design has been chosen on the evidence, the resemblance is simply useful: most of this lesson's storage code is code you have already read once.

So what is missing? One thing, and it is structural rather than incremental:

@@FIG_IDSPACE@@

Every pool<T> mints its own keys. Insert a mesh and you get handle<mesh_data>{index 7, generation 1}; insert a texture into a different pool and you get handle<texture>{index 7, generation 1}. Two sevens. They came off two different free lists, they refer to two unrelated slots, and the phantom type parameter exists precisely to stop you confusing them. Ask “does the thing in mesh slot 7 also have a texture?” and you do not get a slow answer — you get no answer, because the question is not well formed.

An ECS is the arrangement in which that question is well formed. Mint the id once, from one allocator, and hand the same id to every pool. That is all. Everything else in this lesson — the views, the systems, the composition argument — is a consequence of that single inversion.

2.2 A component is a struct; a system is a loop

Before any code, it is worth being precise about how little an ECS asks of you, because most of the reputation for complexity comes from frameworks rather than from the idea.

A component is a plain struct. No base class, no virtual functions, no registration macro, no header of its own. Our registry requires exactly one thing of a component type — that it be movable — and it does not even require that it be default-constructible. The demo in §5 uses engine::transform, written in Lesson 2.8 by somebody who had never heard of an ECS, as a component without modifying or recompiling it.

A system is a free function that takes the world and runs one query:

Not a class, not a virtual update(), not a base System. There is nothing for such a base to hold, because a system's entire state is the query it runs — and Lesson 5.6 measured what a virtual call costs on an iteration (1.5–1.7× at every world size, including four objects sitting in L1) and concluded that ECS iteration must not be virtual. Free functions are not a stylistic preference here; they are that measurement, obeyed.

There is a second thing to notice about that signature, and it will matter in Module 9. The query declares the data flow: orbit_system writes placements and reads orbits, and you can see that from the first line without reading the body. A job system deciding whether two systems may run concurrently needs exactly that information, and here it is legible for free.

2.3 The useful thing is the absence

The mental shift that makes an ECS click is small and slightly counter-intuitive: an entity is not a thing that has components. It is an id, and the components are filed under it.

The difference sounds like philosophy and is entirely practical. If an entity had components, an entity would need to be an object, that object would need to know what it holds, and adding a component would mean modifying it. Because components are merely filed under the id, adding one touches exactly one pool and nothing else in the world learns about it — which is precisely the 4.2 ns structural change Lesson 5.7 measured, and precisely why that number did not move when the entity grew from four component types to twelve.

It also means the interesting queries are the ones about absence. “Every entity with a placement and an orbit but no geometry” is a sentence about a set difference, and in a world of structs it is a sentence about a flag somebody remembered to set. We will not build exclusion queries in this lesson — Exercise 10.2 does — but the reason they are easy is visible already: the pools are sets, and set operations are what sets are for.

3The Theory

3.1 One shared id space

Lesson 5.7's rule 2 says the entity id must be minted once and handed to every pool. Two consequences follow immediately, and both shape the code.

First: the id space must stay compact. Every pool's sparse array is indexed by an entity's index field, so it must be at least as long as the largest index in use. If ids were handed out by an ever-increasing counter, a game that spawned and killed a thousand bullets a second would push that counter past three million in an hour, and every component type in the world would carry a three-million-entry sparse array — twelve megabytes each, almost all of it meaning “absent”.

A free list fixes this, and the fix is worth stating as an equation because it is the whole reason Lesson 5.7 could rule out paged sparse arrays:

The high-water mark

high-water mark = peak simultaneously live entities, not entities ever created.

Reuse a slot before minting a new one and the index space never grows past the largest number of entities that were alive at one instant. The verification harness in §6 makes this concrete: 200 frames of churn create 518 entities and destroy 301, and the id space ends at 220 slots — the peak live count, not the 518.

Second: reuse means an old id can name a new occupant, which is Lesson 5.4's aliasing failure arriving in a world where it happens constantly. Entities die every frame in a way that meshes and textures do not, so the generation is not a nicety here; it is the difference between “that entity is gone” and “that entity is now somebody else's spaceship”.

3.2 The entity word, and what a generation check costs

We reuse Lesson 5.4's bit budget exactly — 20 bits of index, 12 of generation, generation 0 reserved so that the null entity is all-bits-zero — and we include those constants from core/handle.hpp rather than restating them, so the budget has one home.

@@FIG_SLOTS@@

Work Figure 3 through with real numbers. Three entities are minted, so slots 0, 1 and 2 each carry generation 1, and b = {index 1, generation 1}, which packs to:

Packing b

bits = (generation << 20) | index = (1 << 20) | 1 = 1,048,576 + 1 = 1,048,577

Now destroy(b). Slot 1 is marked free, its generation becomes 2, and index 1 goes onto the free list. b still holds 1,048,577, and the slot now says generation 2, so:

Testing the stale id

alive(b) = (1 < 3) && slots[1].live && (slots[1].generation == 1)

= true && false && false = false

Then create() pops slot 1 off the free list and returns b2 = {index 1, generation 2}, packing to 2,097,153. Both ids name slot 1; only one of them is alive; and the test that separates them is a single 32-bit comparison. That is the entire mechanism, and it costs one integer compare on a value already in a register.

Bump on removal, never on insertion

Lesson 5.4 derived this and it is worth re-stating because entities are the case that makes it matter. If the generation were bumped when a slot was taken, there would be a window — between the free and the next create — during which a freed slot still carried the generation an outstanding id holds, and alive() would say yes. Bumping on removal closes the window to zero width: from the instant of the free, every id that ever named that slot is stale.

The 12-bit budget, and why entities are the case it worries about

4,095 usable generations means a slot's generation repeats after 4,095 frees of that same slot, and a LIFO free list hammers one slot rather than spreading the load. core/handle.hpp did the arithmetic: at one recycle per frame that is 68 seconds. For assets — loaded at level boundaries, counted in hundreds — this is unreachable. For entities in a bullet-hell it is not, and §A of the harness drives one slot through 4,096 create/destroy pairs and confirms the wrap counter reads exactly 1. The counter exists so the assumption is monitored; if it ever leaves zero, the two fixes are a FIFO free list (which multiplies time-to-wrap by the slot count) or a 64-bit id split 32/32.

3.3 The sparse set, walked by hand

One component type's storage is three arrays. Let us fill them with actual numbers and then take one apart.

Five entities — ids 7, 4, 91, 30 and 12 — each get a component, inserted in that order. Insertion appends, so:

The three arrays of a sparse set holding five components.
01234
dense_[i]e=7e=4e=91e=30 e=12
data_[i]T(7)T(4)T(91)T(30) T(12)

…and sparse_ is indexed by entity, not by position, so it is a 92-entry array of which five entries are set: sparse_[7] = 0, sparse_[4] = 1, sparse_[91] = 2, sparse_[30] = 3, sparse_[12] = 4, and the other 87 hold the “no component” sentinel.

A lookup is then two array reads: data_[sparse_[e.index()]]. The second read's address depends on the first read's value, which is the two-deep dependent chain Lesson 5.7 spent a whole figure on, and 5.7's finding was that it is latency rather than work — free until the working set leaves cache and the pools' orders diverge.

Removal is where the design earns its keep and where implementations go wrong. Erase entity 4's component:

@@FIG_ERASE@@

Step by step. sparse_[4] is 1, so the hole is at dense position 1. The last element (position 4, entity 12) moves into it: dense_[1] = 12 and data_[1] = T(12). Then both arrays are popped, and sparse_[4] is set to “absent”.

And one more thing has to happen, which is the line people forget. Entity 12 did not ask to move. Its sparse entry still says 4 — a position that no longer exists — so it must be patched to 1. Miss that line and the pool is not obviously broken: it is silently broken, and the symptom appears an arbitrary number of frames later, in a different system, as one entity reading another's data. Lesson 5.7 hit exactly this bug in the archetype arm of its probe, and found it only because the test churned two hundred frames before checking.

Worked edge case — erasing the last element

Erase the element at the end, and the “element that moves” is the element being erased. Trace it: at equals last, so the swap is skipped entirely; both arrays pop; then sparse_[e] is set to absent. If the swap were not skipped, it would copy the element onto itself and patch its own sparse entry to the position it already occupies — harmless, and then immediately overwritten by the final line. Either way the order saves us, and it is the order rather than the branch that is load-bearing. §B of the harness tests this case on its own, because a test that only ever erases from the middle passes forever.

Finally, contains() is three tests and the third is the one that costs a line and buys the whole design:

dense_ stores the full 32-bit entity word, generation included, so an id naming the same slot with an older generation is rejected. Store a bare index there instead — which is what a naïve sparse set does, and it saves nothing — and that third test cannot be written at all. Lesson 5.4's aliasing failure walks straight back in.

3.4 A query is a set intersection

view<placement, geometry, material> asks for the entities in all three pools. That is an intersection of three sets, and the classic result about intersecting sets is that you should iterate the smallest one: the cost is O(smallest × lookups), not O(largest).

Lesson 5.7 turned that into a measurement rather than an assertion. At one-in-four selectivity and 100,000 entities, leading with the big pool cost 1.73× a real archetype and leading with the small one cost 1.46× — identical code, differing only in which array the outer loop walks. That is rule 3, and here is what it looks like in candidates:

A fifth of the walk for the same six answers, and the gap widens as the component gets rarer: a query for “entities with a placement and a player_input” in a world of 10,000 entities and one player walks one candidate if it leads correctly and 10,000 if it does not. The decision is one comparison in a constructor, made once per query rather than once per entity, so it is free in every sense that matters.

There is a second, smaller prize in leading with a pool, and it is easy to miss. For the lead pool, the dense position is the loop counter — we are walking its dense array in order — so the lead's own component needs no sparse lookup at all. Only the other K−1 pools pay the redirect.

3.5 Type erasure without RTTI

One problem remains, and it is the only genuinely hard one in the file. registry::destroy(e) must erase e's row from every pool, and those pools have different types. C++ offers two ways to hold a heterogeneous collection like that.

The obvious one is RTTI: key the pools by std::type_index and recover the concrete type with dynamic_cast. It is not available to us — the engine core is built with RTTI off since Lesson 5.1 — and that turns out to be a mercy rather than a constraint, because dynamic_cast is a runtime walk of the type graph and a type_index lookup is a hash on a path that ought to be an array index.

The alternative is to assign the numbers ourselves:

@@FIG_ERASURE@@

Each component type gets a small integer the first time anybody asks, from a counter behind a function-local static. That integer indexes a std::vector<std::unique_ptr<pool_base>>, and the concrete type is recovered with a plain static_cast — which is safe for a reason worth saying out loud: the id is what created the pool. The object at index component_id_of<T>() was constructed as a pool<T> and nothing else can ever be stored there, so the downcast is justified by construction rather than checked at use. That is the difference between a cast that is safe and a cast that is merely usually right.

The cost of not keeping a per-entity component mask is visible in the lower half of Figure 6: destroying an entity that had three components makes five virtual calls, two of which return after a single array read. At the five types in that figure — or the six the demo uses — that is nothing. An engine with three hundred component types would keep the mask, and Lesson 5.7 §9 said so.

C++ in place — the function-template static

component_id_of<T>() works because of two guarantees the language makes. A static local inside a function template is one object per instantiation, shared across every translation unit — which is what makes the id for placement the same number in the demo and in the test harness, without a registration step. And since C++11 its initialisation is thread-safe (“magic statics”), so two threads calling it simultaneously cannot both run the initialiser.

What is not thread-safe is the counter increment behind it, so the honest rule is the one in the header: touch each component type once before the job system starts. That constraint is shared by every container in this engine until Module 9 revisits all of them at once.
