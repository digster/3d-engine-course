8. The storage swap

math/transform.hpp has carried a promise since Lesson 2.8: the mat3 in the rotation field is honest but not final, and a quaternion replaces it. That promise has moved three times — first to 7.1, then to 7.4, then to here — and the comment that made it said, until this lesson, that the swap "touches one line of parent_from_local() and nothing else".

That sentence was written in Module 2 and was wrong by Module 5. It is wrong for a reason worth the whole section.

8.1 The change itself

struct transform
{
    vec3 position{0.0f, 0.0f, 0.0f};
    quat rotation = quat::identity();     // was: mat3 rotation = mat3::identity();
    vec3 scale{1.0f, 1.0f, 1.0f};
};

And parent_from_local gains exactly one line — the Module 2 comment was right about that much: 

const mat3 basis = mat3_from_quat(t.rotation);

const mat3 axes{basis.c0 * t.scale.x,
                basis.c1 * t.scale.y,
                basis.c2 * t.scale.z};

return affine(axes, t.position);
@@FIG_SWAP@@

That one line is also engine policy arriving as a statement. Lesson 7.4 §10.3 measured the crossover: a quaternion is 1.57× dearer than a matrix at rotating a vector, and converting costs 4.619 ns, so building the matrix first pays for itself after about eight vectors. A mesh has thousands. So the engine stores quaternions, converts exactly once per object per frame, right here, and multiplies every vertex by a matrix. "Quaternions are faster than matrices" is true of storing and composing and false of the thing a frame spends its time on.

8.2 Twenty-five call sites, and what the compiler said about three of them

Narrowing a type is a compile error at every site that was relying on the width. Most of the twenty-five are a rename with a better function underneath — rotation_y(a) becomes quat_y(a), and composing two of them drops from 27 multiplies to 16. Several are a basis the geometry genuinely speaks in, kept as a mat3 and narrowed at the assignment: 

// demos/common/demo_scene.cpp — a plank's frame is "along the rail, across it, up"
t.rotation = engine::quat_from_rotation(engine::mat3{axis_x, axis_y, axis_z});

That pattern is safe precisely because of Lesson 7.4 §9: Shepperd extraction has no bad case anywhere — four candidates that sum to exactly 4, so the pivot is never below 1 — which means there is no angle at which "construct as a matrix, store as a quaternion" is less accurate than another.

Two sites are stepped rather than rebuilt, and those gained a repair: 

// demos/collector/main.cpp — the carousel, one line per frame, for ever
t.rotation = engine::renormalised_fast(t.rotation * engine::quat_y(c.rate * h));

This is the first place in the engine where drift is a real problem rather than a measurement. The mat3 it replaced had the same disease and a dearer cure — Gram-Schmidt, three normalisations and two projections. renormalised_fast is one subtract and five multiplies, no sqrt and no divide, and 7.4 §F.4 measured it holding a million compositions at 6e−08 where the unrepaired walk reached 1e−03. The site next to it, ecs_swarm's spin system, gets no repair and should not: it rebuilds from an angle every frame, so the previous frame's answer is never an input. The difference is not "rotation" versus "rotation" — it is whether the field is an accumulator.

And then there were three sites that did not compile for a more interesting reason.

8.3 The field called rotation with no rotation in it

Lesson 7.4 §11 found the first one and declined to fix it. gfx/renderable.cpp turns an ECS world_transform — a composed 4×4 — into a scene_object, and it did so like this: 

.xform = {.position = translation_of(w.matrix),
          .rotation = linear_of(w.matrix),      // the WHOLE upper-left 3x3
          .scale    = {1.0f, 1.0f, 1.0f}},

Its comment said, correctly, that the recomposition "reproduces the original affine matrix to the bit". It did. It did so because a mat3 will hold anything — including the scale that came down the hierarchy from a parent, sitting in a field named rotation, since Lesson 5.11.

A quaternion will not hold a scale, so that line became a compile error, which is the type doing exactly the job it is here to do. And once you go looking, the same trick is in demos/ecs_swarm — and a third variant, which is the one worth the paper.

8.4 collector's camera boom, sheared since 5.12

Lesson 5.12 built a checkpoint game with a rover and a chase camera, and §6 of that lesson made a good argument: a camera parented to the player inherits the player's 22° of cosmetic roll, the horizon see-saws, and the fix is not a special case in the renderer but one more link in the chain — a boom that applies the inverse roll. It also has to undo the rover's non-uniform scale, or "6.4 units back" means 3.97 metres.

The algebra it derived is right, and the demo's comment spells it out because getting it backwards cost that file its first crash:

\[ \text{boom local} \;=\; \big(H \cdot R_z(\text{bank}) \cdot S\big)^{-1} H \;=\; S^{-1} \cdot R_z(-\text{bank}) \]

Scale first, rotation second. And a transform builds T · R · S — scale innermost. So a single node can say "rotate, then scale" and cannot say "scale, then rotate", and those are different matrices whenever the scale is non-uniform. The difference is a shear: the product S⁻¹R has columns that are not perpendicular.

@@FIG_BOOM@@

So that line had been storing a sheared basis in a field called rotation for thirteen lessons, and nothing complained, because a mat3 will hold anything. Push it through a quaternion and the error is 0.5863 of a matrix entry — not a precision loss, a different basis.

The repair is not a wider type. It is one more link: 

// rover  world       = H · Rz(bank) · S
// unscale node local =                   S⁻¹        -> H · Rz(bank)
// pivot   node local =                        Rz(−bank) -> H

Two entities, each holding something a transform can genuinely express, and the hierarchy multiplies them parent-first — which is the order the derivation asked for in the first place. The harness checks that the chain reproduces the old basis: worst entry difference 0.000e+00, and the camera is where it always was.

The general statement, which is worth carrying into Module 8

T · R · S per node is a restriction, not a representation. The set of matrices a scene graph can express is not the set of affine matrices — and when you need one that is outside it, the answer is usually another node rather than a wider field. Real engines do exactly this, and this is why.

8.5 One decomposition, derived once, instead of three

Three places in this repository were pulling an affine matrix apart. Two of them were doing it with the mat3 trick and one — demos/gltf_view — had been doing it properly since Lesson 6.6. So the compile error did not just need fixing; it had found a function the engine was missing, written out three times with three different sets of defects. It is now in math/transform.hpp: 

struct transform_extraction
{
    transform value;
    float out_of_square = 0.0f;   ///< largest |cos| between two basis directions
    bool mirrored = false;        ///< the matrix had negative determinant
};

[[nodiscard]] inline transform_extraction transform_from_affine(const mat4& m);

The shape — a value plus what the recovery could not represent — is the one axis_angle_extraction (7.2) and euler_extraction (7.1) already use, and for the same reason: a recovery that can lose information should hand back the information about what it lost, in the same breath.

Three steps, and the second is the one nobody writes down.

  1. The scale is the column lengths. parent_from_local builds the matrix by scaling each basis column, and scaling a unit vector by s makes its length s. Reading the lengths back is the inverse of the construction, not an estimate of it.
  2. A negative determinant is a mirror, and no quaternion is one. Every rotation has determinant +1; an object scaled by (−1, 1, 1) has determinant −1 and is a reflection, which is not in the rotation group at all. Column lengths are non-negative by construction, so the sign has to be handed back deliberately. Skip this and a mirrored object silently becomes an unmirrored one that is rotated — the kind of bug that gets blamed on the artist.
  3. Divide the lengths out and extract.

8.6 A zero column, and an inherited defect

A degenerate object — scale 0 on an axis, which is how a sheet of paper or a collapsed node is authored — has no direction to read off that column. The version inherited from gltf_view substituted the parent's axis and said, correctly, that this "keeps the matrix finite instead of producing NaNs".

It does. It also produces a basis whose three columns are not perpendicular, and quat_from_rotation of a non-orthonormal basis is wrong in every column, not just the bad one. The harness measured it at 0.399 of absolute entry error on a flattened object whose other two axes were perfectly recoverable. The zero column is the one that does not matter — its scale multiplies it away. The two good ones are the ones that got broken.

A cross product of the surviving pair is the right answer and costs six multiplies: perpendicular to both by construction, unit because they are, and correctly handed because the order is cyclic. With the repair, the probe table is exact: 

   probe          worst entry   out of square  mirrored
   uniform 1      0.000e+00     1.892e-08      no
   uniform 2      0.000e+00     1.892e-08      no
   non-uniform    0.000e+00     1.892e-08      no
   mirrored x     0.000e+00     1.892e-08      yes
   flat z         0.000e+00     1.892e-08      no
"Finite" is not "right"

That comment had been in a published lesson's listing since 6.6, it was accurate about what it claimed, and the claim was the wrong one. Guarding against NaN is necessary and is not sufficient: a guard that returns a plausible wrong answer is harder to find than a NaN, because a NaN spreads and announces itself and a wrong basis just looks like the artist scaled something oddly.

8.7 What stays outside the struct, and is counted

One case genuinely cannot be decomposed: shear. A non-uniformly scaled parent with a rotated child produces a world matrix whose columns are not perpendicular, and that is not (rotation × axis-aligned scale) under any decomposition. Column lengths cannot even see it — a shear changes the angles between the columns and not their lengths — which is why out_of_square measures the angles instead.

collect_renderables counts those objects in renderable_report::skewed and says so in its warning line. Nothing is dropped and nothing goes NaN: the object draws in the nearest placement a transform can express, and the count turns "the crate looks subtly wrong and I cannot see why" into a number. Measured on a deliberate example — a parent scaled (2, 0.5, 1) with a child yawed 40° — the basis is 0.5941 out of square and the best available repair still leaves 0.3922 of entry error.

The honest fix is unchanged and unmade: scene_object should hold a mat4, which is what Module 6's GPU path already does with gpu_draw_item::world_from_model and what Lesson 5.9's hierarchy already computes. Two functions in this repository now take a matrix apart only to hand the pieces to parent_from_local, which puts it back together. That round trip is the argument. It is a change to a published struct with a dozen callers, so this lesson names it and does not smuggle it in — the same discipline 5.12 applied to view<const T>.

8.8 Did the picture move?

Every object in the software renderer now goes mat3 → quat → mat3 where it used to go nowhere. That is a real round trip with a sqrt and three divides in the middle, and the honest question is whether it moved a pixel.

Measured over 20,000 random poses, the worst matrix entry to survive the round trip differs by 5.960e−07. Put that in the units that decide whether a picture moves: a vertex 3 units from the origin, in a 960-pixel frame about 12 units wide, displaces by 0.00014 pixels.

And then check it rather than trusting the arithmetic. scratch/closure_75.py walks the include graph and reports that math/transform.hpp, math/quat.hpp, gfx/scene.hpp and demos/common/demo_scene.cpp are all in the golden render's closure — so the structural argument does not apply and the run is the only evidence there is: 

golden_75: rc=0  ours=1382416 bytes  reference=1382416 bytes
golden_75: identical=YES

Eight frames, 1,382,400 bytes, hash E917C06C — byte-identical, and identical to the reference Lesson 5.2 recorded. The engine changed how it stores every orientation in the scene and not one pixel moved.
