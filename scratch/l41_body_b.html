Everything above is a claim about hardware. The point of this section is that you can check most of it without any hardware, by making the software rasterizer behave the way the hardware does and measuring the difference.

4.1The fragment, extracted — and what it turned out to be

Two traversals need to share the per-pixel work, so it comes out of the loop into a lambda:

Look at what extracting it revealed. It is a function from three barycentric weights to a colour, with every piece of pipeline state captured. That is a fragment shader. It has been one since Lesson 3.6; it was simply spelt inline, so nobody had to notice. The one thing separating it from the real article is that the caller cannot supply it — which is Module 4's whole argument, and the reason this refactor belongs to a lesson rather than to a tidying commit.

It also acquires a new obligation, and this is the part that needs care. It is now called for lanes the triangle does not cover, so it has to be total: barycentric weights go negative outside the triangle (Lesson 2.3 said so and called it useful), w_recip can come back enormous or negative, and a uv can land anywhere at all. Nothing in there reads out of bounds on such a lane — wrap_texel folds any index into range (3.9) and linear_to_srgb_u8 refuses a NaN (3.3) — and whatever nonsense it computes is discarded. Both of those guards were written for other reasons, and both are load-bearing here.

4.5A 10% speedup that was not there

One thing happened while building this lesson that belongs in it.

After extracting the fragment into a lambda, the Module 3 harness reported the capstone fragment at 40.46 ns/px against the 46.46 Lesson 3.10 published. A behaviour-preserving refactor with a free 10% is a result, so it got measured properly: two binaries differing only by the extraction, run alternately in one session.

The minimums say 2.5% faster and the medians say 1% slower, which together say no measurable difference. The 10% was session drift — and you can see the drift in the data, because both columns climb monotonically as the machine warms up.

This is Lesson 3.10's own pitfall, violated within a day

3.10 §7 says it in as many words: never compare two numbers taken hours apart; measure both variants in the same run, back to back. It took one day to break that rule, on the very code that lesson was written about. Two things follow. Lesson 3.10's published numbers stand, unchanged. And a refactor's performance claim needs the same control as a feature's — "it should be the same speed" is a prediction, and predictions get measured.

4.6Seeing it: one key

5 cycles the traversal: scanline, quads, and quads with the helper lanes written in debug magenta instead of discarded. That third mode is not a rendering mode, it is a picture of the waste — every triangle grows a magenta fringe, and the fringe is the same width whatever the triangle's size, which is precisely why small triangles suffer.

Magenta is this engine's "this value is not real" convention, used for the third time — checker_at in 3.2, an unbound sampler in 3.9, helper lanes now. No real surface is ever that colour by accident.

The budget panel gains a line reporting lanes shaded, lanes wasted, and the efficiency — and it appears only under a quad traversal, because under scanline every lane is covered by construction and a row reading "100% efficient" would be announcing that the feature is switched off, dressed up as a result.

7Common Pitfalls & Debugging

"Small triangles are expensive" taken as folklore

Symptom. An LOD system that reduces triangle counts and does not get faster, or a tessellation setting nobody can justify.

Cause. Triangle count is not the axis. Lesson 3.10 measured a 2-triangle floor costing eight times a 2,304-triangle torus; today's numbers say the cost of a small triangle is its lane efficiency, which is a function of its size in pixels.

Fix. Reason in pixels per triangle, and pick LOD levels so that triangles stay above a few pixels across at the distance they are shown. Below one pixel you are paying full price for lanes you throw away.

A branch that was cheap in testing and expensive in the game

Symptom. A shader branch benchmarks fine on a test scene and costs 30% in production.

Cause. Coherence, not the branch (§2.4). The test scene had large uniform regions; the real one has the two sides interleaved at pixel scale.

Fix. Measure with realistic data, and where possible move the branch out of the shader entirely — sort draws by material, or use separate pipelines. That is the same "specialise rather than branch" move §3.4 describes, and on a GPU it is the whole reason shader variants exist.

Expecting ddx/ddy to work inside a branch

Symptom. A texture sampled inside an if shows garbage mip selection, or the compiler refuses outright.

Cause. A derivative needs the neighbouring lane's value at the same point in the program. If that lane took the other side of the branch, it does not have one.

Fix. Sample outside the branch and select afterwards, or compute the gradient outside and use an explicit-gradient sample. This is a real constraint you will meet in Module 6, and it falls straight out of Figure 2.

A traversal change that "looks the same"

Symptom. You add a quad walk, the image looks right, and something subtle is wrong three lessons later.

Cause. "Looks the same" is not a test. A helper lane that writes depth, or a coverage rule that differs by one pixel at a shared edge, is invisible until it is not.

Fix. Compare buffers, not impressions: zero pixels differing and zero depth values differing, over a scene with thousands of shared edges. Lesson 3.9's bit-identical blit made the same argument, and both were caught by the same kind of check.

Comparing a benchmark against a number from yesterday

Symptom. A refactor appears to gain or lose 10%.

Cause. Thermal and scheduling drift between sessions (§4.5). It happened in this lesson.

Fix. Build both variants, run them alternately in one session, and report both the minimum and the median. If they disagree about the direction, you have no result.

8Exercises

8.1  Predict before you measure

Before running anything: what lane efficiency would you expect for the floor alone — two enormous triangles — and for a 192-segment torus? Write both down, then use 5 and C to check.

Solution sketch

The floor is close to 100%: two triangles covering tens of thousands of pixels have almost no perimeter relative to their area. The torus at 192 segments measures 72.6%. The gap between those two is the whole of §3.1, and it is why "how many triangles" is the wrong question and "how big are they" is the right one.

8.2  Make the block size a parameter

Generalise the quad walk to an arbitrary power-of-two block and reproduce Figure 4's four curves from the real rasterizer rather than from the coverage-only sweep in verify_41 §D. Do the timings track the lane counts?

Hint

The alignment mask & ~1 becomes & ~(block - 1), and the four hard-coded lane offsets become two nested loops. Everything else is unchanged, which is itself worth noticing.

8.3  Implement ddx

Give the fragment function access to its quad's four uv values and compute ddx(uv) and ddy(uv). Then use them: colour each pixel by log2(max(|ddx|, |ddy|) · texture_size), which is exactly the mip level a GPU would select. Compare it against Lesson 3.9's traced footprint down the floor.

Hint

You will have to shade all four lanes before writing any of them, which means computing the quad's four fragments into a small array first. That restructuring is not incidental — it is why the hardware works in quads in the first place.

Solution sketch

The level should rise steadily toward the horizon and match 3.9 §H's traced footprint of 0.60 texels per pixel at the bottom of the frame to 62.46 near the horizon — i.e. about six mip levels. You have now built the input to mipmapping, three modules before Module 6 builds the mipmaps.

8.4  Find the divergence cliff on your own machine (engine challenge)

verify_41 §E assumes a warp of 32. Sweep the assumed warp width — 8, 16, 32, 64 — against coherence and find where your curve steps. Then look up your GPU's actual wavefront width and compare.

Hint

The step happens where the run length crosses the group width, so the curve for an assumed width of W should turn at a coherence of W. That is a falsifiable prediction about a parameter you chose, which makes it a good test of whether the emulation models anything at all.

8.5  Occupancy, by hand (engine challenge)

Extend §F's chain experiment so each chain carries a small array of live values — 2, 4, 8, 16 floats — standing in for a shader's register usage. Plot throughput against chains × registers. Where does it fall off, and why?

Solution sketch

It falls off when the working set exceeds the physical register file and the compiler starts spilling to the stack. That is exactly what happens on a GPU when a shader's register count reduces occupancy: fewer groups fit, less latency is hidden, throughput drops. You have reproduced an occupancy cliff on a CPU.

9Recap & Next

Module 4 opens not with an API but with a model, and the model is now measured rather than asserted:

  • Wide, not fast. Eight independent chains of identical work run 7× faster than one dependent chain, and 32 run 27× faster. A GPU is a machine built to always have something else to do, and occupancy is that table.
  • Lockstep, and what it costs. A warp executes both sides of a branch its lanes disagree about. Measured: 1.93× when incoherent, 1.00× when coherent, with the step exactly at the warp width.
  • 2×2 quads, and why they cannot be avoided. Derivatives are differences between neighbouring lanes, so the neighbours must run. Efficiency falls from 96.3% on a 64-pixel triangle to 25.0% on a 1-pixel one, and it falls faster for every wider block.
  • Eleven pipeline stages, all of which you have written.
  • A pipeline object with ten fields against SDL's nine — and the measured finding that the usual justification for it (branch cost) is wrong, while the real one (validation and compilation) is exactly why shaders exist.

The engine gained one enum and about a hundred lines, and produced a bit-identical image while doing measurably more work. That is an unusual kind of change and worth naming: it is not a feature, it is an instrument — a way of asking your own renderer a question about a machine it is not running on.
