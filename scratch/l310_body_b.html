Drag the second slider to the far right on the default setting: the phase is 96% of the frame and you have made it 64× faster, which no real optimisation ever is, and the frame is 18.2× faster rather than 64×. Now drag the first slider down to 50% and watch the whole curve collapse — the same heroic 64× on half a frame buys 1.97×. The lesson is in which slider moves the answer, and it is not the one you spend your week on.

4Implementation

4.1The profiler, and what it refuses to do

The new file is src/core/profile.hpp, and it goes in core/ rather than gfx/ for the reason all of Module 5's structure will eventually turn on: measuring time is not a graphics concern. The physics step will want a zone, the asset loader will want a zone, and none of them should have to include a rasterizer to get one.

Start with the zones. They are an enum class with a count sentinel last, which is the standard C++ idiom for "this enum also indexes an array":

C++ — inline constexpr at namespace scope

inline on a variable is a C++17 feature and it means exactly what it means on a function: this definition may appear in every translation unit that includes the header, and they are all the same object. Without it, every .cpp that includes this header gets its own k_zone_count — harmless for a constant, and a real one-definition-rule problem the moment somebody takes its address. Lesson 2.12 met the same rule from the other side with inline constexpr mesh arrays; this is the scalar case.

Now the instrument itself. scope_timer is the entire public interface for measuring something, and it is eleven lines:

Two decisions in there are worth defending. It is a class rather than a matched pair of calls for the reason RAII exists at all (Lesson 0.5): a phase with an early return in the middle of it would skip the closing call and silently lose the measurement, whereas a destructor runs on every path out of a scope including the ones you did not think of. And all four copy and move operations are deleted, because two live copies would each report the interval on destruction and the zone would count it twice. Deleting them makes that unwritable rather than merely discouraged — the same move vertex made in Lesson 2.4, where bundling attributes with positions made a whole class of bug impossible to type.

Then the part most profilers leave out: the profiler measures itself at construction.

That is §2.2's rule made executable. The engine logs both numbers at startup and the arithmetic that follows from them, so the first line of every run tells you what you are allowed to measure on this machine:

Notice that the calibration loop's body is an unnamed-looking object with a name — const scope_timer t{...} — and the name is doing real work. Write scope_timer{*this, zone::build}; without one and you get a temporary that is destroyed at the end of the statement rather than the end of the scope. Here those happen to be the same point, so it would work; in a real zone it would be a timer that closes immediately and reports nothing. It is one of the most common C++ RAII mistakes and it fails completely silently, so the habit is: always name your guard.

One arithmetic detail in to_ns is worth pausing on, because it is the single most common way this class of code is written wrong:

Multiply first, then divide. The other order — ticks / freq_ * 1e9 — performs an integer division that truncates to whole seconds before scaling, so every interval shorter than a second reports as exactly zero. It compiles, it runs, and it produces a profiler in which every zone is free.

4.2The median, in one call

§2.4 settled that a frame budget wants a median. The ring buffer holds k_history = 120 frames — two seconds at 60 Hz, long enough to be stable and short enough to respond when you press a key and the cost genuinely changes — and the median comes out of it like this:

std::nth_element is a partial sort: it puts the k-th element where it would be in a sorted range and leaves everything else merely partitioned around it — smaller on the left, larger on the right, in no particular order. That is O(n) rather than the O(n log n) a full sort costs, and the ordering it does not produce is information we would have thrown away anyway. It is exactly the right algorithm for this and almost nobody reaches for it.

The copy is not laziness either. The ring is the record; sorting it in place would destroy the chronological order that makes it a history at all, and a profiler that corrupts its own data when you read it is a profiler you will debug at the worst possible moment.

4.3Cutting the frame into zones

In main.cpp the frame is now bracketed, and where the brackets go is a decision rather than a formality:

The frame starts before the event drain, because draining events is work the frame does and a budget that starts after it has a hole in it by construction. It ends before SDL_RenderPresent, because with vsync on that call blocks until the display is ready, and a budget whose largest bar is "waiting for the monitor" tells you nothing about your renderer. The HUD prints the wall-clock frame time beside the engine total so the gap between the two is visible rather than hidden — and that gap is worth understanding, because it is why a frame-rate counter cannot tell you that you made anything faster. With vsync on, it reads 60 either way.

The sort is the interesting one. It used to live inside draw_triangles, where it would have been counted as part of fill and quietly inflated the fragment stage's number. Instrumentation forced it out into sort_back_to_front, a named function with two callers — the demo, which times it, and draw_triangles, which still does it for anyone who does not care. That is worth generalising, because it will keep happening: instrumentation shapes the code it measures. The harness's renderer projects all triangles into a vector and only then rasterizes them, which is not how you would write a naive renderer — the obvious version projects and fills one triangle at a time — and the difference exists entirely so that collect and fill can be measured apart. Pretending otherwise is how people end up with a profiler whose zones interleave and whose numbers cannot be trusted.

Not every phase is a lexical scope, though. The HUD runs to the bottom of the loop through several hundred lines of per-demo text, so it is timed with an explicit pair instead:

RAII covers the case where a phase is a scope, which is most of them; when it is not, the honest answer is to expose the primitive rather than to contort the code into a scope it does not naturally have. Note also that overlay now accumulates from two places in the frame — the debug-draw call early on and the HUD at the end — which add supports by design. A zone is a category of work, not a point in time.

A zone that reads zero

build reports 0.00 µs, and it is not broken. Placing four objects takes well under the 4.17 µs floor from §2.2, so the counter genuinely cannot resolve it. That is worth keeping rather than deleting, because it is the rule from §2.2 appearing in the engine's own output: a zone that reads zero is either work you are not doing or work you cannot measure, and the two look identical in a table. If you ever need build's real cost, it is a differential benchmark's job (§3.5), not a zone's.

4.4The budget on screen

3 toggles the budget panel. It draws a stacked bar rather than one bar per zone, and that is the whole design: separate bars answer "how big is fill?", while a stacked bar answers "what is a frame made of?", which is the question a budget exists for. It also makes the unmeasured remainder impossible to overlook, because it is the gap at the end rather than a row you can skip reading.

The remainder is drawn to the end of the bar so the bar is always exactly full, in a desaturated grey that deliberately does not look like a phase — because it is not one. It is the part of the frame nobody is measuring, and giving it a cheerful colour of its own would suggest otherwise.

The panel covers part of the render, which is not a compromise for want of screen space. It is what a profiler HUD is: it obscures the thing it is measuring, which is why it lives on a key and why its own cost is charged to overlay rather than being quietly free.

4.5The prediction, and getting it wrong

Now the measurement §1 promised. Same scene, same camera; each object drawn alone, timing only the fill.

The remaining 1.42× is itself informative rather than noise. The torus's triangles are tiny — about 1.2 pixels each — so each one pays the per-triangle setup in fill_triangle (the area, the reorientation, three colour decodes, the pre-divides) against barely any pixels to spread it over. It is the same effect as §3.3's crossing, seen from inside a single draw call.

Why get a prediction wrong on purpose?

Because the alternative is to measure without predicting, and then every result looks reasonable in hindsight. A written-down prediction is the only way to notice that your model of the machine is wrong — and noticing that is worth more than the measurement, because the model is what you will use on the next question, when there is no time to measure. Do this every time. Write the number down where you cannot revise it.

Three things in Figure 5 are worth stopping on, and only one of them is the one this lesson goes on to fix.

The perspective divide is free. Its delta is −0.018 ns/px, which is to say it is below the noise. Lesson 3.2 introduced it with an honest warning — "one divide per pixel, and it is the honest cost of this lesson" — and the measurement says the warning was unnecessary. The divide sits in a dependency chain that is already waiting on other things, so the out-of-order machinery hides it entirely. This is exactly the kind of claim that cannot be settled by reading code, and it is why 3.2 said it would be measured rather than asserting a number.

The depth test is nearly free too — 0.27 ns/px, one compare and one conditional store, on a buffer being walked in perfect order. Lesson 3.1 argued the z-buffer was worth its memory; it turns out to be worth its time by an even wider margin.

And the sRGB encode costs 6.09 ns/px, which is 2.1× everything above it combined. Coverage, colour interpolation, the perspective divide and the depth test together come to 2.94; converting the answer to a storable pixel costs more than twice that. It is three std::pow calls per pixel — one per channel — and a pow is not an instruction, it is a library function containing a logarithm, a multiply and an exponential.

Nobody would have guessed this from the code

Look at where attention naturally goes in that loop. The texture fetch is the most visually interesting thing in it. The perspective divide is the thing Lesson 3.2 spent 5,000 words on. The depth test is the thing with a whole lesson named after it. to_encoded is a one-line call at the end that has been there, unremarked, since Lesson 2.4 — and it is the largest single item. Cost does not distribute itself according to how much you thought about something.

4.7Four candidates for one function

So: make linear_to_srgb cheaper. The obvious move is a lookup table, and it does not exist — Lesson 1.6 already explained why. Decoding has 256 possible inputs so it fits in a kilobyte; encoding takes a continuous float, and there is nothing to index.

"There is nothing to index" is true about the input. Here are four candidates, of which the second and third both come from noticing that:

  1. Exact — std::pow, what we have.
  2. A fitted polynomial in nested square roots. Below the toe (x ≤ 0.0031308) the exact function is 12.92 · x, one multiply, so keep it exactly. Above it, fit a√x + b⁴√x + c⁸√x + dx — three chained square roots, each a single hardware instruction, and four multiply-adds.
  3. A table indexed by the output. There are only 256 possible answers, so there are only 255 places where the answer changes, and those tabulate exactly. The lookup becomes "how many thresholds is this value above", which is a binary search.
  4. A uniform table indexed by the input, 4,096 entries — the thing Lesson 1.6 said could not work, built anyway so that "could not work" has a number attached.
The coefficients are fitted here, not quoted from anywhere

scratch/fit_srgb.py derives them: least squares in that basis, reweighted toward minimax over sixty passes, constrained to be exact at white so that 1.0 encodes to 255 — the one value a reader will check against a screenshot. Excluding the toe from the fit is what makes it good: every basis function has an infinite slope at zero and the truth has a slope of 12.92, so a fit forced to cover the toe spends all its freedom there and is worse everywhere. Measured: including the toe costs 3 codes of worst-case error; excluding it costs 0.0115.

The exact threshold table is slower than pow. 6.919 ns against 3.497 — a "speedup" of 0.51×. It is a beautiful idea, it is exactly correct, and it loses, because eight dependent L1 loads in a binary search is a longer latency chain than a modern powf. This is precisely the kind of candidate that gets shipped on the strength of the argument for it, and the only reason it is not in the engine is that somebody timed it.

The naive table is the fastest thing on the list. 0.994 ns, 3.52×, nearly twice as fast as the polynomial we are about to ship. It also passes the round trip, so it cannot be dismissed on correctness the easy way. Rejecting it takes an actual argument, and the first argument tried did not survive contact with the data.

4.8The hypothesis the data refused

The objection to the table writes itself: it occupies 16 KiB of cache, and a fill loop is already dragging a colour buffer and a depth buffer — four megabytes between them — past the same cache. In a microbenchmark the table is the only thing in memory. In a real frame it should be evicted constantly.

So verify_310 §F2 runs all four again with a framebuffer-sized stream running alongside — one colour store and one depth store per encode, which is exactly what a fragment does. The result:

No penalty. For any of them. The 16 KiB table costs nothing measurable even with four megabytes streaming past it, and the argument this section was written to make is simply false on this machine — because, as §4.10 shows, this CPU's L2 is large enough that a few megabytes are nearly free. The test is kept, with its result, because a hypothesis that got tested and failed is worth more to you than one that was quietly dropped. It may well hold on a machine with a smaller L2, which is exactly the argument for measuring on the machine you ship to instead of reasoning from a cache diagram.

The real reason is in the accuracy column, and it is one number: 0.0115 codes against 0.4022, a factor of 35. Both round to within one code at 8 bits, which is why the worst column cannot see the difference — but 0.4 is nearly the entire half-code budget, and 0.0115 is a hundredth of it. Push both against a deeper target and the hidden gap becomes the whole answer:

Module 6 renders into a float target and encodes at the end of a post-processing stack that may convert several times over. The polynomial's error is a property of the curve and stays where it is; the table's is a property of its cell width and only shrinks if you make the table bigger. An approximation that is only good enough because the output format is coarse is an approximation with an expiry date, and this one expires in three modules.

Two wrong reasons, one right one

This section reached the conclusion it originally set out to reach, by a route that has nothing to do with the argument it started with. That is common and it is worth being unembarrassed about — but only if you go back and change the argument. Shipping the right decision with the reasoning that failed is how folklore is manufactured: the next person inherits "tables blow the cache" as received wisdom, with a measurement sitting right there that says otherwise.

One more measurement, because Module 3 has been accumulating memory without ever asking what it costs. vertex went from 28 bytes to 52 in Lesson 3.8. The colour and depth buffers are two separate streams. A 64×64 texture is 16 KiB and a 2048×2048 one is 16 MiB. Which of those matters?

A cliff, and not where the folklore puts it. Everything up to four megabytes is free on this machine, because its L2 is enormous; only at 16 MiB does the data have to come from main memory, and then a fetch costs 1.7× more for running exactly the same instructions. "The texture must fit in L1" is advice for a different computer, and repeating it here would be quoting somebody else's constants — the specific error §1 warned about.

The second cache measurement is the one that changes how you read every other number on this page. §4.6's ladder says a nearest fetch costs about 9 ns inside the fill; the table above says 2.3 ns. Both are right. With a control to isolate it:

The same instruction sequence, 2.27× more expensive, because in a tight loop consecutive fetches overlap in the pipeline and in situ each one sits in a dependency chain — its uv comes from the perspective divide, its result feeds the encode — with nothing to overlap with. A function's cost is not a property of the function. It is a property of the function and its surroundings, which is why §3.5's ladder measures inside the real loop and why a microbenchmark can only ever be a hypothesis about a real one.

4.11The capstone

Press Tab to the scene demo, C to the model scene, M for a texture, G to per-pixel, U to cull back faces, and 3 for the budget. What is on screen is the whole of Module 3 at once: a textured, lit, z-buffered, back-face-culled, near-plane-clipped, perspective-correct 3-D scene, loaded from a file, rendered by code you wrote, every pixel of it, on the CPU — with a budget beneath it that accounts for every microsecond and a unit cost you could quote to somebody else.

The number to sit with is 45.47 ns per covered pixel. A frame at 1280×720 covers about 475,000 pixels, so that is 21.6 ms — over budget at 60 Hz, from one object and a floor. Module 4's GPU does the same work at a scale that makes those units meaningless, and the reason will not be that its code is cleverer. It is that it does thousands of these at once. Every idea it uses to do that — coverage, interpolation, depth, sampling, shading — is the one you just built, and you now know what each of them costs.
