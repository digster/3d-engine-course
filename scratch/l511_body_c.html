10Common Pitfalls & Debugging

The debug view draws nothing at all

Symptom. The queue reports a sensible size() in the debugger, the flush runs, and the screen is unchanged.

Cause. Almost always the order: advance() is running before the flush, so every default-lifetime line is deleted on the frame it was queued. It reads exactly like "my queueing code never ran", which is why people go and instrument the queueing code.

Fix. advance() is the last thing in the frame. Diagnose it in one step by queueing something with seconds = 5: if the five-second line appears and the default ones do not, it is the order and nothing else.

Debug lines pile up and the drop counter climbs

Symptom. dropped() is non-zero and rising; older markers stay on screen forever.

Cause. Either a real overflow — you are queueing more than the capacity every frame — or advance() is not being called on some path. The --shot path is the classic one: it returns early, and a queue aged only inside the "we have a camera" branch never ages on a frame with no active camera.

Fix. Age unconditionally, outside every branch. In this lesson's demo advance() sits outside the camera check for exactly this reason.

A key stays held after using the panel

Symptom. The camera keeps yawing after you interact with the UI. Tapping the key once fixes it.

Cause. The action map stopped being updated while the UI had focus — either by an if (!ui.wants_keyboard()) around update(), or by events being routed to ImGui and not passed on. Both leave a level stuck true, and a level is only corrected by the event that contradicts it.

Fix. Always update, always through the mask. Never withhold an event from engine::input.

The camera whips round when you let go of a slider

Symptom. Dragging an ImGui widget is fine; releasing it snaps the view by roughly the distance you dragged.

Cause. The mouse position was frozen during the block rather than rebased, so the first unblocked frame differences against a position from several hundred milliseconds ago.

Fix. The virtual cursor of §6.2 — and note that the diagnostic is already on screen: the offset readout should stop growing the instant you release, and the delta the frame after should be small.

One frame of input leaks into the game after clicking a text field

Symptom. The first character you type after clicking into a field also triggers whatever that key does in the game. Only the first.

Cause. begin_frame() is running after the capture flags are read — usually because it was placed next to the panels in on_overlay, which is where it looks like it belongs. Every read then answers about the previous frame.

Fix. begin_frame() first in on_input(). It is one line, and moving it is the entire fix.

ImGui asserts inside ProcessEvent on start-up or shutdown

Symptom. An IM_ASSERT firing with "Context or backend not initialized!"

Cause. Events arrive before on_start() has run and after on_stop() has torn the backends down. ImGui's backend functions are not total: they assume a live context.

Fix. The if (!running_) return; guard at the top of every forwarding function in debug_ui. That guard is not defensive decoration — it is what makes the class usable on a surface that never starts one.

The panel is invisible, or draws under the scene

Symptom. ImGui reports no errors and nothing is on screen.

Cause. render() is being called before blit_framebuffer() — so the framebuffer blit paints over it — or the render scale was left at something other than 1 by a previous overlay call.

Fix. on_overlay() is the hook, and it exists precisely because "after the blit, before the present" is a moment nothing else has. Restore any SDL_SetRenderScale you set before returning from it.

11Exercises

  1. 11.1 — Draw the thing you cannot see. Add a debug_lines::frustum(const mat4& view_projection, Uint32, float) that draws the camera's own frustum, and call it for the inactive camera in ecs_swarm — the one you are not looking through. Press [C] and watch the other camera's frustum swing past.

    Hint

    The eight corners of a frustum are the eight corners of the NDC cube pushed through the inverse of the view-projection matrix, then divided by w. The cube is x, y ∈ [−1, 1] and z ∈ [0, 1] — Lesson 4.2's depth range, not OpenGL's. Then reuse k_box_edges.

    Solution sketch

    Build the eight corners, transform, divide, and emit the twelve edges. The perspective divide is what makes it a frustum rather than a box, and it is worth stopping to notice: you have just run Module 2's pipeline backwards, and the shape that comes out is the shape that was mapped to a cube.

  2. 11.2 — A panel that edits the world. Add a table of entities with a selectable row, and an inspector that shows the selected entity's local placement with three DragFloat3 widgets writing straight into the component. Queue an axis triad on the selection so you can see what you are editing.

    Hint

    Store the selected entity, not a pointer to its components — the pointer dangles the moment a pool reallocates. registry::alive() is your check each frame, and it is exactly why Lesson 5.4 built generational handles.

    Solution sketch

    This is Module 9's inspector in miniature, and the shape you arrive at is the right one: the panel holds an id, re-resolves it every frame, and shows nothing when the resolve fails. That is the whole reason a handle is not a pointer.

  3. 11.3 — Depth-tested debug lines. Add a bool depth_tested to debug_line and honour it in the software backend, so a hierarchy line passing behind geometry is hidden. Then draw the same scene with the flag on and off and decide which you actually prefer.

    Hint

    draw_line does not consult a depth buffer, so the interesting work is deciding what a line's depth even is — it varies along the segment, so a per-pixel test needs the interpolated 1/w the rasterizer already computes for triangles (Lesson 3.2).

    Solution sketch

    Two passes: depth-tested lines first, overlaid lines second, so an overlaid line is never hidden by a tested one. That ordering requirement is the real content of the exercise — it is the first time the queue's order becomes part of its contract rather than an implementation detail.

  4. 11.4 — The other backend. Bring the debug UI up on surface::gpu in sandbox, using imgui_impl_sdlgpu3. §7.1 has the signatures.

    Hint

    debug_ui needs a second start() taking an SDL_GPUDevice* and the swapchain's texture format, and a render() taking a command buffer and a render pass. The platform backend does not change; only the renderer half does.

    Solution sketch

    The awkward part is not ImGui, it is that PrepareDrawData must be called with the command buffer before the render pass begins and RenderDrawData inside it. Your render() therefore splits into two functions, and the demo has to call them at two different points — which is a fair description of the difference between the two surfaces generally.

  5. 11.5 — Break the seam on purpose. Replace the mask with the two wrong designs from §6, one at a time: first skip actions_.update() while the UI has the keyboard, then freeze the reported cursor position instead of rebasing it. Reproduce both symptoms deliberately and write down the sequence of actions that exposes each.

    Hint

    The first needs a key held across the moment focus is taken. The second needs a long drag — the bug is proportional to how far you dragged, so a small drag hides it, which is exactly why it survives testing.

    Solution sketch

    Both are one-line changes and both produce a bug that a casual test passes. That is the point of the exercise: these are not mistakes you avoid by being careful, they are mistakes you avoid by knowing that a level and a delta fail in different ways.

12Recap & Next

The engine gained a debug-draw system and a tooling UI, and Module 5 is finished.

  • A queue that anybody can fill. debug_lines holds world-space segments with lifetimes, bounded and counted, and includes nothing that can draw — so a collision system in Module 8 will be able to queue a contact normal without compiling the renderer.
  • A backend, not a replacement. Everything in debug_draw.hpp survived; the queue was put in front of it. draw_debug_lines is four lines because six lessons of clipping were already correct.
  • Lifetimes, because events are invisible without them. A single-frame marker is on screen for 16.7 ms and a person needs about 250. The expiry rule tests before it subtracts, so a paused clock cannot leak.
  • Dear ImGui, taken publicly and contained. 41,385 lines we did not write, 182 lines that own the lifecycle, and a rule about which code is allowed to speak it.
  • An input seam that changed nothing it did not have to. masked_input is a new type satisfying 5.10's concept; action_map is unchanged to the character. The arbitration is on levels, never on events.
  • A virtual cursor, because a delta cannot be masked by masking one of its endpoints — the subtlest thing in the lesson and the one most likely to ship broken.

60 checks green in debug and release; verify_45 through verify_510 still green; and the reference shot from Lesson 5.1 byte-identical for the eleventh consecutive lesson, which is now a slightly stronger statement than usual: this lesson changed a function signature in the middle of the reference render's own call path and the output did not move by one bit.

Next: Module 6. The renderer stops being adequate and starts being correct. It opens with the lesson every graphics programmer needs exactly once and then has forever — linear versus sRGB — and the reason it opens there is that every lighting result in the module is wrong until it is settled. Lesson 1.6 promised that payment would come due; it is due now.

Both halves of this lesson get their return in that module and the two after it. The debug queue becomes the thing that makes shadow-map frustums, tangent frames and culling bounds visible instead of theoretical; the panel becomes how a BRDF's three terms get separate sliders. And Module 9's editor — hierarchy, inspector, gizmos — is built on exactly the two files this lesson added.
