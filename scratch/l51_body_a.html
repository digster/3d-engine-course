Module 5 — Becoming an Engine · Lesson 5.1

The Refactor: Engine, Demos, and the Public API

Four verification harnesses in a row have had to transcribe the scene by hand, because the function that builds it lives in an anonymous namespace inside a 7,789-line main.cpp. Today we draw a line through that file and through the whole tree: a static library with public headers, and programs that may include only those. The line is not a convention — it is the include path, and the compiler enforces it. And because a refactor's entire claim is that nothing changed, we write the thing that could prove it wrong first.

1The Problem

Open scratch/verify_48.cpp from Lesson 4.8 and scroll to the middle. There is a function in there that builds three objects — an icosahedron, a slab, a plinth — at particular positions, with particular scales, spinning at a particular rate. Now open scratch/verify_49.cpp. It is there too. And in verify_47.cpp. And verify_46.cpp.

Four copies of the same geometry, typed out four times, because the original lives here:

An anonymous namespace is C++'s way of saying nothing outside this translation unit may ever refer to this. It is the right default and it was the right choice at the time. But it means that a second program which wants the same picture has exactly one option, and that option is a copy.

Copies rot. Nothing in the build compares verify_48's transcription against the demo it is checking, so a change to one and not the other produces a harness that passes while checking the wrong scene — the most expensive kind of green tick there is. This has not happened yet. It is going to.

The number that should worry you is four, not 7,789. A big file is a nuisance. A file whose contents cannot be reached is a structural problem, and it gets worse every time somebody works around it rather than every time somebody adds a line.

The tell

src/main.cpp currently runs to 7,789 lines and holds: five software demos on Tab, the GPU probe that Lessons 4.2 through 4.7 were built on, Lesson 4.8's ported scene, a mesh cache keyed by the address of a vector's first element, the frame budget HUD, an orbit camera, an OBJ model loader's calling code, a floor generator, three procedural textures, and the entire CPU render pipeline.

Here is the diagnostic that matters. Go down that list and, for each item, answer one question: would a game need this?

The problem, then, is not that main.cpp is large. It is that the tree cannot tell you which half of itself is the engine, and neither can you, and neither can the compiler — which means the question never has to be answered, so it never is.

2Building Intuition

2.1   A library is a thing with an outside

Every program you have written in this course has been a closed world. You could rearrange anything, rename anything, change any function's signature, and the only thing that could possibly object was the same body of code, which you also controlled. That is an enormous freedom and it has been the right one for four modules.

A library gives it up on purpose. The moment some code has consumers you do not control, its surface stops being an implementation detail and becomes a promise. Break the promise and you break somebody else's build — and the somebody else, in our case, is the capstone game in Module 9, plus every demo, plus every harness. They are all us, but they are us at a distance, which is exactly the point: an API is a message you write to a person who cannot ask you what you meant.

Everything else in this lesson follows from that one asymmetry. A function with a single caller in the same file has never had to answer a question. Publish it, and it must suddenly answer all of them at once: who owns this pointer, what must be true when you call me, what happens if it is not, what does a caller who does not care about your seventh parameter write instead, and what do I have to change if you want an eighth.

2.2   The question the boundary asks about every file

Drawing the line does something a tidy-up never does: it forces a verdict on every single file. There is no "we'll decide later" bucket, because there are only two directories and a file has to be in one of them.

The rule we will use, and it settles almost every case in one reading:

A thing belongs to the engine if a different game, one we have not written, would want it. It belongs to a demo if it exists to show, teach, or drive this particular program.

Applied to collect_triangles: any game drawing 3-D through a CPU rasterizer wants it. Engine. Applied to build_scene: no game wants our icosahedron at our position. Demo. Applied to next_cull(), which advances a cull mode to the next one so that the U key can cycle it: an engine shipping that function is shipping this demo's key bindings to everybody who links it. Demo.

Where the rule genuinely does not settle it — and there are a handful — §7 lists them rather than pretending otherwise.

2.3   Why the include path, and not the style guide

Suppose we do the split, write the rule down, and agree to follow it. Here is what happens. Someone — you, in eleven weeks, at half past eleven at night, one small feature from a working build — needs a function that lives in engine/src/. Including it directly works. It compiles, it links, it ships. Nobody is watching.

A boundary maintained by discipline lasts exactly until the first time somebody is in a hurry, and everybody is eventually in a hurry. So we do not maintain it by discipline. We put the public headers in one directory, the private ones in another, and hand each target only the directory it is allowed to see. Then the November-at-half-eleven version of you writes the include, and this happens:

That message is the architecture. It is not a review comment, not a lint rule somebody can suppress, not a paragraph in a document nobody has opened since onboarding. It is a compiler, which is never in a hurry and never makes an exception, and it costs exactly one line of CMake to obtain.

This is the general principle and it is worth more than the lesson it is in. Prefer rules a machine enforces over rules people remember. Every architectural constraint you can express as a build-system property, a type, or a compile error is a constraint that still holds after you leave. Every one you express as a convention is a constraint with a half-life.

3The Theory

Four ideas, each with a worked example taken from our own code, because "design your API well" is advice of the same quality as "write good code".

3.1   What makes a good public API

(a) It is written in the caller's vocabulary, not the implementation's. projection_scratch is a name from the inside — it describes some arrays the algorithm reuses. camera_view is a name from the outside: it describes a thing the caller already has an idea about. When the two conflict, the caller wins, because the caller is the one reading.

(b) State that always travels together travels as one thing. If two parameters are always derived from the same source and always passed together, they are one parameter that has not been named yet. We have hit this three times now: fill_style in Lesson 3.2 gathered the rasterizer's state, projector in 3.3 gathered the projection and viewport, and today render_options gathers the pipeline's policy. The pattern is settled: gathering is not tidying, it is the removal of a way to be wrong. A caller cannot forget to update the second of two loose parameters if there is only one.

(c) Every default is the correct answer. This one is worth stating as an absolute. Our pipeline offers trs_order::tsr, which deforms objects, and correct_normal_matrix = false, which is Lesson 3.6's bug — because a failure you can summon on a keypress teaches more than a paragraph describing it. But default-constructing render_options cannot get you a wrong picture. Reaching a wrong answer costs you a line of code that says its name out loud.

(d) Instrumentation is optional and says so in the type. The old signature took clip_stats& — a reference, so every caller had to supply one. Five of the eight call sites did not want the numbers, and each declared a variable called ignored to satisfy the compiler. Seven such variables existed in the codebase. A pointer defaulting to nullptr deletes all seven and tells the reader which parameters are the function's job and which are the observer's.

3.2   A worked example: fifteen parameters

Here is what four modules of organic growth produced. Every one of these parameters was added by a lesson that needed it, each addition was locally reasonable, and nobody ever looked at the whole list:

Do not read it as a list of fifteen things. Read it as a list of kinds of thing, and count how many of each there are.

@@FIG_PARAMS@@

Seven of the sixteen rows are the same kind — policy, the choices a caller makes about how the pipeline should behave. Three more are the camera, spelled as two separate values a caller has to remember to derive from the same place. The arithmetic is immediate: fifteen parameters, minus seven policy values, plus one render_options, minus three camera values, plus one camera_view, minus one count folded into a std::span, minus one normal_stats* folded into collect_stats, gives eight.

And now the number that shows why nobody had fixed it. There were eight call sites. Adding a ninth knob to the old signature meant editing eight calls, in a file where the calls are forty lines apart, and getting one of them subtly wrong is a bug you find in a screenshot three weeks later. With the struct, adding a knob is adding a field, and the seven call sites that do not care never mention it. The bad signature was not just ugly. It was a tax on ever improving the thing it belonged to.

Note what did not happen. Nothing was removed from the pipeline. Every capability the fifteen-parameter version had, the eight-parameter version has, and §4 proves it to the byte. Redesigning an interface and changing behaviour are two jobs, and doing them in the same edit is how you end up unable to say which one broke the picture.

3.3   Physical design: what a header costs

Logical design is what your types mean. Physical design is which file each one lives in, and it is the half that decides how the project feels to work in. The rules from our own style guide, now with reasons that bite:

A header must be self-sufficient. Including it first, alone, must compile. If soft_renderer.hpp only works because raster.hpp happened to be included above it, then the day somebody reorders two lines the build breaks in a file nobody touched. This is checkable, so we check it: all 37 of our public headers compile on their own.

One primary type per header, named after it. This is why projector.hpp exists. When the moved code first landed, projector, screen_point, to_pixel and screen_from_clip were sitting inside soft_renderer.hpp, where they had happened to arrive. Then debug_draw.cpp needed them — a wireframe is drawn through the same projection as a filled triangle — and the debug overlay would have had to include the entire software renderer to stroke a line.

A type that two components share is a header, not a section of whichever one defined it first.

And a header is a promise about rebuild time. Not a metaphor: change a .cpp and one object file is recompiled. Change a .hpp and every translation unit that includes it, directly or transitively, is recompiled. So we measured it on this project — touch one file, rebuild, take the best of three:

@@FIG_COST@@

2.3× between the cheapest and the most expensive edit, on a project of about twenty-two thousand lines. The absolute numbers are trivial — under a second, all of them — and quoting them as if they were a hardship would be dishonest. The ratio is the part that travels. Multiply the codebase by fifty and the private-source edit is still one object file while the public-header edit is still everybody, and the two numbers are a coffee break apart. That is the pressure that produces forward declarations, the pimpl idiom, and module systems — and it is why "should this be in the header?" is an engineering question and not a filing question.

3.4   Dependency direction as a design tool

Dependencies have arrows, the arrows should point one way, and which way they point is a design decision you get to make rather than a fact you discover.

@@FIG_DEPS@@

CMake gives us three words to say it with, and the distinction between them is the most useful thing in the whole tool:

PUBLIC, PRIVATE and INTERFACE in CMake
keywordwho gets itours
PUBLICus, and everyone who links us engine/include; SDL3::SDL3
PRIVATEus alone engine/src; stb_image
INTERFACEeveryone who links us, but not us (unused here — it is for header-only libraries)

stb_image being PRIVATE is the case worth studying, because it is a wrapper paying off. Exactly one translation unit — engine/src/gfx/image.cpp — includes stb_image.h, and image.hpp exposes our own engine::image instead. So the dependency stops at the boundary: a demo cannot see stb, cannot accidentally start depending on it, and would not notice if we replaced it. A demo that tries anyway is refused at compile time, and we check that this is true rather than assuming it.

SDL3::SDL3 being PUBLIC is the case worth being honest about. It is not a choice; it is a consequence. framebuffer.hpp says Uint32, gpu_device.hpp takes an SDL_Window*, input.hpp reads an SDL_Event. Those are SDL's types in our public signatures, so anybody who includes our headers needs SDL's headers too, and PUBLIC is CMake's word for "this dependency is contagious, and it has to be". An API that names another library's types has adopted that library's vocabulary permanently. We keep it — SDL is our platform layer and pretending otherwise would cost more than it saves — but we keep knowing about it, and Lesson 5.2 is where the seam gets examined.

One more piece of direction, and it is free: add_subdirectory(engine) comes before add_subdirectory(demos) in the top-level CMakeLists.txt. Swap the two lines and the configure fails, because engine::engine would not exist yet when demos/ asked to link it. An architecture rule enforced by the order of two lines is the cheapest enforcement you will ever get.

3.5   The umbrella header, weighed

Should the engine ship <engine/engine.hpp> — one include that pulls in everything? The received wisdom is no, and the received wisdom is worth measuring, because SDL itself ships exactly that: <SDL3/SDL.h> is an umbrella over forty siblings.

Two translation units, identical except for their first line, both using nothing but engine::framebuffer:

Umbrella header versus including what you use
first linepreprocessed linessyntax-only compile
#include <engine/engine.hpp>82,507262 ms
#include <engine/gfx/framebuffer.hpp>72,942215 ms

22% slower, and only 13% more preprocessed text — a much smaller penalty than the folklore predicts. The reason is instructive and it is not to the umbrella's credit: SDL already dominates. Nearly 73,000 lines arrive before we contribute anything, because framebuffer.hpp pulls in <SDL3/SDL_stdinc.h> for one typedef. Our thirty-seven headers add under ten thousand on top of that. So the honest conclusion is not "umbrellas are cheap"; it is that on this project the umbrella is not where the compile time is, and if we cared we would go after the SDL include in framebuffer.hpp first.

We ship it, and document what it is for: small programs, throwaway tests, the first hour of learning the API. It is also the shortest complete statement of what the engine offers, which makes it a table of contents. Anything built more than a few hundred times should include what it uses — and every demo in this repository does, which is why the umbrella has no callers at all in the code we ship. That is not a contradiction. It is the difference between providing something and depending on it.
