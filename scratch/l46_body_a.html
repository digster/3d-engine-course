Module 4 — To the GPU: SDL_GPU · Lesson 4.6

Uniform Data and the Matrix Upload

The camera in Lesson 4.5's vertex shader was a pile of static const floats, frozen at compile time because there was no way to send it anything. This lesson gives the shader a third kind of input — data that is the same for every vertex of every instance — and finds out, by measurement, exactly which bytes arrive where. One of the answers contradicts a claim this course has carried since Lesson 2.6, and the other contradicts SDL's own documentation.

1The Problem

Here is the camera Lesson 4.5 drew with, in full:

Seven constants, and eleven lines of arithmetic further down that used them. The maths was honest — it is Lesson 2.10's projection matrix written out term by term — but the numbers were welded into the shader, and a camera welded into a shader is not a camera. It cannot orbit, it cannot follow anything, it cannot even adapt to a resized window without the viewport being asked to compensate.

So: send the shader a matrix instead. The obvious question is through which buffer, and the answer is neither of the ones we have.

The vertex buffer is per-vertex. Our torus has 1,225 vertices and is drawn seven times, so putting a view-projection matrix there would mean writing the same sixteen floats 8,575 times a frame — 548 kilobytes to say one thing. The instance buffer is per-instance, which is better arithmetic and worse modelling: the camera is not a property of an instance, and writing it seven times says something false about what it is.

What the camera actually is, is per-frame: one value, shared by every invocation of every shader in the draw. That is a third rate of change, and it needs a third mechanism.

Not yet

Still no depth test. That is Lesson 4.7, and giving the camera freedom is about to make its absence obvious: orbit until two tori overlap and you will see the later one drawn over the nearer one. Lesson 4.5's fixed camera hid this by arranging the scene so nothing overlapped. That is worth noticing as a general shape — a limitation you have designed around stops being visible, and starts being load-bearing.

2Building Intuition

2.1 Three rates, not two

Every piece of data a shader reads changes at some rate, and there are exactly three that matter for a draw call.

@@FIG_RATES@@

Lesson 4.5 built the first two and showed that the difference between them is one enum value — input_rate on a buffer description. It is tempting to expect the third to be more of the same: a buffer, a slot, a rate called PER_DRAW. It is not, and the reason is that the first two are fetches — the hardware indexes into an array using a counter it is already keeping — while the third is not an array at all. There is one value. Indexing into it would be indexing into a single element with a counter that never advances.

2.2 The buffer that does not exist

If you have used OpenGL or D3D11, you know the shape of the answer you expect: create a uniform buffer object, fill it, bind it to a slot, draw. Go looking for it in SDL_GPU and it is not there. Here is the complete list of things a buffer can be:

Read the first parameter again. Not a device, not a render pass — a command buffer. You are not creating a resource and binding it; you are recording bytes into the command stream, and every draw recorded after that point reads them.

@@FIG_PUSH@@

Three consequences follow immediately, and all three are simplifications:

  • There is no lifetime to manage. No create, no release, no move-only wrapper class. Every other GPU resource in this engine needed one; this needs none, because there is no object.
  • There is no synchronisation hazard. Lesson 4.5 built gpu_stream_buffer with cycling precisely because a per-frame write can land on a read the GPU has not performed yet. A push cannot: the bytes are copied into the command buffer at the moment of the call, and that command buffer is not executing yet.
  • Ordering is the only rule, and it is the obvious one. A draw sees the most recent push before it. Measured: push 201, draw, push 77, draw — the second draw reads 77, with nothing bound, rebound or released in between.

The cost of those simplifications is that the bytes are copied, once per call, which is why this mechanism is for small data and why §4.6 measures where "small" ends.

3The Theory

3.1 Why alignment rules exist at all

You are about to meet a rule about where fields may sit in a uniform block, and it will make much more sense if you know what it is protecting.

A GPU reads uniform data in 16-byte units — four floats at a time, matching the width of the vector registers the shader cores work in. Call one such unit a register. Fetching a float4 that sits exactly on a register boundary is one load. Fetching a float4 that starts four bytes into a register is two loads plus a shift to glue the halves together — for every invocation, of which there are millions.

So the hardware would rather not, and the shading languages make sure it never has to, by forbidding a vector from straddling a register boundary. That single sentence generates the entire rule. Everything else is bookkeeping about where the boundaries fall.

3.2 The rule, and the one SDL's header names instead

Here is what SDL's header says about the data you push:

The data being pushed must respect std140 layout conventions. In practical terms this means you must ensure that vec3 and vec4 fields are 16-byte aligned.

That is good advice and it is not what our toolchain does. HLSL has its own constant-buffer packing rule, and it is looser:

HLSL constant-buffer packing, in one sentence

Fields are placed in declaration order and packed tightly, except that a vector may not straddle a 16-byte register boundary — if it would, it starts at the next boundary instead. A scalar is never moved.

The difference from std140 is that std140 also requires every float3 and float4 to start on a 16-byte boundary, while HLSL is happy for a float3 to sit at byte 68, tucked in behind a scalar at 64, because 68 through 79 is still inside register 4.

Which one governs? Whichever one the compiler used — because the offsets are baked into the compiled shader, and SDL simply copies your bytes to where that shader will look. Compiled through shadercross, ours uses HLSL's rule. We know because the offsets are visible in the compiled SPIR-V:

So why follow SDL's advice at all, if it describes a stricter rule than the one in force? Because std140 is a superset: a layout that satisfies it automatically satisfies HLSL packing, since a field on a 16-byte boundary cannot straddle one. Following SDL's advice costs a few bytes of padding and makes the question of which rule applies stop mattering — including if you later add a GLSL front end, where std140 is the rule.

The habit that makes this go away

Pair every float3 with a float. The two together fill a register exactly, so the next field starts on a boundary, so nothing can straddle, so both rules agree. Our lighting block is float3 to_light; float ambient; float3 sky; float diffuse; — thirty-two bytes, two registers, no padding to explain to anyone. Most real uniform blocks can be arranged this way with a little thought, and the thought is cheaper than the bug.

3.3 A worked example, field by field

Take the block above and walk it by hand. Registers are 16 bytes, so their boundaries are at 0, 16, 32, 48, 64, 80, 96.

  1. float4x4 m — a matrix is four float4 columns, each 16 bytes. Starts at 0, occupies 0–63, ends exactly on a boundary.
  2. float scalar_a — a scalar is never moved. 64, occupying 64–67.
  3. float3 vector_b — 12 bytes. Placing it at 68 occupies 68–79. Register 4 runs 64–79, so this fits entirely inside it. 68. (std140 would have moved it to 80.)
  4. float scalar_c — the cursor is at 80. A scalar is never moved. 80.
  5. float2 pair_d — 8 bytes at 84 occupies 84–91. Register 5 runs 80–95, so it fits. 84.
  6. float3 vector_e — 12 bytes at 92 would occupy 92–103, and register 5 ends at 95. It straddles, so it moves to 96.

Now write the same fields as a C++ struct with no padding and run the same walk. C++ has no register concept; it aligns each float to 4 and packs. Every field lands in the same place — until the last one, which C++ puts at 92.

@@FIG_PACKING@@

Four bytes, one field, and the consequence is precise: the shader reads vector_e from bytes 96–107, which is where C++ wrote the second component onward. Measured, having written (241, 242, 243):

Shifted by exactly one float, with a zero on the end where the read ran past what was written. And note which fields survived: everything before the divergence. A uniform layout bug corrupts the tail of a block, so the first thing you look at is usually fine — which is the opposite of Lesson 4.5's vertex-pitch bug, where vertex 0 was always right and things got worse further in. Both are "the beginning looks fine", for completely different reasons.

This is worth a moment's reflection beyond the immediate fact: an intermediate representation is allowed to describe your data in its own vocabulary. The only thing that settles a question like this is a measurement at the endpoint you actually care about — which took one probe shader and about forty lines.

3.5 The register space, and who checks it

Lesson 4.3 established that SDL fixes the register space per stage, and that it is not negotiable. The uniform blocks in this lesson are the first ones the engine actually draws with, so it is worth having the whole table in front of you:

@@FIG_SPACE@@

Lesson 4.3 said a wrong space would be "silent". That was a reasonable inference and it turns out to be half right, in an interesting way. Put the fragment shader's cbuffer in space0 and ask each tool in the chain what it thinks:

Which tool catches a wrong register space
toolverdict
glslc, HLSL → SPIR-Vaccepted — it does not care
the JSON reflectionbyte-identical to the correct shader
spirv-dis | grep DescriptorSet0 instead of 3 — visible
shadercross, SPIR-V → MSL REFUSED: "Descriptor set index for graphics uniform buffer must be 1 or 3!"

So the build catches it — on the way to Metal, and equally on the way to DXIL — with an exact and correct message. That is Lesson 4.3's argument for compiling offline paying off from an unexpected direction: compiling ahead of time did not just save runtime cost, it moved a failure that would otherwise have been a black screen into a build error on your own machine.

Two caveats, both important. The reflection cannot see it — the JSON is byte-identical, which means the cross-check that saved Lesson 4.5 is no help here at all. And a Vulkan build consumes the SPIR-V directly, with no translation step to refuse, so there is nothing in that path to catch it.

⚠ Verify on your backend

The refusal above was measured on the MSL path. The DXIL path goes through the same SPIRV-Cross step and should behave identically; the SPIR-V path has no such step and presumably reads the wrong descriptor set at runtime. That last sentence is a prediction, not a measurement — there is no Vulkan device on the machine this lesson was written on. If you have one, this is a ten-minute experiment and the answer belongs in your notes.
