9. Implementation: quads, a pipeline, one draw call

Everything above is arithmetic. What reaches the GPU is twenty bytes per vertex and one draw call, and three decisions in that are worth reading.

9.1 The colour is four bytes, not a word

Everywhere else in this engine a colour is a packed Uint32 in ARGB order — pack_argb, since Lesson 1.6. A vertex attribute is not a word. SDL_GPU_VERTEXELEMENTFORMAT_UBYTE4_NORM hands the shader the four bytes in memory order, so a packed ARGB word arrives on a little-endian machine as (B, G, R, A) and the text comes out blue.

This is not hypothetical. Lesson 6.15 shipped exactly this bug in a BRDF lookup table, and it survived review because green occupies bits 8–15 in both layouts, so half the data read correctly and the result was merely dim. So overlay_vertex names its four colour bytes:

Naming the bytes makes the endianness question disappear rather than making it catchable, which is a strictly better outcome than a test. set_colour is the one place the ARGB convention is unpacked, and there is nothing left to get wrong.

9.2 The atlas is one channel, and never _SRGB

gpu_texture gained a new entry point rather than a flag on the old one:

Every argument create_sampled makes is about colour: four channels because a picture has three plus alpha, and an srgb flag because a colour is stored through a transfer function. A glyph atlas is neither. It is one byte of coverage per texel, linear by construction, and there is no flag combination on the four-channel path that expresses that — create_sampled(..., srgb=false) would store the right numbers in four times the memory and leave the next reader unable to tell whether the choice was considered.

The 4× is real (16,384 bytes against 65,536 for our atlas) but it is the smaller half of the argument. The larger half is that a distinct entry point with "coverage" in its name is the documentation, and §7.3 is what happens when it is missing.

9.3 One pipeline, blending on, depth off

The pipeline is blend(false) — straight alpha — and nothing else. Straight rather than premultiplied because there is nothing in a coverage atlas to have been multiplied: the shader produces (tint, coverage × vertex_alpha) and the ROP does the rest.

No depth state at all, and it is worth stating the absence rather than leaving it as one. The overlay is drawn last, into a target with no depth attachment, in declaration order — and declaration order is the sort. That is the correct answer for a HUD and it is why overlay_batch has no sort key: Lesson 6.11's order_draws sorts transparent geometry back to front because depth decides what is in front of what; here the programmer decides, and a sort would be second-guessing them.

Culling stays at the course default (counter-clockwise front, back faces culled) rather than being disabled, which turns the winding in push_quad into something the hardware checks: get it backwards and the overlay is invisible on the GPU while remaining perfect on the CPU, which is precisely a divergence §11's comparison exists to catch.

9.4 The flip lives in one line

Pixel space has +y down; SDL_GPU's clip space has +y up. That conversion happens exactly once, in the vertex shader:

No projection matrix. An orthographic matrix would do the same job in four dot products and would invite somebody to put a camera in it; an overlay has no camera, it has a viewport. And inv_half_viewport is 2/width and 2/height, computed on the CPU once per frame rather than divided per vertex — which is the entire reason this is a shader instead of arithmetic baked into the vertices, since a window resize then pushes eight bytes rather than rewriting every quad.

10.2 And the honest half: what it does not catch

Declare the overlay with discard_write instead — "I write every texel and read none", which for a blend is a lie — and the graph compiles it happily and derives DONT_CARE, which would erase the entire frame under the text. The harness asserts that too, as a pass:

check(wrong.compile(r.gpu), "discard_write also compiles — this is NOT caught");

So the graph does not verify dataflow claims; it relocates them. A load op buried in a struct three files away becomes a sentence about arithmetic at the call site, which a pass author can answer correctly without understanding render passes. It cannot check that the answer is true. Saying so is the point — a tool oversold is a tool that gets trusted in the one case it does not cover.

11. The instrument, and proving it can fail

The characterization shot is a null instrument for this lesson, and we know that structurally rather than hopefully: write_reference_shot renders through soft_renderer.cpp and raster.cpp, neither of which includes font.hpp, overlay.hpp or gpu_overlay.hpp, and demo_scene.cpp draws no text. It is run anyway — byte-identical for the twenty-seventh lesson, hash E917C06C — and what that proves is that this lesson broke nothing else, which is a different and smaller claim.

The real test had to be built, and the shape to copy is 6.17's: render the same thing two ways, and include a control that proves the comparison can report a difference. Here the two ways are the two renderers, which is available only because overlay.hpp knows nothing about SDL_GPU.

Here they are not: the CPU decodes bytes to float, lerps, and re-encodes with engine::linear_to_srgb; the GPU's ROP does it in fixed-function hardware whose intermediate precision is not specified anywhere. One code is the honest claim, and the instrument reports the distribution rather than a yes/no — because a comparison that can only say "same" or "different" cannot tell a rounding difference from a bug.

And the control. The same comparison, against a CPU render composited in the deliberately wrong blend space, reports 934 differing pixels, worst difference 53 codes. The instrument can fail, so the 68 means something. That control exists because one lesson ago we found a golden that printed identical=YES when both of its file reads failed, and because this very lesson shipped a draft with a check that passed on infinity (§5.1). Twice in one module is a pattern, not an accident.

12. The ninety-percent picture

What this lesson built is a Latin debug-text system, and the distance between that and "text" is enormous. Naming the gap:

  • No shaping. One codepoint becomes one glyph, in logical order. That is wrong for Arabic, where a letter's shape depends on its position in the word; wrong for Devanagari, which reorders and forms conjuncts; wrong for any font with ligatures; and wrong for combining marks. The library is HarfBuzz, it is larger than this engine's renderer, and it is the right answer the moment you need it.
  • No bidi. Mixed right-to-left and left-to-right runs need the Unicode bidirectional algorithm (UAX #9) applied before layout can begin.
  • No line breaking beyond an explicit \n. Real wrapping needs UAX #14 break opportunities; breaking at spaces is wrong in most of the world.
  • No subpixel antialiasing. We produce one coverage value per texel; ClearType-style rendering produces three, one per LCD subpixel, and is dependent on the display's stripe orientation.
  • No signed distance fields. An atlas baked at one size is crisp at that size and soft elsewhere. SDF text (Green, 2007) stores distance rather than coverage, so a bilinear tap plus a threshold reconstructs a sharp edge at any scale — and it is the right answer for text that scales, rotates, or needs an outline or a drop shadow. It is not free: corners round off, which multi-channel SDF fixes at 3× the memory, and the threshold has to move with the scale to keep the weight constant.
  • One font, one size, one style per atlas. No fallback chain, so a codepoint this atlas does not carry is counted as missing rather than silently skipped.

Two smaller ones worth knowing. stb_truetype reads a useful subset of GPOS pair positioning — enough for the 186 pairs in our font, not enough to be called an OpenType layout engine. And our glyphs are rasterized unhinted: hinting is a bytecode VM that moves outline points onto the pixel grid at small sizes, and skipping it costs real crispness below about 12 px. Both are reasonable places to stop for an engine whose text is a HUD; neither is a place to stop for a word processor.

15. Common pitfalls & debugging

The text is a solid block of colour

Symptom: every glyph is a filled rectangle in the right place and the right size. Cause: the shader is reading the wrong channel of the atlas, or the atlas is bound but the sampler is not, and the fetch returns 1. Fix: an R8_UNORM texture read through Texture2D<float4> gives you (r, 0, 0, 1) — the alpha is one, not the coverage. Declare it as Texture2D<float> and use .r, as the listing does.

The text is upside down

Symptom: correct on the software renderer, mirrored vertically on the GPU, or vice versa. Cause: the pixel-space-to-clip-space flip has been applied twice or zero times. Fix: there is exactly one 1.0f - in the vertex shader and no flip anywhere else. If you added one in the layout so that a quad's y0 is below its y1, remove it: the layout works in pixel space, +y down, and says so.

Every glyph has a faint border of the letter beside it

Symptom: ghosting, worse on tall letters. Cause: insufficient atlas padding for the filtering in use. Fix: §5.2. One texel covers bilinear at level 0; a chain L levels deep needs 2L.

The text is blurry and moving the quad by half a pixel does not fix it

Symptom: soft, slightly doubled glyphs. Cause: the quad is not on the pixel grid, or the viewport the batch was laid out for is not the viewport it was drawn into. Fix: check snap_to_pixel first, then check that overlay_batch::begin was given the same size as the render target. gpu_overlay::record reads the viewport from the batch rather than from the device precisely so that a mismatch is impossible — but a batch built for last frame's size and drawn this frame will still stretch.

Light text looks thin, or dark text looks fat

Symptom: the weight is wrong and the font is not. Cause: §7. Fix: run the diagnostic. Render the same string white-on-black and black-on-white and compare the ink. If one is thin and the other fat, the blend space is wrong — look at the colour target's format. If both are thin, the atlas is being decoded — look at the texture's format.

The frame-time readout jitters horizontally

Symptom: a right-aligned number whose characters shuffle every frame. Cause: proportional digit advances. Fix: text_layout_options::tabular_digits, §3.3.

A string with a j or an f is clipped on the left

Symptom: one letter has a sliver missing. Cause: a background or a scissor rectangle sized from text_metrics::width, which is the advance width. Fix: use ink_x0/ink_x1 when you need the extent of the pixels — they differ, and §3 says by how much.

Kerning does nothing

Symptom: AV looks loose, and font_atlas::kerning is empty. Cause: the font has no legacy kern table and your reader only knows about that one. Fix: §3.2 — use a stb_truetype at 1.19 or later, which reads GPOS. Check font_atlas::kerning.size() after a bake; zero on a modern font is the signal.

The overlay erases the frame under it

Symptom: the 3D scene disappears and only the HUD is left, on a black field. Cause: the pass declared discard_write (or set SDL_GPU_LOADOP_DONT_CARE by hand) on a target it actually blends into. Fix: §10.2 — an alpha blend reads its destination, so the verb is keep.

16. Exercises

  1. Bake at a second size and look at the atlas. Change font_bake_options::pixel_height to 32 and print width, height, used_height and the shelf efficiency. Predict the atlas side before you run it.

    Hint: glyph area scales with the square of the size, so 7,145 texels becomes roughly 28,600 — which needs a 256-square atlas, since 128 × 128 is 16,384. Shelf efficiency should barely move, because the heights still cluster. If it moves a lot, look at which glyph is setting the first shelf's height.

    Solution sketch: predict the side from the area: 4 × 7,145 ≈ 28,600 texels exceeds 128² = 16,384, so the next power of two, 256, and the atlas is 256 × 256. If the shelf efficiency holds at the 83.3% it measured at the default size, the glyphs fill about 28,600 / (256 × 0.833) ≈ 134 rows of the 256; expect slightly fewer, and a slightly higher efficiency, because the per-glyph padding does not double when the glyphs do. The headline number is the other one: the whole-atlas occupancy falls to about 44% again, because the square power-of-two side is chosen before packing — the same 43.6% the lesson computed at the default size.

  2. Make the wrong blend space visible. Change hello_cube's composite_overlay call to overlay_blend::encoded and take two shots — one with light text on the dark background, one with the colours swapped. Look at them side by side at 4× zoom.

    Hint: the effect is much easier to see on the light background, where the text gets heavier, because the eye is better at noticing ink appear than disappear. That is itself worth knowing: the version of this bug that ships is usually the light-on-dark one.

    Solution sketch: put numbers on it first. At half coverage the correct blend of white over black is the encode of 0.5, which is 0.735 — byte 188; the encoded blend writes 128. So every edge pixel is about 60 levels too dark in both arrangements, and what differs is what "too dark" does: on a dark background it eats into light text, which looks thinner; on a light background it thickens dark text, which looks bolder. The same arithmetic error changes the stroke weight in opposite directions, and the side-by-side shots are the evidence; count the edge pixels whose value moved, not just the look.

  3. Add a scissor rectangle. Give overlay_batch a clip rectangle that quads are cropped against, in pixel space, with the texture coordinates adjusted to match. Make it work on both renderers and extend §J's comparison to cover it.

    Hint: cropping a quad means moving a vertex and its uv by the same fraction. The arithmetic is a lerp of the uv by (new_x - x0) / (x1 - x0). The GPU alternative is SDL_SetGPUScissor, which is free but is per-draw — so using it splits the one draw call into one per clip region. Measure both, and then look at which one Dear ImGui chose.

    Solution sketch: on the CPU, drop quads wholly outside the rectangle, and for the rest clamp each edge and move the matching uv by the same fraction, so the glyph is cut rather than squeezed; do it in the one place both renderers consume, and §J's comparison extends without a second copy. For the comparison with ImGui, read its backend rather than assuming: in the version this course vendors (1.92.9b), imgui_impl_sdlgpu3.cpp calls SDL_SetGPUScissor once per draw command, with the command's ClipRect, and ImGui keeps that affordable by merging consecutive commands that share a rectangle. It crops in the vertex data only for text, and only when asked — AddText's optional cpu_fine_clip_rect. So the answer is both, each where it is cheap: the scissor for coarse regions, CPU cropping where a region would otherwise cost a draw per glyph.

  4. Word wrapping. Add a max_width to text_layout_options and break lines at spaces when the pen would exceed it. Then find a string your implementation breaks wrongly.

    Hint: you will find one quickly — "don't" is fine but "e-mail" and "1,000" and any CJK text are not, because break opportunities are a property of Unicode (UAX #14) rather than of the space character. The exercise is worth doing precisely to arrive at that sentence honestly.

    Solution sketch: the greedy algorithm keeps the position of the last break opportunity; when the pen passes max_width it breaks there, and a word longer than the line is split where it overflows. Then test it against the cases the hint names, and notice what they teach about your rule: a space-only breaker never breaks inside "e-mail" or "1,000" — correct for the number, and a missed opportunity for the compound — and it cannot break CJK text at all, which has no spaces and permits a break between almost any two ideographs, so the line simply overflows. Add the hyphen as a break point and "−5" and "2026-09-27" become breakable in places they must not be. Every patch trades one case for another, because the right answer is a table of character classes and pair rules, which is what UAX #14 is.

  5. Engine challenge: signed distance fields. Bake a second atlas holding distance rather than coverage — for each texel, the signed distance to the nearest outline, normalised into a byte — and add a shader path that thresholds it with smoothstep. Draw the same string at 1×, 4× and 16× and compare against the coverage atlas.

    Hint: stbtt_GetCodepointSDF does the bake. Three things will surprise you. The threshold must move with the scale or the weight changes; corners round off, which is the known limitation multi-channel SDF exists to fix; and the padding requirement is now set by the distance range rather than by the filter, because a texel outside the glyph still carries meaningful data. That last one is §5.2's argument arriving with a completely different constant.

    Solution sketch: bake with stbtt_GetCodepointSDF(info, scale, cp, padding, onedge_value, pixel_dist_scale, …) — for example onedge_value 128 and a pixel_dist_scale that maps the padding to the full byte range — and pack with a padding at least as large as the distance range, since those texels now carry data. In the shader, alpha = smoothstep(0.5 − w, 0.5 + w, d) with w from fwidth(d), so the edge stays about one screen pixel wide at every magnification; with a fixed w the text blurs when enlarged and aliases when shrunk, and moving the threshold off 0.5 visibly changes the weight. At 16× the SDF stays sharp where the coverage atlas turns to blur, and its corners are round: near a corner the nearest outline point is the corner itself, so the iso-lines are circles, and multi-channel SDF is the fix. At 1×, the coverage atlas usually looks better — it was rasterised for that size.

17. Recap & next

The engine can say something. It bakes a real outline font into one channel of coverage, packs ninety-five glyphs onto six shelves deterministically, lays out UTF-8 with kerning and tabular figures, and composites the result in linear light — on the CPU into a framebuffer, and on the GPU in one draw call, with the two agreeing to within one sRGB code on every pixel.

What is worth carrying out of this lesson is mostly not about text.

  • The same rounding applied to two different quantities has completely different consequences. Snap a position and the error is bounded forever; round an advance and it is a random walk. Before rounding anything, ask whether the value you are rounding feeds back into itself.
  • A measurement whose denominator does not depend on the thing under test measures something else. "What fraction of the atlas is glyphs" is a fact about the font. Shelf efficiency is a fact about the packer. This is the sixth member of a family running since 6.14 — can this measurement produce a non-null result; has it converged; can this axis show the effect; can this comparison report a difference; is the reason I am building this true here; and now: does my denominator move when the code does?
  • A check whose degenerate case is a pass is not a check. inf > 80.0 is true. This is the second time in three lessons that a degenerate input has produced a green tick, and both times only an implausible printed number gave it away.
  • Two bugs in two different files can be the same function. An _SRGB coverage atlas and an sRGB-space blend agree to four significant figures on a dark background. When two independent explanations predict the same measurement, the useful move is to find the measurement that separates them — here, simply inverting the contrast.
  • A new type's job can be to make a bug impossible rather than catchable. Naming four colour bytes r, g, b, a removes the endianness question that cost 6.15 a debugging session, and there is no test to write because there is nothing left to get wrong.
