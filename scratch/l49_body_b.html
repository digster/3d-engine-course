What changed, across the engine

Every SDL_SetGPU*Name call is gone, replaced by the creation path — and the transfer buffers, which had never been named at all, got names for the first time. That last one matters more than it sounds: a load-time capture of this engine used to show four identical anonymous transfer buffers, and working out which upload was which is exactly the time a debugger is supposed to save you.

C++ — a doc comment is code that cannot be tested

Two comments in this codebase asserted the wrong reason for the naming asymmetry (§3.3) and survived four lessons, a full code listing on a published page, and several readings. They survived because nothing depends on a comment being right — there is no compiler, no test, and no reviewer whose job it is. gpu_shader.cpp's version is now rewritten to quote the wrong version first, which is the only form of correction that inoculates the reader.

The practical rule: be most suspicious of comments that explain why an API is shaped the way it is. Comments about what your own code does are checked constantly by people reading the code beside them. Comments about somebody else's design are checked by nobody.

4.2A group that is a scope

Deleting the move constructor is unusual in this engine — every resource type so far has been movable — and it is the §3.4 rule expressed in the type system. A movable group could be returned from a function, stored in a container, or handed across a pass boundary, and on Metal that produces a capture whose tree is quietly wrong. Making it immovable means the pop happens in the same block as the push, which on every backend is the safe case.

4.3The frame log

frame_log records the events a capture would show. Three decisions in it are worth defending, because they are what separate instrumentation that helps from instrumentation that lies.

A fixed name buffer, not a std::string. This is not premature optimisation: the log runs inside the frame it is measuring, and an allocation per event would make the thing being measured different from the thing that ships. Forty-eight bytes holds every name this engine uses; longer ones truncate, which is the right failure for a debugging aid. Note the copy uses SDL_strlcpy, which always null-terminates — strncpy famously does not, and that one-line difference is how a truncated name becomes a buffer overrun.

Fixed capacity, and full is not an error. It stops recording and sets overflowed(), which print() reports. Silently dropping events would be worse than truncating a name, because a missing event is indistinguishable from a call you forgot to make.

Recorded from inside render(), not described from outside. The tempting design is a function that walks the draw list and prints what it believes the renderer will do. That design drifts the first time somebody changes the renderer, and it drifts silently, and the result is a log that is believed and wrong. So the events are emitted from the same statements that issue the calls:

Which is what makes §D of the harness possible, and it is the test a capture cannot give you: draw_stats and the frame log are two counters incremented from the same statements, so asserting they agree catches an instrumentation bug that would otherwise be invisible.

4.4Wiring it in, and --trace

Four groups per frame — upload, clear, blit, scene — chosen to match the phases Lesson 4.8 already thinks in. Note where the scene's group opens:

Before the pass, closing after it. That is legal everywhere and is the shape §3.4's Metal caveat is happiest with; a group that begins inside a pass must also end inside it, and a group that spans a pass boundary is the case to avoid.

Recording is armed by P for exactly one frame and disarms itself as soon as it prints. That is not laziness about a toggle — it is how a capture works, and for the same reason: an instrument that runs continuously is one you stop reading and keep paying for.

And one flag, which is the piece that outlives the lesson:

Arms the log on the first frame, prints it, and exits. A headless frame dump — no window to click, no GUI, no driver hooks — which means it runs in CI, and the output can be diffed between commits. "This commit added a draw call" is a thing a build can now notice.

An honest note about this section

This course is written on a Mac, so the RenderDoc walkthrough below is assembled from RenderDoc's own documentation rather than from a session the author ran. The steps and the panel names are quoted from its Quick Start guide; the judgements about what to look at are transferable and are the part that matters. The Xcode walkthrough follows SDL_gpu.h's own instructions.

Where a UI detail may have moved since, treat the panel names as reliable and the menu paths as a starting point. ⚠ VERIFY against your installed version.

5.1RenderDoc, on Windows or Linux

  1. Build with debug mode on. The engine passes true to gpu_device::create, which is what you want here: validation messages and a capture are complementary, and §3.5 measured the cost at 1.17× on a three-draw frame.
  2. File → Launch Application. Fill in the Executable field (browse, or drag the binary in). Leave Working Directory empty — it defaults to the executable's directory, which is where assets/ and shaders/ live, so this is the right default for us. Add command-line arguments if you want a particular mode.
  3. Click Launch. The engine starts with RenderDoc underneath it.
  4. Press F12 (or Print Screen) to capture the next frame. Take the capture on a frame you have arranged deliberately — orbit so that two objects overlap, or press C to a scene that is misbehaving.
  5. Close the application. The capture opens in the RenderDoc UI automatically; several captures give you thumbnails to choose from.

5.2Xcode's Metal Debugger, on macOS

SDL_gpu.h gives the procedure directly, and it is worth quoting because it is the one place a Mac reader is likely to give up:

"Open XCode, go to Debug > Debug Executable…, select your application, set 'GPU Frame Capture' to 'Metal' in scheme 'Options' window, run your app, and click the small Metal icon on the bottom to capture a frame."

You do not need an Xcode project — Debug Executable… attaches to a binary CMake already built, which is the whole reason that menu item exists. The header adds one more thing for Mac readers: "For Metal, it should be enough just to run the application from XCode to receive detailed errors or warnings in the output" — which is the Metal equivalent of a validation layer, and is free.

The Metal Debugger's vocabulary differs and its concepts do not. Its navigator is the event browser and your debug groups are its tree; selecting a draw shows bound resources, attachments and pipeline state; it has a geometry viewer and a shader profiler. If you have read §3.7's table, you know what to expect from it.

5.3Four questions to ask a capture

Opening a capture and browsing is how people conclude the tool did not help. Arrive with questions. These four cover most of what goes wrong, and each one has an expected answer you already know from the frame log.

1. Is my draw there at all? Count the draws in the event browser against the frame log's count. If the draw is missing, the problem is on the CPU and happened before submission — a bad conditional, a null mesh, a skipped item. If it is present and nothing changed on screen, the geometry was culled, clipped, depth-rejected, or drawn somewhere you are not looking. Those are two completely different searches, and one glance separates them.

2. Is the right thing bound? Select the draw, open Pipeline State, and read the resource names — which exist now. This is where a missing sampler binding shows up as a blank slot, and it is the fastest possible answer to the failure that has cost this project three debugging sessions (Lessons 4.6, 4.7 and 4.8's harness).

3. Are the bytes what I think? Inspect the uniform buffer contents at b0 and b1. Lesson 4.6 had to build an entire probe shader to read a matrix back one component at a time; the tool shows all sixteen floats. If your matrix is transposed, this is where it is visibly transposed.

4. Where did the geometry go? The Mesh Viewer shows your vertices before and after the vertex shader. Post-transform positions outside the clip volume mean a projection problem; positions that are NaN mean an uninitialised uniform; a correct-looking mesh that does not appear means the fragment stage or the depth test.

The habit worth forming

Predict, then look. Before you inspect anything, say out loud what you expect: "b1 should be a model matrix with 1.4 in the translation column". Then look. If it matches, you have eliminated something; if it does not, you have found it. Browsing without a prediction generates the feeling of investigating and no information, and it is the difference between people who find frame debuggers useful and people who do not.

8Common Pitfalls & Debugging

The capture is a flat list with no tree

Symptom: your debug groups are nowhere in the event browser, though the draws are all there.

Cause: on D3D12, SDL_PushGPUDebugGroup, SDL_PopGPUDebugGroup and SDL_InsertGPUDebugLabel all require WinPixEventRuntime.dll. Without it they are inert — not an error, just silence.

Fix: put the DLL in your PATH or beside the executable. SDL's header says so on each of the three functions, and this is the only cross-platform difference in this lesson that produces no diagnostic at all.

The tree is wrong: groups nest where they should not

Symptom: events appear under the wrong heading, or a group swallows the rest of the frame. Usually on Metal.

Cause: a push and its pop straddle a render-pass boundary. On Metal a group pushed inside a pass is scoped to that pass, so popping it outside leaves the tree inconsistent.

Fix: open the group either entirely outside the pass (what this engine does) or entirely inside it. An RAII scope makes the second case automatic and the first case a matter of where you put the brace.

The capture is enormous, or capturing takes forever

Symptom: pressing F12 hangs the application for several seconds and produces a file measured in gigabytes.

Cause: a capture serialises the full contents of every live resource so the frame can be replayed (§2.2). It is proportional to how much you have allocated, not to how much you drew.

Fix: expected behaviour, not a bug — but capture a small window and a small scene when you can. It is also the reason capturing is a keypress rather than something you leave running.

Your instrumentation says one thing and the renderer says another

Symptom: the frame log reports two draws and draw_stats reports three.

Cause: a code path that issues a call without recording it — almost always an early continue or a second draw added later next to a record() that was not.

Fix: record from the same statement that issues, and keep the cross-check. Note the failure mode you are protecting against: the log would have been wrong and believed, which is worse than having no log — and the assertion costs one line.

Measuring instrumentation and getting a negative cost

Symptom: adding debug groups makes the frame measurably faster.

Cause: the effect is below the noise floor, and you measured a fluctuation.

Fix: measure the floor first — run the identical workload several times and take the spread — then require any claimed effect to beat it by a factor of two. If it does not, scale the work up until it does and divide (§3.5). A negative cost for added work is the clearest possible signal that a measurement has nothing to say, and it is worth learning to recognise as good news rather than as a puzzle.

Everything is named, and the capture still shows "Buffer 12"

Symptom: names appear for some resources and not others.

Cause: the unnamed ones are created somewhere that never took a name — transfer buffers were the whole of this category in our engine until this lesson.

Fix: grep for every creation call rather than every named one; the ones that never had a name parameter will not show up in a search for names. And remember there is no getter (§3.3), so this cannot be asserted in a test — a capture is the only place it is visible, which is an argument for looking at one early rather than once.

9Exercises

  1. 4.9.1 — Break something, then find it. Pick one: bind no texture, use the wrong pitch (8 in --probe still does this), reverse the winding, or push the camera matrix transposed. Do not tell yourself which. Capture a frame and find it using only §5.3's four questions.

    Hint: time yourself, and do it again a week later. The value of a frame debugger is almost entirely in how quickly you reach for it, and the only way to make that reflex is to use it on a bug whose answer you already know.

  2. 4.9.2 — Diff a frame in CI. engine --trace is deterministic. Commit its output, add a script that re-runs it and diffs, and make an unexpected change fail. Then add a draw call and watch it fail.

    Hint: strip the timestamps SDL_Log prepends. The interesting design question is what should be allowed to change: a golden file that fails on every legitimate edit gets deleted within a month. Consider asserting on the counts rather than the whole tree.

  3. 4.9.3 — Name everything, then check. Take a capture and list every object in it that still has no name. Fix them. There are more than you think — the swapchain textures, for instance, belong to SDL rather than to you.

    Hint: the honest finding here may be that some cannot be named because you did not create them. Report that rather than working around it; knowing which objects in a capture are yours is itself worth having.

  4. 4.9.4 — Groups that mean something. Four groups is the minimum. Add one per object inside the scene group, named from scene_object::name, and re-take the capture.

    Hint: §3.5 measured a group triple at ~183 ns, so a hundred objects is ~18 µs — about 0.1% of a 60 Hz frame. That is affordable and it is not free, which is exactly the sort of judgement this lesson is trying to make routine. Consider making it conditional on a debug build and then argue with yourself about whether that is wise.

  5. 4.9.5 — Pay the debt this lesson could not. On hardware RenderDoc or PIX can capture, read the real vertex-shader invocation count for the torus draw and compare it against §3.6's simulated table. Report how far off the model is.

    Hint: the prediction is 2,400 against a best case of 1,225 and a worst of 6,912. If the hardware beats 2,400 substantially, its cache is bigger or smarter than FIFO; if it is worse, the batching assumption is the suspect. Either way you will have learned something about your GPU that no documentation states, which is the whole reason the counters exist.

  6. 4.9.6 — Optimise the index order. §3.6 showed reuse collapsing 2.83× when triangle order is shuffled. Go the other way: implement Tom Forsyth's linear-speed vertex-cache optimiser and re-run the simulation on the reordered indices.

    Hint: the torus is already emitted in a good order, so expect a small win — which makes it a poor test. Optimise the shuffled indices instead and see how much of the 2.83× you recover; that is the number that tells you whether your implementation works.

10Recap & Next

  • A breakpoint cannot catch a GPU bug, and the reason is when work happens rather than any deficiency in the debugger. Recording and executing are separated by a submit, and the bug lives on the far side of it.
  • A frame debugger records inputs and replays them, which is why it can show you any resource at any event — and why captures are large, capturing is slow, and the tool must sit at the driver level.
  • RenderDoc does not support Metal. Vulkan, D3D11, D3D12, GL and GLES on Windows, Linux, Android and Switch. On macOS the tool is Xcode's Metal Debugger, and every concept transfers.
  • Name resources at creation, not with the setter. SDL's own docs say so, and a comment in this codebase spent four lessons confidently explaining an asymmetry that did not exist. A confident explanation of somebody else's API is a hypothesis; the documentation of the function you are already calling is where to test it.
  • Debug groups are a scope — literally, because Metal scopes a group pushed inside a pass to that pass, and an RAII type is how you never get that wrong. On D3D12 they need WinPixEventRuntime.dll and are silent without it.
  • Measure the noise floor before you measure anything against it. The first version of §3.5 reported a negative cost for adding work. Scaling the workload until the effect clears the floor turned "unmeasurable" into 183 ns per group triple, converging across two independent estimates. The validation layer costs 1.17× on a three-draw frame, which is a per-call figure wearing a misleading ratio.
  • Some numbers you cannot measure, and saying so is the job. Lesson 4.5's vertex-invocation debt is unpayable on this machine, so §3.6 models it instead, states every assumption, and points at the counter that answers it. The model turned up something better anyway: reuse is a property of the index order, and shuffling triangle order costs 2.83× with nothing about the geometry changed.
  • Your own instrumentation earns its place where the tools cannot go — every backend, CI, and a cross-check against a second counter. It stops exactly where replay begins.

11Further Reading

  • SDL3/SDL_gpu.h, the "Debugging" section. A page long, on your disk, and the authoritative answer to "which tool do I use" for every platform SDL supports. It is the first place to look and the last place most people do.
  • RenderDoc's documentation — the Quick Start, and then the How do I…? pages. Short, well written, and the source of §5.1's steps and panel names.
  • Apple, "Metal debugger" and "Optimizing GPU performance" (WWDC sessions and the Xcode documentation). The macOS half of this lesson, from the people who wrote the tool.
  • Tom Forsyth, "Linear-Speed Vertex Cache Optimisation" (2006). The algorithm behind Exercise 4.9.6, and still the standard reference — notable for being a heuristic that beats more principled approaches and for the author being clear about why he thinks that is.
  • meshoptimizer (Arseny Kapoulkine). The library everyone actually uses for index-order optimisation, and its README is a good short course in what else a mesh can be optimised for — overdraw, vertex fetch, quantisation.
  • Fabian Giesen, "A trip through the Graphics Pipeline 2011", part 3, on the post-transform cache. What §3.6's model is modelling, from somebody who has read the hardware documentation you have not.
  • Aras Pranckevičius, "Every Possible Way to Debug Graphics" and similar practitioner write-ups. Worth reading for the techniques that are not a frame debugger — printf-to-a-buffer, colour-coding intermediate values, bisecting a frame by commenting out draws — several of which are faster than a capture when you already have a hypothesis.
