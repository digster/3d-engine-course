9Textures and Materials Become Assets

Lesson 6.5 put texture_pool in texture.hpp and explicitly kept it out of asset_store, with this reasoning:

That grounds expire here, in the most direct way possible: a glTF material arrives naming an image on disk, two materials in one file routinely name the same one, and "load it once and hand out the same reference" is precisely the store's job description. So the answer to 6.5's deferred question is yes, and the interesting part is what had to be added around a pool that did not itself change.

9.1 — A texture is a DERIVED asset

A mesh is loaded. An image is loaded. A texture is made from an image — and Lesson 5.5 already had a name and a mechanism for that shape.

Everything about resolving a name against the search path, reading bytes, decoding them and counting the read is load_image's job and is not repeated. That is what makes "the same image loaded twice is decoded once" true for textures as well, without load_texture knowing anything about it.

derive_texture records an edge — image → texture — and that edge is the whole reason the function exists rather than being a plain insert:

A dependency edge, not a reference count

Lesson 5.5 refused reference counting at length: a handle is a value, four bytes, trivially copyable, and refcounting requires copying to have a side effect, which costs every property Lesson 5.4 was written to obtain.

A derivation edge is different in kind. Nobody outside the store can hold one. The store made the texture, nobody asked for it by a name of its own, and it has no independent reason to exist — so unloading the image takes it, transitively, and the rule is enforced by a private member rather than by a contract.

verify_66 §F unloads uv_grid.png and gets 2 back: the image and the texture built from it. The material's handle is then stale, which is not a crash — bind_albedo returns an unbound binding and the surface falls back to its tint. Lesson 5.4's bargain, arriving at last with a real dependency behind it.

One detail that is easy to get wrong and silent when you do

The cascade must remove the texture's name entry as well as the texture. Miss it and find_texture("uv_grid.png") keeps handing out a handle to a slot the pool has already recycled.

It would not crash — 5.4's generation counter catches it and contains() returns false — so the symptom is an object that silently loses its texture some arbitrary number of frames later. Correct behaviour, and still a bug worth not having. verify_66 §F asserts the name entry went.

One more thing about the edge lists, worth a sentence because the tempting shortcut is wrong. There are now two of them — mesh_derivations_ and texture_derivations_ — rather than one generic list of {uint32, uint32} pairs. A single untagged list would compile, and would happily resolve a texture's handle bits against the mesh pool: Lesson 5.4's aliasing failure in a new costume. Two lists, two types, no tag.

9.2 — A material is a named asset with no file

Materials get the other half: insert_material(name, m), find_material(name), unload_material(h), and a material_by_key_ map.

There is deliberately no load_material, and there never will be, because a material is not a file. It arrives as part of one. But naming it anyway is what buys the property glTF needs: a file whose four primitives share one material must produce one material, and two loads of the same file must not produce eight.

The names are derived and deterministic, which is what makes the cache work without a second map:

The derived names asset_store::load_model stores a model's parts under
PartStored asWhy
primitive i"shapes.glb#2" ordinal, because a primitive has no name of its own
material "gold""shapes.glb:gold" namespaced — two models may both call a material "Metal"

verify_66 §F loads cube.gltf twice and asserts the second call returns the same handles with files_read unchanged at 2. It also asks the store directly for uv_grid.png and gets back the texture the material already holds — one decode, one copy, however many materials name it.

Why models_loaded is its own counter

One model file reads many files: the .gltf, its .bin, and one per texture. cube.gltf reports models_loaded = 1 and files_read = 2.

Conflate the two and "did the cache work?" becomes unanswerable, because you can no longer tell one cached model from two uncached textures. A counter that measures two things measures neither.

10The One Thing We Cannot Represent

Every importer has a conformance gap. What separates a good one from a bad one is whether the gap is reported.

Ours is one sentence of the specification, §5.19.4: "If both factors and textures are present, the factor value acts as a linear multiplier for the corresponding texture values."

Our material does not multiply. Lesson 3.9 established that a bound albedo image replaces the tint, on the grounds that both of them are the albedo and a surface has one albedo. That rule is defensible and it is what the rasterizer implements — and it disagrees with glTF whenever a material has a base colour texture and a non-white base colour factor.

Note precisely how narrow that is. It is not "the factor". A material with a coloured factor and no texture imports exactly; a material with a texture and a white factor imports exactly, because multiplying by white is replacing. The gap is only the combination.

Where a conformance gap belongs

At the only point that knows both halves. The parser sees the factor and the URI but not whether the image resolved; the renderer sees a bound texture but has long since lost the factor. load_model is the one place holding both, so the warning lives there and the count travels back in model_load.

And it is a count as well as a log line, because a log line scrolls past and a number can be asserted. verify_66 §F asserts factor_texture_conflicts == 0 for shapes.glb — where the coloured material has no texture — which is a test of the detector as much as of the asset.

Making them multiply is a one-line change in raster.cpp and a matching one in scene.frag.hlsl. It is Exercise 2, and it is deliberately not made here — because the demo scene's textured surfaces carry a non-white tint, so the change would move the reference render, and this lesson's whole claim is that adding a format does not move the picture.

Named, not fixed: two textures glTF offers that we do not read

metallicRoughnessTexture and normalTexture are counted in gltf_material_desc (wants_metallic_roughness_texture, wants_normal_texture) and not loaded.

The reason is one concrete thing rather than lack of time: they are linear data in an image, and texture stores sRGB-encoded texels because sample decodes on read (3.9). A roughness map read through an sRGB decode is wrong by the gamma curve everywhere except 0 and 1. Fixing that means giving a texture a colour space — which is Lesson 6.7's problem, because normal maps need exactly the same thing.

The factors import completely, so a material's metallic and roughness are correct; what is missing is per-texel variation. This is the ninety-percent picture, and the missing ten percent has a lesson number.

Named, not fixed: the one gap that does not announce itself

alphaMode and alphaCutoff are not read at all. What gltf_material_desc carries is alpha — the fourth component of baseColorFactor, stored because the file said it and consumed by nothing. So a material marked MASK or BLEND imports as fully opaque.

That is a conformance gap like the others, but it breaks this section's own rule, and the break is worth staring at. Every other limit in this importer reports: too_many_vertices fires a status, unsupported_primitive fires a status, the factor-times-texture conflict logs a warning and returns a count you can assert on. This one is silent — no status, no warning, no number.

The reason is not an oversight in the parser, and it is the same shape as the metallicRoughnessTexture gap above: there is nowhere to put the answer. A status code says “this file wants something the engine cannot do”, and to detect that, the engine needs a notion of what it can do. The pipeline has carried no blending since Lesson 4.4, and the software rasterizer has no blend equation at all, so there is no state for the importer to compare the file against. It cannot report a conflict with a concept that does not exist yet.

It matters more than the wording suggests. Cutout foliage and glass are two of the most common things in a downloaded asset pack, and both come back as opaque cardboard — a leaf rendered as the rectangle it was mapped onto. Nothing in the load report hints at why. Lesson 6.11 adds alpha masking, blending and the draw order they require; the honest thing to know until then is that this importer's silence about alpha is the one place it is not telling you what it dropped.

12Build & Run, and What You Should See

The first configure after this lesson fetches cgltf, which is one header and takes a second.

The picture

@@FIG_RESULT@@

--model cube.gltf is the one to look at first, because three separate things are being asserted by one image:

  • The arrow points up. uv_grid.png is an orientation chart with a mark in its top-left corner and an arrow along +v; a checkerboard could not tell you this, because a checkerboard is symmetric under every flip. The arrow pointing up means v was not flipped, which is the trap in §4.
  • There is an image at all. The .gltf said "uri": "uv_grid.png", and the store resolved that against its own search path, decoded it, shuffled the channels and cached it. Every step of that is new this lesson.
  • The highlight has the file's shape. roughnessFactor: 0.4 came out of the JSON and went into microsurface::roughness untouched. Nothing in gltf_view types a colour, a shininess or a specular value.

Then shapes.glb, which is four primitives, four placements from a three-deep node tree, and four materials — three from the file plus the specification's default on the plinth, which names none.

What you will actually see, and why it is right

The metals are nearly black, except where they are pure white. The gold octahedron reads gold at some orbit angles and clips to white at others; the silver cube is dark from most directions.

That is not a bug and it is not the importer. A conductor has no diffuse lobe — diffuse_albedo_of returns exactly black at metallic = 1, which Lesson 6.4 derived — so the only light leaving it is the mirrored part. A metal with nothing to reflect but one directional light therefore has exactly two states.

And the bright state is very bright. Evaluating the BRDF in the mirror direction under this engine's reference irradiance:

A polished metal's highlight is sixty-four times what the framebuffer can hold, so to_encoded clamps it and you get a white facet. That number is the quantitative case for two lessons still to come: image-based lighting (6.15) gives a metal something to reflect other than one point light, and a tonemapper (6.12) gives the highlight somewhere to go. The materials in the asset are chosen at defensible values (0.40 and 0.45 — brushed, not polished) so the clipping is a facet rather than an object, and --pose exists so you can sweep past it and watch.

The claim this lesson has to make

58 checks, 0 failures, debug and release. verify_45 through verify_65 all still green.

And the reference render is byte-identical, hash E917C06C — fifteenth lesson at that hash. A whole second asset format, a texture pool inside the store, a material cache and a channel shuffle, and not one pixel moved. Loading a new format adds a path; it must not move the existing picture.

13Common Pitfalls & Debugging

Symptom, cause and fix for the failures this lesson's code can produce
SymptomCauseFix
The model loads, but every texture is upside down. You applied flip_uv_v. It is correct for OBJ and wrong for glTF; the two formats disagree about where (0,0) is. Do not flip. load_model takes no import settings for this reason. Check with the uv grid, not a checkerboard — a checkerboard cannot show you.
missing_buffer on a file that opens fine in a viewer. A .gltf names an external .bin, and it was not copied alongside — or the base directory handed to parse_gltf lost its trailing separator. Copy both files. The base dir must end in /; load_gltf derives it with find_last_of("/\\") and keeps the separator.
The model draws as a spray of triangles connecting the wrong corners. An index was narrowed to uint16 and wrapped. Check report.skipped_too_large and report.max_primitive_vertices. Do not cast — the loader refuses the primitive and says so.
Every imported asset is noticeably darker than in a reference viewer. to_linear applied to baseColorFactor. The factor is already linear; only the texture is encoded. Remove it. Gold's 0.71 becoming 0.4624 is the fingerprint.
Textures come out with red and blue swapped. memcpy from image_data::pixels into texture's texels. RGBA bytes are not ARGB8888 words. pack_argb, per texel. It is the only spelling that cannot get this wrong.
A cube imports with 36 vertices when the file wrote 8. Not a bug. The primitive had no NORMAL, so flat normals were generated, and flat shading forces one vertex per face-corner. Nothing — but know it, because it makes an index-for-index comparison against the source impossible. This is the failure the first run of verify_66 §A produced, and the fix was to make the test asset ship normals.
A model is invisible, or you are looking at the inside of it. glTF says an asset's front faces +Z; our camera looks down −Z. Yaw the object. Do not negate coordinates in the loader — that mirrors the geometry and reverses every triangle, so you fix the facing and break the winding.
Half a model vanishes once back-face culling is on. The primitive is an open shell, and glTF is full of them. cull_of(validate(mesh).closed(), desc.double_sided). The mesh supplies the fact, the file supplies the intent (6.5).
An object silently loses its texture some frames after a level change. An image was unloaded and the derived texture's name entry outlived it, so find_texture handed out a recycled slot. Erase the name in the cascade. It does not crash — 5.4's generation counter sees it — which is exactly why it takes so long to notice.
A duplicate-symbol link error mentioning cgltf_parse. CGLTF_IMPLEMENTATION defined in more than one translation unit, usually because it reached a header. Define it in gltf.cpp and nowhere else. This is the good failure; the bad one is a build that picks one silently.

14Exercises

14.1 — Break the ceiling on purpose guided

Edit scratch/make_gltf_assets.py to emit a grid mesh with more than 65,536 vertices (a 260 × 260 lattice will do it), and load it. Confirm you get gltf_status::too_many_vertices and a max_primitive_vertices that names the real number.

Then make it work, twice. First widen mesh_data::indices to uint32_t and measure what that costs on torus.obj: index bytes before and after, and total mesh bytes. Then revert, and instead split the primitive into chunks of 65,536 with a vertex remap per chunk.

Hint. The split is the harder and more useful one, and the awkward part is that a triangle's three indices must land in the same chunk — so you cannot cut on a vertex boundary, you have to walk triangles and emit vertices on demand. That is the same "unify as you go" loop parse_obj already contains, run backwards. Note which answer a real engine picks and why it depends on the target: SDL_GPU supports both index widths, mobile GPUs used to prefer 16.

14.2 — Make the factor multiply guided

Close this lesson's conformance gap. In raster.cpp's lit path, multiply the sampled albedo by the interpolated vertex colour instead of replacing it; do the same in shaders/scene.frag.hlsl. Then run verify_48 §F to confirm the CPU and GPU still agree, and verify_66 to see the golden move.

Hint. It will move — the demo scene's textured floor carries an amber tint, so the change is visible. Re-baseline properly, the way Lesson 6.4 did: report the number of pixels that moved, the direction they moved in, and the old hash beside the new. "It looks fine" is not a re-baseline. Then argue with yourself about whether the engine should adopt glTF's rule or keep 3.9's, and write the argument down — both are defensible and the point is that you can say which you chose.

14.3 — Frame from the accessors engine challenge

gltf_view computes its camera distance by walking every vertex. The specification requires min and max on a POSITION accessor — precisely so a viewer does not have to. Surface those bounds through gltf_primitive, transform them by the node matrix, and frame from them instead.

Hint. The subtlety is that transforming an axis-aligned box by a rotation and taking the corners' bounds gives you a larger box than the geometry needs — the AABB of a rotated AABB is not the AABB of the rotated geometry. Measure the difference on shapes.glb. This is the same conservative-bounds problem Lesson 6.16's frustum culling has to live with, and meeting it here first is the point of the exercise.

14.4 — Strips and fans open

build_geometry counts and skips any primitive that is not cgltf_primitive_type_triangles. Convert TRIANGLE_STRIP and TRIANGLE_FAN into triangle lists at import so those files load.

Hint. A strip of n vertices is n − 2 triangles, and the winding alternates: triangle i is (i, i+1, i+2) for even i and (i+1, i, i+2) for odd. Get that backwards and every other triangle is back-facing, which is invisible until culling is on — so test it with validate()'s reversed_edges rather than by looking.

14.5 — Prove the coupling difference on screen open

§6 measured the two diffuse couplings as 1.036× apart at normal incidence and 5.62× apart at 88°. Make that visible: render shapes.glb's red tetrahedron twice, once with each coupling, and difference the two framebuffers.

Hint. fill_style has no coupling field, and adding one is the exercise's real content — it is pipeline state by 6.5's rule, so think about where it can legitimately live and what that implies about a scene mixing the two. Then predict, before you run it, where in the image the difference will be largest. If your prediction is "the middle of the bright face", re-read §6.

15Recap & Next

The engine can now read the format the industry actually ships. Concretely, it gained:

  • A glTF 2.0 loader, text and binary, handling node hierarchies, multi-primitive meshes, external and embedded buffers, and the full metallic-roughness material model — behind our own types, with cgltf confined to one translation unit that no demo can reach.
  • Textures as assets. load_texture resolves, decodes, shuffles and caches; the result is a derived asset whose lifetime is bound to its image, so unloading the image takes it.
  • Materials with identity. Named, cached, shared — so a file's four primitives sharing one material produce one material, and loading the file twice produces none extra.
  • to_texture, the twelve-line bridge between "decoded a PNG" and "can sample it" that should have existed since Lesson 5.3 and did not, because no code path had ever crossed the gap.
  • A settled question. The ⚠ VERIFY from 6.4 is discharged with a citation and a measurement: our BRDF differs from glTF's reference in exactly one factor, the specification permits the variation explicitly, and the property it does require — energy conservation — is the one our form has.
  • A conformance gap that reports itself, rather than one you find out about from an artist.

And three things this lesson deliberately did not do, each with a reason and a lesson number: it did not read the metallic-roughness or normal textures (they are linear data and texture has no colour space — 6.7); it did not make the base colour factor multiply (it would move the golden — Exercise 2); and it did not widen the index type (it costs bytes on every mesh — Exercise 1).

The through-line, if you take one thing from this lesson

Almost none of the work here was parsing. It was deciding what agrees with what — four conventions, six BRDF terms, three material parameters — and the answer was overwhelmingly "nothing to do".

That is what it feels like to import into an engine whose conventions were argued rather than picked, and whose parameters were derived rather than tuned. An engine with a Z-up world and a hand-fitted gloss curve would have needed a basis change, a winding fix and a conversion table here, every one of which is a place for a plausible-looking bug to live forever.

Next: 6.7 — Normal Mapping and the TBN Derivation. Every surface in this engine is as flat as its triangles, and the fix is to perturb the normal per pixel from an image — which needs a per-vertex tangent frame, derived from the uv parameterisation, and it needs the thing this lesson deferred: a texture that knows it holds linear data rather than colour. A normal map read through an sRGB decode is wrong everywhere except at its extremes, and it looks almost right, which is the worst possible way to be wrong. glTF has been telling us about normalTexture the whole time; 6.7 is where we listen.
