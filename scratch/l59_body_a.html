Module 5 — Becoming an Engine · Lesson 5.9

Transform Hierarchy and the Camera System

A turret sits on a tank. That sentence needs one component and one line of matrix algebra, and both were ready before this lesson started — parent_from_local has been called that since Lesson 2.8 precisely so this day would change nothing. What is not ready is the order: a parent must be resolved before its children, and Lesson 5.7 established that a component pool hands entities back in insertion order, which is not that. This lesson measures three ways to reconcile them, ships the one the numbers chose, and then spends the payoff on making the camera an ordinary entity.

1The Problem

Lesson 5.8's world is flat. Every transform is a placement in world space, which was exactly right for a swarm of objects orbiting an origin and is useless the moment one thing has to move with another. A turret on a tank; a lamp on a table; a camera in a car; a hand on an arm on a body. Every one of those is the same sentence — my placement is relative to something else's — and a flat world cannot say it.

The fix is one component and one line of algebra:

The composition rule

world_from_local(child) = world_from_local(parent) × parent_from_local(child)

That is the whole of a scene graph. And the striking thing about it, in this course, is how little it costs to adopt: math/transform.hpp has been written for it since Lesson 2.8, which is why the function that turns a transform into a matrix is called parent_from_local and not world_from_local. That header's comment said so at the time:

“Why ‘parent’ and not ‘world’: in Module 2 every object stands on its own, so its parent IS the world… Module 5 adds a transform HIERARCHY, where an object's transform is relative to another object rather than to the world. When that happens this function does not change by a single character — only the meaning of ‘parent’ widens. Naming it world_from_local today would have been a lie we had to go back and correct.”

It did not change by a single character. Neither did transform. So if the maths is free and the naming was paid for seven lessons ago, what is this lesson about?

@@FIG_COMPOSE@@

The order. Look at the lower half of Figure 1. The composition rule reads a parent's world matrix, which means that matrix has to exist already — the parent must be finished before any of its children start. That is an ordering constraint on the graph.

And Lesson 5.7 established, in as many words, that a component pool's dense order is nobody's business but the pool's: it is insertion order, disturbed by every swap-and-pop, and the whole reason a sparse set can be fast is that it was never promised to anyone. Those two facts are in direct tension, and this lesson is what it costs to reconcile them.

It is worth seeing that this is a real problem rather than a theoretical one. §C of the verification harness builds a four-level tree of forty-eight entities, churns it the way a running game churns — create some things, destroy some things — and then asks how many entities sit in the transform pool ahead of their own parent. The answer is twelve of forty-eight. A walk in dense order would compose each of those against a matrix left over from the previous frame: a picture that is wrong, subtly, in a way that nothing reports and that looks like a physics glitch.

A test that passed for the wrong reason — twice

Producing those twelve took three attempts, and the failures are more instructive than the success. The first version destroyed a scattering of leaves and found zero violations, because swap-and-pop fills a hole with the pool's last element, and in a tree built level by level the last elements are themselves leaves — a leaf replaced a leaf and the order was undisturbed. The second version destroyed filler entities created at the end of the pool, which had the same problem for the same reason.

What works is destroying something early while deep entities sit at the end. Twice in a row the test passed because the situation it described had never arisen — which is the failure mode a test of an ordering property is most prone to, and the reason its assertion is written as “this count is greater than zero” rather than “the answer is right”.

2Building Intuition

2.1 The rule, and why nothing had to change

Start with the arithmetic, on real numbers, because the rule is easier to trust once you have pushed something through it.

Worked example — a moon, two composes deep

A sun at the origin, a planet at (10, 0, 0) in the sun's space, a moon at (0, 2, 0) in the planet's space.

world(sun) = parent_from_local(sun) = T(0,0,0)

world(planet) = world(sun) × T(10, 0, 0) = T(10, 0, 0)

world(moon) = world(planet) × T(0, 2, 0) = T(10, 2, 0)

Nobody computed (10, 2, 0). It is not stored anywhere and no system produced it; it is what the two multiplications happen to say.

Now move the sun to (100, 0, 0) and re-run only the composition. The planet is at (110, 0, 0) and the moon at (110, 2, 0), and again — no code said so. “Following” is not a feature anybody implemented. It is what relative to my parent means, and the second half of the sentence is the interesting half:

Rotation and scale compose too, and scale is the one that surprises people. Halve the sun's scale and the planet's world distance halves with it — 10 becomes 5 — because the parent's matrix scales the child's whole coordinate frame, its offset included. In the demo, a moon authored at scale 0.8 under a planet of scale 0.16 comes out 0.128 in world units, and its local orbit radius of 3.6 becomes 0.58. That is not a bug in the composition. It is why a “one-metre” prop dropped under a scaled parent turns out to be twenty centimetres, and it catches everybody once.

2.2 The order, and why everything did

So the maths is free. Here is what is not.

To compute a child you need its parent's world matrix. To compute the parent you need its parent's. The dependency runs up the tree, so the computation has to run down it, and any visit order that ever reaches a child before its parent produces silent nonsense. There is no test you can put in the loop that fixes this cheaply — you could check “has my parent been resolved this frame?”, but then you need a per-entity flag, a way to clear it, and a plan for what to do when the answer is no.

The alternative is to arrange for the question never to arise: visit in an order that guarantees the answer. That is what the rest of this lesson is about, and the reason it is worth measuring rather than deciding is that there are three such orders, they are all correct, and they do not cost the same.

2.3 Depth is a topological sort

One idea makes the whole thing simple, and it is worth stating on its own because it is doing more work than it looks like it is.

The observation the design rests on

A parent's depth is always exactly one less than its child's. So sorting entities by depth puts every parent before every child — which is precisely the definition of a topological order. And a counting sort by a small integer key is O(n).

That gets you a valid order for the price of one pass. But it gives you something else as well, and this is the part that pays off in Module 9: within a level, the order does not matter at all. Everything at depth k depends only on things at depth k−1, and nothing at depth k depends on anything else at depth k. A level is therefore a batch of completely independent work — a parallel_for waiting to happen — and nobody had to design that. It arrived with the choice of order.

A depth-first recursion has the opposite property. It also produces a valid order, but its order is a sequence: node 3 must follow node 1 which must follow node 0, and there is no batch anywhere in it that can be handed to another thread without a dependency analysis.

3Three Candidate Orders

3.1 What the three actually differ in

@@FIG_ORDERS@@
The three candidate resolve orders and what each one costs.
the orderwhat it is good atwhat it pays
A — recurse from roots depth first the best temporal locality available: a parent's matrix was written one call ago and is certainly in L1 stack traffic, and a write pattern that jumps
B — level order, via an index breadth first, through an order[] array flat loops, no recursion, and a level is independent work both reads and writes are scattered through arrays that were never moved
C — level order, rows packed breadth first, with the rows physically rearranged reads and writes go straight down the arrays a permutation, every time the shape changes

B and C are worth looking at twice, because they visit in the same order and differ only in where the rows live. C is Lesson 5.7's group idea, generalised: 5.7 measured that two pools sorted to agree on index let a query skip the sparse lookup entirely, and noted that this was available precisely because dense order had never been promised to anyone. Here the same freedom buys an ordering constraint instead of an agreement between two pools — and it is worth noticing that the second use arrived two lessons after the first, without the design needing to be revisited.

3.2 Measuring an order without an ECS in the way

The three arms differ in a visit order over three parallel arrays, and that is all they differ in. So the probe (scratch/hier_probe.hpp) is three parallel arrays — a local transform, a parent row, an output matrix — plus two indexes built on top of them. No registry, no pools, no entities.

That is the same method Lesson 5.7 used to choose between an archetype and a sparse set before either was built, and it is worth naming the reason again: building the experiment on the ECS would tie four timings to one container's incidental behaviour, and then a change to the container would silently invalidate a design decision. What is being compared here is the order. The container's own cost is measured separately, in §4.4, and it is not small.

3.3 Being fair to all three

Three decisions in the probe are there to stop an arm winning for the wrong reason.

The recursive arm gets a CSR children list, not a vector of vectors. The obvious spelling for “each node's children” is std::vector<std::vector<uint32_t>>, which would hand arm A n separate heap allocations to chase and would make it lose to anything. Compressed sparse row — one children array and one child_start array — is what a competent implementation uses, so it is what the competitor gets.

Arm C's permutation is not timed inside the resolve. It is a cost the world pays when its shape changes, and hiding it in the per-frame number would be measuring a world that never spawns anything. §4.3 prices it separately and it turns out to matter.

The row order is an axis, not an assumption. In a world built all at once, row order is creation order, so parents naturally sit near their children and every arm walks nearly forwards. In a world that has been running for ten minutes the orders have decayed. Both are real; quoting only the first is not an argument. The tables below report both, and the difference between them turns out to be the entire case for arm C.

A measurement that reported the timer instead of the code

The first run of this benchmark reported 10.417 ns/entity for two different arms at n = 100. That number is 25 ticks of SDL's performance counter exactly — 41.67 ns each on this machine — and a pass over a hundred entities takes about a microsecond, which is below the course's noise floor of 100 ticks. The timer was talking, not the code.

The fix is the standard one from Lesson 4.9: scale the workload until it clears the floor and divide. Small worlds are now walked repeatedly — enough repetitions to reach 200,000 composes — and the total is divided by the total items. Every number below the thousand-entity mark in the tables that follow would otherwise be quantisation.
