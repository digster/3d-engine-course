In Lesson 6.4 the metallic workflow arrived as a consequence: a conductor absorbs what crosses its interface, so there is no subsurface scattering to come back out, so the only light leaving it is the mirrored part, so the colour has to live in F0 instead of in the albedo. And now a file arrives saying baseColorFactor = (1.00, 0.71, 0.29) with metallicFactor = 1, and f0_of returns (1.00, 0.71, 0.29) verbatim while diffuse_albedo_of returns exactly black. verify_66 §D asserts both. The engine was already speaking the format's language before it had ever read the format.

The one number in a glTF material that everybody gets wrong

The factor is linear. The texture is sRGB-encoded. They are multiplied together after the texture is decoded.

So gltf_material_desc::base_colour is a linear_rgb and there is no to_linear call anywhere near it — while material::tint is encoded, because Lesson 6.5 decided a tint is authored data that decodes at the input edge. The one conversion in the whole importer therefore runs in the direction nobody expects: linear → encoded, in load_model.

Get it backwards and gold's green channel comes in at 0.4624 instead of 0.7100, every imported asset is darkened by the gamma curve, and the result looks like a plausible lighting problem for years. verify_66 §D asserts the 0.71 and prints the 0.4624 beside it, so the failure mode is in the test output rather than in somebody's memory.

One more thing the file says that we can honour immediately: doubleSided. Lesson 6.5 split back-face culling into two questions — is this mesh closed?, a fact about the geometry that validate() answers, and do we want it culled?, an intent the caller supplies. doubleSided is exactly that second half, arriving from the person who authored the asset. cull_of(mesh_is_closed, want_two_sided) already had the parameter waiting.

This is that lesson, so the marker gets discharged. Here is Appendix B's complete model, quoted from the specification:

The claim in the comment turns out to be true in substance and imprecise in a way that matters. mix(a, b, F) is (1−F)·a + F·b, so the diffuse really is scaled by 1 − F(v·h). But the same F scales the specular up, and our cook_torrance_specular already carries it. Reading "the glTF reference uses 1 − F(v·h)" as a statement about the diffuse alone misses half the sentence.

Laid out term by term against what Lessons 6.3 and 6.4 derived:

@@FIG_BRDF@@

The metallic blend is not even a difference

Look at the fifth row of the figure. The spec lerps two whole BRDFs by metallic; this engine lerps the F0 and evaluates one BRDF (f0_of). Those look like two different models. They are the same model, and the reason is one line of algebra.

Schlick's approximation is affine in F0. Write w for (1 − |v·h|)5:

\[ F(f_0) \;=\; f_0 + (1 - f_0)\,w \;=\; f_0\,(1 - w) \;+\; w \]

That is a straight line in f0, so lerping the inputs and lerping the outputs commute. Work the spec's specular coefficient through, writing m for metallic and c for the base colour:

\[ \begin{aligned} (1-m)\,F(0.04) + m\,F(c) &= (1-m)\big[0.04(1-w) + w\big] + m\big[c(1-w) + w\big] \\ &= \big[(1-m)\,0.04 + m\,c\big](1-w) + w \\ &= F\big((1-m)\,0.04 + m\,c\big) \end{aligned} \]

And (1−m)·0.04 + m·c is exactly what f0_of computes. The specular halves of the two models are not close; they are the same expression.

Measured, because a derivation that has not been run is a conjecture

verify_66 §E evaluates both routes over 21 metallic values × 11 base colours × 21 view angles = 4,851 points. Worst difference: 1.192 × 10−7, which is float rounding and nothing else.

So f0_of is not an approximation of the spec's mix. It is the spec's mix, rearranged into one Fresnel evaluation instead of two.

The one factor that does differ

Everything reduces to a single term. The spec applies one Fresnel crossing, at the half vector; this engine applies two, at the light angle and the eye angle:

\[ k_d^{\text{glTF}} = 1 - F(v \cdot h) \qquad\text{against}\qquad k_d^{\text{ours}} = \big(1 - F(n \cdot l)\big)\big(1 - F(n \cdot v)\big) \]

Lesson 6.4 §7 gave the physical argument for two: light crosses the interface on the way in and on the way out, and each crossing reflects its own Fresnel fraction. The one-sided form describes what got in and says nothing about the light that fails to get out, so at grazing angles it lets out more than went in.

How much does that matter in practice? That is the question two lessons never asked, and it is the number verify_66 §E exists to produce. Sweeping the light and eye over a quadrant on shapes.glb's own red plastic:

So which do we ship?

The specification answers this itself, in two places, and the answers point the same way.

On variation, §3.9.6: "Implementations of the bidirectional reflectance distribution function (BRDF) itself MAY vary based on device performance and resource constraints." The BRDF is explicitly not the conformance surface — the material parameters are.

On correctness, Appendix B's "Complete Model": "In a physically accurate light simulation, the BRDFs MUST follow some basic principles: the BRDF MUST be positive, reciprocal, and energy conserving."

The resolution, and it is not the one Lesson 6.4 expected

Lesson 6.4 kept half_vector around on the assumption that asset interchange might one day require it. It does not. The spec permits the variation outright, and the property it actually requires — energy conservation — is the one two_crossing has at 0.9255 and half_vector lacks at 1.3395.

So the engine loads glTF materials and shades them with its own coupling, and is conformant in doing so. half_vector stays in the enum, named, measured, and selectable — because it is what the student will find in every engine they read next, and because 6.3's two geometry terms set the precedent: a choice you can run beats a choice you can read about.

And the design question 6.5's rule turns into a real one

The obvious alternative is to let each material carry its own coupling, so an imported glTF could be shaded the spec's way and everything else ours.

Lesson 6.5's membership rule refuses it, and the refusal is instructive: can this be a number in a buffer? A coupling is a branch in the shader. Two objects differing in it need two pipelines and a sort between them — it is pipeline state by definition, so it does not belong on material however convenient that would be.

Which leaves exactly one honest place for it: a renderer-wide choice, measured and documented. That is where it is.

7Where a Reference Stops Being a String

Now the architecture question, and it is the one that decides whether this code is still useful in Module 9.

A glTF material says "uri": "uv_grid.png". A engine::material holds a texture_handle. Somewhere between those two a string becomes a handle. Where?

@@FIG_LAYERS@@

The tempting answer is "in the loader" — parse_gltf could take an asset_store& and hand back finished materials. It would be fewer types and fewer lines.

Three things that answer would cost, and none of them is style

1. The parser could no longer be tested without a filesystem. Lesson 3.5 split parse_obj from load_obj for exactly this reason and §8 of that lesson used the split to test a dozen malformed inputs from string literals. A parser that needs a search path needs a disk.

2. Module 9's asset cooker could not use it. An offline importer runs at build time and writes its output to a cache. A handle is meaningless outside the pool that issued it, so a parser that returns handles produces output that cannot be serialised.

3. The policy would end up in two places. "Is this the same image we already loaded?" and "where do images live?" are questions asset_store already answers for OBJ and PNG. A second answer inside the glTF loader is a second answer that will eventually disagree.

So the layers are as the figure shows them. gltf.cpp turns bytes into descriptions — a gltf_material_desc holds a std::string base_colour_uri and an int material index, and knows nothing about pools, handles, caches or search paths. asset_store::load_model turns descriptions into handles. And the renderer turns a handle into a pointer, once per draw, through bind_albedo — which is Lesson 6.5's rule, unchanged.

8Implementation

8.1 — cgltf, wired in the same way stb was

Three lines in the root CMakeLists.txt and one in the engine's, matching the shape Lesson 4.7 established for stb_image. Pinned to a tag this time, because cgltf has releases — stb has none, which is why it had to be pinned to a commit.

PRIVATE is the whole of the boundary argument, and it is checkable rather than aspirational: no demo can include <cgltf.h>, because the directory is not on its include path. Swapping to tinygltf would be a one-file change.

One macro, in exactly one place

#define CGLTF_IMPLEMENTATION before the include compiles the parser into that translation unit. Putting it in a header would compile a copy into every file that included it and then fail to link on the duplicate symbols — which is the good outcome. The bad one is a build system that quietly picks one.

Same rule as STB_IMAGE_IMPLEMENTATION in image.cpp. Worth noticing that the whole cgltf implementation compiled clean at -Wall -Wextra on the first try, which stb did not — and that the macro is what confines the difference.

8.2 — Reading a primitive

The heart of the loader is forty lines. Attributes first, and they are iterated by name rather than fetched by index, because a glTF primitive's attributes are a dictionary whose order carries no meaning:

A real file may also carry TANGENT, COLOR_0, JOINTS_0, WEIGHTS_0 and four texture coordinate sets. We take three and ignore the rest without complaint, which is the correct behaviour for a format designed to be extended — and the loop shape is what makes it correct rather than accidental.

Then the read itself, which is the function that justified taking the library:

Float, normalized uint16, interleaved at a stride, sparse — every case, one call. And it returns false rather than reading past the end when an accessor points outside its buffer view, which is the failure a hand-rolled version gets wrong on somebody else's file.

8.3 — The ceiling, and why it is reported rather than fixed

mesh_data::indices is std::uint16_t, decided in Lesson 2.12. So a primitive can name at most 65,536 distinct vertices.

OBJ never made this fire, because the files this course ships are small. glTF will, because real exported assets routinely exceed it — a single .glb out of Blender may hold one 200,000-vertex primitive.

Why a counter and not a narrowing cast

The lazy version is static_cast<uint16_t>(index) and let it wrap. That version renders: you get a spray of triangles connecting the wrong corners of the model, which looks like a corrupt file rather than like a loader limit, and there is nothing anywhere saying what happened.

Widening the index type is a real answer and it costs real bytes on every mesh in the engine. Splitting the primitive is the other real answer and it costs real code. Both are exercises; neither is a thing to guess at inside a loader. What the loader owes you is skipped_too_large = 1, max 197,346 — a number you can act on.

8.4 — Walking the node tree

A glTF scene is a forest, so the walk is a recursion, and there is one decision inside it worth arguing.

The transform is not baked into the vertices. A loader that bakes produces a scene that can never be re-parented, instanced or animated, and the loss is silent — the picture is identical on frame one and the capability is simply gone. Lesson 5.9 built a transform hierarchy precisely so that placement stays data, so the geometry is what the file said and world_from_local is what the node tree said, kept apart.

verify_66 §C checks both halves. shapes.glb's "group" node translates by (1, 0, 0) and its child "gold octahedron" by (0, 2, 0), so the octahedron's world translation must be (1, 2, 0) — a product down the tree, not the local transform. Two levels deeper, the tetrahedron lands at (1, 3.5, 0). And the octahedron's own vertices still top out at y = 0.60 rather than 2.60, which is the assertion that nothing was baked.

A layout agreement worth noticing

cgltf_node_transform_world writes sixteen floats column-major, which is exactly mat4's own storage (Lesson 2.5). So to_mat4_column_major is a copy and not a transpose.

Three independent decisions landed on one layout: glTF stores matrices column-major because its matrix property says so; mat4 is column-major because its columns are where the basis vectors land; and HLSL constant buffers want the same, which is why Module 4 uploads a mat4 with a plain memcpy. The transpose that catches out every second importer never arises.

8.5 — The bridge that had never been built

Here is a gap this lesson found by walking into it, and it is a good example of a hole that no test could see because no code path crossed it.

The engine has been able to decode a PNG since Lesson 5.3: load_image produces an image_data of RGBA bytes. It has been able to sample a texture since Lesson 3.9: sample(texture, sampler, u, v) returns linear light. Nothing has ever joined them.

Every CPU texture in this engine was generated — make_checker, make_uv_grid — and every loaded image went straight to the GPU as bytes through gpu_texture::create_sampled. Two complete halves with no middle. glTF is what forces the join, because a material names an image file and the software renderer has to be able to sample it.

It is a channel shuffle, not a memcpy

image_data::pixels is R, G, B, A in that byte order, as stb hands it over. texture stores Uint32 in ARGB8888 — the framebuffer's own format (Lesson 1.5) — which on a little-endian machine is the bytes B, G, R, A.

Copy the buffer wholesale and red and blue swap, which is the single most recognisable wrong-looking texture there is. Writing it through pack_argb means the memcpy version is not even expressible. verify_66 §F asserts texel (3,3) comes out 0xFFDE463C and prints 0xFF3C46DE beside it as the shape of the failure.

There is no vertical flip in that loop, and there must not be: image_data stores the file's rows top-first (5.3) and texture puts row 0 at the top (3.9). Those are the same convention. The v flip that OBJ needs lives in the geometry import, which is the only place it can be decided from — it is the format of the mesh that disagrees about which way v points, not the image.
