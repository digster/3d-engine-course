10Implementation

Twenty-two files change and none is created, which is itself a design statement: a local light is a new kind of term in sums the engine already computes, a new kind of camera for machinery it already has, and a new kind of resource in a shader interface it already binds. The order below is the order the work was done in and the order a student should type it: the CPU renderer first, completely, because the CPU renderer is the one you can step through; then the GPU, held to it pixel by pixel.

10.1 — The light, and a function lifted out of shade()

light.hpp gains the struct and the four factors of §3–§5, each a few lines, each named for what it is: 

struct local_light
{
    local_light_kind kind = local_light_kind::point;

    vec3 position{0.0f, 0.0f, 0.0f};
    vec3 direction{0.0f, -1.0f, 0.0f};   ///< spot axis, direction of TRAVEL, unit length

    linear_rgb colour{1.0f, 1.0f, 1.0f}; ///< in linear light, as the sun's is
    float intensity = k_reference_irradiance;   ///< irradiance at 1 m, square-on

    float range = 10.0f;

    float inner_angle = 0.0f;                   ///< spot only, radians from the axis
    float outer_angle = 0.78539816f;            ///< spot only, radians; pi/4

    bool casts_shadow = false;
};

Every default is someone else's default on purpose: the intensity is the sun's, so a default-constructed lamp is comparable with the light the student already has; the cone is glTF's, so an imported spot with no cone block means what its exporter meant; and casts_shadow is off, because a shadow costs a render pass (six, for a point) and should be asked for.

range_window takes the squared distance and never calls sqrt: (d/r)⁴ is (d²/r²)², and d² is what dot(d, d) produced anyway. A range of zero or less means infinite, which returns 1 and lets §A measure the bare inverse square. 

[[nodiscard]] inline local_light_sample sample_local_light(const local_light& light,
                                                           vec3 surface_pos)
{
    local_light_sample s;
    const vec3 d = light.position - surface_pos;
    s.distance_sq = dot(d, d);
    s.to_light = normalised_or(d, vec3{0.0f, 0.0f, 0.0f});

    s.attenuation = inverse_square(s.distance_sq) * range_window(s.distance_sq, light.range);
    if (light.kind == local_light_kind::spot)
    {
        s.attenuation *= spot_cone(dot(light.direction, -s.to_light), cone_terms_of(light));
    }
    return s;
}

sample_local_light is split from the shading because the shadow lookup needs the same direction and distance, and computing them twice is how a shadow and the light it belongs to end up disagreeing about where the lamp is. shade_local then does what shade() does for the sun, with the arriving irradiance replaced: colour × intensity × attenuation × cos θ × visibility, times the BRDF.

And the BRDF is the same one, not a copy. shade()'s dispatch — Lambert, Blinn-Phong or Cook–Torrance, with the NDF choice — is lifted into surface_brdf() statement for statement, and both call it. The words "statement for statement" carry the proof obligation: a lift that reordered one multiplication would change a float somewhere in the reference render, and §D checks that it did not — 1,382,416 bytes, 0 differing. A lamp a kilometre out, scaled to deliver the sun's irradiance, then agrees with the sun to 2.84 × 10−5 over 2,310 evaluations, which is the same comparison from the other side: one BRDF, two ways of delivering light to it. (Why 2.84 × 10−5 and not zero: with coordinates of a thousand metres the direction to the lamp differs from the sun's in the last bits of a float, and a GGX lobe at roughness 0.2 turns a 10−7 change in n·h into a relative change hundreds of times larger. The bound is on the rounding, 10−4, and the harness says why.)

10.2 — The CPU renderer: a loop after shade()

fill_style gains two members — local_lights, a std::span<const local_light>, and local_shadows, a pointer that may be null — and the fragment path in raster.cpp gains one loop, after shade() and before 6.15's ambient term: 

if (!style.local_lights.empty())
{
    const vec3 gn = normalised_or(n, vec3{0.0f, 1.0f, 0.0f});
    for (std::size_t k = 0; k < style.local_lights.size(); ++k)
    {
        const local_light& lamp = style.local_lights[k];
        const local_light_sample at = sample_local_light(lamp, p);
        if (at.attenuation <= 0.0f) { continue; }

        float lamp_visibility = 1.0f;
        if (style.local_shadows != nullptr && lamp.casts_shadow)
        {
            lamp_visibility = style.local_shadows->visibility(
                k, p, gn, dot(gn, at.to_light));
        }

        const linear_rgb c = shade_local(albedo, p, shading_normal, style.eye - p,
                                         lamp, style.surface, style.model,
                                         ndf_model::ggx, lamp_visibility);
        direct = {direct.r + c.r, direct.g + c.g, direct.b + c.b};
    }
}

Three decisions are in those lines. The loop sits after shade(), not inside it, because light is additive (conventions §7c) — a second source is a second term in the sum and nothing about the first changes, so an empty span leaves direct untouched to the bit. The early out comes before the shadow lookup, because the lookup is the expensive part and pointless for a pixel outside the lamp's reach. And the shadow's cosine is taken against the geometric normal and this lamp's own direction: 6.8's rule, one cosine per light. A span is the right type for a list the renderer only reads and the caller owns — the style guide's rule for non-owning access — and it is what makes "no lamps" the default with no special case.

10.3 — The CPU shadows: two fitters and a set

light_camera learns it can be perspective: a flag (false by default, so every camera built before this lesson is unchanged), the near and far planes (the depth curve needs them), and the eye and axis (the slope of §6.4 needs them). fit_spot and fit_cube_face produce such cameras. The cube face's view is built from rows, which is the one line in the lesson worth reading twice: 

const cube_axes ax = cube_face_axes(face);
const vec3 r = ax.u;
const vec3 upv = -ax.v;
const vec3 back = -ax.major;
const vec3 p = light.position;

// Column-major storage (conventions §3): each braced group is a COLUMN.
cam.view_from_world = mat4{
    {r.x, upv.x, back.x, 0.0f},
    {r.y, upv.y, back.y, 0.0f},
    {r.z, upv.z, back.z, 0.0f},
    {-dot(r, p), -dot(upv, p), -dot(back, p), 1.0f}};

A view matrix's rows are the camera's right, up and back axes — Lesson 2.9's definition, which look_at builds from a forward and an up hint. Here all three are dictated by the face table rather than chosen. look_at(p, p + major, −v) would compute the same up and back and then derive right as forward × up, which for every face is −u. Writing the rows out is the whole fix.

local_shadow_set then owns one shadow_map per shadowed spot and six per shadowed point — built on 6.8's shadow_map, not beside it. The rasterizer, the depth format, the PCF loop and the bias policies are all 6.8's; what 6.17b adds to shadow_map::visibility is the perspective branch of §6 (texel × w, the new slope, the depth curve, the rounding floor, the clamp at the face) and nothing else. The orthographic path computes nothing new and is bit-identical, which the golden and every later harness confirm. The set's own visibility picks the map: a spot's is its own; a point's is the face direction_to_cube(p − position) says owns the direction.

10.4 — The guard band, in the one place it belongs

clip.hpp gains §8's four planes, the test and the clipper; soft_renderer.cpp computes the planes once per call from the viewport and uses them in exactly one case — near_mode::clip, on a polygon outside_guard_band says has left the band — fanning the result into triangles from the same vertex the near clip fans from. Every other triangle takes the path it took yesterday.

10.5 — To the GPU: one record per lamp, in a storage buffer

6.15 left one float of padding at offset 180 of the fragment light block. It becomes local_light_count, guarded by a static_assert that says why it matters: the count lands in the pad, or it is not free. Everything else about a lamp goes in a record the fragment stage reads from a storage buffer, the first the engine has bound to a fragment shader:

@@FIG_RECORD@@

Why not push the lamps as uniforms, like everything else so far? Lesson 4.6 measured the answer without knowing it was one: SDL takes every uniform push from a 32 KiB block, and the Vulkan backend's descriptor covers only 4 KiB of each. At 176 bytes a lamp, that is 23 lamps before one backend silently reads past the end — a ceiling set by an implementation detail of a single backend, on a list whose length the scene decides. A storage buffer (SDL_GPU_BUFFERUSAGE_GRAPHICS_STORAGE_READ) is bound rather than pushed, so its bytes move once per frame instead of once per draw, and its size is whatever the scene needs.

Two rules keep the record's layout honest across three compilers. Every member is a float4, so DXC, glslang and SPIRV-Cross have nothing to disagree about — StructuredBuffer packing rules for mixed scalar and vector members are exactly where they do. And the matrix is stored as four rows, not as a float4x4, so no default matrix packing can transpose it on the way; the shader takes four dot products. Three static_asserts pin the size (176) and two offsets.

10.6 — The resource layout, and two numbers that disagree on purpose

The fragment shader now declares eight sampled textures and one storage buffer: 

Texture2DArray<float>   spot_shadows  : register(t6, space2);
SamplerComparisonState  spot_shadow_cmp  : register(s6, space2);
TextureCubeArray<float> point_shadows : register(t7, space2);
SamplerComparisonState  point_shadow_cmp : register(s7, space2);

StructuredBuffer<LocalLight> local_lights : register(t8, space2);

and the C++ binds the storage buffer at slot 0. The shader says t8; the renderer says 0. Both are right. SDL_GPU numbers each resource kind from zero on the C++ side — sampler slot 0, storage-buffer slot 0 — while its HLSL resource layout (the comment block above SDL_CreateGPUShader in SDL_gpu.h) puts sampled textures, then storage textures, then storage buffers into one t sequence in space 2. Eight sampled textures occupy t0–t7, so the first storage buffer is t8. On Metal the translated shader shows the same thing from a third angle: the buffer lands at [[buffer(3)]], after the three uniform blocks, and the cube array becomes depthcube_array<float>. The comment at the bind says all of this, because the next person to add a sampled texture moves the storage buffer to t9 and must know that slot 0 does not change.

10.7 — gpu_local_shadows: budgets, jobs, and a shared depth pass

gpu_shadow.cpp already built a depth-only pipeline and recorded depth draws for the sun's cascades. Those two pieces move into an anonymous namespace — build_depth_only_pipeline, record_depth_draws, begin_depth_pass — with every log string and debug event kept identical, so 6.8's and 6.9's harness transcripts do not move. The new class uses them for lamps:

  • create makes one depth Texture2DArray of max_spots layers and one depth TextureCubeArray of max_points cubes — the latter through gpu_texture::create_depth_cube_array, which asks SDL_GPUTextureSupportsFormat first (§7.5).
  • prepare(lights, out) packs one gpu_local_light per lamp, assigns shadow slots in list order within each kind's budget, and emits a job per pass to record: one for a spot, six for a point. A shadowed lamp past its budget keeps slot −1 and is drawn unshadowed, with a warning naming the budget.
  • render records every job as its own render pass; render_into records one job into a pass somebody else began — the frame graph's shape, which §10.9 uses.

A point light's record carries no matrix, and §7.3 is why: the cube lookup takes a direction and the depth is the major axis. Its four rows stay zero.

10.8 — gpu_scene: the caller's list, the renderer's count

render and render_batched take one more trailing argument, a const scene_local_lights* defaulting to null, so every existing caller compiles and behaves as before. The struct holds the light buffer, its count, the two shadow textures and the comparison sampler. Three things happen with it.

  • The count is the renderer's, not the caller's. The count the shader loops to and the buffer it indexes must describe the same list, and the only place both are in hand is begin_frame. So the light block is pushed from a copy whose local_light_count the renderer sets — zero unless a real list arrived. A caller cannot make the shader read past the end of a buffer by leaving a stale number in a struct.
  • Every declared resource is bound, always. A shader that declares a storage buffer must have one bound even if its loop runs zero times — SDL's debug layer asserts "Missing fragment storage buffer binding" at draw time. The renderer owns three identity elements for the case where the caller has no lamps or no shadows: a zeroed one-record light buffer, a one-layer depth array and a one-cube depth cube array, both cleared to the far plane at creation (seven empty render passes, once). 6.15 established the pattern for its environment maps; the caller never has to know the shader has these slots. And they are created with the types their slots declare, which 6.8's own fallback for the sun's slot turned out not to be: it was a plain 2D texture in the slot 6.9 re-declared Texture2DArray. It rendered correctly, and Metal's validation layer (MTL_DEBUG_LAYER=1) reported it on every draw that used it — twelve times in this lesson's harness. The first version of this page said Metal tolerated it and set it as an exercise; run under the validation layer, it did not, and it is now a one-layer array like the other two.
  • The frame-constant samplers are bound together, now eight of them, in bind_fragment_samplers, and the storage buffer at slot 0 in bind_local_lights, which records a bind_storage event in 4.9's frame log, so a dump of the frame shows the binding.
A correction carried here

Until this lesson, the comment in gpu_scene.cpp explained binding all the samplers in one call by saying a partial SDL_BindGPUFragmentSamplers "replaces the range it names", unbinding everything outside it. The post-Module 8 review read SDL's source at release-3.4.12 and found otherwise: all three backends write only firstSlot + i, and what resets bindings is ending the pass. The measurement behind the old comment was right and its explanation wrong. This lesson rewrites the function anyway, so it carries the correction: binding all eight together is still correct and still one call — only the reason changed. Exercise 6.17b.3 cashes in what the corrected rule permits.

10.9 — The frame graph: seven passes declared, and a frame that declares none

6.17 built the frame graph for passes like these, and a lamp's shadow is the first new pass to arrive since. Each job becomes one declared pass with one statement: it clears one layer of an imported texture. The scene pass samples both textures. 

engine::fg_texture spots  = fg.import("spot shadows",  shadows.spot_texture(),  spot_desc);
engine::fg_texture points = fg.import("point shadows", shadows.point_texture(), point_desc);

for (int j = 0; j < shadows.job_count(); ++j)
{
    const engine::local_shadow_job& job = shadows.job(j);
    const int p = fg.add_pass(names[j], &exec_local, &ctx[j]);
    if (job.kind == local_light_kind::spot) { spots  = fg.clear_depth(p, spots,  1.0f, job.layer); }
    else                                    { points = fg.clear_depth(p, points, 1.0f, job.layer); }
}

const int scene = fg.add_pass("scene", &exec_scene, &sctx);
fg.sample(scene, spots);
fg.sample(scene, points);

6.17's rules then derive everything. A clear of one layer keeps the other layers, so it consumes the previous version and produces the next: the six faces form a chain, and because the scene samples the chain's last version, every face's store op comes out STORE. §I prints the derived ops — seven CLEAR/STORE shadow passes, the scene's colour CLEAR/STORE and its depth CLEAR/DONT_CARE, 4.7's choice derived again — and the declared frame matches the hand-recorded one on all 196,608 channels.

10.10 — The shader loop

scene.frag.hlsl gets the same lift as light.hpp — surface_brdf and specular_alpha move out of main so the sun and the lamps share them — and then one line in main: 

float3 lit = f_r * e + ambient_term;
if (local_light_count > 0.5f)
{
    lit += shade_local_lights(p, n, geometric, v, base, diffuse_albedo, spec_f0, ct_alpha);
}

shade_local_lights is raster.cpp's loop in HLSL, in the same order — where the lamp is, an early out, then the shadow, then the BRDF — because §G holds the two renderers to one another pixel by pixel, and the easiest way to make two implementations agree is to make them the same sequence of operations. The guard on the count is not an optimisation: with no lamps the loop body is never reached and the sun's pixels are bit-for-bit what they were, which §H checks.

10.11 — The demo

gltf_view --lights puts two lamps into the CPU renderer's scene, sized from the model's bounds so any model works: a warm bulb to one side at half the model's span above the floor, and a cool spot high on the other side, aimed at the floor beside the model. Each is given the intensity that delivers twice the sun's reference irradiance where it is aimed — 2π · d² for a lamp d metres from that point, §3.2's unit doing its job — and the sun is turned down to a tenth, so the lamps dominate and the picture reads as night with a lamp on. --lamp-shadows 0 drops both maps.

11The instruments, and the judge that was wrong four times

verify_617b runs forty checks in ten sections, and each section's shape is 5.3's rule: a measurement, a claim, and a control that proves the measurement could have failed. Three instruments carry most of the lesson, and each has a story about being wrong.

11.1 — Two renderers held to each other

§G renders one lit ground from straight above through both renderers, with the same two lamps, and compares every pixel in linear light. Each pixel is a known floor point, so a disagreement has a location, and every disagreement is classified by its distance to the nearest shadow edge in the CPU's image. Without shadows the renderers agree on all 62,940 lit pixels to 2 × 10−4 relative, worst 1.66 × 10−5. With them: 

  with shadows: 61043 lit pixels, 60784 agree, 259 differ; 6115 shadowed lamp-pixels
  disagreeing pixels by distance to the nearest CPU shadow edge:
    <=1 px 259   <=2 px 0   <=3 px 0   <=4 px 0   <=5 px 0   beyond 0

Every one of the 259 is within a pixel of a shadow edge, where the two filters legitimately differ — nearest-texel on one side, a 2×2 bilinear comparison on the other — and they are 259 of the 4,340 pixels in that band. The control widens the spot's cone by 5% and moves 9,992 pixels, so an instrument that reports 259 can see ten thousand. This comparison is what found the GPU's reach (§9.1, 11,098 disagreements off any edge) and the perspective slope (§6.4, nineteen). The last three of those nineteen were not a bias at all: they sat on the rim of the spot's cone, where the attenuation is a few parts in 105 and the two renderers' rounding of spot_cone differed by more than the relative tolerance. The comparison gained an absolute floor of 10−5 — nearly four hundred times smaller than one step of an 8-bit display — and the harness says why next to it.

11.2 — A judge that shares no code with the engine

§F's acne and leak counts need to know, at each point, whether the lamp really sees it. The judge answers by casting a ray from the point to the lamp against the analytic box, sign and ground — no shadow map, no rasterizer, no engine geometry. Then it has to decide which points it is allowed to judge, because a point exactly at a shadow's edge has no right answer at a map's resolution: the map cannot resolve anything finer than a texel, so both answers are defensible there. Excluding those ambiguous points is correct. Deciding which they are was wrong four times.

  1. A fixed 6 cm on the floor around each shadow's edge. A texel's shadow at grazing incidence is wider than that.
  2. One and a half texels on the floor. Scaled with the map, and still too narrow.
  3. Two texels on the floor. It failed on a point whose ray clears the top edge of the box by a fifth of a texel and then travels another three metres to the ground. No floor position within half a metre of that point is anywhere near the box's shadow — and yet the map, which resolves directions from the lamp one texel apart, cannot tell whether that ray grazed the box or not. The ambiguity was never on the floor. It was in the angle.
  4. Two texels of angle, tested only at the two ends. The ray was tilted two texels' worth each way, and stepped straight over the 4 mm sign, which is half a texel wide — the very aliasing the map itself suffers from.

The judge that shipped measures ambiguity in the light's own angles, densely: it tilts the ray from the lamp by every quarter of a texel's angular size, out to two texels, in two perpendicular directions each way, re-places the point along each tilted ray at its own distance, and calls it ambiguous if any tilt changes the answer. That is the resolution the map actually has, expressed in the only coordinates where it is the same everywhere. With it, the derived bias scores 0 acne and 0 leaks over 67,715 spot points and 343,360 cube points — and the controls (no bias: 19,502 and 119,886 acne) show the same judge can see failure in both.

The four wrong judges are recorded in the harness, above the one that replaced them, because the pattern will recur. Each was caught the same way: by probing a single flagged point until it explained itself — rather than excusing it, and rather than changing the engine until the count went to zero. A judge that flags a point is making a claim about the engine and about itself, and the question to ask first is whether it is measuring in the coordinates the thing it judges actually has.

12The ninety-percent picture

This is the ninety-percent picture of local lights. The missing ten percent, named so nobody mistakes the silence for a claim:

  • Every lamp is evaluated for every fragment. The range makes a lamp's reach finite, which is the precondition for culling, but nothing culls yet. Real engines bin lamps into screen tiles or clusters (a compute pass per frame) and loop only over each pixel's own list — Olsson, Billeter and Assarsson's clustered shading (2012), and the tiled and clustered forward shading of RTR4 chapter 20. 6.18b's compute shaders are the tool; the scale at which it pays is dozens of lamps, not two.
  • Lamps are points. A real bulb has a size, which softens its highlights and its shadows. The 1 cm clamp is the only acknowledgement of size here. Area lights — spheres, tubes, rectangles — are the rest of Frostbite 2014's lighting chapter and the subject of Karis 2013's representative-point trick, and their shadows need penumbra estimation (PCSS). The GGX highlight of a point light on a very smooth surface is therefore a pinprick that aliases; 6.14's specular antialiasing reduces it and does not cure it.
  • The cube's PCF stops at the face edge on the CPU. The GPU's one tap is 2×2 PCF and blends across face edges in hardware; the CPU's six maps cannot, so point lights default to radius 0 on both renderers for parity. Exercise 6.17b.4 widens it.
  • Shadow budgets are fixed at creation (four spots, two points), and a shadowed lamp past its budget goes unshadowed. Choosing which lamps get shadows each frame — by screen size, distance, importance — is a policy real engines spend real effort on, and the budget-and-warning here is only its mechanism.
  • Cached shadows need an invalidation policy (§10.9). The graph can express a cached frame; deciding when a lamp's map is stale is not written.
  • Lamps have no volumetric scattering and no IES profiles. Real luminaires emit anisotropically, described by photometric profiles; the cone is a first approximation of one.
