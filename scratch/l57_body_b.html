4The Experiment

4.1Simulating a design you have not built

The probe is one header, and the first thing to say about it is what is not in it. There is no entity manager, no component registry, no type erasure, no view type, no system scheduler, and no way to create an entity. Every one of those is required by a real ECS and none of them differs between the two designs, so including them would put a thousand lines of identical machinery between us and the two numbers we came for.

What is in it is the two access patterns. An archetype is four parallel std::vectors and a shared index; a sparse set is, per type, three vectors and a redirect. Both hold the same entities with the same component values, generated from the entity id by the same integer hash Lesson 5.6 used, so the two arms can be compared bit for bit.

Twenty lines, and everything the sparse-set design claims is visible in them: the insert is two appends and a write, the erase touches one pool, and neither has any way to know what else the entity owns. Compare that with the archetype's move, which needs a source chunk, a destination chunk, a per-entity archetype map, a per-entity row map, and a re-pack — a hundred lines in the same file, and it is not padded.

C++ in place — if constexpr, and why K is a template parameter

The query is written once and instantiated for K = 1, 2, 3, 4. Making K a template parameter rather than a runtime argument matters for a benchmark: if constexpr (K >= 2) is resolved at compile time, so the K = 2 instantiation contains no branch, no dead pointer and no unused load. A runtime if would leave a predictable branch in the loop, and predictable branches are cheap but not free — at 0.5 ns per item, "not free" is 10% of the measurement.

The same trick carries the two body variants as a bool Real. Two template parameters produce eight query functions from one piece of source, which is the property that matters here: every arm runs the same code, so a difference in the source cannot be a difference in the result.

4.2Being fair to the archetype

A benchmark comparing your preferred design against a strawman is a benchmark whose result you already know. Three deliberate concessions were made to the archetype, and each one costs it nothing that a real implementation would not also avoid.

Its columns are statically typed. The probe's chunk holds std::vector<engine::transform>, not a type-erased byte buffer with a per-archetype column index that has to be looked up. A real archetype ECS cannot do this — the set of component types is not known at compile time, so a query must resolve "which column is transform in this archetype" per archetype per query, and its inner loop indexes through a pointer it obtained at run time. The probe skips that cost entirely. Every archetype number below is therefore an upper bound on how good a real archetype ECS would be.

Its query really does skip non-matching entities. The chunk carries a columns count and the query walks only chunks with at least K of them, so in the selectivity test the archetype visits a quarter of the world and the other three quarters cost it literally nothing — not even a rejected test. That is the archetype's genuine structural advantage and the experiment gives it in full.

Its fragmented case is measured, not assumed. §5.4 splits the same entities across up to 4,096 archetypes and reports what that costs, rather than asserting that fragmentation is a disaster because the sparse-set literature says so.

4.3Being fair to the sparse set: the alignment axis

The sparse set gets one concession too, and it is the axis most published comparisons leave out. Ask the question directly: when the query reads velocity.sparse[e], where in memory does it land?

A pool's dense order is its insertion order. In a world built all at once — spawn ten thousand entities in a loop, each with the same four components — every pool receives the same entities in the same sequence, so every pool's dense order is identical. The query walks the transform pool in order, and velocity.sparse[e] therefore also walks in order. The redirect is a sequential read that the hardware prefetcher will have already fetched. It costs almost nothing.

Now run the game for ten minutes. Things spawn and die, components get added when a character picks up a torch and removed when it drops it, and every erase swaps some unrelated entity into the hole. The pools' orders drift apart, and eventually there is no relationship between position in one pool and position in another. The same source code is now performing random access into a 1.6 MB array.

Both are real, and a comparison that quotes one is not a comparison

The benchmark therefore builds the sparse world twice: once aligned (every pool receives entities in id order) and once scrambled (each secondary pool receives them in an independent random permutation). These are the best and worst case of the same design, they differ by up to 1.8× in the results below, and the truth for any given world is somewhere between them. The lead pool is in id order in both, so the two arms visit entities in the same sequence — which is what lets the harness demand bit-identical answers rather than a tolerance.

4.4Two bodies, because one cannot answer the question

§2.3 concluded that the redirect is latency and that latency can be hidden behind work. That is a hypothesis with an obvious test: run the same query with two different amounts of work in it and see whether the penalty changes.

The real body is deliberately the same workload Lesson 5.6 timed — build a model matrix with parent_from_local, then read all sixteen entries of it with layouts::sample. Reading all sixteen was 5.6's hard-won correction: reading five lets a compiler stop computing the other eleven in whichever arm it managed to inline, and 5.6 published a 3.4× that was really 1.7× before it caught that. Reusing the function rather than re-typing it means 5.7 cannot re-acquire the bug, and it puts both lessons' numbers on the same scale.

Everything else about the harness is Lesson 5.6's, unchanged: bench_compare alternates the arms one repetition each so drift lands on both, medians with minimum and maximum so a hiccup is visible, bench_keep so the loop is not deleted, a bias that differs per pass so the pass is not a pure function of nothing, and enough inner repetitions that a sample is worth ~100 µs against a 41.67 ns timer tick. Every ratio quoted below is taken within one alternating pairing, never between two absolutes from different pairings — 5.6 found the same arm reading 0.98 and 1.83 ns depending on who shared the cache with it.

5The Results

Everything below is from one machine — an Apple M4 Pro, 64 KB L1d, 4 MB L2 — built with Clang at -O2 -DNDEBUG, no LTO. Run it on yours; the shapes should survive and the exact sizes will move. python3 scratch/measure_57.py prints every table in this section.

It is 0.99×–1.01× at every size on the real body. The instrument is honest.

5.2The redirect is latency, and latency hides

There is one loose end in the table above and it is at the far left: the cheap arms at n = 4 read 0.81× — the sparse set beating the archetype by 19% on four entities in L1, which no memory effect can explain. Worse, the full data has the archetype's own K = 3 column at n = 4 costing 2.58 ns against 0.87 ns at K = 4. A cost that is not monotonic in the amount of work is not a cost, it is a compiler.

Lesson 5.6's answer to this applies unchanged: rebuild with the vectoriser off and see what moves. One experiment, and it does two jobs.

Job one: the n = 4 anomalies are gone. The archetype's non-monotonic K = 3 column collapses from 2.58 ns to 0.53, and the cheap arms stop beating the archetype at four entities. They were vectorisation decisions — the auto-vectoriser succeeding on one arm's four-iteration loop and not another's — which is a property of the compiler and of nothing else. This is why the left-hand columns of the vectorised table should be read as "no difference" rather than as numbers.

Job two, and it is the mechanism. Look at the real body with codegen held still: 1.00×, 1.00×, 1.01× up to a thousand entities, on the scrambled world. Not "close to". The redirect, performed with the pools in completely unrelated orders, costs nothing at all — and then costs 1.21× at ten thousand and 1.39× at a hundred thousand.

The finding, stated as a mechanism rather than a ratio

The sparse set's extra loads are latency in the shadow of work already being done. While the core is executing the nine multiplies and sixteen stores of parent_from_local for entity i, it has already issued the redirect loads for entities i+1 and beyond, because those addresses are available and independent. The loads finish before anyone asks for them.

Two things break the shadow, and both must happen together. The working set must exceed cache, so the latency to hide grows from ~4 cycles to ~200; and the pools must be out of order, so the prefetcher cannot have fetched the line already. Aligned at 100,000 is 1.02×; scrambled at 1,000 is 1.01×; scrambled at 100,000 is 1.39×. Neither condition alone costs anything.

That also tells you which systems in a real engine will and will not care. A render query building matrices, a physics integrator doing collision maths, a skinning pass blending matrices — these all have work to hide behind. A system that adds two floats across a hundred thousand entities does not, and that is exactly where the cheap body's 2.79× lives.

The ratio is not the finding. The finding is which row moved. The sparse set goes from 4.25 to 4.23, which is the same number.

That is §3.2's cost model confirmed and its correction confirmed with it. The archetype's move is two memory touches per column, and the columns are what widened; the sparse set's insert is three writes into one pool, and the pool did not widen because pools never do.

Four components is a number that flatters the archetype

The probe's entity has four. A shipping game entity has ten to thirty — a transform, a parent link, a mesh, a material, a bounding volume, a rigid body, a collider, a health value, a team, an AI state, a sound emitter, a light, an animation state, a network id. This course's entity will pass twelve during Modules 7–8, when rigid bodies and skeletons arrive. The 13.83× column is the one to plan against, not the 3.08× one.

Both designs' small-world numbers deserve a note, because they look wrong. At n = 4 the sparse set costs 9.56 ns rather than 4.25 — more than at 100,000. That is not the world size, it is the churn set: 1% of four entities is one entity, so a "frame" is two operations and the per-frame overhead (building the set, the loop setup) is divided by two instead of by two thousand. It is measurement overhead, it applies equally to both arms, and the ratio in that column is still meaningful even though the absolute is not.

5.4Fragmentation, measured, and smaller than advertised

The standard argument against archetypes is fragmentation: every distinct component set is a separate chunk, so a game with lots of rare combinations ends up with thousands of tiny archetypes and the contiguity that justified the design evaporates. It is stated confidently and almost never measured. Here it is, at K = 4 on the real body:

Twelve percent, worst case, with two entities per archetype. That is far less than the argument implies, and the reason is visible once stated: a chunk of two entities is still contiguous, still prefetched, and the per-chunk overhead is a loop setup, not a cache miss. Splitting a contiguous array into 4,096 contiguous arrays does not stop it being contiguous.

Be careful about what this does and does not license. It measures iteration over fragmented archetypes, which is the part the probe can simulate honestly. It does not measure what a real archetype ECS additionally pays as archetypes multiply: resolving which archetypes match a query (a set operation over thousands of them, usually cached but the cache has to be invalidated on every structural change), the per-archetype column lookup §4.2 gave the probe for free, and the allocator pressure of thousands of small chunks. Those are real and this lesson does not measure them — so the honest summary is that fragmentation's iteration cost is small, its bookkeeping cost is unmeasured here, and the case against archetypes should not lean on this argument.

5.5Selectivity, and the group that answers it

Now the archetype's best case, and the one the argument should be judged on. Give one entity in four a velocity and query {transform, velocity}. The archetype visits exactly the matching quarter, contiguously. The sparse set walks its dense velocity pool — also exactly the matching quarter — and reaches into a transform pool where only one element in four is wanted, so every cache line it fetches contains one useful transform and two useless ones.

The first three rows are the archetype winning, properly, by 1.46× to 1.94× on a real body at scale — a bigger margin than the all-match query gave it, exactly as §2.1 predicted. Two of those rows are also an implementation lesson worth having: leading with the small pool rather than the big one is one line in a view's constructor, it means no entity is ever visited only to be rejected, and it is worth 1.73× → 1.46×. The "sparse sets are bad at selective queries because they have to skip" claim is about a naive implementation, not about the design.

And then the last row, which is why this lesson's recommendation is confident rather than grudging.

A group is an archetype you can add later

A pool's dense order is nobody's business but the pool's — no id outside it depends on where an element sits. So two pools can be sorted into a common order, putting the entities that have both components at the front of both dense arrays in the same sequence. Once that holds, index i of one array and index i of the other are the same entity, the query needs no sparse read at all, and what you are iterating is — byte for byte, access for access — an archetype chunk.

EnTT calls this a group. It is not a different storage design; it is a maintenance obligation laid on top of one, paid as a couple of swaps on insert and erase for the pools involved. Measured: 0.99× to 1.01× of the archetype at every size, on the archetype's best case.

So the archetype's query advantage is not a permanent property of the archetype. It is something a sparse set can buy, per query, when a measurement says that query needs it, at the price of slower structural changes for the two or three component types in that group — and at no cost to the other thirty.

This course builds a sparse set. Four reasons, in the order of how much weight they carry.

1. The migration only runs one way. This is the argument, and everything else is supporting detail. A sparse set can be given an archetype's query performance later, incrementally, one group at a time, guided by a profile, without changing what a component is or invalidating a single id — measured at 0.99× on the archetype's own best case. An archetype cannot be given a sparse set's O(1) structural change at all, at any price, because moving between archetypes is what an archetype is. Choosing the design that can become the other one is not a preference; it is the option with strictly more future in it.

2. The cost we would be accepting is bounded and the cost we would be avoiding is not. The archetype's query win is at most 1.94×, only above ten thousand entities, only when a query is selective, and only on the arms we have not grouped. The archetype's structural-change loss is 13.8× and it grows with every component type this course adds — Module 6 adds materials, Module 7 adds skeletal state, Module 8 rigid bodies and colliders and state. A cost that scales with the future of the codebase is worse than a larger cost that does not.

3. Nothing at this engine's scale is on the table anyway. Below a thousand entities every arm is within 16% and most within 5%. The demos have four objects. Module 9's capstone will have hundreds. We are choosing the design that will be right at 105 entities while paying nothing either way at 102, which means the decision can be made on the properties above rather than on today's frame time.

4. It is a quarter of the code, and this is a course. Twenty lines against a hundred in the probe, and the gap widens in a real implementation: an archetype needs type-erased columns, chunk allocation, an archetype graph with add/remove edges, and a query cache invalidated on every structural change. A student must be able to read the whole container. This reason is a tiebreaker, admissible only because points 1–3 already decided it — which is what §3.4 promised.

When this is the wrong answer — the one sentence

Choose the archetype when your world is large (past ~104 entities), its component sets are stable (structural changes are rare rather than per-frame), and your systems are narrow (little arithmetic per entity, so there is nothing for the redirect to hide behind) — a streaming open world, a crowd simulation, a particle or boid system with millions of near-identical agents. That is precisely the shape Unity DOTS is built for, and on that shape the 1.46×–1.94× becomes the dominant term while the 13.8× almost never fires.

And note what the escape hatch does to even that: if the engine ever reaches that shape, the fix is to group the two or three pools that matter, not to rewrite the storage.

Two consequences for what 5.8 builds, both of which follow from the measurements rather than from taste. Components must stay small and single-purpose, because the sparse set's whole model is that a system pays only for the pools it names — a fat component drags unread bytes through cache exactly as 5.6's 96-byte scene_object did. And the entity id must be one shared id space, which is the change §3.4 identified: pool<T>'s pattern is right, but the key must be minted by an entity allocator and handed to every pool, instead of each pool minting its own. 5.8 will lift 5.4's generational index out of pool<T> and make it the entity — which is the second time this course has been able to build a new system mostly out of a decision made two lessons earlier for a different reason.

9Common Pitfalls & Debugging

The row map written before the re-pack

Symptom: an archetype ECS that is correct for thousands of moves and then silently corrupts one entity. Cause: add_material originally recorded where the entity landed before calling pop_row on the source chunk. pop_row moves the source's last row into the hole and patches that entity's row index — and when the moved entity is the last row, that entity is the one being moved, so the stale index overwrites the fresh one.

Fix: re-pack first, then record. How it was found: a 1-in-N event needs N tries, so verify_57 §E churns 200 frames and then walks the entire row map. A single-frame test would have passed for weeks.

A benchmark whose arms visit entities in different orders

Symptom: bench_ab::agree is false and you reach for a tolerance. Cause: usually the arms sum the same numbers in a different sequence, which floating-point addition does not promise to give the same answer for — 5.6 hit exactly this. But: reaching for a tolerance disables the check that would catch an arm which is fast because it is doing less.

Fix here: make the orders the same by construction. All three arms walk the lead pool in entity-id order, so every ratio in this lesson is between arms that agree to the last bit. Prefer arranging for exactness over tolerating inexactness — and when you genuinely cannot, report the magnitude, as bench_ab::max_rel_diff does.

Comparing "sparse set" against "archetype" with one number

Symptom: your benchmark says 1.05× and someone else's says 2.4×, and you conclude one of you is wrong. Cause: you built the pools in the same order and they did not, or your body did real work and theirs did not. Those two axes span a range of 1.00× to 2.79× in this lesson's own data, for identical source code.

Fix: state the alignment and the per-entity work with every number you publish, and measure both ends of each. A comparison with one number for a two-parameter family is not a comparison.

Reading the small-n columns as results

Symptom: a table where cost is not monotonic in the amount of work — here, the archetype's cheap query costing 2.58 ns at K = 3 and 0.87 ns at K = 4, on four entities. Cause: at four entities the loop is four iterations and the auto-vectoriser's decisions dominate everything else.

Fix: rebuild with -fno-vectorize -fno-slp-vectorize. If the anomaly disappears — it does, 2.58 → 0.53 — it was codegen. Do not explain a compiler with a cache.

Leading a selective view with the largest pool

Symptom: a sparse-set query over {transform, rare_thing} that costs the same whether one entity in four matches or one in a thousand. Cause: the view is walking the transform pool and testing each entity for rare_thing, so it visits the whole world to find a handful.

Fix: walk the smallest pool. It is one comparison in the view's constructor and it is worth 1.73× → 1.46× at one-in-four; the further the selectivity goes, the more it is worth. 5.8's view must do this, and it is the reason a pool has to be able to report its own size cheaply.

Treating a sparse array as free because it is only indices

Symptom: memory use that grows when you add a component type nothing uses yet. Cause: a sparse array is sized by the entity id space, not by the number of components — so a type with three instances in a 100,000-entity world still costs 400 KB. Fix: keep the id space compact (5.4's free list already does), do not make short-lived swarms into entities, and if a real world needs 32+ types at 105 entities, page the sparse arrays the way EnTT does.

10Exercises

  1. 10.1 — Find the crossover on your machine. §6 argues from a rate comparison it never actually performs. Do it: using your own numbers, solve for the number of structural changes per frame at which the sparse set's total cost equals the archetype's, for a world of 10,000 entities running one K = 4 query per frame. Then do it again for a 12-component entity.

    Hint

    Query cost is N × (ratio − 1) × archetype-ns; structural cost is C × (archetype-ns − sparse-ns). Set them equal and solve for C.

    Solution sketch

    With this machine's numbers — 10,000 entities, real body, scrambled (1.17×, 1.91 ns archetype) — the sparse set gives up 10,000 × 0.17 × 1.91 ≈ 3,250 ns of query per frame, and wins 15.00 − 5.31 = 9.7 ns per structural change. It breaks even at ≈ 335 structural changes per frame, or 3.4% of the world. At twelve components it is 34.6 ns per change and break-even falls to ≈ 94. Two things are worth noticing: the number is small enough that a game with any real spawning reaches it, and it is a per-frame budget you can actually go and count in your own game.

  2. 10.2 — Page the sparse array. §3.3 argues this course does not need paging because 5.4's free list keeps ids compact. Test the cost of being wrong: change pool<T> in the probe to store sparse as a vector of 4,096-entry pages, and re-run the query benchmark.

    Hint

    sparse[e] becomes pages[e >> 12][e & 4095]. That is one more dependent load, so the chain in Figure 2 goes from depth 2 to depth 3.

    Solution sketch

    Expect near-zero cost on the aligned world and on the real body below the knee — the page pointer is one line that stays hot and the extra latency hides. Expect it to be visible on the scrambled cheap body at 100,000, where there was nothing to hide behind already. The interesting part is that it costs memory-bandwidth nothing: the page table is 4 bytes per 4,096 entities. Paging trades a small latency you can usually hide for a large footprint you cannot.

  3. 10.3 — Make the group pay for itself. §5.5 measures what a group is worth on a query but never measures what it costs to maintain. Add a fourth structural arm: a sparse set that keeps {transform, velocity} grouped, so every insert and erase of either component must swap the affected element across the group boundary. Measure it against the ungrouped sparse set.

    Hint

    Maintaining a group is: on insert, if the entity now has both, swap it to position group_size in both pools and increment. On erase, swap it out and decrement. Each swap is two element moves plus two sparse patches, per pool.

    Solution sketch

    You should find it costs on the order of a few nanoseconds per structural change on the grouped types only — a fraction of the archetype's, because it moves two components rather than all of them. That is the whole shape of the argument in §6 reduced to one measurement: a group buys the archetype's query at the archetype's price, but charges it only on the pools you chose, instead of on every component the entity happens to own.

  4. 10.4 — Type-erase the archetype's columns. §4.2 admits the probe's archetype is faster than a real one because its columns are statically typed. Quantify the concession: store each column as a std::vector<std::byte> plus an element size, look up the column index per archetype at query time, and re-run §5.1.

    Hint

    The inner loop's addressing becomes base + i * stride with a stride the compiler cannot see, which blocks some vectorisation. Take the scalar build too, so you can tell the codegen cost from the memory cost — the move this lesson made twice.

    Solution sketch

    Expect the loss to be modest and real, and concentrated on the cheap body where the loop was tight enough for vectorisation to matter. However large it turns out on your machine, subtract it from every archetype-favouring number in §5 — which is what "upper bound" in §4.2 means, and which strengthens §6 rather than weakening it.

  5. 10.5 — Argue the other side. Write the design document that chooses the archetype, using only the numbers in this lesson, and make it honest — no straw men, no numbers omitted. Then write down what it would take to change this course's mind.

    Hint

    The strongest archetype case is not the query ratio. It is the memory table plus a claim about what the engine will look like at Module 9.

    Solution sketch

    The best version runs: at 32 component types the sparse set pays 14.8 MB of index that the archetype does not, which is 3.7× this machine's L2 and is therefore not merely footprint but a permanent tax on every cache the engine uses; the query win is 1.46×–1.94× on exactly the selective queries a mature engine has most of; and the structural-change loss can be mitigated by deferring changes to a command buffer and applying them in bulk at a frame boundary, which is what Unity DOTS does and which the 13.83× column does not model. That last point is the real one, and the honest answer to "what would change our mind" is: a measurement of batched structural change. If moving a thousand entities between two archetypes at once costs much less than a thousand individual moves — and it should, since the destination appends become one memcpy — then the archetype's worst column is an artefact of measuring the operation one at a time. That experiment is not in this lesson, it is the strongest thing that could be, and it is exercise 10.5 rather than a table because it needs a batching API neither probe has.

11Recap & Next

The engine gained no code this lesson and gained the thing it most needed: a decided architecture with its evidence attached. When 5.8's container turns out to be awkward somewhere — and it will — the question "should this have been an archetype?" now has an answer with numbers behind it, and a stated condition under which the answer changes.

What was established:

  • Both designs satisfy every constraint 5.6 produced, so 5.6's numbers genuinely could not decide this, and a new measurement was necessary rather than rhetorical.
  • A design can be measured before it is built, when the difference between the candidates is an access pattern. Three hundred lines answered a question that would otherwise have cost two implementations and a sunk-cost argument.
  • The sparse set's redirect is latency, and latency hides. With codegen held still it costs nothing — 1.00× — until the working set leaves cache and the pools' orders have diverged. Both conditions are needed; either alone is free.
  • The archetype's structural change carries the entity's width in it and the sparse set's does not: 13.10 → 58.48 ns against 4.25 → 4.23 ns when the entity goes from four components to twelve.
  • A group is an archetype you can add later, measured at 0.99× of a real archetype on the archetype's own best case — which makes the migration one-directional and is the reason for the recommendation.
  • Fragmentation's iteration cost is 12% at worst, far less than the argument against archetypes implies, and this lesson says so even though it argues the other way.

Next: 5.8 — The ECS Runtime. It builds what this lesson chose. The entity becomes a generational id in one shared space — 5.4's handle, lifted out of pool<T> and given its own allocator — a component pool becomes a sparse set keyed by it, and a view becomes the thing that walks the smallest pool and looks the rest up, because §5.5 measured what leading with the wrong one costs. Then, and only then, the engine gets its first system, and the demo scene stops being four scene_objects in a std::vector.

  • The EnTT source, entt/entity/sparse_set.hpp and storage.hpp. Denser than the articles and worth the effort: the paged sparse array, the version bits inside the entity, and the group machinery are all there in a form you can now read.

  • Sander Mertens, the Flecs manual and his “Building an ECS” posts. An archetype implementation whose author writes candidly about the costs — particularly the archetype graph and what it does to structural changes.
  • Adam Martin, “Entity Systems are the future of MMOG development” (2007). The historical starting point. Worth reading for how much of the modern argument is already there, and how much of it was about editors and iteration speed rather than about caches.
  • Bjarne Stroustrup / Chandler Carruth on data structure choice. Whenever a "which container" argument stalls, the answer is usually the one this lesson took: measure the two operations that differ, and prefer the option that can become the other one.
