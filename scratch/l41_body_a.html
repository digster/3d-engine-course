Module 4 — To the GPU: SDL_GPU · Lesson 4.1

How GPUs Actually Work

A GPU is not a fast CPU. Per lane it is slower — and it finishes first anyway, for three reasons you can measure using the rasterizer you already own. By the end of this lesson your software rasterizer shades in 2×2 quads like the hardware does, wastes lanes like the hardware does, and can tell you exactly how many.

1The Problem

Lesson 3.10 finished Module 3 with a number: 45.47 nanoseconds per covered pixel. A 1280×720 frame of the capstone scene covers about 475,000 pixels, so that is 21.6 ms of fragment work — over the 16.7 ms budget, from one torus and a floor.

A GPU renders scenes with a thousand times that geometry, at four times that resolution, in a fraction of the time. The obvious explanation is that it is faster. It is not. Take any single lane of a GPU and compare it against one core of your CPU: the GPU lane runs at a lower clock, has a shorter pipeline, no branch predictor worth the name, and far less cache. Per lane, per instruction, it loses.

So the interesting question is not "how is it faster" but "what is it doing instead" — and the answer is three specific architectural choices, each of which has a cost as well as a benefit. This lesson is about those three, and about the fact that you can demonstrate all of them on the machine in front of you, in code you already wrote.

This lesson writes no SDL_GPU code, and that is deliberate

Lesson 4.2 introduces the device, the swapchain, command buffers and render passes; 4.3 does the shader toolchain; 4.4 draws the first triangle. Reaching for the API before the model is in place is how people end up with a working triangle and no idea why any of it is shaped the way it is. Today's job is the model — and by the end of it you will have measured most of it rather than been told it.

2Building Intuition

2.1Wide, not fast

Start with the choice that shapes everything else. Consider a chain of work in which each step needs the previous step's answer:

This runs at the latency of a square root and no faster, however many execution units your processor has, because none of them can start until the previous one has finished. Measured on the reference machine: 3.124 ns per step. The processor is mostly idle, waiting for its own results.

Now run several independent chains, interleaved. Nothing about the work changes — same instruction, same count, same data — but now there is always something else to issue while a result is in flight.

@@FIG_LATENCY@@

Eight chains run at 0.443 ns per step: a 7× speedup from adding no capability whatsoever, only independent work. That is the entire GPU architecture in one table. A GPU is a machine that has decided, at every level of its design, to be the one with something else to do:

  • a memory read that misses cache costs hundreds of cycles — and the GPU simply switches to another group of lanes and comes back;
  • it keeps thousands of lanes resident so there is always another group ready;
  • and it spends its transistor budget on more lanes rather than on the branch predictors and out-of-order machinery a CPU uses to make one lane fast.

This also explains a piece of shader advice that otherwise sounds superstitious: a shader that uses fewer registers runs faster. Registers are the resource that limits how many lane groups can be resident at once. Fewer registers per lane means more groups in flight, which means more independent work available, which means more latency hidden. The word for that ratio is occupancy, and it is the table in Figure 1.

2.2Lanes in lockstep

Having decided to be wide, a GPU makes a second choice: the lanes are not independent processors. They are grouped — 32 on NVIDIA hardware (a warp), 32 or 64 on AMD (a wavefront), typically 32 on Apple and Intel — and every lane in a group executes the same instruction at the same time, on its own data.

That is a huge saving: one instruction decoder, one program counter and one scheduler for 32 lanes instead of 32 of each. The transistors saved go into more lanes. The name for this model is SIMT — single instruction, multiple threads — and it is why a GPU can afford to be as wide as it is.

It also has a consequence that governs how shaders must be written, and §2.4 is that consequence. But first, a smaller group than 32, and one you cannot escape at all.

2.3The 2×2 quad

Every GPU ever built shades fragments in aligned 2×2 blocks of pixels. If a triangle covers one pixel of such a block, all four lanes run the fragment shader; the three that the triangle misses are called helper lanes, and their results are discarded.

That sounds like waste to be engineered away, and it is not, because of a feature you have used without noticing. A fragment shader can ask how fast is this value changing across the screen? — ddx and ddy in HLSL. And the only way to know how a value changes between neighbouring pixels is to have the neighbouring pixel's value. So the hardware computes it: ddx is lane 1 minus lane 0, ddy is lane 2 minus lane 0, and a subtraction is all a derivative ever costs.

@@FIG_QUAD@@
This is where mipmapping comes from

Lesson 3.9 ended with a gap it named honestly: bilinear filtering cannot fix minification, because a pixel covering 62 texels reads four of them. The fix is mipmaps — but choosing which mip level requires knowing how many texels one pixel covers, which is ddx(uv) and ddy(uv), which is a difference between neighbouring lanes. Every automatic mip selection on Earth is paid for by helper lanes. Module 6 spends them; today you find out what they cost.

2.4What a branch costs

Back to lockstep. Thirty-two lanes share one program counter, so what happens when a branch sends them different ways?

The hardware cannot run two instructions at once, and it cannot leave half the group behind. So it runs both sides, with the lanes that did not take a side switched off — masked — for its duration. A warp in which even one lane disagrees pays for every path any of its lanes takes.

@@FIG_DIVERGE@@

The measured curve underneath is the part worth dwelling on, because it says the cost is not a property of the branch at all. The same shader, the same branch, the same amount of work — and the cost steps from 1.00× to 1.93× depending only on how the two sides are arranged across the screen. And the step happens exactly where the run length crosses the warp width of 32, which is what tells you the model is right rather than merely plausible.

Hence a piece of real advice that sounds like nonsense until you have seen this: a branch is cheap if it is coherent and expensive if it is not. Branching on a material id is fine when whole objects share materials and ruinous when the id comes out of a texture. Branching on "is this pixel in shadow" is expensive precisely at shadow edges, which is where it looked worth doing.

3The Theory

3.1Lane efficiency, from area and perimeter

How much do helper lanes actually cost? The answer is derivable before it is measured, and the derivation is one sentence: covered lanes live in the triangle's area, and helper lanes live along its edge.

A quad is wasted in proportion to how much of the triangle's boundary passes through it, so the number of helper lanes grows with the perimeter while the number of covered lanes grows with the area. For a shape scaled by a factor k, area grows as k² and perimeter as k. So:

\[ \text{efficiency} \;=\; \frac{\text{covered}}{\text{covered} + \text{helpers}} \;\approx\; \frac{A}{A + cP} \]

efficiency ≈ area / (area + constant × perimeter) — so it falls as the triangle shrinks

For an equilateral triangle of circumradius r, area is (3√3/4)r² and perimeter is 3√3·r, and taking the constant as 1 lane per pixel of edge gives r/(r+4). Here is that prediction against 32 rotations of a real triangle through the real rasterizer:

Our rasterizer understates this, and it is worth knowing why

vertex::x and vertex::y are integers, so a triangle smaller than about a pixel rounds away to zero area and draws nothing at all. Real hardware rasterizes with sub-pixel precision — typically 1/256 of a pixel — so it happily draws triangles far smaller than one pixel, at an efficiency far below 25%. The right-hand end of Table 1 is therefore the optimistic case.

3.2Why 2×2 and not wider

If lanes are grouped for efficiency, why not group pixels in 4×4 blocks and save more scheduling? Because the argument from §3.1 runs the other way too: a wider block has more perimeter per unit area, so it wastes more.

@@FIG_EFFICIENCY@@

Figure 4 sweeps all four widths over the same triangles. At a circumradius of 8 pixels, 2×2 keeps 75.5% of its lanes and 16×16 keeps 8.9%. Every doubling costs more than the last, and the collapse is worst exactly where modern content lives — small triangles.

So the choice is forced from both ends. 2×2 is the smallest block that can produce a screen-space derivative at all — you need one neighbour in x and one in y, which is three lanes minimum, and a 2×2 square is the cheapest shape containing them. And every larger block wastes more. The hardware picks the smallest block that satisfies a requirement it cannot drop.

Wider SIMT groups still exist, of course — a warp is 32 lanes, not 4. But a warp is built from eight separate quads, which may come from eight different triangles. The grouping for scheduling and the grouping for derivatives are different things, and only the second one is 2×2.

3.4Why state is baked into an object

One structural thing remains, and it is the one that most surprises people coming from older APIs. In OpenGL you set render state with calls: glEnable(GL_DEPTH_TEST), glCullFace(GL_BACK), glBlendFunc(…). In SDL_GPU — and Vulkan, D3D12 and Metal — you cannot. You describe the entire state up front, build an immutable pipeline object from it, and bind that.

You have been doing this since Lesson 3.2 without the name.

@@FIG_STATE@@

fill_style has ten fields; SDL_GPUGraphicsPipelineCreateInfo has nine, which expand to 53 once its nested state structs are counted. They are the same object. That is not a coincidence — Lesson 3.2 adopted the shape deliberately, and 3.4 and 3.9 kept mirroring SDL's field names and enumerator orders — but seeing the two side by side is still the moment the port stops feeling like a leap.

Now, why does the hardware require this? The usual explanation is that it saves the inner loop from branching on state that never changes. That explanation is testable, and our fill loop is the test: it branches per pixel on style.shade, on a value that is constant for an entire draw. Hoisting that branch should be worth something.

Nothing. Slightly worse than nothing. A branch on a value that never changes is predicted perfectly and effectively free, so the folk explanation is wrong.

The real reason is that the driver has to do two expensive things with that state, and both of them are the kind of expensive that is measured in milliseconds. It must validate the combination — is this blend mode legal with this target format, does this vertex layout match what the shader declares — and it must compile a machine-code shader specialised to it, because a real GPU has no runtime "depth test on/off" switch; that decision is compiled in. Doing that once per pipeline is free. Doing it once per draw call would be ruinous.

SDL says so in its own header, in the list of things an application prepares up front:

Render pipelines (precalculated rendering state): use SDL_CreateGPUGraphicsPipeline()

— SDL3/SDL_gpu.h, under “things that are created once and used over and over”

And this is the sixth pressure, arriving on schedule

Lesson 3.10 noted that encode_mode is a per-fragment branch on a draw-constant value — “a compile-time shader variant in a runtime disguise”. Now you can see what it is a disguise for. Our fill_style has four shading modes, two encode modes, two interpolation modes, two blend spaces and now three traversals: 96 combinations, every one of which our fill loop decides at runtime, per pixel. A GPU compiles the one you asked for. That is what a shader is, and Lesson 4.3 is where you get one.
