5Randomness without a sequence

5.1 — Why a generator does not port

Every random-number generator you have used is a sequence: a state, and a function that advances it. std::mt19937 holds 2.5 KB of state; the tiny linear congruential generator Numerical Recipes printed holds 32 bits and advances with x = x · 1664525 + 1013904223. Either way the n-th number depends on the n − 1 before it, and a CPU particle system that calls next() in its spawn loop gets a different number for each particle because the calls happen one after another.

Sixty-five thousand threads do not happen one after another. If they share one generator, every next() is a read-modify-write of the same state — §2's broken counting loop, with randomness as the thing being lost. If each thread keeps its own generator, each generator needs a seed, and the seed must differ per thread; and a seed that is just the thread's index is where the trouble starts.

The way out is to stop thinking of a random number as the next value of a sequence and start thinking of it as a hash of a name. A particle has a name — its serial number, which birth it was — and a function that scrambles 32 bits into 32 bits so thoroughly that neighbouring inputs give unrelated outputs turns that name into as many random numbers as the particle needs. No state is shared, nothing depends on the order the threads run in, and — the property the rest of this lesson leans on — the same name gives the same numbers on any processor that performs the same integer arithmetic, which all of them do exactly.

5.2 — Three generators that are not random

The question is which scrambling function. §C of the harness measures four candidates by the thing a spark actually uses: pairs. A spark's direction is two draws, so the test is whether the pair of numbers particle i draws, (u2i, u2i+1), fills the unit square, and whether particle i's first number tells you anything about particle i + 1's. Figure 4 plots 2,048 pairs from each of three.

One LCG step, seeded by the index. The natural first attempt: seed a tiny generator with the particle's index, take one step, use the result. But an LCG is linear — seed i + 1's output is seed i's plus the constant 1,664,525 — so consecutive particles get numbers that differ by the same amount every time. Measured over 65,536 particles: the correlation between neighbours is +0.9977, and the pairs reach 128 of 4,096 cells of a 64 × 64 grid: every pair lies on one diagonal line, because each number is the one before it plus 1,664,525/232. A fountain built on it would emit its sparks in a slowly rotating pattern that looks like a bug in the emitter, not in the random numbers.

The shader folklore hash, fract(sin(x) × 43758.5453), found in thousands of shaders. It fills the square — all 4,096 cells, correlation +0.0014 for small inputs — and it has two defects that no scatter plot at this scale shows. The first is that it has almost no bits. The product sin(x) × 43758.5453 is up to 43,758 in magnitude, and a float keeps 24 significant bits: between 32,768 and 65,536 the gap between representable floats is 215 − 23 = 1/256, so fract() of anything in that range is a multiple of 1/256. Most products land above 2,048, where the gap is at least 1/4,096 — so the function can only return about four thousand distinct values. Measured: 4,178 distinct outputs from 65,536 inputs, about twelve bits of randomness where the output format holds twenty-four. The second defect appears for large inputs: above 224, float(i) cannot represent odd integers, so particle i and particle i + 1 are the same input half the time, and the neighbour correlation jumps to +0.4963. A serial number passes 224 after fourteen minutes of a 20,000-a-second fountain.

And a third defect, which only a two-processor harness can see: it is not one function. sin on a GPU is a fast approximation, not the correctly-rounded library call of the CPU, and multiplying by 43,758 magnifies the last-bit differences into the visible digits. The probe kernel evaluates the same expression for the first 220 integers: 480,168 of 1,048,576 outputs differ from C++'s, and 1,246 by more than 0.01. A particle system built on it has no CPU reference at all.

PCG's hash. Jarzynski and Olano's "Hash Functions for GPU Rendering" (JCGT 2020) measured many candidates for exactly this use and recommended one built from Melissa O'Neill's PCG generator: one LCG step to advance a state, followed by PCG's output permutation, which uses the state's own top bits to choose a shift and so destroys the linearity that ruined the first candidate. The engine's version is four lines of integer arithmetic, identical in C++ and HLSL: 

[[nodiscard]] constexpr Uint32 pcg_hash(Uint32 input)
{
    const Uint32 state = input * 747796405u + 2891336453u;
    const Uint32 word = ((state >> ((state >> 28u) + 4u)) ^ state) * 277803737u;
    return (word >> 22u) ^ word;
}

Measured: neighbour correlation −0.0019, every one of the 4,096 cells reached, a χ² of 4,198 against 4,095 degrees of freedom, and 65,411 distinct values among 65,536 — which is itself a check, because a perfectly random 24-bit output should collide about 65,536² / (2 · 224) = 128 times, leaving 65,408. And the property the whole lesson rests on: run it on the GPU for 1,048,576 consecutive inputs and every output is identical to C++'s, bit for bit. Integer multiplication, shifts and exclusive-or have exactly one correct answer, and both processors produce it.

5.3 — From bits to a float, exactly

A hash gives 32 random bits; a spark wants a number in [0, 1). The obvious conversion, float(h) / 4294967295.0f, has two roundings in it — 32 bits into a float's 24, then a division a GPU compiler is permitted to approximate — and either can make the two processors disagree. The engine takes the top 24 bits instead: 

[[nodiscard]] constexpr float unit_float(Uint32 bits)
{
    return static_cast<float>(bits >> 8u) * (1.0f / 16777216.0f);
}

An integer below 224 is represented by a float exactly, and 1/16,777,216 is 2−24, a power of two, so the multiplication only changes the exponent. There is no rounding anywhere, and the harness confirms it: the same million floats, bit for bit, on both processors (§C). The result is a multiple of 2−24 in [0, 1 − 2−24], which is every value a float can hold at that spacing.

5.4 — A particle's stream

A spark needs four numbers at birth: two for its direction, one for its speed, one for its life span. It gets them by hashing its name once and then hashing the hash: 

particle_rng rng(serial, seed);     // state = pcg_hash(serial ^ seed)
const float u_cos   = rng.next();   // state = pcg_hash(state); return unit_float(state)
const float u_phi   = rng.next();
const float u_speed = rng.next();
const float u_life  = rng.next();

The emitter's seed selects which fountain — two emitters with different seeds produce unrelated sparks from the same serial numbers — and the order of the four draws is part of the specification: the kernel draws them in the same sequence, so the third number means "speed" on both processors. Reorder the lines in one file and the harness reports every particle wrong while every individual function is still correct.

5.5 — A direction uniform over a cone

The fountain emits into a cone around its axis, half-angle θmax = 0.35 radians (20°). "A random direction in the cone" sounds like "a random angle between 0 and θmax and a random turn around the axis", and that is wrong, for a reason you can see before you compute anything. Look down the cone's axis at the patch of the unit sphere it cuts out — a cap — and draw rings at equal steps of angle. The rings near the rim are long and the ones near the axis are short, because a ring at angle θ has circumference 2π sin θ. Choose the angle uniformly and you put as many directions in the tiny innermost ring as in the long outer one: the density per unit area climbs toward the axis. Figure 5, left, shows it: a bright core where a real fountain has none.

What we want is equal density per unit area of the cap. The area of a strip of the unit sphere between θ and θ + dθ, all the way around, is its circumference times its width, 2π sin θ dθ. Integrate from the axis to θ and the area of the cap is

\[ A(\theta) = \int_0^{\theta} 2\pi \sin\theta'\,d\theta' = 2\pi\,(1 - \cos\theta) \] A(theta) = 2 pi (1 - cos theta)

so the fraction of the whole cap that lies within angle θ is (1 − cos θ) / (1 − cos θmax). For the directions to be uniform by area, that fraction must equal a uniform random number u, which gives the recipe directly:

\[ 1 - \cos\theta = u\,(1 - \cos\theta_{\max}), \qquad \phi = 2\pi v \] 1 - cos(theta) = u * (1 - cos(theta_max)) ; phi = 2 pi v

— uniform in cos θ, not in θ. A worked number, with the demo's cone: the cap has height 1 − cos 0.35 = 0.0606. The median sample, u = 0.5, has 1 − cos θ = 0.0303, so cos θ = 0.9697 and θ = 0.2469 rad (14.1°). Uniform in angle would have put the median at 0.175 rad: half of all sparks within 10° of the axis instead of within 14°, which is the bright core of Figure 5.

Write h = 1 − cos θ — which the sampling formula hands you directly, without ever forming cos θ — and

\[ \sin\theta = \sqrt{1 - (1-h)^2} = \sqrt{h\,(2 - h)} \] sin(theta) = sqrt(h * (2 - h))

has no subtraction near 1 anywhere. For the median sample: √(0.0303 × 1.9697) = 0.2443. The direction is then assembled in a frame around the axis: tangent · sin θ cos φ + bitangent · sin θ sin φ + axis · cos θ. The tangent and bitangent come from Duff and colleagues' branch-free construction (JCGT 2017), because the textbook one — cross the axis with "up" — divides by zero when the axis is up, which for a fountain is the only axis anybody uses. And they are computed once, on the CPU, into the uniform block, because they are the same for every particle; that rule — a number that is the same for every thread is computed once, never sixty-five thousand times — shapes the block in §7.

6Emission: a clock and a ring

6.1 — The fraction

An emitter emits at a rate, 20,000 particles a second, and the simulation runs in fixed steps of 1/60 s, so each step should emit 333.33 particles. Truncate that to 333 and the fountain loses a third of a particle every step — twenty a second, 1,200 a minute, a rate that is silently 0.1% low forever. The fix is a clock that accumulates the rate and pays out whole births, carrying the fraction: 

carry_ += rate * h;                  // 0.33 + 333.33 = 333.67
const double whole = floor(carry_);  // 333 births this step
carry_ -= whole;                     // 0.67 carried to the next

and the step pattern becomes 333, 333, 334, repeating. Measured over one simulated minute: exactly 1,200,000 births — 333 on 2,400 steps and 334 on 1,200 — against 1,198,800 for truncation (§D).

The clock keeps its fraction in a double, and it is worth being exact about why, because the first version of particles.hpp gave a reason the harness then refused. It said a float accumulator would lose its fractional digits after 224 births. It would not: the clock subtracts the whole part every step, so it never holds more than 334.34, and over a simulated hour a float carry and a double carry differ by one birth. What actually limits the clock is the step itself: 1/60 is not a float, the nearest one is 0.0166666675, and at that step both carries emit 72,000,002 or 72,000,003 particles an hour where the arithmetic says 72,000,000. The double costs eight bytes per emitter and removes the question, and the header now says so.

6.2 — A pool is a ring

Where do the new particles go? The CPU answer — append to a vector, erase the dead — is exactly what a GPU is bad at: appending needs a shared counter and erasing reshuffles everything. The answer this engine uses needs neither. The pool has a fixed capacity, a power of two, and particle number s — its serial, counting births from zero — lives in slot

\[ \text{slot}(s) = s \mathbin{\&} (\text{capacity} - 1) \] slot(s) = s AND (capacity - 1) — which is s mod capacity, for a power of two

so births walk round the pool like a clock hand, and each new particle replaces whatever was capacity births ago — the oldest particle in the pool, which with a long enough pool is long dead. A step's births are serials first to first + count − 1, a contiguous arc of the ring. Figure 6 draws a pool of sixteen where serials 13 to 17 are born: slots 13, 14, 15, 0 and 1.

The kernel runs one thread per slot, not per birth, and each thread asks: does this step's arc include my slot? Its distance forward from the arc's first slot is (slot − first) & mask — unsigned subtraction wraps, which is exactly "forward round the ring" — and the slot is born this step if that distance is below count. If it is, the thread spawns serial first + d; if not, it steps whatever lives there. No thread communicates with any other. That is the whole of why a ring suits a GPU, and why this lesson's emitter needs no atomics at all.

6.3 — Why a power of two, and what "long enough" means

Serials are 32-bit and they wrap: at 20,000 a second, 232 births take 59.7 hours. With a mask the wrap is invisible — 4,294,967,295 lives in slot 1,023 of a 1,024-slot pool and 0 lives in slot 0, consecutive as they should be — because 1,024 divides 232. With a pool of 1,000 and s % 1000 the same two serials land in slots 295 and 0, and the ring's one invariant — the next birth replaces the oldest particle — breaks, once every two and a half days. §D prints both sequences across the wrap; Figure 6's table is that output.

"Long enough" is a single inequality. A slot comes round every capacity / rate seconds, and a particle that lives longer than that is replaced while still alive. The fountain's longest life is 3 s, and 65,536 / 20,000 = 3.28 s, so nothing is cut short: §D runs 200,000 births and counts zero live particles overwritten. Halve the pool and a slot comes round every 1.64 s: 152,704 of 200,000 particles — 76.4% — are replaced before their time, losing 0.685 s of life on average. It looks like a fountain whose sparks vanish in mid-air at a height that has nothing to do with gravity.

Note

The ring's price is that a particle's death is decided twice: by its own clock, and by the ring coming round. The alternative, used by many production systems since Gareth Thomas's GDC 2014 talk on compute-based particles, is a dead list: a stack of free slot indices that births pop from and deaths push to, which recycles exactly the dead and nothing else. It needs two atomics per particle per frame and it makes the order of births depend on the order of deaths, which varies run to run — so it has no bit-exact CPU twin. The ring is deterministic, atomic-free and exactly reproducible, which is what a lesson that compares two processors needs. Exercise 5 builds the dead list and measures the difference.

6.4 — Births belong somewhere in the step

A step of 1/60 s emits 333 particles, and it is tempting to give them all age zero at the emitter. Physically they were born at different instants during that sixtieth of a second — the first early, the last just now — and by the end of the step the early ones should already be a little way out. Put them all at the emitter and every step's births travel together as a shell, and shells from successive steps sit one step's travel apart: at 7 m/s, 11.7 cm. The fountain comes out in layers, as if pumped rather than poured.

Where exactly does birth k belong? The clock held the fraction c when the step began and rises at rate per second, so during the step it reads c + rate · t. Each birth happens as it crosses a whole number: birth 0 when it reaches 1, birth k when it reaches k + 1. Solving,

\[ t_k = \frac{k + 1 - c}{\text{rate}}, \qquad \text{age}_k = h - t_k = h - (k + 1 - c)\cdot\frac{1}{\text{rate}} \] t_k = (k + 1 - c) / rate ; age_k = h - (k + 1 - c) * inv_rate

Worked, for a step that begins with c = 1/3 at 20,000 a second: birth 0 happens (1 − 0.3333)/20,000 = 33.3 µs into the step and is 16.63 ms old at its end; birth 332 happens at (333 − 0.3333)/20,000 = 16.63 ms and is 33.3 µs old. The clock reaches 333.67 by the step's end, so there is no birth 333 until next step — the same 333 the clock paid out. The kernel spawns each particle and then advances it by its own age in a single step of that length, so it is where it would be had it really been born then. inv_rate is in the uniform block rather than a division in the kernel, so both processors multiply by the same float.

That is the theory, and the measurement then refused half of what this section first predicted about it. §E runs the fountain twice — births spread through the step, and all at the step's end — and measures how lumpy the heights of young particles are (the average change between neighbouring 5 mm height bins, over the average count). With the demo's own emitter, speeds from 4 to 7 m/s, the two came out 0.232 and 0.221: no shells to speak of either way. The reason is in the speeds. A step's births leave at speeds 3 m/s apart, so after t seconds they are spread over 3t metres — wider than the shell spacing by the second step. The spread of speeds erases the shells by itself. Narrow the speeds to 6.9–7.0 m/s, as an emitter of identical droplets or tracer rounds would, and the prediction holds: 0.912 against 0.213. Figure 7 is that case.

7The step: semi-implicit Euler, implicit drag, and a floor

7.1 — Velocity first

Lesson 1.3 met this integrator in a sidebar: swap the two lines of the obvious update — change the velocity first, then move with the new velocity — and you get semi-implicit Euler, which conserves energy far better in anything that oscillates, and which 1.3 promised proper treatment in Module 8. Lesson 8.1 will give it that treatment; here it is simply the right default, and the particle step is two lines of it: 

p.velocity = (p.velocity + u.gravity * dt) * inv_drag;   // velocity first...
p.position = p.position + p.velocity * dt;               // ...then move with the new one

7.2 — Drag, implicitly

Sparks slow down in air, and the simplest model is linear drag: an acceleration opposing the velocity in proportion to it, dv/dt = g − kv. The explicit step evaluates the drag at the old velocity:

\[ \mathbf{v}' = \mathbf{v} + (\mathbf{g} - k\mathbf{v})\,h = (1 - kh)\,\mathbf{v} + \mathbf{g}h \] v' = v + (g - k v) h = (1 - k h) v + g h

and that factor (1 − kh) is where it can go wrong. If kh exceeds 1 the factor is negative, so the velocity flips sign every step; if kh exceeds 2 its magnitude exceeds 1, and the flipping grows. Evaluate the drag at the new velocity instead — the implicit choice — and solve:

\[ \mathbf{v}' = \mathbf{v} + (\mathbf{g} - k\mathbf{v}')\,h \;\Longrightarrow\; \mathbf{v}'\,(1 + kh) = \mathbf{v} + \mathbf{g}h \;\Longrightarrow\; \mathbf{v}' = \frac{\mathbf{v} + \mathbf{g}h}{1 + kh} \] v' = (v + g h) / (1 + k h)

The factor 1/(1 + kh) is between 0 and 1 for every positive k and h: the velocity decays, whatever the step. §F makes the difference concrete with a thick medium, k = 150/s, at the engine's step (kh = 2.5), starting from 1 m/s: after ten explicit steps the speed is 57.67 m/s (1.510, alternating in sign); after ten implicit steps it is 3.63 × 10−6 m/s (3.5−10). At the demo's k = 0.4/s the two agree to 4.4 × 10−5 of the velocity per step, so the implicit form costs nothing where the explicit one works and saves you where it does not. The factor for a full step, 1/(1 + kh), is the same for every particle, so it too is computed once on the CPU and sent in the uniform block as inv_drag_h; only a birth's pre-age step, whose length varies, computes its own.

7.3 — The floor

A particle that ends a step below the plane y = ground while moving down bounces: 

if (p.position.y < u.ground && p.velocity.y < 0.0f)
{
    p.position.y = u.ground;                          // back onto the surface
    p.velocity.y = -p.velocity.y * u.restitution;     // the normal speed, reversed and reduced
    p.velocity.x = p.velocity.x * u.keep;             // the tangential speed, reduced by friction
    p.velocity.z = p.velocity.z * u.keep;
}

Each clause has a reason. Only while moving down: a particle that bounced last step may still be below the plane this step on its way back up, and bouncing it again would send it back down through the floor. Back onto the surface: a step that overshoots by 3 cm leaves the particle 3 cm under the floor for a frame, and the depth test then hides it — a flicker at every impact. Normal and tangential separately: restitution is how much of the speed into the surface survives, friction how much of the speed along it does, and they are different physical things (Lesson 8.9 builds both properly for rigid bodies).

How much height should a bounce keep? Kinetic energy is ½mv², the height a particle rises to is v²/2g, and the bounce multiplies v by the restitution e — so it multiplies the height by e². At e = 0.45 each bounce should keep 0.2025 of the last one's height. §F drops a particle from 1 m and measures peaks of 0.1848, 0.0318 and 0.0033 m: ratios of 0.185, 0.172 and 0.103. The prediction held for the first bounce and failed, worse and worse, for the later ones — and the failure has a formula.

A semi-implicit step launched upward at speed v0 reaches, after n steps, a height of Σj=1..n (v0 − jgh)h, whose maximum is

\[ y_{\max} \approx \frac{v_0^2}{2g} - \frac{v_0 h}{2} \] y_max ~ v0^2 / (2 g) - v0 h / 2

— the true height less half a step's travel. As a fraction of the true height the shortfall is gh/v0, which grows as the bounce shrinks. For the first bounce v0 ≈ 0.45 × √(2 · 9.81) = 1.99 m/s, so the shortfall is 9.81 × (1/60) / 1.99 = 8.2%, and 0.2025 × (1 − 0.082) = 0.186 — within 0.001 of the measured 0.1848. The third bounce is 3 mm high and lasts three steps; a step that size cannot resolve it at all. The control that proves the diagnosis is the same drop at a quarter of the step: peaks of 0.1970, 0.0386 and 0.0070, ratios 0.197, 0.196 and 0.181, all moving toward e² (Figure 8). It is the step's error, not a bug — and it is the same first-order error Lesson 1.3 measured for a fall, which is one reason Module 8 spends a lesson on integrators.

7.4 — Why state, and not a formula

It is worth asking whether a particle needs a simulation at all, because for a long time GPU particle systems did without one. With gravity and no floor, a particle's position is a closed form, p(t) = p0 + v0t + ½gt², and a vertex shader can evaluate it from the particle's birth time, direction and speed — all of which are hashes of its serial number. No buffer, no step, no compute. §F confirms it would even be more accurate than the step: after one second the stepped height is 0.0817 m off the formula, which is semi-implicit Euler's first-order error ght/2 = 0.0818 m.

The floor ends that. When a particle bounces depends on where it was, which depends on when it last bounced, and each bounce changes the velocity that decides the next one. That is a history — piecewise, and still solvable for one plane, but the moment the floor is uneven, or the particles collide with the depth buffer (Exercise 4), or a wind field varies over space and time, there is no formula left to evaluate. State is what you keep when the future depends on the past in a way you cannot write down, and a compute shader is how you step state on the GPU.

7.5 — Between two steps

The draw interpolates each particle between previous — its position at the start of the last step — and its current position, with Lesson 1.4's alpha. One detail makes that correct for a ring. When a slot is respawned, previous is set to the emitter, not left holding the old tenant's position. Leave it, and for one frame the new spark is drawn somewhere on the line from where the dead one was to the emitter — a streak across the screen, once per birth, sixty times a second, and indistinguishable from a rendering bug. The rule is the one 1.4 gave for any interpolated state: previous must always be a position of this object.

8Drawing without vertices

8.1 — A billboard from two IDs

A spark is drawn as a small square that always faces the camera — a billboard — shaded into a soft disc. Every vertex the engine has drawn so far came from a vertex buffer, described field by field to the pipeline in 4.5. A billboard's four corners are not data anybody stored; they are a function of the particle and the camera. So the particle pipeline has no vertex buffer at all, and its vertex shader has no inputs. It is invoked six times per instance — two triangles — and it finds everything from its two system values:

  • SV_InstanceID says which particle. It indexes the list of living slots (§9), which gives the slot, which indexes the pool.
  • SV_VertexID says which corner: an index into a six-entry table of (±1, ±1), in counter-clockwise order as seen by the camera — the course's front face (conventions §7), so the default back-face cull keeps them.

The corner is then placed in the camera's own plane: 

const float3 centre = lerp(p.previous, p.position, alpha);
const float3 world  = centre + (right * c.x + up * c.y) * radius;

where right and up are the camera's axes in world space. They are free: Lesson 2.9 built look_at so that the view matrix's rotation rows are the camera's axes, and a rotation's inverse is its transpose, so row 0 is the world direction the view maps to +x and row 1 the one it maps to +y. Worked, with the demo's shot camera at (3.7633, 2.3, 6.1382) looking at (0, 1.3, 0): camera_right returns (0.8525, 0, −0.5227), camera_up returns (−0.0719, 0.9905, −0.1173), and the view matrix maps them to exactly (1, 0, 0) and (0, 1, 0) — computed by the engine's own look_at. A spark at (0.10, 1.00, 0.20) with radius 0.03 puts corner v2, (1, 1), at (0.1234, 1.0297, 0.1808). Figure 9 draws the chain and the quad.

Everything the spark looks like comes from two numbers the pool already holds: its age as a fraction of its life, and its serial. 8.2 — Storage buffers in the vertex stage

The vertex shader reads two storage buffers — the pool at t0 and the list at t1, both in space 0, the vertex stage's texture-and-storage space from §4's table — bound with SDL_BindGPUVertexStorageBuffers. The graphics stages can only read storage, so both are declared StructuredBuffer, not RWStructuredBuffer, and both buffers need the GRAPHICS_STORAGE_READ usage bit in addition to their compute bits. Miss that bit and the bind fails validation; miss a compute bit and the kernel's does. gpu_particles::create argues every bit in a comment, because the usage flags are where most of the ways to get this wrong live.

8.3 — Added to the light, tested against the scene

Sparks emit light, and light adds, so the pipeline blends with 6.13's blend_add(): destination += source. That has a consequence that §9 depends on — addition commutes, so the particles can be drawn in any order at all, up to a rounding §9 measures — and it decides where the draw goes: into the HDR target, before the tonemap, because a spark is a quantity of light like any other surface (6.12) and because a spark bright enough should bloom (6.13). The overlay of 6.18 went after the tonemap for the opposite reason; the line between scene-referred and display-referred is the one 6.18 drew, and sparks are on the scene side.

The draw is tested against the scene's depth and does not write it. The test hides sparks behind geometry; the write would make each spark hide the ones behind it — and since the list's order changes every frame (§9), which sparks were hidden would change every frame too. That is Lesson 6.11's rule for blended geometry, arrived at from a different direction. §K checks the test with a depth attachment cleared to the device depth of a plane: in front of every spark (2.89 m from the camera, the nearest spark being 3.09 m out) it leaves zero lit pixels; through the fountain's axis at 6 m, with 21,611 of 43,248 sparks behind it, it leaves 45.9% of the light — and 9,401 of the 10,329 lit pixels, because nearly every pixel the far half covered, the near half covers too.
