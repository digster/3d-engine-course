4Implementation

4.1The harness

engine/core/bench.hpp is §3.1's four rules, mechanised. It is header-only and it is deliberately small: the point is not that timing is hard to write, it is that writing it three times produces three subtly different things.

Per item, not per run, because the comparisons in this lesson are between layouts at different N and a total is not comparable across them. And three numbers rather than one, because rule 2.

The comparison function is the reason the file exists:

One rep of A, one rep of B, microseconds apart. Both arms see the same thermal state, the same scheduler, the same neighbours on the machine.

And rule 4, which is carried out in two parts:

Exact equality is the right default and it is too strict for one real case: an arm that visits the same elements in a different order sums the same numbers in a different order, and floating-point addition is not associative. Two of our arms are exactly that, so agree correctly reports false for them and the caller needs the magnitude to decide whether that is rounding or a bug. Anything above about 10−9 is not rounding.

C++ in place — volatile, and what it does and does not do

inline volatile double g_bench_sink; plus bench_keep(v) { g_bench_sink = v; } is the whole of rule 3.

volatile is widely misunderstood as being about threads. It is not — for threads you want std::atomic, and volatile gives you no ordering and no atomicity. What it does mean is that accesses are observable behaviour of the abstract machine: the compiler must emit every read and every write, in program order relative to other volatile accesses, and may not invent or elide them. That is exactly the property a benchmark needs — the store must happen, therefore the value must be computed, therefore the loop that computed it must run.

inline on a namespace-scope variable is C++17's answer to "one definition across every translation unit that includes this header", and it is what lets a header-only sink exist at all.

The layouts live in scratch/scene_layouts.hpp rather than inside the benchmark, and the reason is the one this course keeps arriving at: they have two consumers. bench_56.cpp times them; verify_56.cpp checks they all describe the same scene. A benchmark whose subject is transcribed into its own test has tested the transcription.

Two of the fairness decisions are worth reading, because a benchmark's conclusions are mostly decided by them.

The virtual arm gets a polymorphic twin. With one concrete type the indirect branch is perfectly predicted and the comparison flatters virtual; with two interleaved types it is not. Measuring only the kind version would have been arguing against a straw man in the engine's favour, so both are timed — and §5.3 is what that produced.

The tree gets a second child order. A tree built and immediately walked has its nodes in allocation order, and the addresses still march forward even though pointers are leading the way. 4.3The check that makes the numbers mean anything

verify_56 has six sections; §E is the one Lesson 5.6 stands on. It builds all seven layouts over the same 2,000-object scene and asserts they compute the same answer — bit-identical where the visit order is the same, within 10−9 where it is not.

It found two problems. Neither was a bug in the engine; both were the benchmark measuring something other than what it claimed.

Finding 1 — the fragmentation nobody can promise

The pointer layout allocates spacer blocks between its objects, so that "pointer chasing" does not quietly measure a contiguous walk with an extra load. §D checked whether it worked, by counting how many consecutive objects were exactly sizeof(scene_object) apart. The answer was 497 of 499.

The first diagnosis was a size-class mismatch — 24-byte spacers between 96-byte objects go in different allocator runs — and matching the sizes did move ptr_ordered at 100,000 objects from 1.09× to 1.98×. But chasing it further produced something more useful, and it is the reason this callout exists. The same layout code gives different answers in different processes:

Adjacency is a property of the process, not of the layout. macOS's allocator hands same-size blocks out of a run and interleaves them, or does not, depending on that size class's state — which depends on everything the process allocated earlier. No amount of care in the layout code decides it, and no separate harness can assert another program's heap state.

So the resolution is not a fix, it is a protocol: bench_56 reports its own layout at every n (0 adjacent throughout, which is why §5.1's table is sound), measure_56.py flags any build whose objects came out contiguous, and verify_56 asserts only what the code controls — that three spacers per object were allocated — and prints the adjacency rather than judging it. A number whose provenance you cannot state is a number you should not publish.

Finding 2 — an assertion that was asserting an accident

§E originally asserted that at least one reordering arm was not bit-identical to the baseline, to prove the tolerance was earning its keep. It failed: at n = 2,000 with this data, all three reorderings happened to land on the same bits.

Whether a reordering differs is a property of the numbers, not of the layout, so asserting it is asserting an accident. The check was replaced with a four-line demonstration of the underlying fact — (a+b)-a against (a-a)+b at 1016 — which is true regardless of the data and is what the tolerance actually exists for.

There is a third, quieter correction that changed a headline. The accumulator originally read five of a matrix's sixteen entries, which sounds harmless. parent_from_local is inlined into the flat, pointer, SoA and tree loops, so a compiler that sees only five entries used is free to stop computing the other eleven — and it cannot see through the virtual call. The virtual arm was building whole matrices while its rivals built a third of one, and the resulting "cost of virtual" was partly the cost of doing more work. Reading all sixteen took it from 3.4× down to 1.7×.

Both rows of that table compare two std::vectors, so §4.3's allocator problem cannot reach them: flat is one allocation and soa is three, in both builds. That is what makes the scalar column quotable even though the same build's pointer rows are not.

The cull win survives, and it appears exactly where the working set leaves cache: 0.97–0.98× up to a thousand objects, then 0.37× and 0.36×. That is the cache effect, in isolation, and with vectorisation switched back on the two effects compound to 0.19×.

The rule this produces, which is not "use SoA"

Split the data a loop does not read away from the data it does, and the size of the prize is the fraction you leave behind.

Reading 60 of 96 bytes, splitting buys nothing from the memory system — you were fetching almost all of it anyway. Reading 12 of 96, splitting buys 5×. That is why an ECS is not "SoA for everything" but "a system declares which components it touches", and it is the number Lesson 5.7 has to design against.

5.3What virtual costs, and what it does not

@@FIG_VIRTUAL@@

A virtual call costs 1.5–1.7× on this workload, and it costs it everywhere. Two things about that number are more interesting than the number.

Monomorphic and polymorphic are the same. One implementation, perfectly predictable, versus two interleaved by a hash: within 4% at every scene size. I expected the polymorphic case to be substantially worse and it is not. Whatever virtual is costing here, it is not branch misprediction — the CPU predicts an unpredictable indirect call about as well as a trivial one, which is a sentence I would not have written before running this.

And it is flat across N. 1.55× at four objects, in L1, where there is no memory effect to have — so it is not the vtable load either. What is left is inlining: the compiler cannot see through the call, so parent_from_local's nine multiplies and sixteen stores cannot be fused, reordered or vectorised across iterations. The cost of virtual in a hot loop is mostly the optimisations it prevents, not the instructions it adds.

That reframes the usual advice. "Virtual calls are slow because of the indirect branch" is the folk explanation and this data does not support it. "Virtual calls in a hot loop cost you inlining, and inlining is where the optimiser lives" does support it — and it predicts the right thing, which is that the cost scales with how much the body would have gained from being inlined.

5.4The tree, judged fairly

The lesson is called "why scene trees creak", and the honest answer is: usually they do not.

A freshly built tree — nodes in allocation order — costs 1.04–1.28× up to ten thousand objects. The addresses still march forward, the prefetcher does not care that pointers are leading the way, and a scene graph is a perfectly reasonable thing to walk. Anyone who has told you a tree is inherently slow has not measured a fresh one.

Shuffle the same nodes — same allocations, same footprint, same addresses in existence, only the order of the links changed — and it goes to 4.86× at ten thousand and 6.47× at a hundred thousand. That is §3.3's serial dependency chain: each node's address is inside the previous node, so the misses cannot overlap.

The honest statement of the case against scene trees

A scene tree is not slow because it is a tree, and it is not slow because it is object-oriented. It is slow when its nodes are in an order the prefetcher cannot follow, which is the state every long-lived scene ends up in — objects created and destroyed, allocator holes reused, children re-parented, draw lists re-sorted.

The compounding argument is that a tree gives you no way to fix that. You cannot compact it, because the nodes' addresses are the identity. Lesson 5.4's handles exist precisely so an array can be compacted underneath you — and that is the connection between these two lessons that the ECS is built on.

5.5What this justifies, and what it does not

A measurement lesson has to be willing to conclude "no". Here is what the data supports.

It does not justify changing the renderer. The scene is four objects. Every layout is within noise of every other at that size, the whole scene is 384 bytes, and the entire per-object transform work for a frame is about six nanoseconds. Rewriting collect_triangles around a different layout would be pure churn, and the golden image staying byte-identical this lesson is not an achievement — it is the consequence of correctly deciding to change nothing.

It does justify three things about the ECS, and each has a number attached:

  • Storage must be dense and contiguous, and it must be compactable. Not because contiguous is virtuous — ptr_ordered is 1.00× up to ten thousand objects — but because a long-lived scene decays into disorder, and the difference between an array you can compact and a tree you cannot is 6.47× at the scale the decay happens. Lesson 5.4 already paid for this with swap-and-patch removal; 5.6 is the justification arriving after the spend, which is the honest order to admit.
  • A system must declare which components it touches. The full-transform workload reads 60 of 96 bytes and splitting buys nothing; the cull workload reads 12 and splitting buys 5×. An ECS that hands every system the whole entity has given away the only mechanism that produced a large number in this lesson.
  • Iteration must not be virtual. A flat 1.5–1.7×, at every scene size, for a call the compiler cannot inline. This is the one cost that is not a function of N, so it is the one that applies to our four-object scene too.

And one thing it explicitly does not settle: archetype versus sparse-set storage. Nothing here distinguishes them — both are dense, both are contiguous, both allow a system to touch a subset. That question is about how components are grouped, and it needs a different experiment. It is Lesson 5.7's, and it should be argued there rather than smuggled in here on the strength of numbers that do not address it.

7Build & Run

Release, and it matters more than usual. Every number in §5 is from -O2 -DNDEBUG. A debug build measures the optimiser's absence, which is a different and much less interesting experiment — the ratios flatten because everything is slow.

It compiles bench_56.cpp twice — once normally, once with -fno-vectorize -fno-slp-vectorize — and prints both tables. The second build is not a curiosity: it is the experiment that separates §5.2's two effects, and without it the SoA result means the opposite of what everybody assumes it means.

Expected: 36 checks, 0 failures, and a golden that is still byte-identical.

What to look for on your own machine. The absolute nanoseconds will differ; four things should not:

  • A flat left-hand side. If layouts differ at 100 objects on your machine, something is wrong with the measurement — check the spread first.
  • A knee, somewhere. Its position tells you your L2 size divided by 96 bytes. On a machine with a 512 KB L2 it should appear earlier than it does here.
  • The SoA full-transform win vanishing under -fno-vectorize. If it survives, your compiler is doing something different and that is worth investigating — start with -Rpass=loop-vectorize.
  • tree_shuffled being the worst line on the chart, by a wide margin, at large N.

8Common Pitfalls & Debugging

1 · A suspiciously round number, especially zero

Symptom. An arm reports 0.0000 ns, or every result is a multiple of the same value.

Cause. The timer is coarser than the work. On this machine one tick of SDL_GetPerformanceCounter is 41.67 ns.

Fix. Repeat the pass inside the timed region until a sample is worth ~100 µs, and divide back out. Print SDL_GetPerformanceFrequency() once so you know what your quantum is.

2 · A number that is not physically possible

Symptom. 0.166 ns per item for four matrix builds — 2.3 cycles for nine multiplies and sixteen stores.

Cause. The compiler computed the loop once. Repeating a pure function of nothing is an invitation.

Fix. Make each pass genuinely different work — a per-pass value used in the arithmetic, not just added at the end. And do the arithmetic on every result you publish: nanoseconds convert to cycles, cycles to instructions, and instructions are countable. This is the only pitfall in the list that no tool will find for you.

3 · Two arms that should differ, agreeing exactly

Symptom. A memory-bound comparison comes out 1.00× at every size.

Cause. Something else is the bottleneck — usually the accumulator. A serial chain of double additions is ~4 cycles each and will happily dominate a loop body of three multiplies.

Fix. Accumulate into something cheap (an int), or into several independent accumulators summed at the end. Then re-run and check the difference appeared.

4 · The fragmentation you carefully arranged did not happen

Symptom. A "scattered heap" benchmark performs exactly like a contiguous array.

Cause. Allocators bin by size class. Spacers of a different size than your objects go in a different run and separate nothing.

Fix. Match the spacer size to the object size — which moved a headline by nearly 2× — and then stop trusting it, because you cannot control this from your code. The same source gives different adjacency in different processes (§4.3). Have the benchmark report its own layout at every size, and treat any number from a build whose objects came out contiguous as measuring indirection rather than scattering.

5 · One arm's baseline moves between pairings

Symptom. The same flat arm reads 0.98 ns/item in one comparison and 1.83 in another.

Cause. At large N the two arms evict each other. Alternation protects against thermal drift and introduces cache interference.

Fix. Pair every arm against its own freshly measured baseline and quote the ratio within a pairing, never an absolute from one pairing against an absolute from another. Both arms in a pairing paid the same interference.

6 · You attributed the win to the wrong mechanism

Symptom. None — this is the one that ships. The number is real, the conclusion is wrong, and it predicts badly ever after.

Cause. A plausible story adopted instead of an experiment. "SoA is faster because of cache lines" fitted our 0.66× perfectly and was completely wrong.

Fix. Find the knob that turns off your hypothesised mechanism and see whether the effect goes with it. -fno-vectorize; a scene small enough to fit in L1; a monomorphic version of a polymorphic call. An effect that survives the removal of its explanation had a different explanation.

9Exercises

  1. 9.1 — Find your knee. Run the benchmark and locate the scene size at which ptr_shuffled first exceeds 1.2×. Divide by 96 bytes, and compare against your machine's actual L2 size (sysctl -a | grep cachesize on macOS, lscpu on Linux). Then add scene sizes either side to bracket it more tightly.

    Hint

    The sizes are one line in bench_56.cpp's main. Powers of two between 1,000 and 10,000 will bracket it in three runs.

    Solution sketch

    You should land within a factor of two of L2 ÷ 96, and the discrepancy is itself informative: the pointer arm's working set is the objects plus the pointer array plus the spacers, so it leaves cache sooner than the flat arm does. Whether you can see the L3 as a second, gentler knee depends on your machine.

  2. 9.2 — Shrink the object. scene_object is 96 bytes and the transform loop reads 60. Make a 64-byte variant (drop name, tint, closed and surface — the transform loop reads none of them), add it as an arm, and predict the result before you run it.

    Hint

    96 → 64 bytes is 1.5 → 1.0 cache lines per object. Where on the curve would you expect that to show, and where would you expect it not to?

    Solution sketch

    Little to nothing below the knee, and a real win above it — the effect is a fraction of the memory traffic, so it can only appear where memory traffic is the cost. The general lesson is the one §5.2 states: the prize is the fraction you leave behind, and it is collected only when you are paying for bandwidth. This is also the honest argument for why an ECS component should be small: not tidiness, bandwidth, above a scene size you should be able to name.

  3. 9.3 — Make the tree fast. Keep the tree structure — parents, children, siblings — but allocate every node from one contiguous array and link them in index order. Measure. Then shuffle the links without moving the nodes, and measure again.

    Hint

    This is tree_fresh versus tree_shuffled with the allocator removed from the experiment.

    Solution sketch

    Contiguous-and-ordered is close to the flat array; contiguous-and-shuffled is still bad, though less bad than heap-shuffled because the working set is smaller. The conclusion is the useful one: a hierarchy is not the problem — a traversal order the prefetcher cannot follow is. Which is why real engines keep the hierarchy and store it as a flat array sorted parent-before-child, and it is exactly what Lesson 5.9 will build.

  4. 9.4 — Devirtualise it. Replace the virtual call with a switch on a small type tag, keeping the two node types. Measure against both the virtual version and the flat array.

    Hint

    §5.3 argues the cost is inlining rather than prediction. A switch whose arms are inlinable is the experiment that tests that claim.

    Solution sketch

    If §5.3 is right, the switch should recover most of the 1.5× because the bodies can be inlined — even though there is still a data-dependent branch per object. If it does not, §5.3 is wrong on your machine and you have found something worth writing down. Either way you have tested a claim rather than believed one, which is the entire point of this lesson.

  5. 9.5 — Break the harness on purpose. In bench.hpp, change bench_keep to do nothing. Re-run the benchmark. Then put it back and remove the per-pass bias from one arm instead.

    Hint

    Both changes remove a defence. Predict which numbers become impossible.

    Solution sketch

    Without bench_keep some arms collapse toward zero and the ratios become meaningless — but not uniformly, which is the dangerous part: a partially-deleted benchmark still produces a plausible-looking table. Removing the bias from one arm makes that arm hoistable and it wins enormously, and agree goes false, which is rule 4 doing its job. Keep the second result: it is the clearest demonstration in the course of why a benchmark needs a correctness check.

10Recap & Next

The engine gained one header — bench.hpp, which is §3.1's four rules mechanised — and this course gained something it needed more: numbers instead of a story for the argument the next two lessons are built on.

What the numbers say, briefly. Below a thousand objects, layout does not matter — every arrangement is within 13% except the virtual call, and our scene is four objects. The knee is where the working set leaves L2, which makes it a property of your cache and not of your taste. An array of pointers costs 2.4× and a linked list costs 6.5×, and the gap between those two is memory-level parallelism: the array's addresses are known in advance so its misses overlap, and the list's are not so they cannot. A scene tree is not slow because it is a tree; a freshly built one is 1.04×. It is slow when its order decays, and it gives you no way to fix that.

And the three that surprised me, all of which survived a correction to the experiment: SoA's win on a full-struct workload is vectorisation, not cache — it vanishes entirely with the vectoriser off, at every size. A polymorphic virtual call costs the same as a monomorphic one, so the cost is not branch prediction; being flat across N, it is not the vtable load either; what is left is the inlining it prevents. And the heap fragmentation the benchmark carefully arranged is not something the benchmark can control: the same layout code produced 0 adjacent objects in one process and 99,411 of 99,999 in another. The fix is not a fix, it is a protocol — the benchmark reports its own allocation layout at every size, and any build whose objects came out contiguous is measuring indirection rather than scattering.

Two methodological points are worth more than any single number, so they get the last word. An effect that survives the removal of its explanation had a different explanation — three of this lesson's tables exist only because that test was applied. And a number whose provenance you cannot state is a number you should not publish, which is why the benchmark now prints where its own objects landed before it prints a single timing.

Next: 5.7 — An ECS from Scratch: Storage Design. 5.6 established what storage has to do: be dense, be compactable, and let a system declare which components it touches. It deliberately did not settle how components are grouped, because nothing measured here distinguishes archetypes from sparse sets — both satisfy all three. That is 5.7's question, it is a genuine design argument with real trade-offs on both sides, and it deserves to be made on its own evidence rather than inheriting this lesson's.
