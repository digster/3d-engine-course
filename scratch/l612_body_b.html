3The theory

3.1   Exposure, in units somebody can talk about

An exposure is a multiplier applied before the curve. You could expose a scene by typing multipliers — 0.5, 0.001, 3 — and a great many engines have. The reason not to is that nobody can reason about them, and there is a scale that a century of photography has already agreed on.

EV is a logarithmic scale of light, and one EV — one stop — is a factor of two.

@@FIG_EXPOSURE@@

The conversion from an exposure value to a render-time multiplier is standardised rather than derived, and it is worth being precise about which part is which:

\[ L_{\max} = 1.2 \cdot 2^{\text{EV}_{100}} \qquad \text{exposure} = \frac{1}{L_{\max}} \]
max_luminance = 1.2 × 2^EV100 exposure = 1 / max_luminance

The 2EV is the definition of a stop and is not negotiable. The 1.2 is not physics: it is 78 / (q × 100) with q = 0.65 from ISO 12232's saturation-based speed definition — a calibration of real camera hardware. This course takes it as given and says so; Lagarde and de Rousiers' Moving Frostbite to PBR §5.1 works it through properly. Quoting a constant and saying that you are quoting it is a different act from presenting it as a derivation.

Worked example, and it is the one that matters. What EV is the engine already using?

k_reference_irradiance = π was chosen so a white surface renders at exactly 1.0. "1.0 maps to white" is precisely "L_max = 1", so:

1 = 1.2 × 2^EV → EV = log2(1 / 1.2) = −0.2630

The harness confirms that exposure_from_ev100(k_reference_ev100) returns 1.0000000. And that is the sentence worth taking away:

Lesson 6.2's choice was an exposure setting. It was simply the only one available.

Which turns this lesson from a replacement into a generalisation — the old behaviour is a point on the new scale, not a special case beside it. Three real settings for calibration: a dim room is EV 3 (white at 9.6), an overcast day is EV 12 (white at 4,915), full daylight is EV 15 (white at 39,322).

3.2   What makes a curve legal

Now the second half. We need a function from [0, ∞) to [0, 1], and before choosing one it is worth writing down what a candidate has to satisfy — because these three properties are what separate an operator from a preference, and every one of them has a visible failure.

  • Monotonic. Brighter in, brighter out. Fail this and a highlight can come out darker than its own edge, which no amount of artistic intent will make read as an image of anything.
  • Close to the identity near zero. Fail this and the dark end of every image is wrong — and the dark end is where an sRGB encode spends most of its codes, so the error lands exactly where it is most visible.
  • Bounded by 1. Fail this and it has not done its job; something downstream will clamp, and you will have a curve and a clamp.

Everything after this is taste. Here are four.

@@FIG_CURVES@@

Reinhard, derived in one line

We want to divide x by something that is about 1 for small x (so the dark end is untouched) and about x for large x (so the bright end flattens). The simplest function that is both is 1 + x:

\[ f(x) = \frac{x}{1 + x} \]
f(x) = x / (1 + x)

That is the whole derivation. Check the three properties: the derivative is 1/(1+x)², positive everywhere, so monotonic; f'(0) = 1, so it is the identity to first order at the origin; and f(x) < 1 for every finite x, so it is bounded.

That last property is also its famous defect

f(x) < 1 strictly. So pure white is unreachable — and it is worth computing how unreachable, because the number is much smaller than people expect and the arithmetic is a trap this whole module keeps setting.

Code 255 needs an encoded value of at least 254.5/255 = 0.998039. Inverting the sRGB transform, that is a linear 0.995545. So:

x / (1 + x) = 0.995545 → x = 223.5

An input of 224. So an image tonemapped this way has no pure white in it at any brightness you would plausibly render, and looks washed out for exactly that reason.

This paragraph first said 768, from applying the 254.5/255 threshold in the wrong space — the same confusion between a code and a quantity of light that Lessons 1.6, 2.4, 3.9, 6.10 and 6.11 each found in a different place, committed here by the person writing the module about it. verify_612 §C measures it rather than repeating it, which is how it was caught.

The white point, also derived

So give the artist the dial the plain operator lacks: pick the value W you want to render as pure white, and require f(W) = 1 while keeping the shape. The answer is:

\[ f(x) = \frac{x\left(1 + \dfrac{x}{W^2}\right)}{1 + x} \]
f(x) = x(1 + x/W²) / (1 + x)

And the check is two lines of algebra rather than an assertion:

f(W) = W(1 + W/W²)/(1+W) = W(1 + 1/W)/(1+W) = (W+1)/(1+W) = 1

The harness drives it at W = 2, 4 and 11 and gets exactly 1.000000 each time. Note also that as W → ∞ the extra factor vanishes and it becomes plain Reinhard, which is the right behaviour for a generalisation to have.

ACES, which is a fit and not a model

The curve the industry actually ships is an approximation to the ACES reference rendering transform — five constants published by Krzysztof Narkowicz in 2015: 

return clamp((x * (2.51f * x + 0.03f)) / (x * (2.43f * x + 0.59f) + 0.14f), 0.0f, 1.0f);

There is no derivation to give, and pretending otherwise would be exactly the hand-waving this course refuses. What it has that the Reinhard family does not is a toe and a shoulder: it darkens the very bottom and rolls off the very top, which mimics film and reads as "photographic" rather than "mathematically correct".

The toe has a price, and the harness prints it: a dark value of 0.02 — code 39 — comes out at code 26. Thirteen codes darker, in the region where the eye is most sensitive. That is a real artistic choice being made on your behalf, and it is worth knowing that you are accepting it rather than discovering it later as "the shadows look crushed".

3.3   Per-channel, or on the luminance?

A curve takes one number. A colour is three. There are two defensible ways to reconcile that and they give visibly different pictures — this is a real choice, like blend_space in 2.4, not a tuning knob.

@@FIG_HUE@@

Worked example. A bright saturated orange — the colour a fire actually is — at (8.0, 2.0, 0.4), through Reinhard both ways.

per channel: (0.8889, 0.6667, 0.2857) red:blue = 3.11
luminance: (1.9230, 0.4808, 0.0962) red:blue = 20.00

The input's red:blue ratio is 20. Per-channel drops it to 3.11, because a saturating curve compresses the big channel more than the small one — so the colour moves toward white as it brightens. That is what film does, it is what people expect a highlight to look like, and it is why it is the default.

Luminance-only holds it at exactly 20, because scaling a colour by a scalar is a move along the ray from black through it, which preserves hue and saturation by construction.

And luminance-only does not solve the problem it appears to solve

Look at its output again: r = 1.9230. The curve was applied to the luminance and the luminance landed in range, but an individual channel did not — and the encode will clamp it, shifting the hue anyway, at a threshold nobody chose.

Blue is the worst case, because its luminance weight is only 0.0722. A pure blue of (0, 0, 8) has a luminance of 0.5776 — comfortably mid-range — sails through the curve, and arrives with b = 5.0710 for to_encoded to clip.

So: per-channel desaturates predictably and stays in range by construction; luminance-only preserves hue right up to the point where it does not. Neither is correct, both are defensible, and the engine exposes the choice with the first as the default. Real pipelines add a third answer — tonemap the luminance and then apply a controlled desaturation — which is a knob this course names and does not build.

3.4   The resolve, and why its three steps cannot be reordered

@@FIG_RESOLVE@@

Each wrong ordering has its own signature, and the harness measures both.

Worked example 1: exposure after the curve.

Take (6.0, 3.0, 1.5) at exposure 0.25 through Reinhard. Done correctly — multiply, then curve — the red channel lands at code 203. Done backwards, code 128.

And the second number is not merely darker. Everything above about 4 had already been squeezed into the same place by the curve before the multiply arrived, so the exposure no longer has a range to select from — which is the whole reason it exists. An exposure applied after a compression is a brightness slider wearing an exposure's name.

Worked example 2: the curve after the encode.

Mid grey, 0.5 of the light. Curved as light: 0.5/(1.5) = 0.3333. Encode it first — code 188, which is 0.7373 as a fraction — and curve that: 0.7373/1.7373 = 0.4244.

A curve applied to codes compresses exactly what the encode had carefully spread out, and because the sRGB curve is steepest at the dark end, it crushes the shadows first. This is Lesson 1.6's rule arriving for the sixth time in this module and the last time in this course: arithmetic on light happens in linear space; the encode is the last step and happens once.

Done in the right order, the payoff is the thing the whole lesson is for. Seven stops of input, through a resolve, into eight bits, with nothing clipped: 

 0.125->94   0.250->124   0.500->156   1.000->188   2.000->213   4.000->231   8.000->242   16.000->248

3.5   What an HDR target does to Lesson 6.11's rule

Lesson 6.11 spent a section establishing that compositing must decode both operands, blend in linear light, and re-encode — and priced the round trip at 3.14× a naive byte lerp. That machinery was correct. It is also, on a float target, entirely absent.

The destination is already linear light; so is the source; so over applies directly. The harness measures one composite at 9.25 ns on a float target against 75.12 ns on 8 bits — 8.1× cheaper, and exactly correct rather than correct-after-conversion.

An HDR buffer is not only about range. It is the buffer that holds the quantity the arithmetic is defined on — and every conversion 6.11 had to perform was a symptom of storing something else.

There is a second, sharper consequence. Compositing a value of 40 at quarter coverage over a dim background gives 10.19, and the float buffer keeps it. The 8-bit path cannot reach that answer at all: 40 was already code 255 before the blend, so it would have composited 1.0 and lost a factor of forty before the operator even ran. Some pictures are not merely less accurate in 8 bits; they are unreachable.

And 6.11's _SRGB-versus-UNORM argument does not transfer

6.11 established that hardware blending on a UNORM target with a shader that encodes its own output lerps sRGB codes, at a cost of 42.2% of the light. It is worth saying plainly that this does not carry over to a float target: there is no transfer function in the ROP to be right or wrong about, because nothing in a float pipeline stores codes.

Which also settles what happens to encode_output. That flag has always meant "must this shader apply the transfer function?", and with the scene rendering to a float target the answer there is permanently no. The question has not gone away — it has moved to the pass that actually writes the display, which is the only place it was ever answerable. Same number, third reason.

3.6   Measuring a frame: why metering is done in log space

One more piece of arithmetic, because it is the foundation of auto-exposure and because the reason is not obvious. To choose an exposure automatically you need a number that says how bright the frame is. The obvious candidate — the mean luminance — is useless.

Worked example. A 100×100 frame at a uniform 0.05, with one specular pixel at 5000.

arithmetic mean = (9999 × 0.05 + 5000) / 10000 = 0.5500

That single pixel — one ten-thousandth of the frame — contributes 0.5 of the 0.55, which is ten times everything else put together. An auto-exposure driven by this number stops down by three stops because one highlight came into view.

The geometric mean — the exponential of the mean of the logs — gives:

log-average = 0.05016

It barely notices, because the log of a large number is a small number. The two disagree by 11× on the same image, and that gap is the difference between an exposure that tracks the scene and one that flickers whenever something shiny turns toward the camera.

measure() returns both, for exactly this reason — a number you can compare against a wrong one is worth more than a number on its own. It also counts pixels over the lid, which is the diagnostic that tells you whether you have an HDR problem at all: run the demo's polished scene and it reports 126 of 129,600 pixels — 0.10%. A tenth of one percent of the frame, and all of the information being destroyed is in it.

4Implementation

4.1   Two passes, and why the tonemap is not in the scene shader

The tempting shortcut is to tonemap at the end of scene.frag.hlsl, where the colour already is. It costs nothing extra. It is also wrong in three ways, each of which becomes a real limitation within two lessons.

@@FIG_PASSES@@
  • An exposure derived from the frame cannot be known while the frame is being drawn. Auto-exposure reads the finished image's log-average, and that does not exist until the last triangle has landed.
  • Bloom comes before the curve (Lesson 6.13) and operates on the whole image. A per-fragment tonemap has already compressed the values bloom needs to find.
  • Blending would composite tonemapped values. over is linear in light and a curve is not linear, so f(a) over f(b) is not f(a over b). Lesson 6.11's operator would quietly stop meaning what it means.

So: the scene renders into a float target, and a second pass maps it down. That second pass is the first thing in this engine whose cost scales with pixels rather than with geometry, and it is the seed of 6.13's stack.

4.2   A full-screen triangle, from nothing

A post pass has no geometry, so binding a quad mesh would be inventing a vertex buffer for a vertex shader to ignore. Instead the corners come from SV_VertexID: 

Output main(uint vertex_id : SV_VertexID)
{
    Output o;
    o.uv = float2((vertex_id << 1) & 2, vertex_id & 2);
    o.position = float4(o.uv.x * 2.0f - 1.0f, 1.0f - o.uv.y * 2.0f, 0.0f, 1.0f);
    return o;
}

That expression gives uv (0,0), (2,0), (0,2) for ids 0, 1, 2. Mapping uv to clip space with the standard flip — x = uv.x·2 − 1, y = 1 − uv.y·2, which is conventions §6, since NDC's +y is up and a texture's v runs down — puts the corners at (−1,1), (3,1) and (−1,−3). The screen is the square from (−1,−1) to (1,1), strictly inside that triangle; everything outside is clipped by hardware at no cost.

One triangle and not two, and Lesson 4.1 is why

The obvious shape for "cover the screen" is two triangles meeting along the diagonal. It works, and it is measurably worse, for a reason this course already built the vocabulary for: fragments are shaded in aligned 2×2 quads (4.1), so along the shared diagonal every quad straddles both triangles and is issued twice, with half of each being helper lanes.

One oversized triangle has no internal edge, so nothing is shaded twice. It is a small saving and an excellent illustration of why 4.1's quad traversal was worth building: the reason to prefer one shape over another here is invisible unless you know how a rasterizer issues work.

The draw call is the whole of the geometry submission:

SDL_DrawGPUPrimitives(pass, 3, 1, 0, 0);   // three vertices, one instance, nothing bound

4.3   The pipeline, and everything it does not have

gpu_tonemap_pass::create is short, and the absences are the interesting part — each one is a sentence about what a post pass is:

  • No vertex input. gpu_mesh::describe is never called, so num_vertex_buffers and num_vertex_attributes stay zero.
  • No depth. A triangle covering the screen has nothing to be occluded by, so the pass is begun with a null depth target.
  • No blending. The resolve replaces the swapchain's contents.
  • No culling. A full-screen triangle's winding is an accident of how SV_VertexID was turned into positions, not a fact about a surface.

4.4   The target, and the flag that is easy to forget

ti.usage = SDL_GPU_TEXTUREUSAGE_COLOR_TARGET
         | (sampled ? SDL_GPU_TEXTUREUSAGE_SAMPLER : 0u);

Both usages. A scene buffer is written by one pass and read by the next, and omitting SAMPLER produces a texture that renders perfectly and reads as undefined — with no error on a release device, since Lesson 6.10 established that SDL's GPU validation lives inside if (device->debug_mode). This is the same pair create_depth(..., sampled) documents for a shadow map, arriving on the colour side.

The format is R16G16B16A16_FLOAT, and the choice is worth three sentences:

  • It holds the range. A half float reaches 65,504, and this engine's own measured peak is 55,917 — inside it, but only just, which is a useful thing to know about your content rather than a comfort.
  • Its precision is relative. Ten mantissa bits, so about three decimal digits — at every magnitude. The dark end, where the eye is most sensitive and where an sRGB encode spends most of its codes, gets the same relative accuracy as the bright end. This is the answer to "why not 16-bit fixed point": fixed point spreads its steps evenly over a range that is not perceived evenly.
  • It costs 2×, not 3×. Eight bytes a pixel against four. The CPU's hdr_buffer stores three floats and pays 3× — 6.22 MB against 2.07 MB at 960×540 — and that difference is entirely the half float.

4.5   The software path: one hoist and one branch

The CPU rasterizer needs the shading equation's answer un-encoded. The whole change is a code motion: everything in fragment's lit branch moves into its own lambda, and the encode stays behind at the boundary. 

const auto shade_lit = [&](float f0, float f1, float f2, float w_recip,
                           float& out_alpha) -> linear_rgb { /* …the hundred lines… */ };

// …and the 8-bit path becomes one line:
else if (lit)
{
    return to_encoded(shade_lit(f0, f1, f2, w_recip, out_alpha), style.encode);
}

Note what is not in shade_lit: to_encoded. That function is the one thing in this engine that routinely exceeds 1.0, and until this lesson its answer was clamped one line later, every time, with no way to ask for the real number.

The HDR fragment is then four lines, and deliberately not a second implementation: 

const auto fragment_linear = [&](float f0, float f1, float f2, float& out_alpha) -> linear_rgb {
    if (lit)
    {
        const float w_recip = 1.0f / (f0 * iw0 + f1 * iw1 + f2 * iw2);
        out_alpha = style.opacity;
        return shade_lit(f0, f1, f2, w_recip, out_alpha);
    }
    return to_linear(fragment(f0, f1, f2, out_alpha));
};

That decode in the last line is exact enough, and it is worth saying why rather than hoping: the other shading modes cannot exceed 1.0 by construction — a uv checker is two constants, a texture sample is a reflectance, an interpolated vertex colour is a weighted average of values in [0,1]. So the round trip loses at most the encode's own rounding, on values that had nowhere else to go, and it buys one implementation of four shading modes instead of two. lit is the only mode with a range to preserve, and it is the one that skips the trip.
