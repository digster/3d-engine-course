3. Finding one: the table of contents that was not one

Before writing a line of the game, I did what a newcomer does: I opened engine/include/engine/engine.hpp, because its first line says “the whole public API, in one include” and its comment goes on to say something stronger and more useful:

It is also a TABLE OF CONTENTS: this file is the shortest complete statement of what the engine offers, and the fastest way to see whether something is public is to look for it here.

That is a testable claim, so let us test it. Count the .hpp files under engine/include/engine/ — other than engine.hpp itself, which is the set it could possibly list — then count the #include lines in engine.hpp, and compare.

@@FIG_UMBRELLA@@

Forty of fifty-five. One of the fifteen absences is correct and documented — platform/main.hpp defines a program's entry point, and an umbrella whose selling point is “include everything, it is harmless” must not be a way to acquire a main by accident. The other fourteen are not absences with reasons. They are the entire ECS, the entire asset system, handles, pools, the logger, the assertion macros, the benchmark harness and the action map: very nearly everything Module 5 built.

The file's own history is the whole explanation, and you can read it with one command:

Three commits. Lesson 5.1 created it. Lesson 5.2 added platform/ and app/. Lesson 5.11 added debug_lines and debug_ui. Lessons 5.3, 5.4, 5.5, 5.6, 5.8, 5.9 and 5.10 shipped fourteen public headers between them and touched this file zero times.

Notice that this is not carelessness in the ordinary sense — 5.2 and 5.11 did remember. It is a rule kept by memory, and a rule kept by memory is kept about half the time. Which is precisely the thing Lesson 5.1 said out loud when it moved the boundary into the include path: enforced by the include path, not by the style guide. We applied that reasoning to one rule and not to the one three lines below it.

3.1 Why it rotted: the file has no consumer

Here is the mechanism, and it is worth more than the bug. Search the repository for anything that includes <engine/engine.hpp>:

Nothing. Not one demo, not one engine source. Every program in this repository includes what it uses, because that is what the umbrella's own comment advises for anything built more than a few hundred times. So the file is never compiled, and a header that is never compiled cannot be kept correct by being used. It can only be kept correct by being checked.

That gives the fix a shape. Adding the fourteen missing lines takes a minute and buys nothing durable, because the next lesson to add a header will forget for the same reason the last seven did. What is worth building is the check, and it belongs where a new header is noticed — at configure time, in engine/CMakeLists.txt:

A glob used as a lint, not as a source list

Every CMake guide tells you not to file(GLOB), and every one of them is talking about globbing sources: adding a new .cpp does not re-trigger CMake, so the build silently omits it and you get a link error you cannot explain. That objection does not transfer here. A stale glob in a lint can only fail to notice a header added since the last configure — it can never drop a translation unit, never change a flag, and never break a build. Weigh that against what it replaces: a silent wrong answer that stood for thirteen lessons. CONFIGURE_DEPENDS asks the generator to re-glob on each build, which most generators honour and none are required to; it is belt and braces, not the argument.

The comparison itself has one trap in it, and the first draft fell in. Grepping the whole file for the header's name passes on headers that are only mentioned in a comment — and the single documented exception, platform/main.hpp, is named in prose precisely to say that it is absent. A check that reads its own excuse as compliance is worse than no check, so the match is anchored to a whole #include line.

3.2 The measurement, which comes out the other way round

Completing the umbrella makes it bigger, and bigger means slower. So before doing it, the obvious prediction: the umbrella is the expensive way to include the engine, the explicit list is the cheap way, and completing the umbrella widens the gap. Lesson 5.1 measured header costs on this project rather than asserting them; let us do the same here. One translation unit, compiled with c++ -std=c++20 -c, best of five.

@@FIG_COMPILE@@

The prediction is wrong, and it is wrong in an informative direction. The umbrella as shipped (0.28 s) was cheaper than including exactly what the game uses (0.37 s) — because the fourteen headers it was missing are the templated ones. registry.hpp, view.hpp, pool.hpp, asset_store.hpp and actions.hpp are where this engine's compile time actually lives, and an umbrella that omits them is not cheap, it is incomplete, and the two look identical on a stopwatch.

Worked: what completing it costs

umbrella, as shipped (40 headers)   0.28 s
umbrella, completed (55 headers)    0.39 s

change        (0.39 − 0.28) / 0.28 = +39.3%
against explicit  (0.39 − 0.37) / 0.37 =  +5.4%

baseline (an empty file)      0.01 s

So the corrected umbrella costs 39% more than the broken one and 5.4% more than including what you use. The honest headline is that the one-translation-unit cost of an umbrella is not the reason to avoid it. The reason is the one Lesson 5.1 measured and this lesson does not re-measure: with explicit includes, editing gpu_scene.hpp recompiles the files that use the GPU scene; with an umbrella it recompiles everything. That is a property of the dependency graph, and it does not show up in a single-file benchmark at all.

Both facts go in the header's comment, because a reader who finds only the first number will conclude the umbrella is fine and a reader who finds only the second will conclude it is a disaster.

4. Finding two: a promise Module 5 made and did not keep

Now the eleventh row of §2's table. The game has entities; the renderer draws scene_objects; what connects them?

Nothing public. collect_triangles takes std::span<const scene_object>, and a scene_object is a struct with a transform in it — not an entity, not a component, not a registry. So the game must walk the registry itself and build the span. That loop already exists, once, in ecs_swarm, and it is twenty lines. Writing it a second time is the obvious move and the wrong one, because of what those twenty lines contain.

Open gfx/scene.hpp and read its opening paragraph, which has been there since Lesson 5.1:

It is deliberately NOT the final answer. Module 5's ECS replaces the struct with components, and Module 6 pulls the surface fields out into a material. Both of those are named in the comments below where the seams already show.

Module 5 is this module. It built the ECS in 5.8 and the hierarchy in 5.9, and it never took the second step — so the seam the comment points at is still open, and the twenty lines in ecs_swarm are what fills it by hand. This lesson is Module 5's last, so it is the last chance for that sentence to be true.

4.1 Hoisting at two callers, against our own rule

There is a complication, and it deserves to be argued rather than waved past. This engine's own stated rule — written twice, in scene.hpp — is that a type invented before three callers have asked for one is a guess. We have two: ecs_swarm, and the game about to be written. Hoisting now breaks our rule.

The reason to do it anyway is not “two is close to three”. It is that what is duplicated is not an idiom, it is a known-broken workaround. Here are the four lines at the heart of ecs_swarm's render_system:

The hierarchy produced a mat4; scene_object wants a transform; and a transform has no field for “a general linear map”. So the whole 3 × 3 linear part is dropped into the field called rotation and the scale is set to 1. It works — exactly, as §4.2 proves — and it works only because that field happens to be a bare mat3 with no orthonormality requirement. ecs_swarm's own comment says so, and predicts the end of it:

It abuses the fact that the field is named rotation and typed mat3, which is precisely why it is a bridge and not a design. Module 6 gives the renderer a matrix directly and this function loses its last four lines.

A stable idiom repeated twice is a coincidence. A workaround repeated twice is two places to fix on the day somebody finally changes scene_object — and one of those two places is inside a demo, which nobody thinks of as engine code and nobody greps when they change an engine type. That is the argument, and it is narrow: we are hoisting a conversion, not inventing a type. renderable is not speculative either — it is scene_object with the placement removed, and scene_object has existed since Lesson 3.1.

4.2 The conversion is exact, and that has to be checked

“It works exactly” is the sort of claim that is either true to the bit or quietly false by a thousandth. Let us derive why it is the former, and then measure it.

parent_from_local builds a mat4 from a transform by scaling each basis column and putting the position in the fourth:

\[ M \;=\; \begin{bmatrix} s_x\,\mathbf{r}_0 & s_y\,\mathbf{r}_1 & s_z\,\mathbf{r}_2 & \mathbf{p} \\ 0 & 0 & 0 & 1 \end{bmatrix} \;=\; \begin{bmatrix} R\,S & \mathbf{p} \\ \mathbf{0}^{\!\top} & 1 \end{bmatrix} \] M = [ R*S | p ; 0 0 0 1 ], where S = diag(sx, sy, sz)

Reading that backwards is the question: given M, find a transform that reproduces it. The obvious route — decompose RS into a rotation and a scale — is a polar decomposition, it is iterative, it is lossy, and it fails outright on a shear. The route the code takes is to notice that the equation has an easier solution if you stop insisting that R be a rotation. Put S = I and let R absorb everything:

\[ R' \;=\; \text{linear}(M), \qquad S' \;=\; I, \qquad \mathbf{p}' \;=\; \text{translation}(M) \quad\Longrightarrow\quad R'S' \;=\; R'\;=\;\text{linear}(M) \] R' = linear(M), S' = I, p' = translation(M) => R'*S' = linear(M), exactly

No arithmetic is performed at all. The nine numbers are copied, the three are copied, and the multiply by I that parent_from_local performs on the way back is a multiply by one. That is why the round trip is exact in the strongest sense available: not “within 1e-6”, but zero.

Worked: one transform, out and back

Take a deliberately awkward one — a non-uniform scale, three rotations, an off-axis position:

position = (1.25, −3.5, 7.75)
rotation = Ry(0.7) · Rx(−0.31) · Rz(1.9)
scale    = (2.5, 0.125, 1.75)

Resolve it through the hierarchy, collect it, and recompose the result. verify_512 §B compares all sixteen elements:

ok   max |element difference| = 0 (expected exactly 0)
ok   CONTROL: a 1.0 nudge is reported as 1 (must be > 0.5)

The control is not decoration. “The difference is zero” is also what you get from comparing something with itself, from comparing two empty matrices, or from a comparison function that returns zero. Perturbing one element by 1.0 and requiring the same code to report it is what makes the first line mean something.

5. Where the new header goes, and what it may include

Two decisions, and both are physical design rather than taste.

5.1 Should the engine define a component at all?

Publishing a system is uncontroversial. Publishing a component is a real commitment: every program that wants this loop must store its mesh handle in the engine's struct rather than its own, and an engine that publishes components is taking a position on how a game is laid out. Some engines do (Unity's MeshRenderer); some deliberately do not (EnTT ships a registry and no components at all).

The precedent is already set, and by this same module. ecs/hierarchy.hpp defines parent and world_transform, and it had to, for a reason that is mechanical rather than philosophical: hierarchy::resolve cannot be written against “whatever component you happen to call parent”. A system the engine owns must name the data it reads or it cannot be compiled. That gives a rule you can apply:

The rule

The engine defines a component when, and only when, an engine system reads it. Everything else is the game's.

So renderable is the engine's, and rover, collectible, spinner, bobber, carousel and pillar are not — nothing under engine/ will ever look at them, and nothing in the game had to ask permission to invent them.

5.2 gfx/ or ecs/?

The struct holds a mesh_handle and the function takes a registry, so it touches both. Put it under ecs/ and every program that includes the ECS compiles mesh.hpp, light.hpp and their transitive closure — to store a component that no simulation code will ever read. Put it under gfx/ and graphics knows about entities while entities know nothing about graphics.

The deciding principle is the direction of the arrow: a dependency should point towards the more general and the more stable. A registry has no opinion about meshes and a great deal of future code — Module 8's physics, a save system, an editor — wants entities and will never want a mesh_handle. So: engine/gfx/renderable.hpp, and the ECS stays clean.

5.3 And the registry is named, not included

Lesson 5.11's rule was that a header's include list is its interface. This header names ecs::registry in one signature and never dereferences it, which is exactly the case a forward declaration covers:

C++ in place: incomplete types

A declaration like class registry; introduces the name of a type without its definition. You may then form pointers and references to it, declare functions that take and return them, and nothing more — you cannot create one, call a member, take sizeof, or inherit from it, because none of those can be answered without the layout. That is the whole trade: a reference parameter needs only a name, so the definition can stay in the .cpp. gpu_scene.hpp already does this for instance_batch, and says why in a comment.

The cost of getting this wrong is not hypothetical. §3.2 measured the templated ECS headers as the expensive half of this engine's public surface; every file that merely stores a renderable would pay for them.

6. The camera boom, and an assertion that hangs

Lesson 5.9 made the camera an entity, and one consequence is so convenient it is easy to take the wrong lesson from it: parent the camera to the player and you have a follow camera, for free, with no system and no code. It rides along because riding along is what “my placement is relative to my parent” means.

It is also wrong, and specifically so. The rover leans into its turns — a cosmetic roll of up to 22°, which looks good on a car and is poison to a camera. A camera parented straight to the rover inherits the entire basis, roll included, so the horizon see-saws. Viewers do not read that as the car leaning; they read it as the world tilting, because the camera is the viewer's inner ear. And there is a second inheritance that is worse than cosmetic: the rover is a scaled box, 0.60 × 0.44 × 0.84 metres, so a camera parented to it inherits a non-uniform scale.

The fix is not a special case in the renderer and not a “camera follow” system. It is one more link in the chain — a boom, an entity with a transform and no components of its own, whose only job is to be a place where the two unwanted factors can be cancelled.

@@FIG_BOOM@@

Now the algebra, which is short and has exactly one trap in it. The rover's world basis is its heading H, times its roll Rz(bank), times its scale S. We want the boom's world basis to be H alone. Since world(boom) = world(rover) · local(boom):

\[ L \;=\; \bigl(H\,R_z(\beta)\,S\bigr)^{-1} H \;=\; S^{-1} R_z(-\beta)\,H^{-1} H \;=\; S^{-1} R_z(-\beta) \] L = (H * Rz(bank) * S)^-1 * H = S^-1 * Rz(-bank) * H^-1 * H = S^-1 * Rz(-bank)

The inverse of a product reverses the order of its factors, so the unscale comes first and the unroll second. Read that sentence again, because the English description of what we are doing — “undo the roll, then undo the scale” — produces Rz(−β)·S−1, which is the other one. And a rotation and a non-uniform scale do not commute, so the two are genuinely different matrices.

Worked: why the wrong order is not a small error

Take the rover's actual scale S = diag(0.60, 0.44, 0.84) and a bank of 0.31 rad (17.8°). Consider what each candidate does to the boom's x axis, (1, 0, 0):

S⁻¹ · Rz(−β) · (1,0,0)  = S⁻¹ · (0.9523, −0.3051, 0)
                    = (1.5872, −0.6934, 0)

Rz(−β) · S⁻¹ · (1,0,0)  = Rz(−β) · (1.6667, 0, 0)
                    = (1.5872, −0.5085, 0)

The x components agree to four decimal places and the y components differ by 36%. That is what makes this bug expensive: the result is close enough to look like a tuning problem. And the first version of this file shipped the second one.

6.1 What actually happened when it was wrong

The program did not draw a tilted horizon. It hung, in a headless --shot run, for ever, with no output at all — and that is a more instructive failure than the wrong picture would have been.

Lesson 5.9's view_from_camera asserts its input is rigid, because a view matrix is the inverse of a camera's placement and the fast inverse it uses (rigid_inverse) is only an inverse when the basis is orthonormal. The boom with its factors swapped leaves a basis that is neither, so the assertion is entirely correct and fires on the first frame. What happens next is the part nobody had met yet:

Lesson 5.3 shipped SDL_assert and made a point of the fact that it expands to a while loop so that its RETRY option genuinely re-tests the condition. That is exactly right at a desk with a dialog box in front of you. In a headless run on a build server, with no display to put a dialog on and no terminal to prompt at, the handler's default answer keeps arriving and the loop keeps retrying a condition that cannot change. The assertion that would have taken one second to diagnose interactively became a hang with no message.

The general shape of this

An assertion is a developer-facing control flow, and --shot is the one configuration in this repository that has no developer in front of it. That is not a reason to remove the assertion — it caught a real bug on the first run, which is precisely its job — but it is a reason to know the failure mode before you meet it at three in the morning on CI. Lesson 5.12 does not change SDL's handler; it reports the behaviour, and Exercise 5 installs a handler that aborts instead of retrying when there is no video subsystem.

The fix is one line, and verify_512 §E keeps it fixed by building all three chains — right order, wrong order, and no boom at all — and asserting the rigidity of each. Note the third: without a control that also fails, “the wrong order is not rigid” would be equally consistent with the boom doing nothing whatsoever.
