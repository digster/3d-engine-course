Module 5 — Becoming an Engine · Lesson 5.6

Data-Oriented Design: Why Scene Trees Creak

Everything since 5.1 has been about structure — where code lives, who owns what, how things refer to each other. This is the first lesson in the module about speed, and its job is to earn the ECS that 5.7 and 5.8 will build rather than assume it. So: no dogma, no parable about cache lines, no appeal to what everybody knows. Six scene layouts, two workloads, five scene sizes, timed on this engine's own transform. Three of the results contradicted what I expected before running them, one of them by a factor of two — and the lesson keeps all three, including the two places where a first attempt measured something that was not there.

1The Problem

Two lessons from now this course builds an entity-component system, and every treatment of ECS you will read opens the same way: object-oriented scene graphs are slow, cache misses dominate modern performance, arrays of structures are bad and structures of arrays are good, therefore ECS. It is a persuasive story, most of it is even true, and it has a defect that matters more than its truth:

The problem with the story

You cannot act on it. It contains no number, so it cannot tell you whether your scene is big enough to care, which of the four things it blames is actually costing you, or what to do first. An argument you cannot check is an argument you have to take on faith — and a course that has derived the perspective matrix from similar triangles and measured the cost of a handle in fractions of a nanosecond should not start taking things on faith in Module 5.

So this lesson does the experiment. It is unusual for the course in that it changes almost no engine code — one new header — and its output is evidence. That evidence then has to be allowed to say whatever it says, including "this does not matter at your scale", which is an answer the ECS literature never gives and which happens to be true of this engine today.

There is a second, quieter problem, and it is the reason the one new header exists. Lessons 5.3, 5.4 and 5.5 each needed to time two things against each other, and each hand-rolled the same twenty lines slightly differently. Lesson 5.5's own argument about the search path was that three copies of one idea is the usual sign that the idea has no name. Its name is A/B timing, and getting it wrong is much easier than it looks — §3.2 is a catalogue of the ways this very lesson got it wrong before it got it right.

2Building Intuition

2.1How much data is there, really?

Before any argument about layout, one question settles most of the argument: how much data is there, and where does it fit?

@@FIG_SCALE@@

An engine::scene_object is 96 bytes — Lesson 5.4 shrank it from 160 by replacing a borrowed mesh view with a four-byte handle — of which 60 are the transform, which is everything a model-matrix loop reads. So a flat array of them is 96 bytes per object with 36 bytes of ballast the transform loop fetches and ignores.

Now put that against a cache. A cache line is 64 bytes; an L1 data cache is typically 32–64 KB; an L2 is a few hundred KB to a couple of MB; an L3 is measured in tens. Multiply out:

That table is the whole shape of the lesson in advance. Every claim about layout is a claim about which row you are on, and a rule with no N in it is not a rule. If your scene is four objects, it fits in a quarter of an L1 cache and no arrangement of it can miss; if it is a hundred thousand, it does not fit anywhere and the arrangement decides how many times you go to DRAM.

2.2Six layouts, as memory

@@FIG_LAYOUTS@@

Flat is what the engine has: engine::scene_object scene[4], and pool::items() for anything the store holds. One stride, one direction. Hardware prefetchers detect a constant stride and fetch ahead, so a linear walk of an array is close to the best a machine can do — at the price of dragging 36 unread bytes along with every 60 read ones.

Pointers is what an object-oriented scene is, in every language: std::vector<Entity*>, or a parent holding unique_ptr children, or a list of shared_ptr. Eight bytes in the array, then a load to somewhere else. We measure two versions, and separating them turns out to matter: ordered visits the heap blocks in the order they were allocated, shuffled does not. Real scenes start ordered and become shuffled, because objects are created and destroyed, the allocator reuses holes, and the draw list gets sorted by material.

SoA takes the transform apart: an array of positions, an array of rotations, an array of scales. A loop that needs only positions touches only positions. This is the layout the ECS literature is really arguing for, and §5.2 finds that why it wins is not what the literature says.

Virtual is the same object hierarchy with a virtual mat4 world() const, because the scene graph being argued against is usually polymorphic too, and comparing against a straw man produces a worthless conclusion. Two variants again: one concrete type (perfectly predictable) and two interleaved (not).

Tree is the thing this lesson is named after — nodes linked by first_child / next_sibling, walked depth-first. Two variants once more, and this is the pair that produces the lesson's headline: children in allocation order, and children shuffled.

3The Theory

3.1Four rules for an honest comparison

The theory in this lesson is not about caches. It is about measurement, because the caches will tell you the truth and the measurement is where the lying happens.

Rule 1 — alternate the arms. Not "run A ten thousand times, then B ten thousand times". A machine warms up, throttles, migrates between cores and gets interrupted, and every one of those effects lands on whichever arm happens to be running. Lesson 3.10 discovered this expensively: it published a 10% improvement that turned out to be session drift, visible in the data as both columns climbing monotonically as the machine warmed. Run one rep of A, then one rep of B, and repeat — then any drift lands on both.

Rule 2 — report the median, and the spread. A single scheduler hiccup moves a mean and cannot move a median. But a median alone hides a bimodal result, so the minimum and maximum come with it. If one arm's range straddles the other's median, you have not measured a difference; you have measured noise, and the honest word for the result is "tie".

Rule 3 — stop the optimiser deleting the work. A loop whose result is unused is a loop a modern compiler may remove entirely, and a benchmark that measures an empty loop reports beautiful numbers. Storing the accumulated value through a volatile is the cheapest portable answer: the standard requires the store to happen, so everything the value depends on must happen too.

Rule 4 — check that both arms computed the same answer. This is the rule people skip and it is the one that makes the other three mean anything. If arm A is faster because it is doing less, the number is not a comparison, it is a bug report with a stopwatch attached. §4.3 is this rule catching two real problems in this lesson's own benchmark.

3.2Three ways a microbenchmark lies

Each of these happened here, in this order, and each produced numbers that looked entirely plausible.

The timer is coarser than the work. The first run reported 0.0000 ns/item at four objects. That is not a fast layout, it is a timer: SDL_GetPerformanceFrequency() is 24 MHz on this machine, so one tick is 41.67 ns and a pass over four objects finishes inside one. Every sample read either zero ticks or one. The tell: a suspiciously round number, especially zero, and neighbouring measurements that differ by exactly one quantum. The fix: repeat the pass inside the timed region until a sample is worth ~100 µs, and divide back out.

The compiler deleted the loop. With the pass repeated, the tree arm reported 0.166 ns per item at n = 4 — which is 2.3 cycles for four matrix builds. parent_from_local is nine multiplies and sixteen stores; two cycles is not a plausible price for it. Repeating a pure function of nothing lets the compiler compute it once and reuse the answer. The tell is arithmetic, not suspicion: multiply the number out and ask whether the hardware could physically do that. The fix: make each pass genuinely different work — here, a per-pass bias added to the accumulator so the running sum's rounding depends on it, which floating-point non-associativity makes impossible to optimise away.

The accumulator is the bottleneck. The cull workload's arms came out identical at every size, which for a memory-bound loop is impossible. The cause was hits += 1.0: a serial chain of double additions, ~4 cycles of latency each, against a body of three multiplies and a compare. The accumulator was the critical path in both arms and the layout difference was completely masked. The tell: two arms that should differ, agreeing exactly. The fix: an integer counter, one cycle and vectorisable, which puts the memory back on the critical path where the experiment wanted it.

The pattern behind all three

Every one of them was found by asking whether the number was physically possible, not by suspecting the code. Nanoseconds convert to cycles; cycles convert to instructions; instructions are countable. A benchmark result you have not sanity-checked against the hardware is a number you have chosen to believe.

3.3Why a linked list is worse than a scattered array

One piece of mechanism is worth having before the results, because it explains the largest number in them. Both an array of pointers and a linked list are "pointer chasing", and they behave completely differently.

@@FIG_CHAIN@@

With an array of pointers, the addresses are known in advance. The CPU reads p0 through p4 out of one or two cache lines and can issue all five dependent loads before any of them has returned. A modern core sustains something like a dozen outstanding misses; they overlap, so five 80-nanosecond misses cost rather less than 400 nanoseconds. This is memory-level parallelism, and it is why scattering objects across the heap costs 2.4× and not 20×.

With a linked list, the address of the next node is inside the current one. You cannot start fetching node 1 until node 0 has arrived, because node 0 is where node 1's address is written down. The misses are a serial dependency chain: they add instead of overlapping.

\[ t_{\text{array}} \approx \frac{N \cdot t_{\text{miss}}}{k} \qquad\qquad t_{\text{list}} \approx N \cdot t_{\text{miss}} \] array of pointers ~ N * miss / k (k misses in flight); linked list ~ N * miss

That factor of k — the number of misses the core can keep in flight — is the entire difference, and it is why the two arms come out at 2.4× and 6.5×. A scene tree is the second picture. That is what creaks: not the hierarchy, not the object orientation, not the virtual calls, but the fact that finding the next thing to work on requires having finished fetching the last one.
