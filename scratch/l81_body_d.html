9. The implementation

engine::phys is the fifth new directory since the Module 5 refactor, and the second (after audio/) whose contents never touch a pixel. It starts smaller than any subsystem in this engine has: one header and one source file.

9.1 motion, and what is deliberately not in it

struct motion
{
    vec3 position{};
    vec3 velocity{};
};

That is the entire state. No mass, no orientation, no handle, no shape, no id. It is worth being explicit about why, because the temptation at the start of a physics module is to write the rigid_body you know is coming and integrate a field of it.

An integrator does not need any of that. It needs a quantity and its rate of change. Keeping the type down to two vectors is what let §5 be an argument about a 2×2 matrix instead of an argument about an engine — and it is also what makes the type reusable for things that are not bodies at all: a spring-damper camera, a smoothed UI value, a particle. Lesson 8.2 adds mass and turns F = ma into a rigid_body that has a motion; 8.3 adds orientation and an inertia tensor beside it.

The units are the ones fixed on the Conventions page in Module 2: metres and seconds. That has been a statement about rendering for six modules and becomes a statement about physics here — 8.2 is where "1 unit = 1 metre" stops being pedantry, because 9.81 is a number in those units and in no others.

9.2 Three rules, as close together as they will go

The stepping function is a template over the acceleration callable, and its three cases are written to sit directly under one another so the difference is impossible to miss: 

case integrator::explicit_euler:
{
    const vec3 a = accel(m.position);
    m.position += m.velocity * h;
    m.velocity += a * h;
    break;
}

case integrator::semi_implicit_euler:
{
    const vec3 a = accel(m.position);
    m.velocity += a * h;
    m.position += m.velocity * h;
    break;
}

Two lines, swapped. The course index calls this "one character's difference", and that is precise if you read it as a formula rather than as code — the update is xn+1 = xn + h·vn against xn+1 = xn + h·vn+1, and the difference is the subscript. In C++ it is a line order, which is if anything worse: a line order is the kind of thing an "obvious" refactor rearranges, and there is no compiler diagnostic anywhere that will tell you what you just did.

Velocity Verlet is the third case, and it does something the others do not — it evaluates the acceleration twice: 

case integrator::velocity_verlet:
{
    const vec3 a0 = accel(m.position);
    m.position += m.velocity * h + a0 * (0.5f * h * h);
    const vec3 a1 = accel(m.position);
    m.velocity += (a0 + a1) * (0.5f * h);
    break;
}

Move with the acceleration you have, then correct the velocity with the average of the accelerations at the two ends of the step. That average is a trapezium rule, which is why the method is second order, and the ½·a·h² in the position line is the Taylor term §3 identified as the one everyone else drops.

A production Verlet caches a1 and hands it to the next step as its a0, halving the force work. This one does not, and the reason is stated in the header rather than hidden: caching costs a state field that the other two rules have no use for, which would push a vec3 into motion for the benefit of one enumerator. That is the right trade when the force evaluation is a broadphase query, and the wrong one for a type whose whole job in this lesson is to be legible. §10 measures what the honesty costs, and it is 14%.

9.3 Why it is a template

Accel&& rather than std::function<vec3(vec3)>, and the justification is a measurement rather than a reflex. A std::function is an indirect call that the optimiser cannot see through, once per body per step: 

I.1  explicit           0.994 ns/body/step
     semi-impl          0.963
     verlet             1.136

I.3  std::function      1.591 ns/body/step

0.63 ns per body per step, which is 65% on top of the step itself — a function call whose body is one multiply, costing more than the arithmetic it wraps. In absolute terms it is small (ten thousand bodies buys it for 6 µs a frame), and the reason to care is that it scales with the same thing everything else in Module 8 scales with. And there is a second, sharper reading of the same table further down: 

I.4  integrate(m, g, ...)     1.222 ns/body/step
   SLOWER than the template in I.1, and that is the
   whole argument for the template: this one is a
   real call into libengine.a and cannot inline
   across the archive.

The non-template overload — the constant-acceleration one that lives in the .cpp and handles gravity — is the slowest of the lot, because it is a genuine call into libengine.a that cannot be inlined across the static archive. The simpler-looking path is the expensive one. That is worth remembering the next time "just put it in the .cpp" sounds like tidying up.

9.4 The diagnostics, and a zero that is an answer

Four functions in the header do no stepping at all, and they exist so that the analysis in this lesson is something the engine can do rather than something the lesson merely says: spring_energy, shadow_energy, area_factor and max_stable_step. Sections B, C and F of the harness check their own claims against these, which means the header is never allowed to drift away from the prose.

The one worth singling out is max_stable_step: 

case integrator::explicit_euler:      return 0.0f;

case integrator::semi_implicit_euler:
case integrator::velocity_verlet:     return 2.0f / omega;

A function called "largest stable step" returning zero looks like a bug and is the most honest line in the file. There is no stable step size for explicit Euler on an oscillator; the answer is not "small", it is "none". Returning some small positive number would be a lie the caller could act on. Returning zero means somebody who writes h = 0.5f * max_stable_step(rule, w) gets a simulation that does not move — which is a far better bug report than a simulation that quietly explodes twenty seconds into a playtest.

The omega <= 0 case returns HUGE_VALF rather than a large number, for the same reason: with no restoring force there is nothing to be unstable about, every rule reduces to straight-line motion, and a caller comparing against the result wants the real answer rather than a sentinel it has to know about.

9.5 The demo, and an accumulator inside an accumulator

demos/integrate draws phase space, because §5 is the argument and a bouncing dot is not. It also does one structural thing worth copying. 

void on_fixed_step(float h) override
{
    if (paused_) { return; }
    sim_.begin_frame(h);
    while (sim_.next_step()) { advance(sim_.h()); }
}

That is Lesson 1.4's fixed_step — the same class, unchanged — running inside the application's own fixed step. It looks redundant and it is the point: the application's rate is a platform decision, and the simulation's rate is the variable this demo exists to vary. Pressing Up changes what physics does without changing how often the screen updates, and the two concerns stay separable because 1.4 made the accumulator a type instead of four lines in a loop.

Two smaller decisions in that file earned their comments. The first is a ceiling on the view scale: the plot follows the worst track only up to three amplitudes, after which the red curve simply leaves. Without the ceiling a diverging explicit Euler pulls the camera back without limit and every other curve collapses to a dot within about ten seconds — the picture ends up showing nothing but the thing that is broken, at exactly the moment you want to compare it against the things that are not.

The second is that the curve leaving means the panel needs a real clip, so the file carries a twenty-line Cohen–Sutherland. engine::draw_line deliberately does not clip — Lesson 2.1 says so in a comment, walks every pixel and lets put_pixel's bounds check discard the ones outside — which is correct for the framebuffer and does nothing at all to stop the red spiral being drawn straight across the energy chart next door. That exercise from 2.1 came due here, seventy lessons later, for a reason nobody predicted.

10. The budget, and the free lunch

@@FIG_DEMO@@

Section I times ten thousand bodies for a hundred steps, with the rule as a compile-time constant so that each of the three loops is a separate monomorphic function. That detail is not incidental — the first version passed the rule as a runtime integrator, and the measurement then depended on whether the optimiser felt like unswitching the loop, which it did on some runs and not others. Explicit came out 15% faster than semi-implicit in one run and 30% slower in the next. A benchmark whose answer changes run to run is measuring the compiler, not the code. 

I.1  rule            ns/body/step   force evals
   explicit           0.994          1
   semi-impl          0.963          1
   verlet             1.136          2

I.5  CONTROL: a loop that does nothing but walk the
     same array.
   touch only         0.608 ns/body/step

0.994 against 0.963. They differ by 3%, against a run-to-run spread of the same size, which is the measurement's way of saying they cost the same — as they must, because they are the same loads, the same multiplies and the same stores, differing only in which order two of them happen. The control underneath says 0.608 ns of that is walking the array at all, so the arithmetic itself is about a third of a nanosecond.

Which makes this one of the genuinely rare things in engineering: a free lunch. One of these two rules is unconditionally unstable and the other is stable up to a hard, computable limit, and they cost the same. There is no trade-off to weigh, no profile to consult, no "it depends on your workload". There is only a correct choice and an incorrect one.

And for scale: ten thousand bodies under gravity cost 0.012 ms of a 16.67 ms frame, which is 0.07% of it. Integration is not where physics time goes. Collision detection is, and Lessons 8.4 through 8.8 are about that — which is worth knowing now, so that nobody spends an afternoon hand-vectorising the cheapest loop in the module.

11. What this does not do

This lesson built the smallest honest thing, and the list of what it is not is longer than the list of what it is.

  • No mass, no forces. integrate takes an acceleration. Turning a force into one is a = F/m, and it needs a body to have a mass, which is Lesson 8.2.
  • No rotation. Angular motion has the same structure and a much worse-behaved version of it: the "mass" is a tensor that rotates with the body, and the equations have a term with no linear analogue at all. Lesson 8.3, and it needs the quaternions from 7.4.
  • No collision, no constraints. Which is why §6.3's stability limit does not immediately doom us. A contact is not going to be a stiff spring; it is going to be an impulse (8.9) inside an iterative solver (8.10), for precisely the reason measured there.
  • No adaptive step. A general-purpose ODE solver estimates its own error and shrinks the step when it is too large. Games do not do this — a variable step makes replays and lockstep networking impossible, and Lesson 1.4 is the whole argument. We choose h once and make the physics fit inside it.
  • No RK4. The fourth-order Runge–Kutta everybody meets first is more accurate than anything here per step, and it is not symplectic: it has the same disease as explicit Euler, milder. It costs four force evaluations, which for a physics engine is four broadphase queries. Exercise 5 measures its determinant, and the answer is worth the twenty minutes.
  • No velocity-dependent force in the symplectic path, for the reason §8 gives. Drag is handled exactly and separately, and anything more exotic — a magnetic force, a gyroscopic term — needs its own analysis rather than an assumption that the reordering helps.
