## The sentence the lesson turns on

**A call records work; it does not perform it.** 0.1879 ms of CPU calls describe 4.7815 ms of GPU
work — **25.45×** — so the CPU is free for 96% of the time the work takes. All four genuinely new
objects are one idea: device = the connection, command buffer = the message, transfer buffer =
shared ground, fence = the acknowledgement. The other five of nine are renames, and `verify_42` §G
*tests* that (enumerator parity for filter / address_mode / cull_mode) rather than asserting it.

## The measurements

- **Recording vs executing.** 48 blits of 2048²: acquire 0.0009, record 0.1846 (0.0038 each),
  submit 0.0024, fence wait **4.7815** ms.
- **The fence is the contract.** Read before it, wrong **64/64**, with the destination poisoned to
  `0xAB` first. After it, 0/64.
- **What a sync costs.** GPU-bound: 9.438 vs 5.904 ms → **1.60×**, and the pipelined figure equals
  the GPU time per submission exactly. Display-bound: fence 0.761, acquire 16.002 → 15.272, frame
  **unchanged** at 16.667. Ship either number alone and you teach something false.
- **A float clear.** 0.5 → **128** (`_UNORM`, exactly `round(255v)`) and **188** (`_UNORM_SRGB`,
  matching *our own* `linear_to_srgb_u8`). RGB only — one clear of (.5,.5,.5,.5) gives R=188,
  A=128. Out of range clamps.
- **The present path.** `SDL_PIXELFORMAT_ARGB8888` → `B8G8R8A8_UNORM` (asked, not reasoned).
  Round trip **bit-identical**. 320×180: memcpy 0.0028 ms, whole round trip 0.2084 ms.

## The finding that contradicts the advice

**A full GPU sync every frame is free on a display-bound frame** — and that is the *dangerous*
result, because a renderer that syncs every frame measures perfectly on a simple scene and falls
apart when the GPU becomes the limit. The rule is neither "syncing is slow" nor "syncing is free":
a sync costs **the overlap you gave up**.

## The benchmark that could not be true

First figure: **763 GB/s on a 273 GB/s bus.** Two independent causes, found in order — the driver
elided 48 identical blits (fixed by ping-ponging), and both textures were cleared **flat**, which
lossless render-target compression squeezes to nearly nothing (fixed with xorshift noise). After
both, 4096² lands on **277.6 GB/s** against a published 273. Kept in the lesson with both reasons,
because "check that the number can be true" is the transferable part.

## The mistake this session records

An unchanged binary measured **120 fps then 60 fps** minutes apart, and for a few minutes this
produced a very exciting, completely false conclusion that fencing halves the frame rate. The
window had opened on a **different display** — a 120 Hz laptop panel, then a 60 Hz external
monitor. Same class as 3.10's rule about numbers taken hours apart, on a new axis; fixed the same
way 4.1 fixed its own version, with three binaries run alternately in one session, twice.

Note that neither the window size nor the swapchain size differed between those runs, so nothing in
the program's own output could have caught it.

## One design decision worth remembering

`engine --gpu` is a second program in the same binary, and that is **forced, not chosen**: a window
can be claimed by an SDL_GPU device *or* driven by an `SDL_Renderer`, never both, and every HUD in
Modules 1–3 is `SDL_RenderDebugText`. Taking the window for the GPU would have deleted the HUD from
the five demos `Tab` cycles. The branch is taken before `SDL_CreateRenderer` is reached, and **it inverts
at 4.8** when the ported scene makes the GPU path the default.
