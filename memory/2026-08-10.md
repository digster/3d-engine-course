## The sentence the lesson turns on

**A texel is a sample, not a square.** Its value lives at `(i + 0.5)/N`. The half-texel offset,
which two texels a point lies between, why a 1:1 blit can be bit-identical, and why nearest
filtering cannot see the offset are all consequences rather than separate facts to learn.

## Three findings the harness produced

- **Three of the first five failures were the test, not the code.** The loudest: the 1:1 blit test
  failed while its *control* passed, which is impossible if the test is sound. Cause — this
  rasterizer evaluates attributes at **integer** pixel coordinates, so pixel `i`'s sample point is
  `i` while a texel's value is at `(i+0.5)/N`. **The half-texel question exists at both ends of the
  pipeline.** The other two failed by not holding a second variable still: probing clamp at
  `v = 0.5` straddles two texel rows, and comparing two meshes' uvs index-by-index measures
  `load_obj`'s first-appearance numbering (3.5's own rule) rather than the flip.
- **The obvious benchmark measured the sRGB encode.** Rule-vs-textured read 5.04× — not believable
  for a lookup into 16 KB. `uv_checker` encodes nothing; `textured` re-encodes through three
  `std::pow` calls per pixel. Holding the encode constant (all variants `lit`): **1.12×** for a
  nearest fetch, **1.41×** for bilinear, i.e. bilinear is 1.26× nearest. Both tables kept and
  labelled in `verify_39` §I, because a plausible benchmark that measures the wrong thing is worse
  than none.
- **Aliasing is not caused by a large footprint.** All four test images are 64 texels wide, so the
  traced footprint is identical at any screen row — 0.60 texels/px at the bottom of the frame,
  **62.46** two rows below the horizon. The sub-pixel-nudge sparkle still ran 8.0% → 16.2% → 32.6%
  → **64.8%** as the checker went 4 → 32 cells. What changes is the *contrast* inside the
  footprint.

## The convention this settles

The uv origin, carried open in STATE since Lesson 3.5. Settled by **quoting** `SDL_gpu.h`'s
"Coordinate System" section — top-left, +Y down — rather than by trying both and keeping the one
that looked right. The flip is `v → 1 − v` and it belongs to the **import** step: not the parser
(3.5 settled that a loader stores what the file says) and not the sampler (which has to match
hardware that will not flip for us). New rule: *a loader must not alter its input; a pipeline may.*

It must be applied to **every** mesh a load produces, in-memory ones included — otherwise 3.5's
round-trip comparison starts measuring the import step instead of the loader.

## The debt this adds on purpose

`raster.hpp` now includes `texture.hpp` as well as `light.hpp`, and **"textured and lit" is not an
enum value** — it is `lit` plus a binding, so `shading` has stopped describing a fragment on its
own. 3.8 fixed the previous instance of this by splitting one enum in two, which worked because
both questions had small closed answer sets. This one cannot be fixed that way: the combinations
of albedo source × what is done with it × which texture are a *program*, not a grid. Fifth pressure
now pointing at Module 4's programmable fragment stage.

## Two defects only a screenshot caught

- **Duplicate SVG marker ids.** Six figures each emitted the same four ids, and `url(#e-i)`
  resolves to the first match — every figure was quietly using figure 1's markers. Harmless while
  the definitions are byte-identical, which is what makes it a trap. Now namespaced per figure;
  3.7 and 3.8 still carry the old pattern.
- **White numerals on pale swatches.** `check-page.js` checks label *geometry*, never contrast. Fix
  is a page-local `.t-onlight` and choosing between it and `.t-inv` by relative luminance in the
  generator — a computation, not a judgement call.
