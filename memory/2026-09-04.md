## The results

**Query, K=4, sparse relative to archetype** (n = 4 / 100 / 1k / 10k / 100k):

| | 4 | 100 | 1,000 | 10,000 | 100,000 |
|---|---|---|---|---|---|
| cheap, aligned | 0.81 | 0.91 | 1.06 | 1.26 | 1.31 |
| cheap, scrambled | 0.84 | 0.98 | 1.16 | 1.92 | **2.40** |
| real, aligned | 0.97 | 1.05 | 1.05 | 1.02 | 0.96 |
| real, scrambled | 0.98 | 1.05 | 1.05 | 1.17 | **1.34** |

**Scalar (`-fno-vectorize`), real, scrambled: 1.00 / 1.00 / 1.01 / 1.21 / 1.39.** The redirect is
**latency in the shadow of work** and costs *nothing* until the working set leaves cache **and**
the orders diverge. Either alone is free. Control: K=1 is 0.99–1.01× everywhere.

**Structural change, ns/op** — the finding is *which row moved*:

| | 4 | 100 | 1k | 10k | 100k |
|---|---|---|---|---|---|
| archetype, 4 comps | 15.4 | 15.3 | 12.3 | 15.0 | 13.1 |
| archetype, 12 comps | 29.7 | 31.4 | 40.9 | 39.0 | **58.5** |
| sparse, 4 / 12 comps | 9.6/10.1 | 9.4/10.4 | 4.5/4.6 | 5.3/4.4 | **4.25 / 4.23** |

Eight components the operation never reads take the archetype 13.1 → 58.5 and the sparse set
nowhere. Cost model is **not** bytes moved (predicts 2.3×, measured 4.5×) but **independent
memory streams touched — two per column, per move**, because a column is a separate allocation.

**Selectivity (1 in 4), real, at 100k:** lead-small 1.46 · scrambled 1.94 · lead-big 1.73 ·
**GROUPED 0.99**. **Fragmentation: 1.12× worst**, at 512 chunks of 19 — far less than folklore.
**Memory:** 25% at 4 types; 12.8 MB of index at 32 types × 1e5, ~80% of it meaning "absent".

## The decision, and why it is not the query ratio

**Sparse set.** Reasons in weight order: (1) **the migration only runs one way** — a group buys
the archetype's query later, measured 0.99× on the archetype's own best case, and the reverse
does not exist; (2) the cost accepted is bounded (≤1.94×, only above 1e4, only selective, only
ungrouped) and the cost avoided **grows with every component type the course adds**; (3) nothing
at this engine's scale is on the table anyway; (4) a quarter of the code — a tiebreaker only,
admissible *after* 1–3.

**Wrong when:** >1e4 entities, stable component sets, narrow systems (DOTS's shape). Even then
group two pools rather than rewrite.

**Refused to let `pool<T>` decide it.** 5.4's pool *is* a sparse set
(`slots_`/`items_`/`owners_` = sparse/data/dense + generations) and noticing that is worth
credit — but choosing an architecture because we own something shaped like it is choosing by
accident. Convenience: admissible as a tiebreaker, inadmissible as evidence. What it actually
lacks is **one shared id space**.

## Traps worth remembering

- **The row map must be written AFTER the re-pack.** `archetype_churn::add_material` recorded
  where the entity landed, then called `pop_row` — which patches the row of whoever swap-and-pop
  displaced, and when the moved entity was the last row that entity **is** the one being moved.
  1-in-N, silent. Found only because `verify_57` §E churns **200 frames** then walks the whole
  row map; a single-frame test passes forever.
- **`box()` strokes at full opacity and fades only the fill** (`figs_5x.py`). Fig 6 drew 32
  elements at 0.26/0.07 to show "one in four is wanted" and rendered as 32 identical outlines.
  A pattern carried by fill alone does not read; mute the **stroke** too.
- **Two adjacent SVG text runs with no space** — again (5.5 fig 6, now 5.7 fig 3:
  `"…PER COLUMN."` at x=24 ending ~x=176, next run at x=178). Only a screenshot finds it.
- **An annotation that contradicts its own caption.** Fig 3 had a dashed box around the *one*
  pool that IS in the picture, under a caption about the pools that are not. Deleted.
- **`eval(check-page.js)` returns a Promise.** `const r = eval(src); r.pass` is `undefined` and
  the MCP serializer *drops undefined keys*, so the result looks like a pass with fields missing.
  `await eval(src)`, or return it directly and let Playwright await it.
- **`figure.dia:nth-of-type(N)` counts every `<figure>` sibling**, listings included — asking for
  figure 6 gave figure 4. Use `figure.dia >> nth=N`.
- Local `playwright` is not installed; the MCP server is the browser. Screenshots must go under
  the repo root (its allowed root), so they need explicit cleanup.

### Design decisions worth keeping

- **The entity is its own type, not `handle<entity_tag>`.** Reuses the constants, not the type: a
  handle names an item *in* one container, an entity names a row *across* every pool.
- **`dense_` stores the full entity word.** Third test in `contains()` — `dense_[at] == e` — is
  what rejects a recycled id, and it is unwritable if you store a bare index.
- **Type erasure by a counter behind a function-local static.** `static_cast` is safe *because
  the id created the pool*. Ids are global to the program; ~80 bytes wasted per registry buys an
  array index instead of a hash.
- **Every `pool_base` virtual is cold**, by design, because 5.6 measured 1.5–1.7× at every size.
- **`entities()` → `span<const entity>` for every `T`** is what makes rule 3 five lines with no
  metaprogramming. The lead pool then pays twice: fewer candidates, and no redirect for its own
  component (dense position *is* the loop counter).
- **Every read path uses `storage_if<T>()`.** Asking must not allocate.
- **No groups** — the hole is named, pointing at 5.7 §5.5.

### Traps worth remembering

- **A rule nothing can observe stops being true.** Every correctness test passes if the view walks
  the *biggest* pool. Hence `lead()`/`size_hint()` exist purely to be asserted on.
- **Two independent defences ⇒ a targeted test proves nothing.** A recycled id inherits nothing
  because the rows were erased *and* the generation moved; the 200-frame `std::map` shadow model
  is what actually tests it.
- **Do not cache the span you are about to iterate** — it dangles only when a vector happens to
  reallocate, the worst schedule for finding a bug. One virtual call per *walk* buys it away.
- **Figure numbers by page order — third occurrence** (5.3, 5.6, now 5.8). Authored erasure
  before the view; the reader saw 6 above 5.
- **`browser_navigate` after a rebuild can serve the cached page.** A fix looked un-applied;
  `grep` the built file, then `location.reload(true)`.
- **A label can overflow its own box without spilling the viewBox.** `check-page.js` cannot see
  it; a throwaway rect-vs-text extent check found all five columns at once.
- **A figure that derives a value from a rendering flag gets it wrong.** Fig 3 showed the free
  list as `[1]` after `create()` popped it, because the display keyed off "is this panel hot?".
- **"Five component types" appeared in six places and the demo has six.** Only running the demo
  and reading its own printed totals caught it — including the SVG's `<title>`/`<desc>`, which
  are prose and drift like prose.
- **`build_57.py` still stamped a STATE block**, months after the consolidation stripped it from
  53 pages; re-running it to repoint one link would have re-added 331 KB. Fixed the builder *and*
  proved it by rebuilding to a temp file and diffing against the shipped page — which also caught
  a one-line whitespace drift the original strip left behind.

**5.9 — Transform Hierarchy and the Camera System.** Every placement in 5.8 is world-space.
The spine of the lesson is a genuine tension: **the parent link is a component, but the order in
which transforms must be resolved is a property of the graph, not of any pool's dense order** —
and 5.7 established that a pool's dense order is its own business. Three candidates, and 5.6/5.7's
method says measure rather than pick: (1) recurse from roots each frame (5.6's 6.47× shape — at
what depth and fan-out?); (2) keep the transform pool sorted parents-before-children and walk it
flat (**this is a group by another name** — say so out loud); (3) dirty flag + topological pass
over only what moved. Honest experiment: depth × fan-out × fraction-moved-per-frame on
`bench.hpp`, all four measurement rules. Also: the camera stops being a special object and becomes
an entity with a component; "which camera is active" becomes a tag.

`verify_59` must cover a child following its parent, re-parenting mid-frame, a destroyed parent
(decide and state the orphan policy), a **cycle** (refuse it — a hierarchy that can loop is a
hang), depth > 1, and the resolution order actually being respected. Golden byte-identical for a
**ninth** lesson if the render path stays untouched — and if 5.9 is the lesson that changes it,
**re-baseline deliberately, with the diff shown**, never quietly. Carry forward: 5.8's
mutate-while-iterating rule bites hardest here, since re-parenting during a hierarchy walk is
exactly that hazard.
