## The design, in five decisions

1. **cgltf over tinygltf.** One C header, no deps. tinygltf pulls a JSON library and a **second
   copy of stb_image at a different pin**. PRIVATE include dir on the engine target, exactly as stb
   — so no demo can include `<cgltf.h>` and swapping libraries is a one-file change.
2. **The parser returns descriptions, not handles.** `gltf_material_desc` holds a
   `std::string base_colour_uri`. Handing `parse_gltf` an `asset_store&` costs three things: no
   testing without a filesystem (3.5's `parse_obj`/`load_obj` split), no offline cooker in Module 8
   (a handle cannot be serialised), and a second answer to "is this the same image?".
3. **A texture is a DERIVED asset.** `load_texture` goes through `load_image`, so one decode serves
   every material naming the file, and `derive_texture` records the edge. Safe where refcounting
   was refused because **nobody outside the store can hold a derivation edge**.
4. **Two edge lists, not one tagged one.** `mesh_derivations_` and `texture_derivations_`. An
   untagged `{uint32,uint32}` list would compile and resolve a texture's bits against the mesh
   pool — 5.4's aliasing failure in a new costume.
5. **`load_model` takes no import settings.** `flip_uv_v` defaults to true and is right for OBJ and
   wrong for glTF. **The flip belongs to the FORMAT, not the caller.**

## The ⚠ VERIFY, and what checking it actually found

6.4's comment said `1 − F(v·h)` is "what the glTF reference BRDF uses". Khronos Appendix B gives
`dielectric_brdf = mix(diffuse, specular, F)`, so the claim is **true in substance and imprecise in
a way that changed the design**: the same F scales the specular *up*, and `cook_torrance_specular`
already carries it. Six terms compared, **five identical**.

The metallic blend is not even a difference. The spec lerps two whole BRDFs; we lerp the F0; they
commute **exactly**, because Schlick is affine in F0 — `F(f0) = f0(1−w) + w`. That was derived on
paper and then measured at 1.19e−07, which is the right order (6.5's rule: write the claim, then
run it).

And the spec answers its own conformance question: §3.9.6 says BRDF implementations **MAY** vary;
Appendix B says a physically accurate one **MUST** be energy conserving. Ours is 0.9255, the spec's
own sample form is 1.3395. **We ship ours and are conformant.** 6.4 had assumed interchange might
*require* the other form; it does not.

## Traps worth remembering

- **A gap between two working halves is invisible to every test.** The engine could decode a PNG
  (5.3) and sample a texture (3.9) and **nothing joined them** — every CPU texture was generated,
  every loaded image went to the GPU. No wrong behaviour, only absent behaviour, and coverage
  measures code that exists. Look for subsystems that ought to compose and have never been asked to.
- **The convention that AGREES is more dangerous than the one that differs.** glTF's uv origin
  matches ours and OBJ's does not, so the flag that is correct for every mesh the engine had loaded
  is wrong for every one it loads next.
- **A test assertion can be wrong about correct behaviour.** §A asserted 8 vertices and got 36; the
  loader was right (no NORMAL → flat generation → one vertex per face-corner). The fix was not to
  relax it but to make the **assets say which case they test** — `cube.gltf` now ships smooth
  normals, `shapes.glb` ships none. One failing check became two better tests.
- **I asserted a texture was 64×64 without checking.** It is 256×256. Third lesson running that the
  habit which catches this is *write the claim, then run it* — and this time the harness caught it
  in the first run.
- **Forward references, again, and worse than 6.4's.** I wrote "6.9's IBL" (it is **6.12**),
  "6.11's frustum culling" (**6.13**), and the wrong *title* for 6.7. `docs/index.html` is the
  authority; grep the body for `6\.[0-9]` before building. Six errors caught this way in three
  lessons — this is now a checklist item, not a reminder.
- **Four figure defects the automated checks structurally cannot see**, all found by *looking*: a
  label column overlapping the next (caught by `svgTextOverlap`, the one it could see); a footer box
  overlapping the last table row; a "kind" column running outside the viewBox entirely; and a `+v`
  label placed on top of a black-and-white checkerboard, where an orange glyph is unreadable at any
  size. Compute column spans from the widest entry × units-per-character, and **look at the
  picture**.
- **A physically correct render can be a bad picture, and saying so is the lesson.** The metals are
  black or clipped at 64× white. The temptation is to fudge the asset; the better move is to keep
  defensible values, measure the clipping, and let the number argue for 6.12 and 6.10.
- **Pinned `build_65.py` before touching anything**, fifth lesson running, and the rebuild diff was
  exactly the two nav lines. That is no longer a habit, it is the standard.
- The lessons manifest in `STATE.md` had drifted — it stopped at `06-03` and never got 6.4 or 6.5.

## What this session predicts for 6.7

**6.7 — Normal Mapping and the TBN Derivation**, and it cannot avoid the thing 6.6 deferred:
**a texture has no colour space.** `texture` stores sRGB-encoded texels because `sample()` decodes
on read (3.9), which is right for a base colour map and wrong for every other kind. A normal map
read through an sRGB decode is wrong by the gamma curve everywhere except 0 and 1 — and it looks
*almost right*, which is the worst way to be wrong.

Three places the colour space could live and the decision must be made **once**, because both
normal maps and the deferred metallic-roughness map read through it: on the `texture` (a property
of the stored data, but a field on a type 6.5 argued should be pure data), on the `sampler` (which
is what hardware does — `texture.hpp` says so already — but contradicts 3.9's own insistence that
the FORMAT decides), or a second sample function (cheapest, and the one that gets called wrong).

The index's promise — "why your normal maps look lavender, and what that says about the encoding" —
**is** that question wearing a different hat: `(0.5, 0.5, 1.0)` encodes a flat normal, and whether
that 0.5 is linear or sRGB is exactly what the decision settles.

`asset_store.cpp` **whole** — all four of which 6.7 edits. Pin before writing a line, and take
