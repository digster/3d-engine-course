# 2026-08-07 — Docs: migrate 03-06 to the shared stylesheet

Not a lesson. A one-page fix to drift the tooling caught, done as its own change so it does not
ride along inside a lesson commit.

## What happened

The 2026-08-06 extraction moved the CSS and page script into `docs/shared/` and converted all 36
pages. `03-06-normals-and-lambert.html` was **not** among them, and it was not an oversight in the
run: the extraction branch was cut *before* 3.6 landed on `main`, so the page did not exist on that
branch and the merge had nothing to convert. Both changes were correct in isolation; the gap opened
between them.

So 3.6 shipped carrying an 881-line inline copy of a stylesheet that by then had one source of
truth — precisely the duplication the previous day's work removed.

## What found it

`apply-shared.py --check`, run before adding 3.7. It reported `would fix [CSS]` and
`would fix [SCRIPT]` for exactly one page. Running it without `--check` corrected both regions;
`docs/lessons/03-06-normals-and-lambert.html` lost **881 lines** and gained the same 10-line
link-plus-comment block every other page carries.

Verified over HTTP in real Chromium: `check-page.js` → `pass: true` (49 equations rendered,
highlighter round-trip clean, shared CSS in effect, no listing corrupted).

## The thing worth remembering

**This class of drift is invisible by construction.** A wrong or missing shared link does not
throw; the page renders unstyled and inert, which reads as an unfinished page rather than a broken
one. And it is introduced by *merging*, not by editing — no diff to the page shows anything wrong,
because nothing about the page changed.

The consequence for workflow: `apply-shared.py --check` is not only for when a page is added or
moved, which is what `docs/_template/README.md` said. **It also has to run after any merge that
brings pages in from a branch cut at a different time.** A tool whose whole job is catching a
silent failure is worth running on a schedule rather than on a trigger you have to remember.
