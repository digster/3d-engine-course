# 2026-08-07 — Docs: migrate 03-06 to the shared stylesheet

Not a lesson. A one-page fix to drift the tooling caught, done as its own change so it does not
ride along inside a lesson commit.

## What happened

The 2026-08-06 extraction moved the CSS and page script into `docs/shared/` and converted all 36
pages. `03-06-normals-and-lambert.html` was **not** among them, and it was not an oversight in the
run: the extraction branch was cut *before* 3.6 landed on `main`, so the page did not exist on that
branch and the merge had nothing to convert. Both changes were correct in isolation; the gap opened
between them.

So 3.6 shipped carrying an 881-line inline copy of a stylesheet that by then had one source of
truth — precisely the duplication the previous day's work removed.

## What found it

`apply-shared.py --check`, run before adding 3.7. It reported `would fix [CSS]` and
`would fix [SCRIPT]` for exactly one page. Running it without `--check` corrected both regions;
`docs/lessons/03-06-normals-and-lambert.html` lost **881 lines** and gained the same 10-line
link-plus-comment block every other page carries.

Verified over HTTP in real Chromium: `check-page.js` → `pass: true` (49 equations rendered,
highlighter round-trip clean, shared CSS in effect, no listing corrupted).

## The thing worth remembering

**This class of drift is invisible by construction.** A wrong or missing shared link does not
throw; the page renders unstyled and inert, which reads as an unfinished page rather than a broken
one. And it is introduced by *merging*, not by editing — no diff to the page shows anything wrong,
because nothing about the page changed.

The consequence for workflow: `apply-shared.py --check` is not only for when a page is added or
moved, which is what `docs/_template/README.md` said. **It also has to run after any merge that
brings pages in from a branch cut at a different time.** A tool whose whole job is catching a
silent failure is worth running on a schedule rather than on a trigger you have to remember.

## The thing I got wrong and had to re-derive

I wrote, in five places including a figure and its alt text, that Phong's cut-off happens because
**the mirror ray dips below the surface**. That is the standard explanation and it is false: `R`
is `l` mirrored about `n`, so `dot(n,R) == dot(n,l)` exactly and `R` is above the surface whenever
the light is. Always.

The truth is sharper. `cos^p` answers only over the hemisphere *around R*, which is not the
*visible* hemisphere; with the light `a` degrees off the normal the visible directions it misses
form a wedge exactly `a` degrees wide. So the trigger is **light and eye on the same side of the
normal** — on a floor, the sun behind you.

**Every measurement passed while the story was wrong**, because the numbers are equally consistent
with either explanation. What caught it was adding the control: rendering the sun-*ahead*
arrangement, where Phong covers all 30,806 pixels and there is no cut-off at all. `render_37` §6
now runs both on purpose.

## Three tests that passed while measuring the wrong thing

- **Per-vertex peak on the 48×24 torus** read 99.6% of the truth — it looked like a refutation.
  With 1,225 vertices some vertex almost always lands near the peak. The real defects are the
  **chord error between** vertices (0.722 of full strength at shininess 128, on 87.8% of the lit
  area) and **flicker** on coarse meshes (`cube.obj`: no highlight at all in 157 of 180 frames of
  a spin; icosahedron 107; 12×8 torus 58; 48×24 torus 0).
- **Grazing comparison on a torus** — a torus presents every incidence angle at once, so lowering
  the sun changes nothing. Needs a *plane*, where the incidence angle *is* the sun's elevation.
- **The `n·l` leak** — the first geometry parked the eye on the mirror ray and swept the light
  past the terminator, which drives `dot(n,h)` to −1 and returns 0 for an unrelated reason. The
  right setup is a fixed light and eye on opposite sides with the *normal* sweeping between them:
  0.608 of full strength on unlit geometry, over 400 of 701 unlit-but-visible normals.

## A figure can pass every check and still hide its claim

Figure 5 was a polar lobe on a linear radial scale. `check-page.js` said `pass: true`, nothing
overlapped, the geometry was exact — and the one thing it existed to show (Blinn at 0.063 where
Phong is 0) was a dot 15 px from the origin, indistinguishable from the dot for 0.004. Replaced
with a Cartesian value-vs-angle plot where 0.063 is 6% of the height. The lobe view stays in
Figure 1, where the question is the *shape* of the spray.

Two smaller ones the checker also could not see: the lobe was drawn **below the surface line** in
Figure 1 and in the widget (the function is defined down there; the surface is not), and the
widget's default exponent made *both* models read 0 in the cut-off region — refuting its own
caption if you dragged it. Default is now `p = 2`, and the caption says the difference between the
models is a *rough-surface* difference.

## The rasterizer did not change, for the third lesson running

`fill_style` gained no field, `fill_triangle` no branch. But the composed `view_from_model`
**is gone**: a highlight needs `eye - position`, so the two hops come apart and every vertex pays
a second matrix multiply. That optimisation existed *because* the shading was view-independent —
a fast path bought out by a feature, which is worth naming rather than absorbing.
