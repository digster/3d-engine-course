## The sentence the lesson turns on

**One source, three binaries, and SPIR-V in the middle.** Two stages, only the first a compiler:
HLSL→SPIR-V 12.3 ms, SPIR-V→{MSL,JSON} 1.5 ms each, four shaders 61.2 ms. Everything right of the
hub is a *translation from SPIR-V*, so losing the front end costs the whole toolchain, not one
backend — not hypothetical, since this machine's shadercross has no DXC and cannot read HLSL at all.

## The correction

LEARNINGS.md said shadercross "ships as 3.0.0-preview". Checked: header macros, pkgconfig and
upstream CMakeLists all say a plain **3.0.0**, and upstream has **no tags and no releases**. The
note was imprecise, and the rule it implied is impossible — `CMakeLists.txt` pins SDL to a tag with
the comment "never a branch name", and there is no tag here. Corrected in place: **pin a commit
SHA**.

## Three failures, opposite temperaments

- **Wrong register space:** compiles, translates, loads, runs, reads the wrong slot. Nothing
  objects. Correct mapping verified on our own output with `spirv-dis | grep DescriptorSet`:
  `space1`→set 1, `space2`→set 2, `space3`→set 3.
- **Wrong entry point: REFUSED at creation**, with a message. Our HLSL says `main`; the MSL says
  `main0`, because `main` is reserved in MSL.
- **Wrong resource counts: ACCEPTED, all of them** — including 99 samplers on a shader with one.
  SDL's FAQ names this as the commonest cause of a broken shader and nothing catches it.

**So the API checks the name and not the numbers**, and the two need opposite defences: get the
name right; never type the numbers. Hence reading them from the reflection JSON and *refusing to
load* when it is missing rather than defaulting to zero.

## The number that could not be true — and my own methodology error

`SDL_CreateGPUShader` measures **0.008 ms cold**, identical to the ninth call, against 61.2 ms of
build-time compilation. Eight microseconds cannot be MSL → machine code.

The first version of that measurement took the **minimum of eight runs** and reported 0.005 ms —
measuring the driver's cache by construction. Same error class as 4.2's flat-texture bandwidth,
caught by the same habit ("check that the number can be true"), fixed by reporting cold and repeat
side by side. Worth noting that the fix did *not* change the conclusion: cold is also 8 µs, so it
was never a cache — the compile simply is not happening there.

**The prediction is published in the lesson rather than resolved in it**, and 4.4's STATE entry
requires an answer either way: the compile happens at *pipeline* creation, because only there does
the driver know the formats, depth/blend state and vertex layout the code must be specialised to.

## Two things that cost time

- **`SDL_SetGPUShaderName` does not exist.** Buffers and textures have name setters; shaders are
  named with `SDL_PROP_GPU_SHADER_CREATE_NAME_STRING` at creation, because a shader is immutable
  the moment it exists. I wrote the call by pattern-matching and the compiler caught it — which is
  exactly the fabrication master prompt §10 forbids, avoided by luck rather than discipline. Check
  the header first.
- **A stale CSS cache nearly hid a real fix.** After adding `.reading a { overflow-wrap: anywhere }`
  the page still scrolled horizontally; the browser was serving the old stylesheet. Verified by
  re-linking with a cache-busting query, then confirmed on a fresh port. **When a CSS change appears
  not to work, prove the browser has the new file before changing anything else.**
