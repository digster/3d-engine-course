## The debt from 4.3, settled — after two wrong answers

**The compile happens at pipeline creation.** `SDL_CreateGPUShader` is ~0.031 ms in every run and
configuration; pipeline creation never is.

| what is created | cost |
|---|---|
| the first pipeline in a process | ~32 ms (one-time driver/compiler setup) |
| each new state permutation after it | **~2.4 ms** — the compile, ~80× a shader |
| a description compiled before, *including in a previous run* | 0.01–0.6 ms |

## The two wrong conclusions, and what caught them

I drew both, wrote both out in full with a figure, and shipped neither:

1. Timed one pipeline, then the same description again, and called the difference the compile.
   The second measurement is a cache hit.
2. Compared release (0.5 ms) with `debug = true` (33.5 ms) and concluded the **validation layer
   costs 66× the compile**. It does not — that run was simply the first time those shaders had
   ever been compiled on this machine. With a freshly-generated blend permutation in both
   configurations, validation costs almost nothing: 31.8 vs 34.5 ms.

**Metal caches compiled pipelines on disk**, so the cache outlives the process and every "second"
measurement is warm. What caught it: running the engine again and seeing **0.077 ms** where the
log had said 42.376. *A number that moves five hundredfold between runs of an unchanged binary is
not a property of the call.* The harness now varies blend state with a run-unique seed so that
"new" means new, and §A prints explicitly which of its findings are robust and which are variable.

This is 3.10's rule (numbers taken at different times) and 4.2's (check the number can be true)
arriving together, on a third module running.

## Three findings about what pipeline creation checks

- A colour target format the texture does not have: **created**, and the frame drew.
- An attribute at a location the shader never declared: **created**.
- No vertex layout while the shader has inputs: **REFUSED** — and the driver's message is exact.
- **A shader in the wrong slot is worse than an error.** Vertex-in-fragment is refused but leaves
  Metal's compiler service broken so the *next* creation crashes; fragment-in-vertex **segfaults**.
  Reproduced three times in an isolated one-trial program, then removed from the harness — a test
  that destabilises the process is not a test, and passing null for a required field is invalid
  input rather than a mistake anyone makes.

## The comparison Module 2 was for

Same triangle, `engine::fill_triangle` and the GPU, offscreen, compared per pixel:

| both | GPU only | ours only | interior disagreements |
|---|---|---|---|
| 20,808 | **0** | 102 (0.49%) | **0** |

Our coverage is a strict superset; every extra pixel is on one edge, one per row. **A fill rule,
not a bug** — hardware uses top-left, our 2.2 edge test uses `>= 0`. Figure 5 is drawn from the
actual comparison via a patch the harness dumps.

Also: coverage matched the geometry's area to **0.9922**, and the centroid read **85, 86, 85**
where a third of 255 is 85 — 2.4's barycentric interpolation, in silicon, to one code.

And winding: CCW 20,808 px, CW **0**, CW with `CULLMODE_NONE` 20,808 again — *identical*, which is
what makes it a two-minute diagnosis rather than a mystery.

## Two mistakes this session records

- **The first boundary-patch dump sampled a stretch where the two rasterizers agree exactly**, and
  produced a rectangle of solid agreement that argued nothing. Fixed by having the harness find the
  first actual disagreement and centre the patch there. A figure drawn from real data can still be
  drawn from the wrong real data.
- **A stale browser cache hid a working fix, again.** Identical to 4.3's: the page was rebuilt,
  `check-page.js` reported the same two defects, and the file on disk was already correct. Serving
  on a fresh port proved it. **Confirm the browser has the new file before changing anything else.**
