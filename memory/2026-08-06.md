# 2026-08-06 — Docs: extract the shared CSS/JS out of all 36 pages

Not a lesson. A structural change to `docs/`, requested after a feasibility question about why
the CSS was copied into every page.

## The question, and the answer that changed the plan

The duplication was **deliberate, not drift**: `CLAUDE.md` §7 required each lesson to be "one
fully self-contained `.html` file … no external assets", and `apply-shared.py` existed to keep the
36 copies identical (it reported zero drift when asked).

The measurement: **26.6 KB CSS + 8.0 KB script × 36 pages = 1.18 MB, 18% of the 6.7 MB tree.**

The premise turned out to be false. `file://` does **not** block a relative `<link
rel=stylesheet>` or a classic `<script src>` — the restriction people remember applies to
`fetch`/XHR/ES modules. Verified with a three-file fixture in **Chromium, Firefox and WebKit**,
including the upward `../shared/` traversal that lesson pages need. WebKit was the one that
mattered (Safari's engine, strictest `file://` policy) and it passed, so the single-copy layout
was safe and the per-directory fallback was not needed.

The user explicitly overrode §7 and accepted the cost.

**6.7 MB → 5.6 MB.**

KaTeX renders 0 equations in this sandbox — Chromium has no route to the CDN through the agent
proxy. Confirmed **identical on the pre-change baseline**, so it is environmental, not a

## Two things worth remembering

**The trade.** A lesson file is no longer portable alone — copied out of the tree it renders
unstyled. `docs/` is the unit now. And the failure mode inverted: duplication drifts *loudly*
(six highlighter versions by 1.2), whereas a wrong href fails **silently** — no error, just an
unstyled page that reads as unfinished. It breaks by *moving* a page, not editing one.

**The probe trap.** `styleSheets[…].cssRules` reports a good page as broken over `file://` in
WebKit, which treats every file as its own origin and throws `SecurityError` on CSSOM access. It
flagged all nine sample pages while `getComputedStyle` showed the shared `--bg: #fdfdfb` and
22,829 highlighted tokens on those same pages. Same shape as the old KaTeX trap: a probe that
cannot tell "absent" from "unreadable" is not a check. Judge by effect; treat a thrown CSSOM read
as inconclusive.

# 2026-08-06 — Lesson 3.6: Normals and Lambert's Cosine Law

## The two facts the lesson turns on

**Lambert is a footprint, not a formula.** A beam of fixed cross-section on a surface tilted by
θ covers `1/cos θ` more area, so power per unit area falls by `cos θ`. Nothing dims; the same
light covers more surface. At 60° the footprint is exactly 2.00 and the brightness exactly 0.50.

**A normal is not a direction — it is a relationship.** It is defined by being perpendicular to
every tangent, and it is that property which must survive a transform. Demanding
`dot(M·t, X·n) = 0` and using `a·b = aᵀb` forces `Mᵀ X = I`, so `X = (M⁻¹)ᵀ`. The generalisable
habit: when you do not know how something transforms, ask what *defines* it.

## The bug that only appears on objects nobody is looking at

The inverse transpose is **identical** to `M` for a rotation (`5.96e−08`) and **parallel** for a
uniform scale (`0.0000°`). It differs only under non-uniform scale — our icosahedron tilts by
`0.03°`, the slab by **67.99°**, the plinth by **66.46°**. On a squashed torus, **97.5% of
covered pixels differ**, worst channel delta 135/255, and the naive version looks like a
correctly lit *round* tube: it lights the shape the object had before the squash.

## The 3.5 payoff, measured

Flat vs per-vertex shading on `cube.obj`: **0 px differ** — bit-identical. On `torus.obj`: 5,576.
The reason is the index problem. A cube's 24 vertices each carry their own face's normal, so the
"per-vertex" normal at a corner *is* the face normal. **A faceted mesh is faceted because of the
split, not the shading model.**

## The rasterizer did not change

`fill_style` gained no field; `fill_triangle` gained no branch. Lighting produces a vertex colour
and interpolating those is 2.4's job — the vertex/fragment split arriving unbidden. The corollary
matters more: `fill_style` is now visibly the wrong home for shading parameters, and 3.7's
shininess and specular colour will not fit there. That is where the material system comes from.

## Three figures lied while check-page said `pass: true`

Figure 1 drawn at 30°, labelled 60°. Figure 2 shaded the wrong half unlit, put the terminator on
the wrong diagonal, and mislabelled a cosine 0.28 where the geometry gives 0.10. Figure 3 and the
widget disagreed with the worked example (one axis squashed vs two). All now generated from
computed coordinates — a script prints each point's normal, dot product and arrow endpoint, and
the SVG carries those numbers. The widget uses the slab's full `(1.8, 0.35, 0.9)`, so 0.35
reproduces 137.5°/90.0° and 0.90 makes the scale uniform and the problem vanish.

A clean rebuild also caught a `-Wmissing-field-initializers` warning in `floor_geometry::view()`
that the incremental build had hidden since `mesh` grew a fourth member in 3.5.
