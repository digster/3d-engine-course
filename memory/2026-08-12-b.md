## The sentence the lesson turns on

**A GPU is not a fast CPU — per lane it is slower, and it wins anyway.** Three structural reasons,
all measurable on the software rasterizer: it is wide rather than fast, its lanes run in lockstep,
and it shades in 2×2 quads.

## The measurements

- **Wide, not fast.** One dependent sqrt chain: 3.124 ns/step. Eight interleaved: 0.443 (7.05×).
  32: 0.112 (**27.88×**). Same arithmetic in every row. That is occupancy, and it is why fewer
  registers per shader means faster.
- **Divergence.** A warp runs every side any lane takes. Against a warp that never diverges:
  1.00× at 1024 px of coherence, 1.03× at 64, 1.52× at 16, **1.93×** at 8 and below — with the
  step falling exactly at the warp width of 32, which is what makes the model checkable rather
  than merely plausible.
- **Quads.** Lane efficiency by circumradius: 96.3% (64 px) → 78.5% (8 px) → **25.0%** (1 px). And
  by block width at r = 8: 2×2 75.5%, 4×4 48.7%, 8×8 30.4%, 16×16 8.9%. 2×2 is forced from both
  ends — smallest block that can produce a derivative, and every wider one wastes more.
- **The cost, on a real scene.** 87.4% efficient; the quad traversal is 1.04×–1.38× slower as
  tessellation rises 66 → 36,866 triangles, and **1/efficiency predicts every row to within
  0.09×**.
- **Bit-identical.** 0 of 230,400 px and 0 of 230,400 depths differ, over 2,306 triangles, while
  shading 21,005 lanes whose results go nowhere.

## Two findings that contradict the received wisdom

- **The usual justification for immutable pipeline objects is false.** "State is baked in so the
  inner loop need not branch on it" — hoisting our per-pixel branch on draw-constant state measured
  **0.93×**, i.e. nothing. A perfectly predicted branch is free. The real reason is driver
  *validation* and shader *compilation*, which SDL's own header states by calling pipelines
  "precalculated rendering state".
- **`fill_style` has 10 top-level fields; `SDL_GPUGraphicsPipelineCreateInfo` has 9** (53 expanded).
  Counted from the pinned headers. We did not approximate a pipeline object — we built one.

## The mistake this session records

Extracting the fragment into a lambda appeared to make the fill **10% faster** than 3.10's
published figure (46.46 → 40.46 ns/px). Measured properly — two binaries differing *only* by the
extraction, run alternately in one session — minimums say 2.5% faster and medians say 1% slower,
i.e. **no measurable difference**. The 10% was session drift, visible in the data as both columns
climbing as the machine warmed.

That broke Lesson 3.10's own pitfall ("never compare two numbers taken hours apart") **within a
day**, on the code that lesson was written about. 3.10's published numbers stand unchanged, and
the new rule is in conventions §7e: *a refactor's performance claim needs the same control as a
feature's.*

## Three harness defects worth remembering

- **A coherence knob that did nothing.** §E hashed the *element* index instead of the *run* index,
  so every row measured the same fully incoherent branch and the penalty was a flat 5×.
- **A benchmark the optimiser deleted.** `acc = acc*k + c` is an affine recurrence with a closed
  form; clang solved it and ran 4.2M steps in 0.001 ms. A `sqrt` chain cannot be folded.
- **`<em>` inside an SVG `<text>`.** HTML in foreign content makes the parser leave the SVG, and
  half of figure 3 rendered as page text. XML well-formedness checks pass — only a browser catches
  it.
