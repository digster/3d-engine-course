## The split, which is the lesson

3.6 shipped one enum holding two questions, and could not be extended. **Where the normal comes
from** is a property of the *mesh* (authoring and vertex splits); **where the equation is
evaluated** is a property of the *pipeline*. Their combinations are a grid, and a list cannot
represent a product. The tell was in 3.6's own doc comment — a comment explaining why a type
cannot express something is describing a type of the wrong shape.

## Three predictions the harness overturned

- **`face × gouraud` is not unconditionally degenerate.** With a face normal the normal is
  constant so all three evaluation points agree — *while the shading is view-independent*. 3.7
  ended that: the specular term reads `eye − position`, which varies across a face. Measured 761
  px (Gouraud) and 1,231 px (flat) against per-pixel with Blinn p=32. The corrected
  `is_degenerate()` is **shorter** than the wrong one.
- **Per-pixel does not fix `cube.obj`.** I planned "157 blank frames → 0". It went to 157. A cube
  has six normals; whether any points near the halfway vector is settled by geometry before
  shading begins. The 12×8 torus (smooth normals) went **58 → 0**. Per-pixel fixes an
  *interpolation* error and cannot invent a normal — which is the strongest possible argument for
  having separated the axes, since each fixes what the other cannot touch.
- **Per-pixel is CHEAPER than Gouraud below ~3 px/triangle.** 0.91× at 320×180, 1.41× at 640×360,
  1.84× at 720p, 2.12× at 1440p, 2.15× at 4K. Our torus is 2,304 triangles over 6,346 covered
  pixels, so there are more vertices than pixels and the folklore inverts. Quote the asymptote
  (2.15×), and never quote a shading cost without the px/triangle ratio.

## The figure that refuted its own caption

Figure 4, "continuous but not smooth": correct geometry, `check-page.js` green, and the Gouraud
chord hugged the true curve so closely it appeared to show the two were *the same*. The content
was in the **derivative**. A second panel plotting the slope of each made it immediate — smooth
curve versus staircase. Second lesson running where a figure passed every automated check while
burying its claim (3.7's Figure 5 hid a tail on a linear radial scale).

The rule that has emerged: state the figure's one claim as a sentence, then ask whether a reader
could extract *that sentence* by measuring the picture. If the claim is about a rate of change,
plot the rate of change.

Related, same lesson: my first drafts put long explanatory prose *inside* the SVGs, which
overran nine viewBoxes. Prose belongs in the `<figcaption>`; only short labels belong in the
figure.

## The dependency this lesson adds on purpose

`raster.hpp` now includes `light.hpp`, and `shading::lit` calls `shade()` per fragment. A real
layering violation. The clean fix is a caller-supplied fragment function — which *is* a fragment
shader, so building it here means inventing Module 4's answer three lessons early. 2.4's header
called the enum "a placeholder for a fragment shader" when it was written; this is where the
placeholder started costing something. Fixed-function hardware made the same trade and lost the
same way.

Also cheated on purpose: the material rides on `raster_triangle` and is rebound per triangle. A
GPU cannot do that — material parameters are pipeline state, so real renderers batch by material.
Taken because splitting the single pass would break the painter's-algorithm comparison running
since 3.1. Third time this pressure has appeared from a new direction (3.4 cull modes, 3.7
specular, now this).
