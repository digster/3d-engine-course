## Three unexpected results, all survived a correction

1. **SoA's full-transform win is VECTORISATION, not cache.** Identical at 384 B and 9.6 MB;
   **1.00× at every size** with `-fno-vectorize`. The cull win *is* the cache (0.97× below the
   knee, 0.37× above, scalar). ⇒ The rule is not "use SoA": **split the data a loop does not read
   away from the data it does; the prize is the fraction you leave behind.**
2. **Polymorphic ≈ monomorphic virtual** (within 4% at every N) ⇒ not misprediction. Flat across
   N ⇒ not the vtable load. **It is the inlining it prevents.**
3. **The fragmentation the benchmark arranged is not controllable.** 24-byte spacers between
   96-byte objects → different size class → 497/499 adjacent; matching sizes moved
   ptr_ordered@100k from 1.09× to **1.98×** and looked like the fix. It is not: the *same code*
   gives 0 adjacent in the `-O2` benchmark at every n, 99,411/99,999 in the `-fno-vectorize` one,
   0 in a standalone probe at n=100k and 485/499 at n=500. **Adjacency is a property of the
   PROCESS.** Resolution is a protocol — `bench_56` reports its own layout per n, `measure_56.py`
   flags contiguous builds, `verify_56` asserts only the spacer count. The `-O2` table is sound
   throughout; from the scalar table only `soa`/`flat` are quoted.

## What the lesson concluded — including "no"

- **Does NOT justify changing the renderer.** Four objects, 384 bytes, ~6 ns of transform work
  per frame. A measurement lesson has to be willing to conclude no.
- **Does justify three ECS constraints**, each with a number: dense + **compactable** (6.47×
  from the decayed tree), a system **declares which components it touches** (12/96 buys 5×,
  60/96 buys nothing), iteration **must not be virtual** (flat 1.5–1.7×, so it applies at n=4 too).
- **Does NOT settle archetype vs sparse set.** Both are dense, contiguous, subset-capable.
  That is 5.7's argument and must not inherit these numbers.

## Traps worth remembering

- **Three ways a microbenchmark lies**, all hit here: timer coarser than the work (`0.0000
  ns/item`; 24 MHz ⇒ 41.67 ns/tick); the compiler deleted the loop (0.166 ns for four matrix
  builds = 2.3 cycles for 9 mults + 16 stores — *not physically possible*); the accumulator was
  the bottleneck (`hits += 1.0`, ~4-cycle serial chain). **All three found by arithmetic, not
  suspicion.**
- **A number whose provenance you cannot state is a number you should not publish.** The
  benchmark now prints where its own objects landed before it prints a timing.
- **Dead-code elimination is asymmetric across arms of different inlinability.** Reading 5 of 16
  matrix entries let the inlined arms skip work the virtual arm could not. `virtual` read 3.4×;
  reading all 16 it reads 1.7×.
- **Alternation introduces cache interference.** The same flat arm read 0.98 and 1.83 ns/item in
  different pairings. Quote **ratios within a pairing**, never cross-pairing absolutes.
- **Do not assert a property of the data as a property of the design.** "At least one reordering
  arm is not bit-identical" failed at n=2000 — all three landed on the same bits. Replaced with
  `(a+b)-a != (a-a)+b` at 1e16.
- **Figure numbering by authoring order, again** (5.3's trap): `fig_chain` is authored last and
  appears third. Numbered by PAGE order now, with the section in a comment.
- **The visual pass caught a label sitting on two shapes** — `svgTextOnShape` only checks
  lines/polylines. Fourth session running that `shot-figs.mjs` earns its keep.
