## The framing, which the probe decided

**The engine had no HDR bug — it was avoiding the question by construction.** Two choices held the
lid on: `k_reference_irradiance` = π (6.2, so a white surface renders at exactly 1.0) and the demo's
roughness of 0.49, which peaks at **0.8676** — just under. Change the second and the *same* shading
equation returns 11.59 at roughness 0.20 and **55,917** for a polished metal, all stored as code 255.

That framing is better than "look at all this clipping" and it came from the probe, not from a plan.

## Traps found

- **A monotonic relationship coming out backwards means the measurement is missing its target.**
  `probe_612.cpp` v1 swept the eye through a plane and found *sharper* surfaces peaking *lower* —
  the sweep never crossed the mirror direction. Same trap in the demo: a flat-faced scene at
  roughness 0.15 reports **zero** pixels over the lid. Fixed by adding a torus, curved in both
  directions, so some point satisfies the mirror condition from every viewpoint.
- **I got the Reinhard white figure wrong in a doc comment** — claimed ~768, the answer is **224**.
  Inverted the 254.5/255 threshold in the wrong space. Module 6's recurring mistake, committed in
  the module about it, caught because the harness measured rather than repeated it.
- **Figure numbers drifted out of page order again** (the resolve at 4, per-channel at 5, body
  showing the reverse). Added a **`figOrder` check to `check-page.js`** — and sweeping every lesson
  page with it found the same defect in **three published lessons**: 02-05-matrices,
  03-10-profiling-capstone, 04-01-how-gpus-work. Not fixed here (out of scope, and the fix must

## The framing, which the probe decided again

**6.12 stopped bright values being destroyed by the fragment shader; it did not make them visible.**
Bisecting the engine's own `to_encoded`, the lid only *moved*: ACES saturates at **6.3774**, so the
polished metal still spends **13.10 stops** on one code. And no curve can do better, because an
8-bit sRGB display holds **11.69 stops, total**.

The best line in the lesson came out of that table rather than from a plan: **reinhard has the
*highest* lid (223.5) and is the operator everyone agrees looks worst** — because it spends its
codes creeping toward a white it never reaches. Tonemapping is not the removal of clipping, it is
the choice of where to clip.

## Measured

| claim | number |
|---|---|
| ACES's lid, bisected / solved by hand | **6.3774** / 6.3773 |
| the display's entire budget | **11.69 stops** |
| pyramid tail, log-log slope at r = 16 | **−2.01** |
| over the octave 32→64: pyramid vs a σ=16 Gaussian | **6.0×** vs **403×** |
| glow area / L over three decades | 1.150, 1.238, 1.140 — **±8.6%** |
| one firefly's share of the bloom's energy | **62.8%** of 132,074 |

| the whole bloom's cost | **0.666** of one full-screen pass |
| the pyramid's memory | 0.3330 of a target — the mip ⅓ again |
| the demo: pixels over the lid → pixels changed | **69 → 64,015** |

## Two findings worth carrying

**A GPU result constant across a parameter sweep means the parameter is not reaching the code.**
The bloom composited as exactly zero at every intensity from 0.05 to 50. The pyramid was *perfect*
— reading level 0 back as half floats gave exactly 8.0, the derived value — so the fault was in the
composite. The cause was not in the shader at all: `engine_use_shaders()` copied shaders with
`add_custom_command(TARGET x POST_BUILD ...)`, and **a POST_BUILD command runs only when its target
is rebuilt**. Editing only a shader recompiles it and gives no demo any reason to relink, so the
copy never fires and every program keeps the shader it was last linked beside. Live since Module 4;
hidden because nobody had ever edited a shader without also touching C++ in the same build. The
diagnostic that found it: the deployed `.msl` was a *different size* from the canonical one.

**The one-tap downsample and per-texel firefly suppression are mutually exclusive**, and that is
the real reason shipping engines use Karis's 13-tap kernel. The free 2×2 box average happens
*inside* the bilinear fetch, so by the time the shader sees a number the four texels are gone.
Measured the gap by pre-clamping the source buffer: 0.30% against 1.19%. Not "a wider kernel" —
**the only shape that can see what it is averaging.**
